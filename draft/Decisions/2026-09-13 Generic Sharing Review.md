# ジェネリック共有仕様の決定記録

2026-09-13 改訂。[優先仕様](../Design/2026-09-13%20Generic%20Sharing%20and%20Specialization.md)を正本とする。本記録は提案の採否と理由をまとめたもので、重複する旧説明は統合した。対象範囲では優先仕様がSPEC.mdと先行文書に優先する。この作業ではSPEC.md本体とコンパイラー実装を変更していない。

## 1. 今回の提案の採否

| 提案 | 判断と反映内容 |
| --- | --- |
| A：入口ABIを呼び出しの種類で決める | 採用。具体署名の直接入口、宣言署名の共有入口、Function Typeの入口を区別し、予算は入口内部を変更する。再帰SCCの一括特殊化とcaller接続の巻き戻しを廃止（仕様§3、§8.1） |
| A：Fixedなら必ず具体ABI | 条件を補正。entryがFixedでも部分固定後の署名の表現が未確定なら共有ABIが必要。具体scalar入口は予算0でも使えるが、その内部の領域化・転送までなくなる保証ではない |
| B：entryと専用contextを一緒に生成する | 採用。callerとの契約を生成方式と入口ABIに限定し、callee内部schemaを照合対象から外す。最適化前のschema固定、schemaだけのadapterを削除（§3.2、§4.3） |
| B：期待ABIを削除する | runtimeのslot別tagや独立したschema照合は不要。ただし間接callには引数・結果・所有権・属性を含む型付きABIが必要であり、この情報まで削除しない |
| C：整数slotとentry／context pairに統一する | 採用。body用のsize・alignment・offset・長さを直接供給し、witnessとFrameLayoutはコンパイル時の計画にする。callee内部の情報は平坦化しない（§4） |
| C：破棄もpair、固定配列のNを明記する | 採用。{destroyValues, metadata}のmetadataを既存の破棄ABIのcontext引数として扱い、二重に渡さない。配列TypeContextはelementMetadataとNを持つ（§6.3） |
| C：整数slotをisizeに限定する | 補正。配置値は非負isizeだが、完全幅のu64型identityは縮められない。整数slotを共通の64-bit格納とし、符号・用途は型付き計画で決める。slotの物理種別を増やさず、型identityを読むためだけのhelper callも不要にする（§4.1–4.2） |
| C：load削減がそのまま性能向上になる | load経路の短縮は採用。平坦化によるcontext bytes増加、操作内部のload、register圧力があるため、実行性能の保証はしない（§4.1、§9） |
| D：閉じた代入ごとの正確な容量にする | 採用。bucketとクラス内最大容量を廃止し、選んだbodyに必要な容量をalignmentで丸める。無関係なinstance追加による容量変更を避ける（§5） |
| D：ABI・容量・alignment・bodyだけで入口を統合する | 条件不足のため補正。同じbodyを呼んでも異なるcontext定数や適応処理を埋め込めば別の入口が必要。埋め込む全事実を含む既存のキー規則へ統一 |
| D：容量0なら入口＝body | 無条件には不採用。確保は省けるが、scalar返却と結果領域返却等のABI差があればadapterは必要。接続も一致する場合だけ入口を省略 |
| E：クラス全メンバーのbody割当を排他的に選ぶ | 採用。各選択肢を基準クラスとの差で一度だけ見積もり、採用後の別選択肢への変更を行わない。共有版は全用途がなくなる場合だけ差し引く（§8.2–8.3） |
| E：入口・adapter・contextを予算から外す | 定型のABI適応・固定確保・データに限って採用。本体を入口やhelperへ移せば無償になる抜け道を防ぎ、本体由来の複製・展開は費用へ含める。件数だけでなく命令数・bytesも資源管理する |
| E：A・Bだけでクラス間の再評価がなくなる | 補正。生成物の重複排除や他クラスのbody取り込みはなお相互作用を生む。選択中は安定した入口経由とし、クラス間重複排除の削減は会計へ還元しない |
| E：優先度キューで全体がO(n log n) | 無条件の計算量保証は不採用。費用を固定しクラスを一度だけ選べば再評価・キュー更新は不要。有限のn個の選択肢のsort・選択はO(n log n)にできるが、候補構築・割当評価・接続検証の費用と探索上限は別 |
| 規範・実装指針・将来導入時を分ける | 採用。キー、会計方式、intern、循環登録、hash比較は第II部へ移した。未導入object cacheのCode Cache Keyと永続contextグラフ形式は削除（§8、§10） |
| 固定事実へ命令・属性の前提を含める | 採用。sizeの一致ではalign・dereferenceable・noalias等を証明できない。動的な値をLLVMの定数属性へ直接使う案は採らず、証明済み定数か弱い共通保証を使う（§2.2） |
| 小さな入口の融合と、既知サイズ領域のbody配置 | 採用。alwaysinlineを一律指定せず、scratchの寿命、loopのstack使用、最終frame量を確認する。先頭領域offsetの0固定も行う（§5、§9） |

## 2. 会計を局所化する理由と限界

入口ABIと不透明なcallee contextだけでは、コード量の相互作用までは消えない。例えば二つのクラスが同じhelperを生成する場合、先に採用されたクラスだけへ費用を負担させると後続候補の費用が変わる。

初期実装では、各クラスの選択肢を必要なhelper込みで独立に見積もる。クラス間の重複排除は出力時に行うが、得られた削減を予算へ戻さない。共通helperの帰属変更や全体再評価をなくす代わりに、重複排除を見込めば採用できた候補を見送る場合がある。基準量も同じ会計を使い、実際のbinary増加率とは区別する。

一つのクラスから一つの割当だけを採用する方式は、貪欲法の最適性を保証しない。少数の有効な選択肢を安価に比較する方針を優先し、候補構築と全メンバーの割当量にも有限の上限を設ける。

## 3. 先行レビューから維持する決定

| 論点 | 現行の共通規則 |
| --- | --- |
| R1：特殊化の取消し | 入口契約を維持。旧「全scalarもpointer」「schemaを事前固定」「caller群を戻す」は今回のA・Bで置き換えた |
| R2：循環context | 有限の有向グラフを許し、node登録と参照解決を分離。永続保存形式は今回の対象から外した |
| R3：容量差で大型bodyが分離する | 小さな入口と共有bodyを分離。旧bucketとFrameLayout runtime recordはC・Dで置き換えた |
| R4：部分固定の相関 | 検証済み代入計画から導出し、実際に埋め込む全前提を固定事実として照合 |
| R5：scalarのFixedで予算を迂回する | 型付きhelperで共有できる大型bodyの複製は任意。具体呼び出しのscalar入口ABI自体は今回Aにより基準へ移した |
| R6：利益推定と取消しの費用 | 簡約後の利益、有限探索、不変の基準を維持。依存束・全体再評価の会計は今回Eで置き換えた |
| 命令数と二つの上限 | 元関数別と生成単位全体の増加枠、利用者向け倍率一つを維持。生成資源上限は別 |
| 小さい特殊化の無償扱い | 共有版100命令が残り60命令を足せば追加60。全用途置換で60だけになれば増加0。将来のLLVMインライン化は削減の証拠にしない |
| 内部ABIと外部契約 | 内部生成方式は単一。方式内のABI適応は維持し、OS入口・FFI・外部helperをすべてinternalとは仮定しない |
| 意味計画cache | 証明と依存を検証して再利用し、使用時Loanは再検証。ABI・context・機械語は生成単位ごとに作り直す |
| 最適化構文 | 今回は追加しない。明示specialize funcは実装選択。局所的問題と全体倍率の副作用を実測した場合だけヒントを再検討 |

長さの型形成と通常算術、完全初期化範囲の逆順破棄、ゼロサイズの論理状態、scratchの非escape、固定frameのprobe・unwindは維持する。動的格納とobject cacheは導入時に規則を定める。

## 4. 検証範囲

今回の作業は文書の整合性確認である。仕様の確認項目・計測対象は優先仕様§9に集約した。リンク、節参照、Markdown構造、差分の空白エラーを確認し、実行テスト・NativeAOTテスト・性能測定は行わない。

LLVM属性の条件は[公式LangRef](https://releases.llvm.org/22.1.0/docs/LangRef.html#parameter-attributes)に照合した。性能上の利点は生成物と実測で検証する設計上の見込みであり、実装済みの成果として扱わない。
