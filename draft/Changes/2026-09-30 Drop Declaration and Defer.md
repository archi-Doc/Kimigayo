# Design Change: drop 宣言への改名と defer の維持

日付: 2026-09-30

状態: 採用。正式仕様・実装への反映は未実施。

本書は合意した変更を記録する。今回の作業は本書の作成のみとし、正式な必須挙動は `docs/SPEC.md` とその参照先を正とする。

## Current Specification — 現在の仕様

- `init` は初期化、`deinit` は構造体の破棄に伴う処理を定義する専用宣言である。`deinit` の通常終了後、フィールドと基底の自動破棄が続く。
- `deinit` の宣言には Copy・部分 Move・破棄時の寿命・特殊な `self` などの制約があるが、詳細は §3.5.1・§15.1.3・§15.6.6・§16.3 に分散している。
- `defer` は到達時に終了処理を登録し、直接囲む実行スコープの退出時に実行する。登録時には本体を評価せず、クロージャー値を作らず、参照するローカル変数を Copy・Move しない。登録だけを理由に参照対象すべてを借用せず、実行時の状態と各退出経路で安全性を検査する。

## Proposed Specification — 新しい仕様

`init` と `defer` を維持し、破棄宣言のキーワードを `deinit` から `drop` に変更する。旧表記を破棄宣言の別名として残さない。名称以外の構文・意味・制約・破棄順序は維持する。

`drop` は手動で呼べる解放関数ではなく、値の破棄に伴う処理を定義する専用宣言である。空の本体もユーザー定義の破棄宣言として扱う。

§16.3 の冒頭に「宣言に伴う制約」の一覧と短い理由を置き、次の詳細規則へリンクする。これは既存規則の要約であり、新たな制約や緩和を導入しない。

| 制約・保証 | 短い理由 | 詳細規則 |
| --- | --- | --- |
| ユーザー定義の `drop` を持つ型は Copy にできない。値全体の Move は可能。 | 暗黙のコピーで破棄責任を複製せず、移転は許す。 | [§3.5.1](../../docs/spec/03-types-and-values.md#351-copy-capability-and-explicit-duplication) |
| 部分 Move 自体は禁止しないが、全体使用や当該 `drop` に到達するすべての経路で完全性を復元する。 | 破棄本体が欠けたフィールドを観測しないようにする。 | [§15.1.3](../../docs/spec/15-ownership-and-lifetime-analysis.md#1513-move-paths-and-partial-move)、[§16.3.2](../../docs/spec/16-scope-exit-and-destruction.md#1632-field-cleanup) |
| ユーザー定義の `drop` は到達可能な全 Origin を観測すると扱う。観測時の Origin・Loan の有効性を要求し、フィールド破棄にも再帰的に検査する。 | 破棄中の参照を有効に保ち、本体の未使用箇所に依存して利用側の条件を変えない。 | [§15.6.6](../../docs/spec/15-ownership-and-lifetime-analysis.md#1566-destruction-lifetime-checking) |
| `self` 全体の Copy・Move・代入・exchange・swap、通常の `uniq/Self` としての受け渡し、逃避を認めない。フィールド操作と全体の共有借用には通常の規則を適用する。 | 破棄中の値の移転・置換・逃避で破棄責任や後続処理を崩さない。 | [§16.3.1](../../docs/spec/16-scope-exit-and-destruction.md#1631-special-receiver) |
| 構造体直下にのみ宣言でき、選択・統合後は各具体的構造体に最大一つ。引数・ジェネリクス・Origin スキーマ・結果注釈・修飾子を持たない。明示呼び出し・間接呼び出し・関数値の取得は禁止。 | 破棄機構が一意の入口と責任を管理する。 | [§16.3](../../docs/spec/16-scope-exit-and-destruction.md#163-aggregate-destruction-and-deinit)、[§16.3.1](../../docs/spec/16-scope-exit-and-destruction.md#1631-special-receiver) |
| 本体の通常終了後、フィールドと基底の自動破棄が続く。`return` では省略できない。 | 本体と構成要素の破棄を合わせて責任を完了する。 | [§16.3.2](../../docs/spec/16-scope-exit-and-destruction.md#1632-field-cleanup) |

空の `drop => ()` でも Copy・部分 Move・Origin 観測の制約は同じである。構築未完了の層は自身の `drop` を実行せず、残る初期化済み要素を破棄する。構築完了後の部分 Move による不完全性とは区別する。

上記リンクは本書作成時の正式仕様を指す。正式反映時には改名後の節名・アンカーに整合させる。

## Changes — 変更点

- 破棄宣言を `deinit` から `drop` に統一する。`init` は変更しない。
- `defer` の名前と現在の意味を維持し、`finally` への改名およびクロージャーのキャプチャに基づく方式への変更は採用しない。
- §16.3 冒頭に制約・理由・詳細リンクを集約する。
- 制約の緩和は採用しない。破棄時に観測しない Origin の契約や、安全な補助メソッド呼び出しの契約は検討案にとどまり、今回の決定には含めない。

## Rationale — 変更する理由

`defer` と `deinit` は見た目が似ている。`drop` への改名は `init` との語形の対称性を失う一方、用途の異なる二つの構文を判別しやすくする。

`defer` は処理を「後回しにする」という現仕様に適合する。`finally` は終了時の処理を連想させるが、到達時の登録という性質を表しにくい。現在の方式は、終了処理と両立する途中の変更・借用を許せるため維持する。解析・診断の実装負担はあるが、クロージャーを使わないことだけで性能優位を主張しない。

`drop` の特殊性は専用宣言と公開された制約で示す。制約を一か所から把握できるようにし、One Concept, One Canonical Form・Local Reasoning・Explicit Semantics を支える。安全性の必須条件と、それを保守的に保証する現行規則は区別しつつ、今回はどちらも変更しない。

- `docs/SPEC.md` の参照先である第16章の §16.3 を改名し、冒頭に制約一覧を追加する。索引に関連記載がある場合も整合させる。
- §2 の予約語・専用形式、§3・§6・§7・§8・§15–17 などの関連規則、付録の用語・文法、コード例にある破棄宣言の名称と参照アンカーを更新する。
- 各詳細規則を正とし、一覧による重複定義や意味の変更を避ける。正式仕様への反映は英語で行う。
- 後続の実装作業では字句・構文解析、AST 表示、診断、ライブラリ、テスト、milestones、関連ツール・文書を整合させる。実装・検証前に対応済みとは記載しない。既存の draft 文書には変更を逆伝播させない。

## Decision — 最終決定

**`init` / `drop` / `defer` を採用する。** `deinit` を `drop` に改名し、旧表記の別名は残さない。§16.3 冒頭に既存の制約一覧・短い理由・詳細リンクを追加する。破棄と `defer` の意味、および既存の制約は維持する。

今回は本 Design Change の保存のみを行う。正式仕様・実装・既存例の変更と検証は、後続の指示で実施する。
