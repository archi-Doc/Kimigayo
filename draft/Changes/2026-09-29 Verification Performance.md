# Design Change：verify の高速化

日付: 2026-09-29

状態: 方針決定済み。Release 標準化は実装済み（`7035485d`）。その他は未実装・正式仕様への取り込み前。

## 1. Current Specification — 現在の仕様

- `verify.ps1` は Unit／Session とも Release を標準とし、`-Configuration Debug` で Debug を指定する。
- Milestone は元ソースに加え、名前・式・値などを変更したソースと、不正化したソースを生成する。
- 成功ケースは `build` 後に、exe 直接実行、`kimi run <exe>`、`kimi run <source/project>` の3経路で実行する。最後の経路では再ビルドが発生する。
- ネイティブビルドごとに LLVM のバージョン・実行ファイルのハッシュ・採用済みバックエンドとの一致を検査し、`kernel32.lib` を生成・検査する。
- Milestone は既に最大8並列で実行する。主な削減対象は、並列数ではなく重複する処理である。

## 2. Proposed Specification — 新しい仕様

### 2.1. コンパイラ構成

- Unit／Session とも Release の1構成だけをビルド・テストする。
- Debug は `-Configuration Debug` による明示指定とする。ビルド、テスト、fixture、Milestone に同じ構成を使う。
- 非増分ビルドと警告のエラー扱いは維持する。
- コンパイラ自身の構成と、生成プログラムの O0／O2 は独立した選択である。

### 2.2. Toolchain の検証

| 場面 | Toolchain の同一性検証 |
| --- | --- |
| 通常の `build`／`run`、`verify.ps1` | 実施しない |
| Toolchain のセットアップ・更新 | 実施する |
| 明示的な検証 | 実施する |

- 明示検証の入口を `kimi toolchain verify` に集約する。選択した Toolchain の LLVM バージョン、実行ファイルのハッシュ、採用済みバックエンドとの一致などを検証する。
- `verify.ps1 -VerifyToolchain` は、開始時にこの検証を一度だけ行う。失敗時は後続処理へ進まない。各ケースでの再検証は行わない。
- 通常ビルドでは `--version` 呼び出し、ツール実行ファイルのハッシュ計算、コンパイラ管理バックエンドの採用同一性検査を省く。Toolchain を明示的に変更した場合も、自動検証は行わない。
- ツールの欠落・起動失敗・処理失敗はビルドエラーにする。生成 IR の検証、マニフェストの整合性、ユーザー指定ネイティブライブラリのハッシュ制約など、個々のビルド入力・生成物の検査は維持する。
- 通常の記録には「今回の Toolchain 検証は未実施」と記載し、検証成功を捏造しない。省略自体の警告は出さない。明示検証の結果と、コンパイル・実行の成否を区別する。
- `reportedVersionsMatched`／`unverifiedToolchain` とハーネスの合否条件を新しい契約に合わせる。既存の `AllowUnpinnedToolchain` の扱いも整理し、通常ビルドの検査省略に追加の解除指定を要求しない。

### 2.3. kernel32 import library

- `kernel32.lib` は Toolchain のセットアップ・更新時に生成・検査し、Toolchain 配下の共通成果物として配置する。
- 通常ビルドはこの成果物をリンクし、プロジェクトごと・最適化レベルごとの生成と再検査を行わない。
- 定義、対象アーキテクチャ、生成ツールなどの生成条件を記録する。条件変更時はセットアップ・更新で再生成し、明示検証でも整合性を確認する。
- 成果物が存在しない場合はセットアップを促すエラーにする。通常ビルドで暗黙に再生成しない。

### 2.4. Milestone の対象と実行経路

- **対象はチェックインされた元の Milestone プログラムのみとし、ソース変種を削除する。** 名前変更、式・値の変更、不正化などの変種生成をハーネスから外す。必要な機能・拒否診断の保証は専用の機能テストで担う。
- **O0／O2 の両方を維持する。** 実行可能な各プログラムを各レベルで1回ビルドし、生成 exe を直接1回実行する。元ソース用の追加 O2 実行も重ねない。
- 作業用コピーが必要な場合はソースの内容とファイル名を維持し、O0／O2 の出力を別ディレクトリに置く。コピー自体を追加の検証ケースにはしない。
- **Milestone の実行経路は exe 直接実行の1種類に統合する。** 標準出力、標準エラー、終了コードを確認する。
- `run-exe`／`run-input` の契約は専用の CLI テストで検証する。ソース／プロジェクト／exe 入力、正常・異常終了、出力転送、自動ビルドの成功・失敗を代表ケースで確認し、Milestone との掛け合わせをなくす。
- ビルド済み成果物を CLI 経由で実行する場面では、既存の **`run --no-build` を使用する**。自動ビルド自体を確認する専用ケースのみ通常の `run` を使う。Milestone に第二の実行経路を追加する意味ではない。

## 3. Changes — 変更点

| 項目 | 従来 | 決定 |
| --- | --- | --- |
| コンパイラ構成 | Unit は Debug、Session は Debug／Release | Release 標準、Debug 明示指定（実装済み） |
| Toolchain 検証 | ビルドごと | セットアップ・更新時と明示実行時 |
| `kernel32.lib` | ビルドごとに生成・検査 | セットアップ時の成果物を共用 |
| Milestone ソース | 元ソースと各種変種 | 元ソースのみ |
| Milestone 実行経路 | 3種類 | exe 直接実行のみ |
| 生成コードの最適化 | O0／O2 | 両方を維持 |
| ビルド後の CLI 実行 | `run` で再ビルド | `run --no-build` |

## 4. Rationale — 変更する理由

Toolchain の導入・整合性確認、言語機能の検証、CLI の動作確認、Milestone の統合検証をそれぞれの責務に分ける。同じ固定入力の検査や、独立した項目の掛け合わせを削減する。

Milestone の成功系は、各プログラムについて **2ビルド・2実行（O0／O2）** になる。変種や Toolchain 改変の検出を通常の Milestone 検証で保証するものではなく、対応する専用テスト・明示検証の結果を別途記録する。

## 5. Impact on SPEC.md — 仕様と実装への影響

- `docs/impl/20-compilation-configuration.md` の §20.8.3、§20.8.5、§20.8.8 と関連記述を更新する。毎回の Toolchain 検証とプロジェクト別 kernel32 生成の要求を改める。
- `NativeToolchain`、CLI、セットアップ・明示検証処理、ビルド記録を更新する。
- `milestone-harness.ps1` と個別ハーネスを元ソースの O0／O2 直接実行に揃える。変種・拒否ケースの保証を専用テストへ整理し、CLI テストの必要な経路を確認する。
- `verify.ps1`、`AGENTS.md`、README、開発計画の手順を揃える。過去の検証記録は書き換えず、今後の証跡に対象ソース、構成、最適化、実行経路、Toolchain 検証の実施有無を記録する。

## 6. Decision — 最終決定

上記を採用する。本書の作成時点では、Release 標準化以外の実装・正式仕様は変更しない。

実装時は工程別の所要時間を記録し、代表的な Milestone で変更前後を比較する。削減率は実測後に報告する。常駐コンパイラ、増分ビルド、並列数の増加、NativeAOT は今回の変更対象に含めない。
