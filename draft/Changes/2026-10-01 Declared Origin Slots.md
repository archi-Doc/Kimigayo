# 仕様変更案：Originスロットのヘッダー宣言

日付：2026-10-01（2026-10-02 最終版）

状態：最終版。採用決定済み。正式仕様への取り込みと実装は未実施。

本書で変更する事項は、SPEC とその参照先より優先する。本書で変更しない事項には、既存仕様を適用する。SPEC の節は「SPEC §n」、実装仕様の節は「impl §n」、本書の節は「本書 n」と表記する。

## 1. 現仕様の問題

### 1.1. private な格納注釈が公開スロットを決める

ヘッダーのない struct・enum は、格納宣言（instance Field、enum payload、基底型）に書いた Origin 名から、自前スロットを一つ推論する（SPEC §15.3.2）。公開型のスロット名は、元の Field が private であっても API である（SPEC §15.3.7）。

```kimi
public struct View<T>
    private let data: ref/T during source   // 推論されるスロット：source

// 利用側
func forward<T>(value: View<T>) -> View<T>{result}
    origin result.source == value.source
    return value
```

この状態では、次のような private な変更が、型宣言を変えないまま公開スロットを変える。

- **改名：** `data` の注釈を `during buffer` に変えるだけで、スロット名が `buffer` に変わり、利用側の `value.source` がエラーになる。
- **追加：** `owner/T` だった Field を借用に変えると、スロットが一つ増える。

推論の結果は公開契約として扱われるので、推論そのものは健全である。問題は、公開契約を導入する位置が private な格納宣言に隠れていて、型宣言だけではスロットの名前も個数も分からないことにある（原則 2、3）。

### 1.2. 書き方と意味が一対一に対応しない

「自前スロットなし」は、ヘッダーなし（推論の候補がない場合）と `{}` の二通りに書ける。逆に、ヘッダーなしの意味は、格納内容によって「スロットなし」にも「スロット一つ」にもなる（原則 1）。

推論を残すために、次の補助規則も必要になっている。

- 推論の候補が二つあれば、型全体を拒否する（SPEC §15.3.2）。
- ヘッダーのない型では、外側の Origin と同名の名前を拒否する（SPEC §15.3.2）。
- 外側の Origin を参照する型と、分割 struct の断片には、`{}` を要求する（SPEC §15.3.2、§6.1.2）。
- 空の波括弧を、型宣言のヘッダーにだけ許す（SPEC §1.2、§2.4、§15.3.1、付録 F.2）。

### 1.3. 診断が原因の位置に出ない

2026-10-01 時点の実装で観察した結果を示す（`artifacts/verify/20261001-origin-slot-header-probe/`）。

| 入力 | 報告 |
| --- | --- |
| `{source}` の型の Field に `during buffer` | 型名に `InvalidOriginBinding_Kd`、`buffer` に `MissingOriginBinding_Kd` |
| ヘッダーなしの型で `during source` と `during souce` | 型名に `InvalidOriginBinding_Kd`、二つの Field 全体にそれぞれ `InvalidConstraint_Kd` |
| ヘッダーを `{buffer}` に改名した型を、利用側が `value.source` で射影 | 戻り値の型に `MissingOriginBinding_Kd`、二つの射影にそれぞれ `InvalidOriginBinding_Kd`、`return value` に「expected View<T>, found View<T>」の `TypeMismatch_Kd` |

一つの原因から、複数の記録が出ている。誤記した `souce` の位置には、主たる記録が出ていない。利用側では、同じ綴りの型どうしが一致しないという、理由の分からない記録まで出る。

## 2. 理想的な動作

判断基準：**公開契約の名前は、公開面に書かれた位置でのみ導入する。**

1. 型の自前スロットの名前・個数・順序は、ヘッダーを読めば分かる。
2. private な格納を変更しても、スロット宣言は変わらない。スロットを追加・削除・改名するには、ヘッダーを変更する。
3. 公開型にも非公開型にも、同じ規則を適用する。
4. 誤りは、原因の位置で一度だけ報告する。Advice は、修正の選択肢と、それぞれが公開契約を変えるかどうかを示す。
5. 関数シグネチャで、未束縛の名前から全称 Origin を導入する規則（SPEC §15.3.4）は変更しない。この導入位置はシグネチャそのものであり、すでに公開面にある。

## 3. 仕様の変更点

### 3.1. ヘッダー

| ヘッダー | 自前スロット |
| --- | --- |
| なし | なし。継承した依存と、完全な Type の依存は残る。 |
| `{source}`、`{left, right}` | 列挙したものだけ |

- **書き方：** ヘッダーには、一つ以上の新しい単純名を書く。次の規則は現行どおりとする。
  - 末尾のカンマは許可する。
  - 重複と、継承名の再宣言は禁止する。
  - 境界・`static`・射影・交差は書けない。
- **空の波括弧：** ヘッダーでも束縛集合名でもエラーとする。現行の `{}` の意味は、ヘッダーの省略で表す。
- **ヘッダーの省略：** 現行の `{}` と同じく、Owned を意味しない。

```kimi
public struct View<T> {source}
    private let data: ref/T during source

public struct Counter                  // 自前スロットなし
    private var count: i32 = 0

public struct Holder<T>                // 自前スロットなし。T の依存は残る
    private let value: T
```

### 3.2. 名前解決

#### 3.2.1. 格納宣言の Origin 名

現行で閉じたヘッダーを持つ型に適用している名前解決（SPEC §15.3.2、§15.3.4）を、すべての型に適用する。

- 格納宣言に書いた名前は、宣言済みのスロットか、見えている外側の Origin に解決する。
- 宣言されていない名前を、新しいスロットにすることはない。
- 役割の衝突、誤った役割に一致したときに外側を探さない規則、隠蔽の禁止を含め、SPEC §15.3.4 の検索規則をそのまま適用する。
- Field・payload に付けた `origin` 節のオペランドは、現行でも既存の名前しか参照できないので、扱いは変わらない。

```kimi
struct Pair {source}
    let first: ref/i32 during source
    let second: ref/i32 during souce        // Error: souce は宣言されていない
```

#### 3.2.2. 入れ子の型

外側の Origin だけを参照する入れ子の型には、ヘッダーが不要になる。外側のスロットは、現行どおり字句的に継承される（SPEC §15.3.2）。

現行の衝突規則は、ヘッダーのない型で、名前が「新しいスロット」なのか「外側の Origin の参照」なのかが曖昧になるのを防ぐためのものだった。格納宣言がスロットを導入しなくなれば、名前は常に既存の Origin を参照するので、この曖昧さは生じない。入れ子の型が外側と同名の自前スロットを持てないことは、現行どおりである（継承名の再宣言の禁止）。

```kimi
struct Outer<T> {source}
    struct Inner                           // 現行では {} が必要
        let value: ref/T during source     // Outer の source
```

### 3.3. 分割 struct、Mod によるメンバーの追加、enum

- **分割 struct：** すべての断片が同じヘッダーを書くか、すべての断片がヘッダーを省略する。ヘッダーの省略は「自前スロットなし」を意味するので、`{source}` を書いた断片と、ヘッダーを省略した断片は一致しない。基底型の節とは違い、ヘッダーを一つの断片だけに書くことはできない（現行どおり）。
- **Mod によるメンバーの追加：** Mod が既存の Container にメンバーを追加する場合（impl §20.7.3）、追加される部分は型宣言を書かないので、ヘッダーの一致の対象にならない。追加したメンバーの Origin 名は、追加先の型のヘッダーで解決する。扱いは現行と同じだが、ヘッダーの省略に意味を持たせるため、明記する。
- **enum：** 分割できない点を除き、struct と同じ規則に従う。

```kimi
// a.kimi
struct Buffer {source}
    let head: ref/u8 during source

// b.kimi
struct Buffer {source}                 // 同じヘッダーを繰り返す
    let tail: ref/u8 during source

enum Choice<T> {source}
    Some(ref/T during source)
    None
```

### 3.4. スロットの安定性と Phantom

- **宣言の位置：** スロット名は API であり、ヘッダーでだけ宣言する（SPEC §15.3.7）。
- **借用 Field の削除：** 最後の借用 Field を削除しても、スロットはヘッダーに残り、Phantom Origin になる（SPEC §15.3.5）。名前と個数は変わらないので、利用側の射影や単一スロットの `during` 束縛は、そのまま解決する。
- **格納から決まる性質：** Loan 要求・分散・Copy・Phantom かどうかは、引き続き格納内容から決まる（本書 5）。例えば Phantom になったスロットは、短縮を構造的に確立できなければ不変になる。

```kimi
public struct View<T> {source}             // 借用 Field を削除しても source は残る
    private let count: isize
```

### 3.5. 診断

#### 3.5.1. 宣言されていない格納 Origin

| 項目 | 内容 |
| --- | --- |
| コード | `MissingOriginBinding_Kd`。局所変数の注釈で、未解決の名前を報告するコードと同じ。 |
| 主範囲 | 注釈の名前。同じ原因の記録を、型名や Field 全体には追加しない。 |
| Reason | その名前が、型のヘッダーでも、見えている外側の Origin でも宣言されていないこと。自前スロットはヘッダーでだけ宣言すること。 |
| 関連位置 | 型のヘッダー。ヘッダーがなければ型名。 |
| Advice | 次の二つを、条件付きで示す。<br>・既存のスロットや外側の Origin を意図していた場合は、その名前に置き換える。スロット宣言は変わらない。<br>・新しいスロットを意図していた場合は、ヘッダーに名前を加える。これは公開 API の変更である。また、メンバーのシグネチャで同じ綴りを全称 Origin として使っていれば、そのシグネチャは追加したスロットに束縛し直される。 |

この診断は、名前がどの役割の宣言にも一致しない場合に適用する。次の場合は、現行の説明を保つ。

- **別の役割の宣言に一致した場合：** 例えば、Field 局所の集合名をスカラーとして使った場合や、集合の射影を誤記した場合である。現行の役割エラーとして報告する（SPEC §15.3.1、§15.3.4）。
- **格納に `during self` を書いた場合：** 未宣言の名前としては扱わない。「`self` は自己借用の格納契約を作らない」という規則（SPEC §11.3）を説明する記録として報告する。

```kimi
public struct View<T> {source}
    private let data: ref/T during buffer
    // Error: buffer は宣言されていない（主範囲は buffer、関連位置は {source}）
    // Advice: 既存のスロットなら source に置き換える。
    //         新しいスロットならヘッダーに buffer を加える（公開 API の変更）。
```

#### 3.5.2. 存在しないスロットの射影

スロットを改名・削除すると、利用側の射影は解決できなくなる。この変更は意図的なものであり、修正する場所は利用側にある。

- **主範囲：** 射影のスロット名。射影ごとに一つの記録とする。
- **関連位置：** 型のヘッダー。Note には、宣言されているスロットを列挙する。
- **派生記録：** この射影が解決できないことから派生する記録は、独立した原因として報告しない。例えば、戻り値のスロットが束縛されないことや、同じ綴りの型どうしの不一致がこれに当たる。
- **Advice：** 宣言されているスロット名に置き換えるよう示す。

```kimi
public struct View<T> {buffer}             // source から buffer に改名した
    private let data: ref/T during buffer

func forward<T>(value: View<T>) -> View<T>{result}
    origin result.source == value.source
    // Error: View に source というスロットはない（二つの射影それぞれに一つ）
    // 関連位置は {buffer}。Note: 宣言されているスロットは buffer
    return value                           // 派生記録は出さない
```

#### 3.5.3. 空のヘッダー

構文問題として報告する。Advice では、自前スロットがなければヘッダーを削除するよう示す。範囲とコードは、DIAGNOSTICS §10 の手順で決める。

#### 3.5.4. 廃止する記録

型全体への `InvalidOriginBinding_Kd` を廃止する。対象は、次の三つの場合に出していた記録である。

- 閉じたヘッダーの型で、未宣言の名前を使った場合
- 推論の候補が二つあった場合
- ヘッダーのない型で、外側の Origin と衝突した場合

#### 3.5.5. 修復候補

前提条件と保証を備えた構造化された修復候補は、CSP の導入時に SPEC §23.5.3 に従って提供する。本書では、Advice の文章だけを要求する。

### 3.6. 変更しないこと

- 関数シグネチャの全称 Origin（SPEC §15.3.4）と、単一スロットの `during` 束縛（SPEC §15.3.1）
- 格納完了・Phantom・分散・Loan 要求の規則（SPEC §15.3.2、§15.3.5）
- Semantics 引数の条件付きスロット（SPEC §8.1.2）
- Group と Contract は、自前スロットを持たない

## 4. 評価

### 4.1. メリット

- **原則 1：** 自前スロットの書き方は「省略」と「名前の並び」の二つになり、それぞれの意味は一つに決まる。本書 1.2 の補助規則は、すべて不要になる。
- **原則 2：** スロットの名前・個数は、ヘッダー（入れ子の型なら外側のヘッダーも含む）だけで決まる。利用側の射影や、単一スロットの `during` 束縛が正しいかどうかも、ヘッダーから判断できる。
- **原則 3：** 型が新しく持つ依存は、型宣言の位置に明示される。
- **原則 4：** 誤りは、原因の位置で一度だけ報告される。スロットを意図的に改名した場合も、利用側には射影ごとに一つの記録が、ヘッダーを関連位置として出る。
- **性能：** スキーマは、格納を束縛する前にヘッダーから確定する。そのため、型の格納から Origin 名を集める走査がなくなる。private な格納を編集しても、スロット名の解決はやり直さずに済む。ただし、分散や Loan 要求に依存する検査は、引き続き再検査が必要である。

### 4.2. デメリットと費用

- **書く量：** スロットを持つ型では、非公開の補助型でも `{source}` を書く必要がある。
- **移行：**
  - テストに多数ある `{}` を削除する。
  - 推論に依存する少数のテストにヘッダーを書く。
  - SPEC §15.3.2 の例（`View`・`Typo`・`Inner`）を書き換える。
  - Kimi ライブラリには変更がない。
- **「スロットなし」の目印：** 積極的に示す書き方はなくなる。ただし、`{}` も Owned を保証していなかった。

### 4.3. 複雑性

削る規則が、加える規則を上回る。

- **削る：** 推論、候補が二つの場合の拒否、外側の Origin との衝突、`{}` の要求、空の波括弧の例外、型全体への事前検査。
- **加える：** 本書 3.5 の診断の要件だけ。未宣言名の記録には、局所変数の注釈ですでに使っているコードと解決経路を再利用する。

Mod によるメンバーの追加についての記述は、現行の扱いを明記するだけである。

### 4.4. 検討して採らなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| 公開型だけに、閉じたヘッダーを必須にする | 「スロットなし」の書き方が `{}` と省略に分かれる。また、「公開型」の判定という新しい境界が増える。 |
| 推論したスロットを、外部から名前で射影できなくする | スロットの個数の変化を防げない。また、型の宣言方法によって、利用側の書き方が変わる。 |
| 推論を残し、公開型に警告を出す | 書き方が二つ残る。また、警告だけでは利用側が壊れることを防げない。 |
| 格納から参照されないヘッダースロットに警告を出す | API を安定させるために残した Phantom スロットや、マーカー用のスロットの削除を促してしまう。 |

## 5. 範囲外

本書では、次の事項を扱わない。

- **格納から決まる公開上の性質：** スロットごとの Loan 要求、分散、Copy、Owned 条件、Phantom かどうか。これらの変化は見た目だけの変更ではなく意味の変更なので、利用側に影響すること自体は正当である。公開型の契約要約と、スナップショット間の差分分類（互換か破壊的か）を CSP の別提案として扱うかどうかは、別途決める。
- **メンバーのシグネチャの束縛し直し：** ヘッダーにスロットを追加すると、同じ綴りを全称 Origin として使っていたメンバーのシグネチャが、そのスロットに束縛し直される（SPEC §15.3.4）。これは現行の閉じたヘッダーにもある性質である。本書では Advice で注意を促すだけにとどめ、規則にするかどうかは別途決める。
- **構造化された修復候補：** CSP の導入時に扱う（本書 3.5.5）。

## 6. 実装計画

各単位では、再現例・実装・焦点テストを揃え、AGENTS.md の手順で Verify してからコミットする。セッションの最後には Session の検証を行う。

1. **スキーマ：**
   - ヘッダーのない struct・enum を、自前スロットのないスキーマとして扱う。この単位では、`{}` をヘッダーの省略と同じ意味で受け付ける。
   - struct・enum を、格納の Origin 名の収集対象から外す。スキーマはヘッダーの名前だけから作る。これにより、推論と型全体への事前検査（本書 3.5.4）がなくなる。関数と accessor の名前収集は残す。
   - 分割 struct の断片は、ヘッダーの有無ではなく、スロット列の一致で照合する。Mod によるメンバーの追加は、照合の対象にしない。
   - 推論に依存するテストにヘッダーを書く。
2. **構文と保存：**
   - 空のヘッダーを拒否する。
   - ヘッダーは、スロットがあるときにだけ書き出す。parse-write-parse、成果物の保存と再読込、文書の生成を、これに合わせる。
   - テストの `{}` を削除する。単位 1 の後なので、意味を変えない機械的な変更になる。ただし、`{}` の意味そのものを検査していたテストは、期待値を見直す。
   - 構文コーパスに、空ヘッダーのケースを加える。
3. **診断：**
   - DIAGNOSTICS §10 の手順で、次を再現例にする。
     - 本書 1.3 の三つの入力
     - 正しい対照例
     - 入れ子、分割 struct、enum payload
     - 別の役割の名前に一致した場合
     - 格納に `during self` を書いた場合
   - 本書 3.5 の記録と Advice になることを確認し、足りない点を直す。未宣言名の記録は、単位 1 の後、既存の解決経路から出る。ここでは、型名や Field 全体に派生記録が出ないことを確認し、回帰テストで固定する。
   - 利用側で、存在しないスロットの射影から派生する記録を整理する。
   - CLI と言語サーバーの出力を確認する。
