# `!` 境界による引数名指定

## 1. 位置付け

本変更案は、ここで定める事項について `SPEC.md` およびその参照先より優先する。それ以外の規則は現行仕様を維持する。本書は変更後の言語仕様を定義するものであり、実装完了を示すものではない。

引数名末尾の `?` を廃止し、宣言の引数一覧に一つの `!` 境界を導入する。通常引数は、境界の前では名前を省略でき、後では名前を必須とする。名前の指定方法と、デフォルト値による引数全体の省略は独立させる。

## 2. 宣言構文

### 2.1. 境界と引数一覧

```kimi
func find(value: i32 ! start: i32, end: i32) => ()

func positional(a: i32, b: i32) => () // 全通常引数で名前省略可。
func named(! a: i32, b: i32) => ()    // 全通常引数で名前必須。
func empty() => ()
```

- `!` がなければ、全通常引数で名前を省略できる。名前付き指定も常に許可する。
- `!` は引数一覧に最大一つとし、境界位置ではカンマの代わりに置く。
- 左側は空でもよい。右側には少なくとも一つの通常引数が必要である。受信者 `self` だけでは満たさない。
- 各区画内はカンマで区切る。引数一覧全体の末尾のカンマは許可するが、境界直前・直後のカンマは許可しない。
- `name!` や `name?` など、引数名に付ける個別マーカーは認めない。

文法の要点を示す。`?` と `*` はそれぞれ省略可能と繰り返しを表す文法記号である。

```text
ParameterList := "(" (Sequence ","? | Sequence? "!" Sequence ","?)? ")"
Sequence      := Parameter ("," Parameter)*
```

`Parameter` は旧 `?` マーカーを除いた既存の引数宣言であり、型、デフォルト値、属性、受信者の制約は適用先に従う。境界は引数でも型修飾でもなく、引数の個数・宣言順を変えない。

### 2.2. 外部名と内部名

両区画で `external => internal: T` により名前を分離できる。分離自体は名前必須を意味しない。分離しない場合は外部名と内部名が同じになる。

境界を使用できる宣言では、受信者を含む引数一覧全体で外部名を一意にする。内部名は別の名前集合として既存の宣言空間の規則で検査する。外部名どうしの重複は、境界位置、デフォルト値、呼び出しの有無にかかわらず宣言時エラーとする。外部名と別の引数の内部名が同じであること自体は禁止しない。

```kimi
func bad(! value => a: i32, value => b: i32) => () // エラー：外部名が重複。
```

### 2.3. 字句・式の終端・レイアウト

既存の字句規則を維持し、境界の前後の空白に意味を持たせない。括弧内の改行・コメントは既存の継続規則に従い、`!` を独立した行にも置ける。標準的な一行表記では、途中の境界の前後に空白を置く。

境界として認識した `!` は、直前の引数宣言・デフォルト式・区切り領域の終了についてカンマと同じ規則に従う。インデントされた本体を同じ行の `!` で閉じてはならず、先に次の有効行で適切に字下げを解除する。`if`、`do`、無名関数を含むデフォルト式にも共通の終端規則を適用する。

境界の所属は括弧の深さだけでなく構文上の包含関係で判定する。内側の引数一覧に属する境界や、文字列・コメント内の `!` を外側の境界にしない。既存の `!=` トークンは分割しない。式の単項・後置演算子としての `!` は導入しない。

## 3. 呼び出しとデフォルト値

呼び出し側は従来どおりカンマで区切り、`!` は書かない。

```kimi
find(10, start: 0, end: 100)        // 可。
find(value: 10, end: 100, start: 0) // 可。名前付き引数は並べ替え可能。
find(10, 0, 100)                   // エラー：start と end は名前必須。
find(10, start: 0, 100)            // エラー：名前付き指定の後に位置指定。
```

位置引数は名前付き引数より前に置き、宣言順に対応させる。名前必須の引数、デフォルト付き引数、後で名前付き指定する引数を飛ばさず、型による対応先の探索もしない。名前付き引数は外部名で対応させる。未知の名前、重複指定、過剰な位置引数はエラーとする。

未指定の引数はデフォルト値があれば補い、なければエラーとする。`!` の右側でもデフォルト値があれば引数全体を省略できる。

| 通常引数の宣言位置 | デフォルト値 | 位置指定 | 名前付き指定 | 引数全体の省略 |
| --- | --- | --- | --- | --- |
| 境界より前、または境界なし | なし | 可 | 可 | 不可 |
| 境界より前、または境界なし | あり | 可 | 可 | 可 |
| 境界より後 | なし | 不可 | 可 | 不可 |
| 境界より後 | あり | 不可 | 可 | 可 |

位置指定の「可」は、共通の順序規則にも従う。

```kimi
func scale(value: i32 ! by => factor: i32 = 1) -> i32 => value * factor
scale(3)         // 可。
scale(3, by: 4)  // 可。
scale(3, 4)      // エラー。
scale(3, factor: 4) // エラー：内部名では指定できない。

func configure(mode: i32 = 0 ! count: i32) => ()
configure(count: 3) // 可。mode のデフォルト値を使う。
configure(3)       // エラー。3 は mode に対応し、count が不足する。
```

デフォルト付き引数を、デフォルトなしの引数より前に置いてよい。明示引数の取得はソース順、その後の省略デフォルトの評価は引数宣言順とする。境界によって評価段階を分けない。宣言時のデフォルト検査、宣言スコープと先行引数の参照、型推論の証拠からの除外、所有権、借用予約、後始末の規則は変更しない。

## 4. 適用先と受信者

| 対象 | 規則 |
| --- | --- |
| 名前付き関数、メソッド、コンストラクター | 本境界を使用できる。ローカル関数、ジェネリック関数にも適用する。 |
| Contract の関数要件 | 本境界を使用できる。デフォルト値は引き続き禁止する。 |
| 外部関数宣言 | 本境界と外部名・内部名の分離を使用できる。デフォルト値は禁止し、既存の宣言・安全性・ABI 制約を維持する。 |
| 無名関数、関数型 | 本境界を禁止する。引数名・名前指定契約・デフォルト値を持つ関数型は導入しない。 |
| Property のアクセサーとアクセサー要件 | 本境界を禁止し、専用の受信者・値供給規則を維持する。 |
| 明示的特殊化のヘッダー | 本境界を禁止し、元の宣言の契約を継承する。詳細は §5。 |

呼び出し式、ジェネリック引数一覧、enum Case のペイロード、属性や組み込みの専用引数構文には境界を導入しない。`deinit` など固有の引数制約も緩和しない。

受信者として認識された `self` は通常引数ではなく、境界の左右で供給規則が変わらない。既存どおり任意の宣言位置に置け、改名とデフォルト値は禁止する。境界後にあっても、通常引数の名前必須区画を終了させない。

- `receiver.method(...)` は受信者を先に取得し、`self` の位置を除いた宣言順で通常引数を対応させる。呼び出し内に `self:` を重ねて指定できない。
- `Type.method(...)` による非束縛の直接呼び出しでは、`self` も元の位置に残る。`self` 自体は位置・名前の両方を許すが、位置引数の飛ばしや名前付き指定後の位置指定は許さない。
- 受信者の役割を持たない通常引数の名前が `self` である場合は、通常引数として境界に従う。

メソッドの `(self !)`、`(! self)` は、右側に通常引数がないためエラーとする。

## 5. 契約、特殊化、関数値

### 5.1. 名前指定契約の正規形

通常引数の個数を `N`、そのうち位置指定を許す先頭部分の個数を `K` とする。受信者はどちらの個数にも含めない。名前指定契約を自ら定める宣言では、次の規則を適用する。特殊化の継承は §5.2 に従う。

- 境界がなければ `K = N`。境界があれば、その前の通常引数の個数が `K` となり、`0 <= K < N` を満たす。
- 通常引数を宣言順に 0 から数え、位置 `i < K` では名前省略可、それ以外では名前必須とする。引数の対応には §3–4 の規則も適用する。
- 通常引数の外部名列と `K` を名前指定契約として扱い、型、受信者位置、デフォルト値はそれぞれ独立して保持する。

ソース上の境界位置は構文情報であり、契約比較には使わない。例えば `(self ! x: i32)` と `(! self, x: i32)` は、外部名列が等しく `K = 0` のため同じ名前指定契約となる。正規化によって引数順や受信者位置を変えてはならない。

### 5.2. 適用と比較

引数名指定の契約は、呼び出しで静的に選択された宣言に従う。比較目的ごとの扱いは次のとおりとする。

| 目的 | 名前指定契約の扱い |
| --- | --- |
| オーバーロードの宣言同一性 | 外部名や `K` だけでは Signature を区別できない。 |
| 呼び出し候補の適用可能性 | 選択対象の宣言の外部名と `K` で対応を判定する。候補間の優先順位は追加しない。 |
| Contract 要件と実装の対応 | 通常引数の個数・順序・外部名を照合するが、`K` の一致は要求しない。 |
| 異なる Contract 要件の呼び出し候補統合 | 外部名と `K` の一致を契約同値の検査に含める。これだけで統合は認めず、型・条件・同じ実装への対応など既存の証明条件も満たす必要がある。 |

- Contract の要件経由では要件側の契約を使い、実装側の境界やデフォルト値で変更しない。
- オーバーライドでも、静的に選択された宣言の境界とデフォルト値を使う。
- 明示的特殊化は元の宣言の名前指定契約とデフォルト値を継承する。ヘッダーに境界とデフォルト値を再記述せず、境界がないことから `K = N` と解釈してはならない。

関数値は、元の宣言の名前指定契約・デフォルト値を保持しない。関数値経由では全引数を位置指定し、名前付き指定と引数省略を許さない。関数型互換性や `Callable` の規則は変えない。

## 6. 旧記法からの移行

### 6.1. バージョンと互換性

本変更は言語バージョンの変更として扱い、境界方式を適用するバージョンを旧方式から区別する。既存の `LangVersion` とコンパイラビルド識別を使用し、依存グラフ全体を一つの実効言語バージョンで検査する。旧方式のバージョンを指定したプロジェクト・パッケージを、新方式として暗黙に読み替えてはならない。異なる実効バージョンの混在はエラーとする。

バージョン未指定のソースは既存のバージョン選択規則に従うが、旧記法の意図を自動識別できない。特に無印の引数は名前必須から名前省略可へ意味が変わり得るため、ソースと依存宣言を一貫して移行する。新しいファイル単位の切替記法は導入しない。

### 6.2. 変換規則

まず §2.2 の外部名の一意性を検査する。重複する旧宣言は診断し、自動改名しない。その解消は、呼び出し側も含めて見直す別の API 変更となる。それ以外の宣言について、受理される直接呼び出しの指定方法を保つ変換を次に示す。

1. 境界を使用できる宣言では、受信者を除き、旧仕様で最初に名前必須だった通常引数の直前に `!` を置く。その位置のカンマは除く。
2. そのような引数がなければ境界を置かない。
3. すべての旧 `?` を除く。型、外部名・内部名、デフォルト値、引数順は維持する。
4. 特殊化は境界なしのまま、元の宣言から契約を継承する。

旧仕様で名前必須の引数より後ろにあった `name?` も、新仕様では名前必須になる。旧仕様でも位置引数でそこまで到達できなかったため、通常の直接呼び出しで受理される指定方法は保たれる。移行のために引数を並べ替えてはならない。

```text
旧: func f(a?: i32, b: i32, c?: i32 = 0)
新: func f(a: i32 ! b: i32, c: i32 = 0)
```

Kimi の規定宣言にも同じ変換を適用する。例えば `writeLine(text: string)` と `swap(first: uniq/T, second: uniq/T)` は境界なし、`replace(target: uniq/T ! with => value: T)` と `exchange(target: uniq/T ! with => value: T)` は `with` の直前を境界とする。型引数・戻り型・所有権契約などは維持する。

## 7. 実装・検証要件

### 7.1. 必須の保持事項

境界はコンパイル時の呼び出し契約であり、実行時引数、ABI 上のスロット、評価処理を追加しない。ソース再出力・保存・再読み込みでも §5 の契約と特殊化の継承を保持する。保存データは形式・言語バージョン・コンパイラビルドの互換性を検査し、旧規則を新規則として誤って再解釈しない。契約変更時は依存する呼び出し計画を無効化する。

### 7.2. コンパイル性能の改善指針

以下は意味を変えない実装上の推奨であり、具体的なデータ構造は規定しない。

- `K` と受信者位置から、束縛・非束縛の各呼び出しで位置指定できる最大個数を前計算する。宣言検証を省かず、位置引数が多すぎる候補を型推論より前に除外する。
- 外部名から宣言位置への検索情報を宣言単位で再利用し、呼び出しごとの構築・確保を避ける。型引数に依存しない情報は、同じ宣言のインスタンス間で共有できる。
- 引数が少ない場合の線形検索と、検索表を使う方式を実測で選ぶ。常に辞書を作ることは要求しない。
- 名前解決で宣言位置が得られても、明示引数の評価・取得は元のソース順を維持する。

### 7.3. 検証範囲

最低限、次を検証する。

- 境界なし・先頭・途中、空引数一覧、改行・コメント・末尾カンマ。重複境界、空の右区画、境界前後のカンマ、旧マーカー、禁止箇所の境界を拒否する。
- 名前指定とデフォルト値の全組み合わせ、外部名の分離と宣言側の一意性、名前の並べ替え、呼び出し側の重複・不足・未知の名前、位置引数の飛ばし禁止。
- `!=`、内側の境界、文字列・コメントを誤認しない。本体を持つデフォルト式の終端、字下げ解除、同じ行の境界による不正な本体終了を検査する。
- 境界の左右と各宣言位置にある受信者、束縛・非束縛の直接呼び出し、コンストラクターと base 呼び出し、Contract、オーバーライド、特殊化、関数値、外部関数宣言。
- 同じ外部名列と `K` を持つ異なる表記の契約同値、異なる `K` の Contract 要件を誤って統合しないこと、境界だけでは区別できないオーバーロード、候補適用と特殊化の継承。
- 新旧バージョン混在の拒否、移行前後の呼び出し受理・選択先・引数対応・評価順の一致、保存・再読み込み、契約変更後の再 Binding。早期判定や検索表の有無でも診断・評価・後始末の意味を保つ。

正式仕様への取り込み対象は、§2 の記号、§6–7 の宣言、§8–10 の契約・候補適用、§11–12 の専用構文・呼び出し、および関連する Kimi 規定宣言、外部関数、Appendix A・F、`SPEC.md` の索引と例である。本作業ではこれらを変更しない。
