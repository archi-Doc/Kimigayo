# Design Change: 整数範囲と原因・修正候補を伝える診断

日付: 2026-09-28

状態: 合意した設計方針に基づく変更提案。正式仕様への取り込み・実装・新仕様の動作検証は未実施。

## 1. 現状、変更の理由と目的

現在の範囲式は、両端が整数でも、対象の長さに対する未解決の区間指定 `Range` を作る。整数境界の期待型は `isize` で、内部では `Index` に正規化する。`Range` は反復できず、非負の確定区間 `ResolvedRange` だけが反復できる（SPEC §4.6.2–4.6.4、§14.6.2）。

```kimi
for var x in [0..10]
    Console.writeLine("Count \(x)")
```

`[式]` は式の値を1個含む配列なので、現状の `x` は整数ではなく `Range` になる。このコードが補間位置で `NoApplicableOverload_Kd` になることを実行環境で再現した。直接の整数補間は実行できるが、診断から反復元の誤解を読み取れない。

目的は、次の二つである。

- 対象なしで列挙できる整数区間を `for x in 0..10` と書け、変数への保存・ジェネリックな受け渡しでも同じ意味を保つ。
- 型・構文の失敗を、原因、関連位置、適用条件付きの修正候補として伝える。範囲・補間だけでなく、Milestoneプログラムを編集して生じる構文エラーも対象にする。

現行の診断には個別コードと一部のMilestone改変テストがある。一方、共通レコードは主にコード・重大度・文章・単一位置で、コレクションは同じ開始位置の後続診断を抑制する。CLIは追加時に表示し、LSPは検査結果から一覧を作る。CSPが要求する関連位置・構造化編集・スナップショットとの対応は、今回整備する共通基盤となる（§23）。

## 2. 採用する概念の分離

| 型 | 保証・役割 | 単独の反復 |
| --- | --- | --- |
| `IntegerRange<T>`（新設） | 同じ整数型Tの確定した両端と包含指定。負数も通常の値として扱う。 | Tの値を生成する。 |
| `Range` | 先頭相対・末尾相対・省略を含む位置の指定。対象長に対して解決する。 | 不可。 |
| `ResolvedRange` | 非負の検証済み半開区間。`isize`の長さを持ち、適用先では再検査する。 | `isize`を生成する。 |

`Range` を `IntegerRange<T>` の実行時状態として統合しない。同じ型に反復可能・不可能な値を混在させると、型から反復の前提を判断できない。`Range<TBoundary>` による型系列の統合は成立するが、条件付きAPIを増やす割に役割の違いは残るため採用しない。表現や検査の実装は共有しても、公開契約は分ける。

## 3. 整数範囲の変更仕様

### 3.1. 構文、型と推論

| 境界 | 結果 |
| --- | --- |
| 両端が同じ整数型Tの `a..b` / `a..=b` | `IntegerRange<T>`。終端を除く／含む。 |
| 境界に `Index` を含む | `Range`。整数側には既存の `isize` 境界規則を適用する。 |
| 片側または両側を省略する | `Range`。省略開始は0、省略終了は `^0`。包含終端の省略は引き続き不可。 |

Tは `i8/u8`、`i16/u16`、`i32/u32`、`i64/u64`、`i128/u128`、`isize/usize` の閉じた集合。浮動小数点・`char`・ユーザー定義型は対象外とする。参照からの整数読み出しには既存のScalar readを適用し、範囲専用の暗黙変換は導入しない。

```kimi
let a = 0..10                       // IntegerRange<i32>
let b = 0@i64..10                   // IntegerRange<i64>
let c: IntegerRange<i64> = 0..10     // 期待型に未確定リテラルを適合
let d = -3..3                       // IntegerRange<i32>
let e = 1..^1                       // Range
let f = ..10                        // Range。0..10への読み替えはしない。
```

確定した境界型を優先し、未確定リテラルを通常の規則で適合させる。固定の期待型からTが決まらず、両端が未確定なら `i32` を既定とする。異なる確定済み整数型はエラー。期待型が `Range` でも整数範囲へ決まった式を再解釈せず、`for`・添字内だけの型決定規則も設けない。

型の種別は構文と静的な境界型から決め、実行時の値や候補の試行順に依存させない。ジェネリック定義では、境界が同じ整数型Tである証明を要求する。既存の型選択制約を用い、汎用Numeric Contractや演算子のユーザー拡張は導入しない。

### 3.2. 構築・反復・失敗

- 左境界、右境界を各1回評価し、完了後に順序を検査する。境界評価自体がAbortすれば以降は評価しない。
- 開始値 > 終了値なら構築時にAbort。空範囲や降順へ読み替えない。通常の式のAbortを、定数が見えるという理由でコンパイルエラーへ変更しない。必須定数評価・不正な型・リテラル範囲外は既存の静的エラー規則による。
- `a..a` は空、`a..=a` は1要素。昇順、刻み幅1。負数、各Tの最小値・最大値を許す。
- `a..=T.MaxValue` を扱えることを要求する。包含終端を常に `end + 1` へ変換したり、最終要素の後で加算したりしない。
- `Iterable`・`UniqIterable`・`IntoIterable` の全入口が所有されたTを生成する。Subjectの取得・Loanは既存規則に従い、反復のために範囲を書き換えない。
- Iteratorだけが進行状態を持つ。新しい反復は先頭から始まり、終了後の `next` は `None` のまま。`for var x` のxを再代入しても生成順序は変わらない。
- 基本的な範囲構築・反復はヒープ確保を要求しない。ユーザーの境界式・ループ本体の確保はこの保証に含めない。

```kimi
let numbers = 0..10
for var x in numbers
    Console.writeLine("Count \(x)") // Count 0 ～ Count 9
```

### 3.3. 公開API

| 宣言 | 保証 |
| --- | --- |
| `IntegerRange<T>` | Owned、Copy、Equatable。内部の有効性を迂回して変更できない。Comparableや範囲の算術は追加しない。 |
| `start: T`、`end: T`、`isInclusive: bool` | 読み取り専用。構築時の境界と包含指定。 |
| `isEmpty: bool` | 終端非包含かつ開始と終了が等しいときだけtrue。 |
| `tryCreate(! start: T, end: T, isInclusive: bool = false) -> Option<Self>` | 有効ならSome、逆転ならNone。引数評価中のAbortは捕捉しない。同型の両端とBooleanは名前付き引数にする。 |
| 三つの反復入口 | 通常のIterator経路でTを生成する。 |

通常の生成は範囲構文を正準形とし、同義の公開 `init` / `create` を増やさない。`tryCreate` は外部入力の失敗を値で受け取る別の用途である。

等価性は同じTの `start`・`end`・`isInclusive` を比較する。`0..3` と `0..=2` は異なり、異なる位置の空範囲も同一視しない。異なるTや他の範囲型への暗黙変換・交差型等価性は追加しない。

`length` は設けない。全整数域の要素数はTにも `usize` にも収まるとは限らない。`Utf8Format` への適合も今回追加せず、範囲値の表示形式は別のAPI設計とする。

### 3.4. 配列・スライスとの接続

`[0..10]` は `IntegerRange<i32>` を1個含む配列のまま。自動展開は行わず、`let r = 0..10; [r]` への切り出しで意味が変わらないようにする。この形だけでは警告しない。

組み込みの固定配列・Array・Sliceのスライスと `Slice.trySlice` に整数範囲を追加する。受け取った整数を切り詰めず、非負、対象長以内、包含終端の有効性を検査して、共通の半開区間へ正規化する。包含終端では先に `end < length` を確認する。負数を末尾相対へ読み替えない。

| 操作 | 結果 |
| --- | --- |
| `values[-3..3]` | 整数範囲の構築は成功。スライス操作でAbort。 |
| `slice.trySlice(-3..3)` | スライス検査に失敗しNone。 |
| `slice.trySlice(10..0)` | 呼び出し前の範囲構築でAbort。 |

`Range` と `IntegerRange<T>` の適用は内部で `ResolvedRange` 相当の検証結果に揃え、以後のストレージ境界・借用・Place処理を共有する。受け手と境界を再評価せず、既存のアクセス予約・Loan規則を保つ。ユーザーのIndexable実装には新しいキー型の適合を自動付与しない。

単一要素の添字は既存の `isize` / `Index` 規則を維持する。`for i in 0..10` のiは `i32` なので、必要なら明示変換する。添字走査の標準形は `for i in values.indices`（iは `isize`）とする。

## 4. 原因・回復・修正候補を共有する診断

### 4.1. 共通レコードと原因の選択

一つの診断モデルを字句解析、構文解析、Binding、所有権検査、CLI、LSPで共有する。CSP全体の導入を前提とせず、将来そのまま参照できる基盤にする。

| 情報 | 内容 |
| --- | --- |
| 主診断 | 安定したコード、重大度、段階、利用者の操作としての原因。 |
| 主位置・関連位置 | 原因式、宣言、反復元、開始括弧、必要なContractなど。位置ごとの役割を付ける。 |
| 構造化した理由 | 実際の型、期待型、満たさない条件、依存する先行診断。Unknownと不成立を区別する。 |
| 修正候補 | 対象スナップショット、適用前提、具体的な編集、意図の仮定、検証範囲・結果。 |

内部の合成呼び出しの失敗は、元の補間・添字・反復などへ対応付ける。オーバーロードは「適用候補なし」と「複数候補成立」を区別し、代表的な不成立理由を付ける。無関係な全候補を主メッセージへ列挙しない。

例（日本語は表示内容の説明であり、診断の日本語化を必須とする提案ではない）:

```text
x を文字列補間できません。
IntegerRange<i32> は Utf8Format に適合していません。

関連箇所: for var x in [0..10]
[0..10] は IntegerRange<i32> を1個含む配列で、x はその要素です。

修正候補: 整数を順に反復する意図なら、[ と ] を外す。
```

主位置は補間内のx、関連位置は反復元とする。括弧削除は実行回数・要素型を変えるため意味保存を保証しない。反復不可、添字型の不一致、名前解決失敗、借用の競合も同じ原因・関連位置の規則で説明する。

### 4.2. 構文回復と派生エラー

- 足りない・余分なトークンに加え、現在の構文上の役割を示す。閉じ括弧不足には開始位置、字下げ不整合には対応する本体・字下げ水準を添える。
- 回復で補ったノード・トークンと、それを必要とした診断を記録する。後続検査では、その欠落から派生する型不明・未解決名を重ねない。
- 改行、同じまたは浅い字下げ、対応する区切り、宣言開始など、構文ごとの明示した地点で回復する。文字列・補間・ジェネリックの区切りを一律に読み飛ばさない。
- 後続の独立した文・宣言は検査する。回復不能な範囲は明示し、推測を確定した型情報として公開しない。
- 回復ループは必ず入力を進めるか現在の解析を終了する。探索・診断数には限度を設け、省略した場合はその事実を示す。
- 開始位置だけの重複抑制を、原因と診断の同一性に基づく抑制へ変更する。同一位置の独立した原因は失わず、表示抑制によってコンパイルの不成立を消さない。

構文が誤っている場合、仕様上は有効だが未実装の場合、実行時にAbortする場合を区別する。`UnexpectedToken` や `Unsupported` をそれらの共通の代替診断にしない。

### 4.3. 修正候補の契約

編集は文章の `Fix` / `Note` から推測せず、ソースID・内容の識別子・範囲・置換文字列として持つ。適用時は全対象の版と前提を再検査し、古い候補・重複編集を拒否する。元ソースを無断で書き換えない。

「提案のみ」「同じ構成で再解析済み」「型・所有権等の再検査済み」と検証範囲を分け、解消した診断・残る診断を記録する。意味保存はこれらと別の保証であり、型検査成功だけでは主張しない。候補が複数あるときは意図の仮定を示す。

CLIとLSPは同じ主診断・関連情報を表示し、LSPでは既存の関連情報フィールドに対応させる。構造化候補の検査・テスト経路までを今回の対象とし、自動適用UI、汎用CSP公開スキーマ、広域な自動修復は含めない。

## 6. 実装上の問題と改善方針

| 問題 | 単純化・性能改善の方針 |
| --- | --- |
| 現行Bindingが全境界をisize/Indexへ正規化する | 最初に構文と境界型で範囲の種別を決め、整数範囲には通常の整数推論を適用する。期待型や用途による再解釈を避ける。 |
| 既存ResolvedRange専用の反復・スライス処理 | 新しい専用LLVMループを増やす前に、Kimi製Iteratorと通常のモノモーフィゼーションを使う。共有できる検査・表現は下位の共通処理へ集約する。 |
| 整数集合を制約に持つジェネリックの演算・比較 | 定義時に全許容型で証明する。整数幅・符号・Scalar readの通常の証明を利用し、実体化時に都合よく再解決する方式へ戻さない。128-bitも仕様対象とし、実装限界を別途記録する。 |
| 全整数域の反復で長さ・差・終端加算が溢れる | 現在値、終端、包含指定、終了状態で進める。差分を要素数として保持せず、加算可能な経路だけで次の値を作る。 |
| 幅・符号の異なる整数をスライスへ渡す | 符号と範囲を検査してからisizeへ変換し、共通の検証済み半開区間を使う。正当性を証明できた重複検査だけを除去する。 |
| 関連情報を全成功経路で構築すると割当が増える | 原因・型・ノードの軽量な識別子を保持し、説明文字列と候補編集は失敗時・要求時に生成する。コンパイラの可変オブジェクトを検査結果へ漏らさない。 |
| 修正候補の再検査が高コストになる | 有力な局所候補に絞り、同じスナップショットの結果を共有する。探索量を制限し、未検査を成功扱いしない。依存が確認できる単位で再検査する。 |
| CLI即時表示では後から原因をまとめにくい | 依存・抑制を決められる最小の段階で診断を確定して表示する。順序は決定的にし、LSPとも同じ確定レコードを共有する。 |

測定は整数反復と、正常・誤りあり・編集中ソースの検査のホットパスに絞る。時間と割当量を同じソース・構成で比較し、診断の品質を落として速くする最適化は採用しない。ゼロ確保は範囲の基本動作の要件であり、数値としての改善幅は測定前に主張しない。

## 7. 検証と実装順序

1. 正式仕様と宣言一覧を更新し、整数範囲の構築・推論・API・反復を実装する。範囲の種別決定と実行時検査を先に固定する。
2. スライスを共通の正規化へ接続し、既存範囲・例・Milestoneを更新する。標準Iteratorの経路と保存した値の経路を検証する。
3. 診断レコード・原因対応・重複抑制を整備し、補間・呼び出し・反復・添字・所有権へ適用する。
4. 構文回復、構造化候補、CLI/LSP運搬とMilestone編集テストを整備する。各単位を検証してコミットする。

| 検証対象 | 受け入れ条件 |
| --- | --- |
| 整数範囲 | 全整数型、負数、空、1要素、逆転、最小・最大値近傍、包含最大値、符号なし上位値、推論・不適合、tryCreateを確認する。巨大範囲を全走査せず境界近傍と早期終了で検証する。 |
| 評価・反復 | 境界の左から1回評価、途中のAbort、三入口、繰り返し利用、for var再代入、終了後None、break/continue相当の既存制御・cleanup、基本動作の確保数を確認する。 |
| スライス | 保存・直接記述で同じ結果、非負化・幅の検査、空と包含境界、負数・逆転の失敗段階、借用の維持、ユーザーIndexableの既存選択を確認する。 |
| 型診断 | 元の例の原因と関連位置、未解決名由来の派生抑制、独立した複数原因、正常な範囲配列への誤警告なしを確認する。 |
| Milestone編集 | 正規ソースのコピーに、括弧・引用符・補間終端・カンマ・in・=>・型注釈・ジェネリック区切りの削除/置換、字下げ変更を適用する。元ソースの字句・構文成功を基準にし、型・実行の未対応とは分ける。 |
| 回復品質 | 主位置・開始位置・後続の独立エラー、複数同時編集、EOF・CRLF・非ASCII、有限時間での終了を確認する。文面全文や診断数1件への固定だけを合否基準にしない。 |
| 修正候補 | 変更箇所の一意性・スナップショットを検査し、コピーへ適用して再解析/再検査する。古い版・競合編集の拒否、残る診断と保証範囲、CLI/LSPの一致を確認する。 |

既存 `DiagnosticPrecisionTest` のMilestone改変を拡張し、構文段階にも検証を広げる。各変更の適用箇所数を検査し、元プログラムが変わってもテストが何も編集せず成功することを防ぐ。

実装単位の検証は `verify.ps1 -Class ...` と関連O0/O2 fixture・Milestone、セッション末尾は `-Mode Session` を使う。構文診断だけのケースにネイティブ実行を要求せず、NativeAOTは対象外とする。本書だけの追加ではコンパイラの支持範囲を更新しない。
