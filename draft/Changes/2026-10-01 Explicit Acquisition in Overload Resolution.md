# 仕様変更案：オーバーロード競合時の明示取得

日付：2026-10-01

状態：最終版。基本方針は採用決定済み。正式仕様への取り込みと実装は未実施。

本書で変更する事項は SPEC より優先し、変更しない事項には既存仕様を適用する。SPEC の節は「SPEC §n」、本書の節は「本書 n」と表記する。例は本書 1.1 の宣言を共有する独立した断片であり、「エラー」と記した行は意図した拒否例である。

## 1. 問題と方針

### 1.1. 現仕様の問題

[SPEC §10.2.1](../../docs/spec/10-overload-resolution-and-inference.md#1021-inference-and-adaptation-classes) は、裸の Place を値渡しする候補に Copy の証明を要求し、適用可能なら共有借用の候補より優先する。そのため、型に Copy を追加・削除するだけで、同じ呼出しが別の関数を選ぶ。条件付き Copy では、ジェネリック本体と具体型の呼出しで選択が異なり得る。

```kimi
struct Node
    Self is Copy

    var number: i32

    public init(number: i32)
        self.number = number

func process(value: Node) -> i32 => 1
func process(value: ref/Node) -> i32 => 2

let node = Node.init(10)
process(node) // 現仕様：Copy なら 1。Self is Copy を削除すると 2。
```

呼出し側の意図が Copy 能力と適応順位に隠れており、原則2「局所的な推論」と原則3「明示的な意味論」に反する。

### 1.2. 方針

1. **同じ Place の値取得と新規共有借用が候補間で競合する場合、Copy 能力にかかわらず明示取得を要求する。** Non-Copy や Copy 未証明でも同じである。
2. **この競合は、他の引数や第三候補の優先順位では解消しない。** 型不一致などによる候補除外は従来どおり有効である。

取得方法が一つに定まる呼出しは、従来どおり省略できる。新しい構文は追加せず、既存の `@ref`・`@copy`・`@move` で意図を示す。従来なら一意に順位付けできた呼出しにも明示が必要になることは、意図した負担として受け入れる。

## 2. 期待する動作

本書 1.1 の宣言と、owner の Place `node: Node` に対する独立した呼出しを示す。

| 呼出し | 提案後の動作 |
| --- | --- |
| `process(node)` | Copy 能力にかかわらず取得競合エラー |
| `process(node@ref)` | 元の Place を共有借用し、借用版を選ぶ |
| `process(node@copy)` | Copy を証明できれば値渡し版を選ぶ。元の値は引き続き使える |
| `process(node@move)` | Move が合法なら値渡し版を選ぶ。元の値は Moved になる |
| `process(Node.init(10))` | 取得済みの一時値を値渡し版へ転送する。競合しない |

`@copy` は値渡し版を選ぶ指定ではなく、書かれた式の完全型の値を Copy する操作である。`r: ref/Node` に対する `r@copy` は参照の Copy であり、参照先を Copy するには `r@follow@copy` と書く。同型取得 `node@Node` も既存の意味のまま使えるが、意図を示すには `@copy` を推奨する。

```kimi
func inspect(value: ref/Node) -> i32 => 2

let node = Node.init(10)
inspect(node)          // 借用版しかないので、暗黙に共有借用する。
inspect(node@copy)     // Copy した一時値を借用する。node 自体は借りない。

process(Node.init(20)) // 一時値の転送。競合しない。
let saved = Node.init(20)
process(saved)         // エラー：Place の Copy と共有借用が競合する。
```

一時値を変数に保存すると受理が変わるのは、Place からの値取得には Copy の証明が必要だが、一時値は既に取得済みの値だからである。

## 3. 仕様変更

### 3.1. 取得競合の定義

同じ裸の Place 引数について、ある候補が C を、別の候補が S を計画する場合を**取得競合**とする。判定は型の分類ではなく、既存規則が作る取得計画で行う。

| 区分 | 取得計画 |
| --- | --- |
| C：裸の値取得 | SPEC §3.5 に従い、Place に格納された完全型の値を Copy する。Copy の証明が必要 |
| S：新規共有借用 | SPEC §10.2 の「Readable Place storing `U` → `ref/U`」の行に従い、同じ Place を新しく共有借用する |

- **Place の範囲：** ローカル（パラメーター・Capture を含む）、フィールド、要素、Place 戻り値、`@follow` で選んだ Place。共有・排他的な経路の先にある Place も含む。括弧は透過的で、`@follow` 自体は値を取得しない。
- **対象外：** 一時値は Place ではないので、C にも S にもならない。既存の参照値から得る共有参照（参照の層をたどる場合を含む）と Reborrow、read Type の値読み、object 借用は S ではない。具体的な参照・ハンドルのスロットを暗黙に借用しない既存の禁止も維持する。
- **条件：** 内部 Origin を含む完全型、Place の同一性、通常の Origin 適合を保つ。owner であることの証明は条件にしない。この規則によって、S の適用条件や型推論を満たさない候補を成立させてはならない。

### 3.2. 検査の順序

各呼出しを次の順で検査する。

1. **候補の検査：** 名前検索を確定し、SPEC §10.1 に従って、引数対応、receiver と独立に型付けできる引数からの推論、正規化、アクセス、宣言の条件、独立した期待結果、取得計画を検査する。リテラルの適合と、匿名関数の arity・明示型による絞込みもここで行う。C の Copy の成否は、まだ候補の除外に使わない。
2. **取得競合：** 残った候補をソース引数ごとに走査し、C と S が共存する引数ごとにエラーとする。競合があれば、その呼出しは順位付けへ進まない。
3. **Copy 条件：** 競合がなければ C の Copy を証明し、不成立の候補を除外する。
4. **順位付けと依存引数：** 残った候補について、SPEC §10.4 の順位付けと、SPEC §10.5 の依存引数（匿名関数本体、外側の期待型を要する入れ子呼出し）の検査を既存規則どおり行う。依存引数は一回だけ検査し、候補ごとに再解析しない。
5. **使用合法性：** 選択した計画の初期化、Move、Loan、寿命、unsafe などを SPEC §10.6 に従って検査する。失敗しても別の候補へ戻らない。

**Copy 条件の扱い**

- Copy が Refuted または Unknown でも、手順2までは候補に残す。Error は元の原因を報告する。
- Unknown は証明でも Non-Copy の証拠でもない。必要な証明は、既存の期限どおり定義の受理までに完了する。
- 保留するのは、明示引数の C に必要な Copy だけである。明示的な `T is Copy`、型形成、receiver、既定値、capture、`@copy` などの明示操作自身の条件は、従来どおり手順1で検査する。
- 同じソース式・完全型・呼出し環境・許容ケースに対する Copy の証明は、引数ごとに一回行って候補間で共有する。一部の許容ケースの証明を全体へ流用しない。

**比較の範囲**

- 名前付き引数は、同じソース式どうしを比較する。
- 既定値と receiver は比較しない。receiver は SPEC §7.3 の単一の receiver shape を維持する。
- 他の引数の型不一致や独立した期待結果で候補が除外されれば、競合しない。
- 適応順位、部分型による優先、非ジェネリック優先、既定値の使用数、第三候補の優位性では、競合を解消しない。

```kimi
func select(value: Node ! flag: bool) -> i32 => 1
func select(value: ref/Node ! flag: i32) -> i32 => 2

let node = Node.init(10)
select(node, flag: true) // 借用版は flag の型で除外。値渡し版（Non-Copy なら Copy 不成立のエラー）。
select(node, flag: 0)    // 値渡し版は flag の型で除外。借用版。

func combine(left: Node, right: ref/Node) -> i32 => 1
func combine(left: ref/Node, right: Node) -> i32 => 2

let a = Node.init(1)
let b = Node.init(2)
combine(a@copy, b)     // エラー：b に競合が残る。a の適応順位では解消しない。
combine(a@copy, b@ref) // 第一の候補。第二の候補は right に ref/Node を受け取れない（Node は read Type ではない）。
```

### 3.3. Copy 条件を順位付けの前に置く理由

C と S 以外の適応もあるため、Copy の検査を選択後へ移すと、C の候補が順位で勝ったあとに Copy で失敗し、従来有効だった呼出しを拒否してしまう。依存引数の期待型を手順3より前の候補で決めた場合も、同じ理由で匿名関数や入れ子呼出しの検査が失敗する。

```kimi
func route(value: obj/Node) -> i32 => 1
func route(value: objref/Node) -> i32 => 2

func visit(value: obj/Node, make: () -> i32) -> i32 => 1
func visit(value: objref/Node, make: () -> i64) -> i32 => 2

func objectCase(handle: obj/Node) -> i32
    let first = route(handle)                // 2。値渡し版は手順3で除外（obj/Node は Non-Copy）。
    let second = visit(handle, func () => 1) // 2。残る候補の () -> i64 で匿名関数を検査する。
    return first + second
```

object の共有借用は S ではないので、これらの呼出しは競合しない。依存引数は SPEC §10.5 により、共通の期待型か確定した一候補で検査され、候補を選ばない。そのため、手順2・3を依存引数より先に行っても競合の判定は変わらず、依存引数の位置で C/S 競合は生じない。

owner の Place では、競合がなければ全候補が C か全候補が S なので、手順3は全候補を残すか全候補を除外する。したがって、同じ候補集合と同じ宣言条件の判定のもとで、裸の取得に必要な Copy 能力だけを理由に値渡し版と借用版が入れ替わることはない。宣言された Constraints（`T is Copy` など）による候補の適用可否の差は、この保証の対象外である。

### 3.4. 適用範囲

- 直接呼出し、メソッドの明示引数、コンストラクター、Contract 経由の候補選択に共通して適用する。
- 演算子と添字にも、既存の構文と公開契約が供給する候補・取得計画に対して同じ判定を行う。新しい候補や暗黙の権限は導入しない。現行の Indexable は key を `ref/Key` で受け取るため、その契約だけでは競合は生じない。
- 固定シグネチャの関数値の呼出しと、そのシグネチャによる関数参照の選択には候補間の競合がなく、通常の取得合法性だけを検査する。

### 3.5. ジェネリック

- `T` や `s/U` の Place も、既存規則が作る取得計画で判定する。新しい型の列挙、一般的な論理ソルバー、実体化時の再選択は追加しない。
- Semantics ペアの条件付き計画は、既存の有限な admitted set のケースごとに判定し、**同じケースで C と S が共存すれば定義時に競合**とする。別々のケースの計画を組み合わせない。
- 制約のない `T` は参照型も含む。C と S の両方の計画が成立すれば競合とする。計画を確定できない場合や、S が成立せず Copy も証明できない場合は、既存の定義時エラーとする。新しい暗黙のスロット借用で補わない。
- ジェネリック本体は公開された Constraints だけで判定し、実体化時に候補を選び直さない。`Option<T>` などの条件付き Copy の型も同じ検査を受ける。

```kimi
func f<U>(value: U) -> i32 => 1
func f<U>(value: ref/U) -> i32 => 2

func g<T>(x: T) -> i32
    T is ObjectPayload // T が owner の完全値型であることを証明する。Copy は証明しない。
    return f(x)        // エラー：C/S 競合。T is Copy を追加しても競合のまま。

func borrowExplicitly<T>(x: T) -> i32
    return f<T>(x@ref) // x のスロットを明示的に共有借用し、借用版を選ぶ。

let node = Node.init(10)
f(node)           // エラー：取得競合。
f(node@ref)       // エラー：一般の曖昧性。両候補とも引数型 ref/Node の Exact で同点。
f<Node>(node@ref) // 借用版を一意に選ぶ。
f(node@copy)      // 値渡し版。Copy した一時値は値渡し版で Exact になる。
```

## 4. 診断と回復

### 4.1. 診断

Language Error `AcquisitionRequired_Kd` を新設する。

- **単位：** 競合するソース引数ごとに一件、ソース順に報告する。同じ引数を候補の組ごとに重複して報告しない。
- **位置：** 主範囲は引数式。関連位置は各候補のシグネチャと、対応するパラメーター。
- **Reason：** Place の値取得（Copy）と新規共有借用が競合した事実と、必要な型・取得方法を示し、省略上限の下でも残す。Non-Copy のときに「両方が適用可能」とは説明しない。
- **Advice：** 書かれた引数式全体に付ける `@ref`、Copy を証明できる場合の `@copy`、Take が可能で移譲を意図する場合の `@move` を示す。`r@follow` なら `r@follow@copy` のように付け、内側の `r` を置き換えない。括弧と評価順を保つ。
- **具体的な修正：** 明示型引数の補足を含め、呼出し先が一意に決まると確認できた修正だけを提示する（例：`f<Node>(node@ref)`）。確認できない場合は条件付きの Advice にとどめる。
- **保証の区別：** 修正の保証が呼出し先の一意性までか、Copy・Take・Loan・寿命まで検証済みかを区別する。意味の異なる修正を自動で選ばず、Advice の文章を機械適用できる編集として扱わない。

### 4.2. 回復

- 競合した呼出しは invalid のままとし、呼出し先・取得計画・結果を確定しない。候補の結果型とカテゴリが一致しても、結果の Loan・Origin 依存や効果まで同じとは限らないので採用しない。
- 依存引数の期待型を決められないことを含め、競合に依存する後続の診断は SPEC §23.3.6.4 の前提関係で扱う。競合がない呼出しで依存引数の期待型を決められない場合は、既存の推論境界エラーとする。
- 候補の試行は Copy・Move・Loan を実行も確定もしない。ただし、引数の内部にある明示操作や内側の呼出しを巻き戻さず、独立したエラーも隠さない。依存する所有権解析を続けられない場合は、その検査を未完了として扱う。

## 5. Uniform Borrow Acquisition 案との関係

[同日の提案](2026-10-01%20Uniform%20Borrow%20Acquisition.md) と、裸取得の規則の管理先を SPEC §3.5 に一本化する。

- SPEC §3.5 の表で「Copy（証明が必要）」「同じ Semantics の再借用」「条件を満たさない取得の拒否」「一時値の転送」を区別する。本案はその Copy の行（C）と SPEC §10.2 の S の行を参照する。
- 期待型のない `uniq/T`・`objuniq/T` の再借用は相手案の変更であり、本案だけでは追加しない。相手案の採用後も、同じ Semantics の再借用は C でも S でもない。
- 条件付き計画に Copy のケースが含まれる場合は本書 3.5 に従う。再借用を先に行ってから適応する連鎖や、新たな暗黙のスロット借用は導入しない。
- 取り込みは、本案、相手案（採用された場合）の順を推奨する。逆順の場合も、後から取り込む側で SPEC §3.5 と §10.2.1 を照合し直す。相手案の「Copy による値渡し候補の優先は変更しない」という文は単独での変更範囲を述べたものであり、合流後の仕様には残さない。
- 両案の依存関係、取り込み順、置き換える文を、正式仕様の変更と同じコミットで `draft/INTEGRATED.md` に記録する。本案の承認から、相手案の receiver・capture の採否を推定しない。

### 6.2. 性能方針

- 実行時の機構は追加しない。
- 競合検査は、候補数 `n`・明示引数数 `a` に対して `O(na)` 時間、追加領域は再利用可能な `O(a)` とする。
- 条件付き計画は既存の有限な表現を走査し、ケースの直積を新たに作らない。
- 候補が一つなら競合検査を省く。他の事前判定やキャッシュは、競合が起こり得ないと証明できる場合だけ省略に使い、不明なら通常の検査へ進む。
- Copy 証明の重複は減るが、早期除外が減る分の費用もあるので、高速化は測定前に主張しない。

## 8. 設計判断

### 8.1. 採用しなかった案

| 案 | 不採用の理由 |
| --- | --- |
| 適用可能な二候補だけを競合とする（弱い規則） | 明示の要否が Copy 能力に依存する |
| 共有借用を常に優先する | 意図を順位に隠し、他の引数の順位との関係も残る |
| 値渡しと借用の同名宣言を禁止する | 他の引数で区別できる組まで失う。ジェネリック代入後の重なりの判定が単純でない |
| Copy の検査をすべて選択後へ移す | 本書 3.3 の object の例で、従来有効な呼出しを拒否する |
| 依存引数の期待型を手順3より前の候補で決める | 同じ例で匿名関数・入れ子呼出しの検査が失敗する。依存引数は候補を選ばないので、手順3の後に検査しても競合の判定は変わらない |
| 宣言側で常に警告する | 明示呼出しで使う意図的な API にも警告が出る。ジェネリック・条件・ラベルの重なりを形だけで正確に判定できない。呼出し側の診断で両宣言を示す |
| 冗長な `@copy` を知らせる hint | Copy はスナップショット・借用先・寿命・後続引数との合法性を変え得るので、直後に借用するだけでも冗長とは証明できない |
| 結果型が一致すれば、競合した呼出しの結果を採用する | 結果の Loan・Origin 依存や効果まで同じとは限らない |

### 8.2. Kimigayo Principles との対応

- **原則1：** 新しい選択構文を作らず、既存の取得操作と、SPEC §3.5 に一本化した取得規則を使う。目的が違う API は別名で表す。
- **原則2：** 呼出し位置と公開シグネチャで競合を説明し、実体化・探索順・Loan 状態で選び直さない。
- **原則3：** 所有権の扱いが競合する位置だけに明示を求め、競合のない呼出しは簡潔に保つ。
- **原則4：** 原因・関連位置・修正条件を構造化した診断を出し、検証の証拠を正確なソースと構成に結び付ける。

### 8.3. 残る確認

本書は仕様・ソース・既存テストとの静的な照合による。新しい規則の実装・実行試験・性能測定は未実施である。残る確認は、既存の呼出しへの影響数、ジェネリックの記号的な全経路への対応、Copy 証明の共有と診断の修正案の実際の費用である。
