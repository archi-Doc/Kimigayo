# 仕様変更・実装計画：コンストラクターと共通の型推論

日付：2026-10-07。状態：採用方針をまとめた提案。正式仕様への取り込み・実装・実行検証は未実施。

## 1. 位置づけと方針

**本書の変更事項は、[SPEC.md](../../docs/SPEC.md) およびその参照先より優先する。変更しない事項には既存仕様を適用する。** 今回の変更対象は本書だけとする。将来の取り込みでは変更事項を正式仕様へ統合し、正式仕様を本書に依存させない。

対象は、コンストラクターの型引数推論、通常関数と共有する推論規則の整理、取得形状と候補選択の改善である。

> 通常の構造照合で完了する推論を認め、取得方法の一致を確かめるための追加探索が必要なら、型引数を明示必須にする。

- **一貫性：** コンストラクター専用の推論言語を設けず、共通規則へ構築対象自身のスロットを接続する。
- **局所性：** 型宣言と外側の環境を先に決める。後続の使用、本体の探索、具体型の列挙で推論しない。
- **明示性：** 推論は Copy・Move・Borrow・変換を実行しない。所有権と失敗の規則を保つ。
- **性能：** 一般的な形を速く処理し、難しい省略形には明示を求める。可否を処理時間・マシン・キャッシュ状態で変えない。
- **検証可能性：** 型、選択した宣言、取得計画、根拠と依存を保持し、診断・後段・検証で共有する。

## 2. 一般的な型推論の整理

### 2.1. 共通の規則

通常関数とコンストラクターは、SPEC §8.1・§10・§15 の推論と適合を共有する。関数自身のスロットと構造体自身のスロットは、宣言上の Identity を保って区別する。

1. 明示済みの型引数、外側の環境、既に固定された束縛を保持する。
2. 候補ごとに位置・名前付き引数を対応付け、省略されたデフォルトを記録する。
3. 独立に型が決まる引数・受け手から構造と Semantics の制約を集める。既知の呼び出しシグネチャ、匿名関数のヘッダーに書かれた型も、§10.5・§10.8 の範囲で照合する。
4. 独立に既知の期待結果型で、まだ束縛されていない部分だけを補う。引数から決まった型を変更しない。
5. 既存のリテラル適合・既定型・適用可能性判定を行い、§10.4 の候補比較を行う。リテラルの既定型でオーバーロードの同順位を破らない。
6. 選択後に待機する引数を既存規則で完成させ、未解決スロットと必要な義務を検査する。取得操作を確定し、Origin 関係・初期化状態・Loan・破棄を検査する。失敗しても選び直さない。

これは論理上の依存関係であり、独立したパス数を要求しない。構造・Semantics・Origin の制約収集は既存の固定点規則に従い、引数や候補の走査順で結果を変えない。

**未確定と不一致を区別する。** 情報不足のスロットだけを理由に候補を除外しない。独立に検査できる部分を検査し、未解決部分の比較・待機引数の扱いは §10.8 に従う。選択後に未解決なら診断し、その結果に依存する検査を派生失敗として扱う。

**Origin と候補選択を区別する。** 完全型の内部依存を保持し、通常の Origin 関係・Loan の不成立を候補除外や順位に使わない。`Owned`・`Callable` など Origin を含む制約の証明は、既存の適用可能性規則を維持する。領域変数の同一性、関係の解決、実際の Loan 生存性を混同しない。

### 2.2. 推論の境界

| 利用する情報 | 利用しない情報・探索 |
| --- | --- |
| 明示型引数、固定された外側の環境、独立な引数型 | 宣言後の使用からの逆向き推論 |
| 同じ名目型・Tuple・既存の配列形などの構造照合 | 共通基底型、暗黙変換経路、具体型の列挙 |
| 既知の呼び出しシグネチャ、匿名ヘッダーの明示部分 | 待機する匿名本体・関数参照・入れ子呼び出しの結果による外側スロットの補完 |
| 独立した期待型の既知部分 | 外側の候補ごとに内側の呼び出しや本体を再解析する組み合わせ探索 |
| 既存の限定的な制約証明・Origin 推論 | 関連型の逆算、一般的な定理証明、制約の強さによる順位付け |

デフォルト引数、フィールド初期化式、コンストラクター本体は推論の根拠にしない。関連型は、元の型が他の情報で決まった後に通常どおり解決・検査できる。

型引数は全指定またはリスト全体の省略とし、部分指定、`_`、型引数のデフォルト、構造体の長さパラメーターを追加しない。一般の深い型を一律に禁止せず、既存の資源上限を適用する。資源上限への到達は、省略を認めない形や曖昧性と別に報告する。

enum Case、配列リテラル、`try` など固有の期待型境界は変更しない。特に enum Case の期待型主導の規則を、通常関数・コンストラクターの引数優先の規則へ置き換えない。

### 2.3. 共通の取得形状契約

目的は、**対応する引数の照合範囲が重なるとき、取得モードが選ばれた候補に依存しないこと**である。完全型の一致はその十分条件であり、常に必要ではない。取得形状の要約は次の三つに統一する。

| 要約 | 内容 |
| --- | --- |
| 取得モード | 外側の Semantics による `ByValue`・`Shared`・`Exclusive` の有限集合 |
| 照合キー | 既存の `Value(U)`・`Object(U)` など。構造的な重複判定に使う |
| 束縛の相関 | 同一モード・非重複の証明に必要なスロット間の同一性と、その根拠・依存 |

Origin・Loan の追加証明を取得形状のために行わない。取得形状で不要な Origin 情報も、型・適合計画では保持し、既存の段階で検査する。

#### 2.3.1. 宣言時に契約を作る

SPEC §7.3.1 の対応位置・照合キー・取得モードを維持し、「同じ束縛だから検査を免除する」という部分を、次の条件付き契約に置き換える。

1. **独立な束縛で検査する。** 呼び出しで推論するスロットは候補ごとに別変数とする。構造体自身のスロットも含む。固定された外側の同じ束縛は共有する。
2. **無条件の結果を保存する。** 独立な束縛の許される各組み合わせで、同一モードまたは構造的非重複なら、呼び出し時の追加条件は不要である。モード集合が等しいだけでは十分でない。
3. **既存の共有関係を条件にする。** 残る組について、同じ構造体スロット、同じ形の型引数リストの同番号スロットを同一と仮定して検査する。同じ投影は元の束縛の同一性に依存する。この仮定で安全になる組は、比較する型パターンで共有扱いにした関係の全体を契約に残す。最小条件集合や、任意の型の等式・制約の組み合わせを探索しない。
4. **それでも競合する宣言は拒否する。** 固定された `Node` と `ref/Node` のように、共有を仮定しても重なる異モードの組は従来どおり不正である。使用箇所で集める群は、そこで同じ契約を作る。

これは宣言検査をなくす変更ではない。従来共有されていた構造体スロットを推論する場合の非重複証明と、通常関数の同番号スロット・同じ投影による免除を、根拠付きの条件へ変更する。ほかの宣言規則、明示型引数による候補集合、異なる型引数リスト間の扱いは維持する。

例えば次の宣言は、`T` を共有すると非重複だが、独立に推論すると重なり得る。

```text
C<T> の候補：init(value: (T, i32),     tag: i32)
             init(value: ref/(i64, T), tag: string)
value の元の型：(i64, i32)
```

一つ目は `T = i64` で ByValue、二つ目は `T = i32` で Shared となる。`tag` で候補を絞って取得方法を変えてはならず、この省略形は拒否する。型引数を固定すれば従来の非重複証明を使える。選ばれた候補だけの確認では、この問題を防げない。

#### 2.3.2. 呼び出し時に条件を確認する

対象は、名前解決で確定した群全体である。引数数、ラベル、デフォルト、制約、条件、期待型による候補の除外を、取得形状の検査免除に使わない。対応付けが失敗しても確定できた部分対応を保持し、宣言の契約を次の有限な根拠だけで確認する。

| 根拠 | 認める範囲 |
| --- | --- |
| 単一宣言、無条件の同一モード・非重複 | 保存した結果を使う |
| 明示・環境から供給された固定束縛 | 必要な相関を直接確認する |
| 同じ実引数の独立した完全型 | 同じ構造位置・同じ推論規則から得る束縛を共有できる |
| 同じ未確定入力から得る束縛 | 下記の共通未確定束縛として扱う |
| 独立した期待型 | §2.1 の順序で未束縛部分を補った結果が共通の場合だけ使う |

**共通未確定束縛：** 同じ実引数の同じ構造位置から、同じ推論規則と同じ依存情報で得る束縛は、具体型が未確定でも同一の記号として比較できる。ただし、その束縛を変え得る他の引数・期待型などの根拠も一致し、候補固有の追加根拠がないことを要する。式の Identity と抽出経路・依存を比較し、候補の制約を一つに混ぜて解かない。リテラル適合・既定化は既存の時点で行い、既定型で同順位を破らない。

同じ取得モードと分かれば完全型の一致まで求めない。それでも必要な相関を直接確認できない省略形は、呼び出し全体を拒否して明示を求める。関連型の逆算、変換探索、候補除外による追加証明、待機本体の解析を根拠に加えない。通常の正方向の関連型解決と待機引数の完成は、§2.1–2.2 に従う。

この契約を通常関数とコンストラクターで共有する。条件付きの宣言自体は有効であり、条件を満たす明示形・固定束縛の呼び出しは引き続き利用できる。

## 3. コンストラクターの型引数推論

### 3.1. 型名の確定と推論対象

`A.init(arguments)` で、構築対象 `A` 自身の型引数リストを省略できる。構文は追加せず、型宣言と外側の環境を確定した後、その宣言自身の未束縛スロットだけを推論する。

通常の名前・役割・アクセス解決で検索段階を確定し、同じ段階の候補を次の規則で選ぶ。参照の同一性には宣言と正規化した外側の束縛を含み、同一参照は重複除去する。

| 省略形の型候補 | 選択 |
| --- | --- |
| 自身の型引数数がゼロの候補がある | ゼロの候補を選ぶ。同順位に複数の異なる参照があれば曖昧 |
| ゼロの候補がなく、ジェネリックな参照が一つ | その宣言を選び、自身の型引数を推論 |
| ジェネリックな参照が複数 | 曖昧。型引数・修飾を明示する |

期待型やコンストラクター引数で別の型宣言を選ばない。選択後の不適合でも検索段階を戻らない。後から同名の非ジェネリック型を追加すると、省略形がそちらを指す可能性がある。

`Outer<i32>.Inner.init(v)` は `Inner` 自身の引数だけを推論する。未束縛の `Outer<T>` を `Outer.Inner.init(v)` の引数・期待型から補わない。字句環境、`Self`、継承経路、alias 経由のコンテナ参照が既に供給した束縛を維持する。基底コンストラクターの対象型も基底宣言から固定する。具体型の名前付き alias は追加しない。

`init` に独立したジェネリックパラメーター、結果注釈、関数値化、継承・拡張コンストラクター、型パラメーター自体の構築を追加しない。構築結果は従来どおり owner である。

### 3.2. 期待型

期待型からの補完は、同じ構造体宣言・同じ外側の環境の owner 型との直接の構造照合に限る。借用、object 化、上方変換、ユーザー変換を逆向きにたどらない。型引数が決まった結果への通常の適合は維持する。

```kimi
let n: i32 = 42
let a: A<i64> = A.init(42) // 未確定のリテラルを i64 に適合
let b: A<i64> = A.init(n)  // エラー：引数から決まった i32 を変更しない
```

### 3.3. 明示形との同値性

**推論が成功した構築式は、その推論結果を構築対象へ明示的に束縛した構築式と、同じコンストラクター、結果型、引数評価順序、取得・構築・破棄動作を持つ。** ABI、実行時の割り当て、単相化の識別にも省略の有無を持ち込まない。ソースで直接綴れない具体的 Closure 型なども、完全型の束縛として同じ保証を適用する。

取得形状だけでは、この保証は導けない。例えば次の二つは両方 Shared だが、推論と固定型への適合は異なる。

```text
C<T> の候補：init(x: ref/i32, y: ref/T)
             init(x: ref/T,   y: ref/T)
実引数の型：x は ref/ref/i32、y は ref/i32
```

省略形では一つ目が `T = i32` となり、二つ目は推論が矛盾し得る。一方、`C<i32>` を明示すると両者のパラメーター型が等しくなり、曖昧になり得る。この省略形を成功扱いにしない。

可否は、次の**固定束縛による基準検査**で定義する。最適化の有無や実装の証明能力で変えない。

1. 推論で選んだ宣言と構築型を仮の結果とする。元の群全体を保持し、推論矛盾などで不採用になった宣言も検査対象へ戻す。
2. 構築型の引数を固定し、元の引数対応・独立した入力情報から、通常の適用可能性と最良候補を判定する。リテラルは元の未型付けの情報から適合させ、候補内の適合結果を独立な入力型として使わない。
3. 次の結果に従う。名前検索、追加の型推論、具体型の列挙、候補別の待機本体解析は行わない。

| 基準検査の結果 | 省略形の扱い |
| --- | --- |
| 同じ宣言が唯一の最良候補 | 受理できる。固定束縛と元入力による共通の適合・取得計画を使う |
| 別の宣言・候補なし・曖昧 | 明示必須。別候補へ切り替えない |
| 判定に別の期待文脈での待機引数解析など、禁止した探索が必要 | 明示必須。解析を試して選択を救済しない |

待機情報は §10.5・§10.8 の境界まで未完成のまま扱う。型引数を固定するときも、引数へ既に与えた期待文脈・呼び出しシグネチャを保持する。その文脈での一回の完成により `F` が具体的 Closure 型などに決まる場合は、完成結果を検査し、固定後の型から本体を再推論しない。結果を別の期待文脈や他候補への独立した型情報に流用しない。単一候補もこの規則に従い、待機していること自体を拒否理由にしない。

単一候補や差分のない検査を省略する場合も、この基準検査と同じ結果を要求する。実際の取得・Loan・破棄の検査は選択後に一度だけ行う。この追加保証はコンストラクターに限り、通常関数の明示型引数による候補集合の変更は維持する。

### 3.4. 例

以下は本書による動作であり、実装済みの宣言ではない。シグネチャだけの例は本体などを省略している。

```kimi
struct A<T>
    public let value: T
    public init(value: T)
        self.value = value@move

let n: i32 = 42
let a = A.init(n)          // A<i32>
let b = A.init("hello")    // A<string>
let c = A.init((n, true))  // A<(i32, bool)>
let d = A.init(n@ref)      // A<ref/i32>。n への依存を保持
let outer = A.init(a@move) // A<A<i32>>

func wrap<T>(value: T) -> A<T>
    return A.init(value@move)

struct Empty<T>

let e: Empty<i32> = Empty.init() // 期待型で補完
let f = Empty<i32>.init()       // 明示も可能
// let g = Empty.init()         // 情報不足。型引数または型注釈が必要
```

| シグネチャ・呼び出しの形 | 結果と理由 |
| --- | --- |
| `Item<T>` の `init(value: T, code: i32)` と `init(value: T, name: string)` に、型が既知の `n: i32` を第一引数として渡す | 同じ元の完全型から `T = i32`。通常の選択が可能 |
| 同じ `Item<T>` に `Item.init(42, 0)` と書く | 第一引数の共通未確定束縛を使える。第二引数で一つ目を選び、通常の既定化で `T = i32` |
| `Holder<T>` の唯一の `init(value: T.Element)` に `i32` を渡す | `T` を逆算しない。型引数または直接の期待型が必要 |
| 唯一の `init(value: T.Element, witness: Tag<T>)` に `Tag<K>` を渡す | witness から `T = K` を決め、`K.Element` を検査できる |
| `Choice<T>` と `Choice<T, U>` が同じ検索段階にあり `Choice.init(v)` と書く | 型宣言が曖昧。型引数・修飾を明示 |
| `Outer.Inner.init(v)` で `Outer<T>` が未束縛 | 外側を推論しない。`Outer<i32>.Inner.init(v)` などと書く |
| `ref/Empty<i32>` を要求する位置へ `Empty.init()` を渡す | 借用を逆算しない。`Empty<i32>.init()` なら通常の一時値借用を検査できる |
| Non-Copy の `text: string` に `A.init(text)` と書く | 型は推論できるが取得が不正。`A.init(text@move)` が必要 |

共通未確定束縛を使えない例は、`C<T>` の `init(value: T, witness: Tag<T>, code: i32)` と `init(value: T, witness: Tag<ref/T>, name: string)` である。`value` に `42`、`witness` に `Tag<ref/i32>` を渡すと、他の引数からそれぞれ `T = ref/i32` と `T = i32` が決まり、Shared と ByValue に分かれる。第一引数が同じリテラルでも相関を保証できず、明示必須となる。

投影も同じ規則で扱う。`init(value: T.Element, witness: Tag<T>)` と `init(value: T.Element, witness: Tag<Wrap<T>>)` に `Tag<Wrap<K>>` を渡すと、`T = Wrap<K>` と `T = K` に分かれ得る。`Element` の同一モードを直接確認できなければ、追加探索せず明示を求める。明示後も通常の曖昧性・型不一致・所有権違反は検査する。

## 4. 性能改善

### 4.1. 候補比較を二段階にする

§10.4 の「ほかの全候補より厳密に優れる候補を選ぶ」という意味を維持し、通常関数・コンストラクターの共通処理で採用する。

```text
対象がゼロなら適用可能候補なし
p = 最初の対象候補
残りの c を一巡：better(c, p) なら p = c
すべての c != p に better(p, c) が成り立つ場合だけ p を選択
それ以外は曖昧性エラー
```

`better` は固定された判定時点の候補情報だけを読む非対称な関係であり、`better(a, b)` と `better(b, a)` は同時に成立しない。推論状態を変更せず、同順位・比較不能は厳密な優位としない。待機・未解決部分は §10.8 の比較を保ち、Origin・Loan を順位に使わない。後段の失敗で選び直さない。

全候補に勝つ候補は一巡目で必ず残り、存在しなければ二巡目で拒否される。推移律は不要である。`K` 候補の比較回数は最悪 `O(K²)` から最大 `2(K−1)` の `O(K)` になる。型の深さ・引数数・制約検査を含む推論全体が線形になるという保証ではない。失敗時に診断の追加比較が必要でも、候補や説明を省略して高速化しない。

### 4.2. 重複処理と割り当てを減らす

| 改善 | 方針 |
| --- | --- |
| 引数の対応付け | 候補ごとに一度作り、型・Origin 推論、適合、デフォルト、取得計画で共有。`ConstructorType` と通常の候補検査の重複を解消 |
| 安価な前処理 | 引数数・名前など確定した不一致を先に処理。ただし §2.3 の契約確認に必要な情報や独立したエラーを消さない |
| 既存の高速経路 | 明示済み・非ジェネリック・単一候補の不要な推論や保存処理を避ける |
| 取得形状 | 候補別の独立スロットで宣言時に重複を調べ、無条件の結果と必要な相関を保存。呼び出し時は有限の関係を確認し、全候補の組を再単一化しない |
| 差分検査 | 各適合・制約・棄却理由に依存スロットと判定前提を記録。固定束縛への移行で影響を受ける部分だけ再検査 |
| 固定点計算 | 同じ依存情報を worklist・キャッシュ無効化と共有し、変化した部分だけを再処理 |
| 作業領域 | 連番スロット、scratch buffer、既存の interning を再利用。候補ごとに AST・型パターンを複製せず束縛表を保持 |
| 後段処理 | 必要な型の適合・形成検査は行うが、単相化・レイアウト確定・コード生成を不採用候補のために開始しない |
| 診断 | 失敗理由を構造化した事実として保持し、公開が必要な時だけ文章化 |

§3.3 の差分検査では、引数数・名前の不一致など、束縛に依存しない結果を再利用できる。一方、推論矛盾は固定型への適合で解消し得るため、候補を復活させて検査する。依存には型引数の値だけでなく「推論か固定型への適合か」も含める。最適化経路は基準検査と照合し、受理・拒否・選択・診断の根拠を一致させる。

キャッシュは宣言・ソーススナップショット・構成・外側の束縛・証明依存関係に結び付けて無効化する。型名だけで呼び出し固有の Origin・Loan を共有しない。スロット数の固定ビット幅を言語上限にせず、大きい入力にも保持容量が有界な経路を用意する。

省略形のための実行時の型探索、boxing、共通 Function Type への追加消去、中継関数を導入せず、具体的 Function Item／Closure 型を保持する。実行時の同値性は §3.3 に従い、速度向上率は約束しない。

## 5. 診断とコンパイラサービス

次を区別し、主範囲、根拠の引数、候補宣言、未確定スロットを必要に応じて示す。

1. 型名の不明・役割違い・アクセス違反・型宣言の曖昧性。
2. 型引数の情報不足と、構造／Semantics の矛盾。
3. 取得形状の宣言違反、省略形で確認できない相関、および固定束縛での選択の不一致・追加文脈の必要性。
4. 通常のコンストラクター不適合・曖昧性、制約違反。
5. 選択後の Origin・Loan・Copy・Move の違反と、資源上限。

型引数を明示する修正候補は、対象スナップショットと確認できた型・選択の前提を伴うものだけを出す。未知の型を推測して挿入しない。明示後も曖昧になる例やソースで綴れない具体型には、不可能な修正を約束せず Advice を示す。必要なら、名前を持つ型パラメーターで構築型を明示するジェネリック helper を案内する。

CLI・JSON・LSP と公開意味情報は、同じ確定済みの構築型・宣言・取得計画・根拠を使う。前提不足による派生失敗と独立した問題を分離し、診断の削減を受理や品質改善の代わりにしない。

## 6. 実装計画

入口は [CODEMAP](../../docs/dev/CODEMAP.md) に従う。下表の `Binding.*` は `src/Kimi/Compiler/Binding/` 配下のファイルを指す。コンストラクターを架空のジェネリック関数や公開 factory に変換しない。

| 単位 | 内容・主な入口 | 完了条件 |
| --- | --- | --- |
| U0：境界を固定 | 本書の正例・拒否例、候補順序、明示形との同値性、性能の基準入力を用意 | 各検査へ到達する最小再現例と独立した期待値。現行の実測基準を保存 |
| U1：比較を共通化 | `Binding.CandidateEvaluation` の純粋な対比較と二段階選択 | 総当たりの参照判定と一致。順序・比較不能・待機・診断を維持し、比較回数と時間を測定 |
| U2：推論の準備を共有 | `Binding.Calls`・`Binding.Structs`・`Binding.InferenceBoundaries`・`Binding.OriginInference`。引数対応表、スロット所有者、作業領域を整理 | 通常関数と明示コンストラクターに回帰なし。対応付けを候補内で再実行しない |
| U3：取得形状の契約 | `Binding.ParameterShapes` にモード・キー・相関を集約。独立スロット、条件付き宣言、共通未確定束縛を導入 | 非重複証明の前提を保持。通常関数・構築式で正例と候補依存の拒否例が一致 |
| U4：構築型の推論 | `ConstructorMember`・`ConstructorType`・`TryCandidate`・`Infer`。型名選択、型形成、固定束縛の基準検査と依存付き差分検査 | 宣言・外側を固定し自身のスロットを推論。基準検査と最適化経路の結果が一致 |
| U5：確定と公開 | Binding の確定済み計画から Ownership・Emission・診断へ接続 | 明示形との宣言・取得・ABI・破棄の一致。CLI・JSON・LSP の説明と修正条件を検査 |
| U6：統合と測定 | 共通回帰、native O0/O2、Benchmark、再 Bind・invalidate・保持容量 | §7 の検証と測定を完了。残る制限は明示し、未検証を対応済みとしない |

U1 と U2 は既存呼び出しの意味を変えない単位として先行できる。U3・U4 は取得形状の前提を崩した中間実装を公開しない。新しい通常関数の境界は、本書による意図的な仕様変更として正例・拒否例を同じ単位に含める。

## 7. 検証と完了条件

### 7.1. 機能・診断

- 単一／複数スロット、Semantics pair、Tuple・入れ子型、既存の関数長さ推論、既知の Callable、ヘッダー明示、待機引数。
- 同名・異なる型引数数、同じ宣言の異なる外側束縛、名前付き引数、デフォルト、`Self`、基底構築、alias 経由の経路。
- 期待型による補完と衝突、情報不足を理由に候補を消さないこと、関連型の正方向解決と逆算拒否。
- 取得形状の無条件／条件付き契約、共有スロットに依存した非重複の反例、固定モードだけで十分な例。共通リテラルと候補固有の追加根拠を対比し、通常関数にも適用。
- §3.3 の候補復活と基準検査の三結果。基準検査・差分検査・省略経路を照合し、単一候補の Closure 完成と別文脈での再解析禁止を確認。
- 所有値・共有／排他参照・Non-Copy・Origin・Loan・制約、独立した複数エラーと各出力アダプター。
- 総当たり対比較を独立したテスト用 oracle とし、同順位、非推移的な関係、比較不能、優位候補なしを二段階方式と照合。契約確認も含め、候補順序・キャッシュ有無で結果が不変。
- 明示形／推論形の結果・副作用順・取得計画・破棄を native O0/O2 で比較。診断文と範囲は人が読んで確認する。

既存回帰の入口は `CallCompletionBindingTest`、`CallAdaptationTest`、`CallReservationTest`、`ParameterShapeTest`、`CallableSignatureInferenceTest`、`AnonymousArgumentInferenceTest`、`AggregateArgumentInferenceTest`、`GenericDefaultTest`、`StructEmissionTest`、`GenericStorageEmissionTest` とし、新規の構築型推論回帰を追加する。実装時には依存を追って選択範囲を確定する。

### 7.2. 性能・作業手順

明示形を基準に、候補数・引数数・スロット数・型の深さ・呼び出し数を変える。成功、曖昧性、情報不足、明示必須、型矛盾を分け、cold／warm の時間・割り当て・保持容量を固定条件で測定する。候補比較、引数対応付け、相関確認、固定点の再処理、固定束縛で再検査した候補・義務の数を記録する。

時間測定は `src/Benchmark`、allocation/reuse 回帰は `Purpose=Allocation` に分離する。既存のゼロ割り当て・保持容量の条件を緩めず、失敗を追加 warming で隠さない。新規の明示形経路を不必要に遅くせず、キャッシュ後の省略形の負担が型構造と候補数に対して有界であることを確認する。

各実装単位は再現例・実装・関連テストをそろえ、[VERIFICATION](../../docs/dev/VERIFICATION.md) に従い正式 Unit Verify 後に commit／push する。最後に Session Verify、関連 native fixtures と milestone、明示的な性能測定を完了する。Benchmark 変更には whole-solution Session build を含め、NativeAOT は実行しない。検証中はソースを変更しない。

検証証跡は `artifacts/verify/`、測定は `artifacts/benchmarks/` に、ソース・構成・結果・未解決事項とともに保存する。本書の作成・静的レビューだけでは、実装や性能の検証完了を意味しない。
