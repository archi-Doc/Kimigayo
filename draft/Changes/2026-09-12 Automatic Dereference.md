# 安全な参照の自動参照解除

状態：設計案。SPEC.mdへの適用は保留。安全な `*` は追加しない。

## 現状と目的

SPEC §3.3.6／§13.2は安全な `*` を認めない。一方、`self.field` の参照先へのアクセスや、`uniq/i32` の参照先の更新に必要な共通規則が不足している。§13.4の安全な参照の比較と§14.8のPatternによる参照先の検査は既に定義されているため、「安全な参照を読む操作が一切ない」という指摘は正確ではない。

メンバー・組込み演算子・引数取得に共通する参照先アクセスを定義する。参照値自体のCopy/Move、参照先の取得、変数の記憶域の借用を区別する。

## 基本案

一般的な自動参照解除は1操作につき `ref/V` または `uniq/V` の1層に限定する。`V`の型・Origin・Loanを保持し、追加の層を探索して成功する型を探さない。raw pointer、Object Semantics、継承投影、既存の比較・Patternにはそれぞれの専用規則を適用する。

| 使用箇所 | 提案する扱い |
| --- | --- |
| メンバー・Tuple要素・添字へのアクセス | 1層の参照先を受信先にする。標準Propertyは許されたPlace操作、計算Propertyは宣言済みの取得操作を使う。参照先の型でメンバー集合を確定し、失敗時に別の層へ戻らない。 |
| 組込み数値・ビット・論理演算 | 1層先が必要な組込み型なら共有アクセスで読む。数値変換や独自演算子は追加しない。論理演算は短絡評価を維持する。 |
| `++`／`--`・複合代入 | 1層先の整数等を対象とし、`uniq`による排他的書込みを要求する。受信先は1回だけ評価し、対象先行の評価順序を維持する。 |
| 引数・初期化子・戻り値 | 期待型が既に固定されている場合に限り、既存の適合で型が一致しなければ1層先からの取得を調べる。取得する完全型がCopyならコピーできる。非Copy値はMoveできず、既存のBorrow/Reborrowで期待する借用型に適合する場合だけ借りる。 |
| 期待型のない取得 | `let x = r` は参照値そのものをCopy/Moveする。後の使い方から参照解除を推測しない。 |
| 単純代入 | `r = other` は変数rへの代入を維持する。右辺の型やrの `let`／`var` によって代入先を切り替えない。参照先の全体置換には、下記の別操作が必要。 |

上記の取得規則は§10.7の関数シグネチャ互換性には適用しない。関数型間の互換性検査に参照解除を挿入すると、呼出し時の適合と型の関係が混同されるためである。

## 所有権と選択

- `ref/V` は共有アクセスだけを与える。`ref/uniq/T` から内側の排他参照をMoveしたり、排他的に使ったりしない。
- `uniq/V` でも参照先の非Copy値をMoveして空にしない。読取り・Reborrow・許可された更新を使い、全体置換は初期化を維持する。
- `let` が固定するのは参照変数のスロットであり、保持する `uniq` の参照先の書込み能力を失わせない。
- コピーした内側の共有参照は内側のOriginを保持する。参照先から新たに借りた場合は外側のLoanにも依存する。Originの短縮はLoanを消さない。
- オーバーロードでは既存の適合順位を優先し、自動参照解除を伴う適合をその後に置く。同順位は従来どおり比較し、解消できなければ曖昧とする。Loan・初期化検査の失敗で別候補を選び直さない。
- 型の未確定なジェネリック引数は参照を含む完全型から推論する。参照解除によって都合のよい型を推測せず、定義時に必要なCopy・型・受信先能力を検証する。
- 値の取得・短絡・代入の評価順序は既存規則を維持する。アクセスの形成時点から必要なLoanを有効にし、一時値の寿命を延長しない。

```kimi
// 以下は提案する動作。現行SPECの機能追加済み例ではない。
func bump(n: uniq/i32)
    n += 1

func read(n: ref/i32) -> i32
    return n // 固定された期待型i32に対し、参照先をCopy。

let reference = value@ref
let same = reference        // ref/i32をCopy。value: i32を仮定。
let number: i32 = reference  // 参照先のi32をCopy。
```

## 適用前の判断点

**参照先全体を置換する操作の表記が必要。** 1層の自動参照解除だけでは、`uniq/T` に新しいTを丸ごと書き込む表記は決まらない。

推奨は、単純代入の意味を維持したまま、明示的な書込み操作を定義すること。参照値を受け取り、その参照先を置換する。型・Originを維持し、旧値の破棄が新値の依存先を無効化しないことを検証する。具体的なAPI名、右辺先行の代入と受信先先行の呼出しのどちらの順序にするかを確定する必要がある。

§15.7のExchangeは旧値を返す初期化維持操作の意味を定義しているが、APIの表記と解決は未確定である。通常の置換とは旧値の破棄責任も違うため、既存の完成した書込みAPIとして扱わない。

これらを確定してから、SPEC §3／§10／§11／§12／§13／§15とコンパイラ検証要件をまとめて改訂する。最小限の検証例には、1層を超える参照、参照と値のオーバーロード、Copy不可、共有経由の排他アクセス、Loan競合、受信先の副作用、参照変数の再束縛と参照先の更新の違いを含める。
