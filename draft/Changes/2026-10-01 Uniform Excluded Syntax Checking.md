# 仕様変更案：条件付きコンパイルの除外構文の検査統一

日付：2026-10-01

状態：最終版。採用決定済み。正式仕様への取り込みと実装は未実施。

本書で変更する事項は SPEC より優先し、変更しない事項には既存仕様を適用する。SPEC の節は「SPEC §n」、実装仕様の節は「impl §n」、本書の節は「本書 n」と表記する。例の環境は、特記がなければ `x86_64-pc-windows-msvc`（`windows` は true、`linux` は false、`arch` は `"x86_64"`）とする。

## 1. 問題と方針

### 1.1. 現仕様の問題

SPEC §19.5 は、選択されない構文の検査を二通りに定めている。

| 検査 | 偽の `#if` の対象 | 未選択の `#case` アーム |
| --- | --- | --- |
| 通常の式・宣言の文法 | 省略 | 必須 |
| 入れ子の Condition の検証 | 省略 | 必須 |

この差と関連する規定から、次の問題が生じる。(1)〜(3) は、2026-10-01 時点の実装で確認した（`artifacts/verify/20261001-excluded-syntax-probe/`）。

**(1) 選択を保つ書換えで、受理・拒否が変わる。**

```kimi
// 書き方A：独立した二つの #if
#if linux
    let pending =            // 書きかけの初期化子
#if not linux
    useDefaultPath()

// 書き方B：同じ選択を表す #switch
#switch
    #case linux
        let pending =        // 書きかけの初期化子
    #case _
        useDefaultPath()
```

二つはどの環境でも同じ項目を選ぶ。しかし Windows では A を受理し、B を `MissingSyntax_Kd` で拒否する。入れ子の Condition の綴り誤り（`#if useDirectWirte` など）も、A では見逃し、B では `UnknownCompileTimeName_Kd` になる。独立選択か排他的選択かは、除外部分をどこまで検査するかとは関係がない。

**(2) 選ばれないコードの受理が、環境の値に依存する。**

- **文法エラー：** 偽の `#if` の内部の文法エラーは、条件が真になる環境でしか見つからない。
- **入れ子の選択失敗：** SPEC §19.3 は、到達した `#switch` の選択失敗をエラーとする。到達には未選択アームの内部も含まれる。次の例は Windows x86_64 では `NonExhaustiveCompileTimeCase_Kd` になり、Windows aarch64 ではならない。

  ```kimi
  #switch
      #case linux
          #switch
              #case arch == "aarch64"
                  useArm64Path()
      #case _
          usePortablePath()
  ```

- **位置の規則：** `alias` は、通常の宣言と実行項目より前に置かなければならない（SPEC §18.1.1）。実装は選択された項目だけを数えるので、次の例は Windows でだけ `TopLevelKeywordAfterCode_Kd` になる。`#if linux` に書き換えると、結果は逆になる。関数の先頭の Constraint や Origin 関係の位置も、同じ仕組みで判定している。

  ```kimi
  #if windows
  func helper() => ()
  alias Kimi.Console
  ```

**(3) Error の Condition が、対象内部の独立したエラーを隠す。** 現在は対象の構造だけを検査して回復するので、対象内部の通常の文法エラーは報告されない。

**(4) 除外部分に構文木がない。** 偽の `#if` の内部は構造だけを走査するので、SPEC §23.5.3 が CSP に求める構文ノードのハンドルを与えられない。また、`#if` の対象の範囲は、真なら文法で、偽なら構造の走査で決まる。そのため、二つの規則が一致することを別に保証しなければならない。

### 1.2. 方針

1. 偽または Error の `#if` の対象と、選ばれなかった `#case` アームを、**除外構文**という一つの概念にまとめる。
2. 除外構文には、選択された構文と同じ構文の検査を行い、意味の検査は行わない。
3. ソース中のすべての Condition を検証する。
4. 選択と選択失敗のエラーは、除外構文の外のディレクティブにだけ適用する。
5. 位置の規則は、除外構文の項目も含めたソース順で判定する。個数と重複の規則は、選択された項目だけで判定する。
6. Condition Name の集合と型が全環境で同じであることを、不変条件として明記する。

これにより、構文・位置・Condition の診断が環境に依存しなくなる（本書 3.2 の保証）。

## 3. 仕様変更

### 3.1. 除外構文

**除外構文**（excluded syntax）は、次の部分と、その内部のすべてである。

| ディレクティブ | 除外構文になる部分 |
| --- | --- |
| Condition が False の `#if` | 対象 |
| Condition が Error の `#if`、またはヘッダーが不正な `#if` | 対象 |
| アームを選んだ `#switch` | 選ばれなかったアーム |
| アームを選ばない `#switch`（Condition の Error、構造のエラー、一致なし） | すべてのアーム |
| `#switch` の外にある `#case` | 本体 |

- 除外構文の内部のディレクティブは、何も選択しない。その対象とアームも、すべて除外構文である。
- `#if` の次の項目が `#switch` の外にある `#case` なら、その `#case` 全体が対象である。
- ディレクティブの前に書いた Attribute は、選ばれた構文に付く。選ばれる構文がなければ、その Attribute も除外構文に含まれる。

### 3.2. 検査の範囲と保証

| 検査 | 選択された構文 | 除外構文 |
| --- | --- | --- |
| 字句、インデント、ブロック構造 | 行う | 行う |
| 文法：式・Pattern・型・宣言・項目、修飾子と Attribute の配置、ディレクティブの配置と構造（SPEC §19.1）、ソースレベルの空でない本体（SPEC §14.2.1）、利用できない機能（`UnavailableFeature_Kd`） | 行う | 行う |
| 位置の規則（本書 3.4） | 行う | 行う |
| Condition の検証（SPEC §19.2、§19.3） | 行う | 行う |
| 選択と選択失敗のエラー | 行う | 行わない |
| 意味：名前・型・所有権、Attribute の解決、個数と重複の規則、最終宣言木の検査（SPEC §6.1.1）、宣言の合併、文書コメントの関連付け、Mod からの可視性、lowering とコード生成 | 行う | 行わない |

- 境界は、SPEC §19.1 がすでに置いている区切りと同じである。
  - 選択と生成より前に、ソースだけで決まる検査は、全体に行う。
  - 選択と生成の後の宣言木や名前を使う検査は、選択された構文にだけ行う。
- 構文の検査は、Condition の検証を除き、準備済み環境の値を使わない。
- 投機的な構文解析も受理を変えない。そのため、除外構文に限って投機的な構文エラーを抑止する規定は削除する。

SPEC §19.5 に、次の保証を加える。

> 生成されたものでない SourceDocument について、字句・文法・位置・Condition の診断のコード・主範囲・Reason は、選択失敗のエラーを除き、そのモジュールのすべての Compilation で同じである。

環境によって変わるのは、次のものだけである。

- 選択の結果
- 選択された構文に対する意味の検査
- 除外を示す関連位置（本書 4.1）

### 3.3. Condition の検証と選択

- SourceDocument 中のすべての Condition を、SPEC §19.3 の規則で検証する。除外構文の内部と、`#switch` の外の `#case` も含む。SPEC §19.3 の「到達した（reached）」という限定は削除する。
- 選択は、除外構文の外の `#if` と `#switch` だけが行う。選び方は従来どおりである。
- 選択失敗（真のアームも `#case _` もない）のエラーは、次の条件をすべて満たす `#switch` にだけ報告する。
  - 除外構文の外にある。
  - Condition と構造がすべて正しい。
- `#case _` を省略して、対応しない環境を意図的にエラーにする使い方は残す。

### 3.4. 位置の規則と個数の規則

**位置の規則**は、ある項目が他の項目より前、または先頭の領域にあることを求める規則である。

- 対象となる規則：
  - `alias` は、通常の宣言と実行項目より前に置く（SPEC §18.1.1）。
  - 関数・アクセサー・型の Constraint と Origin 関係は、先頭の領域に置く（SPEC §7.4、§11.3、§15.3.3、Appendix F）。
- 判定の方法：
  - 選択の前に、除外構文も含めたソース順で判定する。
  - ディレクティブ自体は数えない。その対象とすべてのアームの中の項目を、それぞれの種類として数える。

**個数と重複の規則**は、選択の後に、選択された項目だけで判定する。

- 対象となる規則：
  - Constraint を定義する fragment は一つだけである。
  - enum には、選択された Case が一つ以上必要である（SPEC §6.1.1）。
  - 宣言は重複してはならない。

```kimi
#if windows
    alias Kimi.Windows
#if linux
    alias Kimi.Linux
alias Kimi.Console       // 受理：これより前にあるのは alias だけ

func process<T>(value: T) -> ()
    #if debug
        log("process")
    T is Copy            // エラー：ソース順で実行項目の後にある（release でも同じ）

func inspect<T>(value: T) -> ()
    #switch
        #case debug
            T is Comparable  // 受理：どちらのアームの Constraint も先頭の領域にある
        #case _
            T is Copy
    return

func store<T>(value: T) -> ()
    #switch
        #case debug
            log("store")
        #case _
            T is Copy        // エラー：ソース順で、前のアームの実行項目より後にある
    return

enum Platform
    #switch
        #case windows
            Windows          // 受理：選択された Case が一つあればよい
        #case _
            Other

#switch
    #case windows
        func platformName() -> string => "windows"
    #case _
        func platformName() -> string => "other"  // 受理：重複は選択後に判定する
```

### 3.5. Condition Name の不変条件

SPEC §19.2 に、次の不変条件を加える。

> SourceDocument から見える Condition Name の集合と、それぞれの Type は、そのモジュールのすべての Compilation で同じである。環境ごとに異なるのは値だけである。組込み値は、すべてのターゲットで定義される。

- 現行の構成は、すでにこの条件を満たしている。
  - 組込み値は、全ターゲットで定義されている（impl §20.4）。
  - `CompileTimeSettings` は、条件分岐のない一つのマップである（impl §20.4）。
  - 設定は定義したモジュールに属し、上書きはない（SPEC §18.4.3）。
- 将来、ターゲット別やビルドモード別の設定、コマンドラインからの上書きなどを導入する場合も、この不変条件を守る。名前と型はモジュールで一度だけ宣言し、環境ごとには値だけを与える。

```kimi
#if windows
    #if useDirectWrite        // CompileTimeSettings に定義があれば、Linux でも検証は通る
        useDirectWriteRenderer()
```

`useDirectWrite` が未定義なら、どの環境でも `UnknownCompileTimeName_Kd` になる。未定義の名前はどの環境でも真にならないので、これは誤検出ではない。

### 3.6. 文書コメント

- 除外構文の宣言には、文書コメントを関連付けない。公開もせず、文書コメントの診断も出さない。
- 除外構文の文書コメントが、選択された宣言へ移ることはない。
- 文書コメントのために追加の構文解析を求めない、という規則は残す。
- 構文エラーのある SourceDocument では、関連付けを保留する（現行の方針）。除外構文の構文エラーもこれに含まれる。ただし、その文書はどのみちビルドできないので、受理される文書への影響はない。

### 3.7. Compiler Server Protocol

SPEC §23.5.3 に、次の要件を加える。

> 構文ノードのハンドルは除外構文も含み、そのノードが除外されていることと、原因となった最も内側のディレクティブを示す。意味ノードのハンドルは、選択された構文にだけ与える。

## 4. 診断と回復

### 4.1. 診断

新しい診断コードは追加しない。

- **除外構文の中の診断：**
  - コード・主範囲・Reason・Advice は、選択された構文と同じにする。
  - 除外の原因となった最も内側のディレクティブを、役割とラベルを持つ関連位置として付ける（SPEC §23.3.6.3）。`#if` なら Condition、`#case` ならアームのヘッダーを示す。
  - この関連位置は、Reason には含めない。
- **付け方：** SourceDocument ごとに除外範囲を記録しておき、最終化の段階で、主範囲が除外範囲に含まれる診断に付ける。字句解析が出す診断も、この対象になる。
- **選択失敗：** 本書 3.3 の範囲に限って報告する。
- **Error の `#if`：** Condition のエラーと、対象内部の独立した構文エラーの両方を報告する。対象の意味は検査しないので、対象から名前や型の連鎖的なエラーは出ない。
- **`#switch` の外の `#case`：** `CompileTimeCaseOutsideSwitch_Kd` に加えて、その Condition を検証し、本体を除外構文として構文解析する。

```kimi
#if linux
    let pending =   // MissingSyntax_Kd。関連位置：1 行目の Condition「linux」（この Compilation では除外）
```

### 4.2. 回復

- 除外構文は、選択された構文と同じ回復処理で構文解析する。
- 除外構文は、選択された構文の次のものに影響しない。そのため、除外構文のエラーが、選択された構文の検査に連鎖することはない。
  - 宣言の合併
  - 根の実行項目
  - Constraint と Origin 関係
  - 省略や回復の記録
  - 文書コメント
  - Attribute
- アームを選ばない `#switch` は、回復用にアームを保持してよい。ただし、そのアームは除外構文として扱い、Binding も文書コメントの関連付けも行わない。
- 利用できない機能の読み飛ばしは、除外とは別の回復処理なので変えない。ただし、その診断は除外構文の中でも報告する。

## 5. 実装計画

### 5.1. 構文解析の方式

[CODEMAP](../../docs/dev/CODEMAP.md) の「Compile-time selection」を起点とする。

ディレクティブの本体は、それを囲む所有者（根、コンテナー、実行本体）の項目ループで、再帰的に構文解析する。

- **選択された本体：** 囲む所有者そのものに構文解析する。後から取り込む手順はない。
- **除外構文：** 同じ項目ループに、同じ種類の切り離された所有者を渡して構文解析する。その中では選択を行わない。
- **`#switch`：** アームの本体を構文解析する前に、すべてのアームのヘッダーと Condition を検証して、選択を決める。
- **共通：** 選択の結果は、どの所有者を渡すかだけを決める。位置の規則の状態は、選択されたかどうかにかかわらず、同じループを通る。

次の二つは廃止する。

- 別の文法で構文解析して、後から取り込む現在の方式
- 除外構文の、構造だけの走査

### 5.2. 実装単位

| 単位 | 作業 | 完了条件 |
| --- | --- | --- |
| U0：選択された本体 | 選択された本体を、本書 5.1 の方式で構文解析する。これにより、現行仕様では許されるのに受理されない次の形を直す（probe の p7、p8、p12）。<br>・根の `#if` ブロックの中の `alias` と `rootgroup`<br>・関数本体の `#switch` アームの中の Constraint<br>・enum 本体の `#switch` アームの中の Case | 上の形を受理する。既存のディレクティブのテストが通る |
| U1：除外構文 | 除外構文を本書 5.1 の方式で構文解析し、構造だけの走査を廃止する。あわせて次のものを扱う。<br>・Error の `#if`<br>・`#switch` の外の `#case`<br>・除外構文の中の選択と選択失敗<br>・文書コメント（本書 3.6） | 本書 2 の構文の行が成り立つ。書換えの対が、全環境で同じ結果になる。本書 4.2 の影響がない |

- 各単位は、再現・実装・focused tests の順に進める。

### 5.3. 性能方針

- 除外構文は一度だけ構文解析し、追加の走査はしない。費用は、同じコードが選択された場合の費用を超えない。
- 選択された本体のために一時的な所有者やラッパーを作らなくなるので、現在より割当てが減る。
- ディレクティブのないソースでは、割当ては増えない。除外範囲の記録は、除外構文があるソースにだけ作る。
- 除外構文のノードは、構文解析の後で捨てる。CSP がノードを保持する場合も、保持するのはツールのセッションだけで、ビルドでは保持しない。
- `ParseBenchmark` で A/B を測定する。入力は次の二つとする。
  - 除外構文が多い合成ソース（全体のおよそ半分が `#if` の対象）
  - ディレクティブのない既存の入力

### 5.4. 検証

| 観点 | 対照例 |
| --- | --- |
| 書換えの等価性 | 本書 1.1 (1) の A と B を、受理される版と拒否される版の両方で比べる |
| 環境非依存 | 同じソースを `x86_64-pc-windows-msvc`、`x86_64-unknown-linux-gnu`、`i686-unknown-linux-gnu` と debug/release で構文解析し、本書 3.2 の保証が成り立つことを確かめる。位置の規則の例を含める |
| 入れ子 | 偽の `#if` の中の `#switch`、未選択アームの中の `#if`、積み重ねた `#if`、除外構文の中の真の `#if`。選択失敗が、除外構文の中では出ず、外では出ること |

## 7. 設計判断

### 7.1. 評価

**実現性：** 実現できる。

- 未選択アームは、すでに通常の構文解析を受けている。
- パーサーは、Condition の評価以外では準備済み環境を参照していない。
- 主な作業は本書 5.1 の方式への置き換えであり、これは既存の不具合（U0）の修正も兼ねる。

**メリット：**

- `#if` と `#switch` の書換えで、受理・拒否が変わらない。
- 一つの環境で、全ターゲットの構文・位置・Condition の誤りを見つけられる。
- 環境に依存した誤報告と見逃し（本書 1.1 (2)、(3)）がなくなる。
- `#if` の対象の範囲が文法だけで決まり、CSP がすべてのソースにハンドルを与えられる。

**デメリット：**

- 構文として不完全なコードを `#if false` で無効化できない。代わりにコメントを使う。
- 除外構文の構文解析に、その大きさに比例した費用がかかる。
- 位置の規則が選択によらず適用される。そのため、ある環境では選ばれない項目のために、`alias` や Constraint の位置を直す必要が生じ得る。
- 現在の環境では使われないコードにも、エラーが出る。原因は関連位置で示す。
- 将来、言語バージョンで構文を切り替える条件を入れる場合は、別に例外の規定が必要になる。現在、そのような条件はない。

**複雑さ：** 増加分より、得られる利益のほうが大きい。

- 仕様は単純になる。二列の表、到達の規則、投機的なエラーの抑止、文書コメントの例外がなくなる。位置と個数の区別が加わるが、これは現在あいまいな点を明文化するだけである。
- 実装では、後から取り込む方式と構造だけの走査を、一つの方式に置き換える。増えるのは、切り離された所有者と除外範囲の記録だけである。

### 7.2. 採用しなかった案

| 案 | 理由 |
| --- | --- |
| 構文の検査を省く側に統一する | 未選択アームの誤りまで、別の環境でビルドするまで見つからなくなる。後続アームの Condition まで検証する SPEC §19.3 の趣旨にも反する |
| 差を残し、理由を明記する | 独立選択か排他的選択かは、検査の深さとは無関係であり、差を正当化する理由がない |
| 除外構文の名前と型も検査する | 宣言と型は環境ごとに異なるので、全環境の宣言が必要になる。局所的に推論できない |
| 位置の規則を、選択された項目だけで判定する（現行の実装） | 受理が環境に依存する（本書 1.1 (2)） |
| 個数と重複の規則も、ソース順で全項目を数える | 排他的なアームに一つずつ書く、正しい書き方を拒否してしまう |
| Error の Condition の対象を読み飛ばす（現行） | 対象内部の独立したエラーを隠す |
| 選択された本体を切り離して構文解析し、後から取り込む | 項目の種類ごとに取り込みの処理が必要になり、その漏れが既存の不具合（U0）の原因になっている。位置の状態の受け渡しも二系統になる |
| 構造の走査を残し、文法の検査だけを加える | 範囲を決める規則と文法が、二系統のまま残る |
| 選択しない環境用の設定名を宣言する仕組み | 本書 3.5 の不変条件の下では不要である |
| `#case _` を必須にする | 対応しない環境を意図的にエラーにする手段がなくなる。`#error` に当たるものはない |
| 除外構文でも文書コメントを関連付ける | 公開は選択された宣言に従う。現時点で、関連付けを使う側がない |
| 除外の事実を Note でも伝える | 同じ事実を関連位置と二重に表すことになる。関連位置のラベルに一本化する |
| Error の Condition が除外した宣言への参照を、派生診断にする | 見えるはずだった範囲（文書をまたぐ可視性、オーバーロード）の扱いが決まっておらず、本提案の統一とは独立している。別の提案とする |

### 7.3. Kimigayo Principles との対応

- **原則1：** 検査の規則、対象の範囲の規則、ディレクティブ本体の構文解析の方式を、それぞれ一つにする。`#if` と `#switch` の違いは、選択の仕方だけになる。
- **原則2：** 構文・位置・Condition の受理が、ソースと、モジュールで固定された Name の集合だけで決まる。
- **原則3：** 除外されていることを関連位置で明示する。選択失敗は、実際に選択が行われる場所でだけ報告する。
- **原則4：** すべてのソースに構文ノードのハンドルを与え、除外構文の診断に、原因のディレクティブを構造化して結び付ける。

### 7.4. 根拠

本書は、仕様・ソース・既存テストの静的な照合と、現在の実装での動作確認（`artifacts/verify/20261001-excluded-syntax-probe/`）に基づく。新しい規則の実装、実行試験、性能の測定は、まだ行っていない。
