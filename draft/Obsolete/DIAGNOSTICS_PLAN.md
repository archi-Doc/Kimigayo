状態：最終版（2026-09-29）。本書は実装計画であり、仕様への取り込み・実装・検証の完了を示さない。実装は別途の指示で開始する。

## 1. 目的と範囲

一つの独立した問題を、一つの主診断と必要な根拠で説明する。既存の診断定義と解析データを使い、CLI・LSP・将来の Compiler Server Protocol（CSP）に共通する小さな基盤を整える。

初期実装は、問題の識別、明示した原因による連鎖抑制、位置・理由・補足の構造化、共通の公開経路を対象とする。独立した試作は作らず、本体への小さな変更と回帰テストで検証する。CSP サーバー、永続 ID、機械的な修正の適用などは §6 の Deferred とする。

### 1.1. 設計原則

| 原則 | 契約 |
| --- | --- |
| I1 定義 | 診断の意味と定義を一元化する（§2） |
| I2 決定性 | 到着順・スレッド・文言から問題の整理を独立させる（§3.2・§3.4） |
| I3 説明 | 抑制後も問題を説明する主診断を残す（§3.2） |
| I4 受理 | 表示や補足から受理可否を独立させる（§3.1・§3.6） |
| I5 局所性 | 同じ検査・意味上の入力・前提に対する説明を、無関係な問題によって削らない（§3.3） |
| I6 境界 | 公開内容を一度確定し、不変に保つ（§2.3・§3） |

### 1.2. 用語

| 用語 | 意味 |
| --- | --- |
| 診断事実（DiagnosticFact） | 検査が記録する指摘と根拠。Warning も含む |
| Direct／Derived | 自分で確認した指摘／前提不足で判定できない検査。区別は Code で表し、独立した Kind は持たない。チェック全体の Blocked とは別 |
| 公開診断（CheckDiagnostic） | 整理・確定した共通レコード。各出力への変換元 |
| 修正助言（Advice） | 人間向けの条件付き提案。機械的な修正や保証を意味しない |
| 修正候補（Repair） | 前提条件・保証・検証結果を伴う構造化した編集。初期実装の対象外 |
| 診断所有者 | 一回のチェック要求と、その後のコンパイルの診断を管理するもの |
| 区画・解析世代 | 区画はまとめて無効化する処理範囲、世代はそこで採用する解析結果の版 |
| 結果単位 | 診断を確定する区切り。チェック全体を一単位とし、コード生成などの後続フェーズは別単位 |
| 表示方針 | 説明の上限、CLI 引用の要否、LSP の関連位置対応など、確定前に固定する設定 |
| 確定 | 診断事実を整理し、公開レコードを作る処理 |

## 2. 共通モデル

### 2.1. 診断定義

一つの診断コードに、一つの重大度と分類を定める。分類は「言語上の指摘」「証明不成立」「実装未対応」「入力・設定」「資源制限」「内部障害」とする。異なる分類を兼ねるコードは分けるが、文言の違いだけでは増やさない。

| 定義元 | 責任 |
| --- | --- |
| tinyhand・DiagnosticEntry | 重大度、分類、既定の Message・Label・Note・Advice |
| コードごとの型付き生成処理 | 引数型、関連位置の役割と順位、主体の正規化、条件に応じた説明と既定文の採否 |
| 検査種別の C# 定義 | 要求の安定名と意味、条件の型、定義順、所属区画、条件番号から意味順への対応 |
| DiagnosticRequirement.tinyhand | 要求の安定名をキーとする短い説明文（Name・Message）。診断とは別の語彙であり、診断コードには加えない |

分類は指摘の意味、区画は結果の寿命を表し、互いから推定しない。契約は呼び出し側にも適用する。例えば直列化したソースの形式不一致には「入力・設定」の専用コードを使い、UnexpectedToken_Kd に自由文を渡して代用しない。

理由と表示は同じ型付き引数から作る。TypeMismatch_Kd なら `expected`・`actual` を持ち、コードと同じ意味の reason.kind は重ねない。コード内で機械的な区別が必要な場合だけ引数型に変種を設ける。少数の生成メソッドから始め、汎用属性辞書、継承・置換設定、新しい定義言語やコード生成器、実行時の名前付きテンプレート解析は導入しない。

Derived は PrerequisiteUnavailable_Kd（Error・証明不成立）に統一する。要求・条件とその検査に固有の事実を引数にし、共通の定型文で「前提を確立できないため、この要求を判定できない」と説明する。要求の説明は上表のカタログだけに置き、内部の検査種別と安定名を初期化時に対応付ける。未確認の違反を表すコードや、Direct の断定文への前置句は使わない。

判明した事実は理由、推測した意図は Advice に置く。証明不成立を「条件が偽」と説明せず、Advice・Note の文章から編集や保証を推定しない。既存の Fix は定義と参照箇所を同じ実装単位で Advice へ改名し、別名を残さない。hint は廃止する。

### 2.2. 診断事実と同一性

以下は論理モデルであり、フィールドごとのヒープ割り当てを要求しない。

```text
DiagnosticFact
  Code        : DiagnosticCode
  Subject     : 構文対象・入力・コンパイラ処理への解析内参照
  Check       : 診断コードに依存しない検査種別と条件番号
  Context     : 具体化・展開の文脈への解析内参照、またはなし
  Primary     : ソース参照と任意の範囲
  Args        : コードに対応する型付きの事実
  Evidence    : 役割ごとの補足取得元（必要な小さな値と既存の不変根拠）
  DerivedFrom : 前提の検査キー、または未解決印の列
```

検査キーは `(Subject, Check, Context)`、問題キーは `(検査キー, Code)` とする。

- **Subject：** 解析世代とソースのスナップショットを区別する。字句・構文エラーでは元のトークンや境界、入力失敗では入力そのものを指し、構文ノードを必須にしない。合成した主体は「元の主体・変換の役割・変換内の規定の子順」で区別し、同じ意味の主体は記録前に正規化する。
- **Check：** フェーズ間でも区別し、一つの要求を表す。「宣言の型の確立」と「呼び出しの引数個数」は別の検査とする。条件番号は引数・契約条件・Place・Reservation などを区別し、一条件なら既定値を使う。
- **Context：** 対象宣言・宣言型、型・値・Origin（入力 Origin を含む）の置換、必要な外側の展開文脈を、既存の具体化情報に対応付ける。同一性・説明・意味順はこの共通定義を参照し、表示名や生成時の番号で代用しない。
- **同一性：** 表示範囲や文字列では判定しない。既存の解析内番号は識別に使えるが、公開する説明や順序にはそのまま使わない。

採用した一報告のキー・Primary・Args・補足元の意味は、記録後に変化させない。既存の不変値は共有し、再束縛などで変化する値だけを報告時に保存する。BoundCall などの変更可能な入れ物への参照だけでは固定とみなさず、AST 全体のコピーや正常経路の追加確保は行わない。同一問題の明示的な集約は §3.2 に従う。

複数対象にまたがる問題は、記録前に主体と基準対象を正規化する。宣言の重複なら、後の各宣言を Subject と主位置、最初の宣言を関連位置にする。三宣言なら主診断は二件とし、双方を解析上無効にする処理とは分ける。

全フェーズを最初の記録元からこの契約へ接続する。解析固有の失敗 enum は維持し、Ownership のコード変換には既存の OwnershipIssue.Code を使う。診断のためだけに検査範囲を広げない。

### 2.3. 公開診断

公開レコードは CheckDiagnostic に集約する。DiagnosticFact を直接 JSON 化せず、AST・変更可能な解析データ・遅延クロージャーを外へ出さない。任意項目は根拠がある場合だけ持つ。

| 項目 | 内容 |
| --- | --- |
| Code・Severity・Category | コードの定義名、重大度、分類 |
| Message・Primary | 自己完結した主説明、ソース参照・任意の範囲・任意の Label |
| Reason | コードごとの小さな型付き値。意味上の番号・列挙値・真偽値は正確に保持し、型・制約は省略印付きの有界な表示値とする |
| Related・Note・Advice | 役割付きの関連位置、追加説明、修正助言 |
| 省略情報 | 要約・省略した部分。件数は判明している場合だけ保持する |
| 表示用データ | 行・列、必要な引用と位置の代替文。意味判定には使わない |

Message は指摘の性質と必要最小限の理由を含み、Reason は対応する機械向けの値を持つ。検査条件や具体化による差は、仮引数番号・対象操作・使用箇所・型・値・Origin の置換など、理解に必要な意味情報で説明する。内部の格納番号や永続 ID で代用しない。

PrerequisiteUnavailable_Kd の Reason は `requirement`（要求の安定名）と `condition`（検査種別が定める型付きの条件・必要な事実）とする。安定名は診断コード名と同じく公開語彙であり、内部 enum の番号は公開しない。任意の属性辞書や Kind の重複は設けない。

派生診断の Related は、既に安全に取得できる前提の元位置を「前提」の役割で示す。未解決印だけなら前提不明と説明する。位置が分かることを前提の成立や失敗の証明にせず、失効した解析を辿り直さない。取得と省略は §3.3 に従う。

主説明だけで問題を理解できるようにし、不可欠な事実を省略可能な補足だけに置かない。完全な型・文脈グラフは公開せず、要約を型の同一性に使わない。入力記録・設定・報告元は結果側で扱い、各診断へ複製しない。

### 2.4. 位置とソースの寿命

共通位置型は「ソース参照＋SourceSpan?」とする。

- 範囲は元の不変ソース上の、0始まり UTF-16 `start`・`length`。終端を含めず、長さ0は挿入位置を表す。
- 範囲なしは入力全体、ソースなしはソース外の問題を表す。範囲を持つ場合は、読み取り済みソースと境界内の範囲が必要である。
- 主位置は失敗した条件の主体を説明する最小範囲、関連位置は条件の出どころや根拠とする。生成側が記録時に決め、確定処理で AST を探索し直さない。

| 問題 | 主位置 | 関連位置の例 |
| --- | --- | --- |
| 型不一致 | 要求された型に合わない式 | 型注釈・仮引数・戻り値契約 |
| 不正な代入 | 操作または代入先 | 制限する宣言 |
| Move 後の使用・借用競合 | 不正な使用・競合する操作 | 先行する Move・借用、必要な分岐や使用 |
| 宣言の重複 | ソース順で後の宣言名 | 最初の宣言 |
| 構文要素の不足 | 挿入位置・不足が判明した境界 | 対応する開始記号 |

ソース参照は結果内のソース表の整数索引とする。各項目は「入力参照?・SnapshotToken?・表示情報」を持ち、同じパスでも別スナップショットを区別する。入力記録のない組み込み・生成ソースは入力参照を持たない。表は入力・生成元の規定順に並べ、索引やトークンの割当順を意味順に使わない。

SnapshotToken は現在のコンパイラ／サービスセッションだけで有効な「範囲識別値・番号」とする。範囲識別値はセッション内で入力ストアと所有者をまたいで一意にし、トークンは同じセッション内だけで比較する。

- 記録済み入力の正の revision とソースが対応する場合は、入力ストアの範囲と revision を使う。
- CLI、未登録の初回読み取り、組み込み・生成ソースなど共有 revision がない場合は、所有者の範囲と不変ソースごとの番号を使う。番号は診断の到着順ではなく、入力・生成元・ソース木の世代の規定順で定める。

入力の採用後も確定済みトークンは書き換えず、共有する根拠のない別トークンを同じスナップショットとみなさない。永続 ID や全文ハッシュは追加しない。

入力参照は結果の入力記録へ結び付け、収集中は元の SourceDocument との対応も保持する。読み込み失敗には入力参照と表示情報だけを持たせ、スナップショット・内容 ID・範囲を捏造しない。

登録窓口は診断所有者で共有する。本文への強参照と登録索引は必要な区画の寿命に従い、失効分を回収する。軽量な登録項目にも世代の履歴を蓄積しない。公開表は必要な識別情報だけを持つ不変の値とし、後続処理から書き換えない。

行・列は確定時に同じ不変ソースから計算する。CLI 引用を要求された結果だけ、引用開始位置・有界なテキスト・引用内の強調範囲も保持する。表示用データを位置の正本にせず、公開のためにソース全文を保持したり、後から別の内容を読み直したりしない。旧 Diagnostic.Location の文字列による別経路は廃止する。

## 3. 収集から公開まで

処理は **収集・同一問題の集約 → 連鎖抑制 → 説明と位置の確定 → 整列 → 公開** の順とする。各出力は共通レコードを変換し、意味の再判定や再 Binding を行わない。

### 3.1. 所有者・区画・エラー状態

診断所有者は入力準備前に作り、成立した Compilation と後続フェーズへ引き継ぐ。結果単位ごとに採用する区画を固定し、後続処理は前段の成功条件を参照する。事実領域と索引は必要時だけ確保する。

| 区画 | 寿命と無効化 |
| --- | --- |
| 入力・設定 | チェック要求の入力・実効設定に対応する。ソース解析や意味解析の開始では消さない |
| 構文 | モジュールのソース木に対応し、木の再構築時に交代する。直列化形式検査と構文回復の対応表も含む |
| 意味 | Compilation 全体を対象とし、Binding・起動条件・ControlFlow／Ownership の既存の更新単位で分ける。構文変更で全意味区画を失効させ、単独の再解析では該当フェーズと依存する後段だけを交代する |
| 後続フェーズ | 結果単位ごとに持ち、前段の確定済み結果と分離する |

所属区画は検査種別の定義、世代はモジュールと実行文脈から決める。世代交代では対象区画を切り離し、全事実を走査して選別しない。事実・索引・解析内参照を同じ寿命にそろえ、失効した状態を確定・受理から除外する。同じパスへの追加を置換とみなさず、結果の再利用では世代を交代させない。

Error の記録時に、集約・抑制より先に所属区画の必要なモジュール範囲のエラー有無を更新する。同じ世代内では取り消さない。暫定的な再試行は解析側で処理し、採用する検査結果だけを事実へ変換する。

処理中のキャッシュ判断や Documentation.Finish は、呼び出しごとの軽量な局所結果を使う。処理後の受理・コード生成・ライブラリ検証は、所有者の有効な対象範囲を照会する。TestPresence は当該モジュールの構文区画だけを参照する。独立した HasSourceErrors、共有 ErrorVersion の差分、表示用 errorCount は廃止する。

### 3.2. 記録・重複排除・連鎖抑制

#### 3.2.1. 記録と集約

不変条件は「Code が PrerequisiteUnavailable_Kd ⇔ DerivedFrom が空でない」とする。派生用の生成処理は専用コードを使い、原因不明でも未解決印を入れる。不一致は診断契約違反とする。重大度はコード定義だけから得て、発生時の上書きや Kind の保存は行わない。前提不足で実行できない Warning の検査は記録せず、独立した問題の根拠は Evidence に置く。

収集時に問題キーで集約し、再報告を別レコードとして保持しない。同じキーの Primary・Args・役割ごとの補足取得元は一致させ、派生原因は重複のない和集合にする。補足候補は再報告から集めず、§3.3 で一度取得する。未解決印は既知の原因が加わっても残す。必須事実や取得元の矛盾は Debug・Release とも §3.6 の退避処理で扱い、到着順で上書きしない。

#### 3.2.2. 原因の記録

記録元が、満たせなかった前提を検査キーで指定する。前提のコードが未判明でも参照でき、登録順を問わない。そのキーが表す Error は、参照した要求の成立を妨げる失敗に限る。別の要求はキーを分け、宣言内の全失敗を原因にしない。

各解析は独立した問題を記録する。明示的に参照された検査が不成立なら、その Error、または見送り原因を引き継ぐ Derived に接続する。既知の前提失敗で見送った子孫は原因側で説明し、参照されない各ノードに Derived を作らない。

Derived は検査自身が要求の判定不能を確認した場合に記録し、既知の未対応は対応範囲を判定する箇所で Direct として報告する。Unvisited／Unresolved という状態だけで診断を作ったり、構文上の祖先に失敗があるだけで説明済みとしたりしない。Binding の最終集計と先頭の未解決ノードに診断を置く現行処理を監査し、検査元の報告へ置き換える。既存の完了判定は変えず、説明のない不受理を一般的な Derived で埋めない（§3.6）。

構文回復では、ErrorKoto や補完した構文と、原因になった字句・構文検査のキーを明示的に結び付ける。対応表は構文区画で失敗時だけ確保し、正常なノードのフィールドを増やさない。Binding などは回復箇所を前提にできない場合にこの対応を使い、対応不明なら未解決として残す。

#### 3.2.3. 抑制条件

確定時に有効な事実を検査キーで索引化し、前提をその検査が報告した Error すべてに結び付ける。Error がない、Warning だけ、結果外、失効世代の参照は未解決とする。

Derived は、**全原因が同じ結果で公開する Direct の Error へ解決し、途中にも未解決・循環がない場合だけ**抑制する。それ以外は残し、抑制の根にしない。独立した複数の原因はそれぞれ残す。未解決の引数による派生と、独立して分かる引数個数違反を混同しない。

明示参照を非再帰で一度走査し、前提検査ごとの判定を共有する。Error 一覧や根の集合を参照元ごとに複製・再走査しない。AST 子孫、位置の近さ、直前の診断、助言文から原因を推定しない。言語上の循環は既存の解析が報告する。抑制した事実は公開せず、解析用領域とともに解放する。

### 3.3. 説明の生成と上限

Message・Label・Reason・Note・Advice・省略情報と、必要な引用・位置の代替文を一度確定する。出力側は固定書式で配置し、本文を調べて理由を追加したり、再度切り詰めたりしない。

表示方針の既定値は一か所に置き、テストでは内部設定として差し替える。利用者向けの設定機構は追加しない。上限は診断ごとに適用し、結果全体で説明量を奪い合う予算は設けない。

| 対象 | 規則 |
| --- | --- |
| 必須説明 | 型・制約・長い識別子に共通の深さ・長さ・展開量の上限を適用し、最小限の主説明を残す |
| 補足の取得 | 一問題・一役割の取得元を型付き生成処理で一つに定め、抑制後に固定順で一度取得する。走査・保持の上限は診断全体に適用し、再報告や根拠の数で予算を増やさない |
| 補足の整理 | 上限内で捕捉した候補だけを重複除去・整列し、先頭 N 件を保持する。打切りは省略印で示し、全候補や破棄済み候補の履歴を保持しない |
| 説明部品 | 件数と一部品の長さ・展開量を制限する。合計上限は部品ごとの上限・件数・固定書式から導き、別の切り詰め規則を作らない |
| ソース引用 | 主位置周辺の行数・文字数・表示幅を制限する。引用範囲を絞ってから空白と下線を作り、巨大な行全体や元の列数分の空白を生成しない |

補足の順序は「役割の順位 → 元位置 → 根拠の意味値」、同値判定は整形前の役割・位置・値で統一する。取得元は不変の根拠を固定順で列挙し、取得のための展開・比較・索引作成も予算に含める。生成側は独自の比較器を持たない。派生診断の前提位置は、確定した原因列を共通の取得元とする。到着順で取得元を選ばず、文字数による候補選択や全文生成後の切り捨ても行わない。

型不一致などでは上限内で相違箇所を優先し、共通部分を省略する。差を表示しきれない場合はその旨を本文に残す。同じ要約を同じ型とみなさず、要約のための再判定や完全な差分探索は行わない。

入力失敗・例外の主説明は安定したコードと型付きの失敗種別から作り、環境依存の例外文は有界な Note に置く。入力失敗は SPEC §23.3.4 の省略前の観測値で比較し、公開値は確定後の内容で比較する。観測値が変われば入力の再検証に反映するが、省略部分だけの違いなら表示が同じになることもある。

表示上限は問題の同一性・分類・存続・受理、位置・入力の識別値を変えない。同じ検査・意味上の入力・前提なら、無関係な問題の追加で説明量を減らさない。主診断を件数で消さず、検査の見送りと収集後の抑制を区別する。検査の開始条件と意味解析の資源制限は既存規則に従う。

### 3.4. 一致判定と順序

同じ採用事実・観測済みの失敗情報・診断定義・表示方針から、同じ公開内容と順序を作る。意味解析の決定性は既存仕様に従う。

問題の同一性、公開値の一致、表示順を混同しない。公開値は表示用データを含む全項目で比較し、Note だけの変更も検出する。異なる結果のソース参照は表の対応する値で比較し、参照番号だけで同一視しない。

意味順は「ソース表の順 → 元の対象の順序 → コード名の序数順 → 検査種別の定義順 → 種別内の条件順 → Context」とする。対象は構文上の位置と役割、ソース外では入力・処理の規定順を使う。条件は仮引数順・契約の記述順・対象操作のソース順などへ投影し、格納順・メモリアドレス・型の表示名は使わない。

Context は §2.2 の共通定義に従って比較する。使用箇所のソース順を優先し、同じ箇所では対象宣言・宣言型・各置換・外側の文脈を規定順で比較する。型・値・Origin は省略前の意味情報を使う。先行キーが同じ場合だけ必要な比較情報を作って確定処理内で共有し、深い構造は非再帰で扱う。共有部分を反復展開せず、コード別の比較器や正常経路の専用キャッシュは作らない。

共通レコードは「文書順 → 主範囲 → 意味順」で並べる。範囲なしは同じ文書の範囲付きより前、ソースなしは文書付きの後とする。合成主体にも §2.2 の意味上の区別を用い、異なる公開内容が同順位になる場合は主体・検査・文脈の定義不足として契約検査で検出する。到着順、本文、要約された Reason、補足の採否で順序を補わない。内部キーは公開値の一致に含めない。

### 3.5. CLI・LSP・JSON

CLI は確定後に表示する。入力の消費順と後続処理の開始条件を維持し、後続フェーズは自分の結果だけを出力する。JSON・将来の CSP は §2.3 の全情報と自己完結した Message を持ち、利用側にカタログ取得や文言解析を要求しない。

| 項目 | CLI | LSP |
| --- | --- | --- |
| Message・理由 | 確定した主説明 | 同じ主説明を message に置く |
| Primary・Label | 有界な引用、下線、Label | 主範囲と message 内の Label。代替配置時は元位置の説明も添える |
| Related | 役割・元位置の説明・補足文 | 対応クライアントでは関連位置情報へ置き、代替配置なら元位置も説明する。非対応なら代替文を message に添える |
| Note・Advice・省略情報 | 「補足」「助言」「省略」を区別 | 同じ区別で message に添える |

説明部品は一度だけ配置する。LSP の関連位置対応は能力の読み取りと診断型を併せて追加する。通信のエスケープや装飾で説明の意味・採否を変えない。

#### 3.5.1. LSP の位置と鮮度

位置の対応は「結果とソース表の項目」の組ごとに一度、その結果の入力記録から確認する。パスだけで同一視せず、同じ不変結果と表示方針に対して配置を固定する。現在の編集内容に合わせて URI や範囲を動かさず、古い入力は既存の保留・失効規則で扱う。

主位置・関連位置とも、対応できない範囲は表示上だけ範囲なしとする。file: の位置はそのファイルの先頭、ソースなし・compiler:// の位置はプロジェクトまたは暗黙ソースの先頭へ置く。代替文には既知の元ファイル・行・列と対応不能の旨を含める。元から範囲がなければ入力全体、ソースがなければソース外の指摘と説明する。元位置は共通レコードに残し、Label も元位置の説明として使う。

#### 3.5.2. LSP の集約と再利用

代替配置後、実際の送信値による集約を先に行い、その後で表示順に整列する。同じ結果内の別問題はまとめない。報告元ごとに同値診断の件数を数え、URI ごとの件数は各結果の最大値とする。一方が [A, B, A]、他方が [A] なら A は二件残す。送信値には関連位置なども含め、隣接比較による重複除去は使わない。

表示範囲順に並べ、同順位には報告元（プロジェクトまたは暗黙ソース・モード・Target）の固定順と元の配列位置を使う。チェックの訪問順や完了順は使わない。同値の第 n 件どうしで最小キーを代表にする。単一の報告元では集約を省く。元の結果の同一性・件数は変えず、独自の報告元集合フィールドも追加しない。

採用条件、寄与する全結果が有効なときだけ送る条件、URI の見直し時点は既存契約を維持する。再送は実際の送信内容と文書バージョンで判定する。同じ不変結果と表示方針では文字列・配列を再利用する。

### 3.6. 受理・終了・内部障害

受理成功には、入力・実効設定・依存内容・ロック検証の成立と、SPEC §23.3.2 手順3の全対象モジュールの検査完了・成功が必要である。これには構文解析・Binding・起動条件・制御フローを含む Ownership が含まれる。さらに、有効な対象範囲に Error がなく、Outcome が Completed でなければならない。

公開する不受理結果には、理由を説明する Error を少なくとも一件残す。実行時には結果単位で検査し、全ノードの未完了要求を集める台帳は作らない。独立した失敗や原因不明の不成立は各解析が報告し、網羅性は変異テストで確認する。無関係な Error を別問題の省略理由にしない。後続フェーズを開始できないだけなら前段の結果を参照し、空の不受理結果を作らない。

| Outcome | 意味と必要な診断 |
| --- | --- |
| Completed | チェックを実行した。言語エラー・証明不成立・未対応などによる不受理も含む |
| Blocked | 入力・実効設定を確立できない。「入力・設定」の Error で説明する |
| Faulted | コンパイラ内の例外、または診断契約の障害で終了した。「内部障害」の Error で説明し、再利用しない |
| Cancelled | コマンドの中止。結果を公開しない |

Outcome は終了状態から決め、分類から逆算しない。安全な継続を解析が保証した経路で InternalInvariant_Kd を報告して終了した場合は、Completed かつ不受理になり得る。

入力・設定の失敗は通常の事実として確定する。診断経路が健全なまま解析が例外で終了した場合は、有効な事実に内部障害を加え、共通経路で Faulted を作る。CheckService.Create の独立した整形は統合する。

カタログ読み込み・収集・確定をエラー境界に含める。未知コードを含む定義・位置・引数の不正、必須事実の矛盾、不受理なのに Error がない状態、収集・確定処理の失敗は、一つの退避処理で Faulted・不受理にする。退避診断は小さな障害種別を Reason に持ち、対応する固定本文でも説明する。種別は失敗箇所で決め、カタログ・壊れた引数・通常の整形や確定処理に依存せず、事前に定めた値から生成する。

退避用の固定値は一か所にまとめ、通常経路から同じ退避診断を作る場合も共有する。カタログにも載せるコード名・重大度・分類・既定文との一致はテストで保証し、退避中は照合やカタログの再読み込みを行わない。

信用できない途中の公開列は破棄する。説明欠落だけを Completed として再利用する例外は設けない。中止と、未確立の入力を待つ制御は既存の扱いを保つ。

### 4.2. 段階と完了条件

各段階を「再現例 → 実装 → 対象を絞った検証」の小さな単位に分ける。

- **段階1：基準と定義**

   代表的な変異と性能の基準を記録する。現行の全定義（確認時点で Template を含む146件）と呼び出しを監査し、分類・引数・役割、検査種別の安定名・条件の型・順位・区画を定める。派生専用コード、要求説明表、Advice を導入する。説明表の未知名・重複・欠落と退避定数の一致を検査する。情報を落とす変換より前に現行 API のコード・引数・位置を検査し、関連テスト・Milestone・変異ケースの違反を修正する。

- **段階2a：共通の確定境界**

   所有者・区画・局所結果、位置型とソース表、共通レコードと退避処理、CLI・LSP の順に移す。独立したエラー状態を廃止し、出力と終了状態を比較する。移行用の収集口では旧収集単位と開始位置のキーを再現し、範囲なしも開始位置0とする。この暫定キーを改良・全結果へ拡張しない。共通位置型では範囲なしと長さ0を区別する。

   この段階は情報を運ぶ互換段階とし、旧抑制による別問題の衝突・欠落を新モデルの契約違反にしない。共通化・世代・エラー状態による差は個別に検証し、無関係な本文・件数の変化を防ぐ。

- **段階2b：問題の同一性と明示依存**

   全記録元に固定した検査キーと原因をそろえ、集約と参照された見送り原因の引継ぎを実装する。構文回復からの連鎖抑制、独立問題の存続、未対応・判定不能・診断欠落の区別、事実の整合性、不受理理由、合成主体を含む意味順を確認する。LSP は送信値ごとの件数集約と整列を分ける。切り替え時に旧位置抑制、BorrowOriginHint による抑制、DiagnosticDependencyVisitor を撤去する。

- **段階3：説明の改善**

   有界な整形・引用、診断単位の補足取得を仕上げる。型不一致の相違箇所、不正な代入から理由と下線を改善し、Move・借用・オーバーロードの詳細は取得費用を確認して広げる。

- **段階4：総合評価**

   §5 の検証を完了し、CLI・LSP の結果、性能、検証済みの範囲と残る制限を記録する。

新しい契約の検査は対応する境界の移行時に追加し、問題キーの整合性と不受理理由の保証は2bで完成させる。経路別の旧・新モードや `(範囲, Code)` という中間の同一性を残さない。説明は導入時から有界にする。

enum は自動生成せず、定義との一致をテストする。カタログの未知名・重複・欠落は読み込み時にも検出する。テストでの違反0件を全入力の証明とせず、製品に検査を弱めるモードを設けない。

| 構文回復 | 欠けた式・型・閉じ記号から Binding へ続く連鎖、複数原因、対応不明の保持、近い位置の独立問題、意味解析の再実行と構文区画の交代 |
| エラー状態・世代 | 同位置の Warning 後の Error、呼び出しの入れ子、無効トークンの非キャッシュ、木の再構築・空への置換、構文解析後の入力エラー保持、Ownership 再解析後の Binding 診断保持、ライブラリと TestPresence の範囲 |
| 終了・寿命 | 不受理の Error、説明欠落の Faulted と再試行、解析例外での有効事実の保持、退避の全障害種別とカタログ非依存性、中止、再束縛・作業領域再利用後の記録済み事実、ソース解放後の出力、後続処理による既存結果の不変性 |
| 位置・文脈 | 同じパスの別スナップショット、入力 revision の共有・未登録の初回読み取り・CLI の所有者別トークン、主位置・関連位置の代替説明と URI の固定、版だけの変更・保留解除、複数ファイル、UTF-16・CRLF、長さ0・範囲なし・ソースなし、内部番号の割当順、同範囲の合成主体、同位置・同コード・同条件番号で異なる検査種別、Origin だけ異なる具体化と外側の文脈 |
| 出力・上限 | 全項目と表示用データの比較、Kind の非公開、Note だけの変更、LSP の集約・順序・鮮度・再利用、[A, B, A] と [A] の集約、重複候補・再報告・バッチ分割・集約順、補足取得回数と一問題に多数の根拠、末尾だけ異なる巨大な型、制約・識別子・引用、合計上限と省略情報、省略した例外文だけが変わる場合の再検証と同値表示 |

入力間の関係も検査する。

- 空行の追加では、対応位置以外の意味情報が変わらない。
- 同じ検査・意味上の入力・前提なら、無関係な問題を追加しても既存の主診断と説明が変わらない。検査が見送られる場合は別に確認する。
- 文言だけの変更では、同一性・抑制・意味順が変わらず、公開値の変更は検出される。
- 仕様上のソース順を保って処理順を変えても、公開内容と順序が変わらない。
- 表示上限を変えても、問題の存続・分類・受理が変わらない。

編集前後はコード・検査条件・理由・対応位置で比較し、永続 ID を要求しない。全文一致は少数の表示テストに絞り、下線と説明の対応は人も確認する。診断件数の削減自体を合格条件にしない。

### 5.2. 性能制約と測定

正常経路に診断用のノード単位の割り当てや文字列生成を追加しない。合成主体の識別も既存構造と変換の契約から報告時に求め、診断専用の常設フィールドを増やさない。固定値・空表現・既存の根拠を共有し、局所結果は値型や既存状態で持つ。追加時のロックは呼び出し経路を確認してから外し、並列化は対象外とする。

文字列化と表示順のキー生成は抑制後の公開対象だけに行う。不要なボックス化を避け、ソース・文脈のキーを再利用する。コード名と検査種別の順位は初期化時に一度作り、通常は整数で比べる。小さな問題キーのハッシュは使えるが、公開値はハッシュ一致だけで同値としない。同じ不変結果の参照一致は比較を短絡できる。

| 処理・保持量 | 目標 |
| --- | --- |
| 依存の走査 | 集約後の事実数 F・前提参照数 E に対して O(F + E)。検査ごとの判定を共有し、参照元数と原因数の積に比例する展開を避ける |
| 公開診断の整列 | D 件に対して比較回数 O(D log D)。キーの準備・比較の費用も測定する |
| 補足の取得 | 公開 D 件・一診断の走査上限 B に対して O(D × B)。既存解析の費用や必須の原因参照 E とは分ける |
| 公開説明の保持 | 一診断の説明量上限 K に対して O(D × K)。補足の一時保持も診断単位で制限する。入力・解析・内部事実全体の絶対上限ではない |

同じマシン・設定・入力で変更前後を比較する。初回／初期化後、再利用／再解析、CLI／引用なしの LSP を分け、時間・割り当て・保持量・再解析回数と規模に対する伸びを測る。収集時の集約、区画の破棄、キー処理、文字列化、LSP 変換を含め、領域の消去や GC まで定数時間とはみなさない。

測定ケースは、診断なし・警告・多数の独立エラー・同一問題の大量再報告・一問題に多数の補足根拠・構文回復と長い依存列・深い具体化・型の相違探索・巨大な引用・多数ファイルの世代交代とする。生存する入力・結果の規模が一定なら、本文・登録索引・回復対応表の保持量が世代数に比例しないことを確認する。

基準測定後、実装前に比較方法と許容範囲を記録する。割り当ては影響する頻繁な処理と完了時に測り、初期化・キャッシュ・スレッド移動を区別する。CurrentThread だけで非同期処理全体を評価せず、全処理の割り当て差分を厳密な0とする基準や時間を無視する基準は使わない。再現する性能低下は原則解消し、残す場合は先に簡略化・延期を検討して利益と費用を記録する。

### 5.3. 実施手順と証拠

各実装単位は `scripts/verify.ps1 -Class ...` と関連するネイティブ実行用テスト・Milestone ハーネスで検証し、検証済み単位ごとにコミットする。実装セッション末尾に Session 検証を一度行う。ビルド中はソースを編集せず、NativeAOT は実行しない。拡張機能を変更した場合は、その検証手順にも従う。

失敗を含む証拠は artifacts/verify/、測定は artifacts/benchmarks/、使い捨て出力は temp/ に置く。計画書だけの変更では内容・参照・差分を確認し、ビルドや性能測定は行わない。未測定の改善を性能実績として記載しない。

## 6. Deferred

以下は必要性が明らかになった時点で、契約と費用を確認して実装する。現段階では実装時期を割り当てない。

| 項目 | 導入条件・方針 |
| --- | --- |
| 永続的な診断 ID | 編集・セッションをまたぐ追跡が必要なとき。対応付けを意味上の妥当性の保証にしない |
| 全 AST・全解析処理の因果グラフ | 失敗に限った明示依存では説明・デバッグの要求を満たせないとき |
| 診断への構文・意味ノード ID | CSP の調査・移動に必要なとき。有効範囲をスナップショット・結果内に限定する |
| 完全な型・制約の構造化表現 | 有界な表示値では調査要求を満たせないとき。共有部分・循環・取得上限を定める |
| 抑制した事実の照会・件数、suppressedBy、公開診断の結果内 ID | 照会要求があるとき。共有原因の数え方、容量、参照の寿命を定める。原因修正後は再検証し、依存関係だけで改善を保証しない |
| CSP サーバー・公開スキーマ・永続入力と結果・検証証拠 | 共通基盤の検証後に設計する。内容 ID を実バイト列へ結び付け、BOM を除く復号テキストへの位置対応を定める。[既存の入力識別体系](../../docs/spec/18-modules-and-dependencies.md#1841-identities-and-graph) に接続し、ProjectSnapshotId だけで解析結果まで識別しない |
| 診断・要求説明カタログの公開・enum 自動生成 | 利用側の要求や保守費用が導入費用を上回るとき。公開時は版の対応を定め、Message を失わせない |
| Repair の生成・プレビュー・適用・検証 | 前提条件と保証を示せる修正から導入する。編集と検証結果を分け、指定した入力・設定で検証し、古い入力や編集競合を拒否する |

## 付記：設計判断

以下は判断理由の要約であり、規則は本文に従う。

| 選択 | 理由 |
| --- | --- |
| 既存の解析型を残し、診断の境界を共通化する | Warning と検査条件を表せれば、全フェーズの Failure 型への置換や全解析 API の変更は不要 |
| 既存定義と小さな型付き生成処理を使う | 静的な文はカタログ、意味と型は C# を正本とし、要求説明は小さな表で補う。動的な説明の定義言語、Kind、Derived の許可フラグを増やさない |
| 原因を検査キーで明示する | 単一の原因ポインターでは複数原因を失い、対象だけの探索では別問題を巻き込む。成功検査や未検査ノードの全台帳も不要 |
| 寿命・同一性・公開値・順序を区別する | 一つのフラグ、索引、最新ソースだけでは、それぞれの役割と再解析範囲を満たせない |
| 補足は抑制後に診断単位で取得する | 全体予算は局所性を損ない、根拠ごとの予算と捕捉履歴は内部保持量を抑えられない。必須の原因参照と任意の説明は分ける |
| 未解決状態を一律に Derived へ変換しない | 構文上の祖先は原因の証明ではない。未対応の誤分類や診断漏れの隠蔽を避け、失敗を確認する検査が報告する |
| 診断契約違反は一つの退避経路で扱う | 固定値を共有しカタログとの一致を検査する。説明欠落を Completed にすると、診断経路の健全性や再利用を保証できない |
| 同順位は主体・検査・文脈の定義で解消する | 有界な Reason や補足だけでは全文の一致を保証できず、表示上限や文言で意味順が変わる。合成主体の規定順を使う |
| データ構造は用途と測定で選ぶ | 辞書数の一律制限、固定ビット数への詰め込み、全内容の事前ハッシュ、無条件のロック撤去は性能を保証しない |
| CSP の本格機能を Deferred とする | 初期の診断改善には不要な保持量・公開契約を増やさず、必要性と費用を確認して広げる |
