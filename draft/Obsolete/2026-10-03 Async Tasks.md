# 設計案：非同期処理（中断能力と構造化タスク）

日付：2026-10-03

状態：初版。採否は未決定。正式仕様への取り込みと実装は未実施。

本書は、Kimigayo に非同期処理を加える設計を示す。C#、Rust、Swift、Go、Kotlin の方式を比較し、現在の所有権・Lifetime 規則（SPEC 第 15・16 章）と Kimigayo Principles に合わせた。新しい規則はできるだけ少なくし、既存の概念（Loan、呼出しの保護、未知の効果、Scope Exit、`Result`、Owned）を使い回す。SPEC の節は「SPEC §n」、実装仕様の節は「impl §n」、本書の節は「本書 n」と表記する。

要点は四つある。

1. **中断する権限を入力にする。** 中断できる関数は、能力型 `uniq/Async.Task` のパラメーターを持つ。キーワードは足さない。
2. **未完了の計算を値にしない。** Future や Task 値はなく、`Pin` も要らない。
3. **子タスクは Kimi の呼出しの引数にする。** 呼出しが戻る前に子が必ず完了するので、子は親の局所変数を借用できる。
4. **取消しは値にする。** 待機する操作が `Result` で報告し、後始末は通常の Scope Exit が行う。

## 1. 現仕様の問題

1. **非同期処理がない。** SPEC §22.2.3 は実行スレッドを一つに限り、タスク・スレッド・メモリーモデルは SPEC §D.2 で保留している。I/O を待つ間に他の処理を進める手段がない。
2. **取消しの後始末が決まっていない。** SPEC §16.2.3 は「取消しを導入するなら、Deferred Block・破棄・確保済みの結果について共通の規則が要る」とし、SPEC §15.9 も未定義としている。
3. **他言語の方式をそのまま入れると既存規則と衝突する。**
   - Rust の `Pin` は、すべての値をバイト転送で移動するという規則（impl §21.4.5）と衝突する。
   - Future の破棄による取消しは、SPEC §16.2.3 にない「途中での完了」を必要とする。
   - 環境を借用する Future を返すことは、受け手に依存する公開結果になる。これは保留中である（SPEC Appendix D）。
   - Go や Kotlin のように呼出し側に印がないと、中断点が局所的に分からない（Principle 2）。
   - 値の破棄を前提にした scoped task は、値がリークすると健全でなくなる（Rust の `mem::forget` 問題）。

## 2. 方針

1. **中断の権限は入力。** SPEC §8.4.10.2 は環境効果を「権限を入力からではなく環境から得る操作」と定める。中断の権限を入力（能力パラメーター）にすれば、シグネチャーだけで中断できるかどうかが分かる。推論は要らない。
2. **未完了の計算を値にしない。** 活性（activation）は値ではない。移動もコピーも格納もしない。
3. **構造は呼出しの期間で保証する。** 子タスクは Kimi の操作（`join` など）の引数であり、その操作は子の完了前に戻らない。健全性は破棄の実行に依存しない。
4. **取消しは要求で、値として観測する。** 割り込み・巻き戻し・活性の破棄はしない。
5. **単一スレッドから始める。** スレッドをまたぐ規則は後の段階（本書 12）とする。

## 3. 中核規則

| # | 規則 | 再利用・拡張する既存概念 |
| --- | --- | --- |
| 1 | **能力型。** `Kimi.Async.Task` は能力型である。能力型の一覧は SPEC §22.1 が閉じた形で定め、当面は `Async.Task` だけとする。その値は Kimi の操作（`Async.run` と子タスクを開始する操作）だけが作る。`Async.Task` はタスクごとのハンドルであり、実行器そのものではない。 | Kimi の必須宣言（SPEC §22.1） |
| 2 | **非脱出。** 能力型は、関数・Closure・Function Type・Callable シグネチャー・Contract 要件の直接パラメーターの完全型 `uniq/Async.Task` としてだけ現れる。使い方は、直接の引数または受け手として渡すこと（SPEC §3.5 の Reborrow）だけである。<br>• 捕捉・局所変数・Field・要素・生ポインターの指す型・結果にならない。<br>• 型引数にならない。推論された型引数と関連型の指定も含み、束縛する場所で診断する。<br>• 結果の依存にならない。結果の既定（SPEC §15.4.3）と Callable の呼出しごとの Origin（SPEC §8.6）の入力に数えず、その Origin には名前を付けられない。<br>• 外部表現を持たない。 | `uniq` の排他性、呼出しごとの Origin、型引数の表（SPEC §8.1.3）。保留中の非脱出宣言（SPEC Appendix D）の閉じた特例 |
| 3 | **中断点。** 能力を引数または受け手として受け取る呼出しを中断点と呼ぶ。中断点では、その本体で生きているすべての Loan を、可変静的 Field と外部状態に未知の効果を持つ呼出しに対するものとして比較する。効果要約と公開記録（SPEC §18.7.2）には何も加えない。 | 未知の効果の比較（SPEC §15.6.4） |
| 4 | **再開可能な活性。** 能力パラメーターを持つ本体は再開可能である。これは宣言されたシグネチャーだけで決まり、インスタンスごとには決めない。制御は中断点でだけ本体を離れる。活性は値ではなく、開始から完了まで固定アドレスを持つ。活性は完了（通常の return と Scope Exit）・発散・Abort でだけ終わる。割当てに失敗すると Abort する。 | 呼出しの保護（SPEC §15.6.4）、固定アドレスの payload（SPEC §5.2.1）、消去時の割当て失敗（SPEC §7.6.4） |
| 5 | **構造化完了（Kimi の義務）。** Kimi の操作が開始した活性は、その操作が戻る前に完了する。`join`・`tryJoin`・`each`・`race` は子の完了後に戻る。`run` は根と切り離したタスク（本書 15 の第 2 段階）の完了後に戻る。 | Kimi が負う義務（SPEC §22.1.2.5 の Storage 境界と同じ形） |
| 6 | **取消しは値。** 取消し要求は、タスクとその子にフラグを立てる。<br>• 観測するのは、自分の子以外の事象を待つ Kimi の操作だけである。その操作は `Async.Cancelled` を含む `Result` で報告する。`join` は観測しない。<br>• 活性を中断・巻き戻し・破棄しない。完了の種類も増やさない。Deferred Block・破棄・確保済みの結果は、プログラムが書いた通常の return に従う。 | `Result` と `try`（SPEC 第 17 章）、Scope Exit（SPEC §16.2）。SPEC §16.2.3 が求める規則をこれで満たす |
| 7 | *（第 3 段階、SPEC §D.2 の設計として）* **スレッド。** 本書 12。 | Owned（SPEC §15.2.3） |

Kimi の実装には、言語規則とは別に次の義務を課す（SPEC §22.1 に記す）。

- **表現。** `Async.Task` のインライン記憶域は、能力が生きている間は書き換えない。取消しフラグ・起床状態・タイマーの連結・アリーナの位置など、変わる状態はすべて、読み込んだポインターの先にある Kimi 内部の生記憶域に置く。中断の intrinsic は、その状態に対するコンパイラーバリアとする。これで `uniq` の `noalias`（impl §21.5.5）が保たれる。
- **内部操作。** 活性の開始・中断・再開・完了の判定・結果の取出し・完了後の破棄を、`Kimi.Storage` と同じく宣言の同一性に結び付けた内部操作として定め、それぞれの unsafe な義務を記す。義務は、二重に再開しない、完了後に再開しない、最後の中断より前に破棄しない、自分の内側から再開しない、の四つである。

### 3.1. 新しい規則なしに従うこと

次の項目は既存規則と規則 1〜6 から導ける。

- **中断できない場所。** アクセサー（SPEC §11.2）、`drop`（パラメーターを持たない、SPEC §16.3.1）、静的初期化子、`main`（SPEC §22.2.2）は、能力を受け取れないので中断しない。パラメーターの既定値も中断しない。既定値は前のパラメーターを排他的に使えないからである（SPEC §7.2.3）。
- **中断できる後始末。** 再開可能な本体の中では、`defer` の本体も能力パラメーターを使って中断できる。外へ出る移動は従来どおり禁止なので（SPEC §16.1.1）、結果は `_ =` で捨てる。
- **関数の色。** 色は宣言されたパラメーター型そのものである。Function Type、Callable、Contract、消去（SPEC §7.6.4）の規則は変わらず、非同期の区分や変換規則は要らない。
- **同期の実装。** 能力を取る Contract 要件を同期的に実装するには、そのパラメーターを使わなければよい。
- **局所性。** 中断点は局所的に判定できる。能力はその本体のパラメーターとしてしか存在しないので、引数にそのパラメーターがあるかを見ればよい。

## 4. エフェクトの使い方

### 4.1. Kimigayo の effect

Kimigayo の effect はアクセスの権限を表し、制御の流れは表さない（SPEC §8.9、§8.4.10、§15.6.4）。権限の出所は二つに分かれる。

- **入力から得る権限。** シグネチャーで見える。
- **環境から得る権限。** 可変静的 Field や外部状態から得る。効果要約で扱う。

### 4.2. 中断の権限を入力にする

本書は、中断の権限を入力の側に置く。これは「能力としての効果」で、Effekt の能力渡し、Scala 3 の capture checking、Zig の明示的な `Io` パラメーターと同じ考え方である。

- **ハンドラー。** 能力を作った Kimi の操作（`run`・`join` など）がハンドラーに当たる。ハンドラーは字句的で、静的に決まる。
- **再開。** 再開は一度だけで、活性は値にならない。そのため、所有権の規則（Non-Copy の状態は複製できない）と矛盾しない。
- **制限された中断。** 型で表せる。能力を受け取らない Callable は中断できない。

### 4.3. 中断中に起きること

中断している間は他のタスクが動く。これは「効果が未知の呼出し」と同じなので、既存の比較（SPEC §15.6.4）を中断点にそのまま適用する（規則 3）。

規則 3 は、効果要約に行を足さない。足すと、中断しない呼出し元にまで効果が広がり、`confined` や `preserves results` の証明を壊すからである。

### 4.4. 採らなかった効果の方式

- **代数的効果とハンドラー（Koka、OCaml 5）。**
  - ハンドラーを動的に探すので、Principle 2 に反する。
  - 再開されない継続には、SPEC §16.2.3 にない後始末規則が要る。
  - Koka の複数回の再開は、Non-Copy の状態を複製する。
  - 例外や yield の効果は、第 17 章の失敗と LendingIterator（SPEC §22.1.2.1）を二重にする（Principle 1）。
- **`effect suspends` のような effect bound。** effect bound は Contract にしか書けず、実装を縛るだけである（SPEC §8.4.10.1）。中断は呼び方そのものを変えるので、この形に収まらない。本体から推論すると中断が見えなくなる（Principle 2）。
- **効果の多相、`reasync`。** 能力は型なので、総称化の余地はある。ただし、汎用の本体は一度だけ検証されるので（SPEC §8.10）、どの能力でも効果は同じになり、得るものが少ない。SPEC Appendix D が保留する「一般の効果システム」とともに保留する。

## 5. 書き方

### 5.1. 宣言と呼出し

```kimi
public func fetchPage(task: uniq/Async.Task, url: ref/Url) -> Result<Page, Net.Error>
    var connection = try Net.connect(task, url)   // 中断点
    return connection.readPage(task)              // 中断点
```

- **書き方の規約。** 能力パラメーターは `self` の直後に置き、名前は `task` とする（STYLE で定める）。`Async` 接尾辞のような同期版と非同期版の対は作らない。
- **呼出し。** 能力を渡すことが、そのまま待つことになる。`await` は書かない。

### 5.2. 子タスク

```kimi
func fetchBoth(task: uniq/Async.Task, a: ref/Url, b: ref/Url) -> Result<(Page, Page), Net.Error>
    let getA = func [a] (t: uniq/Async.Task) -> Result<Page, Net.Error> => fetchPage(t, a)
    let getB = func [b] (t: uniq/Async.Task) -> Result<Page, Net.Error> => fetchPage(t, b)
    return task.tryJoin(getA, getB)   // 中断点。子は並行に動き、一方が失敗すると他方を取り消す
```

```kimi
func normalizeAll(task: uniq/Async.Task, rows: uniq/Array<Row>, limits: ref/Limits) -> ()
    let fix = func [limits] (t: uniq/Async.Task, row: uniq/Row) => normalize(t, row, limits)
    task.each(rows.iterateUniq(), fix)   // 項目ごとに一つの子。各 uniq/Row は互いに重ならない
```

| 操作 | 意味 |
| --- | --- |
| `task.join(a, b)`、`task.join(a, b, c)` | 個数が固定で型の異なる子を並行に動かし、すべての結果を Tuple で返す。可変長の型引数はないので（SPEC §8.1）、子の数ごとに多重定義する |
| `task.tryJoin(a, b)` など | `join` の try 形（STYLE の try 接頭辞）。最初の失敗で残りを取り消し、合流してから返す |
| `task.each(items, child)` | Iterator の項目ごとに子を一つずつ動かす。排他的な項目は領域分割で互いに重ならない（SPEC §22.1.2.3） |
| `task.race(a, b)` | 先に完了した子の結果を返す。敗者は取り消して合流してから、その最終結果も返す |
| `task.sleep(d)`、`task.checkCancelled()` | 待機と取消しの確認 |
| `Async.run(root)` | 同期コードからの唯一の入口 |

- **子の型。** 子は `F is Callable<ref, (uniq/Async.Task) -> R>` の形をとる。能力は捕捉できないので、パラメーターで受け取る（規則 2）。

```kimi
    let later = func [task] () => task.sleep(delay)   // Error: 能力は捕捉できない（規則 2）
    let saved: Option<uniq/Async.Task> = .None        // Error: 能力は型引数にならない（規則 2）
```

### 5.3. Contract

```kimi
public contract Reader
    func read(self: uniq/Self, task: uniq/Async.Task, buffer: uniq/Array<u8>) -> Result<u64, Io.Error>
```

非同期の実装も同期の実装も、同じ要件を満たす。同期の実装は `task` を使わない。

### 5.4. 中断をまたぐ静的 Loan

```kimi
group Settings
    var greeting: string = "hello"

func greetLater(task: uniq/Async.Task, delay: Time.Duration) -> Result<(), Async.Cancelled>
    let text = Settings.greeting@ref
    try task.sleep(delay)        // Error: 可変静的 Field Settings.greeting を借用したまま中断する
    Console.writeLine(text)
    return .Ok(())
```

### 5.5. 後始末と入口

```kimi
func appendLine(task: uniq/Async.Task, path: ref/string, line: ref/string) -> Result<(), Io.Error>
    var file = try Io.File.open(task, path)
    defer => _ = file@move.close(task)     // 後始末も中断できる
    return file.write(task, line)

public func main() -> ()
    _ = Async.run(func [] (task: uniq/Async.Task) => serve(task))
```

- **入れ子の `run`。** `Async.run` はどこからでも呼べる。入れ子の `run` は自分の根と子だけを実行し、外側の実行器をその間止める。これで、同期コードから非同期の操作を使える。外側のタスクは入れ子の中では動かないので、初期化中の静的 slot（SPEC §22.2.3）に他のタスクが触れることもない。
- **Abort しない。** 入れ子の `run` で Abort すると、Abort するかどうかが動的な文脈で決まり、Principle 2 に反する。

## 6. 所有権と Lifetime

### 6.1. 中断をまたぐ Loan

- **局所変数とパラメーター。** これらへの Loan は中断をまたいで保持できる。呼出しの保護は「呼び出された側の後始末を含め、呼出し全体」に及び（SPEC §15.6.4）、活性の位置は規則 4 で固定されるからである。
- **他のタスクが触れられる経路。** 他のタスクがこのタスクの状態に触れる経路は四つしかない。
  - 渡された Loan。引数の Loan として検査する。
  - 可変静的 Field と外部状態。規則 3 が扱う。
  - `rc`・`arc` の payload。共有アクセスしかできない（SPEC §13.5.5.2）。
  - Kimi 内部の生記憶域。Place を公開しない。
- **生ポインター。** 生ポインターに固定された Loan は上限を持たない（SPEC §5.2.2）。中断をまたぐ場合は unsafe な義務になり、CSP がその一覧を出す（本書 11）。

### 6.2. 子タスクの借用

- **子は引数。** 子は Kimi の呼出しの引数なので、子の Loan は呼出しの間続く引数 Loan である。規則 5 により、子はその呼出しが戻る前に合流する。
- **共有借用と排他借用。**
  - 共有借用は `ref` のコピーとして子に配れる。
  - 排他借用は互いに重なってはならない。別々のパラメーター、Reborrow の捕捉、または領域分割された Iterator の項目から得る。
- **重なる排他捕捉。** 二つの子が同じ `uniq` を捕捉すると、通常の Loan の衝突になる（SPEC §7.6.2、§15.6.7）。
- **Owned の要否。** Rust の `'static` に当たる Owned は、子には要らない。要るのは、合流しない切り離したタスク（第 2 段階）だけである。

### 6.3. リークへの耐性

- **リークが健全性に影響しない理由。** 実行中の子を表す値（ハンドルやガード）は利用者の手に渡らない。そのため、`rc` の循環（SPEC §16.4）や unsafe なリークがあっても、親の Loan が早く終わることはない。
- **早期終了。** Abort はすべての観測者を終わらせ、発散は戻らない。
- **要らないもの。** 型が Origin より長く生きることを表す制約（Rust の `F: 'a`）も、規範的なリーク禁止規則も要らない。

### 6.4. 移動と Pin

- **Pin は要らない。** 活性は値ではないので、固定する概念が要らない。同じ活性の局所変数を借用したまま中断することは、固定アドレスの payload（SPEC §5.2.1）を指す借用と同じく正しい。
- **既存の規則は変えない。** すべての値をバイト転送で移動するという規則（impl §21.4.5）はそのまま残る。

## 7. 取消しと失敗

- **取消しの発生源。** `race` の敗者、`tryJoin` で兄弟が失敗したとき、`run` の終了。
- **観測。** `sleep`・I/O・チャネルの `send`/`receive`・`checkCancelled` が観測し、`.Err` を返す。誤りの型は暗黙に合成しないので（SPEC §17.2.4）、明示的に変換する。`join` は観測しない。
- **後始末。** 通常の Scope Exit が行う。非同期の後始末は `defer` の中で中断して行う（本書 5.5）。
- **Abort。** プロセスを終わらせる（SPEC §17.3.3）。
- **非同期の `drop` はない。** `drop` はパラメーターを持たないので、同期的に閉じる。実行中の I/O は、その呼出しが Loan を保持し続けるので、`drop` と重ならない。
- **時間の上限。** タイムアウトは `race` と `sleep` で書く。上限が効くのは、観測する操作を通る場合だけである。

## 8. 通信

- **チャネル。** 送信端 `Async.Sender<T>` と受信端 `Async.Receiver<T>` に分け、どちらも `uniq/Self` の受け手で操作する。
- **共有した変更を作らない。** `ref/Self` で変更する API は作らない。作ると、共有経路からの変更という新しい可変性の概念が入り、`rc` の payload を通って Owned でない強い循環も作れてしまう。
- **端点間の結合。** 二つの端点が状態を共有していても、その状態に触れるのは中断点だけである。規則 3 と、外部状態の行（SPEC §8.4.10.2）で扱える。

```kimi
public func send(self: uniq/Self, task: uniq/Async.Task, value: T) -> Result<(), Async.SendError<T>>
public func receive(self: uniq/Self, task: uniq/Async.Task) -> Result<T, Async.ReceiveError>
```

- **送信の失敗。** `SendError<T>` は `Closed` と `Cancelled` のどちらでも値を返す。
- **受信の取消し安全性。** `receive` は完了したときにだけ項目を取り出す。
- **バッファーの破棄。** バッファー内の項目はチャネルとともに破棄する。`T` は借用を持ってよい。チャネルの型が `T` の Origin を運ぶからである。
- **ストリーム。** `loop` と `match` で受信する（`while let` はない、SPEC §14.2.3）。
- **複数チャネルの `select`。** 後でライブラリとして加えられる。Rust の `select!` のように敗者を捨てる形は採らない。

## 9. 実行器と実行時

- **実行器は一つ。** `Kimi.Async` が、単一スレッドの標準実行器を Kimigayo で実装する。構成は、FIFO の実行待ち列、QPC で動くタイマーヒープ（SPEC §22.7）、`GetQueuedCompletionStatusEx` による IOCP ループである。Rust のように実行時ライブラリが分かれることはない（Principle 1）。
- **重ね合わせ I/O。**
  - `OVERLAPPED` は待っている活性の中に置く。その位置は規則 4 で固定されている。
  - 取り消すときは `CancelIoEx` を呼んだうえで完了通知を待つので、借用したバッファーも健全である。
- **入口とテスト。** `main` と `#Test` は同期のままで、`Async.run` を呼ぶ（SPEC §22.2.2、§22.6 は変わらない）。
- **コールバック。** コールバックや APC は使わない（SPEC §22.3.1）。
- **ブロックする外部呼出し。** 外部呼出しがブロックすると、そのスレッドの全タスクが止まる。別スレッドへの退避は第 3 段階で扱う。
- **実行器の選択。** Composition Root の設計（SPEC §13.8）を待つ。

## 10. 実装と性能

- **下げ方。** 再開可能なインスタンスは、LLVM の switched-resume コルーチン（`coro.id`・`coro.begin`・`coro.suspend`・`coro.end`、CoroSplit）に下げる。
  - **隠し引数は要らない。** 能力のポインターがタスクの文脈になる。
  - **O0。** `llc -O0` は `llvm.coro.*` を下げられない。再開可能な本体を含むモジュールでは、`llc -O0` の前にコルーチンの下げパスを走らせる。impl §21 とツールチェーンのマニフェストに記す。
- **フレーム。**
  - `coro.alloc` と `coro.free` は、タスクごとのアリーナを後入れ先出しで積み下ろしする。
  - 一つのタスクで再開可能な呼出しは一本の鎖をなすので、後入れ先出しで足りる。
  - フレームの大きさは、単一化したインスタンスごとに決まる。これは表現だけの義務である（SPEC §8.10）。
- **再開。** 中断せずに完了する呼出しは、実行器に触れない。再開はトランポリンを通す。スタック枯渇は未規定だからである（SPEC Appendix D）。

| 操作 | ヒープ割当て |
| --- | --- |
| 中断点、再開可能な呼出し | 0（アリーナの積み増し） |
| タスクの開始 | プールした記録とアリーナの塊。定常状態では 0 |
| チャネル操作 | 0（リングバッファー） |

- **CoroElide。** 子のフレームを親に埋め込む最適化は、ハンドルが実行器の列に入ると効きにくい。そのため、`Purpose=Allocation` の検査には含めない。上の表を `Purpose=Allocation` の回帰で固定する。

## 12. スレッド（第 3 段階、SPEC §D.2）

第 1・2 段階はスレッドを一つに保つ（SPEC §22.2.3）。タスクは中断点でだけ交互に動くので、Send・Sync に当たる概念は要らない。第 3 段階では次の規則を加える。

- **移動しないもの。**
  - 実行器はスレッドごとに一つとし、タスクはスレッドを移らない。
  - 活性の中身は、別スレッドへの移送を証明しなくてよい。
  - 中断中の活性を所有する値は、移送できない。
- **移送可能性。** 値がスレッドをまたぐのは、タスク開始の入力、スレッド間チャネルの payload、結果の三つだけとする。いずれも `T is Owned` と `T is Transferable` を要する。
  - `Transferable` は、Copy と同じく宣言する。構造的に検査し、本体からは推論しない（SPEC §D.5.1 の先例、Rust の auto trait の漏れを避ける）。
  - 内部可変性がないので、Sync に当たる別の述語は要らない。
  - `rc` は `Transferable` ではない（共有借用から計数を変える）。`arc/T` は `T` が `Transferable` のときだけ `Transferable` である。
- **静的 Field。**
  - 可変静的 Field は、最初のスレッドの実行器に閉じ込める。
  - 他スレッドから届く静的 Field は、不変かつ `Transferable` でなければならない。
  - 初期化はスレッドをまたぐ一度だけの手順で行う。他スレッドの初期化中は待ち、同じスレッドでの循環だけを Abort とする。
- **メモリーモデル。** 安全なコードはデータ競合がなく、逐次一貫である。happens-before は、スレッドの開始と合流、チャネルの移送、`arc` の手順（impl §21.2.3）から生じる。
- **隔離。** actor は導入しない。状態を所有するタスクがチャネル越しに要求を受ける。

## 13. 他言語との比較

| 観点 | C# | Rust | Swift | Go | Kotlin | 本書 |
| --- | --- | --- | --- | --- | --- | --- |
| 中断の仕組み | ヒープの状態機械 | Future 値（インラインの状態機械）と `Pin` | タスクの割当て器から取るフレーム（値でない） | スタックフル（スタックを複製） | CPS 変換と `Continuation` | スタックレス、固定アドレスの活性（値でない） |
| 印 | `async`/`await` | `async`/`.await` | `async`/`await` | なし | `suspend`（呼出し側に印なし） | 能力の引数 |
| 未完了の計算の値 | `Task` | `Future` | `Task`、`async let` | なし | `Deferred` | なし |
| 構造化 | 慣習（`WhenAll`） | `thread::scope` のみ健全。非同期の scoped task は forget で不健全 | `TaskGroup`、`async let` | `errgroup`（慣習） | `CoroutineScope`、Job の木 | 子は Kimi の呼出しの引数（呼出しの期間で保証） |
| 取消し | `CancellationToken` と例外 | Future の破棄（取消し安全性の問題） | 協調フラグと `CancellationError` | `context.Context` | `CancellationException` | 協調フラグ、`Result` の値 |
| スレッド安全 | 検査なし | Send・Sync の auto trait | `Sendable`、`sending`、actor | 検査なし（race detector） | Dispatcher | 第 3 段階で `Transferable`（宣言し構造的に検査） |
| 実行器 | スレッドプール、SynchronizationContext | ライブラリごとに分かれる | 標準 | 標準の M:N | Dispatchers | 標準の一つ |

取り入れたもの：

- **Rust：** 単一化による静的なフレームの大きさ。中断をまたぐ借用の精密な検査（`Pin` なし）。`thread::scope` 型の借用。
- **Swift：** 動かないフレームとタスクごとのアリーナ。協調的な取消し。タスク開始時の移送（`sending`。第 3 段階では静的な Move で示す）。
- **Kotlin：** 構造化の木と、失敗したら兄弟を取り消す形（`tryJoin`）。型による中断の制限。
- **Go：** 未完了の計算を値にしないこと。`ctx` のように明示的に渡す文脈。所有権を受け渡すチャネル。実行時が一つであること。
- **C#：** 取消しを明示的に扱う規律。ただし、例外ではなく値で表す。

採らなかったもの：

- **`Pin` と Future 値：** 二つ目の移動可能性の概念になる（Principle 1）。
- **Future の破棄による取消し：** 途中での完了が要る（SPEC §16.2.3）。
- **非同期の `drop`。**
- **actor：** 再入で局所的な推論が崩れる。
- **暗黙の現在タスク：** Swift の `Task.isCancelled`、Kotlin の `coroutineContext`。暗黙の文脈は Principle 2 に反する。
- **呼出し側に印のない中断：** Go、Kotlin。
- **例外。**
- **スコープを出るときの暗黙の待機。**
- **代数的効果のハンドラー：** 本書 4.4。

## 15. 段階計画

1. **第 0 段階（仕様）。**
   - 規則 1〜6 を書き、規則 2 と規則 3 の検査を実装する。
   - 実行は `Unsupported` と報告する。
2. **第 1 段階（健全な最小の部分集合）。**
   - コルーチンへの下げ方（O0 を含む）を実装する。
   - `Task`・`run`・`join`・`tryJoin`・`each`・`race`・`sleep`・`checkCancelled` と単一スレッドの実行器を用意する。
   - 診断と CSP の一覧を出す。
   - **前提（`docs/STATUS.md` で未完了の項目）：**
     - Callable 制約（owner 取得の witness、任意の Callable のパラメーターと結果）
     - 集合値を捕捉する Closure
     - 借用の入口と lending loop のディスパッチ
     - 可変静的 Field（規則 3 を試すため）
   - 前提がそろうまでは、能力を順に渡す呼出しと、スカラーだけを捕捉する Closure の `join` に絞る。それ以外の形は `Unsupported` とする。
3. **第 2 段階。**
   - チャネル（`uniq` の端点）。
   - IOCP によるファイル・パイプ・ソケット。
   - タイムアウト。
   - 切り離したタスク `task.detach(body@move)`。
     - 条件は `F is Callable<owner, (uniq/Async.Task) -> ()>` と `F is Owned`。
     - 活性のハンドルが型を消去するので、消去した Closure は要らない。
     - `run` の根が戻ると、残りを取り消してから合流する。
4. **第 3 段階（SPEC §D.2）。**
   - 規則 7、`Transferable`、スレッドごとの実行器。
   - ブロックする呼出しの退避、スレッド間チャネル。
5. **別の提案とするもの。**
   - 生成器（下の注記を参照）。
   - 非同期の反復（能力を渡す `for` の入口）。
   - 能力について総称的な高階関数。
   - Origin で上限を付けた消去。
   - 利用者定義の能力。
   - 非同期の `main`（SPEC §13.8）。

生成器も「中断する能力」（`Iter.Emitter<T>`）として同じ仕組みで書けそうに見える。しかし検証で次の問題が見つかったので、本書から外した。

- **`Iterator` になれない。** `preserves results` を満たすことを示せない。
- **リークの保証を崩す。** 中断中の活性を所有する値が利用者の手に渡り、本書 6.3 の保証の前提が成り立たなくなる。
- **停止の手順が重い。** 破棄したときの停止の手順に、二つ目の取消しの値が要り、停止しない本体も扱わなければならない。

能力の一覧は規則 1 で閉じているので、生成器を加えるときも規則 2〜4 はそのまま使える。

## 16. 設計判断

### 16.1. 採用しなかった案

| 案 | 理由 |
| --- | --- |
| `async`/`await` の区分（Function Type の区分、前置 `await`、`await` は async の本体の中だけ） | 次点。慣れた形で、中断点を字句で示せる。ただし、規則の数は本書とほぼ同じで、キーワードが二つ要る。また、取消しや子の開始に暗黙の「現在のタスク」が要るので、Principle 2 の「明示的な文脈」に反する。本書の印は能力の引数で、権限そのものを型で運ぶ。最終的な判断は本書 16.4 の 1 に委ねる |
| Future 値と `Pin`（Rust） | 二つ目の移動可能性の概念で、impl §21.4.5 と衝突する。環境を借用する Future は、保留中の受け手依存の結果になる |
| スタックフルなタスク（Go） | 中断が見えない（Principle 2）。生ポインターがスタックを指すので、スタックを移せない |
| `await` を能力の引数と並べて書く | 一つの事実に二つの綴りができる（Principle 1、SETTLED の項目 3 と同じ理由） |
| join ハンドル、`async let` | 健全性が破棄の実行に依存する。子を開始する方法が二つになる |
| `Async.Blocking`、`Async.Wait`、`Async.block` | 効果は能力によらず同じなので、多相は飾りでしかない。入れ子の `run`（本書 5.5）で足りる |
| 入れ子の `run` で Abort する | Abort するかどうかが動的な文脈で決まる（Principle 2） |
| 規則 3 を効果要約の行にする（SPEC §8.4.10.2） | 権限は入力から来るので、環境効果の定義に合わない。中断しない呼出し元にまで広がる |
| チャネルを `ref/Self` で操作する | 共有経路から変更できるようになる（新しい可変性の概念）。`rc` を通って循環も作れる |

### 16.2. Kimigayo Principles との対応

| Principle | 対応 |
| --- | --- |
| 1. One Concept, One Canonical Form | 中断の印は能力の引数だけ。子の開始は Kimi の操作だけ。取消しは値だけ。実行器は一つ。同期版と非同期版の対を作らない |
| 2. Local Reasoning | 中断点は、その本体のパラメーターを見れば分かる。推論も暗黙の現在タスクもない。子の寿命は呼出しの期間で決まる |
| 3. Explicit Semantics | 中断の権限・取消し・移送はシグネチャーと値に現れる。隠れた割当てはアリーナの積み増しだけで、その上限を回帰で固定する |
| 4. Compiler Server Protocol | 中断点とタスク境界の一覧、関連位置付きの診断、事実で条件を検証した修復候補 |

### 16.3. 検証で見つかった問題と対処

設計の段階では、五つの観点から独立に案を作った。Rust/C#、Swift、Go、Kotlin、エフェクトである。それらを採点して統合し、所有権の健全性、仕様と Principles の整合、規則の最小性の三つの観点から反証を試みた。見つかった主な問題と対処を次に挙げる。

| 問題 | 対処 |
| --- | --- |
| 関連型や推論された型引数を通すと規則 2 を回避でき、同期の呼出し元の下で中断して解放済みメモリーを使う（致命的） | 規則 2 に束縛の規則を含めた。再開可能かどうかはシグネチャーだけで決める（規則 4） |
| 規則 3 を効果要約の行にすると、中断しない呼出し元へ広がる | 中断点での Loan の比較に改めた。要約には加えない |
| 結果の既定に能力が入り、借用を返すたびにタスクが排他的に貸し出されたままになる | 規則 2 で、結果の既定の入力から除いた |
| 取消しの書込みが、生きている `uniq/Async.Task` の参照先を変更し、`noalias` を壊す | 表現の義務（本書 3）を加えた |
| チャネルの署名が取消しを報告できず、`race` によるタイムアウトが止まる | `Result` に `Cancelled` を含めた。観測の範囲を規則 6 で定めた |
| パラメーターの既定値は中断できない（「中断できる」とした誤り） | 本書 3.1 で、中断しない場所に含めた |
| 生成器は「追加の規則なし」では成り立たない | 本書から外し、別の提案とした（本書 15） |
| `Blocking`・`Wait` による多相は飾り | 削除し、入れ子の `run` にまとめた |
| `llc -O0` はコルーチンを下げられない | 下げパスを O0 のパイプラインに加えた（本書 10） |
