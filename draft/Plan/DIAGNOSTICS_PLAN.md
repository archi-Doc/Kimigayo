# 診断情報の再設計・実装計画

状態：計画段階（2026-09-29）。レビューの改善案を反映済み。実装は、別途の指示を受けて開始する。

本書で変更する事項は [SPEC.md](../../docs/SPEC.md) およびその参照先より優先し、変更しない事項には既存仕様を適用する。本書は実装済みの機能を示すものではなく、[PLAN.md](../../docs/dev/PLAN.md) の言語実装マイルストーンの順序も変更しない。既存のサービス契約は [SPEC 第23章](../../docs/spec/23-compiler-services.md)、検証済みの対応範囲は [STATUS.md](../../docs/STATUS.md) を参照する。

## 1. 目的と範囲

一つの独立した問題に、一つの主診断と必要な根拠を対応させる。既存の診断定義とソース表現を活かし、CLI・LSP・将来の CSP で共通に使える小さなモデルを整える。

対象は、診断情報の保持・表示、重複排除と連鎖抑制、代表的な診断の改善、品質と性能の評価手順である。独立した試作は作らず、本体への小さな変更と回帰テストで検証する。CSP サーバー、永続的な入力記録、AST サービス、機械適用する修正は §8 の Deferred とする。

## 2. 共通診断モデル

### 2.1. 項目の役割

| 項目 | 役割 |
| --- | --- |
| コード | 診断の種類。既存の `TypeMismatch_Kd` などを継続して使う |
| 重大度 | Error・Warning など。問題の分類やチェック全体の結果とは別に扱う |
| Message | 問題そのものの説明。単独でも意味が通る文にする |
| 主位置・Label | 問題を直接説明するソース範囲と、そのコードへの短い説明 |
| 理由 | 具体的な失敗の種類と、期待型・実際の型など必要最小限の型付きの事実 |
| 関連位置 | 根拠となるソース範囲・役割・説明の一覧 |
| Note の一覧 | 背景や制約などの補足 |
| 修正助言の一覧 | 人間向けの変更案。機械適用する編集や、その検証結果とは別の情報 |

問題の分類は、言語上の指摘（規則違反や有効なコードへの注意）、必要な証明の不成立、実装未対応、入力・設定の失敗、資源制限、内部障害とする。具体的な理由がある場合は、その種類から分類を決める。理由がない場合は診断定義の分類を使う。この対応を一か所で管理し、呼び出し元に分類を自由指定させない。

確定した事実だけを理由にする。「この構文を意図したかもしれない」といった既存の hint は、条件付きの助言として扱う。証明不能を「条件が偽」と説明せず、実装未対応を言語規則違反として説明しない。表示名だけで型の同一性を判断しない。

### 2.2. 既定値と発生ごとの指定

Label・Note・修正助言には、共通の置換規則を使う。発生ごとの指定がなければ診断定義の既定値を使い、指定があれば項目全体を置き換える。空の指定は、その項目を表示しないことを表す。

定義の単一の Note・Fix は、それぞれ一覧の既定内容とする。最終結果には、解決済みの Label と、それぞれ一つの Note・修正助言の一覧だけを持たせる。表示側で既定値を再結合しない。共通説明を残して追加したい場合も、生成側で最終的な一覧を組み立てる。

この置換は表示項目だけに適用する。診断コード、理由、失敗の状態、重大度を隠したり変更したりする仕組みにはしない。定義の文字列と空の一覧は共有し、利用しない診断に補助領域を確保しない。

### 2.3. 位置の規則

主位置は、問題を直接説明できる最小の範囲とする。ユーザーが編集した場所や修正先とは限らない。

| 問題 | 主位置 | 関連位置 |
| --- | --- | --- |
| 型不一致 | 要求された型に合わない式 | 型注釈、仮引数、戻り値契約 |
| 不正な代入 | 原因となる代入操作または代入先 | 代入を制限する宣言 |
| Move 後の使用 | 不正な使用 | 先行する Move と、必要な分岐 |
| 借用の競合 | 競合を起こす操作 | 既存の借用と、その生存を必要とする使用 |
| 宣言の重複 | 仕様上のソース順で後の宣言名 | 先の宣言 |
| 構文要素の不足 | 挿入位置または不足が確定した境界 | 必要なら対応する開始記号 |

位置は元の不変ソースに結び付ける。標準の範囲は、0 始まりの UTF-16 オフセット `start` と長さ `length` とし、終端を含めない。長さ 0 は挿入位置、範囲なしは入力全体への指摘、ソースなしはソースに対応しない問題を表す。

行・列はこの範囲から導出し、出力用に保持してよい。独立した正規情報として更新しない。位置の計算や引用のために、編集中の文書やディスクを後から読み直さない。LSP の配置上必要な代替位置は表示用とし、本来の位置とは区別する。

## 3. 問題の識別と抑制

### 3.1. 三つの比較を分ける

| 比較 | 規則 |
| --- | --- |
| 問題の同一性 | 同じ解析結果内で、対象・満たすべき条件・具体化などの文脈が同じ失敗かを判断する |
| 公開内容の一致 | 位置、理由、文言、関連位置、Note、助言、省略情報など、公開する値をすべて比較する |
| 表示順 | ソース・範囲・コード・重大度・本文を基本に、同順位では理由や補足も比較して一定にする |

問題の識別には、結果内の小さな参照や識別値を使う。対象のソースと解析文脈を区別し、表示位置や文言をキーにしない。全 AST ノードへの ID 付与や永続的な診断 ID は不要である。同じ場所の独立した失敗は残し、同じ失敗の再報告だけを重複排除する。

代表診断の選択には、仕様上のソース順、元の構文対象の順序、検査条件、具体化文脈から決まる順序を使う。表示順とは分け、文言・下線の範囲・報告の到着順で代表を変えない。

補足一覧の順序は生成規則で固定し、配列の参照ではなく値で比較する。並べ替え後の隣接要素を重複排除するなら、等しい要素が必ず隣接する比較規則にする。Note だけが変わった場合も公開内容の変更として扱う。

チェック単位をまたぐ意味上の重複排除は行わない。値が等しい診断の表示集約は可能だが、報告元の結果・件数・文脈を保持し、同一問題と断定しない。文脈が異なることの表示が必要なら、補足に示す。LSP の再送抑制では、公開内容と文書バージョンを比較する。

### 3.2. 連鎖を抑えてよい条件

失敗は、検査した条件ごとに次のように扱う。

| 状態 | 扱い |
| --- | --- |
| 独立して説明できる失敗 | 主診断を残す。違反、証明不成立、未対応などを理由に応じて説明する |
| 既知の先行失敗による判定不能 | その説明を引き受ける主診断が同じ結果に残る場合だけ、派生診断を抑制する |
| 依存関係が不明 | 推測で抑制せず、分かっている範囲を説明する |

例えば、引数に未解決名があっても、引数個数の違反を独立して確定できるなら両方を残す。必要な証明が期限まで成立せず、既知の先行失敗にも依存しない場合は、証明不成立の主診断を出す。ここでの「判定不能」は内部の検査状態であり、チェック全体の `Blocked` とは異なる。

抑制は根拠のある依存関係だけに基づける。同じ行、同じ宣言、子孫ノードのどこかにある失敗、助言文の有無だけでは判断しない。構文回復の原因も必要な範囲で引き継ぎ、無関係な文は残す。

複数の独立した原因はそれぞれ残す。依存関係が循環する場合は、循環を説明できる代表診断を一つ残し、全員を相互に抑制しない。循環が言語違反かどうかは既存の解析規則で判定し、診断整理だけで新たな言語エラーを作らない。代表は §3.1 の代表選択の順序で決め、根拠や代表を確保できなければ抑制しない。

表示の抑制・集約・削除は、コンパイラのエラー状態や受理可否を変更しない。コレクションから個別の診断を削除する操作も、その診断の識別値を対象とし、開始位置だけで別の問題を消さない。

### 3.3. 処理量と情報量の上限

原因の探索結果は同じ解析結果内で再利用する。長い依存列の根本原因を診断ごとに探し直さず、確認済みの原因を共有する。各診断に全経路を複製しない。保持するのは必要な失敗の関係だけとし、循環の検出を含む探索量を制限する。上限で原因が確定できなければ、推測で抑制しない。

関連位置・Note・助言・候補や経路の詳細には、一診断と結果全体の上限を設ける。展開前の軽量な候補にも上限を適用し、全件を生成してから切り捨てない。採用は主診断・補足の種類・元ソース位置から決まる一定の優先順位で行い、収集の先着順にしない。文字列化や詳細展開は採用分だけに行う。省略の有無を記録し、件数が分かる場合だけ件数も示す。

補足情報の打ち切りは、意味解析の中止とは別である。この計画では主診断自体を件数上限で消さない。意味解析が資源制限に達した場合は、既存の規則に従ってその失敗を報告する。補足が減っても、主診断と受理可否を保つ。

## 4. 収集・確定・公開

### 4.1. 共通の流れ

`収集 → 整理・確定 → 公開` を共通の流れとする。

1. **収集：** 解析中に失敗と必要な根拠を記録する。再利用される作業領域の情報は、再利用前に取り出す。
2. **整理・確定：** チェック単位の結果を確定するときに、重複排除、連鎖抑制、既定値の解決、補足の上限処理を終え、不変の診断レコードを作る。
3. **公開：** CLI・LSP・将来の CSP は、その確定済みレコードを表示・変換する。意味を再判定せず、公開後のレコードも書き換えない。

入力・設定の失敗と内部例外でも、得られた診断と終了理由を確定する。`Completed`・`Blocked`・`Faulted`・`Cancelled` の意味と、キャンセル結果を公開しない規則は既存仕様を維持する。LSP は確定後も既存の鮮度・採用条件を満たす結果だけを公開する。

後続のコード生成などは別の結果単位として確定する。同じ診断を再出力するために、先の結果を再整理しない。通常の CLI 診断は追加時の即時表示から確定時の表示へ変更するが、入力の消費順、言語の判定規則、後続処理を開始する条件は変えない。

### 4.2. 内部データから切り離す境界

結果の確定時を、コンパイラ内部から切り離す境界とする。内部では既存のソースや型への軽量な参照を使い、境界を越える前に必要な値・表示文字列・導出した位置を固定する。失敗を説明するための再 Binding は行わない。

公開レコードは AST、変更可能な解析データ、遅延処理のクロージャーを保持せず、コンパイル全体の寿命を延ばさない。ソーステキストの複製も避ける。出力に必要な抜粋を保持する場合は不変ソースから必要な部分だけを取り出し、補足情報の上限に含める。文字列化を遅らせるのは、この境界までとする。

### 4.3. JSON・LSP と将来の CSP

- JSON の主位置は、ソースへの参照・任意の範囲・任意の Label を持つオブジェクトとする。必要になった公開 ID は不透明な文字列とし、表示名とは区別する。
- 現段階でも元の不変ソースを取り違えない。将来の内容 ID は入力の実バイト列に結び付け、BOM を除いた復号テキストの位置との関係を定義する。読み込み失敗に内容 ID や範囲を捏造しない。
- 永続的な入力・結果の識別は結果全体に持たせ、[既存の入力識別体系](../../docs/spec/18-modules-and-dependencies.md#1841-identities-and-graph) と接続する。ProjectSnapshotId だけでテスト用入力やコンパイラの解析結果まで識別したことにはしない。
- 共通レコードでは理由や補足を保持し、LSP には対応する標準フィールドと読みやすい補足文で反映する。クライアントの対応機能を考慮し、表示文から構造化情報を復元しない。
- 内部型のシリアライズを公開 CSP スキーマとして固定しない。「未計算」「未対応」などの状態は、それを必要とする機能を実装するときに追加する。

## 5. 実装順序

各段階は、再現例・実装・対象を絞った検証からなる小さな実装単位に分ける。最初に代表ケースと性能の比較基準を用意し、以後も各単位でテストする。

| 段階 | 内容 | 完了条件 |
| --- | --- | --- |
| 1. 情報を失わない基盤 | 既存の位置と抑制動作を保ちながら、最小限の補足モデル、Label 表示、チェック結果と LSP への引き継ぎ、既定値の解決を実装する。hint の表示と抑制判断を分離する | 単純な診断と代表的な補足が全経路で保たれる。助言の文言・有無の変更では抑制結果が変わらない。従来の必要な判定根拠は明示的に引き継ぐ |
| 2. 識別・抑制・確定 | 表示位置から独立した失敗の識別を導入し、重複排除・既知の連鎖抑制・循環処理・結果確定を実装する | 同じ位置の独立した失敗が残り、派生診断の説明を引き受ける主診断が必ず残る。受理可否と公開結果が正しく、順序と処理量が安定する |
| 3. 代表診断の改善 | 型不一致と不正な代入から、主位置・関連位置・理由を改善する。Move・借用・オーバーロードは、根拠とコストを確認して個別に広げる | 最小例と代表プログラムで位置・根拠が一致し、位置を変えても問題の同一性が変わらない |
| 4. 総合評価 | コード変異による評価をまとめ、CLI・LSP の結果と性能を変更前と比較する | §6・§7 を満たし、対応範囲と残る制限を記録する |

主位置の改善より先に、開始位置だけによる抑制を置き換える。第2段階の内部処理は生成経路ごとに移行してよいが、結果確定・公開の境界はチェック単位全体で統一し、即時表示と確定後表示を混在させない。移行済みと未移行の範囲を記録し、未移行経路から失われる情報も確認する。位置の変更は、識別と抑制を移行済みの経路に限定する。

第1段階では、現実装の `BorrowOriginHint` の有無に依存する抑制を、文言から独立した判定へ移す。失敗の根拠を表す判定を用意し、表示の変更だけで件数が変わらないことを確認する。最終的な抑制条件は第2段階で §3 に合わせる。

## 6. 品質の評価

### 6.1. 再現例とコード変異

正常に通る Milestone プログラムか、独立して検証済みの対応部分を使う。未完了プログラムの既存エラーを単一エラーの基準にしない。元ファイルは保持し、メモリ上または `temp/` のコピーへ、対象を一意に確認して変異を加える。

各ケースに、元ソース・変更箇所・変更内容・意図した失敗・期待する公開診断を記録する。最小例で原因を確認し、Milestone で他機能との組み合わせを確認する。

| 観点 | 確認事項 |
| --- | --- |
| 正確さ | コード・理由・分類・主位置・Label・関連位置・Note・助言 |
| 抑制 | 同じ位置の独立エラー、重複報告、複数原因、循環、構文回復、探索上限と補足省略 |
| 状態 | 診断の抑制・削除と受理可否の独立、入力失敗・内部例外・キャンセル、公開後の不変性 |
| 位置と寿命 | 複数ファイル、サロゲートペア、CRLF、長さ 0、範囲なし、関連ソースの編集、作業領域の再利用 |
| 公開 | 詳細だけの変更の配信、値による比較、同順位の順序、チェック単位の統合、報告元の保持、LSP の鮮度条件 |

英語全文の一致をすべてのテストに要求しない。意味情報の検査と少数の表示比較を分け、下線と説明の対応は人も確認する。診断件数を減らすこと自体を評価目標にしない。

### 6.2. 入力間の関係を確認するテスト

意味を変えない入力変換と、独立した問題の追加を使い、次の関係を確認する。

- 先頭に空行を追加しても、位置以外の意味情報は変わらない。
- 無関係なエラーを追加しても、既存の独立した主診断は消えない。
- 表示文だけを変更しても、重複排除・連鎖抑制は変わらず、公開内容の変更は検出される。
- 仕様上のソース順を保って内部の処理順を変えても、代表診断と公開順序は変わらない。
- 補足の上限を変えても、主診断と受理可否は変わらない。

編集前後の比較はコード・理由・対応する位置で行い、永続的な診断 ID は要求しない。

## 7. 性能と検証手順

### 7.1. 実装上の制約

診断が発生しない経路に、AST ノードごとの診断用割り当てや表示文字列生成を追加しない。警告は、プログラムが正常でも診断の発生として扱う。診断なし・警告あり・エラーありを分け、後二者でも必要最小限の処理にする。

定義の文字列や空表現を共有し、補助領域は診断が必要な場合だけ確保する。位置ごとの不要なヒープオブジェクト、汎用の属性辞書、説明のための再解析、診断ごとのハッシュ計算は避ける。既存の解析が持つ根拠を使い、得られない補足のために全正常処理の履歴を追加しない。型やメモリ配置は測定に基づいて決める。

### 7.2. 測定と採用条件

同じマシン・設定・入力で変更前後を比較し、初回の初期化と初期化済みの実行を分ける。対象は、診断なし、警告あり、単一エラー、多数の独立エラー、長い依存列とする。エディターでは、結果を再利用するチェックと実際に再解析するチェックを別々に測り、再解析回数も確認する。

時間・診断件数・保持量を確認し、割り当て量は影響する頻繁な処理と完了時に測る。入力・失敗数を増やしたときの伸びと測定のばらつきも記録する。共有原因の再探索、公開時の再生成、解析データの長期保持による退行を検出する。

基準測定でばらつきを把握した後、実装前に比較方法と許容範囲を記録する。診断なしの経路にノード単位の診断用割り当てを増やさず、再現する性能低下は原則解消する。原因の説明だけで合格にしない。低下を残す必要がある場合は、先に簡略化・延期を検討し、採用する利益とコストを明示して判断する。未測定の性能改善は主張しない。

### 7.3. 検証と文書更新

各実装単位は `scripts/verify.ps1 -Class ...` で検証し、該当するネイティブ実行用テストデータと Milestone ハーネスも確認する。実装セッション末尾に Session 検証を一度実行し、検証済み単位ごとにコミットする。ビルド中はソースを編集せず、NativeAOT テストは実行しない。拡張機能を変更した場合は、その検証手順にも従う。

失敗を含む証拠は `artifacts/verify/`、測定は `artifacts/benchmarks/`、使い捨て出力は `temp/` に置く。計画書だけの変更では、内容とリンクを確認し、コンパイラの検証は実行しない。

実装時は、既存仕様の即時表示・位置による抑制・LSP 公開に関係する §23.3.2・§23.3.3・§23.4.7 を更新する。STATUS は検証済みの対応範囲だけを記録し、PLAN_HISTORY に短い実施記録、PLAN に現在の作業への参照を追加する。Deferred は §23.5 と Appendix D に反映し、正式仕様を本書への参照に依存させない。実装に伴う `draft/` の自動更新は行わない。

## 8. Deferred

以下には実装時期を割り当てない。具体的な必要性が生じたときに、契約とコストを確認して実装する。

| 機能 | 再検討する条件・維持する方針 |
| --- | --- |
| 編集やセッションをまたぐ永続的な診断 ID | 編集前後の確実な追跡が必要になったとき。対応付けを意味上の妥当性の保証にしない |
| 全 AST・全解析処理の因果グラフ | 失敗に限定した依存関係では説明・デバッグの要求を満たせないとき |
| 診断への構文・意味ノード ID の付与 | CSP の調査・移動機能で必要になったとき。参照は特定のスナップショット・結果内で有効とする |
| CSP サーバー、公開スキーマ、永続的な入力・結果記録、検証証拠のサービス | 診断基盤が整い、サービス実装が計画されたとき。既存の CSP 要求と入力識別の契約を維持する |
| 構造化された修正候補の生成・プレビュー・適用・検証 | 前提条件と保証を示せる修正から導入する。助言・編集・検証結果を分け、文章から編集を推測しない。指定スナップショットへの適用と再検証を行い、古い入力や競合する編集は拒否する |

現在は文書の整理・再評価までとし、実装、仕様への取り込み、性能測定は行っていない。追加のユーザー判断が必要な設計上の未決事項はない。実装指示後、比較基準と第1段階の回帰テストから着手する。
