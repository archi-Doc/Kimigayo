# Documentation Comments

日付: 2026-09-17  
状態: 確定設計・実装計画。正式仕様への統合および実装は未実施。

**文書コメントは、宣言に関連付けたMarkdownである。** 宣言の目的・使い方・注意事項を説明し、言語独自の文書タグや文書専用Attributeは導入しない。

## 1. 役割

| 形式 | 役割 |
| --- | --- |
| `//`、`/* ... */` | 実装を読む開発者向けの通常コメント |
| `///` | 宣言を利用する人向けの説明 |
| `#Attribute` | コンパイラーやツールが解釈するメタデータ |

公開・非公開を問わず記述できる。記述できる対象と生成文書への掲載範囲は分ける。

言語は文書コメントに、名前解決・型検査・コード生成を変更する効果を与えない。ただし、Modなどがソースを読む場合は、他のソース文字列と同様に文書への依存が生じ、生成結果が変わり得る。

文書は宣言や言語規則を上書きしない。`#Description`や非推奨指定を代行する文書項目は標準化せず、新たなAttributeも導入しない。

## 2. 基本構文と本文

通常の字句解析で行コメントになる位置で、次の両方を満たす行を文書コメントとする。

- 行頭から`///`までがU+0020の空白だけである。
- `///`の直後が`/`ではない。

`////`、コード末尾の`///`、`/** ... */`は通常コメントである。文字列やブロックコメント内の`///`に文書としての意味を与えない。`///Text`と`/// Text`は両方使用できる。

同じインデント位置に連続する文書コメント行を、一つの**文書ブロック**とする。本文は次の手順で取り出す。

1. 各行の行頭空白と`///`を除去する。
2. その直後にU+0020があれば、一文字だけ除去する。
3. 残りの文字を変更せず、行の間をLFで結ぶ。末尾に改行は追加しない。

追加の字下げ・末尾空白・空行は保持する。`///`だけの行は本文の空行になる。LF・CRLF・CRは同じ本文に正規化する。通常の空行や通常コメントは本文に含めず、文書ブロックを区切る。

```kimi
/// Returns a shared reference to the first element.
///
/// - Abort: `values` is empty.
func first<T>(values: ref/Array<T>) -> ref/T from values
    return values[0]@ref
```

文書コメントは実行可能な構文要素を作らず、言語のブロック構造を変更しない。文字コード・トークン・インデントの検査は既存仕様に従う。

## 3. 宣言への関連付け

宣言ヘッダーに先行する、その宣言のAttributeと空行・コメントの連なりを**宣言前置部**と呼ぶ。Attributeは宣言と同じ行にも置ける。Attributeは構文全体を一単位とし、その引数内や宣言ヘッダー内のコメントは前置部の文書候補に含めない。

前置部は、他の構文要素、ディレクティブ、実際のスコープ境界、またはファイル境界で終わる。対象外の構文要素を飛ばして次の宣言へ付けない。

Attributeの配置と適用対象は[§6.5](../../spec/06-declarations-and-containers.md#65-attributes)に従う。空行・コメントのインデントだけでは前置部を切らない。この用語は既存のAttribute構文を変更しない。

**一つの構文上の宣言に付く文書ブロックは、高々一つとする。** 前置部で最も宣言に近い候補が、宣言ヘッダー開始行と同じインデントなら関連付ける。他の候補は未関連とし、インデント不一致や空の本文でも、前の候補へ戻らない。

```kimi
/// Checks that the sample code can be invoked.
#Test
func sample() => ()
```

文書はAttributeの前・間・後に置けるが、文書、Attribute、宣言の順を推奨する。

```kimi
/// Old behavior.
// func old() => ()
/// New behavior.
func current() => () // New behaviorだけが関連付く。
```

未関連の候補はlintで診断できる。構文エラーからの回復中は、関連付けが確定できない範囲を保留し、誤った対象への関連付けや派生する未関連診断を出さない。

## 4. 対象

文書は宣言一覧または実行ブロックに直接現れる**宣言単位**に付ける。ディレクティブ内の宣言も含むが、各宣言を記述できる場所は既存仕様に従う。

| 対象 | 含まれるもの |
| --- | --- |
| Container | group、rootgroup、struct、enum、contract |
| 関数・構築・破棄 | 名前付き関数とその要件、明示的特殊化、init、deinit |
| Property・束縛 | let・var・computed・Contractのproperty、ローカルlet・var |
| enumのCase | Case全体とそのペイロードの説明 |
| associate | Contractの関連型宣言、および実装側の関連型指定 |

`public main`も名前付き関数として対象に含む。`rootgroup A.B`の文書は末尾の`B`の宣言断片に属し、合成された中間groupには付かない。Fieldは格納スロットを指し、Propertyと別の文書対象にはしない。

パラメーター、型・Originパラメーター、Caseのペイロード、get・setは所属する宣言内で説明する。パターン内の束縛、式、alias、制約節、ディレクティブ、Attribute自体は対象にしない。

ファイル・プロジェクト全体には専用コメント構文を設けず、groupの説明または独立したMarkdown文書を用いる。

## 5. Markdown

本文は[CommonMark 0.31.2](https://spec.commonmark.org/0.31.2/)を基準とし、**生HTMLのブロック規則とインライン規則だけを無効にする。** HTML風の文字列は通常の本文として扱い、HTMLとして実行・描画しない。例えば`<T>`だけの行も、後続行のMarkdown解析を止めない。URLの自動リンクなど、他の規則は維持する。

表・脚注・独自タグなどの拡張らしい記述も上記の規則で解釈し、標準表示ではツール独自の解釈に置き換えない。

````kimi
/// Returns the sum of two integers.
///
/// # Example
///
/// ```kimi
/// let total = add(2, 3)
/// ```
public func add(left: i32, right: i32) -> i32 => left + right
````

見出しは宣言見出しの下に配置し、本文内の階層関係を保つ。コードフェンスの`kimi`は色分けのヒントであり、自動検査・実行を要求しない。

相対パスを持つリンクは[§20.7.4](../../spec/20-compilation-configuration.md#2074-generated-sources-and-declaration-order)の論理ソース名の親ディレクトリを基準に、所属プロジェクト内で解決する。生成ソースにはその基準名がないため、未解決とする。出力先への変換と文書内アンカーの識別規則は表示ツールが定め、同一入力では同一結果とする。

コード表記の名前は自動リンクにしない。宣言参照用の`kimi:`リンクは本案では導入しない。

## 6. 執筆規約と項目の抽出

先頭には目的や主要な動作を短い段落で書き、その後に必要な説明だけを追加する。先頭要素が段落なら、それを要約として使用できる。要約の推測は要求しない。

### 6.1. パラメーター

基本形は、コード表記の名前を先頭にしたリストとする。

```kimi
/// Scales a value by the given factor.
///
/// - `value`: The value to scale.
/// - `by`: The scale factor.
func scale(value: i32, by => factor: i32) -> i32 => value * factor
```

項目のキーには外部引数名を使い、本文は自然な表現で書く。外部名はContractの実装照合や特殊化でも保持され、内部名は異なり得るためである。型・Semantics・定数・Originパラメーターには宣言上の名前を使う。

レシーバー`self`は通常パラメーター項目に含めず、対象インスタンスへの操作や条件を本文・`Safety`で説明する。無名のCaseペイロードは位置と意味を文章で説明する。名前付きの情報構造が必要なら、既存のstructペイロードを使う。

全パラメーターの説明は必須ではない。同名パラメーターは説明や自由な見出しで区別でき、文書のための改名は要求しない。

### 6.2. 標準項目

| 項目名 | 内容 |
| --- | --- |
| `Returns` | 戻り値の意味、順序、丸め方など |
| `Abort` | 利用者が把握すべきAbort条件 |
| `Safety` | unsafe APIのメモリー安全性を守る条件と、その必要期間 |
| `Note` | 補足情報 |
| `Warning` | 誤用しやすい点や重要な制約 |
| `Example` | 使用例 |

短い説明は`- Returns: ...`、複数段落やコードを伴う説明は`# Returns`などの見出しを使う。どの項目にも同じ規則を適用する。

```kimi
/// Divides `left` by `right`.
///
/// - `left`: Dividend.
/// - `right`: Divisor.
/// - Returns: The quotient, truncated toward zero.
/// - Abort: `right` is zero, or `left` is -2147483648
///   and `right` is -1.
func divide(left: i32, right: i32) -> i32 => left / right
```

`Abort`にはAPI固有の条件を優先し、言語・実行環境に共通する失敗を毎回列挙する必要はない。未記載や列挙漏れを、他のAbortが起きない保証にはしない。

`Safety`は[§7.5](../../spec/07-functions-and-callable-values.md#75-unsafe-functions)の安全性契約を説明する場所である。項目の有無は`unsafe`指定や呼び出し側の義務を変えない。公開unsafe関数の説明不足はlintで診断できる。

### 6.3. 共通の認識規則

項目抽出に対応するツールは、Markdown構文木のルート直下にあるリストと見出しについて、次の要素を認識する。コードブロック・引用・入れ子リスト内からは抽出しない。

- 最上位リストの項目で、最初の段落が装飾のない標準項目名と`:`で始まるもの。
- 最上位リストの項目で、最初の段落が名前一つのコード表記と`:`で始まるもの。これはパラメーター説明の候補とする。
- 最上位の見出しで、装飾のない本文が標準項目名と完全一致するもの。

項目名は大文字・小文字を区別し、`:`はASCIIとする。その直後はU+0020・タブ・改行・段落末尾のいずれかとする。説明は項目名と区切りの後から始まり、リストではその項目末尾、見出しでは次の同じ階層以上の見出しの直前または文書末尾までとする。

抽出結果は元の構文木への参照とし、順序・重複・包含関係を保持する。本文を再構成したり、後の項目で置き換えたりしない。パラメーターは§6.1の名前と完全一致する候補が一つの場合だけ対応付け、それ以外は本文を保持してlintで診断できる。自由な見出しから名前空間を推測しない。

これは表示用の規約であり、言語構文や意味検査ではない。未知の項目名、自由な見出し、日本語の本文も通常のMarkdownとして保持する。

## 7. 宣言と説明の分担

型、Semantics、Origin、Ownershipなど、宣言から自動表示できる情報の機械的な言い換えは省略する。例えば`-> ref/T from values`に`Origin: values`を重ねる必要はない。

目的、値の意味、境界条件、副作用、処理順序、計算量、安全に使う前提など、利用者の判断に必要なことを書く。理解を助けるために型や言語規則へ触れてもよい。

文書の条件をコンパイラーが自動検証することはない。型・制約で表現できる保証は宣言に書き、unsafeの安全性契約など、利用者が守る条件は文書で明示する。

## 8. 構成選択と関連宣言

### 8.1. 解析と構成選択

関連付けは[§19.5](../../spec/19-compile-time-directives.md#195-diagnostics-and-excluded-syntax)に従って通常の宣言構文を解析する範囲でのみ行い、元のソース位置と前置部を使う。選択後に隣接した別の宣言へ付け替えない。

Falseの`#if`対象内は関連付け・文書診断の対象外とする。到達した`#switch`の各分岐は通常構文を解析するが、その中のFalseの`#if`対象には同じ除外規則を適用する。文書処理のために解析義務を追加しない。

ディレクティブは前置部の境界なので、文書は`#if`の前ではなく、その制御対象内に置く。同じインデントの次の宣言を制御する形式でも同じである。

```kimi
#if windows
/// Returns the platform name.
func platformName() -> string => "windows"
```

生成文書には選択された宣言だけを載せる。複数構成を扱うツールは構成ごとに解析・選択し、表示を区別する。非選択の分岐には意味解析やリンク解決を追加要求しない。

### 8.2. 宣言断片と参照

文書はその構文上の宣言だけに属する。group・structの断片を統合表示する場合は、既存の論理宣言順に、出典付きで各断片の文書を並べる。本文を連結・上書きせず、Markdownの見出し・参照リンク定義の範囲も各文書内に保つ。生成ソースにも同じ規則を適用する。

それ以外の関連宣言は参照で示し、本文を暗黙にコピー・継承・統合しない。継承元のメンバー、実装したContract要件、特殊化元の関数にも同じ規則を適用する。参照先が掲載対象外なら、その本文を公開文書へ展開しない。オーバーロードは独立した宣言である。

呼び出しの説明は、呼び出し契約を定める宣言を基準にする。明示的特殊化の文書は実装注記とし、API文書では元の関数の文書を示し、必要なら注記を参照する。[§8.8](../../spec/08-generics-constraints-and-contracts.md#88-explicit-full-function-specialization)が許す結果・副作用の違いは説明できるが、継承する呼び出し契約やSafetyを上書きできない。

## 9. ツール・診断・整形

文書ツールが扱う基本情報は、**対象の宣言断片・本文・SourceDocumentと元の範囲**とする。文書なしと、空の文書が関連付いた状態は区別する。掲載範囲は設定可能とし、公開API文書は実効的な公開範囲に従う。

未関連の文書、欠落・曖昧な項目、未解決リンクは任意の文書診断とする。コード末尾などの認識されない`///`も、実際の行コメントだけを対象にlintで注意できる。§8.1の除外範囲には適用しない。

文書診断は通常の言語エラーにしない。CIで文書検査を必須にすることはできるが、言語としての妥当性とは区別する。既存の字句・インデント・構文診断を文書lintへ格下げしない。

整形では`/// `を推奨形とし、抽出後の本文を変えずに再出力する。空行は`///`でよい。文書をAttributeより前へ移す場合も、すべての文書の関連付けと本文が変わらない場合に限る。

Markdownは必要時に解析し、本文の不要なコピーや実行時メタデータを要求しない。Modがコメント・位置を観測する場合は、[§18.7.4](../../spec/18-modules-and-dependencies.md#1874-observable-source-information)と[§20.7.5](../../spec/20-compilation-configuration.md#2075-inputs-and-regeneration)の依存関係規則に従う。構造化した文書取得APIだけを理由に、元ソースへの依存を狭めてはならない。

## 10. 実装計画

### 10.1. 範囲と構成

初期実装の成果物は、文書の収集・関連付け、本文取得、標準Markdown表示、項目抽出、および任意の診断とする。新しいCLI、専用Modクエリー、`kimi:`リンク、コード例の実行は別途設計する。整形機能は既存の整形経路に適用する際に§9を満たすものとし、新しい整形ツールは要求しない。

現行の[Tokenizer](../../Kimi/Compiler/Lexing/Tokenizer.cs)は行コメントを読み飛ばす。[SourceDocument](../../Kimi/Compiler/Core/SourceDocument.cs)と[SourceSpan](../../Kimi/Diagnostics/SourceSpan.cs)を利用し、通常のトークン列とは別に文書情報を保持する。

| 段階 | 実装内容 | 完了条件 |
| --- | --- | --- |
| 1. 収集 | 既存の字句解析中に文書候補の範囲を収集する。文字列・補間・コメントの判定を別の正規表現で再実装しない。 | 収集の有無で通常トークン・言語診断が変わらない。 |
| 2. 関連付け | Parserの宣言境界、Attribute全体の範囲、元のディレクティブ境界、除外範囲を使用する。構成選択・宣言統合で位置関係を失う前に断片へ対応付ける。 | 全対象で§3・§8を満たし、除外範囲の通常解析を追加しない。 |
| 3. 本文と出典 | 元ソースの範囲から本文を必要時に生成し、本文内の位置を元ソースへ戻せる行別対応を保持する。 | 改行・空白・Unicodeが正しく復元され、診断が元の文字を指す。 |
| 4. 表示と抽出 | Markdownを必要時に解析し、同じ構文木から表示・要約・項目参照を作る。HTML表示では本文を適切にエスケープし、リンクには表示先のURL許可規則を適用する。 | 生HTMLを解析段階で無効化できることを確認し、自由な本文・重複項目を失わない。 |
| 5. 統合と診断 | 選択済み断片、実効アクセス、論理宣言順から掲載対象を作り、文書診断を別経路で返す。 | 構成・生成ソース・特殊化・複数断片でも出典と順序が安定する。 |

### 10.2. 保持・再利用

- 文書情報はSourceDocument単位の連続した範囲データと、宣言断片からの対応表を基本とする。行ごとのオブジェクトや通常トークンの追加は避ける。
- 収集を無効にした通常コンパイルでは、文書機能による追加の確保を行わない。候補ゼロの場合も専用バッファを確保しない。候補収集・関連付けはソース順の走査とし、宣言ごとのファイル全体の再走査を避ける。
- Tokenizerのプール済みバッファを破棄後に参照しない。範囲は不変のSourceDocumentに属し、異なるスナップショットのノード・範囲を混在させない。
- 本文は元ソース、解析結果は本文とMarkdown設定、関連付け・掲載結果は構成と宣言集合に依存する。変更された層から再計算し、対応を証明できないキャッシュは再利用しない。
- 生成ソースの更新・削除では旧文書と対応表も破棄する。並行要求は同じ不変スナップショットを読み、キャッシュはその寿命内に限定する。Modの再実行条件は§9に従う。

### 10.3. 受け入れ条件

次の境界を.NETの単体・統合テストで検証する。文書だけを変えた場合は、位置・文書を観測する処理を除いて意味が変わらないことを確認する。

| 観点 | 必須の検証 |
| --- | --- |
| 字句・本文 | `///`、`////`、末尾コメント、文字列・補間・ブロックコメント、LF/CRLF/CR、EOF、空本文、末尾空白、コードの字下げ、非BMP文字。 |
| 関連付け | 全対象、同一行・複数行Attributeとその引数内コメント、空行、異なるインデント、複数候補、空の直近候補、スコープ・ファイル境界、構文回復。 |
| 構成選択 | Falseの`#if`内の不完全な宣言を文書機能が拒否しない。到達した`#switch`の全分岐と入れ子の除外を区別し、削除された対象の文書を後続へ移さない。 |
| 表示・項目 | 採用するMarkdownパーサーを固定版の適合例とHTML無効化の追加例で検証する。`<T>`の次行、コード例・引用、名前衝突、区切り、重複、見出し階層、HTML出力のエスケープを確認する。 |
| 統合・出典 | 複数断片、合成group、関連型、特殊化、非公開の参照先、生成ソース、未解決リンク、正規化後の診断位置。 |
| 再利用・性能 | 文書編集・構成変更・生成削除後に古い表示を返さない。収集無効時の追加確保ゼロ、通常トークンと診断の一致、処理時間・確保量の基準値を測定する。 |

各段階では変更に関係する対象テストと既存の字句・構文・SourceDocument・Attribute・ディレクティブの回帰テストを実施する。コンパイラー統合時は通常のビルドと.NETテスト全体を確認する。NativeAOTテストは明示的な依頼がある場合だけ行う。

実装完了は上記成果物と受け入れ条件で判断し、設計の確定やParser対応だけでは完了としない。本更新では設計文書のみを変更する。
