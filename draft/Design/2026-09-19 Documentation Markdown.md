# 文書コメント用 Markdown

日付: 2026-09-19  
状態: 合意した限定仕様と境界ルールをまとめた仕様原案。正式仕様への統合・パーサーの実装・性能検証は未実施。

## 1. 目的と適用範囲

文書コメントには、API の目的、引数、戻り値、注意事項、使用例を簡潔に記述できる Markdown を用いる。本案では、その用途に必要な機能を選び、内部実装するパーサーの規則を定める。

基準は [CommonMark 0.31.2](https://spec.commonmark.org/0.31.2/) とする。ただし、本案で省略・変更する規則を優先する。採用した機能の細かな解釈は、明示的な変更がない限り CommonMark に従う。CommonMark 全体への互換性は要求しない。

本案は、[現行仕様 §2.3.4](../../spec/02-source-and-lexical-structure.md#234-markdown-and-links) の「生 HTML だけを除外した CommonMark」を、文書コメント用の限定仕様へ変更するための原案である。[既存の文書コメント設計](2026-09-17%20Documentation%20Comments.md) の Markdown に関する部分も、正式採用時にこの内容へ更新する。

変更する範囲は本文の Markdown 解釈と、その結果を扱う API である。`///` の認識、宣言への関連付け、構成による選択、掲載範囲、元ソースの保持は既存仕様に従う。文書が名前解決・型検査・実行の意味を変えることはない。

```text
文書コメントの処理
├─ 既存の規則
│  ├─ /// の認識と本文の取り出し
│  ├─ 宣言への関連付け・構成選択
│  └─ 掲載対象と出典の管理
└─ 本案の対象
   ├─ 限定した Markdown の解析
   ├─ 読み取り専用の構文木と元ソース位置
   └─ 同じ構文木を使う処理
      ├─ HTML 表示
      ├─ 概要・項目の抽出
      └─ 文書診断
```

本書のコード例は、`kimi` と示すものを除き、`///` を取り除いた後の Markdown 本文を示す。本書自身の表や説明用コードフェンスは、文書コメントで使用できる構文を追加するものではない。

## 2. 機能の全体像

### 2.1. 採用する機能

| 分類 | 機能 | 主な用途 |
| --- | --- | --- |
| 文章 | 段落、空行、通常の改行、強制改行 | 概要、説明、表示上の改行 |
| 見出し | `#` 形式の見出し | 説明の分類、Example、Safety |
| コード | インラインコード、フェンス付きコードブロック | 引数名、型名、式、使用例 |
| リスト | 箇条書き、番号付きリスト | 引数説明、条件、手順 |
| リストの構造 | 明示的に字下げした入れ子、複数段落、コードブロック | 詳しい説明 |
| 引用 | 各行に `>` を記述した引用と入れ子 | 外部仕様の引用、補足 |
| 装飾 | `*`・`_` による強調と太字 | 用語、重要な条件 |
| リンク | 通常リンクと任意のタイトル、自動リンク | 関連資料、外部サイト |
| 文字表現 | バックスラッシュエスケープ、数値文字参照 | 記号、Unicode 文字 |
| 名前付き文字参照 | `amp`、`lt`、`gt`、`quot`、`apos` | 基本的な記号 |

### 2.2. 採用しない機能

| 分類 | 採用しない機能 | 代わりに使う表現 |
| --- | --- | --- |
| 見出し | 下線形式の見出し（Setext） | `#` 形式 |
| コード | 字下げだけによるコードブロック | フェンス付きコードブロック |
| リスト・引用 | 必要な字下げ・`>` を省略した継続行（lazy continuation） | 明示的な継続 |
| リンク | 参照形式のリンクと参照定義 | `[説明](URL)` |
| 画像 | 画像構文 | 図を掲載した資料へのリンク |
| 区切り | 水平線 | 見出し、段落 |
| 文字参照 | §2.1 に挙げた 5 種以外の名前付き文字参照 | 文字を直接記述、または数値文字参照 |
| HTML | 生 HTML のブロック・インライン認識 | Markdown または通常の文字 |
| 拡張構文 | 表、脚注、取り消し線、タスクリスト、数式、Mermaid、独自タグなど | 通常の説明文、リスト、コード、リンク |

拡張構文は自動で有効にしない。例えば `mermaid` というコードフェンスの言語名があっても、図へ変換しない。

## 3. 共通の解析規則

### 3.1. 本文の取り出しと空白

同じ字下げ位置に連続する `///` 行が、一つの文書ブロックになる。各行から宣言側の字下げ、`///`、その直後の空白一つを除き、行間を LF で結ぶ。残りの字下げ・末尾空白は保持する。末尾に改行を追加しない。

```kimi
/// 最初の段落です。
/// 次の行も同じ段落です。
///
/// 二つ目の段落です。
func sample() => ()
```

`///` だけの行は本文の空行になる。`///` を書かない通常の空行は、文書ブロックを終了する。

本文中の空白・タブの解析は、採用する CommonMark の規則に従う。字下げ計算でのタブは 4 桁のタブ位置を使う。これは Kimigayo の宣言・実行コードにタブの字下げを許す変更ではない。文書の字下げには空白を推奨する。

### 3.2. ブロックとインライン

最初に段落、見出し、リスト、引用、コードブロックの構造を決める。その後、段落と見出しの内部にあるコード、強調、リンクなどを解釈する。

採用しないブロック規則は、段落を終了させたり、他の構文を抑制したりしない。採用する規則同士の優先順位、段落への割り込み条件、マーカーの細則は CommonMark に従う。

例えば水平線を認識しなくなった結果、CommonMark では水平線だった文字列が、本案ではリストなどの採用構文として解釈されることがある。省略した規則の優先順位だけを残すことはしない。

### 3.3. 未対応構文と不完全な入力

未対応構文には専用の意味を与えない。残った文字列を、採用した規則で通常どおり解釈する。未対応構文らしい範囲を見つけて、その全体を文字表示に固定する処理は設けない。

```markdown
![構造図](https://example.com/diagram)
```

この例は画像にはならない。`!` は通常の文字、`[構造図](...)` は通常のリンクになる。画像構文全体を表示したい場合はコード表記を使う。

閉じていない記号やリンクなどを、文書の構文エラーにしない。採用した構文の CommonMark 規則で処理する。例えば対応する終端のないインラインコードや強調の記号は、通常の文字として残る。一方、閉じていないコードフェンスは、§4.3 の規則でコードとして続く。

Markdown の不完全さは通常のコンパイルを失敗させない。ただし、元ソースの文字コード・字句・言語構文に対する既存の検査は維持する。

## 4. ブロック構文

### 4.1. 段落と改行

空行で段落を分ける。同じ段落内の通常の改行は soft break とし、HTML では改行文字として出力する。`<br />` にはしない。ブラウザー上の折り返しは表示幅などに従う。

行末に空白を 2 個以上置くか、バックスラッシュを置くと hard break になる。HTML では `<br />` を出力する。段落末尾など、強制改行が成立しない位置は CommonMark に従う。

```markdown
この行の後は通常の改行です。
この行の後は強制改行です。\
ここから表示上の次の行になります。

ここから別の段落です。
```

例では、末尾空白を目視しにくいためバックスラッシュを使用している。

### 4.2. 見出し

`#` から `######` までの見出しを認識する。見出し記号の後の空白、任意の末尾 `#`、見出し内のインライン構文は CommonMark に従う。

```markdown
# Example

基本的な使い方です。

## 境界値

境界付近での動作を説明します。
```

表示では宣言の見出しの下へ配置し、本文内の階層を保つ。宣言がレベル 2 なら、本文の `#` はレベル 3、`##` はレベル 4 とする。HTML の見出しレベルが 6 を超える場合は、`div` に `role="heading"` と対応する `aria-level` を付ける。

下線形式の見出しと水平線は認識しない。次の例は一つの段落であり、見出しや水平線にはならない。

```markdown
Example
---
```

### 4.3. フェンス付きコードブロック

バッククォートまたはチルダを 3 個以上並べたフェンスを使う。開始・終了フェンスの条件、字下げ、情報文字列の制約は CommonMark に従う。終了フェンスは開始と同じ文字を使い、開始以上の個数とする。

````markdown
```kimi
let total = add(2, 3)
```
````

コード内部では Markdown の見出し、項目、強調、リンク、文字参照を解釈しない。HTML 表示ではコード本文をエスケープする。

情報文字列の先頭の語は言語名として表示ツールへ渡せる。`kimi` は色分けのヒントであり、コードのコンパイル・実行を要求しない。特定の言語名で図や別の構文へ変換しない。

終了フェンスがない場合は、所属するリスト項目・引用などのブロックの末尾までコードとする。最上位なら文書末尾まで続く。

````markdown
```kimi
let total = add(2, 3)
# この行もコードの一部
````

この例の最後までがコードであり、`#` は見出しにならない。

字下げだけでコードブロックは作らない。4 個以上の空白で始まっても、他の採用ブロック構文に該当しなければ段落として扱う。段落の表示用字下げは段落の規則で処理し、字下げされた原文自体はソース情報として保持する。

### 4.4. リスト

#### 4.4.1. マーカーと継続行

箇条書きには `-`、`+`、`*`、番号付きリストには数字と `.` または `)` を使う。番号の桁数、開始番号、段落への割り込み、マーカー変更によるリストの区切り、空の項目などは CommonMark に従う。

各項目の本文開始位置を、継続に必要な字下げの基準とする。必要量の算出は CommonMark のリスト規則に従い、すべてを固定の 2 個または 4 個の空白に統一する規則は設けない。空の項目やマーカー後の空白が多い場合も、CommonMark の基準を使う。

次は、マーカー後に空白を一つ置く一般的な例である。

```markdown
- 短い項目です。
  同じ項目の継続行です。

10. 番号付きの項目です。
    同じ項目の継続行です。
```

`- ` の後の本文位置は 2 桁先、`10. ` の後は 4 桁先になる。いずれも継続行をその位置まで字下げする。

字下げが不足した非空行を、直前の段落の継続としてリスト内へ取り込まない。継続条件を満たさない項目を閉じ、残る外側の構造でその行を解釈する。

```markdown
- 項目の説明です。
この行はリスト外の段落です。
```

この例では、空行がなくても 2 行目はリストの外になる。入れ子では、内側の項目を閉じた後に外側の項目へ属する場合もある。

#### 4.4.2. 入れ子と複数ブロック

リスト項目には、段落、子リスト、見出し、引用、フェンス付きコードブロックを含められる。非空の継続行は、その項目に必要な字下げを満たす。項目内の空行に字下げを要求しない。

````markdown
- `value`: 処理する値です。

  ここは同じ項目の二つ目の段落です。

  - 正の値を受け付けます。
  - 上限は呼び出し側で確認します。

  ```kimi
  let result = add(2, 3)
  ```

- Returns: 処理結果です。
````

```text
リスト
├─ 項目: value
│  ├─ 最初の段落
│  ├─ 二つ目の段落
│  ├─ 子リスト
│  │  ├─ 項目: 正の値
│  │  └─ 項目: 上限
│  └─ コードブロック
└─ 項目: Returns
   └─ 最初の段落
```

#### 4.4.3. 空行と HTML 表示

CommonMark の tight／loose の区別を維持する。tight は項目の段落を HTML の `<p>` で囲まず、loose は囲む形式である。判定は空行や子ブロックの配置に従い、リスト単位で行う。子リストは独立に判定する。

```markdown
- 一つ目
- 二つ目
```

上は tight の例である。次は項目間に空行があるため loose になる。

```markdown
- 一つ目

- 二つ目
```

### 4.5. 引用

引用に含める各行に `>` を書く。引用内部の空行にも `>` が必要である。引用内では採用するブロック構文を使用できる。

```markdown
> 引用の最初の段落です。
> 続きの行です。
>
> 二つ目の段落です。
>
> > 入れ子の引用です。
```

入れ子の引用を継続するには、各階層の `>` が必要になる。`>>` と `> >` はどちらも使える。

```markdown
> 引用です。
この行は引用外の段落です。
```

`>` のない行を引用の継続として取り込まない。リストと引用を組み合わせた場合も、外側から順に必要な字下げと `>` を満たす。

```markdown
- Note: 補足です。

  > 項目内の引用です。
  > 続きです。
```

## 5. インライン構文

### 5.1. コード、強調、エスケープ

| 記述例 | 意味 |
| --- | --- |
| `` `value` `` | インラインコード |
| ``` ``a ` b`` ``` | バッククォートを含むインラインコード |
| `*重要*`、`_重要_` | 強調 |
| `**注意**`、`__注意__` | 太字 |
| `***特に重要***` | 強調と太字の組み合わせ |
| `\*記号\*` | アスタリスクを文字として表示 |

コードの区切りの長さ、コード内の改行・端の空白の扱い、強調の前後の文字や入れ子の判定は CommonMark に従う。コード内ではエスケープや文字参照を解釈しない。

バックスラッシュでエスケープできる文字は CommonMark の ASCII 記号とする。すべての文字に対してバックスラッシュを取り除く処理にはしない。

### 5.2. 通常リンクと自動リンク

```markdown
[利用ガイド](guide.md)
[外部資料](https://example.com/api "API の説明")
<https://example.com/api>
<name@example.com>
```

通常リンクの表示文にはコードや強調などを含められる。URL 内の括弧、エスケープ、任意のタイトル、リンクの入れ子の禁止などは CommonMark に従う。タイトルの区切りとして使用できる引用符・括弧も同じとする。

自動リンクは CommonMark の山括弧付き形式を認識する。山括弧のない URL を自動リンクにする拡張は採用しない。構文として認識することと、HTML に有効なリンクを出すことは区別し、後者には §7.2 の URL 制限を適用する。

参照形式のリンクと参照定義は認識せず、参照定義の辞書も作らない。

```markdown
[利用ガイド][guide]

[guide]: guide.md
```

この例はリンクにならず、参照定義も本文から取り除かれない。通常の段落として表示される。

### 5.3. 文字参照

数値文字参照は、十進の `&#...;` と十六進の `&#x...;`・`&#X...;` を採用する。桁数、Unicode 値の扱い、不正な値の置換は CommonMark に従う。

名前付き文字参照は次の 5 種だけを認識する。大文字・小文字を区別し、末尾の `;` を必須とする。

| 記述 | 変換先 |
| --- | --- |
| `&amp;` | `&` |
| `&lt;` | `<` |
| `&gt;` | `>` |
| `&quot;` | `"` |
| `&apos;` | `'` |

```markdown
&lt;T&gt; と &#169; を説明します。
&copy; と &AMP; は変換しません。
```

最初の行では `<T>` と `©` が表示される。次の行の `&copy;` と `&AMP;` は、その表記のまま表示される。HTML のエスケープは別途行うため、未対応の文字参照をブラウザーに再解釈させない。

文字参照を解釈できる位置は CommonMark に従う。コード内では変換せず、解釈した文字を Markdown の構造記号として再解析しない。例えば `&#42;` から得た `*` は強調の開始記号にはならない。

## 6. 概要と文書項目

### 6.1. 概要と標準項目

文書の最初のブロックが段落なら、それを概要として取得できる。見出しやリストから概要を推測しない。

標準項目名は、`Returns`、`Abort`、`Safety`、`Note`、`Warning`、`Example` とする。説明文には日本語を含む任意の自然言語を使用できる。標準項目名の大文字・小文字は区別する。

````kimi
/// 二つの整数の和を返します。
///
/// - `left`: 左側の値です。
/// - `right`: 右側の値です。
/// - Returns: 二つの値の和です。
///
/// # Example
///
/// ```kimi
/// let total = add(2, 3)
/// ```
public func add(left: i32, right: i32) -> i32 => left + right
````

### 6.2. 抽出対象と範囲

構文木のルート直下にあるリストと見出しだけを調べ、次を抽出する。

1. 最上位リスト項目の最初の段落が、装飾のない標準項目名と ASCII の `:` で始まるもの。
2. 同じ位置が、名前一つのインラインコードと `:` で始まるもの。これはパラメーター説明の候補とする。
3. 最上位の見出しの本文が、装飾のない標準項目名と完全一致するもの。

リストの `:` の直後は、空白 U+0020、タブ、改行、段落末尾のいずれかとする。見出しの末尾に `:` は付けない。エスケープと採用する文字参照を解釈した通常文字も、装飾のない文字として扱う。

| 記述例 | 抽出結果 |
| --- | --- |
| `- Returns: 説明` | Returns 項目 |
| `- Returns\: 説明` | Returns 項目。元ソース位置も保持 |
| `- Returns&#58; 説明` | Returns 項目。数値文字参照の後から説明が始まる |
| `- Returns:説明` | 抽出しない。区切り後の空白がない |
| `- **Returns**: 説明` | 抽出しない。項目名に装飾がある |
| `# Returns` | Returns 節 |
| `# returns` | 抽出しない。大文字・小文字が異なる |

引用、コード、入れ子リスト内から項目を抽出しない。

```text
文書の構文木
├─ 段落                         → 先頭なら概要
├─ 最上位リスト
│  └─ 項目
│     ├─ 最初の段落             → 項目名・引数名を判定
│     └─ 子リスト               → 新たな項目としては抽出しない
├─ 最上位見出し                 → 標準項目名との完全一致を判定
├─ 引用                         → 内部から抽出しない
└─ コードブロック               → 内部から抽出しない
```

リストの説明範囲は項目名と `:` の後からその項目末尾までとし、子ブロックも含める。見出しの説明範囲は見出しの後から、次の同じ階層以上の最上位見出しの直前、または文書末尾までとする。

抽出結果は元の構文木を参照し、順序、重複、包含関係を保持する。自由な見出しや未知の項目名は本文として残す。項目抽出のために本文を再構成したり、同名の後続項目で上書きしたりしない。

### 6.3. パラメーターと診断

通常の引数は外部引数名、型・Semantics・定数・Origin のパラメーターは宣言上の名前で照合する。名前は Kimigayo の識別子規則に従い、宣言側の一致候補が一つの場合だけ対応付ける。`self` は通常パラメーター項目に含めない。

不明・曖昧な名前でも説明文は保持する。文書診断は言語エラーと分け、既存の構成選択・宣言関連付けの制限を守る。標準項目の有無が、関数の動作、Abort 条件、unsafe の義務を変更することはない。

## 7. HTML 表示とリンク解決

### 7.1. 生 HTML と表示用エスケープ

生 HTML をブロックとしてもインラインとしても認識しない。HTML らしい記述を理由に、後続の Markdown 解析を停止しない。

```markdown
<T>
*型パラメーターの説明です。*

<script>alert(1)</script>
```

`<T>` と `<script>...</script>` は文字として表示し、説明の強調は有効とする。HTML 出力では本文・コード・属性値をそれぞれ適切にエスケープする。HTML の山括弧と、自動リンクを認識する山括弧は区別する。

見出しの変換、言語名の付与、リンクの変換を含め、同じ本文と同じ設定から同じ結果を生成する。表示のために構文木を書き換えない。

### 7.2. リンクの解決と許可

相対パスは、通常ソースの論理ソース名の親ディレクトリを基準に解決する。例えば `src/api.kimi` の文書からの `guide.md` は `src/guide.md` になる。プロジェクトの外へさかのぼるパスは解決しない。ファイルの実在確認を解析の条件にはしない。

生成ソースには相対パスの基準を設けず、相対パスは未解決とする。文書内の `#anchor` と許可された絶対 URL は、相対パスの基準がなくても扱える。

HTML 出力では、現在のリンク処理を維持する。

- 解決可能な相対参照と、`http`、`https`、`mailto` の URL を許可する。
- `/path` のような出力先ルートからの参照を扱い、`//host/path` は許可しない。
- 制御文字やバックスラッシュを含む宛先、許可されていないスキームの宛先は有効なリンクにしない。
- 出力用に URL を書き換える場合は、その結果にも同じ許可規則を適用する。
- 解決できない場合や許可されない場合も、リンクの表示文とその装飾は残す。

コード表記の名前を宣言へ自動リンクせず、`kimi:` のような専用のリンク方式を追加しない。アンカー識別子の生成と出力先の構成は表示ツールが定める。

## 8. 構文木、ソース位置、処理の寿命

### 8.1. 独自の構文木

製品側の Markdown API は Markdig の型に依存しない独自型とする。具体的なクラス名や格納形式は実装時に決めるが、次を満たす。

- 構文木は、解析完了後に読み取り専用として公開する。
- 概要と抽出項目は、その構文木のノードを参照する。
- ノードから、正規化した本文上の範囲と元ソース上の位置を取得できる。
- 表示文字とソース範囲を区別する。エスケープや文字参照を変換しても元の位置を失わない。
- 見出し階層、リストの種類と開始番号、tight／loose、リンク先・タイトル、コードの言語名など、表示と抽出に必要な情報を保持する。

位置は既存のソース API と同じ UTF-16 の単位で扱う。本文上の公開範囲は開始位置を含み、終了位置を含まない形式を基本とする。非 BMP 文字、改行正規化、`///` の除去後でも元ソースへ対応付ける。

リストや引用の字下げ・マーカーを除いて表示する場合も、元の範囲を保持する。ノードのソース範囲と、表示される文字列が同じ長さとは限らない。

### 8.2. 必要時の処理と再利用

通常コンパイルでは文書収集を無効にし、Markdown を解析しない。文書処理が有効な場合も、本文の生成と Markdown 解析は必要時に行う。

解析済みの構文木は、同じ不変のソースと同じ解析規則の範囲で再利用できる。元ソースや規則が異なる構文木を混在させない。HTML の再利用には、見出しレベルやリンク書き換えなど表示設定も考慮する。

宣言断片ごとの文書は独立に解析する。断片を統合表示するために本文を連結し、一つの Markdown 構造へ変えない。

不要な本文コピーと小さなオブジェクトの大量生成を避ける。配列によるノード管理や本文範囲の参照は実装上の選択肢とし、特定の内部構造を言語仕様として固定しない。

## 9. 検証の基準

### 9.1. 動作の検証

Markdig は比較対象として使用するが、限定仕様の正解を決める実装とはしない。根拠は本案と、採用する CommonMark 0.31.2 の規則である。

| 区分 | 検証する内容 |
| --- | --- |
| 共通機能 | 対象となる CommonMark の適合例を使い、期待結果および固定版の Markdig と比較する |
| 意図的な差分 | 未対応構文、限定した文字参照、リスト・引用の継続規則を、本案固有の期待結果で検証する |
| 文書固有の機能 | 概要、項目、重複、包含関係、パラメーター照合、元ソース位置、リンク、診断を検証する |
| 不完全な入力 | 未閉鎖の区切り、括弧の連続、深い入れ子、長い行などで停止性と処理量を確認する |
| 統合 | 既存の宣言関連付け、構成選択、生成ソース、掲載範囲を維持することを確認する |

比較では、生 HTML 無効化、見出し階層の変換、URL 制限などの表示条件を合わせる。HTML の改行形式など、意味と無関係な差は比較方法を明示して扱う。構文木、項目の範囲、元ソース位置は HTML 比較だけで済ませない。

### 9.2. 性能の検証

時間、割り当てバイト数、GC 回数を測定する。短い概要、引数リスト、長いコード例、入れ子の説明、不完全な入力を含め、次の処理を分ける。

```text
比較する処理
├─ 解析のみ
├─ 解析 + 項目抽出
└─ 解析済み構文木からの HTML 出力
```

主な速度比較には、両実装が同じ構造として解釈する本文を使う。位置情報の精度、キャッシュ条件、出力条件を合わせる。初回の初期化を含む測定と、初期化後の反復測定は分ける。

未対応機能を処理しないことによる差は別に報告する。速度や割り当て削減の数値は実測で示し、仕様段階では改善倍率を保証しない。通常コンパイルの高速化を、このパーサー置換の成果として扱わない。

## 10. 正式仕様へ統合する際の対応範囲

本案の正式採用時には、§2.3.4 の Markdown プロファイル、§2.3.5 の項目抽出に関係する例、Appendix A.21 の検証対象を整合させる。参照リンクと全名前付き文字参照への対応は、限定仕様では提供しないことを明記する。

Markdig の公開型を使う既存 API とテストは、独自の読み取り専用 API へ移行する。比較用の Markdig はテスト・ベンチマーク側に限定し、製品側のパーサーは内部実装とする。

本書は仕様原案であり、実装済み機能や性能改善を報告するものではない。具体的な実装状態と次の作業は、実装に着手する際に `PLAN.md` で管理する。
