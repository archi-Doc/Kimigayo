# 文書コメント用 Markdown — 最終仕様変更案

日付: 2026-09-19  
状態: 項目表記の統一とレビューを反映した最終案。正式仕様への統合・パーサーの実装・性能検証は未実施。

## 1. 目的と適用範囲

文書コメントには、API の目的、引数、戻り値、注意事項、使用例を簡潔に記述できる Markdown を用いる。本案では、その用途に必要な機能を選び、内部実装するパーサーの規則を定める。

基準は [CommonMark 0.31.2](https://spec.commonmark.org/0.31.2/) とする。ただし、本案で省略・変更する規則を優先する。採用した機能の細かな解釈は、明示的な変更がない限り CommonMark に従う。CommonMark 全体への互換性は要求しない。

本案は、[現行仕様 §2.3.4](../../spec/02-source-and-lexical-structure.md#234-markdown-and-links) の「生 HTML だけを除外した CommonMark」を、文書コメント用の限定仕様へ変更する原案である。変更案の解釈では、本書で明示的に変更する事項を `SPEC.md` とその参照先より優先し、未変更の事項には既存仕様を適用する。正式採用時には、[既存の文書コメント設計](2026-09-17%20Documentation%20Comments.md) も整合させる。

変更する範囲は本文の Markdown 解釈と、その結果を扱う API である。`///` の認識、宣言への関連付け、構成による選択、掲載範囲、元ソースの保持は既存仕様に従う。文書が名前解決・型検査・実行の意味を変えることはない。

本書のコード例は、`kimi` と示すものを除き、`///` を取り除いた後の Markdown 本文を示す。本書自身の表や説明用コードフェンスは、文書コメントで使用できる構文を追加するものではない。

§2–7 は構文・抽出・表示の規則、§8 は公開 API と処理の保証、§9 は受け入れ基準、§10 は統合対象を定める。§11 の実装候補は任意であり、すべての実装を要求しない。

## 2. 機能の全体像

### 2.1. 採用する機能

| 分類 | 機能 | 主な用途 |
| --- | --- | --- |
| 文章 | 段落、空行、通常の改行、強制改行 | 概要、説明、表示上の改行 |
| 見出し | `#` 形式の見出し | 説明の分類、example、safety |
| コード | インラインコード、フェンス付きコードブロック | 引数名、型名、式、使用例 |
| リスト | 箇条書き、番号付きリスト | 引数説明、条件、手順 |
| リストの構造 | 明示的に字下げした入れ子、複数段落、コードブロック | 詳しい説明 |
| 引用 | 各行に `>` を記述した引用と入れ子 | 外部仕様の引用、補足 |
| 装飾 | `*`・`_` による強調と太字 | 用語、重要な条件 |
| リンク | 通常リンクと任意のタイトル、自動リンク | 関連資料、外部サイト |
| 文字表現 | バックスラッシュエスケープ、数値文字参照 | 記号、Unicode 文字 |
| 名前付き文字参照 | `amp`、`lt`、`gt`、`quot`、`apos` | 基本的な記号 |

### 2.2. CommonMark との差分と未対応機能

次の例は独立した文書の本文とし、`⏎` は改行、`␠` は U+0020 を表す。各行を §9.1 の差分検証と §6.4 の任意診断の基準にする。未対応構文の文字列でも、採用した構文に該当する部分は解釈する。

| 対象・例 | CommonMark 0.31.2 | 本案 | 推奨表記 |
| --- | --- | --- | --- |
| `example⏎---` | Setext 見出し | 一つの段落 | `# example` |
| `␠␠␠␠# example`、`␠␠␠␠- a` | 字下げコード | 段落。見出し・リストにはしない | コードにはフェンスを使う |
| `- a⏎b`、`> a⏎b` | 段落の省略継続 | `b` はリスト・引用の外 | 必要な字下げ・`>` を記述 |
| `10. a⏎␠␠␠b` | 項目内の段落継続 | `b` はリストの外 | この例では 4 桁字下げ |
| `[x][r]⏎⏎[r]: guide.md` | 参照リンクと非表示の定義 | 二つの通常の段落 | `[x](guide.md)` |
| `![図](guide.md)` | 画像 | `!` と「図」を表示文に持つリンク | 図を掲載した資料へのリンク |
| `---`／`- - -` | 水平線 | 段落／空の項目まで 3 段に入れ子になったリスト | 見出し、段落 |
| `&copy;`、`&AMP;` | 名前付き文字参照 | 表記どおりの文字 | 直接記述、数値文字参照、採用する 5 種 |
| `<T>⏎*説明*` | 生 HTML ブロック | 段落内の `<T>` と強調 | Markdown または通常の文字 |
| `<Key:Value>`（既定の URL 設定） | 自動リンク | 自動リンクとして解析し、HTML では山括弧も残す | 文字表記を固定するならコード |

表、脚注、取り消し線、タスクリスト、数式、Mermaid、独自タグなども採用しない。これらは CommonMark 自体の機能ではなく、拡張との差分として扱う。通常の文章・リスト・コード・リンクで記述し、コードフェンスの言語名などから拡張を自動で有効にしない。

## 3. 共通の解析規則

### 3.1. 本文の取り出しと空白

本文の認識・取り出し・ブロックの終了条件は、[現行仕様 §2.3.1](../../spec/02-source-and-lexical-structure.md#231-documentation-text) に従う。

```kimi
/// 最初の段落です。
/// 次の行も同じ段落です。
///
/// 二つ目の段落です。
func sample() => ()
```

空白・タブは CommonMark に従い、字下げの桁は取り出した本文の各行頭を基準に数える。外側のリスト・引用を消費しても基準は変えない。文書の字下げには U+0020 を推奨する。宣言・実行コードのタブ禁止は変更しない。

### 3.2. ブロックとインライン

インライン構文は、それを含む段落・見出しの境界と内容が確定してから解釈する。文書全体の一括解析でも、確定したブロックからの逐次解析でもよい。未閉鎖フェンスやリストの tight／loose など、後続入力に依存する情報を未確定のまま公開しない。処理順や遅延の有無で結果を変えない。

本案で明示した変更以外は、採用する構文の定義を CommonMark のまま使う。外側のコンテナーを消費した位置からの開始字下げ上限（3 桁）、リスト本文位置の計算、段落への割り込み条件も維持する。字下げコードを廃止しても、これらの条件は撤廃しない。

未採用のブロック規則は開始を認識せず、段落の終了や他の構文の抑制にも使わない。残る規則同士の優先順位は維持する。例えば `- - -` は、水平線の優先規則を除くため入れ子のリストになる。

エスケープ・文字参照の変換結果を Markdown 構文として再解析しない。項目抽出は、解析済みの内容に対する別の規約である（§6.2）。

### 3.3. 未対応構文と不完全な入力

未対応構文は §3.2 に従って解釈する。その全体を文字表示に固定する専用処理は設けない。

未対応構文を含め、表記全体を文字として固定したい場合はコード表記を使う。

閉じていない記号やリンクなどを、文書の構文エラーにしない。採用した構文の CommonMark 規則で処理する。例えば対応する終端のないインラインコードや強調の記号は、通常の文字として残る。一方、閉じていないコードフェンスは、§4.3 の規則でコードとして続く。

Markdown の不完全さは通常のコンパイルを失敗させない。ただし、元ソースの文字コード・字句・言語構文に対する既存の検査は維持する。

### 3.4. Unicode の判定

Markdown の空白・句読点・記号の分類には Unicode 15.0.0 を使う。分類の用途と条件は CommonMark に従い、ホストのランタイム・OS・ロケールで結果を変えない。版を変更する場合は解析規則の改訂として扱う。

文書項目の名前は §6 の規則で取り出し、宣言上の名前と直接照合する。宣言側の識別子検査は [現行仕様 §2.5](../../spec/02-source-and-lexical-structure.md#25-names) に任せ、文書側で予約語・文字種・NFC の妥当性を再検査しない。

## 4. ブロック構文

### 4.1. 段落と改行

空行で段落を分ける。同じ段落内の通常の改行は soft break とし、HTML では改行文字として出力する。`<br />` にはしない。ブラウザー上の折り返しは表示幅などに従う。

行末に空白を 2 個以上置くか、バックスラッシュを置くと hard break になる。HTML では `<br />` を出力する。段落末尾など、強制改行が成立しない位置は CommonMark に従う。

```markdown
この行の後は通常の改行です。
この行の後は強制改行です。\
ここから表示上の次の行になります。

ここから別の段落です。
```

強制改行には、目視でき、末尾空白の削除設定にも影響されないバックスラッシュを推奨する。文書本文の末尾空白は §2.3.1 の保持対象であり、実行コードの末尾空白を無視する規則とは矛盾しない。

### 4.2. 見出し

CommonMark の ATX 見出し（`#`〜`######`）を使う。

表示では宣言の見出しの下へ配置し、本文内の階層を保つ。宣言がレベル 2 なら、本文の `#` はレベル 3、`##` はレベル 4 とする。HTML のレベル 6 を超える階層の表現は表示ツールが定める。現行表示の `div role="heading" aria-level="7"` などは、その実装例である。

### 4.3. フェンス付きコードブロック

CommonMark のフェンス付きコードブロックを使う。代表的な記述は次のとおり。

````markdown
```kimi
let total = add(2, 3)
```
````

コード内部では Markdown の見出し、項目、強調、リンク、文字参照を解釈しない。HTML 表示ではコード本文をエスケープする。

情報文字列の先頭の語は言語名として表示ツールへ渡せる。`kimi` は色分けのヒントであり、コードのコンパイル・実行を要求しない。特定の言語名で図や別の構文へ変換しない。

終了フェンスがない場合は、所属するリスト項目・引用などのブロックの末尾までコードとする。最上位なら文書末尾まで続く。

````markdown
```kimi
let total = add(2, 3)
# この行もコードの一部
````

この例の最後までがコードであり、`#` は見出しにならない。

字下げだけでコードブロックは作らない。ブロック開始を調べる位置で残りの字下げが 4 桁以上なら、新たな見出し・フェンス・リスト・引用は開始せず、段落として扱う。既存のコードフェンス内部や、外側のリストの継続判定にはそれぞれの規則を使う。表示用の字下げは段落の規則で処理し、原文の範囲は保持する。

### 4.4. リスト

#### 4.4.1. マーカーと継続行

マーカー、開始番号、段落への割り込みなどは CommonMark に従う。

各項目の本文開始位置を、継続に必要な字下げの基準とする。必要量は CommonMark のリスト規則で算出し、固定の 2 桁や 4 桁に統一しない。空の項目の規則も維持する。マーカー幅を W とすると、直後の空白が 5 桁以上の場合は W + 1 桁を項目の字下げとして消費し、残りは本文側で処理する。例えば `-     a` はコードではなく段落 `a` を持つ項目であり、継続に必要な字下げは 2 桁になる。

次は、マーカー後に空白を一つ置く一般的な例である。

```markdown
- 短い項目です。
  同じ項目の継続行です。

10. 番号付きの項目です。
    同じ項目の継続行です。
```

`- ` の後の本文位置は 2 桁先、`10. ` の後は 4 桁先になる。いずれも継続行をその位置まで字下げする。

字下げが不足した非空行を、直前の段落の継続としてリスト内へ取り込まない。継続条件を満たさない項目を閉じ、残る外側の構造でその行を解釈する。

```markdown
- 項目の説明です。
この行はリスト外の段落です。
```

この例では、空行がなくても 2 行目はリストの外になる。入れ子では、内側の項目を閉じた後に外側の項目へ属する場合もある。

#### 4.4.2. 入れ子と複数ブロック

リスト項目には、段落、子リスト、見出し、引用、フェンス付きコードブロックを含められる。非空の継続行は、その項目に必要な字下げを満たす。項目内の空行に字下げを要求しない。

````markdown
- value: 処理する値です。

  ここは同じ項目の二つ目の段落です。

  - 正の値を受け付けます。
  - 上限は呼び出し側で確認します。

  ```kimi
  let result = add(2, 3)
  ```

- return: 処理結果です。
````

#### 4.4.3. 空行と HTML 表示

CommonMark の tight／loose の区別を維持する。tight は項目の段落を HTML の `<p>` で囲まず、loose は囲む形式である。判定は空行や子ブロックの配置に従い、リスト単位で行う。子リストは独立に判定する。

単純な段落項目を空行なしで並べれば tight、項目間に空行を入れれば loose になる。

### 4.5. 引用

引用に含める各行に `>` を書く。引用内部の空行にも `>` が必要である。引用内では採用するブロック構文を使用できる。

```markdown
> 引用の最初の段落です。
> 続きの行です。
>
> 二つ目の段落です。
>
> > 入れ子の引用です。
```

入れ子の引用を継続するには、各階層の `>` が必要になる。`>>` と `> >` はどちらも使える。

`>` のない行を引用の継続として取り込まない。リストと引用を組み合わせた場合も、外側から順に必要な字下げと `>` を満たす。

```markdown
- note: 補足です。

  > 項目内の引用です。
  > 続きです。
```

## 5. インライン構文

### 5.1. コード、強調、エスケープ

| 記述例 | 意味 |
| --- | --- |
| `` `value` `` | インラインコード |
| ``` ``a ` b`` ``` | バッククォートを含むインラインコード |
| `*重要*`、`_重要_` | 強調 |
| `**注意**`、`__注意__` | 太字 |
| `***特に重要***` | 強調と太字の組み合わせ |
| `\*記号\*` | アスタリスクを文字として表示 |

コード、強調、バックスラッシュエスケープの成立条件と内容の処理は CommonMark に従う。コード内ではエスケープや文字参照を解釈しない。

### 5.2. 通常リンクと自動リンク

```markdown
[利用ガイド](guide.md)
[外部資料](https://example.com/api "API の説明")
<https://example.com/api>
<name@example.com>
```

通常リンクは CommonMark に従い、表示文にはコードや強調を含められる。

自動リンクは CommonMark の山括弧付き形式を認識する。山括弧のない URL を自動リンクにする拡張は採用しない。構文として認識することと、HTML に有効なリンクを出すことは区別し、後者には §7.2 の URL 制限を適用する。

参照形式のリンクと参照定義は認識せず、定義の辞書も作らない。§2.2 の例のように、参照定義らしい行も本文に残す。

### 5.3. 文字参照

数値文字参照は、十進の `&#...;` と十六進の `&#x...;`・`&#X...;` を採用する。桁数、Unicode 値の扱い、不正な値の置換は CommonMark に従う。

名前付き文字参照は次の 5 種だけを認識する。大文字・小文字を区別し、末尾の `;` を必須とする。

| 記述 | 変換先 |
| --- | --- |
| `&amp;` | `&` |
| `&lt;` | `<` |
| `&gt;` | `>` |
| `&quot;` | `"` |
| `&apos;` | `'` |

```markdown
&lt;T&gt; と &#169; を説明します。
&copy; と &AMP; は変換しません。
```

最初の行では `<T>` と `©` が表示される。次の行の `&copy;` と `&AMP;` は、その表記のまま表示される。HTML のエスケープは別途行うため、未対応の文字参照をブラウザーに再解釈させない。

文字参照を解釈できる位置は CommonMark に従い、コード内では変換しない。§3.2 により、`&#42;` から得た `*` は強調の開始記号にはならない。

## 6. 概要と文書項目

### 6.1. 概要と標準項目

文書の最初のブロックが段落なら、それを概要として取得できる。見出しやリストから概要を推測しない。

標準項目名は次の小文字表記に統一する。これらは文書の規約であり、言語キーワードの定義を変更しない。説明文には日本語を含む任意の自然言語を使用できる。

| 項目名 | 内容 |
| --- | --- |
| `return` | 戻り値の意味・条件 |
| `abort` | 関数固有の Abort 条件 |
| `safety` | unsafe の呼び出し側が守る義務 |
| `note` | 補足 |
| `warning` | 特に注意する制約 |
| `example` | 使用例 |

大文字・小文字は区別し、`Returns` などの旧表記を標準項目の別名として認識しない。

````kimi
/// 二つの整数の和を返します。
///
/// - left: 左側の値です。
/// - right: 右側の値です。
/// - return: 二つの値の和です。
///
/// # example
///
/// ```kimi
/// let total = add(2, 3)
/// ```
public func add(left: i32, right: i32) -> i32 => left + right
````

### 6.2. 項目名と説明範囲

#### 6.2.1. 共通の項目名

項目名は、装飾のない通常文字の列、または単一のインラインコードとする。バッククォートは任意で、通常文字とコードの混在や、強調・リンクで囲んだ名前は項目名にしない。

通常文字ではエスケープと採用する文字参照を解釈した値、インラインコードでは CommonMark のコードスパン規則で正規化した内容を使う。その後の空白除去、大小文字変換、Unicode 正規化は行わない。区切りとその直後の空白も、変換済みの通常文字で判定する。Markdown の構造や表示は変更しない。

#### 6.2.2. リストと見出し

構文木のルート直下だけを調べる。引用・コードブロック・入れ子リストの内部は対象外とする。

| 対象 | 認識する形 | 説明範囲 |
| --- | --- | --- |
| 最上位リスト項目 | 最初のブロックが段落で、先頭が空でない項目名と `:` | `:` の直後から項目末尾まで。子ブロックも含む |
| 最上位見出し | 本文全体を §6.2.1 の項目名として取り出すと標準項目名に完全一致 | 見出しの後から、次の同じ階層以上の最上位見出しの直前、または文書末尾まで |

通常文字の項目名は最初の ASCII `:` までとし、コード表記では閉じたコードの直後に通常文字の `:` を要求する。いずれも `:` の直後は U+0020、タブ、改行、段落末尾のいずれかとする。見出しには `:` を付けない。

リストはまず名前と範囲を持つ候補として取得し、§6.3 で分類する。見出しは標準項目だけを抽出し、パラメーターと照合しない。抽出結果は元のノードへの参照（§8.1）と説明範囲を持ち、順序・重複・包含関係を保持する。未知の名前や自由な見出しも本文に残し、本文の再構成や同名項目の上書きはしない。

次の例では、`left`・`value` がそれぞれ一つのパラメーターに一致するものとする。

| 記述例 | 結果 |
| --- | --- |
| `- left: 説明`、``- `left`: 説明`` | どちらもパラメーター `left` の説明 |
| `- return: 説明`、``- `return`: 説明`` | どちらも戻り値の説明 |
| `- return\: 説明`、`- return&#58; 説明` | 戻り値の説明。変換元の区切り表記の直後から説明が始まる |
| `- r&#101;turn: 説明` | `return` として照合 |
| `- return:説明` | 候補にしない。区切り後の空白がない |
| `- **return**: 説明` | 候補にしない。抽出を避ける場合に使える |
| `# return`、``# `return` `` | どちらも戻り値の節 |
| `# Return`、`# Returns` | 標準項目ではない通常の見出し |
| ``- ` value `: 説明`` | コードの空白処理により、パラメーター `value` の説明 |
| `- value : 説明`、``- `value name`: 説明`` | 一致先のない候補。本文はそのまま残す |

### 6.3. 分類・照合と診断

通常の引数は外部引数名、型・Semantics・定数・Origin のパラメーターは宣言上の名前を使う。宣言上の役割がレシーバーであるものだけを除き、リストの候補を次の順で分類する。

| 名前の完全一致 | 扱い |
| --- | --- |
| パラメーターが一つ | そのパラメーターの説明 |
| パラメーターが複数 | 曖昧な候補。標準項目へ読み替えない |
| パラメーターがなく、標準項目名に一致 | 標準項目の説明 |
| いずれにも一致しない | 不明な候補。通常の本文として表示 |

宣言の情報を取得するまではリストの分類を確定しない。バッククォートの有無で優先順位を変えず、標準項目と同名のパラメーターがある場合は見出しで書き分ける。

```kimi
/// 補足文字列を返します。
///
/// - note: 引数 note の説明です。
/// - return: 受け取った文字列です。
///
/// # note
///
/// この節は関数全体の補足です。
func echo(note: string) -> string => note
```

`self` という文字列だけでは除外しない。[現行仕様 §7.3](../../spec/07-functions-and-callable-values.md#73-explicit-receivers) に従い、group 内などの通常パラメーターであれば照合対象に残す。

```kimi
group Samples
    /// 値をそのまま返します。
    /// - self: 返す値です。
    func identity(self: i32) -> i32 => self
```

不明・曖昧な候補には任意の文書診断を出せる。文書診断は言語エラーと分け、既存の構成選択・宣言関連付けの制限を守る。標準項目の有無が、関数の動作、Abort 条件、unsafe の義務を変更することはない。

### 6.4. 任意の執筆診断

§2.2 の差分や未対応の拡張らしい表記は、任意の文書診断で知らせられる。字下げ不足や下線らしい行が意図的な本文である場合もあるため、確定した構文エラーとはせず、診断によって解析結果を変えない。差分の完全検出や別パーサーでの再解析は要求しない。

タブによる字下げと末尾空白による強制改行も、別の執筆上の注意として診断できる。後者は CommonMark との差分ではない。診断を無効にした場合は専用の情報を収集せず、有効時の追加処理量は §9.2 で測定する。

## 7. HTML 表示とリンク解決

### 7.1. 生 HTML と表示用エスケープ

生 HTML をブロックとしてもインラインとしても認識しない。HTML らしい記述を理由に、後続の Markdown 解析を停止しない。

```markdown
<T>
*型パラメーターの説明です。*

<script>alert(1)</script>
```

`<T>` と `<script>...</script>` は文字として表示し、説明の強調は有効とする。HTML 出力では本文・コード・属性値をそれぞれ適切にエスケープする。HTML の山括弧と、自動リンクを認識する山括弧は区別する。

表示のために構文木を書き換えない。出力の決定性と再利用に必要な入力は §8.2.3 にまとめる。

### 7.2. リンクの解決と許可

#### 7.2.1. 参照の分類

Markdown の規則で得た宛先を、次の順に分類する。通常ソースの基準には §20.7.4 の論理ソース名を使い、ファイルの実在確認は要求しない。前後の U+0020、制御文字、バックスラッシュを含む宛先は §7.2.3 に従って拒否する。

| 種類 | 例 | 基準と条件 | 生成ソース |
| --- | --- | --- | --- |
| 絶対 URL | `https://example.com` | スキームを大文字・小文字を区別せず、表示ツールの許可設定で判定 | 使用可 |
| ネットワーク相対 | `//host/path` | HTML 表示では不許可 | 不許可 |
| パスが空の相対参照 | 空の宛先、`?q`、`#anchor`、`?q#anchor` | 表示ページの URL が基準 | 使用可 |
| ルート相対 | `/guide.md` | 出力先 URL のルート。ソースプロジェクトのルートとは区別する | 使用可 |
| ソース相対 | `guide.md#sec`、`api.kimi?q` | 空でないパスを、所属プロジェクト内の論理的な参照先へ解決 | 未解決 |

パスが空の相対参照は、通常・生成ソースとも表示ページを基準とする。クエリーは指定があれば置換し、なければ基準のものを継承する。断片は指定されたものを使い、省略時には継承しない（[RFC 3986 §5.2.2](https://www.rfc-editor.org/rfc/rfc3986.html#section-5.2.2)）。`?q` はクエリーによって別の資源を指す場合があり、「常に同じ資源」という意味ではない。HTML の `base` が別の URL を指す場合は、表示ページの URL を明示してこの基準を保つ。

#### 7.2.2. ソース上の参照先と出力 URL

論理パスと URL は別の値として扱う。ソース相対の解決結果は、プロジェクトの識別情報、論理パス、クエリー、断片を分けて保持し、一つの URL 文字列に連結して再解釈しない。クエリー・断片の「なし」と「空」も区別する。

1. 宛先を URI 参照としてパス・クエリー・断片に分ける。エンコードされた `?`・`#` は区切りにしない。
2. パスを `/` で区切り、各区間のエンコードを UTF-8 として一度だけデコードして論理名へ変換する。不正なエンコードと、デコードによって生じる `/`・バックスラッシュ・制御文字は拒否する。既存の論理ソース名はデコードしない。
3. 論理ソース名の親を基準に `.`・`..` を処理する。プロジェクト外への遡行は拒否する。クエリー・断片はパス正規化に含めない。
4. 表示ツールが論理的な参照先を出力先へ対応付け、URL を組み立てる。パス中の `#`・`%` などはデータとしてエンコードし、クエリー・断片と混同しない。対応付けできなければ未解決とする。

これは区切りを確定してから値を変換する規則であり、URL 全体の一括デコードや二重デコードはしない（[RFC 3986 §2.4](https://www.rfc-editor.org/rfc/rfc3986.html#section-2.4)）。例えば `%252e%252e` は論理名 `%2e%2e` であり、`..` として再処理しない。

| 論理ソース名 | 宛先 | 解決結果 |
| --- | --- | --- |
| `src/api.kimi` | `guide.md#sec` | 論理パス `src/guide.md`、断片 `sec` |
| `src/api.kimi` | `api%23v2.kimi?q` | 論理パス `src/api#v2.kimi`、クエリー `q` |

後者を同じパス配置の URL に変換する場合は、`src/api%23v2.kimi?q` と表す。実際の `href` は出力ページの位置と基準 URL に合わせる。論理パスをそのまま出力ページからの相対 URL にしない。

#### 7.2.3. 共通の URL 検査と出力

許可スキームは表示ツールの設定とし、既定値を `http`、`https`、`mailto` とする。スキームの比較は ASCII の大文字・小文字を区別しない。入力時と、対応付け・書き換え後に、次の検査を行う。

1. 前後の U+0020、Unicode 15.0.0 の制御文字（`Cc`）、バックスラッシュ、不正な `%` エンコードを拒否する。空白を取り除いて受理し直さない。
2. 構成要素を分け、URL の構文と参照種別を検査する。ネットワーク相対参照と許可設定にないスキームを拒否する。相対パス内のエンコードされた `/`・バックスラッシュ・制御文字も拒否する。`http`・`https` の絶対 URL は `scheme://host` の形式と空でないホストを要求し、`https:example.com` などを補完して受理しない。

出力は、参照種別と構成要素を保持したまま次の形式で組み立てる。ブラウザーとの逐次比較や、製品内への WHATWG URL 解析器の組み込みは要求しない。

| 対象 | 出力規則 |
| --- | --- |
| 論理パスからの生成 | 各区間のデータを UTF-8 でエンコードし、区切りの `/` で結ぶ。データ中の `%`・`?`・`#` と、その区間で使用できない文字をパーセントエンコードする |
| パス相対参照 | 出力の先頭区間に `:` が残る場合は `./` を前置する。例: `a:b.html` → `./a:b.html`。ルート相対へも変更しない |
| ルート相対参照 | 先頭の `/` を一つ保つ。生成結果が `//` で始まる場合は拒否する |
| URL 形式で受け取った宛先 | 検査済みの区切りと有効な `%HH` を保持し、各構成要素のデータとして使用できない文字だけをエンコードする。既存のエンコードを二重化しない |
| クエリー・断片 | パスと別に組み立て、空と欠如を保持する。区切りをデータ文字から生成しない |

各構成要素の使用可能文字は [RFC 3986 §3](https://www.rfc-editor.org/rfc/rfc3986.html#section-3) に従う。国際化ホスト名などのスキーム固有の変換・妥当性検査は表示ツールが担当し、扱えない宛先は無効化する。ホストをパスと同じ方法で一括エンコードしない。

組み立て後は先頭のスキームと `/` を調べ、意図した参照種別と許可条件が保たれていることを確認する。HTML 属性値としてのエスケープは最後に行い、その後に宛先を書き換えない。書き換えが返した ` javascript:...` も手順 1 で拒否する。相対参照が表示先から継承するスキームと、宛先に明示されたスキームは区別する。

この規則が保証するのは参照種別・スキームの取り違え防止であり、全 URL 解析器での宛先の同一性ではない。文字検査と構成要素の組み立ては線形走査で実装できるが、ホスト名変換などを含む処理全体が一回の走査で済むとは要求しない。

#### 7.2.4. 未解決・不許可の表示

解決不能・不許可・書き換えによる無効化の場合、通常リンクは表示文とその装飾を残す。自動リンクは山括弧を含む元の表記をエスケープして出力する。例えば既定設定の `<Foo::bar>` はリンクにせず、そのまま表示する。自動リンクを認識する CommonMark の構文自体は変更しない。

コード表記の名前を宣言へ自動リンクせず、`kimi:` のような専用方式を追加しない。アンカー識別子と出力構成の安定性は表示ツールの公開規約によるものであり、`#anchor` の認識だけで参照先の存在は保証しない。

## 8. 構文木、ソース位置、処理の寿命

### 8.1. 独自の構文木

#### 8.1.1. 読み取り専用 API

製品側の Markdown API は Markdig の型に依存しない独自型とし、完成した結果を読み取り専用で公開する。見出し階層、リストの種類・開始番号・tight／loose、リンク先・タイトル、コードの言語名など、表示と項目抽出に必要な情報を保持する。

概要・項目が指すノードは、同じ解析済み文書の寿命内で安定して識別できなければならない。オブジェクト参照、または文書識別子とノード番号の組などで表せる。.NET の参照同一性や、ノードごとのオブジェクト確保は要求しない。別の解析済み文書へ識別子を流用しない。

#### 8.1.2. 必須の位置情報と任意の詳細対応

本文座標は §2.3.1 で取り出した正規化本文上の位置とする。本文・元ソースの公開位置は UTF-16 単位、範囲はすべて `[開始, 終了)` とし、表示桁数とは区別する。必須の情報は次の三つとする。

- 各ノードの構文範囲と、各項目の説明範囲（いずれも本文座標）。
- その範囲に対応する元ソースを覆う最小の単一区間。複数行では途中の `///` や字下げを含んでよい。
- 文書診断の対象となる文字・記号の正確な元ソース位置。複数行を覆う診断範囲は、上記の単一区間でよい。

本文上の LF は元の LF・CR・CRLF 全体に対応させる。空範囲は本文の挿入位置へ対応させ、行頭なら除去した接頭部の直後、本文末尾なら最終行の本文末尾とする。表示文字列の長さから元ソース位置を逆算しない。無効な自動リンクの原表記は、本文範囲から取得できればよい。

表示文字ごとの対応や、除去したマーカーを含まない区間列は任意 API とする。提供する場合、エスケープ・文字参照の変換文字は変換元の表記全体、タブの部分消費による仮想空白は元のタブへ対応させる。仮想空白のために本文座標を変更しない。詳細対応を全ノードに保持することは要求しない。

例えば `- return&#58; 説明` の説明範囲は `&#58;` の直後から始まる。診断がこの区切りを指す場合は `&#58;` 全体を対象にし、変換後の `:` 一文字の長さを使わない。

### 8.2. 必要時の処理と再利用

通常コンパイルでは文書収集を無効にし、Markdown を解析しない。文書処理が有効な場合も、本文の生成と Markdown 解析は必要時に行う。

#### 8.2.1. 解析と公開の単位

文書要求時の一括解析と、§3.2 に従う逐次・遅延解析のどちらも認める。概要の構造取得には先頭段落の確定だけで足り、その表示にはインライン解析も必要となる。リスト全体の性質や節の説明範囲などは、それらが確定してから公開する。

解析・公開の単位は実装が選ぶ。どの単位でも、公開済みの内容とノードの識別は変えず、最適化の有無で構文・表示・抽出・必須の位置情報を変えない。

#### 8.2.2. 並行要求と中断

同じ解析済み文書への並行要求では、同じ公開単位の完成結果とノード識別を共有する。同期・待機・重複計算の方式は実装に委ね、特定の状態機械や同期オブジェクトは要求しない。

中断した処理は未完成の結果や恒久的な解析失敗を公開せず、他の要求と後続の再試行を妨げない。既に公開した完成結果は維持する。重複計算を許す場合も、時間・一時メモリーを含めて §9 の基準を満たす。

#### 8.2.3. 決定性と再利用の条件

キャッシュは任意であり、文書全体の再計算も認める。次の表は依存関係を示すもので、行ごとのキャッシュを要求しない。同じ入力と規則からは同じ結果を生成し、再利用する場合は入力の一致を確認する。解析・URL 処理の規則や Unicode データの版も入力に含める。

| 結果 | 必要な入力 |
| --- | --- |
| 本文・元ソース位置 | 不変のソース、文書ブロックの範囲、取り出し規則 |
| Markdown 構文木・項目候補 | 上記の本文と位置情報、Markdown・抽出規則 |
| リスト項目の分類・パラメーターとの対応 | 項目候補、分類規則、宣言の識別情報・パラメーター・レシーバーの役割 |
| ソース上のリンク先（空でないソース相対パスのみ） | 解析済み宛先、プロジェクト、通常／生成ソースの区別、論理ソース名、解決規則 |
| HTML | 構文木、リンク先、出力先への対応表、表示ページと基準 URL、表示設定。項目を分類して表示する場合は、その分類結果も含む |
| 診断・掲載結果 | 対象となる上記の結果、構成・選択・掲載範囲、診断設定 |

表示設定には見出し・アンカー・言語表示・URL 許可・書き換えを含む。例えば同じ `[資料](guide.md)` でも、`a/api.kimi` と `b/api.kimi` ではソース上のリンク先が異なる。本文の一致だけで HTML を共有しない。外部コールバックも入力・設定に対して決定的であることを要求し、その依存を識別できない結果はキャッシュしない。

宣言断片ごとの文書は独立に解析する。断片を統合表示するために本文を連結し、一つの Markdown 構造へ変えない。

元ソースや規則が異なる構文木を混在させない。依存入力が変わった結果は再利用しないが、無効化の粒度は実装が選ぶ。任意診断の有効化だけで構文の解釈を変えない。

### 8.3. 処理量と資源の制御

本文長を UTF-16 単位で `n`、出力量を `o` とする。文書一つの構文木・必須の位置情報の保持量は `O(n + 1)`、一回の木の走査・HTML 生成は `O(n + o)` を基準とする。解析・抽出は入力に概ね比例する処理量を目標とし、同じ範囲の反復探索による二乗的増加を避ける。本文や重なる説明範囲をノードごとに複製しない。

位置問い合わせ、宣言との照合、リンク解決でも、文字・項目ごとの全体再走査を避ける。元ソースの読み取り、宣言・論理名など本文以外の入力、外部コールバック、出力保存、並行計算、任意の詳細対応は、それぞれの入出力量と処理回数を含めて評価する。

解析・抽出・出力・診断は、深い入れ子でもスタック枯渇を起こさない。ツールが時間・メモリー・深さの上限を設ける場合は条件を公開し、超過を文書処理の中断として報告する。キャンセルも扱い、上限超過を通常文字へ読み替えたり、言語エラーにしたりしない。具体的なアルゴリズムは固定しない。

## 9. 検証の基準

### 9.1. 動作の検証

検証の根拠は本案と、採用する CommonMark 0.31.2 の規則とする。Markdig との比較は調査・検証を補助する任意の手段であり、正解の基準や受け入れの必須条件にはしない。

| 区分 | 検証する内容 |
| --- | --- |
| 共通機能 | 対象となる CommonMark の適合例と期待結果で検証する。Unicode 15.0.0 の空白・記号・非 BMP・未割当文字の判定を環境差も含めて確認する |
| 意図的な差分 | §2.2 の全例を本案固有の期待結果で検証し、`-     a`、コンテナー内外の 3・4 桁境界も確認する |
| 文書固有の機能 | §6 の例、順序・重複・包含関係、レシーバーと通常引数の `self` を確認する。コード表記の有無、文字参照、大小文字・非 NFC 名の非同一視、標準項目と引数の衝突、複数パラメーターへの一致、宣言情報取得前の未確定状態を含む |
| ノードと位置 | §8.1 の安定したノード識別、本文範囲、元ソース範囲、診断位置を確認する。LF/CR/CRLF、空範囲、EOF、非 BMP、文字参照、複数行、タブの部分消費を含める。任意の詳細対応は提供する場合に検証する |
| リンクの解決 | §7.2.1 の各分類を通常・生成ソースで検証する。空宛先・`?q`・`#f` の表示ページ基準、クエリー・断片の空と欠如、HTML の別 `base`、`#`・`%` を含む論理名、異なる出力配置を含む |
| URL の出力 | `a:b.html` → `./a:b.html`、ルート相対の `//` 拒否、`https:example.com` の拒否、`%2e%2e`・`%2f`・`%5c`・二重エンコード、前後空白、書き換え後の拒否、HTML エスケープ、無効な自動リンクの原表記を確認する |
| 解析・再利用 | 提供する処理方式で期待結果が一致し、公開後の内容とノード識別が安定することを確認する。並行要求と中断でも未完成結果を公開せず、後続要求を妨げないことを検証する。最適化・キャッシュを採用する場合は、結果の同値性と依存入力の変更を確認する |
| 不完全・過大な入力 | 未閉鎖の区切り、強調・括弧・長さの異なるバッククォート列、深い入れ子、長い行で処理量とスタック安全性を確認し、上限超過と未完成状態の非公開も検証する |
| 統合 | 既存の宣言関連付け、構成選択、生成ソース、掲載範囲を維持することを確認する |

構文木・項目範囲・元ソース位置は、HTML 出力だけでなく直接検証する。他実装と比較する場合は版と条件を記録し、生 HTML・見出し階層・URL 制限・Unicode 分類などを合わせる。残る差は本案の期待結果で判定し、HTML の改行形式など意味と無関係な差の扱いも明示する。

### 9.2. 性能の検証

短い概要、引数リスト、長いコード例、入れ子、不完全な入力を使い、時間・割り当て量・最大保持メモリーを測定する。解析、概要・項目の取得、HTML 出力、位置問い合わせを対象とし、提供する遅延処理・キャッシュ・診断の条件を明示する。検証用に未採用の最適化方式を実装する必要はない。

入力長・入れ子深さ・同時要求数を段階的に増やし、§8.3 の処理量とスタック安全性を確認する。中断・再試行・重複計算の費用も含め、反復探索による二乗的増加を認めない。測定だけで計算量を証明したとはせず、実装レビューを併用する。探索回数などの内部カウンターは必要に応じて使い、常設や公開 API 化は要求しない。

Markdig などとの速度比較を行う場合は、共通機能・位置情報の精度・キャッシュ・出力の条件を合わせ、初回と反復を分ける。機能を省略したことによる差は別に報告し、通常コンパイルの高速化と混同しない。改善倍率は実測で示し、仕様段階では保証しない。

測定環境、データ、手順、具体的な合格値は、実装に着手する際に `PLAN.md` の受け入れ条件へ記載する。

## 10. 正式仕様へ統合する際の対応範囲

正式採用時には、§1 の優先関係に従って次を統合する。変更案の確定と、製品実装の完了は区別する。

| 統合先 | 対応 |
| --- | --- |
| §2.3.1 | 本文の認識・取り出しは維持し、再定義しない |
| §2.3.4 | 生 HTML だけを除外する規定と `Other CommonMark rules … remain` を限定プロファイルへ置換。`Reference-link definitions are block-local` は参照リンク非対応へ変更し、§2.2 の差分を反映 |
| §2.3.4 の表示規約 | `permitted URL schemes belong to the rendering tool` は維持。パスが空の参照は表示ページ基準へ統一。論理パスと出力 URL、検査・出力形式、原表記保持、見出し表示の責任を明確化。Markdown の Unicode データの版を固定 |
| §2.3.5 | 標準項目名と例を §6.1 に置換し、コード表記を任意化。§6.2–6.3 の直接照合、パラメーター優先、見出しでの書き分け、役割によるレシーバー除外を反映。範囲・順序・重複・包含関係は維持 |
| §2.3.6 | 必要時の解析、公開内容とノード識別の安定性、中断、依存入力を整合。位置情報の必須範囲を定め、詳細対応・キャッシュ・候補の事前除外は任意とする。解析・公開・同期の単位と方式は実装へ委ねる |
| Appendix A.21 | §9 の差分、項目の分類、位置対応、URL、Unicode、病的入力、遅延・並行処理、処理量の検証を追加。Markdig との比較は任意とする |
| 既存の文書コメント設計 §5・§6・§8.2・§9・§10 | Markdown プロファイル、抽出、参照定義への言及、API と受け入れ条件を更新 |

Markdig の公開型を使う既存 API とテストは、独自の読み取り専用 API へ移行する。製品側のパーサーは内部実装とし、Markdig を比較用に残す場合はテスト・ベンチマーク側に限定する。

具体的な実装状態と次の作業は、実装に着手する際に `PLAN.md` で管理する。

## 11. 任意の実装候補

まず単純な実装で §8・§9 を満たし、測定結果に応じて次を検討する。特定のライブラリー、データ構造、アルゴリズムは必須にしない。

| 対象 | 候補と注意点 |
| --- | --- |
| 解析の単位 | 小さな文書は要求時に一括解析する。必要性が確認できた場合にブロック単位の遅延解析を加える |
| 文字列とノード | 本文の範囲や区間列、配列上のノード番号で表し、文字列の複製や小さなオブジェクトの大量確保を避ける |
| 探索と入れ子 | `SearchValues` などの一括探索、区切りの索引、明示的なスタックを検討する。各方式の準備・保持費用も測る |
| 項目抽出 | §6.2 の候補にならないと確定できるものだけを、インライン解析前に除外する。標準項目以外の名前も候補に残し、文字参照・エスケープを含む表記を生文字列だけで判定しない |

| 再利用と位置対応 | 文書単位のキャッシュや行単位の位置索引から始め、細粒度のキャッシュ・詳細対応は利用頻度に応じて追加する |
