# 仕様変更案：整数の算術と変換（Wrapping整数・ラップ変換・ビット変換）

日付: 2026-10-01

改訂: 2026-10-01（再構成）

状態: 最終案。正式仕様への取り込み・実装・実行検証は未実施。

## 1. 概要

### 1.1. 目的と範囲

本書は次の三つを定める。

- **整数演算の共通規則**: 整数型と新しいWrapping整数型の算術を、「数学的な結果と、表せないときの型の方針」という一つの規則で定める。
- **Wrapping整数（`Wrapping<T>`）**: ハッシュ、PRNG、チェックサム、暗号、シーケンス番号のように2ᴺを法とする計算を、演算子を増やさず、値の型で書けるようにする。
- **変換とリテラル**: 既存の数値変換`@Type`に、ラップ変換`@wrap<U>`とビット変換`@bits<U>`を加える。直接リテラルの扱いは、すべての変換で一つの規則にする。

本書で変更する事項は、[SPEC.md](../../docs/SPEC.md)とその参照先より優先する。変更しない事項には既存仕様を適用する。節番号は本書を指し、「既存§」は正式仕様、「impl §」は実装仕様（`docs/impl`）を指す。本書は、同日の二つの提案「Wrapping Integers」と「Integer and Float Bit Conversions」を統合したものである。

### 1.2. 中心定義

> **整数演算**: 結果は数学的な結果である。値域で表せなければ型の方針に従い、整数型はAbortし、Wrapping整数型はラップする。演算が定義されない入力は、型によらずAbortする。
>
> **Wrapping整数**: `Wrapping<T>`は、`T`と同じ表現・符号・値の解釈・レイアウト・ABIを持つ別の整数型であり、表せない結果の方針だけが異なる。
>
> **変換**: 数値変換`@Type`は範囲検査と所定の丸めに従い、ラップしない。ラップ変換`@wrap<U>`は値を`U`へラップし、ビット変換`@bits<U>`は浮動小数点と同じ幅の整数の間でビット列を読み直す。この二つは失敗しない。

### 1.3. 例

```kimi
let a: Wrapping<u8> = 250
let b: Wrapping<u8> = a + 10      // 4: 2⁸を法としてラップする。
let c: u8 = 250
let d = c + 10                    // Abort: 260はu8で表せない。

let digest: u64 = 0x1234_5678_9abc_def0
let low = digest@wrap<u32>        // 0x9abc_def0: 下位32ビット。
let code = 0x8000_4005@wrap<i32>  // -2147467259: HRESULTのE_FAIL。
let raw = 1.5@bits<u32>           // 0x3FC0_0000: f32の1.5のビット列。
let back = raw@bits<f32>          // 1.5。

func fnv1a(bytes: Slice<u8>) -> u32
    var hash: Wrapping<u32> = 0x811c_9dc5
    for byte in bytes             // byte: ref/u8。
        let value: u8 = byte      // value readで値を読む。
        hash = (hash ^ value@wrap<Wrapping<u32>>) * 0x0100_0193
    return hash@u32
```

### 1.4. 設計原則

| 原則 | 内容 |
| --- | --- |
| 方針は型で決まる | 同じ`+`でも、`Wrapping<T>`ならラップし、`T`なら検査する。`f64`の`+`がIEEE 754に従うのと同じ仕組みで、式の外側の文脈やビルド設定には依存しない |
| 表せない結果と定義されない入力を分ける | 表せない結果は型の方針に従う。0除算や範囲外のシフト数のように演算が定義されない入力は、型によらずAbortする。`Wrapping`は「検査なしの整数」ではない |
| 値を変える変換は名前で明示する | `@Type`はラップしない。ラップは`@wrap`、ビットの読み直しは`@bits`と書く |
| 一つの概念に一つの形式 | 整数どうしでラップする変換は、同じ幅での符号の読み直しも含めて常に`@wrap`。`@bits`は浮動小数点が関わるときだけ。直接リテラルは、どの変換でも同じ規則に従う（§6.3） |
| 合法性は型だけで決まる | `@wrap`はすべての整数型の組で合法。`@bits`は型の幅で決まり、幅がプラットフォームで変わる`isize`／`usize`は対象外 |
| 値であって数量・位置ではない | Wrapping整数型は、位置や数量を表す文脈には使えない（§3.4） |

## 2. 用語と分類

### 2.1. ラップ

**ラップ**（wrap）は、整数xを型Uの値域へ2ᴺを法として還元した値である。すなわち、x ≡ r (mod 2ᴺ)を満たす、Uの値域内のただ一つのrを指す。Uは整数型またはWrapping整数型で、NはUのビット幅、`Wrapping<U>`の値域は`U`と同じとする。

この定義を、Wrapping整数型の算術（**ラップ演算**、§4.1）と、**ラップ変換**`@wrap<U>`（§5.4）が共有する。

### 2.2. 型の範囲を表す用語

| 用語 | 範囲 | 既存規則の適用 |
| --- | --- | --- |
| 整数型 | 12の組み込み整数型（従来どおり） | 整数型を名指しする既存規則は、本書が定める範囲でだけWrapping整数型に及ぶ |
| Wrapping整数型 | `T`が整数型である`Wrapping<T>` | — |
| 数値型 | 整数型、Wrapping整数型、浮動小数点型 | 「numeric」と書かれた既存規則（同じ数値型どうしの演算、単項`+`、比較のオペランドなど）はWrapping整数型にも及ぶ。ただし数値変換`@Type`は§5.3に従う |

### 2.3. Scalar

- Scalarを、名前ではなくCoreの同一性で定義し直す。Scalarは、primitive scalar Core（12の整数、2の浮動小数点、`bool`、`char`）と、`::Kimi.Wrapping<T>`が表す12のWrapping整数Coreからなる閉じた集合である。Scalarを「primitive scalarの略」とする既存の説明は削る。
- 型の分類図は「Scalar: Integer, Wrapping integer, Floating-point, Boolean, Character」にする。Wrapping整数型は、既存§3.1にprimitiveではないScalarの小節として置く。
- Scalarであることから、Copy、Owned、Sealed、ObjectPayload、read Type（既存§3.5.3）、コード生成上のScalarの扱いが既存規則のとおり従う。ジェネリックな`Wrapping<T>`は、`T is PrimitiveInteger`が証明されているときread Typeになる。

## 3. Wrapping整数型

`Wrapping<T>`は`T`と同じ規則に従い、本書が定める違いだけを持つ。

### 3.1. 宣言と形成

- `Wrapping<T>`は、`Option`や`FromEnd`と同じく、コンパイラが同一性を認識するKimiの宣言としてルートに置く（既存§22.1）。既定エイリアスで`Wrapping<u32>`と書ける。ユーザーが`Wrapping`という名前を隠しても、Scalarになるのは`::Kimi.Wrapping<T>`だけである。
- 型引数は`T is PrimitiveInteger`を満たさなければならない。`Wrapping<f32>`、`Wrapping<ref/u32>`、`Wrapping<Wrapping<u32>>`は不正。ジェネリック宣言で`Wrapping<T>`を形成するには、`T is PrimitiveInteger`の証明が要る。
- メンバ（Field・Property・関数）も公開コンストラクタも持たない。値は、リテラル（§6）、演算（§4）、変換（§5）で作る。

### 3.2. 型の同一性

`Wrapping<T>`と`T`は別の型で、部分型関係も暗黙変換もない。異なるWrapping型どうしも同じ。オーバーロードでも別の型として扱うため、リテラル引数が両方に適合すると既存§12.3.1どおり曖昧になる。

```kimi
func describe(value: u32) -> () => ()
func describe(value: Wrapping<u32>) -> () => ()
describe(5)                // Error: 両方の候補に適合する。
describe(5@Wrapping<u32>)  // OK。
```

### 3.3. 表現

ビット幅、サイズ、アラインメント、stride、ABIは`T`と同じで、foreign関数のシグネチャにもそのまま使える。`Option<Wrapping<T>>`は`Option<T>`と同じく明示タグを持つ。

### 3.4. Contractと言語構造

| 項目 | 扱い |
| --- | --- |
| Copy、Owned、Sealed、ObjectPayload、read Type | Scalarとして従う（§2.3） |
| Equatable、Comparable | `T`と同じ意味と順序 |
| Utf8Format | `T`と同じ表現（§8.1） |
| Dictionaryなど`Indexable<Key>`のキー | ほかのEquatableな型と同じく使える |
| `PrimitiveInteger` | 満たさない。`T is PrimitiveInteger`を前提にしたジェネリックコードに、ラップする値は入らない |
| 位置と数量の文脈 | 使えない（Positionでも整数型でもないため）。配列やSliceの位置（Position・PositionRange、既存§4.6.2）、Rangeの構築と反復（既存§4.6.3）、`^x`、長さ定数（既存§4.2）、ConstantIndexExpression、シフト数が該当する |

```kimi
let index: Wrapping<isize> = 3    // values: Array<i32>。
let first = values[index]         // Error: WrappingはPositionではない。
let second = values[index@isize]  // OK。
let shifted = index << index      // Error: シフト数にWrappingは使えない。
```

## 4. 整数演算

### 4.1. 共通規則

整数型とWrapping整数型に共通の規則である。

| 演算 | 規則 |
| --- | --- |
| 算術（`+ - * / %`、単項`-`、`++ --`、これらの複合代入） | 結果は数学的な結果（除算は0方向に切り捨て）。値域で表せないとき、整数型はAbortし、Wrapping整数型はラップする（§2.1） |
| ビット演算（`& \| ^ << >>`とその複合代入） | ビット列に対する演算で、表せない結果はない。`<<`は上位ビットを捨てる（既存） |
| 定義されない入力（0による除算・剰余、`0 <= count < N`を満たさないシフト数） | 型によらずAbortする（既存§17.3） |

- 表せない結果でAbortする増減と複合代入は、既存どおり書き込まない。Wrapping整数型では、ラップした値を書き込む。
- **既存からの変更**: 整数型の`MIN % -1`は、Abortをやめて0を返す。数学的な結果の0は表せるからである。これにより、Abortの原因は「表せない結果」と「定義されない入力」の二つに整理される。

| 式（`MIN`は`i32`の最小値、`MAX`は最大値） | `i32` | `Wrapping<i32>` |
| --- | --- | --- |
| `MAX + 1` | Abort | `MIN` |
| `MIN / -1` | Abort | `MIN` |
| `MIN % -1` | `0`（変更） | `0` |
| `x / 0`、`x % 0` | Abort | Abort |

### 4.2. Wrapping整数型の演算子

- `T`と同じ組み込み演算子を持つ。優先順位、評価順序、評価回数、書き込み回数、value readは既存規則のまま。
- 二項演算のオペランドは同じWrapping型で、結果も同じWrapping型になる（比較は`bool`）。シフト数は整数型に限る（§3.4）。
- 比較は`T`と同じ順序である。循環する順序（RFC 1982のシーケンス番号比較など）ではない。

### 4.3. 単項`-`

- 符号なし整数型の単項`-`は、0以外で必ず表せない結果になるので、既存どおり静的に拒否する。
- Wrapping整数型には表せない結果がないので、符号なしを含むすべてで使える。

```kimi
func lowestBit(value: u32) -> u32
    let w = value@Wrapping<u32>
    return (w & -w)@u32  // 最下位の1ビットだけを残す。
```

## 5. 変換

### 5.1. 三つの変換

変換は、「数値として変換するか、ラップするか、ビットを読むか」で選ぶ。

| 形式 | 結果 | 失敗 | 対象 |
| --- | --- | --- | --- |
| 数値変換`@Type`（既存） | 整数どうしは同じ値。浮動小数点を含むと所定の丸めを行う | 値域外ならAbort | 整数型・浮動小数点型どうし、`U` ↔ `Wrapping<U>`（§5.3） |
| ラップ変換`@wrap<U>` | `U`へラップした値 | なし | 整数型・Wrapping整数型どうし（§5.4） |
| ビット変換`@bits<U>` | 同じビット列 | なし | 浮動小数点型と、同じ幅の整数型・Wrapping整数型（§5.5） |

`@Type`は、Wrapping整数型（§5.3）と直接リテラル（§6.3）のほかは変えない。既存§13.5.4の「Integer -> integer: no truncation or wrapping」は`@Type`の規則として引き続き成り立ち、ポインタのキャスト（既存第5章）も変えない。

### 5.2. `@wrap`と`@bits`の構文

- `wrap`と`bits`は、`move`・`copy`・`follow`と同じく、`@`の直後でだけ認識する文脈キーワードとする（既存§2.5.1）。
- 変換先の型引数は、既存§13.1の「隣接する`<`」規則で直後に書く。型引数のない`E@wrap`や`E@bits`は不正。
- 優先順位と結合は、他の明示操作と同じレベル3、左結合。`-x@wrap<u8>`は`(-x)@wrap<u8>`になる。
- オペランドの評価、value read、結果の扱いは`@Type`と同じ。一つの式は一つの操作で、隠れた操作の連鎖は挿入しない（既存§13.5.3）。

### 5.3. Wrapping整数型への出入り

Wrapping整数型が関わる`@Type`の数値変換は、`U` ↔ `Wrapping<U>`だけである（直接リテラルは§6.3）。常に成功し、値もビットも変わらない。幅や符号が異なる整数型や浮動小数点型との`@Type`は不正である。名前から「ラップする」と誤読される変換を、実行時のAbortではなく静的なエラーにするためである。

それ以外の出入りは、意図に応じて書き分ける。

| 意図 | 入る（xから`Wrapping<U>`へ） | 出る（wから`V`へ） |
| --- | --- | --- |
| 数値変換（値域を検査する） | `x@U@Wrapping<U>` | `w@U@V` |
| ラップする | `x@wrap<Wrapping<U>>` | `w@wrap<V>` |
| 浮動小数点のビット | `f@bits<Wrapping<U>>` | `w@bits<F>` |

```kimi
func mix64(state: u64) -> u64
    var x = state@Wrapping<u64>        // 同じ基底型どうしは@。
    x = (x ^ (x >> 30)) * 0xbf58_476d_1ce4_e5b9
    x = (x ^ (x >> 27)) * 0x94d0_49bb_1331_11eb
    return (x ^ (x >> 31))@u64

let small: u8 = 200
let seed: u64 = 0x1_0000_0007
let w1 = small@wrap<Wrapping<u32>>    // 200: 符号なしの拡大なので値は変わらない。
let w2 = seed@wrap<Wrapping<u32>>     // 7: ラップする。
let w3 = seed@u32@Wrapping<u32>       // Abort: 数値変換は値域を検査する。
let bad = seed@Wrapping<u32>          // Error: 基底型が違う。上のどれかを選ぶ。
```

### 5.4. ラップ変換`@wrap<U>`

- **対象**: オペランドの型と`U`は、どちらも整数型またはWrapping整数型である。幅と符号の組み合わせに制限はなく、同じ型どうしも合法とする（ジェネリックで一様に使えるようにするため）。浮動小数点、`bool`、`char`、ポインタは対象外。
- **結果**: オペランドの値を`U`へラップした値（§2.1）である。ビットで見ると次のとおり。
  - 狭める変換では下位Nビットを残す。
  - 同じ幅ではビットを変えない。
  - 広げる変換ではオペランドの符号に従って拡張する（符号付きは符号拡張、符号なしはゼロ拡張）。
  - いずれも、得たビット列を`U`として読む。
- ゼロ拡張が欲しい場合は、同じ幅の符号なし型を経由する。

```kimi
let a = 300@i32@wrap<u8>          // 44。
let b = 200@u8@wrap<i8>           // -56。
let c = 0xFFFF_FFFF@u32@wrap<i32> // -1。
let d = -1@i32@wrap<u64>          // 0xFFFF_FFFF_FFFF_FFFF: 符号拡張。
let e = -1@i32@wrap<u32>@u64      // 0x0000_0000_FFFF_FFFF: ゼロ拡張。

func zigzagEncode(value: i64) -> u64
    return ((value << 1) ^ (value >> 63))@wrap<u64>
```

### 5.5. ビット変換`@bits<U>`

- **対象**: オペランドの型と`U`のうち、ちょうど一方が浮動小数点型で、他方が同じ幅の整数型またはWrapping整数型である。

  | 浮動小数点 | 相手の型 |
  | --- | --- |
  | `f32` | `i32`、`u32`、`Wrapping<i32>`、`Wrapping<u32>` |
  | `f64` | `i64`、`u64`、`Wrapping<i64>`、`Wrapping<u64>` |

  整数どうし（§5.4を使う）、浮動小数点どうし、幅の異なる組、`isize`／`usize`、128ビット整数、`bool`、`char`は対象外。型パラメータに依存する場合の制限は§7.1。
- **結果**: オペランドのビット列（IEEE 754のbinary32／binary64の符号化）そのものである。どちらの方向でも正規化せず、NaNのペイロード、quiet／signalingのビット、ゼロの符号を保つ。得た浮動小数点値に対するその後の演算は、既存の規則に従う。

## 6. リテラル

### 6.1. Wrapping整数型への適合

- `Wrapping<U>`への整数リテラルの適合は、`U`の値域で判定する。直接付いた符号は、既存§13.5.4どおりリテラルの一部として扱う。
- 型の決まらない整数リテラルの既定型は、従来どおり`i32`である。

```kimi
let allOnes: Wrapping<u32> = 0xFFFF_FFFF   // OK。
let minusOne: Wrapping<u32> = -(1)         // OK: 単項-のラップ演算で0xFFFF_FFFF。
let invalid: Wrapping<u32> = -1            // Error: 符号付きリテラル-1はu32の値域外。
let key = 0x9E37_79B9@wrap<Wrapping<i32>>  // OK: 値域外の定数はラップ変換で入れる。
```

### 6.2. リテラルだけの式

既存§12.3.1どおり、適合した型が各オペランドに伝わり、式はその型で評価される。単項`-`はWrapping整数型で定義されているので、`-(1)`は`Wrapping<u32>`に適合する。`let x: Wrapping<u8> = 200 + 100`は44。

定数畳み込みは、演算ごとの意味を保つ。正確な整数で計算して最後に一度だけラップする方法は、`/`、`%`、`>>`、比較を含むと結果が変わるので使えない。

### 6.3. 直接リテラルの変換（すべての変換に共通）

直接リテラル（括弧と、直接付いた一つの符号を含む。既存§13.5.4）のオペランドは、既定の型を経由せず、正確な値に変換を一度だけ適用する。失敗はコンパイル時のエラーになる。

| 変換 | 整数リテラル | 浮動小数点リテラル |
| --- | --- | --- |
| `@`整数型 | 値域を検査する（既存） | 0方向に切り捨ててから値域を検査する（f64を経由しない点と、失敗がコンパイル時になる点が**変更**） |
| `@Wrapping<U>` | `U`の値域を検査する（§6.1と同じ） | 不正（§5.3） |
| `@f32`・`@f64` | 一度だけ丸める（既存） | 一度だけ丸める（既存） |
| `@wrap<U>` | `U`へラップする | 不正 |
| `@bits<F>`（Fは浮動小数点型） | Fと同じ幅の符号なし整数型へラップし、そのビット列を読む | 不正 |
| `@bits<I>`（Iは整数型・Wrapping整数型） | 不正（整数どうしは`@wrap`） | Iと同じ幅の浮動小数点型へ一度だけ丸め、そのビット列を読む |

- **変更の例**: `9007199254740993.0@i64`は9007199254740993（従来は9007199254740992）、`1e10@i32`はコンパイル時のエラー（従来は実行時のAbort）。`3.9@i32`は従来どおり3。
- 直接リテラル以外のオペランドは、既存§13.5.2どおり独立に型が決まる。`(200 + 100)@wrap<u8>`は`i32`で300を計算してから44にし、`(200 + 100)@u8`は実行時にAbortする。

```kimi
let mask = -1@wrap<u64>                 // 0xFFFF_FFFF_FFFF_FFFF。
let wrapped = 0x1_0000_0005@wrap<u32>   // 5。
let negInf = 0xFF80_0000@bits<f32>      // −∞。
let exact = 9007199254740993.0@i64      // 9007199254740993。
```

### 6.4. パターンとキー

- リテラルパターン（既存§14.8.1）は`Wrapping<U>`の値にも使え、`U`の値域で適合を判定する。`Wrapping<u32>`に対する`-1`パターンは不正で、`0xFFFF_FFFF`と書く。
- Dictionaryのリテラルキー重複検査（既存§12.3.4）は、`Wrapping<U>`のキーにも適用する。

## 7. ジェネリック

### 7.1. 証明規則

`T is PrimitiveInteger`の証明（既存§8.4.7.3）は、次を与える。

- `Wrapping<T>`の形成と、Scalarかつread Typeであること、§3.4のContract
- `Wrapping<T>`の§4の演算子（単項`-`を含む）、複合代入、増減
- `T` ↔ `Wrapping<T>`の`@`変換
- `T`と、整数型または`PrimitiveInteger`が証明された型`U`（およびそれぞれのWrapping型）の間の`@wrap`。幅に関係なく合法なので、定義の検査は一度で済む
- `Wrapping<T>`に適合する0から127までのリテラル

`@bits`は、変換元または変換先の型が型パラメータに依存する場合は使えない。浮動小数点のContractがなく、型パラメータの幅も定義の時点では分からないためである。ジェネリック本体の中でも、型が確定していれば使える（`x: f32`の`x@bits<u32>`など）。

新しいContractは追加しない。数値Contractをユーザーが拡張できないという既存の方針も変えない。

```kimi
func scramble<T>(value: Wrapping<T>, key: Wrapping<T>) -> Wrapping<T>
    T is PrimitiveInteger
    return -(value ^ key) * 31  // Tには単項-がないが、Wrapping<T>にはある。

func foldToU64<T>(value: T) -> u64
    T is PrimitiveInteger
    return value@wrap<u64>      // 符号付きの値は符号拡張される。
```

### 7.2. 推論

既存§10.2.1の規則を、特例を足すのではなく「read Typeのパラメータ」として言い換える。

> パラメータの型が宣言の制約の下でread Typeなら、参照の層を持つ引数から参照先の型で推論し、値を読む。

既存の、制約付きの裸の`T`（`Position`、`PositionRange`、`PrimitiveInteger`）も、`T is PrimitiveInteger`の下の`Wrapping<T>`も、この一文に含まれる。`ref/Wrapping<u32>`の引数は`T = u32`を束縛する。

## 8. 出力とスタイル

### 8.1. 書式・テスト・実装プロファイル

- **書式**: Utf8Formatの既定表現と容量見積もりは`T`と同じ。`Wrapping<u8>`の255は`255`と書き、`Wrapping(255)`のような包んだ表示はしない。デバッガでの表示は本書の範囲外。
- **テスト**: テスト失敗時のScalarスナップショット（impl testing-profileのkind 7）は、`T`と同じkindとビット幅で記録する。
- **実装プロファイル**: `T`に対する制限（128ビット除算など）は`Wrapping<T>`にも同じく適用する。

### 8.2. スタイル（`docs/STYLE.md`）

- `[Kimi]` Wrapping整数型の束縛は、型が行内で見えるように書く（型注釈、`@Wrapping<…>`、`@wrap<Wrapping<…>>`）。推論だけでは、ラップするかどうかが行から読めないためである。
- `[Kimi]` ラップが意図の計算は`Wrapping<T>`と`@wrap`で書き、マスクや広い型を経由して検査を避けない。
- `[Kimi]` 同じ基底型どうしの出入りには`@`を使う（`@wrap`でも結果は同じ）。

既存のDiagnostic Workflowに従う。修正候補は既存§23どおり前提条件と保証を示し、適用後の式が合法になるものだけを示す。自動適用はしない。

| 状況 | 説明と修正候補 |
| --- | --- |

| Wrapping整数型と、基底型の異なる型（浮動小数点を含む）の間の`@Type` | `U`を経由する二段の数値変換、`@wrap`、`@bits`のうち合法なものを示す（§5.3） |

## 10. 範囲外と将来

### 10.1. 採用しないもの

| 案 | 理由 |
| --- | --- |
| `+%` `-%` `*%`、Swiftの`&+`など演算子ごとの指定 | 記号が増えて読みにくい。`&+`はKimigayoの`&`と単項`+` `-` `*`に字句上衝突する |
| `wrap(...)`やブロック単位の指定、ビルド設定による切り替え | 意味が外側の文脈で変わり、局所推論に反する。式の抽出や移動で意味が黙って変わる |
| `wrappingAdd`などのメソッド、Kimiの変換関数（`Bits.truncate(x)`など） | 同じ概念の二重形式になる。変換は`@`に集め、整数型はメンバを持たない（既存§4.6.2） |
| `@Type`（`@Wrapping<U>`を含む）でラップや切り捨てをする（Rustの`as`、Cのキャスト） | 範囲を検査する変換とラップする変換が同じ綴りになり、損失が見えない。`@Type`の意味が変換先の種類で変わる |
| `@Type`で幅や符号をまたいでWrappingに出入りする | 名前からラップすると誤読され、実行時Abortの罠になる |
| 負のリテラルをラップして適合させる（`Wrapping<u32>`に`-1`） | Kimigayoの`-1`は符号付きリテラルで、`-(1)`ではない。特例が必要になり、値域の一般則に反する |
| `PrimitiveInteger`への適合 | 位置、Range、Abortを前提にしたジェネリックコードに入り込む |
| 切り捨て・符号の読み直し・拡張を別々の操作にする（Zigの`@truncate`／`@bitCast`） | いずれも「ラップ」という一つの概念である。一つの規則なら、ジェネリックで幅が分からなくても合法性が決まる |
| 広げるときに常にゼロ拡張する | 値と合同にならず、符号付きの-1が別の値になる。ゼロ拡張は`x@wrap<u32>@u64`で明示できる |
| 整数どうしにも`@bits`を許す | `@wrap`との二重形式になる |
| `isize`／`usize`を`@bits`の対象にする | 合法性がプラットフォームで変わり、局所推論に反する |
| `$wrap(...)`などComposition Rootの操作 | 特別な評価規則を持たない普通の変換で、`$`を使う理由がない |

### 10.2. 別提案と将来の拡張（本書の提案項目ではない）

- **Dictionaryのハッシュ化（別提案、未作成）**: 現在の`DictionaryStorage.find`は線形探索である。`Wrapping`と`@wrap`を使えば、検査のないハッシュ計算をKimigayoで書ける。キーのハッシュ方法（既存仕様には公開のHash制約がない）を含めて、別提案で定める。
- **表せない結果の他の方針**: `Saturating<T>`などは、同じ「型で方針を選ぶ」枠組みで別提案とする。
- **値で失敗を返す演算と変換**: `tryAdd`などの演算や、`Option`を返す変換（Swiftの`exactly:`、Rustの`try_from`に相当）。
- **その他の変換と操作**: 飽和する変換（Swiftの`clamping:`に相当）、エンディアンを指定するバイト列との相互変換、ビット操作関数（回転、ポップカウント、先頭ゼロ数など）。

## 12. 検証と実装

### 12.1. 必須検証

- **整数演算**: 12種すべての整数型とWrapping整数型で、境界値（最大値、最小値、0）の`+ - * / %`、単項`-`、増減、複合代入を確かめる。`MIN / -1`と`MIN % -1`を含む。0除算と範囲外のシフト数は、どちらの型でもAbortすること。同じビット列でも、`/`、`%`、`>>`、比較の結果が`Wrapping<u32>`と`Wrapping<i32>`で異なること。
- **変換**:
  - `T`との往復が常に成功し、基底型の異なる`@Type`が静的エラーになること。
  - `@wrap`は、すべての整数型とWrapping整数型の組で境界値（最小値、最大値、-1、0）を確かめる。狭める変換、同じ幅、符号拡張とゼロ拡張、同じ型どうしを含む。
  - `@bits`は、許可された各組の往復で全ビット列が保たれること（NaNのペイロード、signaling NaN、±0、±∞、非正規化数を含む）。
- **リテラル**:
  - Wrapping整数型への適合の値域外エラー、`-(1)`、リテラルだけの式（`200 + 100`が44）、`/` `%` `>>`や比較を含む式の定数畳み込み。
  - §6.3の表の各欄。浮動小数点リテラルを整数へ変換するとき、f64を経由せず、値域外がコンパイル時のエラーになること。直接リテラル以外は独立に型付けされること。
- **型エラーと拒否**: 混在、§3.4の位置・数量の文脈での使用、形成の条件、`@bits`の対象外の組（幅の不一致、`isize`／`usize`、整数どうし、型パラメータに依存する場合）、`@wrap`への浮動小数点。対になる有効例として、Dictionaryのキーに使えること、ジェネリック本体の中で型が確定した`@bits`が受理されること。
- **ジェネリックと推論**: Wrapping整数型の単項`-`、0から127のリテラル、幅の異なる`@wrap`の各インスタンス化、`ref/Wrapping<T>`の引数からの推論。
- **その他**: リテラルパターン、書式、テストのスナップショット。
- **既存試験の更新**:
  - 整数型の`MIN % -1`のAbortを期待する試験は、0を期待するように直す（`DivisionEmissionTest`、`ElementUpdateEmissionTest`、`IntegerEmissionTest`、`SharedConcreteCallTest`、`ConstantLengthBindingTest`）。
  - `ConversionEmissionTest`の`3.9@i128`（未対応を期待）は、§6.3により定数として受理されるので直す。
- **コード生成（O0／O2）**:
  - §12.2のloweringになること。
  - Wrapping整数型の演算にオーバーフロー検査がなく、省略規則の対象にも検査が残らないこと（動的な除数・シフト数の検査は残る）。
  - `@wrap`と`@bits`が単一の命令（または命令なし）になり、NaNを正規化しないこと。
  - Wrapping整数型が`T`と同じABIであること。
- **診断**: §9の各経路と、誤検出しない有効な対応例。

### 12.2. 実装

- **検査の省略（impl §21.5.3に追加）**: 型とリテラルのオペランド（リテラルだけの式を含む）だけから成功を証明できる検査は、O0でも生成しない。
  - 変換元の値域が変換先の値域に含まれる数値変換。`T` ↔ `Wrapping<T>`、`u8@u32`、`i8@i64`が該当し、`i8@u32`は負数の検査が残る。
  - 除数が0以外のリテラルなら0除算の検査。整数型の除算で除数が-1以外のリテラルなら、最小値`/ -1`の検査。
  - 範囲内のリテラルのシフト数の検査。
- **整数演算のlowering**:
  - Wrapping整数型の`+ - *`と単項`-`は、`nsw`／`nuw`なしの`add`／`sub`／`mul`にする。オーバーフロー検査の組み込み関数は使わない。
  - 符号付きの`/`と`%`は、整数型とWrapping整数型で共通に扱う。除数が-1なら、除算は`0 - x`（整数型は検査付き、Wrapping整数型は`nsw`なし）、剰余は0にする。
    - 除数がリテラルの-1ならこの置き換えだけを生成する。
    - 除数が動的なら、-1の判定を分岐かselectで行う。selectでは除数-1を1に置き換えて`sdiv`／`srem`を実行し、除算だけ結果の符号を反転する。
    - 0除算の検査は通常どおり行う。
    - LLVMの`sdiv`／`srem`は、最小値と-1の組で剰余も含めて未定義動作になるので、この組を渡さない。
- **変換のlowering**:
  - `@wrap`は、狭めるとき`trunc`、広げるとき符号付きのオペランドなら`sext`・符号なしなら`zext`、同じ幅なら命令なし。Wrapping整数型も同じ。
  - `@bits`はLLVMの`bitcast`にする。signaling NaNをquietにし得る経路（x87や浮動小数点演算）を通さない。
  - 直接リテラル（§6.3）は、コンパイル時に任意精度で（浮動小数点リテラルは10進の正確な値から）変換して定数にする。実行時の変換が未対応の組（`3.9@i128`など）でも、直接リテラルは定数として使える。
- **内部表現**: 整数型の内部記述に、表せない結果の方針（checked／wrapping）を持たせる。飽和のための一般化は先取りしない。
- **測定**: `src/Benchmark`に、ハッシュとPRNGのループで`Wrapping`版と検査付き版を比べる測定を加え、検査がなくなる効果を確認する。
