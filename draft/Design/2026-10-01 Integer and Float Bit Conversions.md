# 仕様変更案：整数と浮動小数点のビット変換（`@wrap<U>`・`@bits<U>`）

日付: 2026-10-01

状態: 提案。正式仕様への取り込み・実装・実行検証は未実施。

## 1. 目的と適用範囲

既存の数値変換`@Type`は値を保つか、保てなければAbortする（既存§13.5.4）。そのため、次の操作を素直に書く方法がない。

- 切り捨て（u64 → u32）
- 同じ幅での符号の読み直し（u32 → i32）
- ビット列としての拡張（i32 → u64）
- 浮動小数点のビット列の取り出しと復元（f32 ↔ u32）

本書は、これらを名前付きの明示操作として追加する。本書は[Wrapping整数](2026-10-01%20Wrapping%20Integers.md)の§10.2から移管された提案である。

本書で変更する事項は、[SPEC.md](../../docs/SPEC.md)とその参照先より優先する。変更しない事項には既存仕様を適用する。Wrapping整数型に関する記述は、同提案の取り込みを前提とする。同提案が取り込まれない場合は、その記述を除いて適用する。節番号は本書を指し、「既存§」は正式仕様、「impl §」は実装仕様（`docs/impl`）を指す。

### 1.1. 中心定義

> `E@wrap<U>`は、整数`E`の値を、`U`の値域へ2ᴺを法として還元する（Nは`U`のビット幅）。`E@bits<U>`は、浮動小数点と同じ幅の整数の間で、ビット列をそのまま読み直す。どちらも失敗せず、未定義動作もない。

### 1.2. 例

```kimi
let hash: u64 = 0x1234_5678_9abc_def0
let low = hash@wrap<u32>          // 0x9abc_def0: 下位32ビット。
let code = 0x8000_4005@wrap<i32>  // -2147467259: HRESULTのE_FAIL。
let mask = -1@wrap<u64>           // 0xFFFF_FFFF_FFFF_FFFF。
let raw = 1.5@f32@bits<u32>       // 0x3FC0_0000。
let back = raw@bits<f32>          // 1.5。

func zigzagEncode(value: i64) -> u64
    return ((value << 1) ^ (value >> 63))@wrap<u64>

func zigzagDecode(value: u64) -> i64
    // どちらの値も値域内なので、通常の@で足りる。
    return (value >> 1)@i64 ^ -((value & 1)@i64)
```

## 2. 設計原則

| 原則 | 内容 |
| --- | --- |
| 値を保つ変換は`@Type` | 既存規則のまま。値を保てなければAbortする |
| 値を変える変換は名前で明示する | `@wrap<U>`は2ᴺを法とする還元、`@bits<U>`はビット列の読み直し。`@Type`の意味は変えない |
| 一つの概念に一つの形式 | 整数どうしは、同じ幅の符号の読み直しも含めて常に`@wrap`。`@bits`は浮動小数点が関わるときだけ |
| 失敗しない | どちらも全域の操作で、Abortも未定義動作もなく、`unsafe`も要らない |
| 合法性は型だけで局所的に決まる | `@wrap`はすべての整数型の組で合法。`@bits`は型の幅で決まり、幅がプラットフォームで変わる`isize`／`usize`は対象外 |

## 3. 構文

- 形式は`E@wrap<U>`と`E@bits<U>`。`wrap`と`bits`は、`move`・`copy`・`follow`と同じく`@`の直後でだけ認識する文脈キーワードとする（既存§2.5.1）。
- 変換先の型引数は、既存§13.1の「隣接する`<`」規則で直後に書く。型引数のない`E@wrap`や`E@bits`は不正。
- 優先順位と結合は、他の明示操作（`@Type`、`@move`、`@copy`）と同じレベル3、左結合。`-x@wrap<u8>`は`(-x)@wrap<u8>`、`x@wrap<u32>@u64`は`(x@wrap<u32>)@u64`。
- `U`はSemanticsの注釈を持たない値の型（§4.1、§5.1の対象）でなければならない。`@wrap<ref/u32>`は不正。
- オペランドの評価、value read、結果の扱いは数値変換`@Type`と同じ。一つの式は一つの操作であり、隠れた操作の連鎖は挿入しない（既存§13.5.3）。

## 4. `@wrap<U>`：整数の合同変換

### 4.1. 対象

オペランドの型と`U`は、どちらも整数型またはWrapping整数型である。幅と符号の組み合わせに制限はなく、同じ型どうしも合法（値は変わらない）。浮動小数点、`bool`、`char`、ポインタ、その他の型は対象外。

### 4.2. 結果

- 結果は、オペランドの数学的な値と2ᴺを法として合同な、`U`の値域内のただ一つの値である。
- ビットで見ると、次のとおりになる。
  - 狭める変換では下位Nビットを残す。
  - 同じ幅ではビットを変えない。
  - 広げる変換ではオペランドの符号に従って拡張する（符号付きは符号拡張、符号なしはゼロ拡張）。
  - いずれも、得たビット列を`U`として読む。
- ゼロ拡張が欲しい場合は、同じ幅の符号なし型を経由する（`x@wrap<u32>@u64`）。

```kimi
let a = 300@i32@wrap<u8>          // 44。
let b = 200@u8@wrap<i8>           // -56。
let c = 0xFFFF_FFFF@u32@wrap<i32> // -1。
let d = -1@i8@wrap<u16>           // 0xFFFF: 符号拡張してから16ビットとして読む。
let e = -1@i32@wrap<u64>          // 0xFFFF_FFFF_FFFF_FFFF。
let f = -1@i32@wrap<u32>@u64      // 0x0000_0000_FFFF_FFFF: ゼロ拡張。
```

### 4.3. 直接リテラル

- 直接の整数リテラル（括弧と、直接付いた一つの符号を含む。既存§13.5.4）をオペランドにすると、既定の型を経由せず、数学的な値から直接還元する。既存の`@f32`／`@f64`の直接リテラル規則と同じ考え方である。結果はコンパイル時に決まり、リテラルの表現上の上限は既存規則のまま。
- `-1@wrap<u32>`は`0xFFFF_FFFF`、`0x8000_4005@wrap<i32>`は`-2147467259`、`0x1_0000_0005@wrap<u32>`は`5`。
- 直接リテラル以外のオペランドは、既存§13.5.2どおり独立に型が決まる。`(200 + 100)@wrap<u8>`は`i32`で300を計算してから44にする。

### 4.4. Wrapping整数型

- `Wrapping<U>`は`U`と同じ値域を持つ型として、変換元にも変換先にもなる。
- 型を指定する`@Wrapping<U>`は値を保つ変換のまま。値域外の値を還元してWrapping領域に入れるには`@wrap<Wrapping<U>>`と書く。

```kimi
let seed: u64 = 0x1_0000_0007
let state = seed@wrap<Wrapping<u32>>  // 7。
let checked = seed@Wrapping<u32>      // Abort: 値を保つ変換は値域を検査する。
```

### 4.5. ジェネリック

`T is PrimitiveInteger`の証明（既存§8.4.7.3）は、`T`と、整数型または`PrimitiveInteger`が証明された型`U`（およびそれぞれのWrapping型）の間の`@wrap`を与える。幅に関係なく合法なので、定義の検査は一度で済む。

```kimi
func foldToU64<T>(value: T) -> u64
    T is PrimitiveInteger
    return value@wrap<u64>  // 符号付きの値は符号拡張される。
```

## 5. `@bits<U>`：浮動小数点のビット

### 5.1. 対象

オペランドの型と`U`のうち、ちょうど一方が浮動小数点型で、他方が同じ幅の整数型またはWrapping整数型である。

| 浮動小数点 | 相手の型 |
| --- | --- |
| `f32` | `i32`、`u32`、`Wrapping<i32>`、`Wrapping<u32>` |
| `f64` | `i64`、`u64`、`Wrapping<i64>`、`Wrapping<u64>` |

整数どうし（§4を使う）、浮動小数点どうし、幅の異なる組、`isize`／`usize`、128ビット整数、`bool`、`char`は対象外。

### 5.2. 結果

- 結果は、オペランドのビット列（IEEE 754のbinary32／binary64の符号化）そのものである。
- どちらの方向でも正規化しない。NaNのペイロード、quiet／signalingのビット、ゼロの符号を保つ。得た浮動小数点値に対するその後の演算は、既存の規則に従う。
- 失敗しない。

### 5.3. オペランドの型

オペランドの型は確定していなければならない。型が既定の規則だけで決まるもの（型の決まらないリテラル、リテラルだけの式）は不正であり、型を明示する。

```kimi
let nan = 0x7FC0_0001@u32@bits<f32>  // OK: ペイロード付きのquiet NaN。
let bad = 0x7FC0_0001@bits<f32>      // Error: オペランドの型が既定だけで決まる。
```

### 5.4. ジェネリック

オペランドまたは`U`が型パラメータに依存する場合は使えない。浮動小数点のContractはなく、型パラメータの幅も定義の時点では分からないためである。

## 6. 既存仕様との関係

- `@Type`は変えない。既存§13.5.4の「Integer -> integer: no truncation or wrapping」は、`@Type`の数値変換の規則として引き続き成り立つ。
- Wrapping整数の提案の原則「変換は決してラップしない」は`@Type`を指す。`@wrap<U>`は、ラップを名前で明示する別の操作である。
- 浮動小数点から整数への`@Type`（0方向に切り捨ててから値域を検査）は変えない。飽和する変換は追加しない。
- ポインタのキャスト（既存第5章）は変えない。`@bits`はポインタや集約型には使えない。

## 7. 診断

既存のDiagnostic Workflowに従う。修正候補は前提条件とともに示し、自動適用しない。

| 状況 | 説明と修正候補 |
| --- | --- |
| `@Type`の直接リテラルが値域外（既存のコンパイルエラー） | 2ᴺを法とする還元が意図なら`@wrap<U>`を示す |
| `@bits`で両方が整数 | 整数どうしは`@wrap<U>`を使うことを示す |
| `@bits`で幅が違う、または`isize`／`usize` | 同じ幅の型（f32なら32ビット、f64なら64ビット）を示す。`isize`／`usize`は幅がプラットフォームで変わることを説明する |
| `@bits`のオペランドの型が既定だけで決まる | `@u32@bits<f32>`のように型を明示する |
| `@wrap`に浮動小数点 | 浮動小数点と整数の変換は`@Type`（値域検査付き）か、ビットなら`@bits`を使うことを示す |
| `@wrap`／`@bits`に型引数がない | 変換先の型が必要であることを説明する |
| ジェネリック本体での`@bits` | 型が具体的に決まった場所で使うことを説明する |

## 8. 範囲外と将来

### 8.1. 採用しないもの

| 案 | 理由 |
| --- | --- |
| `@Type`自体に切り捨てを持たせる（Rustの`as`、Cのキャスト） | 値を保つ変換と値を変える変換が同じ綴りになり、損失が見えない |
| `@Wrapping<U>`で還元する | `@Type`の意味が変換先の種類で変わる（Wrapping整数の提案で却下済み） |
| 切り捨て・符号の読み直し・拡張を別々の操作にする（Zigの`@truncate`／`@bitCast`） | いずれも「2ᴺを法とする還元」という一つの概念である。一つの規則なら、ジェネリックで幅が分からなくても合法性が決まる |
| 広げるときに常にゼロ拡張する | 値と合同にならず、符号付きの-1が別の値になる。ゼロ拡張は`x@wrap<u32>@u64`で明示できる |
| 整数どうしにも`@bits`を許す | `@wrap`との二重形式になる |
| `isize`／`usize`を`@bits`の対象にする | 合法性がプラットフォームで変わり、局所推論に反する |
| `@bits`で直接リテラルを幅に合わせて適合させる特例 | 型を一段明示すれば足りる |
| Kimiの関数として提供する（`Bits.truncate(x)`など） | 変換は`@`に集める既存の形と揃える。整数型はメンバを持たない（既存§4.6.2） |
| `$wrap(...)`などComposition Rootの操作 | 特別な評価規則を持たない普通の変換であり、`$`を使う理由がない |

### 8.2. 将来の別提案（本書の提案項目ではない）

- 失敗を値として返す変換（`Option`を返す。Swiftの`exactly:`、Rustの`try_from`に相当）
- 飽和する変換（Swiftの`clamping:`に相当）
- バイト列との相互変換（エンディアンを指定する）
- ビット操作関数（回転、ポップカウント、先頭ゼロ数など）

## 10. 検証と実装

### 10.1. 必須検証

- `@wrap`: すべての整数型とWrapping整数型の組で、境界値（最小値、最大値、-1、0）、狭める変換、同じ幅、符号拡張とゼロ拡張、同じ型どうし
- 直接リテラル: 正確な値からの還元、負の値、表現上の上限。リテラルだけの式が独立に型付けされること
- ジェネリックな`@wrap`: 幅の異なる各インスタンス化
- `@bits`: 許可された各組の往復で全ビット列が保たれること（NaNのペイロード、signaling NaN、±0、±∞、非正規化数を含む）
- 拒否: 幅の不一致、`isize`／`usize`、整数どうしの`@bits`、既定だけで決まる型、ジェネリック本体での`@bits`、`@wrap`への浮動小数点
- コード生成（O0／O2）: 検査を生成しないこと、§10.2の単一命令（または命令なし）になること、NaNを正規化しないこと
- 診断: §7の各経路と、誤検出しない有効な対応例

### 10.2. 実装メモ（非規範）

- `@wrap`は、狭めるとき`trunc`、広げるとき符号付きのオペランドなら`sext`・符号なしなら`zext`、同じ幅なら命令なし。Wrapping整数型も同じ。
- `@bits`はLLVMの`bitcast`にする。signaling NaNをquietにする可能性のある経路（x87や浮動小数点演算）を通さない。
- 直接リテラルの`@wrap`は、コンパイル時に任意精度で還元して定数にする。

## 付録A. 決定事項

| 事項 | 決定 |
| --- | --- |
| 操作の数 | 二つ。整数の合同変換`@wrap<U>`と、浮動小数点のビット`@bits<U>` |
| 広げるときの拡張 | オペランドの符号に従う（値と合同にする） |
| 綴り | `@`の直後の文脈キーワード。`wrap`は「2ᴺを法とする」というWrapping整数と同じ意味を表す |
| `isize`／`usize` | `@wrap`では使え、`@bits`では使えない |
| 直接リテラル | `@wrap`は正確な値から還元する。`@bits`は型の明示を求める |
| ジェネリック | `@wrap`は使え、`@bits`は使えない |
