# 仕様変更案：Wrapping整数（`Wrapping<T>`）

日付: 2026-10-01

状態: 提案。正式仕様への取り込み・実装・実行検証は未実施。

## 1. 目的と適用範囲

ハッシュ、PRNG、チェックサム、暗号、シーケンス番号のように2ᴺを法とする計算を、新しい演算子なしで書けるようにする。ラップするかどうかは演算子ではなく**値の型**で決める。

本書で変更する事項は、[SPEC.md](../../docs/SPEC.md)とその参照先より優先する。変更しない事項には既存仕様を適用し、他のdraftには依存しない。節番号は本書を指し、「既存§」は正式仕様、「impl §」は実装仕様（`docs/impl`）を指す。

### 1.1. 中心定義

> `Wrapping<T>`は、`T`と同じ表現・符号・値の解釈・レイアウト・ABIを持つ別の整数型である。算術オーバーフローだけが、Abortではなく2ᴺを法として定義される（Nは`T`のビット幅）。

### 1.2. 例

```kimi
let a: Wrapping<u8> = 250
let b = a + 10      // 4: 2⁸を法としてラップする。
let c: u8 = 250
let d = c + 10      // Abort: 通常の整数は従来どおり検査する。

func mix64(state: u64) -> u64
    var x = state@Wrapping<u64>
    x = (x ^ (x >> 30)) * 0xbf58_476d_1ce4_e5b9
    x = (x ^ (x >> 27)) * 0x94d0_49bb_1331_11eb
    return (x ^ (x >> 31))@u64

func fnv1a(bytes: Slice<u8>) -> u32
    var hash: Wrapping<u32> = 0x811c_9dc5
    for byte in bytes             // byte: ref/u8。
        let value: u8 = byte      // value readで値を読む。
        hash = (hash ^ value@Wrapping<u32>) * 0x0100_0193
    return hash@u32
```

## 2. 設計原則

| 原則 | 内容 |
| --- | --- |
| ラップは型で決まる | 同じ`+`でも、オペランドが`Wrapping<T>`ならラップし、`T`なら検査する。`f64`の`+`がIEEE 754に従うのと同じ仕組みで、式の外側の文脈やビルド設定には依存しない |
| 数値変換`@Type`は決してラップしない | `@Type`による数値変換は値を保つかAbortする。ラップするのは算術と、名前でラップを明示する別の変換（§10.2）だけ |
| なくすのはオーバーフローの失敗だけ | 0除算と不正なシフト数は従来どおりAbortする。`Wrapping`は「検査なし整数」ではない |
| 値であって数量・位置ではない | `Wrapping`の値は、添字・Range・`^x`・長さ・シフト数には使えない |
| 差分だけを定義する | `Wrapping<T>`は`T`と同じ規則に従い、本書が列挙する違いだけを持つ |

## 3. 型

### 3.1. 宣言と形成

- `Wrapping<T>`はKimiのルートに置くcompiler-intrinsicなTypeである。既定エイリアスにより`Wrapping<u32>`と書け、`::Kimi.Wrapping<T>`で常に指せる。
- 型引数は`T is PrimitiveInteger`を満たさなければならない（外側Semanticsが`owner`の12の整数Core）。`Wrapping<f32>`、`Wrapping<ref/u32>`、`Wrapping<Wrapping<u32>>`は不正。
- ジェネリック宣言で`Wrapping<T>`を形成するには、`T is PrimitiveInteger`が証明されていなければならない（既存`FromEnd<T>`と同じ）。
- メンバ（Field・Property・関数）も公開コンストラクタも持たない。値は§4の演算結果、§5の変換、§6のリテラル適合としてだけ得られる。ユーザーの同名宣言はこの扱いを得ない。

### 3.2. 分類と用語

- `Wrapping<T>`を**Scalar**に加える。既存§3.1のScalarは、12の整数Core、12のWrapping整数Core（`T`が整数Coreである`Wrapping<T>`）、浮動小数点Core、`bool`、`char`からなる閉じた集合になる。
- これにより、Copy、Owned、Sealed、ObjectPayload、read Type（既存§3.5.3）、コード生成上のScalarの扱いが既存規則から従う。
- ジェネリックな`Wrapping<T>`は、`T is PrimitiveInteger`が証明されているときread Typeになる。
- 正式仕様の「整数型（integer Type）」は、従来どおり12の組み込み整数型だけを指す。`Wrapping<T>`は「**Wrapping整数型**（wrapping integer Type）」と呼ぶ。整数型を名指しする既存規則は、§4–§8が適用を定める範囲でだけWrapping整数型に及ぶ。Position、Range、`^x`、長さ、シフト数などの規則は及ばない。

### 3.3. 型の同一性

- `Wrapping<T>`と`T`は別の型であり、部分型関係も暗黙変換もない。`Wrapping<u32>`と`Wrapping<u64>`のように異なるWrapping型どうしも同様。
- オーバーロードでも別の型として扱う。リテラル引数が両方に適合する場合は、既存§12.3.1の規則どおり曖昧になる。

```kimi
func describe(value: u32) -> () => ()
func describe(value: Wrapping<u32>) -> () => ()
describe(5)                // Error: 両方の候補に適合する。
describe(5@Wrapping<u32>)  // OK。
```

### 3.4. 表現

- ビット幅、サイズ、アラインメント、stride、ABIは`T`と同じ。foreign関数のシグネチャにも`T`と同じABIで使える。
- `Option<Wrapping<T>>`の表現は`Option<T>`と同じ規則（明示タグ）に従う。

## 4. 演算

### 4.1. 一般則

`Wrapping<T>`は`T`と同じ組み込み演算子を持つ。二項演算のオペランドは同じWrapping型でなければならず（シフト数を除く）、結果も同じWrapping型になる（比較は`bool`）。value read、評価順序、評価回数、書き込み回数は既存規則のまま。

| 演算 | `Wrapping<T>`での動作 |
| --- | --- |
| `+` `-` `*`、単項`-`、`++` `--`、これらの複合代入 | オーバーフローすると2ᴺを法としてラップする（§4.2） |
| `/` `%` | `T`の符号の解釈で計算する。符号付きの最小値`/ -1`は最小値、`% -1`は0。0除算はAbort |
| `&` `\|` `^`と複合代入 | `T`と同じ |
| `<<` `>>`と複合代入 | `T`と同じ。シフト数は整数型に限る（§4.5） |
| `==` `!=` `<` `<=` `>` `>=` | `T`と同じ順序（§4.6） |
| 単項`+` | `T`と同じ |

### 4.2. ラップの定義

- 結果は、数学的な結果と2ᴺを法として合同な、`T`の値域内のただ一つの値である。
- `Wrapping<i8>`の`127 + 1`は`-128`、`Wrapping<u8>`の`0 - 1`は`255`。
- 増減と複合代入はオーバーフローで書き込みを妨げられない。既存§13.2の「overflow prevents the write」は適用しない。

### 4.3. 変わらない失敗

- 0による除算・剰余と、`0 <= count < N`を満たさないシフト数は、既存§17.3どおりAbortする。
- `Wrapping`が無効にするのはオーバーフローによる失敗だけで、整数の安全性ではない。

### 4.4. 単項`-`

- 符号なしを含むすべての`Wrapping<T>`で使える。結果は数学的な`-x`を§4.2でラップした値。
- 符号なし整数型が単項`-`を持たないのは0以外で必ずオーバーフローするためであり、その失敗がない`Wrapping`では許可するのが一貫する。

```kimi
func lowestBit(value: u32) -> u32
    let w = value@Wrapping<u32>
    return (w & -w)@u32  // 最下位の1ビットだけを残す。
```

### 4.5. 数量と位置

- シフト数（右オペランド）は整数型でなければならず、`Wrapping`は使えない。左オペランドには使える。
- 添字、Position、Rangeの境界、`^x`、長さ、定数添字など、数量や位置を求める文脈にも使えない（§7.2）。

### 4.6. 順序

- 比較は`T`の順序に従う。`Wrapping<i8>`では`-128 < -1 < 0 < 127`、`Wrapping<u8>`では`0 < 127 < 255`。
- RFC 1982のシーケンス番号比較のような循環する順序は提供しない。

## 5. 変換

### 5.1. 一般則

`@`による数値変換（既存§13.5.4）では、`Wrapping<U>`は`U`と同じ値域を持つ型として、変換元にも変換先にもなる。

| 変換元 → 変換先 | 規則 |
| --- | --- |
| 整数型・Wrapping整数型どうし | 変換先の値域を検査する。切り捨てもラップもしない |
| 整数型・Wrapping整数型 → 浮動小数点 | `U`と同じ（最近接偶数丸め） |
| 浮動小数点 → 整数型・Wrapping整数型 | `U`と同じ（0方向に切り捨ててから値域を検査） |

- `T`と`Wrapping<T>`の相互変換は常に成功し、値もビットも変わらない。
- 一つの`@`は一つの変換である。`u8`から`Wrapping<u32>`への変換も、値域検査付きの一回の変換として定義する。
- 変換先の型引数は省略できない（`x@Wrapping`は不正）。
- `@ref`、`@uniq`、`@move`、`@copy`、`@follow`などの明示操作は既存規則のまま。
- 切り捨てとビットの読み直しは本書では定めない（§10.2）。

```kimi
let small: u8 = 200
let big: u64 = 0x1_0000_0005
let a = small@Wrapping<u32>                // 200。
let b = big@Wrapping<u32>                  // Abort: u32の値域外。変換はラップしない。
let c = (big & 0xFFFF_FFFF)@Wrapping<u32>  // 5: 残す下位ビットを明示してから変換する。
```

## 6. リテラル

### 6.1. 適合

- `Wrapping<U>`への整数リテラルの適合は`U`の値域で判定する。直接付いた符号は、既存§13.5.4どおりリテラルの一部として扱う。
- `5@Wrapping<u32>`は直接リテラルの適合である（既存§13.5.4）。
- 型の決まらない整数リテラルの既定型は従来どおり`i32`であり、`Wrapping`にはならない。

```kimi
let allOnes: Wrapping<u32> = 0xFFFF_FFFF  // OK。
let minusOne: Wrapping<u32> = -(1)        // OK: 単項-の結果は0xFFFF_FFFF。
let invalid: Wrapping<u32> = -1           // Error: 符号付きリテラル-1はu32の値域外。
let key: Wrapping<i32> = 0x9E37_79B9      // Error: i32の値域外。Wrapping<u32>を使う。
```

### 6.2. リテラルだけの式

- 既存§12.3.1どおり、適合した型が各オペランドに伝わり、式はその型で評価される。`Wrapping<U>`では各演算がラップする。`let x: Wrapping<u8> = 200 + 100`は44。
- 定数畳み込みは演算ごとの意味を保つ（既存規則の確認）。正確な整数で計算して最後に一度だけ切り捨てる方法は、`/` `%` `>>`や比較を含む式で結果が変わるため使えない。

### 6.3. ジェネリック

型引数が未確定の`Wrapping<T>`に適合するリテラルは、`PrimitiveInteger`と同じく0から127まで。

### 6.4. パターンとキー

- リテラルパターン（既存§14.8.1）は`Wrapping<U>`の値にも使え、`U`の値域で適合を判定する。`Wrapping<u32>`に対する`-1`パターンは不正で、`0xFFFF_FFFF`と書く。
- Dictionaryのリテラルキー重複検査（既存§12.3.4）は、`Wrapping<U>`のキーにも適用する。

## 7. Contractと言語構造

### 7.1. 参加するもの

| 項目 | 内容 |
| --- | --- |
| Copy、Owned、Sealed、ObjectPayload | Scalarとして既存規則から従う |
| Equatable、Comparable | `T`と同じ意味。Comparableの順序は`T`の順序 |
| Utf8Format | `T`と同じ表現（§8.1） |
| value read | `ref`／`uniq`の層の先にある`Wrapping<T>`を値として読む（既存§3.5.3） |

### 7.2. 参加しないもの

- `PrimitiveInteger`を満たさない。`T is PrimitiveInteger`を前提にしたジェネリックコードに、ラップする値は入らない。
- Position・PositionRange（既存§4.6.2）、Rangeの構築と反復（既存§4.6.3）、`^x`、長さ定数（既存§4.2）、ConstantIndexExpressionには使えない。

```kimi
let index: Wrapping<isize> = 3    // values: Array<i32>。
let first = values[index]         // Error: WrappingはPositionではない。
let second = values[index@isize]  // OK。
let shifted = index << index      // Error: シフト数にWrappingは使えない。
```

### 7.3. ジェネリックの証明規則

`T is PrimitiveInteger`の証明（既存§8.4.7.3）は、`Wrapping<T>`について次を与える。

- 形成、Scalarかつread Typeであること、§7.1のContract
- §4の演算子（単項`-`を含む）、複合代入、増減
- `PrimitiveInteger`を満たす型とそのWrapping型の間の`@`変換
- 0から127までのリテラル

新しいContractは追加しない。数値Contractのユーザー拡張がないという既存の方針も変えない。

```kimi
func scramble<T>(value: Wrapping<T>, key: Wrapping<T>) -> Wrapping<T>
    T is PrimitiveInteger
    return -(value ^ key) * 31  // Tには単項-がないが、Wrapping<T>にはある。
```

### 7.4. 推論

既存§10.2.1では、`PrimitiveInteger`を含意する制約を持つ裸の`T`が、参照の層を持つ引数から終端の参照先の型を束縛する。この扱いを`Wrapping<T>`型のパラメータにも適用する。`ref/Wrapping<u32>`の引数は`T = u32`を束縛し、値を読む。

## 8. 書式・テスト・実装プロファイル

- **書式**: Utf8Formatの既定表現と容量見積もりは`T`と同じ。`Wrapping<u8>`の255は`255`、`Wrapping<i8>`の-1は`-1`と書き、`Wrapping(255)`のように包んだ表示はしない。デバッガ表示は本書の範囲外。
- **テスト**: テスト失敗時のScalarスナップショット（impl testing-profileのkind 7）は、`T`と同じkind（signed／unsigned）とビット幅で記録する。
- **実装プロファイル**: `T`に対する制限（128ビット除算など）は`Wrapping<T>`にも同じく適用する。

## 9. 診断

既存のDiagnostic Workflowに従う。修正候補は前提条件とともに示し、自動適用しない。

| 状況 | 説明と修正候補 |
| --- | --- |
| `Wrapping<U>`と`U`（または別の整数型）の混在 | 別の型であることを説明する。ラップが意図なら他方を`@Wrapping<U>`、検査が意図なら`@U`で変換する |
| Position・Range・`^x`・長さ・シフト数への使用 | 値であって数量・位置ではないことを説明する。`@isize`などへの変換を示す |
| 値域外のリテラル | `U`の値域で判定することを説明する。全ビット1なら`0xFFFF_FFFF`や`-(1)`を示す |
| `PrimitiveInteger`でない型引数 | 形成条件を説明する |
| 存在しない構築・取り出し（`Wrapping(5)`、`.0`など） | メンバもコンストラクタもないことを説明する。`5@Wrapping<u32>`、`w@u32`を示す |

## 10. 範囲外と移管

### 10.1. 採用しないもの

| 案 | 理由 |
| --- | --- |
| `+%` `-%` `*%`、Swiftの`&+`など演算子ごとの指定 | 記号が増えて読みにくい。`&+`はKimigayoの`&`と単項`+` `-` `*`に字句上衝突する |
| `wrap(...)`やブロック単位の指定、ビルド設定による切り替え | 意味が外側の文脈で変わり、局所推論に反する。式の抽出や移動で意味が黙って変わる |
| `wrappingAdd`などのメソッド | 同じ概念の二重形式になる |
| `@Wrapping<U>`による切り捨て | 「変換はラップしない」に反し、`@`の意味が変換先の種類で変わる |
| 負のリテラルのラップ適合（`Wrapping<u32>`に`-1`） | Kimigayoの`-1`は符号付きリテラルで`-(1)`ではない。特例が必要になり値域の一般則に反する。`-(1)`で足りる |
| `PrimitiveInteger`への適合 | 添字、Range、Abortを前提にしたジェネリックコードに入り込む |

### 10.2. 移管

- 切り捨て（u64 → u32）、同じ幅のビットの読み直し（u32 → i32）、浮動小数点のビット（f32 ↔ u32）は、別提案[整数と浮動小数点のビット変換](2026-10-01%20Integer%20and%20Float%20Bit%20Conversions.md)に移管する。本書はこれらを定めない。
- 移管先は、整数の合同変換`@wrap<U>`と浮動小数点のビット`@bits<U>`を提案している。いずれも`@Type`の意味は変えない。

### 10.3. 将来の拡張（本書の提案項目ではない）

- `Saturating<T>`などは、同じ「型で方式を選ぶ」枠組みで別提案とする。
- 検査結果を値として返す演算（`tryAdd`など）は、必要になった時点でライブラリとして追加する。

## 12. 検証と実装

### 12.1. 必須検証

- 12種すべての`Wrapping<T>`で、`+ - *`、単項`-`、増減、複合代入の境界値（最大値・最小値・0）
- 符号付きの最小値`/ -1`と`% -1`、0除算と不正なシフト数のAbort
- 符号の解釈の違い: 同じビット列で`/` `%` `>>`と比較が`Wrapping<u32>`と`Wrapping<i32>`で異なること
- 変換: `T`との往復、拡大、値域外のAbort、浮動小数点との変換
- リテラル: 値域外のエラー、`-(1)`、リテラルだけの式（`200 + 100`が44）、`/` `%` `>>`や比較を含むリテラルだけの式の定数畳み込み
- 型エラー: 混在、Position・Range・`^x`・長さ・シフト数への使用、形成条件
- ジェネリック: 単項`-`、0から127のリテラル、各インスタンス化
- value readと推論、リテラルパターン、Dictionaryキー、書式、テストスナップショット
- コード生成（O0／O2）: §12.2のlowering、`T`との変換が命令を生まないこと、`T`と同じABI
- 診断: §9の各経路と、誤検出しない有効な対応例

### 12.2. 実装メモ（非規範）

- 整数型の内部記述にオーバーフローの扱い（checked／wrapping）を持たせる。飽和のための一般化は先取りしない。
- `+ - *`と単項`-`は、`nsw`／`nuw`なしの`add`／`sub`／`mul`で生成する。オーバーフロー検査の組み込み関数は使わない。
- 符号付きの`/` `%`は、0除算を検査したうえで最小値`/ -1`を明示的に分岐し、最小値と0を返す。LLVMの`sdiv`／`srem`はこの組み合わせで未定義動作になるため、命令に渡さない。
- `T`と`Wrapping<T>`の変換は命令を生まない。
