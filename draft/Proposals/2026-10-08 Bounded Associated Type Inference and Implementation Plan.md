# 仕様変更・実装計画：関連型の限定的な推論

日付：2026-10-08。状態：精査に基づく提案。正式仕様への取り込み・実装・実行検証は未実施。

## 1. 位置づけと結論

**本書の変更事項は、[SPEC.md](../../docs/SPEC.md) およびその参照先より優先する。変更しない事項には既存仕様を適用する。** 今回は本書を作成するだけで、正式仕様・実装・既存提案を変更しない。将来の取り込みでは正式仕様を自己完結させ、本書への依存を残さない。

**採用を推奨する。実装を戻り型に依存せず一意に識別できるとき、その宣言で確定する値戻り型から、省略された関連型を補う。** 戻り型は明示注釈、または省略時の既定 Unit に限る。関数本体・呼出し側・具体化からは推論しない。候補の選び直し、連鎖的な推論、一般的な制約探索は導入しない。

現在の §8.4.3・§8.7 と算術 Contract の章は、実装シグネチャからの推論を禁止している。一方、§8.4.5 の実装識別キーには戻り型が含まれず、識別と互換性検査が分離されている。この分離を保った宣言情報の補完なら実現可能である。主な実装費用は照合アルゴリズムより、関連型の確定時期・キャッシュ・診断の整理にある。

## 2. 評価と設計判断

### 2.1. 得られるものと負担

| 観点 | メリット | デメリットと対処 |
| --- | --- | --- |
| 記述量 | `added -> Self` と `Output is Self` の重複をなくす。例の Vec2 は四つの指定を省略できる | 型宣言の冒頭だけでは結果が見えにくい。公開契約・Hover に確定型と推論元を残す |
| 一貫性 | 演算子専用の省略規則を設けず、通常の Contract に適用できる | どこでも推論できるわけではない。戻り型の構造照合という一つの入口に限定する |
| 保守 | シグネチャと関連型の二重修正を減らす | 実装の戻り型変更が関連型の公開契約も変える。依存先を失効させ、安定させたい API は明示指定を使う |
| 予測可能性 | 本体を読まず、定義時に決定できる。実行時の処理は増えない | オーバーロード追加で推論不能になり得る。候補を固定し、結果で曖昧さを解消しない |
| コンパイラ | 小さな構造照合と既存の適合検証を組み合わせられる | 未確定状態と確定状態を分ける必要がある。古い失敗キャッシュの残留も検証する |

利益は Vec2 の四行削減にとどまらない。生成・変換操作、`IntoIterable.IteratorType`、既存の固定等式を展開した `Iterator.Item` にも適用できる。一方、消費する引数だけに現れる関連型や、呼出しごとに変わる Origin family には利益がない。

この範囲なら複雑性の増加に見合う。**完全な関連型推論まで拡張する利益は、今回の目的には見合わない。** コンパイル時間・メモリの増分は未計測であり、実装時の測定と回帰検証を完了条件にする。

### 2.2. 単純化の方針

- 新しい構文・キーワード・有効化スイッチを追加しない。省略を許す条件だけを定める。
- 正規の意味表現は、これまでどおり「関連型の束縛と要求から実装への対応」とする。明示と推論で、呼出しやコード生成の規則を分けない。
- 推論は一度固定した宣言情報から等式を集めるだけにする。結果を使って新しい推論元を増やさない。
- 明示指定は引き続き使える。公開型を実装の具体的な戻り型から独立させる場合にも使う。
- 最初の案の「明示注釈だけ」は、既存規則で結果が Unit と決まる名前付き関数の省略形も含める形に整理する。`-> ()` の有無による特例を避けるためであり、本体からの戻り型推論は導入しない。

Kimigayo Principles との関係は明確である。一つの意味表現に正規化することで原則1、宣言シグネチャと固定された適合範囲で決めることで原則2、所有権・失敗・Origin を含む型を保持することで原則3、根拠と確定型を構造化して公開することで原則4を守る。

## 3. 仕様変更案

### 3.1. 対象と既存情報の固定

対象は、struct／enum の宣言済みの静的適合に属する、**Origin パラメーターを持たない関連型**である。名前から適合を自動登録する機能は追加しない。

推論前に、明示指定、Contract と祖先の型同一性制約、継承済みの束縛、および既存の限定された証明規則で得られる情報を固定する。以下、これを「基礎情報」と呼ぶ。

- 単位は束縛済み Contract 参照とその適合経路である。`Addable<A>.Output` と `Addable<B>.Output`、別 Contract の同名関連型を混同しない。
- 推論に使う事実は、型の制約・適合条件・Contract の制約など、適合の全域で成り立つものに限る。要求／実装関数だけの前提で、公開する関連型を特殊化しない。各要求の前提は、後段の通常の互換性検査で既存規則どおり使う。前提を別経路へ流用しない。
- 明示された同一性によって同じ未確定型を表す関連型は、同じ推論対象として扱う。新しい型同一性を探索してまとめることはしない。
- 既存規則で循環した指定として拒否される宣言を、追加推論で救済しない。関連型や適合が自分自身の成立を証明することも許さない。
- 固定等式は通常どおり前向きに展開する。例えば `LentItem(step) is Item` を展開して `Item` を推論してよい。これは Origin family 自体の推論ではない。
- 別の宣言の公開契約は、その束縛が推論由来でも利用できる。ローカル宣言では、循環のないヘッダー依存を完成させて束縛を利用し、適合の最終証明を別途必須にする。依存宣言の完成待ちは既存の依存解決規則に従い、循環から証拠を作らない。

型パラメーターなどを含む記号的な型も利用できる。基礎情報が固定されていることは、すべての型が具体型であることを意味しない。

### 3.2. 推論元となる実装の識別

通常の名前解決を行い、§8.4.5 の実装識別キーを**基礎情報だけで**照合する。名前、関数種別、generic の形、task slot、引数数・順序・外部ラベル、receiver・引数の型構造、値／Place の結果区分を既存規則どおり扱う。

次のすべてを満たす要求と実装だけを推論元にする。

1. 識別キーの比較が、新しく推論する関連型に依存しない。
2. 既存の識別規則で実装候補がちょうど一つに定まる。
3. 要求と実装が値を返し、実装の結果が `-> Type`、または名前付き関数の省略時の既定 Unit により定まる。
4. 証拠として取り出す型を、基礎情報と明示シグネチャから束縛できる。

戻り型、Origins、Constraints、条件付きメンバーの適用条件、Effects を使って候補を絞らない。アクセスは既存の名前解決と適合互換性の段階を保つ。推論のために別の候補優先順位を設けない。

入力に未確定関連型が残る要求は、候補が見かけ上一つでも推論元にしない。ほかの要求から関連型が決まれば、最後に通常の実装照合を行える。基礎情報の段階では推論元でなかった要求を、その後で推論元に昇格させない。

### 3.3. 戻り型からの等式の抽出

要求側と実装側の戻り型を、それぞれ基礎情報による既存の alias・固定等式で正規化する。要求の未確定関連型の位置と、一意に識別した実装の宣言上の戻り型の対応位置を照合する。

| 要求側の形 | 抽出規則 |
| --- | --- |
| 推論対象 `A` そのもの | 対応する実装側の完全な型 `T` を取り出し、`A is T` の証拠とする |
| 同じ nominal 型の構築、Tuple | 宣言の同一性・引数数、または Tuple の要素数が一致するとき、対応する型の位置へ進む |
| 固定長配列 | 長さが基礎情報だけで同一と分かるとき、要素型へ進む。長さは推論しない |
| 具体的な Semantics の層 | 同じ層どうしで内側へ進む。`owner` の正規化は既存規則に従う |
| Function Type、未解決の関連型 projection、未確定 Semantics 適用 | 内部を逆算しない。基礎情報で既に正規化できる場合だけ、上の規則へ進める |

**未確定関連型に到達する経路だけを照合する。既に固定された部分には通常の互換性検査を適用する。** 例えば `(A, Known)` の `A` を対応位置から求めるとき、`Known` 側に戻り型の完全一致を追加要求しない。対応構造がない位置からは証拠を得られず、構造の不適合自体は最後の通常検査で扱う。

取り出した `T` は次の条件を満たす必要がある。

- Semantics・型引数・内部 Origins・長さを含む完全な型を保持する。参照を外して値型へ変えたり、Origin を `static` に置き換えたりしない。
- 自由に参照する型・length・Origin は適合のスコープで有効である。実装関数固有の generic 引数、呼出しごとの Origin、省略から導入された receiver の Origin を持ち出さない。
- `T`、`Box<T>`、前提により有効な `T.(Source).Element` などの記号的な型もよい。今回の未確定関連型や、未検証の循環した適合証拠への依存は許さない。
- 一つの完全な型として束縛するなら Function Type もよい。その内部で束縛される変数と、実装関数から持ち出す自由変数を区別する。

経路上にあるが取り出す型に含まれない Origin は、通常の戻り値互換性検査で扱う。新しい Origin 推論・寿命の短縮・借用は行わない。部分型からの逆算、共通上位型、暗黙の変換、Copy 判定、能力を満たす型の探索も行わない。

### 3.4. 一致・確定・検証

すべての推論元から得た証拠を、基礎情報を更新せずに集める。同じ関連型への証拠は、Origins も含む既存の正規化された型同一性で一致しなければならない。列挙順・ファイル順・キャッシュ状態で最初の一件を採用しない。

| 状況 | 結果 |
| --- | --- |
| 同じ型を示す証拠が一件以上ある | その型で補完する |
| 異なる型を示す証拠がある | 省略した適合はエラー。共通上位型の探索や一部証拠の無視はしない |
| 必要な関連型に証拠がない | 明示指定が必要。候補探索や関数本体の解析で埋めない |
| 証拠の型が適合スコープから外れる | その証拠は使えない。流出する binder と推論元を説明する |

収集後に束縛を補完し、**すべての要求について**従来の実装照合・型形成・能力制約・アクセス・Origins・Loans・Safety・Effects・経路整合性を検査する。推論できたことは、適合が有効であることの証明ではない。失敗しても別実装へ切り替えない。

明示・固定・継承で既に型が定まる関連型は、推論対象にしない。例えば公開結果を `Base` と明示し、実装が既存の互換性規則で許される `Derived` を返すコードは、引き続き認める。省略時の異なる証拠も、適切な明示型で通常の互換性が成立すれば解消できる。ただし明示型が合わない実装を許すわけではない。

`associate C.Item is Copy` のような能力制約だけの指定は型を固定しないため、推論対象に残る。補完後にその制約も検証する。

推論結果を再投入する反復は行わない。`make() -> A` から `A` が決まっても、入力に `A` を使う `convert(value: A) -> B` を新たな推論元にはしない。その場合は `A` または `B` を明示して、必要な基礎情報を与える。

### 3.5. 適用範囲と変更しない事項

- **generic・条件付き適合：** 定義時に、宣言された前提が許すすべての束縛に対して検証する。都合のよい具体化から型や追加条件を決めない。
- **refinement・継承：** 同じ束縛済み要求の重複経路は既存規則で扱い、独立した要求は分ける。継承された関連型・実装対応を基礎情報に保持し、派生型の `Self` や新しいメンバーから勝手に推論し直さない。継承メンバーを新しい適合に使う場合も既存の receiver 対応に従う。
- **Origin family：** family 自体の束縛、引数対応、定義域は推論しない。既存の明示等式の展開だけを許す。
- **Property・Place：** Property、Field、accessor、Place 結果からは証拠を抽出しない。ほかの関数で決まった関連型を使って、通常どおり検証する。標準 Property witness は Copy／借用などを伴い、Field の型だけでは要求型が一意にならない。
- **本体と省略戻り型：** `return`、式本体、Abort などの本体の到達不能性、呼出し側の期待型は使わない。名前付き関数の戻り型省略は、既存規則で決まる Unit の証拠にだけなる。本体が数値を返しても数値型の証拠にはならず、通常の本体検証で不適合を報告する。Never をソースに書く新構文は追加しない。
- **公開契約：** 確定した関連型は既存の適合情報に記録し、利用側はその情報だけで型検査する。明示と推論が同じ束縛・実装対応なら、意味上の契約は同じである。推論元の位置は説明用情報として保持する。

公開束縛や実装対応が変わる編集では依存先を再検証する。推論元や候補の変更も、再検証完了まで古い確定結果を利用できない。既存のコード生成・ABI・所有権規則は変えない。

## 4. 例

以下は提案後のコードであり、現在のコンパイラでの受理を主張するものではない。

### 4.1. Vec2

```kimi
struct Vec2
    Self is Addable<Self> and Multipliable<f32> and LeftMultipliable<f32> and Negatable

    public let x: f32
    public let y: f32

    public init(x: f32, y: f32)
        self.x = x
        self.y = y

    drop => ()

    public func added(self: ref/Self, right: ref/Self) -> Self
        return Self.init(self.x + right.x, self.y + right.y)

    public func multiplied(self: ref/Self, right: ref/f32) -> Self
        return Self.init(self.x * right, self.y * right)

    public func multipliedFrom(left: ref/f32, self: ref/Self) -> Self
        return self.multiplied(left)

    public func negated(self: ref/Self) -> Self
        return Self.init(-self.x, -self.y)
```

四つの `Output` はそれぞれ独立に `Self` へ決まる。`multipliedFrom` はその明示戻り型から推論し、本体の `multiplied` 呼出しからは推論しない。必要なら従来どおり `associate Addable<Self>.Output is Self` と書ける。

### 4.2. 構築型と推論不能の境界

```kimi
contract OptionalSource
    associate Item
    func read(self: ref/Self) -> Option<Self.Item>

struct NumberSource
    Self is OptionalSource
    drop => ()

    public func read(self: ref/Self) -> Option<i32> => Option.Some(1)
    // Item is i32：Option の同じ型引数位置から決まる。

contract Consumer
    associate Item
    func consume(self: ref/Self, item: Self.Item) -> ()
```

`Consumer` の実装が `consume(..., item: i32) -> ()` だけでも、入力の識別に未確定 `Item` が必要なので推論しない。`associate Consumer.Item is i32` を書く。

| 要求の結果 → 実装の明示結果 | 判断 |
| --- | --- |
| `Output` → `f32` | `Output is f32`。出力が `Self` である必要はない |
| `Option<Item>` → `Option<T>` | 適合スコープの `T` なら `Item is T` |
| `Output` → `ref/T during source` | `source` が型の外部 Origin なら候補になる。関数の呼出し Origin なら候補にならない |
| `Output` → 関数固有の型引数 `U` | 適合へ持ち出せないので証拠にならない |
| `Output` → 未確定の `Self.Output` | 自分を確定する証拠にならない |
| 二つの要求の `Output` → `i32` と `f32` | 矛盾。数値変換を挿入しない |

既存の `Iterator` は `LentItem(step) is Item` を公開しているため、`next -> Option<LentItem(step)>` を `Option<Item>` に展開できる。`next -> Option<i32>` なら `Item is i32` を推論できる。一方、`LendingIterator` 単独の未指定 `LentItem(step)` は推論できない。

## 5. 診断・開発支援

推論不能をすべて「関連型がない」で済ませず、**証拠なし、識別に未確定関連型が必要、対応構造なし、証拠の矛盾、スコープ外 binder** を区別する。既存の未知名・重複宣言・実装候補の不足や曖昧さは、その本来の原因を保持する。

主位置は省略によって成立しない適合宣言とし、矛盾や流出する型を示す実装の戻り型、関連型の要求宣言、必要なら入力位置を関連位置にする。明示指定の誤りは引き続きその指定を主位置にする。既存コードで事実を表せるものは再利用し、新しいコードが必要なら独立した原因にだけ追加する。

CLI・JSON・LSP で同じ原因と位置を公開する。表示制限下でも関連型の識別、決められない理由、必要な明示の場所が残るようにする。独立した問題を隠さず、同じ未確定型に由来する派生エラーは既存の前提・回復規則で扱う。

型を決める根拠が足りないとき、推測した `associate` の自動修正候補は出さない。Advice で明示指定の形を示す。確定済み推論を明示化する編集は、型の合法な綴り・挿入範囲・意味不変を検証できる場合だけ構造化された修正候補にできるが、その編集機能の追加は本提案の完了条件にしない。

既存の Hover には、関連する確定束縛が推論由来であることと推論元を表示できるようにする。意味情報には同じ情報を構造化して保持し、文字列の再解析を不要にする。未検証の適合を有効として公開しない。Compiler Server Protocol 全体の新規実装は要求しない。

## 6. 実装計画

### 6.1. 入口と内部構成

[CODEMAP](../../docs/dev/CODEMAP.md) と現行実装を確認した。次の既存責務を使い、推論のために呼出し解決系を作り替えない。

| 入口 | 変更方針 |
| --- | --- |
| `Binding.cs` の `BindDeclarations`／`BindHeader`、`Binding.Constraints.cs` | 基礎情報、推論用の宣言シグネチャ、通常の確定ヘッダーという依存順を整理する |
| `Binding.AssociatedTypes.cs` の `PrepareAssociatedBindings`／`ResolveAssociated` | 未指定だが推論待ちの状態を、確定した失敗から分離する |
| `Binding.ContractMatching.cs` の `MatchesRequirement`／`CompatibleRequirement` | 既存の識別キーを共有し、推論後の通常互換性検査を維持する |
| `Binding.Contracts.Model.cs` の `BoundConformancePath` | 経路ごとに候補・束縛・根拠を保持し、条件や同名関連型を混ぜない |
| `ValidateBoundDeclarations`、`ResetPass`、`ResetContracts` | 後発の不適合、編集、再解析で推論結果と証明を失効・再利用する |

推論処理は専用の小さな型構造走査にする。呼出し側の `Binding.Calls.Infer` は Origin・length・参照読み出しなど目的の違う処理を含むため、そのまま使わない。入力キー用の `SignatureEquals` も Origin を除外するため、抽出した完全な型の一致判定には使わない。

### 6.2. ヘッダーとキャッシュの境界

現行の `BindHeader` は完了状態を、`BindType` は `syntax.BoundType` を保持する。関連型解決も証拠がない結果を保存するため、全ヘッダーを通常どおり束縛した後で推論結果だけを足す方法は採らない。

**推論用の宣言シグネチャ情報を分離し、通常の確定ヘッダーを早まって作らない方式を採る。** 名前・型構造の解決部品は共有し、別の言語規則は作らない。

1. 基礎情報を固定し、対象のない適合は従来経路で処理する。
2. 推論用情報で、対象に依存しない識別キーと宣言上の結果の必要部分を得る。依存する部分は未確定として保持し、不足診断を早期確定しない。
3. 証拠を再利用可能な一時領域へ収集・比較し、一括で束縛を補完する。
4. 通常ヘッダー・関連型形成・実装対応を完成させ、全検証を行う。未検証状態を有効な適合証明として外部に公開しない。
5. 後から witness が無効になった場合は、推論束縛に依存する projection の証明も失効させる。修正後は負のキャッシュを含めて再構築する。

基礎情報を得るための正当な依存待ちと、推論結果で推論元を増やす反復を区別する。前者の処理順は受理結果を変えてはならず、後者は言語規則として行わない。宣言重複や型形成が関連型に依存する場合も、確定後の検査を省略しない。

ローカルな宣言間では、ヘッダーの非循環依存から先に型を正規化し、最終 projection obligation を保持する。本体検証を推論の証拠収集へ混ぜず、後発の形成・witness・効果の失敗は既存の証明失効経路で利用側まで伝える。型の正規化完了と、適合の最終検証完了を同じ状態にしない。

### 6.3. 実装単位

| 単位 | 作業と完了条件 |
| --- | --- |
| U0：再現・期待値 | Vec2、通常の生成 Contract、曖昧・矛盾・有効な対照例を用意し、現在の拒否地点を確認。公開診断の期待値を実装から独立に記述し、未達の期待値は最初の実装単位とまとめる |
| U1：最小経路 | 基礎情報と未確定状態を導入し、直接の値戻り型からの推論と明示指定の優先を完成させる。再選択・本体推論を拒否する |
| U2：構造とスコープ | §3.3 の構造、完全型の一致、自由変数の流出防止、固定 family 等式の展開、generic・条件付き・refinement・継承の整合性を完成させる |
| U3：公開と横断検証 | 各経路を組み合わせた編集→失敗→修正、後発 witness 不適合、公開契約、Hover、CLI・JSON・LSP を完成させる。独立エラーと表示制限も確認する |
| U4：回帰・費用・完了 | generic dispatch と native O0/O2、割り当て・保持容量・規模測定、関連文書と例の整合性を確認し、Session Verify を通す |

U0 は準備段階であり、失敗する将来期待値だけを完成済み単位としてコミットしない。U1・U2 でも、その単位で追加する経路の診断、編集時の失効、失敗後の復元、関連する公開出力・割り当て回帰まで完成させる。U3 まで正当性の処理を先送りしない。

各実装単位は再現・実装・関連テストをそろえ、Unit Verify の成功後にその単位だけをコミット・push する。途中で残る仕様上有効な形式は、言語違反とせず Unsupported として STATUS・PLAN に境界を記録する。実装の段階化は最終的な仕様範囲を縮小する理由にしない。

### 7.2. コストと実行手順

候補識別は既存コストに従い、追加の証拠走査は対象の戻り型構造と証拠数に応じた有界な処理にする。任意の型列挙・全組合せ探索・収束までの再選択を入れない。構造共有による反復展開にも上限と再利用を設ける。

推論なしの既存経路と推論ありの経路の両方で、温まった Binding のゼロ割り当て、保持容量、失敗・修正後の再利用を確認する。既存の `ArithmeticContractTest`、`ContractBindingTest`、`ConditionalConformanceBindingTest`、`InheritedConformanceTest` の割り当て回帰を維持する。

時間測定は `src/Benchmark` に置き、宣言数・要求数・候補数・戻り型の深さを変え、明示版と推論版の初回／再解析を同条件で比較する。時間測定を通常の回帰テストに混ぜず、割り当てが失敗したときに追加 warm-up で隠さない。

- 各単位：`./scripts/verify.ps1 -Class <関連クラス> -Fixtures '<関連パターン>'`。必要な milestone だけ `-Milestone` を加える。
- セッション末：`./scripts/verify.ps1 -Mode Session`。Benchmark 変更も全 solution のビルド対象にする。
- NativeAOT は実行しない。検証中はソースを編集しない。失敗を含む証拠は `artifacts/verify/`、測定は `artifacts/benchmarks/` に残す。

完了には、仕様上の全対象、正しい位置と説明を持つ診断、編集による失効、関連 native 実行、割り当て・費用の確認が必要である。テストが通っても診断の説明に不備があれば修正・再検証する。未解決項目は対応範囲と次の作業を記録し、完了扱いにしない。

### 8.2. 採らない拡張

| 案 | 採らない理由 |
| --- | --- |
| `Output` の既定値を `Self` にする | ベクトルの内積、変換、失敗を返す演算などに合わず、別の既定値規則を増やす |
| 演算子だけ推論する／専用の Self 結果 Contract を増やす | 通常の生成・Iterator に同じ利益がある。共通規則で扱える用途に特例や Contract を増やさない |
| 出力を Contract の型引数へ移す | 適合の識別と generic API を広く変える。重複記述を省く目的に対して変更が大きい |
| 入力型の穴埋め、連鎖推論、戻り型での候補選択 | 実装識別と推論が相互依存する。追加オーバーロードや処理順の影響を説明しにくくなる |
| 本体・具体化・能力探索から推論する | 公開契約が局所的な宣言情報で決まらず、検査範囲と失効範囲が広がる |
| Property・Place・family・Function Type 内部まで一度に推論する | 操作の生成、可変性、Origin の量化・形成域・分散を同時に扱う負担が大きい。今回の主要な用途には不要 |

これらの不採用は現行の全推論禁止を維持する理由にはしない。必要な範囲を一つの宣言補完規則として追加し、その外側には従来の明示指定を残す。
