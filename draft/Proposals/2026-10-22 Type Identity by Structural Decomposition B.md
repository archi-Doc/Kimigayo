## 1. 背景

### 1.1. 現行仕様

[§8.2.3](../../docs/spec/08-generics-constraints-and-contracts.md#823-type-identity-and-identity-premises) は、スコープの型同一性の事実（完全な型を名指す `X is U` と関連型の指定）を含み、型の内部（射影を含む）での置換で閉じた最小の同値関係によって、型を同一性クラスに分ける。

- `X is U` は型の同一性で、変換を意味しない。
- 同一性は分解しない。`T is Option<U>` と `T is Option<i32>` から `U is i32` は出ない。
- 同じクラスなら Proven。両側が完全束縛されて異なるとき、または否定の前提があるときだけ Refuted。他は Unknown（§8.3.2）。
- 宣言の誤りは、一つのクラスに異なる完全束縛型が二つある場合と、型が自分を真部分に含む場合だけ。他の矛盾する証拠は、直接得られるか問い合わせた命題についてだけ Error（§8.3.2）。条件付き適合は満たす型がなくても検証し（§8.8.2）、Refuted な前提の条件付きメンバーは不適用になる（§7.5）。
- 型の形は規則ごとに列挙される。衝突検査（§8.9.1 手順 2）と重なり判定（§7.4）は名義型・タプル・Function Type・確定した Semantics の適用を単一化し、抽出（§8.5.5）は名義型・タプル・確定した Semantics の層をたどり、Function Type には入らない。
- 関連型の指定に複数の同一性原子があれば §8.2.3 に従い、完成した型は指定のすべてを満たす（§8.5.1）。原子が入力どうしの同一性を含むとき、それを前提とするか義務とするかは読み方が分かれる。

### 1.2. 問題

- 一つのクラスに `Option<U>` と `Option<i32>` が並び、型全体を同一視しながら成分を区別する。クラスを一つの形で表せず、`Array<V> is Option<i32>` のような明らかな不一致も Unknown になる。
- Contract の制約は導出された主語や再帰する主語にも適用される（§8.3.2、§8.5.3）。現在の実装は書かれた修飾ごとに前提を展開するので、証明が綴りに依存する（PLAN G170: `T.(Tree).Child.(Tree).Child is Copy` が Unknown）。需要駆動の解法（[PlanB](2026-10-20%20G170%20Premise%20Dependencies%20and%20Inference%20PlanB.md) の案 C、単位 C1）は同一性の扱いで四回の独立レビューを通らなかった。非分解則はその一因である。

## 3. 新しい仕様

`A ≡ B` は説明用の記号で、構文ではない。

### 3.1. 同一性の根拠と関係

**根拠。**

- 利用可能な正の同一性前提 `X is U`。`and` から連言消去で取り出したものと、外側の宣言の入力を含む。
- `T is C` が与える Contract の制約と関連型宣言の要件（§8.3.2、§8.5.3）。問い合わせで初めて必要になった深い射影にも、綴りと同一性の経路によらず適用する。宣言時に列挙した有限個の射影だけを意味としない。
- 利用可能な完了済みの関連型束縛（本書 3.5）。

`or`・`not` を含む原子、本体、呼出し、実体化、義務（宣言中の型自身の適合など）は根拠にならない。適合する型の関連型の指定は本書 3.7 に従う。

**関係。** 型同一性は、根拠を含み、反射・対称・推移、型の内部（射影の主語と Contract 引数を含む）での置換、本書 3.3 の分解で閉じた最小の関係である。

- 入力の左右、前提の記述順・向き・綴り、検査と問い合わせの順は意味を変えない。
- 型パラメーターは宣言に束縛された一つの型を表し、任意の型に一致するパターンではない。
- 同一性は変換・サブタイプ・Copy・適合ではない。同一な型の既知の能力は、通常の証拠供給で使う。
- 矛盾から任意の同一性を導かない（本書 3.10）。

### 3.2. 構造表

比較の前に、別名、括弧、冗長な `owner/`、利用可能な完了済み射影を既存の規則で解釈する。名前の綴りではなく束縛先の宣言を使う。抽象型以外の行の型を**構築型**と呼ぶ（struct・enum の `Self` を含む）。

| 形 | 頭部 | 分解する成分 | 比較だけの属性 |
| --- | --- | --- | --- |
| 原始型、Never | 型そのもの | なし | なし |
| 名義型（struct、enum、ライブラリー型、入れ子の型。`Wrapping<T>` を含む） | 宣言（外側の宣言を含む） | 自身と外側の宣言の型引数。未使用の引数も含む | Origin（`during`、束縛集合） |
| タプル（Unit は要素数 0） | 要素数 | 各要素 | なし |
| 固定配列 `[N of E]` | 固定配列 | `E` | 長さ（§4.4.2 で正規化） |
| Semantics の層 `k/V during o`（`owner/V` は `V`） | `k` | `V` | `o` |
| ペアバインダーの適用 `s/V during o` | 許容集合が一つの `k` ならその `k`、他は未確定（同じ `s` の適用どうしは同じ頭部） | `V` | `o` |
| 共通 Function Type | task スロットの有無、パラメーター数 | パラメーター型、結果型 | Origin（量化構造: 量化された Origin の数と、パラメーター・結果での出現位置と関係。改名は同一性を変えない。固定 Origin） |
| Function Item、具体的なクロージャー | 関数宣言、クロージャー式の出現 | 同一性に含まれる実体化の型引数 | 実体化の長さ引数と Origin |
| 抽象型（型パラメーター、ペア対象、Contract の `Self`、未解決の射影） | なし | なし | なし |

- 名義型のフィールド、クロージャーのキャプチャー、メソッド集合は分解しない。異なる宣言の型は、構造・レイアウト・値の有無が同じでも同一でない。Function Item・クロージャーと共通 Function Type の間の変換は同一性でない。
- 抽象型は頭部を持たない。束縛、完了済み射影、許容集合で形が確定したときに、その形を使う。
- **ペアバインダーの適用。** 頭部が未確定のとき、他の形と異なる（Refuted）のは、許容集合（§8.3.4）が相手の外側の Semantics（Semantics の層でない型では `owner`）と交わらないときだけである。`owner` を含む許容集合では `s/V` が `V` そのものになりうるので、どの形とも交わる。
- **量化された Origin。** Function Type の中で量化された Origin は、その Function Type の中でだけ対応し、外側の型と同一にならない。Function Type 全体を結び付け、内部の量化を保つことはできる。
- 実行時 Contract ビュー（§8.12。この版では形成できない）の対象は、Contract 宣言を頭部、型引数と公開された関連型束縛を成分とする。

この表を、分解（本書 3.3）、Refuted、前提の誤り、循環（本書 3.6）、衝突検査（§8.9.1 手順 2–4）と重なり判定（§7.4）が使う。抽出（§8.5.5）もこの表の成分をたどるが、入る範囲は現行どおりとする（Q2）。

### 3.3. 分解と Refuted

頭部が同じと確定し、比較だけの属性の一致が証明された二つの構築型を `F<A1, …, An>`、`F<B1, …, Bn>` と書く（成分だけを示す）。

```text
F<A1, …, An> ≡ F<B1, …, Bn>  ⇔  各 i について Ai ≡ Bi
```

- 右から左は現行の置換、左から右が新しい分解則である。直接の前提にも、推移的に得た同一性にも、関連型束縛にも同じ規則を使う。
- 命題としては、頭部が同じ二つの構築型の同一性を、比較だけの属性の一致と各成分の同一性の連言と同じ命題とする（§8.3.1 の命題の正規化に加える）。Proven・Refuted・Unknown は §8.3.2 の連言の規則で決まる。
- 同じ型に複数の束縛があっても、先や後の束縛を優先しない。すべてを同じ関係に入れる。

**Refuted。** 同一性の命題は、未束縛の型引数があっても、次のとき Refuted である。

1. 対応する位置で頭部が確定して異なる、または比較だけの属性が確定して異なる（定数の長さ、Function Type の量化構造）。
2. 対応する成分の同一性が Refuted である。
3. 一方が他方の真部分と同一である（本書 3.6。`owner` を含む許容集合のペアバインダーの適用だけを通る場合を除く）。

命題を前提に加えて矛盾を探すこと（背理法）では Refuted を得ない。未解決の射影や異なる型パラメーターは、見た目が違うだけでは Refuted にしない。否定された複合型の同一性から、どの成分が異なるかを選ばない。

### 3.4. 比較だけの属性

分解は、Origin の関係、長さの等式、Semantics の許容集合を新たに作らない（Explicit Semantics）。二つの構築型を同一とする前提では、比較だけの属性とペアバインダーの頭部の一致を、宣言の利用可能な前提と各領域の規則（Origin は §15.6.5、長さは §4.4.2、Semantics は §8.3.4）で証明する。この証明は、結び付けるその同一性に直接にも間接にも依存しない。

- `[4 of U]` と `[(2 + 2) of i32]` は長さが正規化で一致し、`U ≡ i32` となる。`[N of U]` と `[M of i32]`（`N`、`M` は長さスロット）からは `N = M` を作らない。
- `ref/U during a` と `ref/i32 during b` は、`a` と `b` の一致が証明されれば分解する。一方向の `outlives` では足りない。
- `s is ref or uniq` のもとの `s/U` と `ref/i32 during a` は、Semantics の一致が証明されない。

一致が未証明であることは、不一致の証明ではない。問い合わせでは Unknown、前提としては未証明要件（本書 3.10）とする。判定には宣言の独立した全前提を使い、記述順の途中で拒否しない。

- Semantics ケースごとに満否が変わる前提も、未証明要件とする（新しい規則。ケースごとの前提は不健全: [SETTLED](../../docs/SETTLED.md#pair-slot-premises-in-every-semantics-case)）。
- Function Type の外の `T is ref/U` のように、制約の中の型の層で省略した Origin の補完は §15.4.2 に行がなく、本案もそれを定めない（仕様の不足）。Function Type のパラメーターには §15.4.2 のパラメーターの規則を当てはめる（`escape`）。

### 3.5. 射影

射影 `X.(C).A(o)` の同一性は、主語、関連型の宣言、束縛済みの定義元 Contract、Origin 引数で決まる。継承経路や同じ名前だけで別の関連型を同一視しない。

- 同一な主語・Contract 引数・Origin 引数への同じ射影は同一である。
- 射影の結果が同一でも、主語・Contract 引数・Origin 引数の同一性は導かない。Contract の引数も分解しない。`T is K<U>` と `T is K<i32>` は二つの適合で、`U` と `i32` を関係づけない。
- 構築型の射影は、その型の宣言された適合（明示、継承、親 Contract 経由、条件付き）の束縛に、型引数と Origin 引数を代入した型である。主語が構築型と同一なら、その射影も同じ型に解決し、結果が構築型なら通常の分解に加わる。束縛の利用には、その適合経路の前提が必要で、条件付き適合の束縛を別のスコープへ無条件に持ち出さない。
- Origin 引数の異なる適用（`I.LentItem(a)` と `I.LentItem(b)`）は同一視せず、その同一性は Unknown である。Contract が束縛を与えればそれに従う（Iterator の `LentItem(step) is Item` により、どの `a` でも `I.LentItem(a) ≡ I.Item`）。
- ペア対象の同一性から、元の完全な型や外側の Semantics を逆算しない。

### 3.6. 循環

型の**真部分**は、構築型（頭部が未確定のペアバインダーの適用を含む）の分解する成分を一段以上たどって得る型である。同一性による置換を考慮し、射影の主語や引数、名義型のフィールドはたどらない。

- 型が自分の真部分と同一になる前提は、前提の誤り（Language）である。
- `owner` を含む許容集合のペアバインダーの適用だけを通る循環は、`s` が `owner` のときだけ満たせるので、未証明要件とする。

`T ≡ U ≡ T` は同一視、`T ≡ Option<T>` は誤り、`T ≡ T.(C).X` と `T ≡ Option<T.(C).X>` はそれだけでは誤りでない。後者は、さらに `T.(C).X ≡ T` が得られれば誤りになる。再帰する名義型のレイアウト、Contract の再帰、証拠の自己依存は既存の規則に従う。

### 3.7. 関連型、適合、推論

- **関連型の指定。** 適合する型の指定 `associate C.X is R` の同一性原子と、Contract と祖先の同一性制約は、その定義の未決定の関連型を決めるため（分解を含む）にだけ前提として使う。それ以外の帰結、つまり未決定の関連型を含まない型どうし（入力どうし、入力と具体型など）の同一性は、適合の義務として検査し、仮定しない。
- **適合と証拠。** 同一な型についての Contract の事実は、その根拠が使えるスコープで使える。構築型と同一な型への適合前提も、そのスコープの証拠になる（現行どおり。Q1）。同一性は新しい適合宣言やメンバーを作らず、名前探索は既存の規則に従う。
- **推論。** 凍結前提（§8.5.5）には、上の範囲で分解の帰結を含める。現在の定義で推論した値、またはそれに依存する証拠を、その定義の推論へ戻さない。抽出、実装の識別、呼出しの型引数推論はそれぞれの規則を維持する。

### 3.8. 他の規則への影響

- **条件付き適合と条件付きメンバー**（§8.8、§7.5）: `when P` と条件付きメンバーの前提の同一性原子は、そのスコープの前提として分解に加わる。§8.2.3 は今も条件の完全束縛型の衝突を誤りとしており、本書 3.10 の前提の誤りも同じスコープで検査する（§8.8.2 の「満たす型がなくても検証する」からは除く）。使用時の `P` は頭部の違いで Refuted になりうるので、Unknown だった判定が「不適用」「この経路からの適合なし」に確定することがある。
- **衝突検査と重なり判定**（§8.9.1、§7.4）: 衝突検査の手順 1 の正規化に分解の帰結が加わり、非衝突を証明できる組が増える。手順 2–4 と重なり判定は構造表の頭部と成分を使い、重なり判定は現行どおり Origin（量化構造を含む）を無視する。比較だけの属性（定数の長さを除く）、射影、頭部が未確定のペアバインダーの適用は残余条件のままである。
- **オーバーロード**（§10.1、§10.4）: 分解で導いた同一性は、書かれた同一性前提と同じく、候補の適用可能性と比較に影響する。

### 3.10. 前提の誤り、報告、診断

**前提の誤り。** 宣言の前提について、次を誤りとする。

| 誤り | 区分 | 例 | 修復候補 |
| --- | --- | --- | --- |
| 構造の衝突: 前提で同一とされる型の同一性が Refuted（量化された Origin を外へ持ち出す同一性を含む） | Language | `conflict`、`escape`、`Either` | 前提を除く |
| 真部分の循環（本書 3.6） | Language | `cyclic` | 前提を除く |
| 比較だけの属性の一致が証明されない | Proof（未証明要件） | `otherView`、異なる長さスロット | `origin a == b`、同じ長さスロット |
| Semantics で満否が変わる前提（ペアバインダーの頭部の一致、`owner` を含む適用だけを通る循環） | Proof（未証明要件） | `s/U` と `ref/i32 during a`、`loopy` | `s is ref`、`s is owner` |

他の矛盾する証拠（前提が与える適合が閉世界で Refuted になる、`not P` の前提のもとで `P` が Proven になるなど）は、現行どおり直接得られるか問い合わせた命題について Error とする（Q4）。

**報告位置。** 上の誤りは、それを生む前提が初めてそろう宣言で一度報告する。Contract の制約だけから生じるものはその Contract で、Contract の連言や他の前提を要するものはその制約付き宣言（関数、型、条件付き適合のスコープ、条件付きメンバー）で報告する。使用箇所では報告し直さない。

**Resource。** 上限に達しても、それまでに得た同一性は正しいので、それによる Proven と Error は残る。上限に達した解析の結果に依存する Refuted・Unknown の判定だけが Resource になる。上限は達した宣言で一度報告し、それに依存する宣言の Resource はそれに関連づける（§23.1.2）。上限の値と数え方は IMPL が定める。結果は検査順に依存しない。

**診断。**

- 誤りは、衝突した構造や循環と、それを結び付けた元の前提の位置を示す。未証明要件は不足した要件を、Resource は達した上限と対象位置を示す。
- 診断と hover は記述どおりの型を示し、同一性を使った判断では、同一と判断した型と導出の源（前提、制約、分解、射影の解決）を併記する。表示する型の選び方は意味を持たない。結果は対象のソースと設定に関連づける。
- 修復候補は前提条件と保証を持つ（§23.1.3）。Unknown の同一性には、その同一性を前提に加える候補を示す。前提条件は、それが Refuted でなく前提の誤りを生まないこと、保証は、要求が Proven になり呼出し側がそれを証明することである。前提を加える・除く修復は §23.3 のスキーマの種類にないので、種類を加える。

## 4. 例

本案での結果であり、現行コンパイラーでの実行結果ではない。各例は独立して読む。ただし `Source` は §8.4.1、`Linked` は本書 4.2 の宣言とする。「（変更）」は現行と結果が異なることを示す。

### 4.1. 分解

```kimi
func same<T, U>(value: U) -> i32
    T is Option<U>
    T is Option<i32>
    return value                    // 有効（変更）: U は i32。

func tuplePart<T, U>(value: U) -> i32
    T is (U, bool)
    T is (i32, bool)
    return value                    // 有効（変更）

func arrayPart<T, U>(value: U) -> i32
    T is [4 of U]
    T is [(2 + 2) of i32]
    return value                    // 有効（変更）: 長さは正規化で一致する。

func functionPart<F, U>(value: U) -> i32
    F is (U) -> U
    F is (i32) -> i32
    return value                    // 有効（変更）
```

`same` の前提のもとで `show(value@move)` は、`func show(value: i32)` と `func show<V>(value: V)` のうちジェネリックでない前者を選ぶ（§10.4。変更、現行は後者）。

### 4.2. 不一致、Refuted、矛盾する証拠

```kimi
func conflict<T, U>(value: T) -> i32
    T is Option<U>
    T is Array<U>                   // エラー（変更）: 異なる名義型を同一視している。
    return 0

contract Flag

struct Either<A, B>
    Self is Flag when A is Option<B>, A is Array<B>  // エラー（変更）: 条件の構造が衝突する。
    var value: A

struct Slot<T>
    Self is Flag when T is Option<i32>
    var value: T

func plain<T>(value: T) -> i32
    T is not Flag
    return 0

func fill<V>(slot: Slot<Array<V>>) -> i32
    return plain(slot@move)         // 有効（変更）: 条件 Array<V> is Option<i32> は Refuted（現行は Unknown）。

contract Linked
    associate Next

func optional<T>(value: T) -> i32
    T is Linked
    T is Option<T.(Linked).Next>    // エラー（現行どおり）: 射影が T is Linked を問い合わせ、Option<…> is Linked は閉世界で Refuted。
    return 0
```

### 4.3. 射影と循環

```kimi
func independent<T, U>(left: T, right: U) -> i32
    T is Source
    U is Source
    T.(Source).Element is U.(Source).Element
    return 0                        // Element は同一だが、T と U の同一性は導かれない。

func cyclic<T, U>(value: T) -> i32
    T is Option<U>
    U is Option<T>                  // エラー（現行どおり）: T が自分を真部分に含む。
    return 0

enum Cell<E>
    Self is Linked
    associate Linked.Next is E
    Item(E)
    Empty

func reconstructed<T>(value: T) -> i32
    T is Linked
    T is Cell<T.(Linked).Next>      // 有効（現行は読み方が分かれる）: T.(Linked).Next は自身に解決する。
    return 0
```

`T = Cell<i32>` は `reconstructed` の前提を満たす。`T.(Linked).Next = i32` であり、型の構造に `T` 自身は現れない。

### 4.4. Origin、Semantics、量化

```kimi
func sameView<T, U>(first: ref/U during a, second: ref/i32 during b, item: U, value: T) -> i32
    T is ref/U during a
    T is ref/i32 during b
    origin a == b
    return item                     // 有効（変更）: Origin が一致し、U は i32。

func otherView<T, U>(first: ref/U during a, second: ref/i32 during b, value: T) -> i32
    T is ref/U during a
    T is ref/i32 during b           // エラー（変更）: a と b の一致が証明されない。修復候補 origin a == b。
    return 0

func escape<F, V>(value: F) -> i32
    F is (V) -> ()
    F is (ref/i32) -> ()            // エラー（変更）: 量化構造が異なり Refuted。V は呼出しごとの Origin を持てない。
    return 0

func loopy<s/T, U>(value: s/T, item: s/U during a) -> i32
    s is owner or ref
    U is s/U during a               // エラー（変更）: s が ref なら満たせない。修復候補 s is owner。
    return 0
```

### 4.5. 関連型の指定

```kimi
contract Wrapped
    associate Inner
    associate Outer is Option<Inner>

struct Number
    Self is Wrapped
    associate Wrapped.Outer is Option<i32>      // 有効（変更）: 分解で Inner は i32 に決まる。

contract Holder
    associate Item

struct Pack<T>
    Self is Holder
    associate Holder.Item is Option<T> and Option<i32>  // エラー: T ≡ i32 は義務で、証明できない。
```

`Pack` は現行では読み方が分かれる。`Self is IntSource`（§8.5.3）と `associate Source.Element is T` の組も、`T ≡ i32` を仮定できないので同じく誤りになる。

### 4.6. 綴りによらない Contract の前提（G170）

```kimi
contract Tree
    associate Child is Tree

contract CopyTree: Tree, Copy
    Self.(Tree).Child is CopyTree

func twice<T>(value: T.(Tree).Child.(Tree).Child) -> (T.Child.Child, T.Child.Child)
    T is CopyTree
    return (value, value)           // 有効（現行どおり）: 孫も綴りによらず CopyTree で、Copy。
```

## 5. 結果の変化

| 区分 | 内容 |
| --- | --- |
| 有効になる | 分解の帰結（`same`、`tuplePart`、`arrayPart`、`functionPart`、`sameView`、`Number`）。頭部の違いによる Refuted（`fill`、衝突検査の非衝突、`not` 要件） |
| エラーになる | 構造の衝突（`conflict`、`escape`。`when` 条件（`Either`）、条件付きメンバーの前提、Contract の制約にあるものを含む）。比較だけの属性が証明されない前提（`otherView`、異なる長さスロット）。Semantics で満否が変わる前提（`loopy`）。入力を同一視する指定（`Pack`。現行は読み方が分かれる） |
| 結果が変わる | オーバーロードの比較（本書 4.1） |
| 変わらない | `twice`、`independent`、`cyclic`、`optional`。`reconstructed` は有効（現行は読み方が分かれる） |

## 6. 未決事項

### 6.1. 意味の選択

| 番号 | 問い | 選択肢と理由 | 推奨 |
| --- | --- | --- | --- |
| Q1 | 構築型と同一な型への適合前提を証拠にするか | 本案: 現行どおり証拠にする。Conformance Identity により束縛は一つに決まる。G′: 宣言から証明できなければ未証明要件にする（`T is Option<U>` と `T is Copy` に修復候補 `U is Copy`）。適合の源は宣言だけになるが、複数の経路の条件の選言は書けなくなる | 本案 |
| Q2 | 抽出（§8.5.5）を Function Type に入れるか | 本案: 入れない（推論は別の規則）。G′: 入れる（`func apply(self) -> (i32) -> i32` の実装から `Input is i32`）。呼出しごとの Origin を含む抽出はどちらでも使えない | 入れない。§8.5.5 の改訂として別に扱う |
| Q3 | 「依存する」（§8.5.5、§8.3.3）を、現在の定義で推論した値をすべて保留しても同じ値に決まるか、で定めるか | 分解で証拠が増え、依存する証拠としない証拠が両方ある関連型が生じる。保留で読めば決まり、導出の記録で読めば決まらない | 採用する。受理を導出の記録から独立させる |
| Q4 | 満たせない前提をすべて宣言で報告するか | 本案: 同一性から生じる誤り（本書 3.10）だけを宣言で報告し、他は現行どおり。G′: 前提の適合が閉世界で Refuted になる場合（`T is Array<U>` と `T is Copy`）、`not P` の前提と Proven な `P`、満たせない `when` 条件と条件付きメンバーの前提も宣言の誤りにする（§8.8.2 と §7.5 を改める）。別案は、使われない宣言として警告に留める | 本案。受理の変更を同一性から生じる誤りに限る |

### 6.2. 決定可能性

G′ の決定手続き（前提を宣言ごとに一度閉じ、使用箇所では正規化と比較だけを行う）は、閉包を有限にするため次の選択を要する。どれも受理されるプログラムを変えるので、実装方式ではなく SPEC の規則として決める。本書 3 の規則はどの選択とも両立する。Q5・Q6 を採らない場合、該当する宣言は有効で、判定が上限に達すれば Resource になる。

| 番号 | 問い | 補足 |
| --- | --- | --- |
| Q5 | 拡大する再帰を誤りにするか。互いに参照する Contract の循環で、束縛（外側の宣言の束縛を含む）が大きくなるもの（`associate Inner is Nest<Option<A>>`） | 先例は §8.9.2（親 Contract の経路）。失うのは、具体型が適合できない Contract の抽象的な使用だけ |
| Q6 | 展開が限りなく深くなる型を誤りにするか（`associate Next is Stream` と `Self.(Stream).Head is Option<Self.(Stream).Next.(Stream).Head>`、射影の引数を通る循環 `T is Option<U.(K<T>).X>`） | `Stream` に適合できる具体型はない。射影の引数を通る循環は満たせることがあるが、まれである。本書 3.6 ではどちらも循環でないので、新しい規則になる |
| Q7 | 経路等式（`Self.A.B.A is Self.B.A.B` のように、主語からの二つの射影の列を結ぶ同一性）を禁止して Appendix D に送るか、残して上限で扱うか | 経路等式は Contract の連言からも導かれる。残すなら、上限に達するかは宣言の名前で変わりうる（検査順では変わらない）ので、本書 3.1 の綴りへの非依存に例外を加える |

推奨: Q5・Q6 を採用し、Q7 は経路等式を残す。

## 7. 評価

### 7.1. Kimigayo Principles

| 原則 | 本案の判断 |
| --- | --- |
| One Concept, One Canonical Form | 型同一性を一つの関係とし、直接の前提・推移的な同一性・関連型束縛に同じ分解則を使う。型の形は一つの構造表で決まる |
| Local Reasoning | 帰結は宣言の前提と型の構造から読め、前提の向き・順序・綴りに依存しない（Q7 の Resource の有無を除く）。前提の誤りは前提がそろう宣言で一度報告する（本書 3.10） |
| Explicit Semantics | 同一性・変換・適合・推論・循環・解析未完了を区別する。Origin・長さ・Semantics の関係と、関連型の指定による入力の同一性を仮定しない |
| Compiler Server Protocol | 誤り・未証明・上限を区別し、元の前提、導出の源、前提条件と保証のある修復候補を示す（本書 3.10） |

本案は、型全体を同一視しながら成分を区別する規則をなくす。証拠の依存関係や Contract の導出を省く変更ではなく、実装量や性能の改善を保証しない（未計測）。

### 7.2. 採らない案

| 案 | 理由 |
| --- | --- |
| 現行（分解しない） | 本書 1.2 |
| 案 G（記述方向をそのまま書き換え規則にし、宣言時に一度ですべて完備化し、射影を通る自己参照を一律に Resource とする。G′ 6.3 で比較） | 前提の向きが意味を持ち、有効な `reconstructed` を Resource にし、再帰 Contract で主語ごとの規則が無限になる |
| 射影や Contract 引数の分解 | 不健全（`independent`） |
| 分解で Origin・長さ・Semantics の関係を導く | 書かれない前提を作り、Semantics ケースごとには不健全 |
| 命題を加えた矛盾で Refuted を判定する | 背理法で、使用箇所に前提の閉包が要る |
| 構築型の主語（`Option<U> is Option<i32>`）を書けるようにする | `U is i32` の二つ目の綴りになる |
| G′ の決定手続き（正規形、代表の順序、完備化）を仕様に書く | 内部表現の選択である。手続きに伴う言語の制限は Q5–Q7 で決める |
