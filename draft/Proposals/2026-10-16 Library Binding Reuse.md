# 埋め込みライブラリーのBinding結果の再利用

日付: 2026-10-16

状態: 設計案。変更内容の提案だけで、実装と実行検証は行っていない。プロジェクト所有者の判断待ち（本書§1.3）。

基準: `4cbb3499`（`dev`）。テスト全体の計測は`4cbb3499`（割当て計測の標準窓`ed55d90a`を含む）と`6497288e`（含まない）、コミット間の比較は`c548993f`（9/30）・`2bf8e74f`（10/7）・`6497288e`（10/16）で行った。2つの独立設計（付録A）をまとめた。計測データ、計測用コード（`Binding.Probe.cs`）、独立設計の原文は`artifacts/benchmarks/20261016-library-binding-profile/`にある。

## 1. 概要

### 1.1. 変更内容

埋め込みKimiライブラリー（31ファイル、2,109行）は、コンパイルのたびに構文解析される（トークンはプロセス内で共有済み）。Bindingのパスごとには、ライブラリー全体の索引付け・宣言と本体の束縛・検証がやり直される。ライブラリーの事実（本書§3.1で定義）の大部分はユーザーのプログラムに依存しないと考えられるが（仮説。例外は本書§3.1）、パスごとに捨てられ、作り直されている。次の3段階でこの重複をなくす。

1. **今（任意）:** Binding内部で、ライブラリー宣言あたりの定数コストを計測に基づいて下げる（本書§4のC）。
2. **R6とR7の後:** 事実をモジュールごとの寿命で保持し、1つのコンパイル内ではライブラリーを一度だけ束縛する（本書§4のA）。
3. **段階2の後（プロジェクト所有者の判断）:** ライブラリーをプロセス内で一度だけ構文解析・束縛した**束縛済みライブラリー層**とし、全コンパイルが読む（本書§4のP）。

### 1.2. 理由と優先順位

- **計測（本書§2）:** 現在の`dev`では、テスト時間の87.5%がBindingに費やされている。ユーザーのソース本体の束縛は0.4%にすぎず、残りの大部分はライブラリーの処理と推定される。LSPは検査のたびに新しいコンパイルを作り（`CheckService.cs:10-14`、`Project.cs:404-410`）、同じコストを毎回払う。1回のコンパイルの割当て量は、9/30から10/16の間に54%増えた（同じ期間にライブラリーは41%増）。R8でライブラリーはさらに増える。
- **一貫性:** ライブラリーの事実は、1つの所有者が1つの表現で一度だけ決める。いまは寿命の区別がなく、ライブラリーが固定であることは消費側の例外`IsLibraryDeclaration`にしか表れていない。
- **短さ・速さ:** 段階2と3で、パスごと・コンパイルごとのライブラリー処理（`Restore`、`IndexLibrary`、ライブラリー本体のループ、コンパイルごとの構文解析と番号付け）が消える。

### 1.3. 必要な判断

プロジェクト所有者の判断が必要なもの:

- **目標と順序の採用:** 段階2をR6とR7の後に、段階3を段階2の後に置く。採用する場合、PLANの未解決課題とR7の段階台帳に記録する（本書§7）。R7の範囲には、Kotoキーの表の移行に加えて、**シンボル・型・呼出し計画をキーにする表の寿命による分割**を足す（本書§3.2）。
- **段階1を今行うか:** 単独の計測ではパス単価の退行は確認できなかった（本書§2.4）。効果は定数倍の改善に限られ、R7で統合されるBindingのコードを変えるため、手戻りのおそれがある。
- **段階3の契約の反転:** 「ライブラリーはコンパイルごとに別の状態を持つ」という現在の契約（`CoreCatalogTest`、`HoverCollectionTest`、`KimiLibrarySources.cs:11-12`の注記、Library README:73-77、CODEMAPの「Hover collection」の行）を反転する。

不要なもの:

- 閉じた語彙とその上限の変更。
- SETTLEDの再開。ライブラリーの共有、`ResetPass`、増分再束縛を扱う項目はない。
- DECISIONS R4-M12の変更。これは維持し、ライブラリー本体のMIRは段階3でも各コンパイルで作る。この費用は未計測で、Pでは減らない（本書§5.1）。

## 3. 設計の連鎖

### 3.1. 要求される意味

ここでいう**事実の寿命**は、Bindingが求めた事実が有効なままでいる範囲（パス、コンパイル、プロセス）を指す。仕様の値の寿命とは関係しない。

ライブラリーの事実の大部分は、ライブラリーのテキスト、コンパイラーのビルド、Bindingの設定K（ポインター幅、ドキュメントとホバーの収集）とパスのモード（Provisional / Final）だけで決まり、ユーザーのプログラムに依存しないと考える（仮説。例外は表に示す）。根拠:

- ライブラリーのスコープには親がない（`KimiLibrary.cs:21`）。ユーザーのコードは既定の別名`Kimi`を通してだけライブラリーに届く（`Binding.Imports.cs:39-44`）。
- 適合は型自身の宣言の中だけで宣言され、外部登録はない（§8.6.1、§8.8）。インスタンス化は適合を検証せず（§8.6.1）、インスタンス化で推論は走らない（§8.5.5）。特殊化は元の宣言のKotonohaに属する（§8.13）。
- `709faaba`はライブラリーの適合を「固定」として扱い始め、R1c-3（`a8096e75`）はライブラリーの形の検証をコンパイルごとから`KimiLibraryShapeTest`に移した。

事実の寿命は、入力の寿命のうち最も短いものとする。

| 事実 | 寿命 |
| --- | --- |
| テキスト、トークン | プロセス（共有済み） |
| 構文木、モジュール内のSyntaxId | ライブラリーの構文版Vごと |
| シンボル、スコープ、ヘッダー、`AdtDef`、Contract、制約環境、本体の束縛結果、HIR列、ライブラリー自身の適合と証人の行、Originの原子・関係・要求 | (V, K)ごとに不変と考える。いまは毎パス作り直している |
| ライブラリーのモジュール序数 | ソースモジュールの数で決まる（ユーザーに依存する項目の1つ） |
| `#LibraryImport`の最終シンボル表（IMPL §21.2）、`LibraryImports`の並び、署名キャッシュ | パスごと（ライブラリーとユーザーの宣言の組で決まる） |
| 旧経路の破棄効果の検証による、ライブラリーの適合経路などの無効化（`Binding.EffectBounds.cs:34-56`） | パスごと（解析が到達した本体で決まる）。R6で削除 |
| パスのモードで変わる証明の結果（Provisionalでは未決、Finalでは反駁。`Binding.Capabilities.cs:196,403`、`Binding.ConditionalConformances.cs:319,363`、`Binding.Constraints.cs:857`、`Binding.Contracts.cs:338`） | パスごと。ライブラリーを常にFinalで束縛するか、モードを寿命の鍵に含める（S2bで決め、L1に記録） |
| インスタンス化、ユーザーの型引数を持つContract参照、ユーザー型の適合、クロージャーの型、到達するライブラリー本体 | パスごと（ユーザー側の事実） |
| ライブラリーの診断 | ライブラリーを拡張するテストとユーザーのインポートとの衝突を除いて空。空でなければコンパイラーのビルドの欠陥 |

`#LibraryImport`の例: `ValidateLibraryImports`（`Binding.Attributes.cs:71-166`）は、ソースのノードを先、ライブラリーのノードを後にたどり、1つの最終シンボル表を使う。ユーザーが物理型の違う同名のインポートを書くと、ライブラリー自身のインポート（`Windows.kimi:4`）が`ConflictingImportSignature`になり、`LibraryImports`（`EmissionArtifacts.cs:141`、`LlvmEmitter.cs:142`が読む）から落ちる。

開いている提案「2026-10-10 Contract Requirement Bodies and External Conformance」（外部適合と要件本体）が取り込まれると、§8.6.1の前提が変わり、この分類を見直す必要がある。

### 3.2. 表現に足りないもの

1. **寿命の区別:** `ResetPass`はパスの事実をすべて捨てる（`Binding.cs:319-388`）。ソースの編集でもライブラリーの事実が捨てられる（`Binding.cs:179-194`）。
2. **ライブラリーが固定であることを知る場所:** いまは2つの検証にある消費側の例外`IsLibraryDeclaration`（`Binding.Contracts.cs:795-818`、`Binding.Constraints.cs:385-389`）だけである。
3. **Kの記録:** ポインター幅はBindingで23箇所読まれる（`Binding.Conversions.cs`、`Binding.Expressions.cs`、`Binding.Lengths.cs`、`Binding.Patterns.cs`、`Binding.PositionWarnings.cs`など）。
4. **どのコンパイルにも属さない置き場所:**
   - `KimiLibrary`はコンパイルごとの識別を持つ（`KimiLibrary.cs:11,20`）。79箇所の`CodeContext.Compilation`の参照が、ライブラリーのノードを1つのコンパイルに結び付けている。
   - シンボルはパスごとの可変状態を持ち、`TyCtxt`はBindingごとにある。
   - Bindingのコレクション型のフィールドは約250個あり、そのうち106個がKoto（構文ノード）をキーにする。R7はこのKotoキーの表をSyntaxId列に移す（COMPILER_ARCHITECTURE「No Koto-keyed dictionary…」）。
   - 約30個の表はシンボル・型・呼出し計画をキーにし、ライブラリーとユーザーの行が混ざる（`conformances`、`conformancesByType`、`instances`、`associatedInference`、`defaultCalls`、`comparisonPlans`、`requirementCalls`、`specializationsByOriginal`、`overrideEntries`など）。R7の移行だけでは、これらは寿命で分かれない。
   - パスごとの`storageVersion`で印を付けたメモがある（`Binding.cs:324`、`Binding.Storage.cs:33,307`、`Binding.ComparisonPlans.cs:20`、`Binding.Formatting.cs:63`、`Binding.Structs.cs:63`、`Binding.Hir.cs:37`、`AdtDef.Version`）。
5. **ユーザーに依存しない識別:** ライブラリーの序数はソースモジュールの数で変わる（`Binding.cs:102`、`SyntaxTable.cs:48,90-92`、`SourceRef.cs:24`）。

### 3.3. 所有コンポーネント

- Bindingのパス駆動（`Binding.Bind`、`ResetPass`）が事実の寿命を決める。
- `KimiLibrary`がライブラリーの識別、構築、Kを持つ。段階3では「ライブラリーを束縛する」責務がパス駆動から`KimiLibrary`に移り、束縛済みライブラリー層を構築し、完全性を確かめて読み取り専用で公開する。この移動はL3（本書§5.3）に記録する。
- Syntaxが序数を持つ。HIRの公開、MirBuilder、SemanticQuery、旧経路は読むだけで、何も決めない。

### 3.4. 共有する表現と操作

- 規則: **モジュールの事実は、そのモジュールの構文版、依存先モジュールの版、K、パスのモードのいずれかが変わったときだけ作り直す**（ライブラリーを常にFinalで束縛するなら、ライブラリーではモードを除く）。ライブラリーは依存先のないモジュールに当たる。この規則はPLAN T4「Verified semantic reuse」とも合い、ライブラリー専用の判定を作らずに済む。
- 事実はモジュール単位のSyntaxId列に置く。HIRの基本列はすでにそうなっている。シンボル・型・呼出し計画をキーにする表は、寿命ごとに分ける（ライブラリーの寿命の行と、パスごとの行）。`storageVersion`の印も寿命ごとに持つ。
- ライブラリーの寿命を持つ記憶域には、入力がすべてライブラリーの寿命を持つ事実だけを置く。`#LibraryImport`の最終シンボル表はパスごとのまま組み合わせる。
- ライブラリーの序数は予約した定数にする。`SyntaxOf`はすでに`Module >= SourceModules.Length`をライブラリーとして扱う（`Compilation.Pipeline.cs:139-140`）。
- 段階3では、プロセスごとに(ライブラリーのソース, K)ごとの束縛済みライブラリー層を1つ作る。各コンパイルは、層を参照する子の`TyCtxt`（型の一意化表）と、ライブラリーのキーでは層を読む、シンボルをキーにする表を持つ。

### 3.5. 不要になるもの

- `IsLibraryDeclaration`とその例外（段階2）。
- ライブラリーの事実が有効なパスでの、`ResetPass`のライブラリー部分、`IndexLibrary`、`KimiLibrary.Restore`、ライブラリー本体のループ、`ValidateBoundDeclarations`でのライブラリーの再検証、`PublishHir`のライブラリー部分（`Binding.Hir.cs:49`）（段階2）。
- コンパイルごとの`LoadSources`と`ParseSource`（`KimiLibrarySources.cs:179-216`）、番号付け、`CreateAbort`、トークンとドキュメント候補のキャッシュの同期手順、Binding構築時のライブラリーシンボルの登録（`Binding.cs:39-42`）（段階3）。

| テストへの効果（上限） | 不明。退行は確認できず、定数倍に限られる | 2回目以降のパスのライブラリー処理だけを除く。現在の`dev`ではテスト時間の最大約23%（0.304×76.6%） | ライブラリーの構築と束縛を除く。最大約83%（38.2%＋44.7%）。テストの工程の所要時間がスレッド時間の合計に比例するなら（今回の計測では2,263秒÷8＝283秒に対し実測289秒）、278秒は最小で約47秒（278×0.17）になる。宣言の束縛と検証の半分だけがライブラリーの処理なら約110秒（278×0.40） | 小さなプログラムでは大きい。ライブラリーの構文解析は残る |
| LSPへの効果 | テストと同じ割合 | なし（LSPは検査ごとに新しいコンパイルを作る） | 検査ごとに、新しいコンパイルのBinding段階（単独で12〜16 ms）の大部分と、割当て量（4.76 MB）の最大98%（10/2のパイプライン計測でBinding段階が全割当て量に占めた比。ユーザーのソースの束縛を含み、10/16では未計測）を節約（推定） | 一部 |
| CLI（1回のコンパイル） | テストと同じ割合 | なし | なし（層はプロセスごとに1回作る） | 一部 |

効果の上限の求め方: Aは、パスごとの費用が等しいと仮定し、2回目以降のパスの数の割合（30.4%）に、ライブラリー関連の段階（`IndexLibrary`、ライブラリー本体、宣言の束縛と検証の合計76.6%）を掛けた。単独の計測では再Bindは最初のBindより軽い（本書§2.2）ので、この仮定と、宣言の束縛と検証をすべてライブラリーの処理とみなすことにより上限となる。Pは、ライブラリーだけの段階（38.2%）と宣言の束縛と検証（44.7%）の和である。0.17は1−0.829、0.40は1−0.382−0.447÷2である。278秒は`ed55d90a`のSession（`20261016-091104-645`）のテスト工程の時間。設計が挙げた28.5 msは10/2のパイプライン計測の最初の構成の値で、同じ計測の後の構成（9.3〜17.4 ms）より高く、準備不足で膨らんだと考えられる。

却下した案: コンパイルのプール（返却点がなく、並列テストが可変状態を共有する）、束縛済みイメージの複製・再生（全Kotoと計画の型の直列化が要る）、ライブラリー検査の省略（検査と導出が絡み合い、テスト専用のモードが要る）、R6・R7より前のAまたはP（モードと経路が膨らむ）。

## 5. 段階計画と検証

### 5.1. 残りの計測

- `BindDeclarations`、ライブラリー本体、`ValidateBoundDeclarations`のCPUサンプリング。ライブラリー宣言あたりのコストが高い所有者を特定する。既存のカウンター（`InferenceMetrics`、`OriginProofMetrics`、`AssociatedInferenceMetrics`）も使う。
- 段階3の前に、`KIMI_PIPELINE=mir`でライブラリー本体のMIRの費用を計測する（R4-M12によりPでは減らない）。
- 各段階で`KimiLibraryBenchmark`、パイプライン計測、テスト全体のCPU時間をA/B/Aで計測し、効果を示す。

### 5.2. 段階1（今、任意）: C

- 原因ごとに1単位とし、各単位に設計の連鎖を付ける。守る不変条件: 最初の判断の後の再判断は、本体の束縛が無効にした分に比例し、ライブラリーの大きさには比例しない。
- 後半の検証が支配的なら、「入力が変わった宣言」の集合が3つの`IsLibraryDeclaration`例外を置き換え、変わらないソース宣言の再検証も省く。これは新しい表現なのでDECISIONSに記録する。
- R7で統合されるBindingのコードを変えるため、R7の目標構造に沿う修正に限る。

### 5.3. 段階2（R6とR7の後）: A

前提: R6で旧経路（破棄効果の検証を含む）が消えていること。R7でKotoキーの表がSyntaxId列に移り、シンボル・型・呼出し計画をキーにする表と`storageVersion`の印が寿命で分かれていること。

- **S2-0（挙動変更、単独のコミット）:** `#LibraryImport`の検証でライブラリーを先にたどり、衝突をユーザーのインポートの位置で報告する。診断の位置が変わるので、S2bより前に分ける。
- **S2a（ダンプだけの挙動変更）:** ライブラリーの序数を予約定数にする。MIRダンプの期待値を理由付きで更新する。
- **S2b（構造変更、挙動は不変）:** Bindをモジュール単位にし、ライブラリーを先に完全に束縛してからソースを束縛する。まだ毎パスすべてのモジュールを束縛する。証拠:
  - 診断スナップショットの差がゼロ。
  - `SemanticSnapshotTest`（`KIMI_SEMANTIC_HIR=1`、`KIMI_SEMANTIC_MIR=1`）。
  - 同じワークツリーのパスでの`.ll`の一致（VERIFICATION「Behavior-preserving commits」）。
  - 独立性の確認: 全コーパスのプログラムについて、FinalとProvisionalの両方で、ライブラリーのモジュールのHIRとMIRのスナップショットが同一（`SemanticSnapshotTest`のライブラリーのケースは空のプログラムしか束縛しないため、それだけでは足りない）。
- **S2c（挙動変更）:** ライブラリーの事実が有効なパスではライブラリーを省く。例外とライブラリーのループを削除する。テスト:
  - 何度か再Bindした後とソース編集後のスナップショットが、新しいコンパイルのスナップショットと一致する。
  - 最初のBindの後にライブラリーへ`AddSource`すると、ライブラリーが束縛し直される。
  - ユーザーの適合宣言を消すと、それに頼る使用が再Bind後に拒否される。
  - ProvisionalのBindの後のFinalのBindのスナップショットが、新しいコンパイルのFinalのスナップショットと一致する（Mods実装後の経路、`Compilation.cs:301-304`）。
  - 再Bindの割当て量が0のまま。
- DECISIONS: L1（ライブラリーの事実の分類、本書§3.1）とL2（モジュールの事実の寿命。`709faaba`の例外を置き換える）を実装コミットで記録する。

### 5.4. 段階3（段階2の後、プロジェクト所有者の判断）: P

- **S3a（構造変更）:** 各コンパイルが、ライブラリーの寿命の事実をすべて持つ自分専用の束縛済みライブラリー層を作る。証拠はS2bと同じ。
- **S3b（挙動変更）:** (ソース, K)ごとに層を共有する（`Lazy`、ExecutionAndPublication）。凍結後のライブラリーの束縛し直しと、ライブラリーKotonohaの編集は`InternalInvariant`にする。ライブラリーを拡張・変更するテスト（本書§6）は、構築時に追加ソースまたは宣言の並べ替えを指定して専用の層を作る。`CoreCatalogTest`の「コンパイルごとに別状態」は「1つの層、並列コンパイルでも同じスナップショット」になる。
- 新しい回帰テスト: 並列コンパイルでライブラリーのスナップショットが前後で同一。凍結後に基底の`TyCtxt`への一意化（インターン）が起きない。
- DECISIONS: L3（(ライブラリーのソース, K)ごとの束縛済みライブラリー層）。L2のコンパイル単位の範囲と、Library READMEの共有範囲の記述を置き換え、ライブラリーを束縛する責務が`KimiLibrary`に移ったことを記録する。R4-M12は維持する。

## 8. リスク

- **前提の崩れ:** ライブラリーの事実がユーザーに依存する箇所が、`#LibraryImport`と旧経路の破棄効果の検証のほかにもあるかもしれない。S2bの独立性の確認で確かめる。外部適合の提案（本書§3.1）が取り込まれた場合も見直す。
- **並列テストでの安全性（P）:** 公開後の層は不変でなければならない。遅延キャッシュ（`field ??=`）、`SourceDocument`の行表、旧経路のノードへの書き込みを監査する。
- **ユーザーの事実の漏れ込み（P）:** ライブラリーのシグネチャへの`TyCtxt.Apply`は、コンパイル側の子に一意化しなければならない。ユーザーの型引数を持つContract参照とクロージャーの型はパスごとのままにする。
- **MIRの費用（P）:** R4-M12によりライブラリー本体のMIRは各コンパイルで作るため、R6の後にはPの効果が見積もりより小さくなる（未計測）。
- **段階1の手戻り:** R7で統合されるBindingのコードを変える。
- **番号:** 序数の定数化でMIRダンプが変わる。
- **診断の所有:** ライブラリーの問題は、ライブラリーの寿命を持つ型付きの事実とし、各コンパイルの`ReportDiagnostics`が公開する。
- **割当て計測の回帰:** ライブラリーを省くと、再Bindの割当て量0の検査が自明に通る。前後で再Bindが到達するBindingのメソッドを比べ、範囲が減る場合はユーザーソース側の対応テストを足す。割当て量0の表明は残す。Bindingのカウンター（`InferenceMetrics`など）を表明するテスト（5ファイル）も前後で確かめる。
- **未検証:** 効果と規模の見積もり、ライブラリーの事実がソースに依存しないこと（S2bとS3aで確かめる）。
