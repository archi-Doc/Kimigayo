# ゼロサイズ型のraw操作

**状態：提案。** 2026-10-16。正式仕様への取り込みと実装は本書の対象外。

## 1. 方針

**バイト範囲はメモリーへのアクセスを、Placeは値の初期化・所有権・借用を表す。ゼロサイズでも後者は失われない。**

対象は `stride(T) == 0` の型を扱うraw操作全体と、その値を構成要素として含む場合である。`stride` は仕様上の記法であり、ソース言語の演算子ではない。

現行の[§5.2・§5.3・§5.6](../../docs/spec/05-raw-pointers-and-unsafe-memory.md)は、ゼロ変位でポインターが変わらないことを定める一方、初期化状態を持つ論理要素の選び方を定めていない。また、終端の参照禁止とゼロ長provenanceが組み合わさり、ゼロバイトのアクセスまで禁止する読み方が残る。

本提案は、Rustのゼロバイトアクセスとポインター演算に準じ、この不足を次の三規則で補う。新しい構文、API、ポインター内の要素番号、実行時の管理表は導入しない。

## 2. 共通規則

### 2.1. バイト範囲

raw操作がアクセスするバイト範囲が空なら、メモリー割当て、その生存、バイト範囲のprovenanceを要求しない。要素へのアクセスには、引き続き**非nullで、対象の型に整列したアドレス**を要求する。対象は実際にアクセスする値の型で決まり、親の型のサイズでは決まらない。

したがって、ゼロサイズの値には、ゼロバイト割当ての結果、整列した終端アドレス、整数から作った整列済みの非nullポインターも使える。ただし、次節の値・権限の条件は別に満たさなければならない。整数からの変換が既存の値への権限を回復するわけではない。

`p + n`、`p - n`、`p[n]` の意味は§5.3のままとする。ゼロ変位はポインター全体を保存し、`p[n]` は常に `*(p + n)` と同じである。`stride(T) == 0` なら、どの `n: isize` でも変位はゼロであり、論理要素の番号はポインターに加わらない。

**終端は二つを区別する。** バイト範囲の終端から正のバイト数をアクセスしてはならない。列の論理的な終端は `index == length` であり、要素ではない。ゼロサイズの列の走査・添字検査には整数の長さを使い、ポインターの等値では終端を判定しない。

### 2.2. 論理要素と初期化

raw領域に置かれた値も[§3.4のStorageとPlace](../../docs/spec/03-types-and-values.md#34-places-and-storage)で扱う。各値とその構成要素には、それぞれのPlaceがある。これを本書では**論理要素**と呼ぶ。異なるゼロサイズのPlaceが同じアドレスを持っても、初期化状態は共有しない。

ゼロサイズのraw操作は、**型・アドレス・操作主体が持つ権限**に適合する一つのPlaceに対応する。各操作までに実行された配置・Move・借用・破棄の全履歴について、通常のPlace規則を同時に満たす一貫した対応が存在しなければ、未定義動作である。対象は操作前に存在する値と権限から選び、初期化だけが新しい値を置く。後の初期化で先の未初期化読出しを正当化できない。

フィールドや要素の選択は、選ばれた親Placeの構成要素に従う。子を同じアドレスの別要素へ選び直すことはできない。成分関係、既に確定した借用先、ビューの順序は、後続の操作でも保つ。

この対応はポインターに格納されず、`p[n]` という書き方からも決まらない。所有者の添字・長さ・初期化済み範囲は、対応を示すために使える。コメントや独自の約束だけでは値や権限は生じず、他の所有者の値を勝手に対応させることもできない。関数境界では、呼出し側と実装が同じ所有・借用契約を満たす必要がある。

`P@raw` で既存のPlaceから得た権限は、引き続き `P` とその構成要素に限られる。ゼロバイトの条件免除やアドレスの一致によって、別のPlaceへの権限が増えることはない。

| 操作 | 論理要素への作用 |
| --- | --- |
| `Raw.initialize(p, value)` | 未初期化の既存Place、または宣言済みPlaceを持たないraw領域の新しいPlaceに、値とその責任を移す。初期化済みの既存Placeには使えない。 |
| Read・通常の代入 | 対象のPlaceに通常のCopy・代入規則を適用する。代入は初期化済みの値を置き換え、必要な破棄を行う。 |
| `(*p)@move` | 一つのPlaceから値と責任を取り出し、そのPlaceを未初期化にする。他の同一アドレスのPlaceには作用しない。 |
| `_ = (*p)@move` | 対象の一つの値を破棄する。ゼロバイトでも破棄の効果は実行する。 |

アドレスだけをキーとする「初期化済み」は存在しない。raw領域の同じアドレスに二つの値を置ける一方、既存の同じPlaceを二度初期化することはできない。

### 2.3. 借用と所有責任

値の妥当性、構築完了、Copy、Move、アクセス能力、Origin、Loan、破棄は、サイズによらず通常の規則に従う。ゼロサイズはCopyを意味せず、値を持たない `Never` や満たされていない依存を持つ値を作る根拠にもならない。

raw Placeを借用すると、借用先の論理Placeが確定し、Loanが生きている間は変わらない。`Raw.slice(p, length)` は、相異なる `length` 個の初期化済み論理要素を一定の順序で借用する。その順序と対応はビューの利用中に変更しない。生成だけで値を初期化したり、所有責任を増やしたりはしない。`noinit` の既存の扱いは維持する。

借用の競合はアドレスの一致ではなく、通常のPlaceの重なりで判断する。異なる論理要素には同時に排他借用を作れるが、同じ要素への競合するアクセスや、その親全体のMove・破棄は許されない。raw借用の新しいanchorは、この義務を免除しない。

値をraw領域へ移した所有者は、各値の責任と依存を保持する。Takeは責任を移し、破棄は責任を終える。`Raw.release` は値の破棄を兼ねない。正サイズの領域を解放する場合は、そこに残る値を事前に取り出すか破棄する。ゼロバイト結果への `release` は何も解放せず、残る値の責任も変えない。言語全体に新しい「リークしない保証」を加えるものではない。

## 3. Raw APIと境界

| 対象 | この規則から決まる扱い |
| --- | --- |
| `Raw.allocate<T>(count)` | 未初期化のraw領域を用意し、値は作らない。ゼロバイトなら非null・整列済みの代替アドレスを返す。`count` や論理要素の上限はポインターに記録しない。負の個数・サイズ計算の失敗の扱いは現行どおり。 |
| ゼロサイズ型の `count == 0` | 同じく代替アドレスを得られる。バイト容量は論理要素数を制限しない。コンテナーが定める容量や長さの契約は別に守る。 |
| `Raw.slice(p, length)`、`length > 0` | ゼロサイズでも非null・整列を要求する。値とLoanの条件は要素数に対して満たす。ゼロバイトだから空のスライスになるわけではない。 |
| `Raw.slice(p, 0)` | 現行どおり `p` はnullでもよく、要素をアクセスしない。空のスライスには参照できる要素がない。 |
| `Raw.release` のゼロバイト結果 | 何もしない。正サイズ解放の事前破棄とポインター失効の条件は適用しない。先に呼んでも値の責任は残り、代替アドレスは引き続き使える。論理要素やLoanの寿命を終了させない。 |
| `p[n]` の範囲 | raw添字に検査はない。ゼロサイズでは `n` は要素を識別しない。列の要素として使うなら、その列の長さと論理要素への対応を別に満たす。通常の配列・スライスの範囲検査は変わらない。 |

ここで「ゼロバイト結果」は元の `allocate` 要求のバイト数がゼロだった結果を指す。正サイズの割当てを `raw/()` に変換しても、`release` の解放・事前破棄の条件は変わらない。

## 4. 例

### 二つの値を同じアドレスに置く

```kimi
let p = Raw.allocate<()>(2)
unsafe
    Raw.initialize(p, ())
    Raw.initialize(p + 1, ())   // 新しい別の論理要素。p + 1 == p。

    let items = Raw.slice(p, 2)
    let first = items[0]
    let second = items[1]       // 別要素。両方とも値は ()。

    _ = p[0]@move              // 一つ目の責任を終える。
    _ = p[1]@move              // 残る一つの責任を終える。
    Raw.release(p)
```

最初の二呼出しは、raw領域に別々のPlaceを作るので有効である。二つ目を `Raw.initialize(p, ())` と書いても意味は変わらない。最後の二操作も添字が対象を選ぶのではなく、異なる二要素の責任を一度ずつ終える対応が成立する。`items` のLoanは最後の利用までであり、その利用中に対応する値を取り出してはならない。

### 既存のPlaceには通常の初期化規則を使う

```kimi
var value = ()
let p = value@raw
unsafe
    Raw.initialize(p, ())      // 未定義動作：valueは初期化済み。
```

ゼロサイズの非Copy型でも同じ規則になる。完成した値を二つraw領域に移せば、二つの破棄責任が残る。片方を取り出しても、もう片方は初期化済みである。この二つ以外に対応する値がない状態で三つ目のTake・破棄を行えば、未定義動作になる。ゼロサイズのフィールドのTakeも、そのフィールドだけに作用する。

## 5. 採用理由と反映先

**採用する設計。** §5がrawアクセスのバイト条件と対象選択を定め、値の状態と責任は既存のPlace規則へ委ねる。バイトprovenanceと論理要素を同一視していた不足をこの境界で直す。初期化・添字・借用・破棄ごとのゼロサイズ専用状態は不要になる。

ポインターに論理位置を加える案は、ゼロ変位による保存、整数変換、レイアウトに新しい状態を必要とする。個数だけで定義する案は、借用中の要素や部分Moveを表せず、Place規則を別に作り直す。どちらも採らない。添字・長さを使う通常のコンテナー実装は、そのまま義務の説明に使える。

既存の[Raw Storage as Storage案](2026-10-15%20Raw%20Storage%20as%20Storage.md)は未統合の別案である。本提案ではRustに合わせてゼロバイトアクセスのprovenance要件を外し、型を変えたバイトアクセスやバイト転送一般の再設計は扱わない。

| 反映先 | 取り込み時の変更 |
| --- | --- |
| SPEC §3.4、§4.1 | raw領域の値もStorage・Placeを持つこと、アドレスの共有が論理的同一性を意味しないことを§5へ接続する。 |
| SPEC §5.2・§5.2.1–§5.2.3 | 三規則を集約する。無条件の終端禁止と、アドレス単位にも読める初期化状態の記述を置き換える。 |
| SPEC §5.3–§5.6 | ゼロ変位、整数アドレス、各Raw APIを三規則へ接続する。`release` の事前破棄・失効は正サイズ解放に限定し、Buffer例の長さ管理の意味を明確にする。 |
| SPEC §15.1・§15.6、§16 | raw操作の状態遷移・借用先・破棄が同じPlace規則に従うことを確認する。安全なコードの解析規則は変更しない。 |
| IMPL §21.1.1・§21.1.3・§21.4.3、LIBRARYのRaw契約 | 論理要素と物理レイアウトの区別、非null・整列、ゼロバイト割当てを同期する。 |

本提案の変更は文書のみで、コンパイラーのコード増減はゼロ。採用案はポインターの表現変更や追加割当てを要求しない。実装の適合性・性能は未検証であり、採用時には同じ規則をUnit、非Copyのゼロサイズ型、ゼロサイズの構成要素、借用中の操作、無効な値で検証する。

## 6. Rustとの対応

Rustの[ポインターのprovenance規則](https://doc.rust-lang.org/std/ptr/index.html#provenance)は、ゼロバイトのアクセスにprovenanceを要求しない。[Rustonomiconのゼロサイズ型](https://doc.rust-lang.org/nomicon/vec/vec-zsts.html)は、ポインター変位が進まないため、反復の個数を別に管理する必要を説明している。本提案はこの二点に準じる。

一方、Rustでも[read](https://doc.rust-lang.org/std/ptr/fn.read.html)は正しく初期化された値を、[drop_in_place](https://doc.rust-lang.org/std/ptr/fn.drop_in_place.html)は破棄に必要な型の不変条件を要求する。ゼロサイズだから値の条件まで消えるわけではない。

論理Placeの対応、構築完了、Origin・Loanの規則はKimigayo自身の仕様として定める。`()` でも、非null・整列だけを根拠に未初期化のPlaceから読み出してよいとはしない。要素へのアクセスを非nullに統一することと、長さゼロの `Raw.slice` にnullを許すことも、Kimigayoの既存契約を保つ。
