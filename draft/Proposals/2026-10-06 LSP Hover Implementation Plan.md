# LSP Hover：仕様・実装計画

日付：2026-10-06。状態：方針決定済み。正式仕様への取り込み・本計画の実装と検証は未実施。

## 1. 位置付けと目的

本書は、LSP Hoverの仕様と実装計画を一体で定める。本書で追加・変更する事項は、[SPEC.md](../../docs/SPEC.md)およびその参照先より優先する。本書が変更しない事項には既存仕様を適用する。この優先関係は本書の対象範囲に限り、他の未完了提案を暗黙に採用しない。

今回の成果物は本書だけとし、`docs/SPEC.md`、その参照先、実装、既存の計画・状態・取り込み記録は変更しない。正式仕様への取り込みは別作業とし、本計画の実装開始条件にはしない。

目的は、型・Property・関数について、解析済みの宣言・契約・説明を素早く確認できるようにすることである。

- 型には宣言、Copy判定、コメントを表示する。Property・関数には宣言とコメントを表示する。
- 意味情報はコンパイラの判定を使い、Hover側で名前解決・型推論・Copy判定を再実装しない。
- 確定した事実、未確立の事項、説明文を区別する。証明結果の`Unknown`は確定した回答であり、説明文は言語上の保証を増やさない。
- 不変の解析結果から同期処理とキャッシュで応答する。最新結果と更新待ちの旧結果を区別し、将来のCSPや他の表示にも意味情報を再利用する。

追加するのはHoverの対象・表示・応答条件と、そのための内部情報である。言語構文、アクセス制御、所有権、Copyの成立条件、呼び出し選択、コメントの対応付け規則は変更しない。

## 2. Hoverの対象と表示

### 2.1. 初版の範囲

開いていてLSPの文書同期が取れた`file:`の`.kimi`文書について、次の宣言箇所と解決済みの参照箇所を対象にする。解析結果の鮮度は§4で別に扱う。

| 対象 | 含めるもの | 基本表示 |
| --- | --- | --- |
| 型 | struct、enum、組み込み型、型パラメーター、関連型、型の具体化 | 宣言または型表記、関連制約、Copy、コメント |
| Contract | Contract名とその参照 | 宣言、要求する契約とeffect、コメント。Contract自体にはCopy欄を付けない |
| Property | `let`・`var`・`computed`、ContractのProperty要求 | 宣言、型、アクセサの契約、コメント |
| 関数 | 名前付き関数、メンバー関数、Contract要求、`init`・`drop`、明示特殊化 | シグネチャ、制約、effect、コメント |

依存先とKimiライブラリの宣言も、参照が解決済みなら同じ規則で扱う。生成宣言は、確定した表示情報だけを使い、存在しない物理ファイルや宣言位置を作らない。

ローカル変数・通常の引数・enum Case・group・Origin名・Semantics名の専用Hover、任意の式の型表示、補完、Signature Help、定義への移動、コメント中のDocument Linkは初版の対象外とする。文書コメントの対象であることだけでは、専用Hoverの対象にならない。ただし、Callable呼び出しの契約とeffectは維持し、表示位置を§2.2へ統一する。

### 2.2. 位置と対象の選択

1. 位置と範囲はLSPのUTF-16座標とし、範囲は開始を含み終端を含まない。行末を超える文字位置は行末に丸める。存在しない行や対象のない位置は`null`とする。不正な形式の要求はプロトコルエラーとして扱う。
2. 各対象に、その構文自身の代表トークンを割り当てる。名前付きの宣言・参照は名前、コンストラクター等は`init`・`drop`とする。`Container<T>`では`Container`が外側の具体化型、`T`が内側の型を表す。
3. 名前のない型は自身の構造トークンを使う。Unit・Tupleは`(`、Function Typeは`->`、固定配列は`[`、Option表記は`?`、Semantics適用型`X/T`は`X`とする。`X`がキーワードかSemantics引数かは問わない。子構文のトークンでは子を優先し、Copy判定の対象型を明記する。単なる括弧によるグループ化は対象を増やさず、Origin注釈は既存の対象型に含める。
4. 呼び出し契約の代表トークンはその呼び出しの`(`とする。型引数適用を含む直接の名前・メンバー参照が一意に解決される場合は、呼出名上のHoverにも契約・effectを統合する。`A.f<T>(x)`では`f`、`Box<T>.init(x)`では`init`が該当し、修飾部・型引数は自身の対象を保つ。`factory()(value)`・`items[index](value)`の外側の契約は外側の`(`に置き、内側の名前を借用しない。
5. Bindingの一意な選択結果を使う。一候補が複数の要求宣言から構成される場合は、共通契約と構成宣言集合を保持する。これは曖昧な候補集合ではない。複数候補、未解決、回復処理による推測、同じトークンに異なる対象が残る場合は`null`とする。

同じ対象の情報は一つにまとめ、子の優先と統合を索引作成時に確定する。検索キーと返す`range`は代表トークン一つの範囲とする。呼び出し式全体を範囲にしていた既存effect Hoverもこの規則へ変更する。対象の選択・除外は表示に使う解析結果に従い、その版のその他の区切り・一般キーワード・空白・コメント本文には対象を広げない。旧結果の範囲は§4.3で現在位置へ対応付け、参照上で宣言元の範囲を返さない。

### 2.3. 宣言と使用箇所の情報

表示順は、旧結果の場合の更新待ち注記、所属先と対象種別、宣言、使用箇所で確定した補足、Copy・effect、コメントとする。意味上の宣言、出典となる構文断片、使用箇所の完全な型を分ける。空の項目は表示しないが、保留・中断は不在と区別する。

生成するラベルは英語に揃え、コメントの言語は保持する。既存effectの`Call:`・`Requirement:`・`Callable:`・`Available bound:`・`Declared by:`・`Premise:`は維持する。その他の装飾・見出しは固定APIにせず、将来のCSPには描画テキストではなく意味情報を渡す。

- 宣言は本体を除く正規化したヘッダとする。修飾子、型・長さ引数、引数名、受け手、`task;`、取得Semantics、結果区分・型、Origin、基底型と先頭のConstraint領域など、公開契約に必要な情報を保持する。条件付きCopyを含む適合宣言や関連型の指定も対象とする。
- 関数の既定引数は存在を保持する。表示上限で式を省略するときは、省略したことを明示する。関数本体、Propertyの初期化式、アクセサ本体は表示しない。
- 型の全メンバー一覧は展開しない。Propertyは宣言された操作とアクセス条件を示し、`var`だけを根拠に「この場所で書込可能」とは表示しない。個別の使用可否を補足する場合は確認済みの事実に限る。
- ジェネリックの元宣言を書き換えず、確定した型・長さ引数や呼び出しシグネチャを別項目で補足する。無関係な内部型名や確定していない型引数を出さない。
- 分割structは各断片が提供する基底型・制約を含め、一つの論理宣言として表示する。主断片は選ばない。複数の要求宣言からなる一意な候補も共通契約を一度表示し、各宣言の出典を残す。
- 関連型の参照は契約側の関連型宣言を説明元とし、`T.Element`が`i32`に確定した場合も置き換えない。確定型は補足とCopy判定に使う。関連型の仕様付けの宣言上では、その仕様付け自身を表示する。
- `i32`などソース宣言のない型は正規の型表記と`Built-in type`を表示する。架空の宣言・位置・コメントは作らない。

表示用フォーマッターは既存の型・構文表示処理を再利用し、宣言ヘッダと意味情報を共通に扱う。構文全体の`ToString()`やソース行の切り出しを完成形にせず、要求ごとの再字句解析は行わない。省略された結果型などを補う場合も、元の表記とコンパイラの確定情報を区別する。

### 2.4. Copyとeffect

Copyは、表示対象の完全な型と当該箇所の制約を渡して、既存の`Binding.ProveCopy(type, context)`から取得する。宣言箇所では宣言の文脈、使用箇所では使用側の文脈を使う。

| 証明結果 | 表示 |
| --- | --- |
| `Proven` | `Copy: Yes` |
| `Refuted` | `Copy: No` |
| `Unknown` | `Copy: Unknown`。この文脈では証明も反証もできない |
| `Error` | `Copy: Error`。根拠に問題があり判定できない |

`Unknown`と`Error`も得られた証明結果として表示し、未確立の事実と混同しない。Contract自体など判定対象外のものには欄を設けない。未解決の型には証明を要求せず、無効な制約・回復ノード・未検査の呼び出しから保証を発行しない。証明がないことをNon-Copyと解釈しない。

宣言済みの`Self is Copy when P`は宣言表示に保持する。型引数の代入後の条件を補足する場合も、宣言された条件と当該文脈での証明結果を区別し、Hover側で条件の推論や簡約をしない。

effectは[§8.4.10.6–7](../../docs/spec/08-generics-constraints-and-contracts.md#84106-diagnostics-and-recovery)の要求を満たす。

- Contractが宣言するboundを表示する。
- requirement呼び出しでは利用可能なbound、各boundを宣言したすべてのContract、証明に寄与したpremiseを表示する。
- Callable呼び出しでは現在のeffect表示を維持し、寄与するすべてのpremiseを残す。
- 同じ対象の宣言表示と統合する。内部実装や特殊化の本文から呼び出し契約を強めない。

### 2.5. 例

```kimi
/// 値を複製して返す。
///
/// - T: Copy可能な値の型。
/// - value: 複製する値。
/// - return: 複製した値。
/// - note: [利用例](guide.md#copy)を参照。
public func duplicate<T>(value: T) -> T
    T is Copy
    return value
```

`duplicate`の宣言上では本体を除くシグネチャ・制約・コメントを表示する。`T`上では型パラメーターであること、制約、`Copy`、親宣言の`T`項目を表示する。`T = i32`と確定した呼び出しでは、元宣言にその具体化情報を補足する。`guide.md`は呼び出し側ではなく、このコメントの宣言元から解決する。

## 3. コメントとリンク

### 3.1. コメントの取得範囲

[§2.3](../../docs/spec/02-source-and-lexical-structure.md#23-whitespace-and-comments)の収集・対応付け・選択規則を維持し、次の参照範囲をHoverに適用する。

| 場所 | 取得する説明 |
| --- | --- |
| 宣言箇所 | その宣言自身の選択済みコメント。アクセスレベルを問わない |
| 解決済みの参照 | その場所から正当に参照できる対象宣言のコメント。`publicOnly`を一律適用しない |
| 通常の呼び出し・特殊化された呼び出し | 呼び出し契約を定める元宣言のコメント |
| 特殊化の宣言箇所 | 特殊化自身のコメントを`Implementation note`として表示。元契約を示す場合は出典を明記し、別項目にする |
| 型パラメーター | 親宣言の分類済みパラメーター項目のうち、その型パラメーターを一意に指すものを出典付きで表示。該当しなければ省略 |

継承・実装関係の別宣言から説明を暗黙にコピーせず、オーバーロード間で共有しない。分割structと一候補を構成する要求宣言は、全コメント断片の出典を保持し、既存の論理宣言順で独立して解析・表示する。別プロジェクト間はプロジェクトの同一性による固定順を先に適用し、到着順には依存しない。同じ宣言へ至る重複経路は除くが、別宣言の同文コメントは統合しない。

コメントなし、明示的に空、対応付け保留を区別する。構文エラーがあるSourceDocumentは、既存仕様どおり文書全体の対応付けを保留し、`Documentation deferred: syntax errors`と表示する。保留はコメントの有無を断定しない。現在の結果の不足を除外構文・古い版・近隣のコメントで補わない。§4.3の旧結果を表示する場合も、説明を含めて同じ版に揃える。

### 3.2. 描画と省略

- 原則としてコメント全体を表示する。概要だけの表示に切り替えて本文の条件を隠さない。
- [Documentation Markdown profile](../../docs/spec/documentation-markdown.md)の解析済み構造から、Hover用Markdownまたはplaintextを生成する。原文の直接転送やHTMLへの変換後の流用は行わない。
- 未採用の構文がエディタで画像・HTML・参照リンク等として再解釈されないようにテキストをエスケープする。コードはコードとして保持し、コードフェンス・リンク先・ラベルをそれぞれ正しく符号化する。
- 宣言見出しはレベル2、コメントのレベル`n`は`n + 2`として配置する。6を超える場合は`Heading level 7: …`等の深さを示す太字段落とし、同じ深さへ丸めない。plaintextでも階層を明記する。独立断片は個別に描画して区切り、型パラメーター項目の抽出にも解析済み構造を使う。
- plaintextでは構造を読み取れる改行と字下げを使い、有効なリンクはラベルとURLを併記する。
- 表示上限では、完成したブロックの境界でコメントを省略し、対象と理由を明示する。件数は確定できる場合だけ添える。リンク・コードブロックを途中で切らない。深度・処理量の上限では、不完全な解析結果を公開せず、中断理由と確定済みの宣言情報を返す。
- 省略は意味が完結する範囲に限る。更新待ち注記、シグネチャの契約部分、Copyの結果、effectと全出典・premiseは必須とし、これらを保持した応答が上限に収まらなければ`null`とする。既定引数は式だけを省略できるが、引数の既定値が存在する事実を残す。

資源制限や内部障害による`null`は理由をログに記録する。コメントだけの障害は理由を表示して他の確定済み情報を残す。障害境界は§5.2に統一し、新しい文書lintは追加しない。

### 3.3. リンクの解決

既存のURL検査・論理パス解決を共通利用し、HTMLの出力先とは別に、エディタ向けの対応付けを行う。

| リンク | 初版の扱い |
| --- | --- |
| `http:`・`https:`・`mailto:` | 既存の形式検査を通ったURLをリンクとして出力 |
| `guide.md`・`guide.md#section`等 | 宣言元プロジェクトの論理ソース名から宛先を解決し、物理配置が既知の場合だけ絶対`file:` URIへ変換。未知ならラベルを表示 |
| 空のリンク先・`?q`・`#section`・`/guide.md`等 | 表示ページ・出力URLルートの対応付けを初版では持たないため、リンク化せずラベルを表示 |
| 生成ソース・`compiler://Kimi/...`等で基準や物理配置のない相対パス | 未解決としてラベルを表示 |
| `//host/path`、未許可のscheme、不正な宛先 | リンク化しない。通常リンクは装飾付きラベル、autolinkは山括弧を含む元の表記を残す |

対応付けは`(プロジェクト, 論理パス) → 物理URIまたは未対応`の不変な入力とする。通常配置が確定している範囲は配置規則、外部ファイルへ別の論理名を与えたものは既知の個別対応を使う。一つのファイルの対応から周辺ファイルの配置を推測せず、全ソースへプロジェクトルートとの連結を適用しない。

パス・query・fragmentを分離し、パス成分を一度だけUTF-8復号する。論理プロジェクトルートを越える`..`、復号された区切り・制御文字、不正なエンコードを拒否する。URI化ではパスの`#`・`%`等をデータとして符号化し、query・fragmentとは混ぜない。変換後もURIを検査する。

`file:`は、サーバーがソース相対リンクから生成した結果に限って許可する。コメントに直接書かれた任意の`file:`・`command:`等を許可せず、VS Codeの信頼済みMarkdownやコマンド実行を要求しない。

解決のためにリンク先ファイルの内容・存在やネットワークを調べない。クリック可能であることは、ファイルの存在や見出しへの移動成功の証明ではない。fragmentを保持し、実際の移動はクライアントの対応範囲として検証・記録する。コード名の自動リンク化、新しい`kimi:`記法、文書ビューアーは追加しない。

## 4. LSP応答と整合性

### 4.1. プロトコル

`initialize`の既存の`hoverProvider: true`を維持し、`textDocument/hover`へ`Hover | null`を返す。`contents`は`MarkupContent`とし、`textDocument.hover.contentFormat`の順序から最初に対応する形式を選ぶ。省略・空・対応形式なしの場合はplaintextを使う。Markdownの宣言コードには言語ID `kimi`を付ける。[LSP Hover](https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_specifications/lsp/3.17/language/hover.md)と[MarkupContent](https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_specifications/lsp/3.17/types/markupContent.md)に従う。

一般Hoverとeffect Hoverの独立した競合するproviderは作らない。エディタ拡張で意味情報を再生成しない。

サーバー側の結果更新は、次のHover要求から反映する。標準LSPのHoverは一要求一応答であり、表示済みの吹き出しを自動更新する保証は含めない。自動更新にはクライアント側の再要求・表示更新が必要で、初版とは別に扱う。

### 4.2. 採用結果と設定間の一致

1. [§23.4](../../docs/spec/23-compiler-services.md#234-language-server-protocol)の入力・依存・必須単位・採用規則を使う。一致確認には診断の`contributors`を使わず、以下の参加集合を用いる。Hover用の旧結果の保持・表示だけを§4.3で追加し、診断の公開規則は変えない。
2. 参加するのは、文書を成員とするプロジェクトの必須単位のうち、その単位のソース選択規則で文書を検査する単位すべてとする。依存先として読むだけの消費側単位は含めない。例えばTestSourcesのみの文書は、それを検査しないProduct単位を含めない。
3. 開いている文書ごとに、参加集合が確定し、全単位に有効な`Completed`結果と利用可能なHover情報が揃った一組を採用する。集合が空・未確立、結果が未取得・held・`Blocked`・`Faulted`等の場合は、新しい一組として採用しない。未完了の単位を除外して揃ったものと扱わない。待機中の旧結果の可否は§4.3に従う。
4. 対象ごとの一致は要求時に判定する。採用した一組の全単位で、宣言集合とその出典・内容の同一性、代表範囲、ヘッダ・具体化、Copy、effectと全根拠、コメント入力・対応付け状態・分類用事実・断片順、論理リンクの配置条件を比較する。一単位だけ対象がない場合や不一致は`null`とする。Compilation内の参照や連番をCompilation間の同一性に使わない。
5. 初回は不変入力を厳密比較し、一致した入力だけを同期的に描画する。一致・不一致と完成した描画を、対象、参加集合、全採用結果の世代、描画条件に結び付けて再利用する。ハッシュだけで同一性を断定せず、繰返し要求で長文・全根拠を再比較しない。

コメント入力の同一性は名前と範囲だけでは判定しない。描画規則・形式・上限・リンク配置も再利用条件に含める。現在範囲と更新待ちの注記は描画本文と分け、位置移動だけで本文を再描画しない。文書versionだけに依存せず、依存先の編集でも旧結果として扱う。ディスク変更の検知限界は既存規則を引き継ぐ。

### 4.3. 更新待ちの表示

既定の流れは、`編集 → 前回の結果でHover → 最後の入力から1秒後に再検査開始 → 結果が揃ったら切替え`とする。1秒は検査開始までの待機時間であり、更新完了までの時間ではない。Hover要求で検査を前倒しせず、実行中の検査があれば既存のスケジュールに従う。

1. 採用結果が入力変更で再確認を要し、最新入力の検査が待機中・実行中の間は、最後に採用した一組を旧結果として保持する。影響を受けず有効な結果は現在の結果のまま使う。旧結果は文書ごとに一世代だけとし、過去の参加集合と各単位の情報を固定して新旧を混ぜない。描画済みの箇所に限らず、索引から未表示の箇所も利用できる。
2. 旧結果には先頭に`Previous analysis: update pending`（前回の解析結果・更新待ち）と表示する。この注記は宣言・Copy・effect・コメントの全体にかかる。現在のコードに対する保証として扱わない。前回の結果がない場合や§4.2の一致条件を満たさない対象は`null`とする。
3. 現在位置と旧版の代表範囲は、受理済みの範囲編集を順に適用して対応付ける。旧範囲の内部・開始・終端のいずれかに触れる編集があれば、その対象は再利用しない。返す範囲は現在文書内とし、範囲の文字列が旧版と一致することも確認する。
4. 位置対応は文字範囲の対応だけを保証する。対象選択・字句分類・束縛・コメントは旧版に従い、現在の構文や意味の一致を推測しない。例えば前方の編集でコメント化された文字範囲にも、注記付きの旧情報が表示され得る。現在の再字句解析・再Bindingは追加しない。
5. 設定・プロジェクト設定入力・所属の変更、文書閉鎖・再オープン・同期喪失、全文置換、対応履歴の上限超過では旧結果と位置対応を破棄する。通常のソース編集で現在のTest単位の必要性などが未確立になっただけなら、旧集合での暫定表示を続ける。
6. 新しい一組が揃えば一括で切り替え、対象なし・設定差による`null`でも旧結果へ戻らない。Hover情報なし・`Blocked`・`Faulted`・内部障害など、新しい一組を採用できないまま最新入力の検査が確定終了した場合は、旧結果と位置対応を破棄し、次の編集でも復活させない。途中の新たな編集で次の検査を待つ場合は、同じ旧結果を保持できる。

### 4.4. 同期処理と資源制限

- チェック結果全体の`Accepted`を表示の必須条件にしない。別箇所にエラーがあっても、対象について確定した事実は表示する。未確立の情報はその状態を示し、Copy・effectの保証を補わない。確定した`Unknown`を省略しない。
- 対象の決定自体ができなければ`null`。コメントの対応付け・処理だけができない場合は、§3の保留・中断理由を表示する。
- Hoverは状態管理ループで同期処理する。要求開始までに適用したイベントの状態を使い、位置検索・比較・必要なコメントの解析と描画・応答の送信依頼までを一処理で完結させる。コンパイラの再解析・再Bindingや検査待ちは行わない。
- 同期処理中は後続の状態更新が待つが、エディタの文字入力を止める方式ではない。比較量・解析入力量・深度・出力量・編集履歴・キャッシュ容量に上限を設ける。上限と応答性の測定基準を実装時に記録し、最大入力と連続要求でも検証する。
- 応答は一要求につき一度とし、未完成の描画は返さない。取消しと終了は既存のメッセージ処理順で扱い、完了後の取消しで再応答しない。Hover専用のワーカー・待機ジョブ・並行取消し機構は追加しない。
- 完成結果と確定した不一致・対象なしを再利用する。一時的な失敗は成功キャッシュにせず、入力上限等の再現可能な制限結果は理由付きで区別する。経過時間だけで描画を途中確定しない。
- 非同期化は初版の前提にしない。同期処理の待ち時間が測定基準を満たさない場合に限り、初回比較・描画の非同期化を別変更として検討する。

## 5. 実装構成

### 5.1. 責務とデータ

```text
既存のチェック
  → Binding・解析で確定した事実とコメント範囲を取得
  → Compilationを参照しない単位のHover情報を生成
  → 参加単位の結果が揃った一組を採用。更新待ちは前回の一組を保持
  → Hover要求を同期処理し、必要な位置対応と索引検索
  → キャッシュを再利用。初回だけ設定間比較・コメント解析・描画
  → 一処理内で応答の送信を依頼
```

以下は内部モデルの役割であり、公開プロトコルやクラス名を追加する約束ではない。

| 情報 | 保持内容 |
| --- | --- |
| 文書ごとの採用結果 | 参加集合、各単位の不変なHover情報への参照、基準ソース。更新待ちにも同じ一組を使う |
| 文書の位置索引 | 重ならない代表トークン範囲、選択済み対象、使用箇所の事実 |
| 位置対応 | 採用以後の受理済み範囲編集。旧結果から現在への対応可否を判定する有界の履歴 |
| 宣言情報 | 論理宣言の識別・種別・所属先・共有ヘッダと、独立した出典断片・コメント入力 |
| 選択済み対象 | 一意な宣言または呼び出し契約と、それを構成する宣言集合。曖昧候補とは分ける |
| 使用箇所の情報 | 確定した型・引数、Copy証明結果、effectと全根拠。宣言情報と分ける |
| コメント入力 | 不変な元テキストと範囲、対応付け状態、断片順、項目分類に必要な値、宣言元プロジェクト・論理パス |
| 比較・描画キャッシュ | §4.2の世代・条件に結び付いた一致判定と完成した本文。現在範囲・更新待ち注記は応答時に付ける |

`Compilation`・`Binding`・`Koto`・可変な`BindingSymbol`をLSP側に保持しない。`DocumentationComment`は宣言ノードを参照するため、そのまま結果へ渡さない。出典・項目分類に必要な値をチェック中に切り離し、Markdown構文木は要求時に生成する。分類用の値には全パラメーター名前空間と受け手の除外情報を含め、`self`という綴りだけで判定しない。

位置索引は、自プロジェクトの成員のうち当該単位が検査する全`file:`ソースに作り、文書の開閉には依存させない。依存先は参照先の宣言・コメント情報を保持し、消費側ごとに依存先全体の位置索引を作らない。依存先文書を開いた場合は、その所属プロジェクトの単位を§4.2で用いる。

### 5.2. 既存の入口と追加作業

| 入口 | 作業 |
| --- | --- |
| `Checking/CheckContext.cs`、`SolutionAndProject/Project.cs` | LSP用の収集要求をCompilation生成時に渡し、ソース解析前に`CollectDocumentation`を有効化。既存effect情報の生成も同じ要求で制御し、CLIの不要なHover生成を止める |
| `Compiler/Binding/KimiLibrarySources.cs` | 静的トークン経路にも文書範囲の収集・登録とParserへの受渡しを接続。下記の共有・分離規則に従う |
| `Compiler/Parsing`、`Compiler/Binding` | 代表トークンの範囲を保持し、選択済み契約・宣言集合・型・呼び出しを索引へ射影。足りない範囲はParserで保持し、文字列検索で推測しない |
| `Binding.Capabilities.cs`、`Binding.EffectHover.cs` | Copyの既存証明を利用。Callable表示を共通情報へ移し、Contract・requirement側のeffect検査情報も射影 |
| `Binding.Documentation.cs`、`Compiler/Documentation` | 宣言とコメントの対応を一度索引化し、全コメントの繰返し走査を避ける。切り離した入力、Hover向けMarkdown/plaintext、エディタ向けリンク配置を追加 |
| `Checking/CheckService.cs`、`CheckResult.cs` | 診断確定後、Compilationの解放前に不変情報を生成。チェック結果とHover情報の利用可否を分離し、下記の障害境界を設ける。CLIの診断JSONは変えない |
| `Lsp/LspSession.cs`、`Json.cs`、`LspJsonContext.cs` | 形式交渉、結果の一括切替え、編集履歴、位置対応、同期比較・描画とキャッシュを接続 |
| `src/kimi-ext` | 標準LanguageClient経由の表示・`kimi`コード・リンクを実機確認。意味解決用の独自Hoverは追加しない |

Kimiライブラリは不変なテキスト・トークンに加え、収集要求があった場合だけコメント候補範囲を生成して共有する。宣言との対応付け・分類・可変ノードはCompilationごとに作る。先にCLIがトークンをキャッシュしていても収集でき、先にLSPが収集していても収集無効のCompilationに文書オブジェクトを作らない。字句エラーのある共有結果で個々のCompilationの診断を失わせない。

索引・Copy情報・ヘッダ・コメント・切り離しを含むHover専用処理に、共通の障害境界を設ける。障害はログに記録し、コメントだけに閉じた障害は§3.2の注記、それ以外は当該単位のHover情報の利用不可として扱う。確定済みの診断・受理結果・TestPresenceは保持し、本体解析の障害は従来どおり`Faulted`とする。入力失効・取消し等の制御通知を内部障害として飲み込まない。収集・情報生成・描画の有無でチェック結果を変えないことを検証する。

現在の同期`OnHover`を拡張し、比較・描画・キャッシュ更新も状態管理側で完結させる。要求中は他の状態イベントを処理せず、別の完了イベントや送信直前の非同期再検証を設けない。チェックworkerの並行実行・結果採用の仕組みは維持する。

編集履歴には編集直前のUTF-16絶対オフセット・削除長・挿入長を記録する。要求位置を逆順に旧版へ戻して索引を検索し、代表範囲を順方向に現在へ移す。挿入・置換された文字に旧位置を割り当てず、近傍や同じ綴りで代用しない。行・列の差分加算はせず、既存の文書座標変換を使う。一通知の複数編集も適用順に扱い、編集ごとに全索引を書き換えない。

### 5.3. 費用と寿命

- 位置索引は文書別の整列済みトークン範囲を二分探索し、要求ごとに全AST・全宣言を走査しない。
- 同じ宣言・コメントを使用箇所ごとに複製しない。チェック時は範囲と確定事実を保持し、全文抽出・Markdown解析・描画は要求時に行う。
- Copyは`(完全な型, 制約スコープ)`ごとに既存証明・キャッシュを再利用し、同じ証明を使用箇所ごとに作り直さない。新しい重複表を必須にせず、前提走査を含む実費を測る。ヘッダも論理宣言単位で共有する。
- 要求のなかったコメントの構文木を作らない。繰返しHoverでは比較済みの結果と描画を再利用し、検索・比較・再描画にコメント長・effect根拠数に比例する処理を残さない。
- 初回・キャッシュ済み要求、編集、依存変更、文書閉鎖、単位の退役、セッション終了で、保持容量と解放を確認する。Compilationは保持せず、旧結果は開いている文書に必要なHover情報と不変ソースだけを一世代保持する。§4.3の切替え・破棄で履歴と不要なキャッシュも解放する。
- 同期処理の初回・再利用、編集履歴による位置対応、連続要求下の変更通知・診断採用の待ち時間を分けて測る。有限な入力上限だけで応答性を保証したと扱わない。
- 収集無効時は追加の文書収集・Hover生成をしない。収集有効化によるチェック時間・保持量の増分も測り、送信JSON等の必要な割り当てと検索・再利用部分を分ける。共有キャッシュの初回費用と再利用費用も区別する。

- 性能測定は`src/Benchmark`で固定入力・固定ウォームアップを使い、通常の回帰と分離する。Benchmark変更は全ソリューションのSessionビルドも必要。表示の速さを検索部分の時間だけで主張せず、初回描画・再利用・編集後の再チェックを分ける。
- VS Code拡張を変更する場合は、その[AGENTS.md](../../src/kimi-ext/AGENTS.md)の単体・統合検証を追加する。テストだけで表示の明瞭さを認定せず、代表的な実表示とクリック結果を確認する。
- 検証の成功・失敗は`artifacts/verify/`、測定は`artifacts/benchmarks/`に保存する。実装単位は検証後に対象ファイルだけをコミットし、証拠を対応付けて現在のブランチを`origin`へpushする。
- 実装時は責務の変更を`CODEMAP.md`、確認済みの対応範囲を`STATUS.md`、残件を`docs/dev/PLAN.md`へ反映する。必要に応じて文書APIのREADME、LSPの利用説明、セッション履歴を更新する。現在の正式仕様への取り込みは別作業で行う。

本書の作成・承認や、一部テストの成功だけでは実装完了としない。未対応・未確認の項目が残れば、対象と次の作業を明示して当該単位を未完了とする。初版の対象外を後から追加する場合は、独立した変更として扱う。

## 7. 採用しない代案と理由

Kimigayo Principlesに従い、意味の混合や新しい推測規則を避け、確定済み情報の共有で費用を抑える。今回の検討で次の代案は採用しない。

| 代案 | 採用しない理由・採用する形 |
| --- | --- |
| キャッシュを持たない | 同期・非同期とは独立に、繰返しの比較・描画費用が増える。同期処理と完成結果の再利用を組み合わせる |
| 初版から非同期描画を必須にする | 同期だけを理由に性能悪化と判断しない。まず同期＋キャッシュで測定し、応答性基準を満たさない場合に別変更として検討する |
| 呼出対象式の最後の名前を代表にする | `items[index](value)`の`index`等を外側の呼び出しと誤対応させる。構文自身のトークンを使う |
| 全文書対象・全パラメーターへ初版を拡張し、`Implements:`一覧も必須にする | 合意済みの範囲を広げ、前提付き実装関係の列挙も必要になる。適用型の代表位置だけを共通化し、機能拡張は別に扱う |
| 契約節・effectのpremiseを件数付きで部分省略する | 全出典・全寄与前提の要件を満たさず、条件を欠いた契約になる。意味上不可分な情報は完全に保持する |
| すべての表示文言を固定APIにする | 表示の都合を意味APIへ持ち込む。既存のtyped blockは保持し、CSPは構造化情報を再利用する |
| 要求時にヘッダを再字句解析する | 分割・生成宣言や確定型をソース範囲だけでは表せず、反復費用も増える。既存表示処理で宣言単位に構築・共有する |
| 論理パスを常にプロジェクトルートへ連結する／見出しをh6へ丸める | 前者は外部・埋め込みソースの配置を誤り、後者は階層を失う。部分的な配置写像と深さ付き表示を使う |
| Hoverでチェック開始を前倒しする | Hoverは入力停止の証拠ではなく、取消さないチェックを増やし得る。既存のquiet periodを維持する |
| 設定差を項目単位で合成する | 契約・具体化・証明・説明の依存を保つ合成規則が増える。初版は全参加単位の一致を要求する |
| 正式仕様への同時取り込みを今回の作業に加える | 今回は提案書だけを修正する指示に従う。取り込みは§1の別作業とする |
