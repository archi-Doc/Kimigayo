# LSP Hover：仕様変更案・実装計画

日付：2026-10-06。状態：最終案。正式仕様への取り込み・本計画の実装と検証は未実施。

## 1. 位置付けと目的

本書で追加・変更する事項は、[SPEC.md](../../docs/SPEC.md)およびその参照先より優先する。変更しない事項には既存仕様を適用し、他の未完了提案は暗黙に採用しない。

今回の成果物は本書だけとし、正式仕様・実装・既存の計画・状態・取り込み記録は変更しない。正式仕様への取り込みは別作業とし、本計画の実装開始条件にはしない。

型・Property・関数の宣言とコメント、型のCopy判定を素早く確認できるようにする。Kimigayo Principlesに従い、次を設計の基準とする。

- 意味情報と更新スケジュールは既存のコンパイラ・診断処理と共有する。
- 確定事実、未確立の事項、説明文、更新待ちの旧情報を区別する。説明文から言語上の保証を増やさない。
- 不変の解析結果に対して「同期処理＋キャッシュ」で応答する。意味情報を描画から分け、将来のCSPにも再利用できる形にする。

変更範囲はHoverの対象・表示・応答条件と内部情報に限る。言語構文、アクセス制御、所有権、Copyの成立条件、呼び出し選択、コメントの対応付け規則は維持する。

## 2. Hoverの対象と表示

### 2.1. 初版の範囲

開いていてLSPの文書同期が取れた`file:`の`.kimi`文書について、次の宣言箇所と解決済みの参照箇所を対象にする。解析結果の鮮度は§4で別に扱う。

| 対象 | 含めるもの | 基本表示 |
| --- | --- | --- |
| 型 | struct、enum、組み込み型、型パラメーター、関連型、型の具体化 | 宣言または型表記、関連制約、Copy、コメント |
| Contract | Contract名とその参照 | 宣言、要求する契約とeffect、コメント。Contract自体にはCopy欄を付けない |
| Property | メンバーの`let`・`var`・`computed`、ContractのProperty要求 | 宣言、型、アクセサの契約、コメント |
| 関数 | 名前付き関数、メンバー関数、Contract要求、`init`・`drop`、明示特殊化 | シグネチャ、制約、effect、コメント |

依存先とKimiライブラリへの解決済み参照も同じ規則で扱う。生成宣言には確定情報だけを表示し、架空のファイルや位置を作らない。

ローカル変数・通常の引数・enum Case・group・Origin名・Semantics名の専用Hover、任意の式の型表示、補完、Signature Help、定義への移動、コメント中のDocument Linkは対象外とする。文書コメントの対象でもこの範囲は広げない。Callable呼び出しの契約とeffectは維持し、位置を§2.2へ統一する。

### 2.2. 位置と対象の選択

位置はLSPのUTF-16座標、範囲は半開区間とする。行末を超える文字位置は行末に丸め、存在しない行や対象のない位置は`null`を返す。不正な形式の要求はプロトコルエラーとする。

各対象には、その構文自身の代表トークンを割り当てる。

| 対象 | 代表トークン |
| --- | --- |
| 名前付きの宣言・参照 | 名前。`init`・`drop`も同様 |
| 型の具体化 | `Container<T>`の`Container`。`T`は内側の型を表す |
| 名前のない型 | Unit・Tupleは`(`、Function Typeは`->`、固定配列は`[`、Optionは`?` |
| Semantics適用型`X/T` | `X`。キーワード・Semantics引数のどちらも適用後の型を表す |
| 呼び出し契約 | その呼び出しの`(`。直接の名前・メンバー参照では、型引数適用を含め呼出名にも契約・effectを統合 |

子構文のトークンでは子を優先する。単なる括弧によるグループ化は対象を増やさず、Origin注釈は対象型に含める。Copy欄には判定対象の型を明示する。

例えば`A.f<T>(x)`の呼出名は`f`、`Box<T>.init(x)`では`init`であり、修飾部・型引数は自身の対象を保つ。`factory()(value)`・`items[index](value)`の外側の契約は外側の`(`に置き、内側の名前を借用しない。

Bindingの一意な選択結果を使う。一候補が複数の要求宣言からなる場合は、共通契約と構成宣言集合を保持する。複数候補、未解決、回復による推測、同じトークンに異なる対象が残る場合は`null`とする。

同じ対象の統合と子の優先は索引作成時に確定する。検索・応答の`range`は代表トークン一つの範囲とし、既存effect Hoverの呼び出し式全体の範囲も変更する。選択・除外は表示に使う解析結果に従い、その版のその他の区切り・キーワード・空白・コメント本文には広げない。参照上で宣言元の範囲を返さず、旧結果の位置対応は§4.3に従う。

### 2.3. 宣言と使用箇所の情報

表示順は、更新待ち注記（旧結果のみ）、所属先と種別、宣言、使用箇所の補足、Copy・effect、コメントとする。論理宣言、出典となる構文断片、使用箇所の完全な型を分ける。空の項目は省略し、保留・中断は明示する。

生成ラベルは英語、コメントは元の言語とする。既存effectの`Call:`・`Requirement:`・`Callable:`・`Available bound:`・`Declared by:`・`Premise:`を維持し、その他の装飾・見出しは固定APIにしない。

- 宣言は正規化したヘッダとする。修飾子、型・長さ引数、引数名、受け手、`task;`、取得Semantics、結果区分・型、Origin、基底型、先頭のConstraint領域、適合宣言（条件付きCopyを含む）、関連型の指定など、契約に必要な情報を保持する。
- 関数・アクセサの本体、Propertyの初期化式、型の全メンバー一覧は出さない。既定引数の存在は残し、式の省略は§3.2に従う。
- Propertyは宣言された操作とアクセス条件を示す。`var`だけで「この場所で書込可能」とはせず、使用可否の補足は確認済みの事実に限る。
- ジェネリックの元宣言を保ち、確定した型・長さ引数や呼び出しシグネチャを別項目で補足する。無関係な内部型名や未確定の型引数は出さない。
- 分割structは全断片の基底型・制約を含めた論理宣言とし、主断片を選ばない。複数の要求宣言からなる一意な候補も共通契約を一度表示し、各出典を残す。
- 関連型の参照は契約側の宣言を説明元とする。`T.Element`が`i32`に確定しても説明元を置き換えず、確定型を補足とCopy判定に使う。仕様付けの宣言上では、その仕様付け自身を表示する。
- ソース宣言のない型は正規の型表記と`Built-in type`を使い、架空の宣言・位置・コメントは作らない。

既存の型・構文表示処理を再利用し、宣言単位でヘッダを共有する。構文全体の`ToString()`やソース行の切り出しを完成形にせず、要求ごとに再字句解析しない。省略された結果型を補う場合も、元の表記と確定情報を区別する。

### 2.4. Copyとeffect

Copyは、表示対象の完全な型と当該箇所の制約を渡して、既存の`Binding.ProveCopy(type, context)`から取得する。宣言箇所では宣言の文脈、使用箇所では使用側の文脈を使う。

| 証明結果 | 表示 |
| --- | --- |
| `Proven` | `Copy: Yes` |
| `Refuted` | `Copy: No` |
| `Unknown` | `Copy: Unknown`。この文脈では証明も反証もできない |
| `Error` | `Copy: Error`。根拠に問題があり判定できない |

`Unknown`・`Error`は得られた証明結果であり、未確立と区別する。Contract自体など対象外には欄を設けず、未解決の型には証明を要求しない。無効な制約・回復ノード・未検査の呼び出しから保証を出さず、証明の不在をNon-Copyとしない。

宣言済みの`Self is Copy when P`は宣言表示に保持する。型引数の代入後の条件を補足する場合も、宣言された条件と当該文脈での証明結果を区別し、Hover側で条件の推論や簡約をしない。

effectは[§8.4.10.6–7](../../docs/spec/08-generics-constraints-and-contracts.md#84106-diagnostics-and-recovery)の要求を満たす。

- Contractが宣言するboundを表示する。
- requirement呼び出しでは利用可能なbound、各boundを宣言したすべてのContract、証明に寄与したpremiseを表示する。
- Callable呼び出しでは現在のeffect表示を維持し、寄与するすべてのpremiseを残す。
- 同じ対象の宣言表示と統合する。内部実装や特殊化の本文から呼び出し契約を強めない。

### 2.5. 例

```kimi
/// 値を複製して返す。
///
/// - T: Copy可能な値の型。
/// - value: 複製する値。
/// - return: 複製した値。
/// - note: [利用例](guide.md#copy)を参照。
public func duplicate<T>(value: T) -> T
    T is Copy
    return value
```

`duplicate`の宣言上ではシグネチャ・制約・コメントを表示する。`T`上では型パラメーターであること、制約、`Copy: Yes`、親宣言の`T`項目を表示する。`T = i32`と確定した呼び出しには具体化情報を補足する。`guide.md`はコメントの宣言元から解決する。

## 3. コメントとリンク

### 3.1. コメントの取得範囲

[§2.3](../../docs/spec/02-source-and-lexical-structure.md#23-whitespace-and-comments)の収集・対応付け・選択規則を維持し、次の参照範囲をHoverに適用する。

| 場所 | 取得する説明 |
| --- | --- |
| 宣言箇所 | その宣言自身の選択済みコメント。アクセスレベルを問わない |
| 解決済みの参照 | その場所から正当に参照できる対象宣言のコメント。`publicOnly`を一律適用しない |
| 通常の呼び出し・特殊化された呼び出し | 呼び出し契約を定める元宣言のコメント |
| 特殊化の宣言箇所 | 特殊化自身のコメントを`Implementation note`として表示。元契約を示す場合は出典を明記し、別項目にする |
| 型パラメーター | 親宣言の分類済みパラメーター項目のうち、その型パラメーターを一意に指すものを出典付きで表示。該当しなければ省略 |

継承・実装先や別オーバーロードから説明を暗黙にコピーしない。分割structと一候補を構成する要求宣言は、全コメント断片を出典付きで独立して解析・表示する。順序はプロジェクトの同一性による固定順、既存の論理宣言順とし、到着順に依存しない。同じ宣言への重複経路は除くが、別宣言の同文コメントは統合しない。

コメントなし、明示的に空、対応付け保留を区別する。構文エラーがあるSourceDocumentは文書全体の対応付けを保留し、`Documentation deferred: syntax errors`と表示する。有無を断定せず、除外構文・古い版・近隣のコメントで不足を補わない。旧結果の表示は§4.3に従う。

### 3.2. 描画と省略

- 原則としてコメント全体を表示し、概要だけに限定しない。[Documentation Markdown profile](../../docs/spec/documentation-markdown.md)の解析済み構造からMarkdownまたはplaintextを生成する。原文の直接転送やHTML出力の流用はしない。
- 未採用の構文がエディタで画像・HTML・参照リンク等として再解釈されないようにテキストをエスケープする。コードはコードとして保持し、コードフェンス・リンク先・ラベルをそれぞれ正しく符号化する。
- 宣言見出しはレベル2、コメントのレベル`n`は`n + 2`として配置する。6を超える場合は`Heading level 7: …`等の深さを示す太字段落とし、同じ深さへ丸めない。plaintextでも階層を明記する。独立断片は個別に描画して区切り、型パラメーター項目の抽出にも解析済み構造を使う。
- plaintextでは構造を読み取れる改行と字下げを使い、有効なリンクはラベルとURLを併記する。
- 表示上限では、完成したブロックの境界でコメントを省略し、対象と理由を明示する。件数は確定できる場合だけ添える。リンク・コードブロックを途中で切らない。深度・処理量の上限では、不完全な解析結果を公開せず、中断理由と確定済みの宣言情報を返す。
- 更新待ち注記、宣言の契約部分、Copyの結果、effectと全出典・premiseは省略しない。必須情報を保持した応答が上限に収まらなければ`null`とする。既定引数の式は省略を明示して省けるが、既定値の存在は残す。

資源制限や内部障害による`null`は理由をログに記録する。コメントだけの障害は理由を表示して他の確定済み情報を残す。障害境界は§5.2に統一し、新しい文書lintは追加しない。

### 3.3. リンクの解決

既存のURL検査・論理パス解決を共通利用し、HTMLの出力先とは別に、エディタ向けの対応付けを行う。

| リンク | 初版の扱い |
| --- | --- |
| `http:`・`https:`・`mailto:` | 既存の形式検査を通ったURLをリンクとして出力 |
| `guide.md`・`guide.md#section`等 | 宣言元プロジェクトの論理ソース名から宛先を解決し、物理配置が既知の場合だけ絶対`file:` URIへ変換。未知ならラベルを表示 |
| 空のリンク先・`?q`・`#section`・`/guide.md`等 | 表示ページ・出力URLルートの対応付けを初版では持たないため、リンク化せずラベルを表示 |
| 生成ソース・`compiler://Kimi/...`等で基準や物理配置のない相対パス | 未解決としてラベルを表示 |
| `//host/path`、未許可のscheme、不正な宛先 | リンク化しない。通常リンクは装飾付きラベル、autolinkは山括弧を含む元の表記を残す |

対応付けは`(プロジェクト, 論理パス) → 物理URIまたは未対応`の不変な入力とする。確定済みの通常配置規則と、外部ファイルへの既知の個別対応を使う。周辺ファイルの配置を推測せず、全ソースをプロジェクトルートへ単純連結しない。

パス・query・fragmentを分離し、パス成分を一度だけUTF-8復号する。論理プロジェクトルートを越える`..`、復号された区切り・制御文字、不正なエンコードを拒否する。URI化ではパスの`#`・`%`等をデータとして符号化し、query・fragmentとは混ぜない。変換後もURIを検査する。

`file:`は、サーバーがソース相対リンクから生成した結果に限って許可する。コメントに直接書かれた任意の`file:`・`command:`等を許可せず、VS Codeの信頼済みMarkdownやコマンド実行を要求しない。

解決時にファイルの内容・存在やネットワークを調べない。fragmentは保持するが、リンク化は存在や見出しへの移動を保証しない。実際の移動はクライアントごとに検証する。コード名の自動リンク化、新しい`kimi:`記法、文書ビューアーは追加しない。

## 4. 更新・応答・整合性

### 4.1. 診断と共有する更新規則

Hoverは診断と同じチェックを使い、独立したタイマー・更新間隔・設定を設けない。待機と検査開始は[§23.4.6](../../docs/spec/23-compiler-services.md#2346-scheduling-and-consistency)、`initializationOptions.checkQuietPeriodMs`の既定値・範囲・初期化時の検証とセッション中の固定は[§23.4.9](../../docs/spec/23-compiler-services.md#2349-watching-and-session-settings)に従う。

```text
入力変更 → 前回のHover情報を暫定利用
        → 共通の待機時間が経過し、チェックworkerが空いたら検査
        → 有効な参加単位の結果が揃った時点でHover情報を切替え
```

待機時間は最後の入力から検査開始までの条件であり、更新完了時刻ではない。Hover要求で検査を開始・前倒しせず、入力による待機の延長や実行中チェックの扱いも既存規則に従う。

更新の契機はチェック結果の採用・入力の再確認・参加集合の確定や変更とし、診断通知の送信には依存させない。診断内容が同じで通知が省略されても更新する。内容不変の再確認で既存結果が有効になった場合も、再コンパイルなしで利用を再開する。

診断の公開条件は変えない。Hoverの参加集合やコメント処理の完了を診断公開の条件にせず、両者の表示更新が同時になることも保証しない。Hoverの新しい結果は次の要求から反映し、表示中の吹き出しの自動更新は初版に含めない。

### 4.2. 採用結果と設定間の一致

**参加集合。** [§23.4](../../docs/spec/23-compiler-services.md#234-language-server-protocol)の必須単位のうち、文書を成員とするプロジェクトに属し、そのソース選択規則で文書を検査する全単位を対象にする。結果未取得の単位も含めるため、診断の`contributors`は使わない。依存先として読むだけの消費側単位や、TestSourcesのみの文書を検査しないProduct単位は含めない。

**一組の採用。** 開いている文書ごとに、所属と参加集合が確定し、全単位に有効な`Completed`結果と利用可能なHover情報が揃った一組を採用する。未取得・held・`Blocked`・`Faulted`の単位を除外して揃ったものと扱わない。集合が空・未確立なら採用せず、更新待ちの旧結果は§4.3に従う。

結果の有効性は入力・依存の既存規則で判断する。生成時期が異なっても現在有効な結果は再利用できるが、現在の一組に失効した旧情報を補充しない。文書versionだけに依存せず、依存先の変更も反映する。ディスク変更の検知限界は既存規則を引き継ぐ。

**対象ごとの一致。** 要求された対象について、全参加単位の次の情報を比較する。一単位でも対象がない、または不一致なら`null`とする。

- 宣言集合とその出典・内容の同一性、代表範囲、ヘッダ、使用箇所の具体化情報。
- Copyの結果、effectと全出典・寄与前提。
- コメントの元テキスト・範囲、対応付け状態、分類用事実、断片順、リンク配置条件。

Compilation内の参照や連番をCompilation間の同一性に使わず、名前・範囲・同じ表示だけで同一と判定しない。一致確認の結果と描画の再利用は§4.5に従う。

### 4.3. 更新待ちの表示

**保持と注記。** 採用結果が入力変更で再確認を要し、最新入力のチェックが待機中・実行中なら、最後に採用した一組を一世代だけ保持する。過去の参加集合と各単位の情報を固定し、宣言・証明・説明を同じ一組から表示する。索引があるため、描画済みの箇所に限らず利用できる。影響を受けず有効な一組は現在の結果のまま使う。

旧結果の先頭には`Previous analysis: update pending`（前回の解析結果・更新待ち）を必ず付け、表示全体が現在のコードの保証ではないことを示す。前回の一組がない、旧集合内で§4.2の一致条件を満たさない、または位置対応ができない対象は`null`とする。

**位置対応。** 受理済みの範囲編集から、現在位置と旧版の代表範囲を対応付ける。対応途中の範囲の内部・開始・終端に触れる編集が一度でもあれば再利用しない。返す範囲は現在文書内とし、その文字列が旧版と一致することも確認する。

この対応は文字範囲だけを保証する。対象選択・字句分類・束縛・コメントは旧版に従うため、前方の編集でコメント化された範囲にも注記付きの旧情報が表示され得る。現在の構文・意味の一致を推測せず、要求時の再字句解析・再Bindingは行わない。

**切替えと破棄。**

| 状態・イベント | 扱い |
| --- | --- |
| 新しい有効な一組が揃う。再確認による復帰を含む | 一括で現在の結果へ切替え、旧結果・位置対応を解放。対象なし・不一致の`null`でも旧表示へ戻らない |
| 通常のソース編集で現在のTest単位の必要性などが未確立 | 更新待ちとして旧集合での表示を継続 |
| 設定・プロジェクト設定入力・所属・リンク配置の変更、文書閉鎖・再オープン・同期喪失 | 旧結果と位置対応を破棄 |
| 全文置換、位置対応の履歴上限超過 | 同上。近傍や同じ綴りから対応を推測しない |
| 当該文書の最新入力について、Hover情報なし・`Blocked`・`Faulted`等のままチェックが確定終了 | 旧結果と位置対応を破棄し、後の編集でも復活させない |
| 実行中に新たな入力があり、その入力のチェックを待つ | 途中のチェック終了だけでは破棄せず、同じ旧結果を保持できる |

### 4.4. LSP応答

`initialize`の`hoverProvider: true`を維持し、`textDocument/hover`へ`Hover | null`を返す。`contents`は`MarkupContent`とし、`textDocument.hover.contentFormat`の希望順で最初に対応する形式を選ぶ。省略・空・対応形式なしの場合はplaintext、Markdownの宣言コードには言語ID `kimi`を使う。[LSP Hover](https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_specifications/lsp/3.17/language/hover.md)と[MarkupContent](https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_specifications/lsp/3.17/types/markupContent.md)に従う。

チェック結果全体の`Accepted`は必須条件にしない。別箇所にエラーがあっても対象の確定事実を表示し、未確立の情報はその状態を示す。対象自体が決まらなければ`null`、コメントだけの保留・中断は§3の注記とする。

一般Hoverとeffect Hoverは一つの応答に統合し、拡張側で意味情報を再生成しない。一要求につき一度応答し、取消し・終了は既存のメッセージ処理順で扱う。完了後の取消しで再応答しない。

### 4.5. 同期処理・キャッシュ・上限

Hoverは状態管理ループで同期処理する。要求開始までに適用済みの状態を使い、位置検索・比較・必要なコメント解析と描画・応答の送信依頼までを一処理で完結させる。検査を待たず、専用ワーカー・待機ジョブ・非同期完了イベント・並行取消しは追加しない。

- 初回は§4.2の不変入力を厳密比較し、一致した入力を描画する。一致・不一致・対象なしと完成した描画を再利用し、ハッシュだけで一致を断定しない。
- キャッシュは対象、参加集合、各採用結果の世代、描画規則・形式・上限・リンク配置に結び付ける。失効・切替え時に再利用条件を更新し、繰返し要求で長文・全effect根拠を再比較しない。
- 現在範囲と更新待ち注記は本文と分けて応答時に付ける。位置移動だけで本文を再描画しない。
- 一時的な失敗は成功キャッシュにせず、再現可能な制限結果は理由付きで区別する。経過時間だけで不完全な解析・描画を確定しない。
- 比較量・解析入力量・深度・出力量・編集履歴・キャッシュ容量に上限を設ける。上限値と応答性基準はU0で定め、最大入力と連続要求で測定する。一致確認を完了できなければ`null`、コメント処理・表示の超過は§3.2とする。

同期処理中は後続のサーバー状態更新が待つが、エディタの文字入力を止める方式ではない。有限な上限だけで応答性を保証せず、基準を満たさない場合に初回比較・描画の非同期化を別変更として検討する。

## 5. 実装構成

### 5.1. 責務とデータ

チェック時に確定事実とコメント範囲をCompilationから切り離し、要求時に必要な説明を解析・描画する。以下は内部モデルの役割であり、公開APIやクラス名の指定ではない。

| 情報 | 保持内容 |
| --- | --- |
| 文書ごとの採用結果 | 参加集合、各単位の不変なHover情報への参照、基準ソース。更新待ちにも同じ一組を使う |
| 文書の位置索引 | 重ならない代表トークン範囲、選択済み対象、使用箇所の事実 |
| 位置対応 | 採用以後の受理済み範囲編集。旧結果から現在への対応可否を判定する有界の履歴 |
| 宣言情報 | 論理宣言の識別・種別・所属先・共有ヘッダと、独立した出典断片・コメント入力 |
| 選択済み対象 | 一意な宣言または呼び出し契約と、それを構成する宣言集合。曖昧候補とは分ける |
| 使用箇所の情報 | 確定した型・引数、Copy証明結果、effectと全根拠。宣言情報と分ける |
| コメント入力 | 不変な元テキストと範囲、対応付け状態、断片順、項目分類に必要な値、宣言元プロジェクト・論理パス |
| 比較・描画キャッシュ | §4.5の世代・条件に結び付いた一致判定と完成した本文 |

`Compilation`・`Binding`・`Koto`・可変な`BindingSymbol`をLSP側に保持しない。宣言ノードを参照する`DocumentationComment`も渡さず、出典・分類に必要な値を切り離す。分類用の値には全パラメーター名前空間と受け手の除外情報を含め、`self`という綴りだけで判定しない。

位置索引は、自プロジェクトの成員のうち当該単位が検査する全`file:`ソースに作り、文書の開閉には依存させない。依存先は参照先の宣言・コメント情報を保持し、消費側ごとに依存先全体の位置索引を作らない。依存先文書を開いた場合は、その所属プロジェクトの単位を§4.2で用いる。

### 5.2. 既存の入口と追加作業

| 入口 | 作業 |
| --- | --- |
| `Checking/CheckContext.cs`、`SolutionAndProject/Project.cs` | LSP用の収集要求をCompilation生成時に渡し、ソース解析前に`CollectDocumentation`を有効化。既存effect情報の生成も同じ要求で制御し、CLIの不要なHover生成を止める |
| `Compiler/Binding/KimiLibrarySources.cs` | 静的トークン経路にも文書範囲の収集・登録とParserへの受渡しを接続。下記の共有・分離規則に従う |
| `Compiler/Parsing`、`Compiler/Binding` | 代表トークンの範囲を保持し、選択済み契約・宣言集合・型・呼び出しを索引へ射影。足りない範囲はParserで保持し、文字列検索で推測しない |
| `Binding.Capabilities.cs`、`Binding.EffectHover.cs` | Copyの既存証明を利用。Callable表示を共通情報へ移し、Contract・requirement側のeffect検査情報も射影 |
| `Binding.Documentation.cs`、`Compiler/Documentation` | 宣言とコメントの対応を一度索引化し、全コメントの繰返し走査を避ける。切り離した入力、Hover向けMarkdown/plaintext、エディタ向けリンク配置を追加 |
| `Checking/CheckService.cs`、`CheckResult.cs` | 診断確定後、Compilationの解放前に不変情報を生成。チェック結果とHover情報の利用可否を分離し、下記の障害境界を設ける。CLIの診断JSONは変えない |
| `Lsp/LspSession.cs`、`Json.cs`、`LspJsonContext.cs` | 共通チェックの採用・再確認・必須単位導出/退役へ更新を接続。同期`OnHover`に形式交渉、一括切替え、位置対応、比較・描画キャッシュを追加 |
| `src/kimi-ext` | 標準LanguageClient経由の表示・`kimi`コード・リンクを実機確認。意味解決用の独自Hoverは追加しない |

Kimiライブラリは不変なテキスト・トークンに加え、収集要求があった場合だけコメント候補範囲を生成して共有する。宣言との対応付け・分類・可変ノードはCompilationごとに作る。先にCLIがトークンをキャッシュしていても収集でき、先にLSPが収集していても収集無効のCompilationに文書オブジェクトを作らない。字句エラーのある共有結果で個々のCompilationの診断を失わせない。

Hover専用処理の失敗から診断を守る共通規則を設ける。索引・Copy情報・ヘッダ・コメント・切り離しを対象とし、要求時の比較・描画にも適用する。

| 障害の範囲 | 扱い |
| --- | --- |
| コメント処理だけ | §3.2の注記を出し、他の確定情報を保持 |
| 単位のHover情報生成 | その単位のHover情報を利用不可にする |
| 要求時の比較・描画全体 | 当該要求を`null`とし、採用済みの不変情報や診断を変更しない |
| 本体解析 | 従来どおり`Faulted` |

Hover専用の障害はログへ記録し、確定済みの診断・受理結果・TestPresenceを維持する。入力失効・取消し等の制御通知を内部障害として飲み込まない。収集・情報生成・描画の有無でチェック結果が変わらないことを検証する。既存チェックworkerの実行・採用規則は変えない。

編集履歴には編集直前のUTF-16絶対オフセット・削除長・挿入長を記録する。要求位置を逆順に旧版へ戻して索引を検索し、代表範囲を順方向に現在へ移す。挿入・置換された文字に旧位置を割り当てず、近傍や同じ綴りで代用しない。行・列の差分加算はせず、既存の文書座標変換を使う。一通知の複数編集も適用順に扱い、編集ごとに全索引を書き換えない。

### 5.3. 費用と保持量

- 位置索引は文書別の整列済みトークン範囲を二分探索し、要求ごとに全AST・全宣言を走査しない。
- 宣言ヘッダ・コメント入力は宣言単位で共有し、使用箇所ごとに複製しない。要求されなかったコメントの全文抽出・構文木生成は行わない。
- Copyは`(完全な型, 制約スコープ)`ごとに既存証明・キャッシュを再利用する。新しい重複表を必須にせず、前提走査を含む実費を測る。
- 反復時の検索・比較・描画に、コメント長・effect根拠数に比例する処理を残さない。送信JSON等の必要な処理・割り当ては分けて測る。
- 旧結果は開いている文書に必要なHover情報と不変ソースだけを保持する。切替え・破棄・単位退役・セッション終了で、不要な情報・履歴・キャッシュを解放する。
- 収集無効時は追加の文書収集・Hover生成をしない。チェック時間と保持量の増分、共有キャッシュの初回と再利用、位置対応、連続要求時の変更通知・診断採用の待ち時間を測定する。

## 7. 採用しない代案と理由

| 代案 | 採用しない理由 |
| --- | --- |
| キャッシュ廃止／非同期描画の必須化 | 前者は反復費用を増やす。後者は測定前に状態管理を複雑にする。§4.5の同期＋キャッシュを基本とする |
| Hover専用スケジュール／要求による検査前倒し | 更新規則が二重になり、取消さない検査を増やし得る。§4.1で診断と共有する |
| 全文書対象・全パラメーター・`Implements:`一覧への拡張 | 初版の範囲を広げ、前提付き実装関係の列挙も必要になる。§2.1を超える機能は別変更とする |
