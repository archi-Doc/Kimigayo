# コンパイラー縮小・再構成計画 — 単一 MIR と未対応報告の一本化

日付: 2026-10-10

状態: 提案。実装は未着手。

調査基準: `419e8e79`（`dev`）。

関連: [2026-10-09 Compiler Semantic IR and Responsibility Reorganization Plan](<2026-10-09 Compiler Semantic IR and Responsibility Reorganization Plan.md>)（`620b2a1a` で追加。以下「10-09 計画」）、[COMPILER_ARCHITECTURE](../../docs/dev/COMPILER_ARCHITECTURE.md)。

## 1. 結論と目標

`src/Kimi/Compiler` は 2026-09-15 の 45,680 行から 2026-10-10 の 134,591 行へ、25 日で約 2.9 倍になった。増加の大半は Binding（12,212 → 60,703 行）、Analysis（5,534 → 20,613 行）、Emission（7,261 → 20,859 行）である。調査の結果、肥大化の原因は個々のコードの書き方ではなく、次の構造にある。

1. **関数本体の意味を 5 か所で解釈し直している。** Binding、ControlFlowAnalysis、OwnershipAnalysis（本体構築）、BodyLowering（構文と Binding からの再導出・再検証）、Binding.EffectBounds（効果要約）がそれぞれ構文木を読む。各所が独自の分岐、補助表、未対応判定を持つため、機能を 1 つ足すたびに複数箇所へ特例が増える。
2. **中間表現が意味を閉じていない。** 所有権 IR（`OwnershipBody`）は、すべての操作と Place に構文ノード（`Koto`）を持つ。型は Binding へ遅延問い合わせし、基本ブロックと終端命令を持たない。そのため後段が構文に戻り、同じ判定と検証を繰り返す。
3. **Binding 内部に同じアルゴリズムが複数ある。** 例として、呼び出し解決が 6 系統、候補選択が 6 系統、型の走査が 10 種、型の書き換えが 31 種、Origin の包含判定が 8 種ある。
4. **意味判定と説明生成が混在し、未対応報告の仕組みが乱立している。** 未対応の判定が狭い形の部分実装を生み、その部分実装がさらに特例を生んでいる。

本計画は、次の 3 本柱でこれを解消する。

- **単一の本体 IR（以下 MIR）を本体ごとに一度だけ構築する。** MIR をすべての解析とコード生成の唯一の入力にし、構文を意味のために読むのは Binding と MIR 構築器だけにする。
- **Binding は不変の意味モデルを公開した時点で役割を終える。** 構文木に意味を書き込まず、後段から問い合わせを受けない。内部の重複アルゴリズムは 1 実装へ統合する。
- **未対応は位置付きの汎用 `Unsupported` 1 種類に統一する。** pre-alpha の間は、理由文、Advice、機能列挙、狭い形の部分実装を作らない。

既存の構造に記録や状態所有者を追加していく方式は採らない。新しい MIR 経路を横に作り、一度に切り替え、旧経路を同じ作業単位で削除する。各段階に削除予算を設け、行数が増えたままの段階を完了とはしない。

## 2. 調査方法

- 基準は `419e8e79` の Compiler 配下の C# 458 ファイルである。行数は空行とコメントを含む `wc -l` で数えた。
- 次の 4 観点で全ファイルを分類した: Binding、Analysis、Emission、フェーズ横断。そのうえで、フェーズ間の参照、構文の参照、Binding の呼び出し、未対応報告、診断生成を grep とメソッド長の走査で計測した。
- 数値は「実測」と「推定」を区別する。行番号は基準時点での目安である。
- これは構造調査であり、全分岐の動作監査ではない。依存の全一覧と挙動の基準は M0 で確定する。

## 4. 根本原因

### 4.1 本体を 5 回解釈している

| 解釈箇所 | 規模（実測） | 導出しているもの |
| --- | --- | --- |
| Binding の式束縛（`Binding.Expressions`、`Calls`、`ArgumentOperations` など） | `BindNodeCore` 341 行、47 種の構文 | 型、候補選択、取得と適合 |
| [ControlFlowAnalysis](../../src/Kimi/Compiler/Analysis/ControlFlowAnalysis.cs) | 2,107 行（関連ファイルを含め 2,809） | 到達性、結果型の互換、ジャンプ先、unsafe の許可、ポインターと null の型推定（Binding の外で行う型検査）。Binding の後、所有権解析の前段として全体を再実行する |
| [OwnershipAnalysis](../../src/Kimi/Compiler/Analysis/OwnershipAnalysis.cs) の本体構築 | 約 8,100 行（Analysis の 39%） | 構文の形を Binding への 54 種の問い合わせで判別し、操作列へ翻訳する |
| [BodyLowering](../../src/Kimi/Compiler/Emission/BodyLowering.cs) | 前処理・検証メソッド 2,860 行、`Fail` ガード 2,140 行 | 構文と Binding から、変換、呼び出しの対応、型の適合を再判定する。支配木と drop flag を独自に計算する |
| [Binding.EffectBounds](../../src/Kimi/Compiler/Binding/Binding.EffectBounds.cs)（`EffectSummary`） | 2,205 行 | 効果要約のために構文を再走査し、所有権解析の後片付けも読む |

ほかにも次の重複がある。

- 到達性は 2 回計算される。構文上の `CanCompleteNormally`（構築器が 43 回参照）と、操作グラフ上の `Reachable[]` である。
- 基本ブロックの分割は 3 回行われる（`PartitionBlocks`、`PartitionCheckingBlocks`、`LowerGraph`）。
- その他の構文走査が約 6,000 行ある。再束縛のための `IndexVisitor` 464 行、`ClosureEffects`、`DefaultDeclarationVisitor`、`LocalLoopProof`、検査継続の証明などである。

### 4.2 所有権 IR が意味を閉じていない

- 操作は 39 種、値は 31 種、Place は 8 種ある。操作のうち約 15 種は特定機能専用である（Swap、Exchange、ReplaceBorrowed、Dictionary のキーとエントリ、Test 系、受け手フィールド系など）。
- 全操作と全 Place が `Koto Source` を持つ。型は `body.Resolve` を通じて Binding に遅延問い合わせする（Emission で 150 回）。
- 基本ブロックと終端命令がない。複数の入力を持つ操作は、隣接順序に依存する（「Call entries must be consecutive and immediately precede their call」）。
- 一つのフィールドが複数の意味を兼ねている。
  - `OperationSteps` は、操作種によって意味が変わる多態インデックスである。
  - `OwnershipValue.Constant` は 4 つの用途を兼ねる。
  - `OwnershipBody` は 136 個の格納フィールドを持つ。
- 解析結果（`Placement`、`CleanupStep.Action`）を IR へ書き戻す。
- 何度も構文から再構築する。
  - Semantics ケースごと、ジェネリックインスタンスごと（Emission から呼ばれる）、既定値宣言ごとに再構築する。
  - defer 本体は出口ごとに再翻訳する（上限 `DeferredOperationLimit = 8192`）。
  - インライン既定値は、呼び出しのたびに既定値の構文を再走査する。

このうち 2 つは仕様と食い違っている。

- Emission の失敗は位置を持たず、分類も Internal である。これは SPEC §23.3.6.1（許された形の未対応は `Unsupported` コード）と IMPL §21（未対応の選択操作は生成を失敗させ、未使用の本体にも未対応の診断を出す）の意図に沿わない。
- `Language` コードで報告している実装制限も、§23.3.6.1 に反する。

狭い部分実装は次の箇所に見られる。

- [STATUS](../../docs/STATUS.md) §4.1〜4.11 は、対応範囲を形の列挙で記述している。例として「静的な文字列要素の比較と共有引数」「所有引数と一時値からの静的な文字列要素の借用」がある。
- 検査継続の「証明」ビジター（`LocalLoopProof`、`ScopedCheckingProof` など）は、ある形が再生可能かどうかを判定するためだけに存在する。
- Emission には構文の形に依存する特例がある（§4.6）。

### 4.7 手書き IR に置かれたライブラリ処理

- `LlvmModuleWriter` の 4,567 行のうち 2,866 行は、補助関数や複数ブロックの制御を生成している。
- Array の伸長、挿入、削除、pop、swap、clear の各アルゴリズムは `LlvmModuleWriter.Arrays.cs`（414 行）にあり、`BodyLowering.Arrays.cs`（609 行）がそれを駆動する。一方、Dictionary は既に Kimigayo で書かれている（`DictionaryStorage.kimi`）。Array の現状は、AGENTS.md の「コアライブラリは Kimigayo で書く」方針と一致しない。

  - 書き出し時に複数ブロックへ展開されるマクロ命令。例として、文字列で区別される 15 のサブ命令を持つ `Sequence`、`CompositePattern`、`TupleRelation` がある。
  - LLVM の綴りを文字列で持つフィールド。

### 4.8 進め方の問題

- 作業単位が「1 つの狭い形」になっている。各単位が、5 か所の解釈箇所それぞれに特例と専用の診断を追加する。
- 10-09 計画の実施（2026-10-09〜10）は、事実の記録と状態の所有者を既存構造へ足していく方式だった。そのチェックポイントでの削減は 115 行（0.09%）にとどまった。境界の目標は正しいが、この移行方式ではコードが減らない。

## 5. 設計原則

1. **一つの決定は一か所、一つの表現にする**（Kimigayo 原則 1）。各構文の意味は MIR 構築器で一度だけ翻訳し、各解析は MIR の小さな語彙を処理する。
2. **構文を意味のために読むのは、Binding と MIR 構築器の 2 か所だけにする**（原則 2）。MIR を構築した後は構文に戻らない。親ノードをたどって意味を推定しない。
3. **所有権、失敗、変換、依存を MIR の構成要素として明示する**（原則 3）。たとえば Copy と Move のオペランド、中断先を持つ Call、変換の種類である。
4. **MIR と問題記録を構造化して外部へ出せるようにする**（原則 4）。MIR のテキストダンプと、型付きの問題記録を、検査と編集の基盤にする。
5. **pre-alpha の間、未対応は位置付きの汎用 `Unsupported` だけにする。** 部分実装はしない。
6. **削除で解決する。** 各段階は削除予算を満たすまで完了しない。新しい抽象は、それによって消える行数で正当化する。
7. **性能は計測で示す。** 本体ごとに一度だけ構築し、配列ベースの表現、ブロック単位のビット集合データフロー、作業領域の再利用を基本にする。

## 6. 目標アーキテクチャ

```text
ソース
  │  Lexing / Parsing
  ▼
Koto（純粋な構文。意味フィールドを持たない。ノード ID を持つ）
  │  Binding（名前、宣言、型、Origin、制約、推論、候補選択、取得の決定、定数）
  ▼
意味モデル：宣言表・型表・本体ごとのノード事実表（型 ID と計画）・問題記録
  │  MIR 構築器（構文の構造とノード事実だけを読む）
  ▼
MIR（ジェネリックのまま、本体ごとに 1 回構築）
  │  MIR 解析：検証器 → 初期化 / Move → drop elaboration → 借用検査 → 効果 → lint
  ▼
検査済み MIR（ジェネリック、Semantics ケースごとに検査済み）
  │  単相化収集器（関数インスタンス、witness、drop glue、仮想表、オブジェクト記述子）
  ▼
MIR → 物理モジュール（平坦な型付き命令） → LLVM テキストの書き出し → ネイティブツール

問題記録 + 位置表 → 診断公開アダプター（Note・Advice・修正候補を作るのはここだけ）
意味モデル + 構文   → Hover・ドキュメントのアダプター
```

| 構成要素 | 読んでよいもの | 読んではいけないもの |
| --- | --- | --- |
| Lexing / Parsing | ソース、指令環境 | 意味モデル、解析結果 |
| Binding | 構文、宣言表、自身の作業領域 | MIR の解析結果、物理表現 |
| MIR 構築器 | 構文の構造、ノード事実表、宣言表、型表 | Binding の内部メソッド、親ノードたどりによる意味推定 |
| MIR 解析 | MIR、宣言表、型表 | Koto、Binding |
| 単相化と生成 | 検査済み MIR、型表、レイアウト | Koto、Binding、解析の内部状態 |
| LLVM 書き出し | 物理モジュール | 上記すべて |
| 診断公開・Hover | 問題記録、意味モデル、表示用の構文 | 意味の再計算 |

ノード事実表は、式ごとに解決済みの記録を、ノード ID で引ける配列として持つ。記録の中身は型 ID と計画である。計画には、呼び出し計画（呼び出し先、引数と仮引数の対応、既定値、取得、結果の由来）、Place 計画（射影パス）、変換計画、演算子計画、パターン計画、クロージャ計画がある。この表が、構文ノード上の 44 メンバー、構文ノードをキーとする補助表、後段からの Binding 呼び出しを置き換える。

10-09 計画の境界規則は引き継ぐ。具体的には、意味を一度だけ決めること、構文に依存しない解析と生成、検査専用の経路と実行時の経路の区別、インライン既定値、Semantics ケース、源泉位置の保持である。本計画との違いは次の 5 点である。

- 表現を、既存の操作列の拡張ではなく、基本ブロック・文・終端命令・射影付き Place からなる標準的な MIR にする。
- 移行を、経路ごとのアダプター付き段階移行ではなく、並行構築と一括切替にする。
- 名前付きの解析所有者を 12 個置く代わりに、解析パスを 4 つにする。
- 削除予算を明記する。
- 未対応の報告、診断、ライブラリ処理の扱いを含める。

## 7. MIR の設計

### 7.1 データ構造

本体ごとに、配列の組（struct-of-arrays）で持つ。要素ごとにヒープオブジェクトを作らない。

```text
MirBody
  Signature     宣言 ID、型引数スキーマ、Semantics ケース集合
  Locals[]      型 ID、種類（Return / Argument / User / Temp）、可変性、位置
  Blocks[]      文の範囲、終端命令
  Statements[]  種類、Place、右辺値、位置、ケースマスク
  Places[]      ローカル、射影の範囲
  Projections[] Field(ID) | Index(ローカル) | ConstIndex(n, 末尾から) | Subslice(始, 終) | Deref | Payload(ケース)
  Operands[]    Copy(Place) | Move(Place) | CopyOrMove(Place) | Const(ID)
  Scopes[]      親、位置、インライン元（既定値・defer）と解釈文脈
  Anchors[]     源泉位置（文書、範囲、役割）
```

- `CopyOrMove(Place)` は、ジェネリックな値の Copy と Move の区別が Semantics ケースや型引数で決まる場合に使う。解析はケースごとに解決し、生成時には確定している。
- 定数は ID で定数表を引く。トークンの綴りから算術を復元しない。
- 静的な選択子（リテラル）と実行時の鍵を区別する。サイズ 0 の値も論理上の Place と効果を保つ。

### 7.2 文、右辺値、終端命令

| 区分 | 種類 |
| --- | --- |
| 文 | `Assign(Place, Rvalue)`、`StorageLive(Local)`、`StorageDead(Local)`、`SetDiscriminant(Place, ケース)`。SPEC が借用の字句的な終わりを要求する箇所に限り、`EndBorrow(Local)` |
| 右辺値 | `Use`、`Ref(種類, Place)`、`RawAddress`、`Unary`、`Binary`、`Checked`、`Cast(種類)`、`Aggregate(種類, オペランド)`、`Discriminant`、`Length`、`Closure(環境)` |
| 終端命令 | `Goto`、`Switch(オペランド, 値→ブロック, その他)`、`Call(呼び出し先, 引数, 結果, 正常先, 中断先)`、`Drop(Place, 次)`、`Assert(条件, 種類, 次)`、`Return`、`Unreachable`、`CheckOnly(次)` |

- 呼び出し先は `Direct(宣言, 型引数)`、`Requirement(要求, witness)`、`Virtual(スロット)`、`Value(オペランド)`、`Intrinsic(種類)` のいずれかである。`Intrinsic` は、`Raw`、`Storage`、テスト検証など、コンパイラーが提供する操作の閉じた列挙である。
- 引数は、Call の前に源泉の評価順で一時ローカルへ評価する。Call のオペランドは仮引数の順に並べる。こうして評価順と仮引数順を構造的に分ける（現在の `RightFirstArguments` などの特例が不要になる）。
- 演算子、Property の呼び出し、インデクサー、範囲、反復、文字列補間は、Binding の計画に従って Call または右辺値に脱糖する。合成構文ノードは作らない。

### 7.3 Kimigayo 固有の要件の表現

| 要件 | 表現 |
| --- | --- |
| 発散後の到達しないコードも、引き継いだ状態で検査する | 発散点から `CheckOnly` 辺で続きのブロックへつなぐ。実行時のデータフロー（配置、drop flag、後片付け）は実行時の辺だけで、検査のデータフローはすべての辺で計算する。`CheckOnly` だけで到達するブロックは生成しない。これで検査継続の再生機構（1,235 行）と証明ビジターを置き換える |
| Semantics ケース（SPEC §8.10）と条件付きスロット | MIR は 1 回だけ構築する。ケースに依存する文には「ケースマスク」を付け、解析はケースごとに置換を与えて実行する。ケースごとに再構築はしない。問題記録はケースのビットを OR で合併する（現在の公開上の合併規則を保つ） |
| インライン既定値（SETTLED「Instance-evaluated generic defaults」） | 既定値の本体を MIR テンプレートとして宣言ごとに 1 回構築する。呼び出し側でローカルを付け替えて展開し、展開範囲の `Scope` に合成した解釈文脈を記録する。インラインの複製、評価順、準備済みスロットの保護、後片付けは保つ。呼び出しごとの構文再走査は行わない |
| defer と後片付け | スコープ出口の drop と defer を、出口の間で共有する後片付けの木として構築する。出口ごとの再翻訳と `DeferredOperationLimit` に頼らない |
| 結果を後片付けより前に確保し、後に引き渡す | 結果ローカルへの `Assign` → 後片付けのブロック → `Return` の順を、構造として表す |
| 呼び出しの予約（二相借用） | `Ref(Reserved)` を作り、`Call` で有効化する |
| 比較のための検査借用 | `Ref(Inspect)` を作り、必要な箇所に `EndBorrow` を置く |
| swap と exchange | Binding の更新計画を、旧内容を一時ローカルへ移す `Assign` と新内容の設置へ展開する。二つの破壊的な代入で模倣はしない。別名の関係と自己更新は、計画が持つ合法性に従う |
| 中断された呼び出しの後片付け | `Call` の中断先へ、準備済みの引数の後片付けをつなぐ |
| Origin と Loan | 型に Origin 変数を持たせる。呼び出し計画の「結果の由来」を、Origin の制約として MIR の `Call` に付ける。Origin の名前が等しくても、独立した入力を同一視しない |

### 7.4 段階

1. **構築済み**: 構築器の出力。ジェネリックのままで、`CopyOrMove` を含みうる。
2. **検査済み**: 初期化と Move の解析、drop elaboration、借用検査、効果解析が成功したもの。drop elaboration は drop flag を bool のローカルとして挿入し、出口に `Drop` を置く。この段階で、生成に必要な事実はすべて MIR 上にある。
3. **生成時**: 単相化収集器が求めたインスタンスごとに、置換を適用しながら物理モジュールへ下ろす。MIR はインスタンスごとに複製しない。型に破棄処理がなければ、`Drop` は何も生成しない。

インスタンス時の所有権の再解析（`AnalyzeInstance`）は廃止を目標とする。ジェネリックな drop elaboration は、具体型が Copy であっても健全である（Move 扱いの後に `Drop` が無効になるだけ）。インスタンス時にしか判定できない事実が仕様上あるかどうかは M0 で調べ、あればその事実だけを生成時の検査として明示する。

### 7.5 記述子表と検証器

文、右辺値、終端命令の種類ごとに、記述子表を 1 つだけ持つ。記述子は、読み込み、書き込み、Move、借用、定義、ケース依存を表す。

- 初期化解析、借用検査、生存解析、効果解析、lint は、この表を通してオペランドを列挙する。現在の `OwnershipFlow.FlowOf`、`DefinesBorrowHolder`、`BorrowLiveness.Uses` という手で保守している 3 つの分類器を、これに置き換える。
- 新しい種類を表に追加しないと、検証器が失敗する。既定の分岐へ黙って落ちることはない。
- 検証器は MIR の整合性を検査する。検査項目は、型、Place の射影、ブロックの終端、到達性、ケースマスクである。Emission の約 440 の `Fail` のうち内部整合性の再確認は、ここへ集める。

### 7.6 MIR ダンプ

テストと外部ツールのために、テキスト形式のダンプを用意する。構築器の規則は、ダンプを使って最も低い層で検査する。解析の規則は、手で書いた MIR を入力にして、構文なしで検査できるようにする。

### 7.7 量の目安（推定）

| 部分 | 行 |
| --- | ---: |
| MIR モデル、記述子表、検証器、CFG ユーティリティ（逆後順序、先行、支配）、ダンプ | 1,200〜1,800 |
| MIR 構築器 | 5,000〜6,500 |
| 初期化と Move、drop elaboration | 1,000〜1,400 |
| 借用検査（二相、検査借用、既定値の規則、Origin の制約を含む） | 3,000〜3,500 |
| 効果解析 | 600〜900 |
| lint（到達不能、破棄、不要な unsafe、関数末尾への落下） | 300〜400 |
| **合計** | **14,500 以下** |

## 8. フェーズ別の再構成

### 8.1 Binding

**責務**: 名前と宣言の解決、型・長さ・Origin の形成、制約、適合（conformance）、関連型の推論、オーバーロードの選択と推論、取得と適合の決定、定数評価。ジャンプ先とラベルの解決、結果型の互換、unsafe の許可、ポインターと null の型付けは ControlFlowAnalysis から Binding へ移す。これらは名前と型の規則だからである。

**出力**: 次からなる不変の意味モデル。

- 宣言表: 宣言 ID から、シグネチャ、契約、witness、効果の上限、既定値テンプレートの参照を引く。
- 型表: インターン済みで不変の型。`BoundType` が持つ可変のレイアウトフィールド（`StoredFields`、`StoredBase`、`StoredCases`、`StorageVersion`）はレイアウト計画へ移す。
- ノード事実表。
- 問題記録。

**やめること**:

- 構文ノードへの書き込み（44 メンバー）と、合成構文ノードの生成（40 箇所以上）。
- 後段からの問い合わせを受けること（Analysis の 170〜200 箇所、Emission の 70〜80 箇所）。
- 所有権解析の結果を読むこと（`EffectBounds` と Analysis の循環を断つ）。
- 親ノードをたどる文脈推定。

**統合**: §4.3 の表のとおり。中心になるのは次の 3 つである。

- **呼び出し可能シグネチャの統一ビュー**: 関数、コンストラクター、列挙ケース、アクセサー、インデクサー、演算子要求、関数項目、クロージャを 1 つのビューで扱う。その上に 1 つの `ProbeArgument`、`SolveCall`、`SelectBest` を置く。関数参照は「期待されるシグネチャに対する解決」として扱う。
- **型代数の核**: 走査 1 つ、置換 1 つ、包含判定（`OriginPremiseClosure`）1 つ、Origin ソルバー 1 つ。
- **定数評価器 1 つ**: 長さ、リテラルの適合、位置警告、変換の畳み込みで共用する。

**外へ出すもの**:

- `EffectSummary` と破棄効果の検証 → MIR の効果解析。
- ストレージのレイアウト → レイアウト計画。
- 説明文、Advice、修正候補 → 診断公開。
- Hover → アダプター。

**目標**: 32,000 行以下（D3 採用時は 29,000 行以下）。Origin、Semantics の組、関連型、効果の上限といった言語固有の意味が実質的な下限を決める。これより下げるには仕様の簡素化が要る。

### 8.2 MIR 構築器

- 入力は、構文の構造（文、式、パターンの入れ子）と、ノード事実表だけである。各構文について、ノード事実表の計画を読み、決まった MIR の列へ翻訳する。構築器自身が意味を選んではならない。たとえば、Binding への順次問い合わせで呼び出しの形を判別することはしない。
- 翻訳規則のない構文や計画は、その位置で `Unsupported` にする。本体を未対応として印を付け、以降のフェーズはその本体を処理しない。
- 移行期間（M3〜M6）は、現在の Binding の結果を `BodyFacts` という狭い窓口で読む。窓口のメソッド一覧には上限を設け、減らす方向にしか変えない。M7 で窓口がノード事実表そのものになる。

### 8.3 MIR 解析

1. **CFG の事実**: 逆後順序、先行ブロック、支配を 1 回計算し、解析と生成で共有する。
2. **初期化と Move**: Move パスの MaybeInit / MaybeUninit をデータフローで求める。使用、Move、再代入の誤りを報告し、drop elaboration を行う。現在の `OwnershipBody.Solve`、`Checking`、`MovePaths` と、Emission にある 3 つの drop flag 方式（文字列と配列の生存フラグ、Move パスのフラグ、条件付き集成体の破棄）を置き換える。
3. **借用検査**: SPEC §15 を直接実装する。
   - Loan の生成元: `Ref`、予約、検査借用。
   - 型と呼び出し計画の「結果の由来」から、Origin の制約グラフを作る。
   - ローカルごとの生存を後ろ向きに求め、有効な Loan の集合を前向きのビット集合データフローで求める。
   - アクセスごとに衝突を検査する。
   - 準備済みの既定値と要求効果の規則は、Loan の種類として表す。
   - これで次を置き換える: 依存、権限、保持、格納済み借用、referent、内容更新の各表、根ごとの Loan フロー、`VerifyBorrows` の 702 行の手続き、構築中の衝突検査（`RecordComparisonState`）。
   - 「権限」と「依存」は、異なる規則として扱い続ける。等しい Origin や独立した入力についての既存テストを保つ。
4. **効果解析**: 本体ごとの要約と、呼び出しグラフ上の不動点を求める。`Drop` と `Call` を走査するので、構文は再走査しない。
5. **lint**: 到達不能コード、破棄された結果、不要な unsafe、関数末尾への落下を報告する。

削除するもの:

- `OwnershipAnalysis*.cs`、`OwnershipBody*.cs`、`OwnershipModel`、`OwnershipFlow`、`InterpretationContext`（MIR の `Scope` に吸収）。
- `ControlFlowAnalysis`、`ControlFlowTypes`、`BindingControlFlowTypes`。ただし Binding が型付けに使う `StructuralCompletion` は残す。
- 検査継続の再生機構、未対応判定の述語、インスタンス解析、ケースごとの再構築。

### 8.4 単相化と生成

- **単相化収集器**: 検査済み MIR から、関数インスタンス、要求の witness、drop glue、仮想表、オブジェクト記述子を、上限付きで求める。`GenericStoragePlan`、`VirtualGenerationPlan`、`ObjectGenerationPlan`、`DefaultGenerationPlan`、`CompilerFunctionAdapters`（計 2,102 行）を 600〜900 行で置き換える。インライン既定値は MIR 上で展開済みなので、既定値ごとの生成は不要になる。
- **MIR から物理モジュールへの下ろし**:
  - Place のアドレス計算を 1 つにする（基底と射影の列から計算し、境界検査は MIR の `Assert` で済ませる）。
  - 右辺値と検査付き算術の下ろし。
  - 呼び出しの経路を 1 つにし、組み込み操作の表を加える。
  - 終端命令の下ろし。
  - これで次を置き換える: 現在の 5 系統の Place アクセス（Elements、StructBorrows、Sequences、References、DictionaryStorage）、15 の呼び出し入口、Match と CompositeMatch の二重実装。パターンは MIR 構築器が `Switch` にする。目標は 2,800〜3,500 行である。
- **物理モジュール**:
  - 命令は型付きの列挙にし、LLVM の綴りを文字列で持たない。
  - マクロ命令（`Sequence` のサブ命令、`CompositePattern`、`StringPattern`、`TupleRelation` など）を廃止する。比較や関係演算は、Kimi ライブラリの関数か、MIR として生成した補助本体に置き換える。
- **書き出し**: 直列化だけを行う（1,500〜1,800 行）。
- **ライブラリの移行**:
  - Array の変更アルゴリズムを `Array.kimi` へ移す。既存の `Raw` / `Storage` の基本操作の上に書き、Dictionary と同じ方式にする。
  - 文字列の比較も Kimi ライブラリへ移す。
  - 書式処理の手書き IR（`Utf8FloatRyu` を含む 2,031 行）は第二波の候補とする。
- **報告**:
  - Emission は言語の誤りも未対応も判定しない。
  - 目標表現の制限（例: 128 ビットの除算）は、MIR の文の位置で `Unsupported` にする。この判定は生成の前段（単相化収集の時点）で行う。未使用の本体も、MIR の構築時に同じ判定を受ける（IMPL §21）。
  - 内部整合性の違反は Internal として、位置とともに 1 経路で報告する。
- **目標**: 7,500 行以下。

### 8.5 構文、その他

- **Koto**: 意味メンバー（`BindingState`、`BoundType`、`BoundSymbol`、`ConversionBinding`、`CallStorage` など 44 個）を削除する。代わりに構文解析時に密なノード ID を割り当て、Binding の結果を外部の配列に置く。再束縛のためのリセットウォーカー（`IndexVisitor`）は削除する。
- **ルート直下のファイル**:
  - `ElementAccess` は、構文の認識（→ Binding）とパス操作（→ MIR 構築器）に分けて解体する。
  - `*Types` / `*Storage` は、型表の照会（→ Binding）と表現の照会（→ レイアウト）に分ける。
  - `StaticScalar` は定数評価器へ、`StrictBestCandidate` は `SelectBest` へ移す。
  - `CompilerHelper` の、呼び出し元がない分類述語は削除する。
- **Core**: `Compilation` は、Parse → Bind → BuildMir → Analyze → Collect → Lower → Write の順序と無効化だけを持つ。
- **対象外**: Parser の文法部分、Lexing、Documentation は対象外とする（上記の意味メンバーの除去を除く）。

### 8.6 今後の機能追加の手順

再構成の後、新しい機能は次の順で追加する。

1. **構文**（Parser）。
2. **Binding**: 解決の結果をノード事実表の計画として公開する。
3. **MIR 構築器**: 計画を既存の MIR の語彙へ翻訳する。ほとんどの機能は、新しい MIR の種類を必要としない。
4. **新しい種類が必要な場合**: 記述子表に 1 行、検証器、物理への下ろしをそれぞれ 1 か所追加する。解析は記述子を通して自動的に追従する。
5. **一般形を実装できない場合**: 構築器で `Unsupported` にする。形を絞った部分実装はしない。

現在は、たとえば swap と exchange の追加が、初期化解析、借用内容の解析、Emission の更新処理という 3 か所での構文判定を必要とした（10-09 計画 §3）。再構成の後は、計画 1 つと構築器の翻訳 1 つで済む。

## 9. 未対応報告の一本化

### 9.1 規則

- **コード**: コードは `Unsupported_Kd` の 1 つだけにする（分類 `Unsupported`、深刻度 Error）。メッセージは固定で、「この形はまだ実装されていない」とする。
- **記録の中身**: 記録に入れるのは、主位置（その構造の最小範囲）と固定のラベルだけである。Reason、Note、Advice、関連位置、修正候補は付けない（決定事項 D6）。
- **重複の扱い**: 同じ位置に対しては 1 件だけ記録する。未対応を含む本体には印を付け、以降のフェーズはその本体を処理しない。そこから派生する記録も作らない。独立した他の本体と、他の問題は報告し続ける（局所性）。
- **仕様との関係**: SPEC §23 は、この規則のままで満たせる。§23.3.6.1 は、許された形の未対応に `Unsupported` 分類のコードを使うことだけを要求しており、コードが 1 つでも問題はない。§23.3.6.2 は、根拠のない欄を持たないことを許している。§23.3.3 は、未対応が完了結果を拒否することを要求しており、Error であることがそれを満たす。

### 9.2 報告する場所

| 場所 | 条件 |
| --- | --- |
| Binding | 束縛の規則がない構文や宣言の形。OCC-X など、要求された証明が未実装である場合を含む |
| MIR 構築器 | 計画はあるが、MIR への翻訳規則がない場合 |
| 単相化収集器 | 目標表現の制限（整数幅、レイアウト、ABI） |
| MIR 解析と生成 | 報告しない。解析が扱えない MIR の種類は、記述子表と検証器の欠陥であり、Internal である |

`Language` コードで報告している実装制限（DIAGNOSTICS.md §11 の 4 件）は、`Unsupported` に改める。`OwnershipCaseLimit_Kd`、`OwnershipStorageLimit_Kd`、`GenerationResourceLimit_Kd` などの `Resource` 分類は、仕様上の資源制限なので残す。ただし、defer の展開上限（`DeferredExpansionLimit_Kd`）は、後片付けの木の共有で不要になれば削除する。

### 9.3 削除するもの

- コードと分類の付随物:
  - `UnsupportedBinding_Kd`、`UnsupportedOwnership_Kd`、`UnsupportedIntegerOperation_Kd`、生成元のない `UnsupportedEmission_Kd`。
  - 要求語彙の `Binding.Unsupported`、`Ownership.Unsupported`、`Emission` の行（1 行に統合する）。
- Binding の理由文:
  - 理由文の補助表（`originQualifierLimits`、`staticStorageLimits`、`pendingExclusiveLimits`、`payloadCallees`、`virtualDeclarationFailures`、`baseCallFailures`）と、それらの `ReportIssue` の分岐。
  - `ReportOriginQualifier`、`RejectedOriginQualifier` の理由生成。
  - `MarkUnsupportedTree`。
- Analysis の機能列挙: `OwnershipFeature`、`FeatureNote`、`FeatureLabel`、`UnsupportedRoute`、`OwnershipIssue.Feature`、`OwnershipIssue.OperationType`。
- Emission の失敗文: 約 440 の `Fail` 文字列と `out string? failure` の受け渡し。M1 では、未対応にあたるものを位置付きの `Unsupported` に、それ以外を Internal にする。M6 で検証器に集約する。
- 削減量の推定は 1,500〜2,500 行。

### 9.4 狭い部分実装の扱い

- **新規**: 新しい部分実装は作らない。一般形を実装するか、`Unsupported` にする。
- **既存**: 既存の部分実装は MIR へ移植しない（決定事項 D2）。
  - MIR 構築器で一般形を少ない量で実装できるもの（例: 静的な要素パスの借用は、射影付き Place で一般に扱える）は、一般形として実装する。
  - それ以外は `Unsupported` にする。
- **一覧と記録**: 対象の一覧は M0 で作る。STATUS §4.1〜4.11 の形の列挙、`Supports*` 述語、構文の形に依存するガードが対象である。マイルストーンが依存しているものには印を付ける。対応範囲が狭まる場合は、その単位で STATUS を更新する。

### 9.5 テストと文書

- **テスト**:
  - 特定の未対応コードや理由の存在を確認する 56 メソッドは、`Unsupported_Kd` と位置の確認に改める。
  - 不在を確認する 162 メソッドは、共通の述語 1 つにまとめる。
  - 理由文と失敗文を確認する約 30 箇所は削除する。
- **文書**:
  - [IMPL A.8](../../docs/impl/appendices/A-compiler-requirements.md) には、OCC 状態が未計算の使用について、「選択した実装、射影パス、未完了の検証を名指しする `Unsupported` コード」で報告するという要求がある。これを「使用の位置で `Unsupported` を報告する」に改める。
  - DIAGNOSTICS.md の規則 3（理由に欠けている機能を書く）と §11 も改める。
  - STATUS のコード別の記述（31 件）も改める。
  - SPEC §23 は変更しない。

## 10. 診断の分離と縮小

### 10.1 分離（本計画の必須部分）

- 意味判定のコードが作るのは、型付きの問題の値だけにする。中身は、コード、主位置と関連位置のアンカー、SPEC が要求する Reason の事実である。
- メッセージ、ラベル、Note、Advice、関連位置の役割、修正候補は、診断公開アダプターだけが作る。アダプターは問題の値と位置表から作り、意味を再計算しない。
- その結果、次のものを削除する。
  - Binding の `ReportIssue` の 61 分岐と、`BindingFailure` から診断コードへの 86 分岐。
  - 遅延確保される診断専用の補助表（約 45 個）と、そのリセット処理。
  - 解析内の説明文。
- Semantics ケースの合併、問題の単位（§23.3.6.4）、前提の扱いは、現在の公開上の挙動を保つ。

### 10.2 pre-alpha の間の縮小（決定事項 D3）

- **保つもの**: SPEC が要求する事実（§23.3.6.5 の Origin 関係、`Owned`、`UnprovenOriginContract` の Reason など）と、構文の診断（表駆動のもの）。
- **作らないもの**: それ以外の Advice、Note、修正候補を、pre-alpha の間は新たに作らない。
- **既存のものの扱い**: 専用の補助表や構文の形の解析を要するもの（例: `IsStringJoin` / `StringJoinAdvice` 約 120 行）は削除する。表の行だけで作れるものは、公開アダプターへ移す。
- **仕様変更**: SPEC の各章には、説明内容の個別要求がある（第 4・7・8・10・11・15・17 章など）。これらを「事実」と「推奨される説明」に分け、後者を pre-alpha の間は任意にする仕様変更が要る。採用する場合は、変更理由と原則との整合を記録し、`draft/INTEGRATED.md` に取り込みを記録する。
- **効果の推定**: Binding で 3,000〜5,000 行、テストで 1,000〜2,000 行の削減。

## 12. 検証と計測

- **この文書について**: 文書のみの変更なので、ビルドとテストは実行しない。
- **実装の検証**:
  - 各単位で、関係するクラス、フィクスチャ、マイルストーンを選んで Unit 検証を行う。
  - セッションの終わりに Session 検証を 1 回行う（[VERIFICATION](../../docs/dev/VERIFICATION.md)）。NativeAOT は実行しない。
- **差分比較ハーネス**（M3〜M6 の間だけ存在する）:
  - 全テスト入力とマイルストーンを両方の経路でコンパイルし、次を比較する: 受理されるかどうか、診断のコードと位置、O0 / O2 の実行出力。
  - 結果は `artifacts/verify/` に置く。差分は SPEC で裁定する。旧経路の出力との一致を、成功の唯一の基準にはしない。
- **フィクスチャ**: ネイティブフィクスチャの期待 IR は、生成器の変更に伴って作り直す。挙動は実行出力で判定する。
- **計測**:
  - 既存の固定ワークロード（借用の格納、検査継続、ペアのケース、ジェネリック既定値、要素 Place、Origin 証明、関連型の推論、オブジェクト、Hover）で、冷えた状態と温まった状態のコンパイル時間、割り当て、保持容量、入力規模に対する伸びを計る。
  - 割り当てとゼロ割り当ての回帰（`Purpose=Allocation`）は条件を緩めない。MIR の作業領域は再利用して、温まった状態での再解析のゼロ割り当てを保つ。
  - 予想される改善: ケース・インスタンス・既定値ごとの再構築がなくなる。根ごとの Loan フローがビット集合データフローになる。`GetInputState` のブロック先頭からの再生（二乗の計算量）がなくなる。ControlFlowAnalysis の全体再実行がなくなる。ただし、改善は計測でのみ主張する。
- **規模**: 規模は、10-09 計画の基準（`artifacts/benchmarks/compiler-reorganization-2026-10-09/`）と同じ範囲と方法で計る。ファイルの分割、改行の変更、コメントの削除は削減として数えない。

## 13. 完了条件

1. Binding と MIR 構築器以外に、構文ノードの型を判定するコードと `.Source` から意味を読むコードがない。
2. MIR の解析、単相化、生成が、Binding のメソッドを呼ばない。
3. 構文ノードに意味メンバーがない。Binding が合成構文ノードを作らない。
4. 本体は定義ごとに 1 回だけ構築される。Semantics ケース、インスタンス、既定値の呼び出しで再構築しない。
5. 記述子表がすべての MIR の種類を網羅し、解析ごとの手書きの分類器がない。
6. 未対応のコードは `Unsupported_Kd` の 1 つだけで、すべての記録が位置を持つ。`Language` / `Internal` コードで実装制限を報告していない。
7. 意味判定のコードが説明文を作らない。
8. 手書き IR にライブラリのアルゴリズム（Array の変更、文字列比較）がない。
9. 合計行数が上限以内で、各領域が §1 の上限以内である。
10. Session 検証、選択したネイティブフィクスチャ、マイルストーン、固定ワークロードの計測が通り、証跡がコミットに対応している。
11. CODEMAP、COMPILER_ARCHITECTURE、DIAGNOSTICS、STATUS が実装と一致している。

再構成の後は、§8.6 の手順を通常の作業規則に加える。レビューでの問いは「この機能は、計画 1 つ、翻訳 1 つ、記述子の行 1 つ以下で追加されているか。追加されていなければ、それはなぜか」である。

## 15. リスクと対応

| リスク | 対応 |
| --- | --- |
| 借用検査の受理範囲が変わる | 差分比較ハーネスで全差分を分類し、SPEC で裁定する。等しい Origin、独立した入力、スロットと内容の権限、最後の保持者の回復についての既存テストを保つ。SPEC が曖昧な箇所は、仕様の明確化として扱う |
| 二重経路の期間が長引く | M2〜M6 を集中期間とし、凍結（D5）と中止条件を設ける。経路ごとの恒久的なフォールバックは作らない |
| 部分実装を外すことでマイルストーンが後退する | M0 で依存関係を一覧にし、一般化するか `Unsupported` にするかを単位ごとに決める（D2）。STATUS を正確に保つ |
| MIR の追加によって割り当てと保持量が増える | 配列の組で表現し、作業領域を再利用し、生成後に MIR を解放する。インスタンスごとに複製しない。固定ワークロードで計測する |
| 検査専用の経路の意味が変わる | `CheckOnly` の辺と 2 種類のデータフローで表し、`ContinuationVerificationTest` などの既存テストで確認する。実行時の配置と後片付けに検査専用の状態を混ぜない |
| Semantics ケースや既定値の文脈が崩れる | ケースマスクと `Scope` の解釈文脈で明示する。SETTLED の 2 項目（インスタンス評価の既定値、全ケース共通のペアスロット前提）の理由を保つ |
| 診断の質が下がる | SPEC が要求する事実と構文の診断は保つ。縮小は D3 の決定と仕様変更を経て行う |
| 並行するセッションが衝突する | 新しいフォルダーで作業し、ステージするファイルを明示する。M7 の並行作業は `BodyFacts` の外側に限る |
