# `do` のラベルなし `exit` — 仕様変更案・実装計画

2026-10-17。所有者採用済み。正式仕様への取り込み・実装は未実施。実装開始は **R9完了後**。

## 1. 目的と適用範囲

所有者の指示により、本書が変更すると明記した事項では、[SPEC.md](../../docs/SPEC.md) とその参照先より本書を優先する。
変更しない事項には既存仕様を適用する。本書の作成では正式仕様・コンパイラーを変更しない。
正式仕様への取り込みは別途の指示で行い、実装はR9完了後に本書に従って進める。

すべての `do` をラベルなし `exit` の対象にする。単に値を返すためだけのラベルを不要にし、
ラベルは通常選ばれない外側の対象を指定する場合に使う。

```kimi
let answer = do
    let value = 42
    exit value
```

現行の [§14.1](../../docs/spec/14-control-flow.md#141-completions) は既に `do` が値付きの `Exit` を受け取ると定める。
制限は [§14.3](../../docs/spec/14-control-flow.md#143-do-and-unsafe) と §14.5.2 の対象探索にある。
必要な意味 → 制限 → 所有者 → 不要になるもの、の対応は次の一つである。

> `do` は名前がなくても自分への終了結果を受け取れる → ラベルなし探索だけが `do` を飛び越える
> → 制御転送先を決める共通の解決処理で対象集合を揃える → `do` 専用のラベル必須規則が不要になる。

| 原則 | 本書での適用 |
| --- | --- |
| One Concept, One Canonical Form | 既存の `exit` を使う。値返却用の別構文・別モードを追加しない。 |
| Local Reasoning | 対象は構文の入れ子で一度決定し、型や到達可能性から選び直さない。 |
| Explicit Semantics | 終了は `exit`、外側への終了は `exit to`、Non-Copy値の転送は `@move` で示す。 |
| Compiler Server Protocol | 解決した対象とソース位置を既存の意味情報で公開し、後続処理で再探索しない。 |

## 2. 変更後の仕様

### 2.1. 対象の決定

ラベルなし `exit` は、現在位置を本体内に含む最も内側の `for`・`while`・`loop`・`do`・`defer` を対象とする。
関数境界とDeferred Block境界は既存の §14.5.2 に従う。対象がなければ言語エラーとする。

次の条件は対象選択を変えない。

- `do` のラベルの有無、および単一項目本体 `=> item` とインデント本体の違い。
- `exit` のオペランドの有無、型、期待型、到達可能性。
- `do` の結果を使う文脈（Value Context）か、捨てる文脈（Discard Context）か。

対象を決めてから結果型を検査する。型が合わなくても外側を探し直さない。
`exit` は `exit ()` と同じであり、どちらも最も内側の対象を終了する。

| 制御転送 | ラベルなしの対象 | 名前付きの対象 |
| --- | --- | --- |
| `exit` | `for`・`while`・`loop`・**`do`**・`defer` | `for`・`while`・`loop`・`do` |
| `continue` | `for`・`while`・`loop` | 同左 |
| `yield` | `if`・`match` | 同左 |
| `return` | 関数境界 | なし |

変更は太字の `do` の追加だけである。名前付き転送は既存の名前解決と対象種別の検査を保つ。
`if`・`match`・`unsafe`・`require` は `exit` の対象にならず、単なるインデント本体も対象にならない。
構文が対象になるのはその本体内だけであり、条件・列挙元・ガード内からその構文を対象にはできない。
その位置に書かれた `do` の本体からは、その `do` を対象にできる。

`do` は反復しないため `continue` の対象にしない。`return` と `try` の失敗伝播は、既存規則どおり関数へ向かう。
入れ子の関数・クロージャーから外側の `do` へ転送できず、既定引数から宣言の外側へ転送することもできない。
`$expect` / `$require` の `message:` 内も、[§17.6.3](../../docs/spec/17-failure-handling.md#1763-message-and-observed-values)
の外向き転送禁止を保つ。メッセージ内の `do` は終了できるが、メッセージ外の対象へは転送できない。

### 2.2. 結果・所有権・後始末

[§14.2.2](../../docs/spec/14-control-flow.md#1422-evaluation-contexts-and-body-results)、
[§14.9](../../docs/spec/14-control-flow.md#149-result-validation)、
[§16.2](../../docs/spec/16-scope-exit-and-destruction.md#162-scope-exit) をそのまま適用する。

- 自分を対象とする `exit` のオペランドが `do` の結果源になる。省略したオペランドは Unit。
- インデント本体の末尾式は引き続き捨てる。構造上、末尾へ通常到達する経路があれば Unit が結果源になる。
- 値を使う文脈では、既存の期待型・共通型の規則で結果型を決める。到達不能な結果源も検査し、Neverの規則も変えない。
- 結果を捨てる文脈の `do` の対象結果型は Unit。`exit 42` を黙って捨てる規則は追加しない。
- オペランドを評価・取得して結果を確保し、実際に去るスコープを内側から後始末して、対象へ結果を届ける。
  Non-Copy値の Move、借用の寿命、後始末による結果配送の阻止は既存規則に従う。

```kimi
func choose(ready: bool) -> i32
    return do
        if ready => exit 42
        exit 0

let unit: () = do => exit       // 有効。exit () と同じ。
let value = do => exit 42       // 有効。i32。

do => exit 42                   // エラー。捨てる文脈の対象結果型は Unit。

func incomplete(ready: bool) -> i32
    return do
        if ready => exit 42
        ()                     // エラー。通常終了の Unit は i32 に合わない。
```

例は独立した断片であり、エラーと記した例は不受理を要求する。

### 2.3. 入れ子とラベル

内側の反復構文はその `exit` を受け取り、内側の `do` もその `exit` を受け取る。
外側の対象を終了するにはラベルを指定する。ラベルを追加・削除してもラベルなし転送の対象は変わらない。

```kimi
func findPositive(values: ref/Array<i32>) -> i32
    return label search: do
        for value in values
            if value > 0 => exit to search value
        exit 0
```

この例の名前付き `exit` は `for` を越えて `do` を終了する。末尾の `exit 0` は同じ `do` を対象とする。

### 2.4. Deferred Block

`defer` の本体は Unit を返す終了対象かつ外向き転送の境界であり続ける。
ラベルなし `exit` がそこへ到達する前に内側の `do` が見つかれば、その `do` を終了する。
内側の対象がなければ、従来どおり `exit` / `exit ()` がDeferred Blockを終了する。
名前付き転送でDeferred Block境界を越えること、および `defer` 自体へのラベル付けは許可しない。

入れ子を越えて後始末の処理全体を終了したい場合は、既存のラベル付き `do` を使える。

```kimi
func cleanupExample(skip: bool)
    defer
        label cleanup: do
            do
                if skip => exit to cleanup
            Console.writeLine("Finished")
    ()
```

`cleanup` を抜けた後も、そのスコープの後始末は実行する。元の保留中の結果・制御転送は置き換えない。
追加した `do` は実際のスコープなので、変数の可視性と `defer` の登録先を確認する。

## 3. 互換性と採用理由

### 3.1. 意味が変わる既存コード

これは受理範囲の拡大だけでなく、既存のラベルなし転送先を変える仕様変更である。

```kimi
loop
    do
        exit
    Console.writeLine("Continued")
```

現行仕様ではループを終了する。本書では `do` だけを終了し、出力して反復する。
どちらも Unit なので型検査では変化を検出できない。旧動作を保つ場合はループにラベルを付けて `exit to` を使う。
`defer` 内も §2.4 に従って移行する。新しい `do` で既存コードを囲む編集にも同じ注意が必要である。

移行監査は `exit`、`exit ()`、値付き `exit`、ラベル付き・なしの `do`、入れ子を含める。
ソース・テスト・ライブラリ・milestone・現在有効な例示を対象とし、各転送の旧対象と新対象、去るスコープを確認する。
正規表現検索だけで監査完了とはしない。意味保存を意図する例には明示ラベルを付け、新規則を示す例には期待する対象を記録する。
凍結済みの過去文書は書き換えない。互換モード、型による再探索、永続的な旧規則の複製は追加しない。

### 3.2. 利点・代償・不採用案

不要なラベル名を減らし、単一式から複数行への展開と条件付きの早期結果を簡潔にする。
`do` が終了対象であることをラベルの有無によらず揃えられる。
代償は、`do` が外側の `exit` に対して透明なスコープではなくなることと、既存コードの移行である。
新しい構文・結果表現・実行時機構を必要としないため、この代償に見合う改善と判断する。

| 不採用案 | 理由 |
| --- | --- |
| 値付き `exit` だけ `do` を対象にする | `exit` と `exit ()` の同値性を壊す。 |
| 値を使う文脈の `do` だけ対象にする | 式を束縛するか捨てるかで内部の転送先が変わる。 |
| 型が合う対象を外側へ探す | 対象決定を型推論に依存させ、失敗後の再探索を導入する。 |
| `do` を `yield` の対象にする | 内側の `if` が `yield` を受け取り、条件付き早期終了が煩雑になる。 |
| `do` 専用、または全本体への末尾式結果の導入 | 前者は本体規則の例外、後者は広範な再設計になる。今回の変更には不要。 |
| `yield` を廃止して選択も `exit` に統合する | `if condition => exit` でループや `do` を抜けられなくなる。 |

同じ原因を持つ箇所は、対象解決と、その結果を利用する結果源収集・完了判定・診断・IR公開・生成である。
実装時に共通解決処理の全利用箇所と独自の親探索を検索し、対象決定を一か所に保つ。

選択するのは既存の所有者内での規則修正である。共有構造に新しい対象種別・能力表を加える案は、
既に `do` の終了先と結果が表現されているため採用しない。新しいモード引数、機能専用の表、転送種別は不要。
R9後の表現がこの前提と異なる場合は、実装者が局所的な回避を加えず、設計へ差し戻す。

削除対象は `do` をラベルなし探索から除く規則と重複判定、および旧仕様だけを理由にした不受理期待である。
名前付き終了、結果検査、借用・破棄の検査は残す。規則変更は小規模を見込むが、行数や速度改善は断言しない。
同じ対象へ転送する名前付き版と同等の生成コード・メモリー割当てを期待し、§4.3で確認する。
