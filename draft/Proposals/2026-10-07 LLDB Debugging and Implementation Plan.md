# LLDB によるデバッグ機能の仕様変更案・実装計画

日付：2026-10-07。状態：方針決定済み。正式仕様への取り込み・実装・動作検証は未実施。

## 1. 位置付けと目的

本書に明記した変更は、[SPEC.md](../../docs/SPEC.md) およびその参照先（[IMPL.md](../../docs/IMPL.md) を含む）より優先する。本書で変更しない事項には既存仕様を適用する。デバッグの対応範囲は言語の合法性や実行時の意味を狭めない。

目的は、LLVM・LLDB・Visual Studio Code の標準機能を最大限利用し、Kimigayo のソース上で停止・実行制御・値の確認を行えるようにすることである。独自実装は、コンパイラの情報出力、ビルドと起動の接続、必要な型表示に限定する。

本作業は本書の作成のみとし、正式仕様と既存ファイルは変更しない。後日の正式取り込みでは変更を各所有節へ統合し、`draft/INTEGRATED.md` に対応を記録する。採用方針、仕様への取り込み、検証済みの実装対応は区別する。

## 2. 採用構成と初期範囲

### 2.1. 責務分担

```text
Kimi コンパイラ → デバッグ情報付き LLVM IR → llc / lld-link → EXE + PDB
Kimi 拡張 → 公式 LLDB DAP 拡張 → lldb-dap / LLDB → 対象 EXE
                  ↕
          VS Code 標準デバッグ UI
```

| 担当 | 責務 |
| --- | --- |
| Kimi コンパイラ | ソース位置・関数・型・変数・有効範囲を LLVM の標準形式で出力する |
| LLVM / LLD | 機械語、CodeView、PDB を生成する |
| LLDB / `lldb-dap` | 停止・再開・ステップ・スタック復元・値の取得と DAP 通信を行う |
| 公式 LLDB DAP 拡張 / VS Code | アダプターの起動、標準デバッグ UI、ターミナルを提供する |
| Kimi 拡張 | 入力の選択・保存、ビルド、今回の成果物の取得、起動設定とセッションの管理を行う |
| Kimi 用 formatter | LLDB の summary / synthetic children を用いて必要な型表示を補う |

新規デバッガーエンジン、独自 DAP サーバー、独自シンボル形式、LLDB の fork、専用デバッグ UI は初期構成に含めない。通常の型情報で表示できる型に formatter を追加しない。

### 2.2. 初期対応の完了範囲

初期目標は §7 の D0〜D3 全体とする。D1 の基本操作だけでは初期対応完了としない。

- Windows x64 の Application を、O0 で新規起動してデバッグする。
- F5、行ブレークポイント、継続、一時停止、ステップイン・オーバー・アウト、関数名付きコールスタック、停止・通常終了、統合ターミナルを扱う。
- 引数・ローカル変数・確定したループ／パターン束縛について、名前・型・スコープ・取得可能な値を表示する。
- §5 の型表示を、コンパイラが実行生成をサポートする具体化とその組合せに提供する。未実装の言語機能は別の実装課題として記録し、デバッグ対応を理由に仕様上不正としない。

O2 でのデバッグ品質、attach、remote、core dump、テスト実行への専用統合、Task の論理スタック、`obj` 系の動的型表示、クロージャの専用表示、Kimigayo の任意式評価、値の編集、詳細な所有権・Loan 可視化は初期完了条件に含めない。LLDB の標準機能として利用できる操作を独自に作り直すこともしない。

## 3. 設定と起動の契約

### 3.1. 三つの独立した設定

| 設定 | 通常の既定 | Kimi の F5 起動時の既定 |
| --- | --- | --- |
| 意味上のモード | 既存の Release（`--Debug false`） | Debug（`--Debug true`） |
| `Optimization` | 既存のプロジェクト設定。未指定は `O2` | `O0` |
| `DebugInfo`（追加） | `false` | `true` |

`--Debug` は条件コンパイルの既存の意味を維持する。`DebugInfo` はデバッグ情報を出力する独立した真偽値とし、`.kimiproj` に同名の設定を追加する。公開設定に行情報用・型情報用などの段階別モードは設けず、実装段階による対応差は STATUS に記録する。

ソースを処理する `emit`、`build`、ビルドを伴う `run` に `--Optimization O0|O2` と `--DebugInfo true|false` を追加する。明示 CLI 値、プロジェクト値、既定値の順で一度だけ有効設定を確定し、全工程で共有する。F5 は必要な上書きを CLI に渡し、プロジェクトファイルを書き換えない。

意味上の Release とデバッグ情報ありの組合せも認める。Kimi のデバッグ起動設定に `semanticMode: "debug" | "release"` を設け、既定を `debug` とする。これは既存の `--Debug` へ変換する設定であり、第三の言語モードではない。

`build --Manifest` は生成設定を manifest から取得し、これらの上書きを認めない。`run --no-build` の `--Optimization` は既存成果物の選択・照合にのみ使い、生成や再ビルドを行わない。`--DebugInfo` は生成を伴う経路でのみ受け付ける。既存 EXE の直接実行には、これらの設定を受け付けない。通常の Build / Run / Ctrl+F5 の既定と既存の失敗時動作は維持する。

例えば、意味上の Release のままデバッグ情報付き O0 を生成し、そのビルド記録を検証して通常実行する場合は次のようになる。以下は追加予定の CLI 例であり、現在の対応を示すものではない。

```powershell
kimi build App.kimi --Optimization O0 --DebugInfo true
kimi run App.kimi --no-build --Optimization O0
```

### 3.2. VS Code からの起動

1. 既存の対象選択・信頼済みワークスペース確認・保存処理を使い、`.kimi` または `.kimiproj` と一つの Application／target を確定する。曖昧な候補から最初のものを選ばない。
2. §3.1 の設定でビルドする。失敗・保存中止・キャンセルなら起動しない。
3. §4.2 の今回のビルド結果を取得し、成果物の対応を確認する。
4. 公式拡張へ起動設定を渡し、`lldb-dap` が EXE を起動する。Kimi の `run` で先に起動してから attach する方式は採らない。
5. 終了・停止・起動失敗のいずれでもセッションの資源と保持を解放する。Stop／キャンセルは、この起動で開始した対象を終了させ、detach して残さない。Pause は対象を保持した一時停止とする。起動完了前のキャンセルも後続の起動を防ぐ。

Kimi 側の `program` は既存同様にソース／プロジェクトを指定し、省略時は対象選択を使う。公式 LLDB 設定の `program` は生成 EXE を指定する。この二つを混同しない。F5 の設定解決は VS Code と公式拡張の公開 API で接続し、見かけだけの親デバッグセッションや DAP の独自中継は追加しない。

デバッグ起動の `args`、`cwd`、`env` は標準 launch 設定へ渡す。既定の `cwd` はコンパイラが確定したプロジェクトディレクトリとし、出力先ディレクトリから推測しない。標準の `sourceMap` と統合ターミナルを利用する。

実行可能命令のない行では、LLDB が解決した位置と未解決状態を標準 UI に反映する。要求したすべての行で必ず停止するとは保証しない。`stopOnEntry` のネイティブ入口 `__kimi_start` と、最初のユーザーソース行も区別する。

## 4. 情報生成・成果物・配布

### 4.1. LLVM デバッグ情報

- Lowering でソース文書・位置・関数・スコープ・変数の対応を確定し、閉じた `EmissionModule` に保持する。LLVM writer は AST、Binding、ownership state を再参照しない。
- LLVM の compile unit、file、subprogram、location、type、local variable と debug record を使う。型名と物理レイアウトを区別し、同名の別モジュール型やジェネリック具体化が混同されない識別を保つ。
- 生成した起動処理・補助関数・命令には人工的な位置の扱いを適用し、実在しないユーザー位置を付けない。明示された破棄・defer の位置とコンパイラ内部の補助処理を区別する。
- Abort の位置文字列は従来どおり別用途とする。ソース位置の事実を共用しても、それをデバッグ情報の代用にはしない。
- `DebugInfo=false` の経路でデバッグ専用の表や文字列を収集しない。有効時も ID・共有表・再利用バッファを優先する。情報付加によってプログラムの受理、所有権、ABI、初期化・破棄の意味を変更しない。

### 4.2. ビルド結果と成果物の対応

`DebugInfo=true` では CodeView 付きオブジェクトを生成し、`lld-link` に PDB の出力先と最終参照先を明示する。一時 EXE 名に由来する壊れた PDB 参照を残さない。以下の PDB の生成・検証・保持はこの設定の場合に必須とし、`false` の結果では PDB をなしと記録して旧 PDB を関連付けない。

EXE、PDB、IR／manifest、有効設定、入力ソース、formatter 互換情報を同じ成功ビルドに関連付ける。既存の処理記録の識別子を利用し、ファイル名だけを同一性の根拠にしない。必須項目を追加する manifest／記録は schema を更新し、旧形式を成功扱いして読み飛ばさない。

`build` に任意の `--Report <path>` を追加し、既存のビルド結果を機械可読な JSON として出力する。人向けログと別に、次を契約とする。

- schema、成功／失敗、今回の処理記録の識別子。複数結果を返す場合は各成果物を明確に識別する。
- 実際に解決したローカルの EXE／PDB の絶対パス・ハッシュ、`cwd`、有効設定、入力識別への参照。
- デバッグ情報ありの結果では、Kimi が解決した `lldb-dap`／formatter の場所と必要なソースパス対応。

LLDB／formatter の場所は起動準備の情報であり、デバッグ情報付きコンパイル自体にはデバッガーの起動を必要としない。このローカル起動用の値と、証跡公開用に秘匿化したパスを区別する。拡張は `.kimiproj`、manifest、`Built:` ログを独自解釈せず、今回要求した結果から一つの Application を取得する。古い report を再利用せず、正常終了と対応する成功 report の両方を要求する。失敗・中断・欠落した report からは起動しない。

成果物を完成させてから成功記録を最後に公開する。開始時の失効、部分生成時の失敗、ハッシュ検証、immutable record／active pin は既存の原則を適用する。デバッグ中は対象 EXE／PDB を保持し、他ウィンドウや CLI のビルドで置き換わらないようにする。現在の拡張内ディレクトリロックだけでプロセス間の保護を保証しない。

ソースは実際にビルドした入力の識別と checksum に関連付ける。`sourceMap` はパス変換であって内容一致の証拠ではない。起動前に入力の不一致を検出したら再ビルドするか中止し、実行中の入力編集では旧ビルドを実行中であることを通知して再開始を案内する。編集後の行へ自動で位置を読み替えない。O2 の既存パス秘匿化も、デバッグ情報を破壊しないように扱う。

### 4.3. ツールチェーンと拡張の配布

`src/kimi-ext/package.json` に次の必須依存を指定し、インストールを VS Code に任せる。

```json
"extensionDependencies": ["llvm-vs-code-extensions.lldb-dap"]
```

公式拡張は `lldb-dap` 本体を同梱しないため、Kimi の `toolchain` に `lldb-dap.exe`、必要な LLDB ライブラリ・DLL・Python 関連ファイル、Kimi 用 formatter とライセンスを含める。利用者の Python インストールを前提にしない。

探索・選択・setup・配布・明示的検証は Kimi が管理し、拡張へ重複実装しない。セッションの `debugAdapterExecutable` で絶対パスを渡し、利用者のグローバル設定を書き換えない。Marketplace へ接続できない環境では依存拡張の VSIX も別途必要になる。

調査時の compiler profile は LLVM 22.1.8。これと整合する LLDB 配布・依存関係・公式拡張の対応版を D0 で確認して採用する。`extensionDependencies` は版固定の仕組みとはみなさず、利用する公開 API／設定の対応版を記録・検証する。

setup／`kimi toolchain verify` の対象をデバッガー一式へ拡張する。setup がダウンロードを行わない既存契約と、通常の build／起動で毎回ツールの版・ハッシュを検証しない原則を維持する。必要ファイル不足や起動不能は明確に報告する。formatter と生成レイアウトの互換識別はビルド結果に結び付け、異なる版を推測で解釈しない。

## 5. 型表示の契約

### 5.1. 初期の保証対象

下表は有効な値を取得できる停止地点での表示契約である。汎用的な内部表現の展開と、Kimi 向けの論理表示を区別する。

| 型 | 表示内容 |
| --- | --- |
| 基本型 | 型名と値。整数の幅・符号、真偽値、浮動小数点、ゼロサイズ値を混同しない |
| 構造体・タプル | 型名、フィールド名／要素番号、各部分の取得可能な値 |
| 固定配列 `[N of T]` | 型・長さ・要素。穴や部分 Move の扱いは §5.2 に従う |
| `string` | 長さと文字列の要約。埋め込み NUL、Unicode、長い値の省略を扱う |
| `Slice<T>` / `UniqSlice<T>` | 型・現在の長さ・範囲内の要素。共有／排他の違いを保持する |
| `Array<T>` | 型・長さ・初期化済みの論理要素。capacity の未使用領域を要素として表示しない |
| `Dictionary<K, V>` | 型・件数・有効な key/value。空き・削除済みスロットを除外し、順序の新しい保証を導入しない |
| enum（`Option` / `Result` を含む） | 型・有効な Case・その payload。非活性 Case の領域を値として展開しない |
| `ref/T` / `uniq/T` | 参照の型・層を保持し、取得可能な参照先を展開する。ハンドルの参照と要素への参照を混同しない |

上記のジェネリック具体化、入れ子、空の値にも同じ規則を適用する。Slice と UniqSlice を対として扱い、独立した表示規則を増やさない。

対象外の型には、取得できる型名・標準の内部表示を提供できる。`obj` 系・クロージャ・Task の専用表示を、部分的な内部表示だけで対応済みとしない。Property の getter など、呼び出しが必要な値は自動評価しない。

### 5.2. 有効性・読み取り・負荷

- formatter は停止中のメモリとデバッグ情報を読む。表示のためにユーザー関数、getter、Iterator、文字列化関数を実行しない。対象プロセスのメモリを書き換えない。
- 変数のスコープと値の有効範囲を区別する。Move・破棄・通常の未初期化・再初期化に応じて位置記録を終了／再開し、残存ビットを現在の有効な値として見せない。
- 分岐合流や部分 Move で状態を確定できなければ保守的に取得不可とする。確定できる部分だけを表示できるが、不完全な aggregate を完全な値として要約しない。取得不可を初期対象型全体の未実装の代用にしない。
- `noinit` と unsafe／raw 操作の既存の責任分担を維持する。追跡していない初期化、任意の破損や dangling の完全検出は保証しない。独自の実行時初期化 bitmap や所有権追跡機構を追加しない。
- 読み取り失敗、型／レイアウト不一致、不正な長さや tag は、空・ゼロ・別の Case に置き換えず、取得不可として区別する。互換な範囲だけ標準の内部表示へ戻せる。
- summary の文字数、子要素数、探索量、展開深さを制限し、省略を明示する。標準の遅延展開／ページ指定を利用し、Dictionary の疎な領域にも走査量の上限を設ける。循環参照で無限展開しない。
- 再開・次の停止・フレーム変更では取得済みの値やキャッシュの有効性を更新する。compiler と formatter に独立した手書きの ABI 定義を持たず、既存のレイアウト定義を共有またはそこから生成する。

これらは自動表示の契約である。利用者が Debug Console で明示的に行う LLDB コマンドや任意メモリ操作に、Kimigayo の安全性保証を与えるものではない。標準の Watch／条件式を、Kimigayo 構文の評価対応とは表示しない。

## 7. 実装単位と完了条件

| 段階 | 主な作業 | 完了条件 |
| --- | --- | --- |
| D0：組合せの実証 | 採用版 LLDB の配布確認。小さなネイティブ例と Kimi 例で PDB・行情報・代表的な型情報を生成し、公式 DAP と formatter を接続する | 行停止・ステップ・スタックに加え、enum payload、generic collection、参照、ゼロサイズ値、位置の無効化が成立する。LLVM の言語 tag／型名の互換表現も確定し、Kimi の意味を別言語の式評価で代用しない |
| D1：基本デバッグ | §3〜4 の設定、生成、成果物、配布、F5 とセッション終了を実装する | 対象選択から停止・終了まで標準 UI で動作。未解決 breakpoint、ビルド失敗、キャンセル、旧成果物、別ビルドとの競合を正しく処理する |
| D2：基本的な値 | 型・変数・スコープ・位置の記録、基本型・構造体・タプル・固定配列の表示を実装する | 同名変数、引数、入れ子スコープ、再代入、Move／partial Move／再初期化、分岐合流、破棄で名前・型・値・取得不可が正しい |
| D3：Kimi の型表示 | §5 の残りを標準情報と必要最小限の formatter で実装する | 保証対象の具体化・組合せについて、通常値・空・大きな値・入れ子・読み取り失敗・非活性領域を確認。ユーザーコードを実行せず、有界な表示である |

D0 の実証不足を D3 まで先送りしない。方式が成立しない場合は未解決条件と実証結果を記録し、既存機能で解けるか再検討する。未検証の LLDB fork や独自 DAP を暗黙に導入して完了としない。

主な実装入口は [CODEMAP](../../docs/dev/CODEMAP.md) に従う。生成は `BodyLowering` → `EmissionModule` → `LlvmModuleWriter`、成果物は `EmissionArtifacts`／`NativeToolchain`、配布は `ToolchainResolver` と backend setup、拡張は `src/kimi-ext` の対象選択・command runner・起動連携を拡張する。既存の実行専用 `RunAdapter` にデバッガー本体を実装しない。

## 8. 検証と記録

1. **情報の検査**：採用版 LLVM で IR を検証し、CodeView／PDB のファイル・行・関数・型・変数・位置を検査する。PDB の存在だけで合格にしない。
2. **DAP の確認**：独立した期待値で停止位置・スタック・値を確認する。通常終了、Pause／Stop、起動失敗、キャンセルに timeout と後片付けを設ける。
3. **VS Code の確認**：分離した profile と公式拡張で F5、breakpoint、各ステップ、変数展開、統合ターミナルを確認する。単一ソース／プロジェクト、空白・日本語パス、ソース変更、EXE／PDB 不一致、依存ファイル不足を含める。
4. **回帰・負荷**：同じ意味上のモード・最適化でデバッグ情報の有無による実行結果と破棄順序を比較する。既存 O0／O2 回帰を維持し、デバッグ操作の初期保証は O0 と区別する。情報なしの allocation／reuse と、情報あり・formatter の記憶量／走査量の上限を検証する。時間測定は Benchmark に分離する。

実装単位ごとに関連 Unit Verify、セッション末に Session Verify を行い、拡張変更にはその unit／integration tests を併用する。診断の追加・変更には既存の診断開発手順を適用する。NativeAOT テストは実行しない。

結果・失敗・未確認事項は `artifacts/verify/`、測定は `artifacts/benchmarks/`、配布物は `artifacts/packages/` に保存する。証跡にはソース／設定／EXE／PDB／compiler・LLDB・formatter・公式拡張の版と識別を結び付ける。

後日の実装・正式取り込みでは、該当する SPEC／IMPL、STATUS、CODEMAP、PLAN、README の VS Code 手順、拡張 CHANGELOG を各責務に従って更新する。公開宣言を変えない限り LIBRARY は変更しない。D3 の必須項目に未解決が残る場合は、その範囲を明示して初期対応を未完了とする。
