## 1. 位置づけと方針

**本書の変更事項は、[SPEC.md](../../docs/SPEC.md) およびその参照先より優先する。変更しない事項には既存仕様を適用する。** 本書の作成時点では、正式仕様・実装・既存提案は変更しない。将来の取り込みでは正式仕様を自己完結させ、本書への依存を残さない。

2026-10-08 のレビューで、補完は「Hover と共通の採用済み解析集合」を使う方針に決まった。本書はこの方針で全体を作り直したもので、旧版の規則をすべて置き換える。

LSP にコード補完（code completion）を追加する。補完は、Hover と同じ**採用済み解析集合**（§2）を読む。要求を処理するときに、コンパイル、構文解析、Binding、ディスクの読込みはしない。チェックの予約・開始・完了待ちも変えない。

設計の優先順位は次のとおり。

1. 要求処理の速さ。定常状態では、応答オブジェクト以外を割り当てない。
2. チェックに追加される費用の小ささ。通常の CLI コンパイルには費用を課さない。
3. 候補の精度。

精度は、次の形で明示的に下げる。候補は**代表単位**（§3.2）一つの、解析時点での到達可能性だけを表す。他の参加単位と一致すること、現在のコードで合法であること、最新であることは保証しない。精度を下げた点の一覧は §7.2 にある。

名前・アクセス・型・所有権の言語規則は変えない。補完は文字列を挿入するだけで、その結果が妥当かどうかは次のチェックの診断が判断する。

## 2. 共通基盤：採用済み解析集合

Hover の参加単位・採用・保持・編集対応の規則（SPEC §23.4.11.4–6）は、機能を問わない共通規則として扱う。Hover と補完は、どちらもこの集合を読むだけの機能になる。機能ごとに採用・保持の規則を持つことはしない。

### 2.1. 構成

開いて同期している `.kimi` 文書ごとに、採用済み解析集合を高々一つ持つ。

| 要素 | 内容 |
| --- | --- |
| 参加単位 | 単位キーを正準順に並べたもの。正準順は §23.4.7 の contributor の順（プロジェクト識別、単位種別、ターゲット）。各単位について、採用した結果の世代も持つ |
| 編集支援投影 | 各参加単位がその文書について作った不変データ。Hover 部と補完部を持ち、どちらも独立に欠けることがある |
| 編集対応表 | 採用後に行われた編集を記録する（§2.4） |
| 現在フラグ | 採用・再検証の直後に真になり、編集・保留で偽になる。Hover の前回表示の判定に使う |

### 2.2. 参加単位と採用

SPEC §23.4.11.4 の Participants と Adoption を、そのまま共通の規則にする。

- **参加単位**：その文書を自身のソースとしてチェックする、全プロジェクトの required unit すべて。結果をまだ持たない単位も含む。依存として読むだけの consumer は含めない。TestSources 専用の文書をチェックしない Product 単位も含めない。
- **採用**：次の条件がそろったとき、集合を一括で採用する。
  - 文書の所属と、空でない参加集合が確定している。
  - 全参加単位が、有効な Completed 結果を持つ。
- **採用の補足**：
  - Accepted である必要はない。単位ごとに結果の生成時刻が違ってもよい。
  - 未完了・held・Blocked・Faulted の単位を除外して採用することはしない。
  - 編集支援投影の各部が欠けていても採用する。部の欠落は、その機能を使えなくするだけである。
- **再評価の時期**：採用・入力の再検証・参加集合の確定や変化のたびに再評価する。診断が通知されたかどうかとは関係しない。

### 2.3. 保持と破棄

SPEC §23.4.11.5 の表を共通規則にする。

| 事象 | 扱い |
| --- | --- |
| 全参加単位の新しい結果がそろった（再検証だけで回復した場合も含む） | 一括で置き換え、旧集合と編集対応表を解放する |
| 通常のソース編集のために、Test 単位が必要かどうかなどが一時的に決まらない | 同じ集合を使い続ける |
| 構成・プロジェクト設定の入力、所属・配置の変化、close／再 open、同期の喪失 | 破棄する |
| 全文置換、または編集対応表が上限を超えた | 破棄する。綴りや位置の近さで復元しない |
| 最新入力に対するチェックが、採用できる集合なしで確定した（Blocked、Faulted） | 破棄する。後の編集で復活させない |
| チェック中に新しい入力があり、次のチェックが保留中 | 途中の完了だけでは破棄しない |

補完は Hover と同時に集合を失い、同時に回復する。補完だけの保持規則、時間による失効、補完のためのチェック予約は持たない。

### 2.4. 編集対応表

採用後の編集は、現在のテキスト座標で互いに重ならない**領域**の列として持つ。各領域は、現在範囲と旧範囲の組である。

- 新しい編集が既存の領域に重なるか接するときは、一つの領域に結合する。旧範囲は和集合にする。
- 領域の外にある位置は、それより前にある領域の長さの差だけずらして旧位置へ写す。
- 位置の写像は二分探索で O(log 領域数)、編集の適用は O(領域数) かかる。
- 連続して打鍵しても一つの領域に吸収されるので、打鍵の回数で上限に達することはない。
- 上限は 256 領域。既存の Hover の上限 `HoverLimits.Edits` を、編集の件数から領域の数へ読み替える。

Hover の規則は「代表範囲の内部か境界に触れた編集があれば、その対象を再利用しない」である。これは「対象の旧範囲（閉区間）に触れる旧範囲を持つ領域がある」という判定と同値になる。結合は接触か重なりに限るので、結合後の旧範囲に触れる対象は、結合前のどれかの編集にもその段階で触れている。この同値性は、C0（§6）で検査を置いて確認する。

### 2.5. 編集支援投影

- **収集の指定**：投影はチェック時の任意出力である。Hover と補完の収集は一つの指定で要求する。言語サーバーのチェックだけが要求し、通常の CLI コンパイルには費用を課さない。
- **失敗の分離**：単位ごとに、Hover 部と補完部で別々の分離境界を持つ。一方が失敗しても、もう一方、診断、受理、TestPresence には影響しない。失敗は記録し、その部を欠落とする。入力無効化や取消の制御例外は握りつぶさない。
- **切り離し**：コンパイルを解放する前に、不変データへ切り離す。構文木、Binding、宣言ノードは保持しない。
- **寿命**：投影は単位の結果と採用済み集合に従って解放される。不変データを参照で共有し、GC が解放する。補完専用のストア、参照カウント、セッション全体の LRU は持たない。大きさは、投影ごとに生成時の上限で抑える。
- **収集対象**：自プロジェクトの検査済み `file:` メンバーすべて。閉じている文書も含める。文書を開いただけでは、有効な単位は再コンパイルされないためである。補完部は代表単位だけが作る（§3.2）。

### 2.6. Hover への影響

Hover の観測できる挙動は変えない。

- 参加・採用・保持の規則は、文言を共通節へ移すだけである。
- 投影の欠落は、規則を整理するだけで応答は同じになる。従来は、Hover データを欠く参加単位があると集合を採用せず、チェックの確定時に破棄していた。新しい規則では集合を採用し、Hover はその集合について常に null を返す。どちらの場合も、応答は null になる。
- 編集対応表の結合は、§2.4 の同値性があるので Hover の応答を変えない。
- 前回表示の注記（`Previous analysis: update pending`）、参加単位間の一致、描画、キャッシュは、Hover の規則のままとする。

## 3. コード補完の仕様

### 3.1. 対象と意味

- **対象**：開いて同期している `file:` の `.kimi` 文書。
- **候補の意味**：代表単位（§3.2）の採用済み解析において、写像した位置（§3.4）から到達できた名前・メンバー・キーワード。
- **保証しないこと**：
  - 他の参加単位でも到達できること。
  - 現在のコードで名前選択が成り立つこと、受理されること。
  - 引数の適合、Move・Loan・効果が成り立つこと。
  - 最新であること。
- **現在と前回の区別**：応答に区別を付けない。補完の意味が定義上「解析時点の情報」であり、項目ごとに印を付けても情報が増えないためである。
- **チェックへの影響**：要求は新しいチェックを予約しない。quiet period、チェックの開始と完了、診断の公開条件も変えない。

### 3.2. 代表単位

**代表単位**は、採用済み集合の参加単位のうち、正準順で最初の単位とする。

- Product 単位は Test 単位より前に並ぶ。そのため通常のソースでは、最初のプロジェクトの、ターゲット名の序数順で最初の Product 単位が代表になる。TestSources 専用の文書では Test 単位が代表になる。
- 補完部は代表単位だけに要求する。チェック側は、その回の required unit の導出から各文書の代表を求め、その単位でだけ補完部を作る。
- 採用時に代表の補完部がなければ、意味的な候補は返さない（§3.5 のキーワードだけを返す）。
- 次のものは候補にならない。
  - 代表単位で `#if` により除外された領域の中の候補。
  - 構文回復で失われた束縛。
  - 他のターゲットや Test 単位にだけある名前。
- セッションの `target` 設定で、代表になるターゲットを選べる。

### 3.3. 行の字句文脈

要求時の字句処理は、カーソルのある一行に限る。字句の判定には Tokenizer と共有する字句関数を使い、別の規則で言語を定義し直さない。

1. **行頭の状態**：行頭が編集対応表の領域の外にあれば、その旧位置が、代表単位の投影に記録された複数行の非コード範囲（ブロックコメントと複数行リテラルの本文）の中にあるかどうかで決める。行頭が領域の中にある行（新しく書いた行）は、コードの状態から始まるとみなす。
2. **走査**：行頭からカーソルまでを走査する。カーソルがコメントかリテラル本文の中（補間の式は除く）なら、空の一覧を返す。
3. **範囲**：カーソル位置の識別子全体を範囲 [始点, 終点) とし、接頭辞を [始点, カーソル) とする。カーソルが識別子の途中、末尾、直前のどこにあっても同じ扱いにする。識別子がなければ、範囲は空とする。
4. **文脈**：識別子の直前にある有意なトークンで、次の閉じた表から文脈を決める。

| 直前 | 文脈 |
| --- | --- |
| なし（行の最初のトークン）、または `=>` | 行頭（文・宣言の開始。式も含む） |
| `.`（数値リテラルの一部や `..` は除く。同じ行に receiver があるもの） | メンバー |
| `::` | 修飾パス |
| `@`、`$`、`#`、または receiver のない `.`（先頭が `.` の行を含む） | 空の一覧 |
| その他 | 式・型の位置 |

型の位置と式の位置は区別しない。区別するには、名前付き引数・ラベル・宣言の `:` を見分ける必要があり、そのためには文法が要る。式・型の位置では両方の候補を出すので、型の位置に値の名前が混ざるだけで、必要な候補が欠けることはない。

### 3.4. 位置の対応

旧位置 p と、それを含むスコープ S を次の手順で決める。

1. **起点**：起点 x を、識別子の始点とする。メンバーと修飾パスの文脈では、receiver 列の先頭とする。
2. **既存の行**：行頭が領域の外にあるときは、x を旧位置へ写したものを p とする。x が領域の中にあるときは、その領域の旧始点を p とする。p を閉区間として含む最も内側のスコープを S とする。
3. **新しい行**：行頭が領域の中にあるときは、p をその領域の旧始点とする。次に、しきい値 t を現在行のインデントで初期化する。そこから領域の始点まで上の行をさかのぼり、インデントが t より小さい行があるたびに、t をそのインデントへ下げる（空行とコメントだけの行は数えない）。そのうえで、p を含む最も内側のスコープから出発し、スコープの本体ベースライン（ヘッダーのベースラインに 4 を足した値。ファイルのスコープは 0）が t より大きい間は外側のスコープへ移る。最後に止まったスコープを S とする。
4. **可視な束縛**：S とその祖先にある束縛のうち、可視開始位置が p 以下のものを使う。内側のスコープから順にたどり、同じ名前空間で先に見つかった名前を優先する（シャドーイング）。

可視開始位置は、§9.2 に基づいてコンパイラが使う位置を投影に記録したものである。通常は次の値になる。

- ローカル、ループ束縛、パターン束縛：宣言項目の終端。
- その他の宣言（関数、型、メンバー、パラメーター）：スコープの始点。

この規則から、次のことが言える。

- 新しく書いた行の中で宣言した名前と、新しいヘッダーが導入する束縛は、未知のままになる。
- 新しい入れ子ブロックの中でも、外側の名前は使える。
- インデントを戻した行では、閉じたブロックの名前は出ない。
- 旧スコープの境界を壊す編集（ヘッダーの削除など）は検出しない。

### 3.5. 候補

**無修飾（行頭、式・型の位置）**

- Value と Type の両方の名前空間の名前を返す。型、Contract、group、alias、モジュール名は、修飾子として使うためにも返す。
- インスタンスメンバーと継承した宣言は、無修飾では出さない（§9.4：暗黙の receiver を持たない）。これらは `self.` や `Self.` を書いてから、メンバー補完で選ぶ。
- 同じスコープにある同じ名前の関数群は、一つの項目にまとめる。

**メンバー・修飾パス**

receiver 列は、同じ行の中で後ろから読む。列の各要素は次のように解決する。

| 要素 | 解決 |
| --- | --- |
| 先頭の識別子 | §3.4 の S から無修飾の規則で探す。最初に見つかったスコープに同じ名前の Type と Value が両方あれば、空の一覧を返す |
| `self` | 上と同じ規則で見つかる receiver パラメーターの型 |
| `Self` | 包含する型。型レベルのメンバー、入れ子の型、enum Case、`init` を出す |
| 先頭の `::` | ルートのモジュール |
| `.名前` | 前の要素のメンバー表で名前を探す。フィールドや Property なら宣言された型、入れ子の型やモジュールならそれ自体に進む |
| `(…)` | 直前の名前が宣言一つだけの関数群を指し、その結果型が receiver の型引数の置換だけで決まる場合に、その結果型へ進む |
| `[…]` | 投影が添字の結果型を一意に記録している型（組込みの配列・Slice と、添字演算が一つだけの型）なら、その結果型へ進む |

- 括弧は同じ行の中で対応している必要がある。括弧の中身は解析しない。
- 解決できない要素があれば、その時点で空の一覧を返し、推測はしない。
- **型の層**：Semantics と参照の層を外した Core の定義のメンバー表を使う。型パラメーターなら、制約にある Contract の要件のメンバー表を使う。関連型は解決せず、空の一覧になる。
- **最後の要素**：値が receiver ならインスタンスメンバー、型や `Self` が receiver なら型レベルの宣言を出す。基底の層は近いものから順にたどり、近い層で見つかった名前を優先する。コンパイラが提供するメンバー（`length` など）は、Kimi ライブラリの組込みメンバー群としてメンバー表に含める。
- **アクセス**：メンバーごとに、コンパイラの実効アクセス範囲（§9.3.1）を記録する。カーソルのスコープ連鎖がその範囲内にあるメンバーだけを出す。protected の receiver 制限は判定しない。

**キーワード**

綴りは §2.5.1 で定義されたものだけを使う。補完が持つのは、どの文脈でどの綴りを出すかの区分だけである。

| 文脈 | キーワード |
| --- | --- |
| 行頭、`=>` の直後 | 下の行のすべてに加えて、`let` `var` `func` `for` `while` `return` `exit` `continue` `yield` `require` `defer` `else` `public` `internal` `private` `protected` `init` `drop` `alias` `rootgroup` `group` `struct` `enum` `contract` `computed` `property` `virtual` `override` `open` `specialize` `unsafe` |
| 式・型の位置 | `if` `match` `loop` `do` `try` `not` `true` `false` `null` `self` `Self` `base`、組込み型（`isize` から `string` まで）、Semantics（`owner` `ref` `uniq` `obj` `rc` `arc` `objref` `objuniq` `raw`） |
| メンバー、修飾パス | なし |

意味的な候補を決められない場合は、文脈に合うキーワードだけを返す。該当するのは、集合がない、代表の補完部がない、位置が除外領域にある、さかのぼりが上限を超えた、のいずれかの場合である。

### 3.6. LSP 応答

- **capability**：`completionProvider: { "triggerCharacters": ["."] }` を広告する。`resolveProvider` は広告しない。`::` の後は、手動起動か、続く識別子の入力で補完する。
- **応答の型**：`textDocument/completion` は常に `CompletionList` を返す。対象外の文書や文脈がない場合は空の一覧で、`isIncomplete: false` とする。不正なパラメーター、initialize 前や shutdown 後の要求は、既存の JSON-RPC 規則に従う。
- **`isIncomplete`**：§3.7 の上限のためにサーバーが絞り込みや切り詰めをした場合だけ `true` にする。接頭辞では通常は絞り込まず、絞り込みはクライアントに任せる。上限を超えたときだけ、接頭辞と大小文字を区別しない部分列一致をする候補へ事前に絞る。それでも超える場合は、列挙した順に切り詰める。
- **範囲**：insert 範囲は [識別子の始点, カーソル)、replace 範囲は [識別子の始点, 識別子の終点) とする。
  - クライアントが `textDocument.completion.completionList.itemDefaults` に `editRange` を含めていれば、`itemDefaults.editRange` に範囲を一度だけ置く。`completionItem.insertReplaceSupport` があれば `{insert, replace}` を置き、なければ insert 範囲を置く。
  - `itemDefaults` に `editRange` がなければ、同じ規則で、範囲を各項目の `textEdit` に置く。
- **項目**：`label`（挿入する文字列と同じ）、`kind`、`detail`、`sortText` だけを持つ。`filterText`、`insertText`、snippet、commit characters、追加の編集、コマンド、documentation、自動選択は使わない。
- **`detail`**：
  - 値の束縛と Property：型の綴り。コンパイラの型表示を使う。
  - 宣言が一つの関数群：`(name: T, …) -> R`。
  - 宣言が複数の関数群：`N overloads`。
  - 型、Contract、モジュール：種別を表す語。
  - キーワード：なし。
  - メンバーの detail は宣言の綴りのままで、receiver の型引数は置換しない。長さは 128 UTF-16 code units までとし、超えた分は切って `…` を付ける。
- **`sortText`**：一文字の段で表す。`0` は最内の関数のローカルとパラメーター、または receiver の型自身のメンバー。`1` はその他の名前と継承したメンバー。`2` はキーワード。同じ段の中の並びはクライアントに任せる。
- **`kind`**：次の表のとおり。クライアントの `completionItemKind.valueSet` にない kind は、代替の kind に置き換える。

| 宣言 | kind | 代替 |
| --- | --- | --- |
| ローカル、パラメーター、ループ束縛、パターン束縛 | Variable (6) | — |
| Property（メンバーの `let`、`var`、`computed`） | Property (10) | — |
| 型のメンバー関数 | Method (2) | — |
| その他の関数 | Function (3) | — |
| `init` | Constructor (4) | — |
| struct | Struct (22) | Class (7) |
| enum | Enum (13) | — |
| enum Case | EnumMember (20) | Value (12) |
| Contract | Interface (8) | — |
| group、rootgroup、モジュール | Module (9) | — |
| 型パラメーター、関連型 | TypeParameter (25) | Class (7) |
| alias | Reference (18) | — |
| キーワード（組込み型を含む） | Keyword (14) | — |

- **処理の流れ**：要求は状態管理スレッド上で処理する。既に適用済みの文書イベントに対して、同期的に候補を選ぶ。応答には、投影への参照と、選んだ項目の番号列だけを渡す。項目の文字列化（detail を含む）は、送信側が直接書き出す。非同期の補完ジョブ、要求ごとの結果キャッシュ、通知ウィンドウは持たない。
- **応答の回数**：各要求には一度だけ応答する。取消と shutdown は既存の規則に従う。表示済みの一覧は、採用が起きても更新しない。新しい候補は次の要求で返す。

### 3.7. 上限

| 資源 | 上限 | 超えたとき |
| --- | ---: | --- |
| 現在行の字句走査 | 4,096 UTF-16 code units | 空の一覧 |
| 新しい行のさかのぼり | 1,024 行、かつ 65,536 code units | キーワードだけ |
| 編集対応表 | 256 領域 | 集合を破棄（§2.3） |
| receiver 列 | 16 要素 | 空の一覧 |
| 要求の作業（束縛・メンバーの訪問数） | 65,536 | 訪問した順に打ち切る。`isIncomplete: true` |
| 応答 | 512 項目。detail は各 128 code units | 事前の絞り込みと切り詰め。`isIncomplete: true` |
| 単位の補完投影 | 1,048,576 要素（スコープ、束縛、メンバー、型項）、文字列の合計 4,194,304 code units | その単位の補完部を欠落とする |
| ライブラリ部のキャッシュ | 4 キー | 最も古いキーを外す。参照中のデータは有効なまま残る |

列挙の順は、スコープ連鎖の内側から外側へ、各スコープの中では名前の序数順とする。この順は決定的なので、打ち切ったときの結果も入力ごとに一意に決まる。時間切れによって結果が変わることはない。上限の数値は C4 の測定で根拠を残したうえで調整できる。ただし、上限を設けることと、超えたときの扱いは省略しない。

### 3.8. 例

例の `|` はカーソルを表し、Kimi の構文ではない。

```text
cou|                   → 代表単位の集合で、写像した位置から見える count
::Kimi.Con|            → Console（insert 範囲も replace 範囲も Con）
items.len|gth          → length（insert 範囲は len、replace 範囲は length 全体）
items.|length          → items の型のメンバー（insert 範囲は空、replace 範囲は length）
self.items.first().|   → first が宣言一つで Option<T> を返すので、Option<Entry> のメンバー
values[i].|            → 添字の結果型が一意な型なら、要素型のメンバー
make(x).|              → make が複数宣言の関数群なら、空の一覧
x@mo|                  → 空の一覧（`@` 操作は対象外）
```

位置の対応の例を示す。採用済み集合は、次のテキストから作られたとする。

```text
func load(path: string) -> i32
    let text = read(path)
    return 0
```

利用者が、2 行目の末尾と最終行の後に新しい行を書いた。

```text
func load(path: string) -> i32
    let text = read(path)
    if check(text)        ← 新しい行
        te|               ← t は 4。load の本体のスコープに残り、path と text が候補になる
    return 0

func save()               ← 新しい行
    te|                   ← t は 0。ファイルのスコープへ出るので、text は候補にならない
```

### 3.9. 初期対象外

初期実装では、次のものを扱わない。

- `.kimiproj` の補完。
- 定義への移動、Signature Help、documentation と `completionItem/resolve`。
- Origin・Label・名前付き引数の専用補完。
- `@` 操作の補完、期待型からの enum Case 補完。
- 呼出しのスニペット、alias や依存設定の自動追加。
- 修飾付きの綴りを自動で挿入すること（`cou` から `self.count` を挿入するなど）。
- リテラルや関連型を receiver とする補完。
- 先頭が `.` の継続行での receiver 列。
- 型の絞り込み（§14.10）を反映すること。

## 4. 実装設計

### 4.1. データ

| データ | 所有 | 内容 |
| --- | --- | --- |
| 文書部 `CodeCompletionDocument` | 代表単位の投影 | スコープ配列（始点の順。範囲、親、種類、本体ベースライン、束縛の区間）、束縛配列（名前、名前空間、種類、可視開始位置、型項またはメンバー表への参照）、`#if` の除外領域、複数行の非コード範囲 |
| 単位部 `CodeCompletionUnit` | 代表単位の投影（その単位の文書部が共有する） | 名前の intern 表、ソースに由来する定義のメンバー表、型項、モジュール木 |
| ライブラリ部 | チェック側のワーカーが持つ小さなキャッシュ。キーはライブラリの識別と、その指令を選ぶ環境（ターゲット、構成） | Kimi ライブラリの定義のメンバー表、型項、モジュール木。`KimiDeclarationId` で引く |

- **メンバー表**：項目を名前順に並べて持つ。各項目は、名前、種類、インスタンスか型レベルか、実効アクセス範囲、型項または関数群、シグネチャの構造（パラメーター名と型の綴り、結果の型の綴り）を持つ。基底の表への参照も持つ。
- **型項**：定義（メンバー表）への参照と型引数を持つか、型パラメーターの番号を持つ。Semantics と参照の層は綴りのために持つが、メンバーを探すときは外す。要求時の型引数の置換は、(型項, 束縛環境) の組を固定深さの作業領域に積んで行い、新しい型項は作らない。
- **型の綴り**：コンパイラの型表示で作り、同じ型の綴りは単位の中で一つだけ持つ。
- **名前**：文字列を intern し、序数で比較する。
- **ライブラリ部**：不変で、複数の単位・世代・文書から参照で共有する。キャッシュから外しても、参照しているデータは無効にならない。

### 4.2. 生成

| 部品 | 入口と責務 |
| --- | --- |
| 共通集合 | `Lsp/LspSession.Hover.cs` の `RefreshHover` と `Lsp/HoverState.cs` から、参加・採用・保持・編集対応を `EditorAnalysisSet`（仮称）へ移す。`LspSession.cs` で変更を適用する部分（`Edited` の呼出し）は `EditMap`（仮称）に置き換える。Hover の一致判定・描画・キャッシュは Hover 側に残す |
| 収集の指定 | `Checking/CheckContext.cs`・`CheckService.cs` の `collectHover` を、編集支援の収集指定（Hover の有無と、補完部を作る文書の集合）に置き換える。`CheckOutput.Hover` は、Hover 部と補完部を持つ `EditorProjection`（仮称）にする |
| 代表の決定 | `Lsp/WorkspaceCheck.cs` で required unit を導出した後、文書ごとに最小の単位キーを求め、`UnitPlan` に補完部を作る文書を渡す |
| 補完投影 | `Compiler/Binding/Binding.CodeCompletion.cs` で、インデクサーが作った `scopes` と `symbols` から投影を作る。AST は走査し直さない。可視開始位置・実効アクセス範囲・制約は、既存の Binding の関数で求める。補完専用の言語規則は持たない |
| 字句の記録 | `Compiler/Core/Compilation.Hover.cs` の任意収集フックで、Tokenizer と条件コンパイルの選択処理から、複数行の非コード範囲と `#if` の除外領域を記録する |
| ライブラリ部 | 初めて必要になったコンパイルから作り、キーごとにワーカーで再利用する |

- 収集が無効なときに追加される費用は、分岐一つだけで、割り当てはない。
- 収集が有効なとき、代表単位での費用は O(宣言数 + スコープ数) である。ライブラリ部はキーごとに一度だけ作る。
- 上限を超えたら、作りかけの補完部は公開せず、その単位の補完部を欠落として記録する。

## 5. 性能目標と計測

以下は見直しの基準であり、言語の保証でも時間に依存する機能テストでもない。超えた場合は、原因を記録して修正し、測り直す。

| 対象 | 目標 |
| --- | --- |
| 要求（状態管理スレッド上の時間。書き出しは除く） | 通常の要求で p95 が 1 ms 以下。上限付近で 5 ms 以下 |
| 書き出し（送信側） | 512 項目で 2 ms 以下 |
| 要求の割り当て | 定常状態では、応答オブジェクト一つ以外は割り当てゼロ。書き出しは借りたバッファを返却する |
| チェック | 補完部の生成が、同じワークロードの Binding 時間の中央値の 5% 以下。収集が無効なときの追加割り当てはゼロ。ライブラリ部の初回の生成時間と大きさを記録する |
| 編集 | 編集対応表の更新が 1 打鍵あたり O(領域数)。10,000 打鍵の連続入力で領域数が 1 のまま |
| 保持 | 単位部・文書部・ライブラリ部の要素数と文字数を記録する |

- **ワークロード**：Hover と共有しているワークロードに、次の場合を加える。広いスコープ（多数のローカルとトップレベルの名前）、深い receiver 列、多数のオーバーロード、`::Kimi.`、複数ターゲット（allTargets）。
- **測定方法**：時間は `src/Benchmark` で固定条件のもとで測る。割り当てと保持は xUnit の `Purpose=Allocation` の回帰テストで確認する。

| 単位 | 内容 | 完了条件 |
| --- | --- | --- |

重点的に回帰テストを置くもの：

- 宣言の前後、初期化式、シャドーイング。
- 新しい行と新しい入れ子ブロック、インデントを戻した行。
- アクセス制限と継承、alias と `::Kimi`、標準コレクション。
- 同じ名前の Type と Value、オーバーロード、receiver の型引数の置換。
- `#if` の除外領域、代表単位の選び方。
- 採用・保持・破棄のすべての遷移（Hover と同時に起きること）。

期待結果は、実装の出力から自動生成せず、本書の規則から書く。

検証は [VERIFICATION.md](../../docs/dev/VERIFICATION.md) に従う。

- 各単位では、関連するテストクラスを指定して Unit 検証をする。セッションの終わりに Session 検証を一度だけ行う。
- コード生成を変えないので、native fixture は選ばない。
- 診断を変えないので、Diagnostic Development Workflow は適用しない。
- 拡張を変更する場合は [src/kimi-ext/AGENTS.md](../../src/kimi-ext/AGENTS.md) に従う。
- NativeAOT は実行しない。
- 結果は `artifacts/verify/` に、測定は `artifacts/benchmarks/` に残し、検証済みの単位だけをコミットして push する。

## 7. Kimigayo Principles による評価

### 7.1. 原則との対応

| 原則 | 本書での扱い |
| --- | --- |
| 1. One Concept, One Canonical Form | 採用・保持・編集対応は、Hover と同じ一つの集合で扱う。代表単位は既存の正準順で一つに決まる。範囲、`isIncomplete`、文脈の規則はそれぞれ一つだけ。キーワードの綴りは §2.5.1 だけで定義し、補完は位置の区分だけを持つ。型の綴りはコンパイラの表示を使い、補完専用の表示規則を持たない |
| 2. Local Reasoning | 候補は、代表単位、写像した旧位置、現在の一行だけで決まる。各手順は閉じた表と上限で予測できる。要求のたびに全体を走査したり、解析し直したりしない |
| 3. Explicit Semantics | 候補の意味（解析時点、代表単位、挿入するだけ）を契約に明記する。暗黙の receiver、修飾の自動付加、自動 import、スニペットは使わない。精度を下げた点は §7.2 にすべて列挙する |
| 4. Compiler Server Protocol | 投影は不変で、コンパイルから切り離されている。内部検査 API が解決の過程を構造化して返す。テストは現在のテキストと編集列に結び付け、計測条件は固定して記録する |

### 7.2. 精度を下げた点

| 点 | 影響 | 回復・緩和 |
| --- | --- | --- |
| 代表単位だけを使う | 他のターゲットや Test 単位にだけある名前は出ない。代表単位では使えない名前が、他の単位では使えることもある | 次のチェックの診断。`target` の設定 |
| 代表以外の参加単位が Blocked や Faulted の間は、集合がない | Hover と同じく、意味的な候補が出ない | 共通規則を変える場合は、Hover と一緒に検討する |
| 新しい行で宣言した名前と、新しいヘッダーの束縛は未知 | 書いたばかりのローカルは、次の採用まで出ない | 次の採用 |
| 構造を壊す編集を検出しない | ヘッダーを削除した後も、旧スコープの名前が出る | 次の採用 |
| 新しい行は、行頭がコードの状態とみなされる | 上の行で開いた複数行コメントや文字列の中でも、候補が出る | なし（挿入するのは利用者の操作） |
| 型の位置と式の位置を区別しない | 型の位置にも値の名前が出る | クライアントの絞り込み |
| receiver の呼出しと添字は、一意な宣言・結果型に限る | オーバーロード、メソッドの generic、関連型の receiver では空の一覧 | 将来の拡張 |
| 構文回復で失われた束縛は出ない | 未完成の文がある関数では、候補が減ることがある | 次の採用。必要なら構文回復を改善する（C1 で記録） |
| 型の絞り込みと protected の receiver 制限を反映しない | 実効型のメンバーが欠けたり、使えないメンバーが出たりする | 診断 |
| detail で receiver の型引数を置換しない | `Option<T>` のように表示される | Hover |
| 表示済みの一覧を更新しない | 採用が起きても、次の要求までは古い一覧のまま | 次の要求 |

### 7.3. 採用しなかった案

| 案 | 採用しない理由 |
| --- | --- |
| 全参加単位で一致する候補だけを返す | 費用が参加単位の数に比例する。補完は綴りを挿入するだけなので、他の単位との一致は次のチェックの診断で分かる |
| 補完専用の採用・保持規則（Blocked・Faulted の後も旧集合を保持するなど） | 同じ概念に二つの状態機械ができ、Hover と補完の応答が食い違う（原則 1） |
| 要求時の再構文解析や再 Binding、補完のためのチェック予約 | 応答が遅れ、quiet period を迂回することになる。Hover についての既存の決定（SETTLED）と同じ理由 |
| 編集ごとに字句状態が収束するかを判定する | 費用と仕組みが増える。現在行の走査と、投影の非コード範囲で足りる |
| サーバー側での接頭辞の絞り込み、大小文字の区別 | クライアントのあいまい一致と食い違い、打鍵ごとの再要求で状態管理スレッドが混む |
| `self.count` のような修飾付きの綴りの自動挿入 | 暗黙の receiver を持たない設計（§9.4）と、明示的な綴りの原則に反し、規則も増える |
| 補完専用のストア、LRU、参照カウント | GC と生成時の上限で足りる。追い出した索引は再び作られないので、補完が使えない期間が生じる |
| 項目ごとの `Cached analysis` の表示 | 編集直後は常に前回の解析になるので、印は情報にならない |
| 要求結果のキャッシュ | 要求は単語の始めと `.` でしか起きないため、効果が小さい |
| 任意の式の型を位置ごとに保存する | 保持量が大きく、新しく書いた式には効かない |
