# 仕様変更・実装計画：LSP Completion

日付：2026-10-07。状態：採用方針をまとめた提案。正式仕様への取り込み・実装・実行検証は未実施。

## 1. 位置づけと目的

**本書の変更事項は、[SPEC.md](../../docs/SPEC.md) およびその参照先より優先する。変更しない事項には既存仕様を適用する。** 今回は本書だけを作成し、正式仕様・実装・既存提案は変更しない。将来の取り込みでは正式仕様を自己完結させ、本書への依存を残さない。

LSP にコード補完（Completion）を追加する。**通常の診断チェックで作成したキャッシュから補完し、情報が最新であることを要求しない。** 補完要求はコンパイル、Binding、型推論、制約証明、ディスク読み込みを開始せず、チェックの開始を早めたり完了を待ったりしない。補完専用のタイマー・ワーカー・設定は追加しない。

名前・アクセス・型・所有権の言語規則は変えない。候補は解析時点の名前の到達可能性を表し、現在のプログラムの受理、引数の適合、Move・Loan・効果の成立を保証しない。コンパイラと同じ規則を使うことで一貫性を保ち、現在の編集範囲と履歴上の意味情報を分けることで、応答性と安全な文字列編集を両立する。

## 2. 補完の範囲と候補

### 2.1. 初期対象

同期済みで開かれている `file:` の `.kimi` 文書を対象とする。

| 文脈 | 候補・例 |
| --- | --- |
| 可視な名前 | ローカル、引数、関数、型・Contract、group、alias、参照可能なモジュール名。確定したループ・パターン束縛もローカルとして扱う |
| 型の位置 | 型注釈、引数型、戻り型など。その Lookup Role に合う組み込み型・Semantics、可視な型パラメーターを含む |
| 修飾された名前 | `::Kimi.`、`Group.`、`Self.`、alias を経由した名前 |
| インスタンスメンバー | `value.`、`self.`。継承メンバーと標準コレクションのメンバーを含む |
| キーワード | 宣言・文・式・型の位置に合うもの。構文上認められない位置では返さない |

`.kimiproj`、定義への移動、Signature Help、Origin・Label・名前付き引数の専用補完、`@` 操作の専用補完、期待型からの enum Case 補完、呼出しスニペット、alias・依存設定の自動追加は初期対象外。修飾済み enum の通常のメンバー候補は対象に含める。

### 2.2. 名前解決との一致

- 候補生成は SPEC §9 の名前空間・Lookup Role・検索段階・シャドーイングを共有する。ローカルは宣言後から可視で、自身の初期化式では外側を参照する。ローカル関数や Container メンバーの前方参照も既存規則に従う。
- アクセス権と到達可能性の両方を満たす名前だけを列挙する。公開名を自動的に取り込まず、private／protected、モジュール境界、alias の優先順位を変えない。
- 修飾が必要な名前は、有効な綴り `self.count`、`Self.marker`、`Container.name`、`::Path.name` を候補にする。解析時点で根拠を持つ修飾だけを使い、無修飾名として紛れ込ませない。既に入力された修飾子は重複挿入しない。
- generic の置換、参照層・object view・Contract 要件を経由するメンバーは、解析で確定した環境と選択規則を使う。型名と値名の曖昧さを任意の優先順位で解消しない。
- `length`、`indices`、`capacity` などコンパイラが提供するメンバーも、通常の Binding と同じ適用表から供給する。宣言辞書に存在するものだけを対象にしない。
- 名前選択後の不適合を理由に、隠れている外側の名前や別の検索段階を候補として復活させない。未入力の引数や取得操作を推測して候補の合法性を保証しない。

関数は名前を挿入し、括弧・引数・`@move` などを自動追加しない。同じ選択されたオーバーロード群は一項目にまとめ、個々の宣言識別とシグネチャを内部に保持する。一件ならシグネチャ、複数なら所属と件数を簡潔に表示し、一つを選択済みのように見せない。同じ名前でも別の修飾経路が必要なら別項目にする。

### 2.3. 現在の文脈と編集範囲

要求時には現在のテキストから、入力中の識別子、その接頭辞と置換範囲、直前の修飾子・receiver、字句上の文脈を取得する。この限定した字句処理とキャッシュ索引の参照は許可するが、文書全体の再構文解析や意味解析は行わない。字句規則は既存 Tokenizer と共有し、別の正規表現だけで言語を再定義しない。

- コメント・文字列本文では返さない。文字列内の式は式として扱う。数値の小数点や `..` をメンバー参照の `.` と誤認しない。
- 複数行コメント・文字列などの開始状態が不明な場合は、既知の字句状態から上限付きで走査する。判定できなければ空の結果とし、推測しない。
- 構文文脈・スコープはキャッシュの位置索引と編集履歴に対応付ける。新しく作ったスコープや対応が壊れた領域には、近傍のスコープを推測して流用しない。
- 補完中の識別子の挿入・削除・置換と、その直後への `.` の挿入は通常操作として扱う。これだけで包含スコープを失効させない。挿入位置の境界で内外を決められない場合は使わない。
- 既存の関数・ブロック内に通常行を追加して名前を入力した場合も、包含と字句状態を確定できれば旧環境を使う。新しい入れ子ブロック、ヘッダー・境界・インデントの変更などで構造対応が曖昧な領域は使わず、独立して対応できる領域は残す。
- `value`、`self`、`::Kimi` などの単純な名前・修飾経路は、対応するキャッシュの環境・メンバー索引だけでたどれる。新しい宣言の推論や generic の新しい具体化はしない。
- 呼出し・添字・複合式を receiver とする場合は、式の対応が保たれたキャッシュ済みの型を使う。未解析の式、編集された複合式、型が得られない receiver のメンバーは返さない。
- 新しい変数・型はキャッシュに現れるまで意味的な候補にならない。同名の古い束縛が残る場合も結果は履歴上の情報であり、新しい宣言を解析したことにはしない。

置換範囲は必ず現在の文書で計算し、カーソルを含む一行の識別子範囲とする。末尾では入力中の名前全体を置換し、先頭・中間でも後続の識別子部分を含めて全体を置換する。カーソル位置に補完対象の識別子がない場合だけ挿入とする。`.`、`::`、周囲の括弧・空白・改行は置換しない。UTF-16、CR／LF／CRLF は既存の文書同期規則に従い、Unicode の文字や識別子を途中で切らない。

例の `|` はカーソルであり、Kimi の構文ではない。

```text
cou|                 → キャッシュ上で可視な count
::Kimi.Con|          → Console（Con のみ置換）
items.len|gth        → length（length 全体を置換）
items.|length       → length（空の接頭辞でも既存の length を置換）
items.|             → キャッシュ上の items の型に属する候補
```

`items` の型が変わった直後でも旧型の候補は許容する。新しい型で有効であるとは表示せず、通常チェック後のキャッシュ更新で置き換える。

## 3. キャッシュの作成・採用・保持

### 3.1. 作成と参加単位

通常の workspace check に任意の補完情報収集を追加する。診断と同じ `checkQuietPeriodMs`、入力スナップショット、解析単位を使う。補完要求はチェックの予約・期限・再実行条件を変更しない。同期的な要求処理による実時間上の遅延は §6 で別に測定する。

補完の参加単位は、その文書を自身のソースとしてチェックする全プロジェクト・全ターゲットの required unit とする。結果未取得の単位も含め、依存ソースとして読むだけの consumer や TestSources 専用文書をチェックしない Product 単位は除く。診断通知の contributors だけから決めない。

文書の所属と非空の参加単位集合が確定し、全単位に有効な Completed 結果と利用可能な補完索引がそろったとき、文書単位の集合を一括採用する。Accepted は必須でなく、他の箇所にエラーがあっても独立して確定した情報を収集する。有効な単位は生成時刻が異なってもよく、更新のためだけに再解析しない。

新しい集合への採用は、診断が空・同一で通知されない場合にも行う。参加単位の欠落を無視して採用せず、新旧の項目をつぎはぎしない。新しい索引で消えた・不明になった候補を古い集合から補わない。

### 3.2. 複数単位の一致

要求位置の文脈と候補を各参加単位に対応付け、全単位で一致する候補だけを返す。一つの候補が不一致でも、独立して一致した別候補は返せる。参加単位を特定できない場合は意味的な候補を返さない。

一致は、宣言またはオーバーロード群の構造的な識別、名前空間・役割、修飾と挿入内容、置換後に指す対象、具体化された型・シグネチャで判断する。同名・同じ表示文字列・ハッシュ値・Compilation 内の連番だけでは一致としない。初期実装は候補に文書本文を付けないため、文書コメントだけの差で候補を消さない。

履歴集合は、採用時の参加単位と各単位のデータを固定して使用する。途中まで更新された参加単位から新しい共通集合を作らない。参加集合が同じまま所属判断が一時保留になった場合は、次項の破棄条件に当たらない限り直前の集合を使える。

### 3.3. 保持と破棄

開いた文書ごとに最後に採用した集合を一つ保持する。過去世代を連鎖して保持せず、時間経過だけでは失効させない。単なる入力の invalid／held 状態は、履歴集合を使用不可にしない。

| 事象 | 扱い |
| --- | --- |
| 通常のソース編集、依存ソースの変更、チェック待機・実行中 | 位置対応が保たれる対象について直前の集合を使う |
| 通常チェックの Blocked／Faulted、補完索引の生成失敗 | 構成・参加集合・同期の条件を保つ限り、直前の集合を保持する。待機が終わったことだけでは破棄しない |
| 全参加単位の新しい利用可能な集合がそろう | 一括置換する。正しく生成された空の索引も新しい結果として採用する |
| プロジェクト設定・依存構成・ターゲットの変更、確定した所属・参加集合の変更 | 関係する文書の集合と要求キャッシュを破棄し、新しい構成の結果を待つ |
| close／再 open、同期喪失、全文置換 | 集合と位置対応を破棄する。同名・近い位置による復元はしない |
| 編集履歴や保持容量の上限 | 該当する履歴・集合を破棄する。共有データは他の利用者がなくなった時点で解放する |
| セッション終了・プロジェクト離脱 | 不要な索引・入力・履歴を解放する |

設定・依存構成の入力イベントは、新旧内容を確認できるまで保守的に破棄してよい。ソースの追加・削除で所属が一時不明な間は旧集合を保持できるが、新しい参加集合が確定したら切り替える。ファイル自身の close／同期喪失等の破棄条件が優先する。

キャッシュがない場合は、現在の文脈を確定できるキーワードだけを返す。型・メンバー・名前を推測せず、補完のためのチェックを予約しない。更新後の候補は次の要求で返し、既に表示された一覧の自動更新は保証しない。

## 4. LSP 応答

標準の [LSP 3.17 Completion](https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_specifications/lsp/3.17/language/completion.md) を使い、独自要求を追加しない。

- `completionProvider` を広告し、`triggerCharacters` は初期状態で `['.']` とする。通常の識別子入力・手動起動も扱い、`::` は手動起動または続く識別子入力で補完できる。
- `textDocument/completion` は常に `CompletionList` を返す。対象外・文脈不明なら空の一覧。不正なパラメーター、initialize／shutdown 前後の扱いは既存の JSON-RPC 規則に従う。
- 各項目は `label`、対応する `kind`、必要な短い `detail`、`filterText`、安定した `sortText`、通常文字列の `textEdit` を持つ。クライアントの kind 対応範囲に合わせて代替分類する。snippet、commit characters、追加編集、コマンド、自動選択は使わない。
- 接頭辞との比較は識別子の大文字・小文字を区別する。修飾付き挿入でも入力中の名前で絞れる `filterText` を持たせる。候補順は近い可視スコープ、明示修飾が必要な候補、キーワードの順を基本とし、同順位は名前・修飾名・宣言識別で固定する。順序で名前選択の規則は変えない。
- 接頭辞で絞った一覧、件数制限した一覧、履歴集合またはキャッシュ未取得からの一覧は `isIncomplete: true` とする。これらに該当せず、現在の文脈の候補をすべて返した場合は `false` とする。これは次の入力で再要求するための情報であり、チェック完了による push 更新や候補の最新性を保証しない。
- 履歴集合からの意味的な項目には、`detail` に `Cached analysis` を付ける。`label`・挿入文字列には混ぜない。キーワードには付けず、通知ウィンドウは出さない。
- 初期実装では `resolveProvider` は広告しない。長い文書説明と `completionItem/resolve` は後の拡張とし、必要なら Hover の文書処理を共有する。

要求は状態管理スレッド上で、既に適用済みの文書イベントに対して上限付きで処理する。応答の構築と送信予約までに後続編集を割り込ませない。LSP の通常の補完編集には文書版番号がないため、送信後のクライアント編集までサーバーが適用を保証するものではない。各要求には一度だけ応答し、後着の取消通知で二重応答しない。非同期の補完ジョブは作らない。

## 5. 実装設計

### 5.1. データと処理の境界

```text
通常チェック → Parser／Binding の任意収集 → 不変の補完索引 → 集合の一括採用
文書変更     → 現在テキスト・字句状態・位置対応の更新
補完要求     → 現在の文脈＋採用済み索引 → 候補の一致・絞込み → 現在範囲の TextEdit
```

型名は案であり、責務の分離を固定する。

| 部品 | 責務・入口 |
| --- | --- |
| `CompletionSnapshot`／補完ストア | `Checking/CheckResult.cs` に引渡し用の任意出力を追加。ソース識別、世代、スコープ・可視開始位置、候補、型・メンバー索引、確定した式の型を保持。長期所有は容量管理できる補完ストアへ移す |
| `Binding.Completion` | `Binding.Types`、`Binding.MemberLookup`、`Binding.Calls`、`Binding.Sequences` 等と規則を共有し、解析中の情報を切り離す |
| 補完位置の収集 | Parser／Binding の任意収集。未完成の `value.`、途中の型名、空白位置でも包含スコープと独立した事実を保持 |
| `CompletionState` | `LspSession.Hover` の参加判定・採用の共通部分を利用。保持・破棄は本書の規則とし、Hover の条件を変更しない |
| `CompletionContext` | `TextDocument` と編集履歴から現在の接頭辞・字句文脈・置換範囲・索引への対応を得る |
| LSP アダプター | `Json.cs`、`LspJsonContext.cs`、`LspMessageReader.cs`、`LspSession` に capability と要求・応答を追加 |

通常の `Lookup`／`Member` は診断や解析状態を変更するため、候補名ごとに呼び出す実装にしない。検索の役割・アクセス・優先順位の判定を共有可能な処理へ切り出し、補完側に別の言語規則を複製しない。

スコープの親子関係、可視開始位置、宣言群・具体化済み型・メンバー表を共有し、各カーソル位置の全候補を複製しない。メンバーを実際に使用した箇所だけでなく、可視な束縛の確定した型から利用できるメンバーも収集する。要求時は位置索引と名前索引を使い、AST やプロジェクト全体を走査しない。AST、Binding、宣言ノードへの参照を LSP に保持せず、必要な不変の識別・文字列・索引だけを残す。

補完情報収集は opt-in とし、通常の CLI コンパイルには収集・索引生成の費用を課さない。診断・Accepted・TestPresence の確定と任意投影を分離する。任意収集・投影・要求処理の失敗は記録し、その補完情報を利用不可にするだけで、診断・受理・Hover を変えない。入力無効化・取消の制御例外は握りつぶさない。

### 5.2. 上限と再利用

`CompletionLimits` に初期上限を集約する。数値は C0・C5 の固定条件で測定し、根拠を残して調整できるが、上限・中断・破棄の契約は省略しない。

| 資源 | 初期上限 |
| --- | ---: |
| 一文書の履歴編集 | 256 件 |
| 一要求の字句走査 | 65,536 UTF-16 code units |
| 一要求の索引・一致比較の作業 | 65,536 要素／辺、深さ 64（全参加単位の合計） |
| 一応答 | 512 項目、文字列合計 65,536 UTF-16 code units |
| 補完専用索引のセッション内保持 | 1,048,576 要素／辺、文字列合計 4,194,304 UTF-16 code units |

構築中の索引にも上限を適用し、巨大な中間集合を作ってから切り詰めない。構築・配送中と未採用の投影、採用・履歴集合、要求結果キャッシュ、補完のために残す旧ソース文字列を計上し、共有要素は一度だけ数える。入力管理など既存機構の保持費用とは分けて測定するが、他のオブジェクト経由の参照で補完の保持費用を隠さない。保持上限では使用の古い集合から解放し、単独でも収まらない投影は利用不可とする。

長期の `UnitResult.Output` に回収不能な索引参照を残さない。投影を引き渡した後は補完ストアが所有し、単位結果は識別子で参照する。容量回収では診断結果を破棄せず、補完専用の所有参照と派生キャッシュを解放する。回収された索引の再構築だけを目的とするチェックは予約しない。

字句文脈・位置対応・全参加単位での一致を確認できない項目は返さない。件数・出力制限では確認済みの項目だけを安定順で返し、項目の綴りや編集を途中で切らない。時間切れによる非決定的な候補集合を作らない。

要求結果を再利用する場合は、集合の世代・参加単位・補完文脈・接頭辞・表示条件をキーとし、現在の編集範囲は別に組み立てる。応答済みの全位置を無制限に保存しない。同一文脈の反復検索は作業領域を再利用し、通信出力の割り当てと内部検索の割り当てを区別する。

| C2：文脈と編集対応 | 現在テキストの字句判定、スコープ対応、接頭辞置換、名前・receiver の索引参照 | 入力途中・新しい行と `.`・識別子先頭／中間・Unicode・複数行構文で正しい編集になる。新しいブロックや境界削除で対応不明なら候補なし |
| C3：集合と履歴 | 参加単位、共通候補、一括採用、旧集合の保持・破棄、容量制限 | 更新順序・無通知更新・Blocked／Faulted・構成変更・close／再 open の全状態遷移が本書に一致 |

| C5：総合検証と計測 | 連続入力、広いスコープ、深い型、複数単位、上限・解放、既存機能への影響 | 関連 Unit／Session、割り当て・保持回帰、固定条件の性能測定を完了し、未解決条件がない |

重点回帰は、宣言前後・初期化式・シャドーイング、無修飾と明示修飾、アクセス制限・継承、alias・Kimi、標準コレクション、同名 Type／Value、オーバーロード、型引数の置換、独立した構文エラーと未完成構文を含める。期待結果を実装の出力から自動生成せず、仕様から記述する。

キャッシュ回帰では、入力停止前にも旧候補が返ること、新しい名前が次の通常チェックで現れること、旧型の候補が現在範囲へ挿入されること、同じ文書版番号の編集、依存先だけの変更、空キャッシュの採用、失敗後の旧集合、上限破棄、解放を確認する。同じ入力イベント列と制御時計で、補完要求がチェック予約・quiet period・診断の公開条件を変更しないことを検証する。実時間の連続送信は、実行回数や通知時刻の完全一致ではなく、次の遅延・処理量測定で評価する。

初回・反復要求、接頭辞編集直後、上限付近、複数参加単位で、遅延・割り当て・保持量・後続文書イベントの処理遅延を測る。収集無効／有効の通常チェック費用も比較する。初期の見直し基準は測定ホスト上で通常要求の p95 20 ms 以下、上限付近の単一要求 100 ms 以下、応答生成を除く同一文脈の反復検索は割り当てゼロとする。これは言語保証や時間依存の機能テストではなく、超過時に修正・再測定する性能目標である。

実装時の検証は [VERIFICATION.md](../../docs/dev/VERIFICATION.md) に従い、関連 Unit、最後に一度の Session、必要な native fixture を実行する。診断・回復処理を変更した単位は Diagnostic Development Workflow も適用する。拡張変更は [src/kimi-ext/AGENTS.md](../../src/kimi-ext/AGENTS.md) に従う。NativeAOT は実行しない。結果は `artifacts/verify/`、測定は `artifacts/benchmarks/` に残し、検証済み単位だけをコミット・push する。
