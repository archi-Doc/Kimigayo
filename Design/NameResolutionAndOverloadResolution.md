# 名前解決とオーバーロード解決の仕様原案

Name Resolution / Overload Resolution — 設計原案。作成日・更新日: 2026-09-07。

本書は、名前がどの宣言を指すか、同名関数のうちどれを呼び出すかを定める。これまでに合意した方針をまとめた原案であり、機能が実装済みであることを示すものではない。

[SPEC.md](../SPEC.md)を補完する。元の原案の規則を保ち、説明・章立て・例を整理している。既存仕様との違いは6.1節、残る決定事項は6.2節にまとめる。SPEC.mdへの反映は別途行う。

**コード例の読み方:** 各例は独立した説明用のコードである。「エラー」と書いた行は、規則の境界を示すため意図的に含めている。宣言済みと仮定する型やライブラリーは例の直前に示す。構文が未確定のものと内部処理の例には、疑似コードと明記する。コード例は、この原案の意味を説明するものであり、現在のコンパイラーでの実行を保証しない。

## 1. この仕様の読み方

まず、名前を探す処理と、同名関数から1つを選ぶ処理を分けて考える。

### 1.1. 処理の全体像と設計原則

名前と呼び出しの解決は、次の4段階で進める。

```text
Name Resolution
    → Candidate Applicability
    → Best Candidate Selection
    → Usage Legality
```

| 段階 | 決めること | 例 |
| --- | --- | --- |
| 名前解決（Name Resolution） | どの宣言、または同名関数の組を参照するか | `f`を現在のContainerから探す |
| 候補の適用可能性（Candidate Applicability） | 引数・型引数・期待戻り値型・制約に合う候補はどれか | i32の引数に適合しない候補を除く |
| 最良候補の選択（Best Candidate Selection） | 適用可能な候補のうち、どれを呼び出すか | 完全一致する候補を借用が必要な候補より優先する |
| 使用可否の検査（Usage Legality） | 選んだ操作を、その場所で実行してよいか | 選んだ関数がunsafeなら、呼び出す場所の権限を調べる |

**最上位原則：ある段階の結果が確定した後は、後段の失敗を理由に前段へ戻って別の名前や候補を選び直さない。** 候補の適用可能性と最良候補の選択を合わせて、オーバーロード解決と呼ぶ。

次は結果がまだ確定していない場合の扱いであり、確定後のやり直しには当たらない。

- アクセスできない宣言や、Lookup Roleに合わない宣言だけでは名前探索を停止しない。
- 正当な未確定のコンパイル時条件や型パラメーターへの依存があれば、影響を受ける解決を保留する。名前探索環境を変える条件は、その環境を使う通常の名前解決を開始する前に選択を確定する。解決に必要な情報が相互依存し、確定不能となる循環はエラーとする。

字句可視範囲や`#case`の選択順など、言語で定めたソース順の規則を適用した上で、ファイルの読み込み順、alias順、候補の列挙順や最適化によって結果を変えない。推論範囲を越えて決められない場合は、修飾名・型注釈・明示型引数を要求する。

### 1.2. 用語の意味

本文では、説明に必要な場合を除き、日本語の名称を使う。次の表は、コードや他の仕様書で使う英語との対応を示す。

| 用語 | この文書での意味 |
| --- | --- |
| Binding | 名前と型を調べ、ソースコードがどの宣言・操作を意味するかを決める処理 |
| Declaration Container（以下Container） | `group`や`struct`など、宣言をまとめる単位 |
| スコープ | 名前が有効な範囲。ソース上のブロックの入れ子などで決まる |
| 名前空間（namespace） | 型名・値名など、名前を別々に管理する区分。Containerそのものとは異なる |
| 名前（Name） | ソース上の識別名。使用できる文字と名前の等価性はSPEC.mdに従う |
| アクセス権（Accessibility） | 使用位置が宣言のprivate/internal/publicによるアクセス範囲内にあるか |
| 名前への到達可能性（Name Reachability） | 使用位置から直接参照・修飾名・alias・re-exportなどの有効な経路で名前を探せるか |
| 宣言を表す情報（Symbol） | 「どの宣言か」を表すコンパイラー内部の情報。複数ファイルの宣言を統合した場合も、1つのSymbolで表せる |
| 宣言の識別情報（Signature） | 同じスコープに同名の宣言を置けるかを判定する情報。関数では名前・型パラメーターの個数・順序付きの正規化引数型 |
| 宣言断片（Declaration Fragment） | 統合前の、1カ所に書かれたContainer宣言。ヘッダー・ソース位置・CodeContextを残す |
| 名前解決の文脈（Lookup Context） | 使用位置のCodeContext、スコープ、名前空間、Lookup Role、アクセス権などの情報 |
| 探索時の役割（Lookup Role） | Core Type、Type Semantics、Qualifier、Valueなど、構文上その名前に要求される役割。候補を収集する段階で使う |
| 候補集合（Candidate Set） | 同じ探索段階で見つかった宣言の集まり。列挙順に優先順位はない |
| 適用可能な候補（Applicable Candidate） | 引数の対応、型、制約などを満たし、今回の呼び出しに使える候補。使用可否の検査は別途必要 |
| 受け手（receiver） | `object.method()`の`object`。メンバーを使用する対象の値 |
| 期待型（expected type） | 周囲の記述から要求される型。`let x: i64 = expression`なら、右辺の期待型はi64 |
| 修飾名／非修飾名 | `Group.Type`のように所属先を付けた名前／`Type`のように名前だけを書いたもの |
| 型パラメーター／型引数 | 宣言側の`func f<T>`にあるT／呼び出し側の`f<i32>`で指定するi32 |
| 型推論 | 省略された型を、引数などの既知の情報から決めること |
| ジェネリックの具体化（specialization） | 型パラメーターに具体的な型を当てはめること |
| 下位型（subtype） | 言語で定義された型関係により、別の型が求められる場所で使える型。数値幅の大小とは異なる |
| 借用／再借用（borrow／reborrow） | 所有権を移さずに値を参照すること／既存の参照から別の借用を作ること |
| 曖昧性エラー（ambiguity） | 規則を適用しても、参照先や呼び出す関数が1つに決まらないエラー |

Symbolは、名前の書き方やalias経路ではなく、参照先の宣言を区別する。外部型では宣言元Kotonohaの識別情報も含め、異なるバージョンの同名型を同一視しない。

`Property`、`Type Contract`、`Type Semantics`、`Origin`、`Loan`はKimigayo固有の用語として維持する。Type Contractは型が満たすべき制約、Type Semanticsは所有・借用などの性質、Originは参照の有効期間の由来、Loanは実際の借用を表す。

## 2. 宣言とソースファイルを整理する

複数ファイルの宣言は共有できる。一方、どのaliasが使えるかは、コードが書かれたファイルごとに決まる。

### 2.1. ソースごとの情報を保持する

SourceDocumentは1つのソースファイルを表す。CodeContextは、そのファイルを解析するときに必要な情報を保持する。Compilationは、あるターゲット向けにプロジェクトをコンパイルする単位である。

Compilation rootは、そのCompilationで絶対修飾名の探索を始める場所を指す。詳しくは3.4.2節で定める。

```text
Compilation
  ├─ 直接依存Kotonohaの参照名 → ライブラリーの識別情報
  ├─ Compilation root
  └─ デフォルトalias

CodeContext：1つのSourceDocumentに対応
  ├─ SourceDocument
  ├─ ソースに記述されたalias
  └─ 解決済みのalias対象Containerへの参照

各構文ノード・宣言断片
  └─ 記述元のCodeContextへの参照
```

#### 2.1.1. CodeContextとソースファイルの対応

- ソース由来のCodeContextは、1つのSourceDocumentに固定する。
- 同じCodeContextを別のSourceDocumentの解析へ再利用しない。
- ソースを解析し直すときは、新しい解析結果として管理する。以前のalias解決結果やBinding結果を混在させない。
- rootや生成ノードなどソースを持たない内部ノードは、特定ファイルのalias環境を代表しない。ソース由来の式を生成ノードへ移しても、元のCodeContextを保持する。

#### 2.1.2. 統合後も記述元の情報を使う

Containerの統合後も、各メンバー、型注釈、Type Contract、ヘッダーは記述元のCodeContextで名前解決する。統合されたContainerに付随する単一のCodeContextを、全メンバーの名前解決環境として使用してはならない。

統合後の宣言は1つのSymbolで表す。一方、元の宣言断片も、エラー位置の表示やヘッダーの一致検査のために残す。

**例：Containerを統合しても、aliasは共有しない。** ExternalLib.GroupAは公開されたStructBを持つものとする。

```kimi
// A.kimi
alias ExternalLib.GroupA

group Work
    func accept(value: StructB) -> () => () // A.kimiのaliasを使う。
```

```kimi
// B.kimi
group Work
    func reject(value: StructB) -> () => () // エラー：A.kimiのaliasは使えない。
```

2つのWorkは1つのContainerになるが、rejectの型注釈はB.kimiのCodeContextで調べる。

### 2.2. 外部ライブラリーとalias

#### 2.2.1. 参照できる外部ライブラリー

- 外部Kotonohaへの名前による直接参照は、プロジェクトが直接参照する依存ライブラリーに限る。
- 全外部ライブラリーから非修飾名を無条件に探索しない。
- `ExternalLib.GroupA.StructB`のような修飾参照、または明示的に導入された名前を使う。
- 複数バージョンは、異なるKotonoha参照名を割り当てて参照できる。参照名を設定する構文・設定形式は別途定義する。
- Kotonoha参照名の割り当てと、Containerのメンバーを導入するソース上の`alias`は異なる操作である。
- 推移的依存のメタデータを型検査のために読み込むことは、そのKotonoha名をソースから直接探索可能にすることを意味しない。

#### 2.2.2. aliasが導入する名前

```kimi
alias ExternalLib.GroupA
```

この宣言は対象Containerを開き、その直接のメンバーを非修飾名による探索対象へ加える。

1. aliasはトップレベルに記述し、記述したSourceDocument内だけで有効とする。既存の、通常の宣言・実行コードより前に置く制限を維持する。
2. 対象はContainerとする。ネストされたContainerも指定できる。
3. 型、関数、Property、子Containerなど、対象の直接のメンバーを各名前空間の規則に従って導入する。
4. 子Container内部のメンバーを再帰的に導入しない。子Container自体が導入されれば、その先は修飾して参照できる。
5. ソースaliasを別ファイルや利用側ライブラリーへ自動的に再公開しない。
6. alias同士の記述順で結果を変えない。
7. alias対象の解決には、同じソースの別aliasやデフォルトaliasを使用しない。Compilation rootを起点に対象パスを解決する。
8. alias対象自体へのアクセス権を宣言位置で検査する。導入されたメンバーのアクセス権は実際の使用位置で検査する。

CodeContextにはalias対象Containerへの参照を保存する。ファイル全体に対して「アクセス可能な全メンバー一覧」を確定して保存してはならない。privateメンバーへのアクセス可否は使用位置によって異なる。

**例：aliasで省略できる範囲。** ExternalLibが次の型を公開しているものとする。

```text
ExternalLib
└─ GroupA
   ├─ StructB
   └─ Child
      └─ StructC
```

```kimi
alias ExternalLib.GroupA

func useB(value: StructB) -> () => ()       // GroupA直下なので名前を省略できる。
func useC(value: Child.StructC) -> () => () // Childの内側は、さらに修飾する。
func invalid(value: StructC) -> () => ()    // エラー：孫の名前までは導入しない。
```

`StructC`を直接使いたい場合は、`alias ExternalLib.GroupA.Child`を明示する。別のaliasを使った省略形`alias Child`では解決しない。

#### 2.2.3. 複数のaliasとデフォルトalias

- 同じ段階のaliasは1つの探索段階として扱う。
- 同じSymbolへの複数経路は重複排除する。aliasの重複回数を優劣に使用しない。
- 異なる型が同名の場合は、Lookup Roleで候補段階を確定し、3.5節のType Name Selectionに従う。
- 異なるContainerから導入された同名関数は、同じオーバーロードの候補集合に含める。
- 関数とPropertyなど、異なる値の宣言が同じ優先段階に導入される場合は名前の衝突とする。引数の形で関数側を優先しない。
- デフォルトaliasはCompilationに設定する。各ソースの明示aliasより低い優先段階で作用する。

#### 2.2.4. 利用者へ明示的に再公開する

re-exportは明示的な宣言を必要とし、通常のaliasからは発生しない。再公開によって元宣言やそのアクセス経路の権限を拡大しない。再公開は元のSymbolの同一性を保存する。

探索は公開名から元Symbolへの参照として扱い、再公開経路を毎回再帰的にたどらない。循環だけで実体へ到達しない再公開はエラーとする。具体的な構文は6.2節に残す。

### 2.3. 分かれて書かれたContainerを統合する

#### 2.3.1. どの宣言を統合するか

同じKotonohaに属する宣言だけを統合する。「親のContainerが同じ」「宣言名が同じ」断片を集め、宣言種別と型パラメーターの個数で整理する。統合の識別情報は、宣言元Kotonoha、親ContainerのSymbol、宣言名、宣言種別、型パラメーターの個数である。

- 同名の`group`と`struct`など、宣言種別が矛盾するものはエラーとする。
- この識別情報が一致し、2.3.2節のヘッダー検査に通る断片を、1つのContainer Symbolへ統合する。
- 同名でも型パラメーターの個数が異なる型宣言は別の型として扱う。例えばBoxとBox<T>を統合しない。
- 使用側で型に付けるType Semanticsは統合の識別情報に含めない。`ref/Box<T>`と`uniq/Box<T>`は同じBoxの宣言Symbolを参照する。
- 別Kotonohaの同名Containerは統合しない。外部型へのextensionも、元型の宣言断片とは扱わない。
- 同じファイル内の反復宣言にも、ファイルをまたぐ場合と同じ統合規則を適用する。

#### 2.3.2. ヘッダーに必要な一致

本原案の補完規則として、各断片には同じ型パラメーターの宣言とOriginリストを記述し、次を一致させる。

- 型パラメーターの数、種類、順序、名前。
- Origin宣言の数、順序、名前。
- 宣言種別と、意味に影響する修飾子。
- 既定値を適用した後のAccessibility。

例えば、ある断片が`public`、別断片が無指定で既定の`private`になる場合は不一致とする。暗黙に広い方のアクセス権を採用しない。

`rootgroup A.B`によって自動生成される中間groupは、ソースに書かれた独立したヘッダー断片とは扱わない。そのAccessibilityは、そのgroupの明示宣言があればそれに従い、なければprivateとする。公開経路が必要なら各groupを明示的に公開する。

#### 2.3.3. Type Contractとメンバーの重複

- ContainerのType Contractを記述できる宣言断片は1カ所だけとする。
- 同じ内容であっても複数断片での定義はエラーとする。
- 他の断片はType Contractを省略し、唯一の定義の制約を共有する。
- Contractの名前は、その定義位置のCodeContextで解決する。
- 統合後に、同名Property、Signatureが同じ関数、同じ名前空間に置けない異なる種類の同名宣言を検査する。
- コンパイル時条件によって排他的な断片は、条件選択後の有効な宣言に対して検査する。保留条件は4.4節に従う。

structのStorage順序は2.3.4節に従う。groupの複数断片にまたがる静的Property初期化順や、トップレベル実行順は6.2節の別の決定事項である。

**例：制約は1カ所に書き、統合後の型全体で共有する。** Comparableは別途宣言済みの制約とする。

```kimi
// A.kimi
struct Box<T>
    T is Comparable
    var count: i32 = 0
```

```kimi
// B.kimi
struct Box<T>
    func countValue(self: ref/Self) -> i32 => self.count
    // Box全体には、A.kimiに書いたTの制約が適用される。
```

B.kimiにも`T is Comparable`を書くと、同じ内容でも重複エラーになる。また、B.kimiを`struct Box<U>`とすると、断片間で型パラメーター名が一致しないためエラーになる。

#### 2.3.4. 分割structのStorage・レイアウト・初期化

groupとstructは複数断片に分割できる。structでは、Source Generatorが生成した断片を含め、複数断片にStorageを持つPropertyを宣言してよい。primary fragmentは要求しない。ヘッダー・重複宣言・Type Contractの検査は維持し、暗黙のStorageや`has`の展開もSPEC.mdのProperty規則で分類する。

[SPEC.mdの論理宣言順序](../SPEC.md#431-split-structures-and-storage-order)を次のように適用する。

1. 通常ソースを生成ソースより先に置き、通常ソース同士は安定した論理ソース識別子順にする。
2. 生成ソース同士は、安定したGenerator識別子、Generator内の論理出力識別子の順にする。
3. 同じソース内では、同じstructの複数断片も含めて宣言位置順にする。

通常ソースは正規化したプロジェクト相対の論理パスを使う。プロジェクト外のソースには安定した論理名を割り当て、生成出力にはGeneratorが論理名を付ける。パス区切りを`/`へ統一し、冗長なパス要素を取り除き、ホストの大文字小文字規則やロケールに依存しないordinal比較を使う。識別子の重複は、その識別子の所属範囲内でビルドエラーとする。

絶対パス、一時出力先、ファイル列挙順、解析完了順、Generatorの実行完了順を順序に使わない。ファイル名や論理出力名の変更で論理順序が変わる可能性はある。

| 項目 | 規則 |
| --- | --- |
| Storageの論理順序 | 各特殊化で選択された宣言を上記の順序に並べ、Storageを持つPropertyを取り出す |
| メモリ配置 | Storageの型・ターゲット・配置方式から決定。同じ入力・コンパイラー・設定で再現可能にするが、論理順序と物理オフセット順の一致は要求しない |
| 宣言初期化式 | 論理順序で各1回実行し、副作用の順序を維持。setterを呼ばず、初期化に成功したStorageを記録する |
| 回復可能な構築失敗の後始末 | 構築側が所有する初期化済みStorageだけを、初期化の逆順で破棄。初期化式の副作用は取り消さない |

通常structは、ソースやコンパイラーの変更をまたぐABI固定を保証しない。FFIなどに必要な固定配置は別の明示的な仕組みとして定義する。

インスタンスPropertyの宣言初期化式から、構築途中の`self`や、そのインスタンスの他のPropertyへアクセスしてはならない。そのインスタンスの初期化済みPropertyの参照、`self`を受け手とする関数呼び出し、`self`を他の関数へ渡すことも禁止する。独立した関数呼び出しや、別の初期化済みの値へのアクセスは通常の型・寿命規則に従って許可する。Property間に依存する初期化は、明示的な構築処理や生成された初期化処理に記述する。その構文・許されるアクセス・全Storageの初期化完了の検証は構築仕様で定める。初期化式のないPropertyへ暗黙の既定値は与えない。

後始末は[SPEC.mdの初期化規則](../SPEC.md#66-initialization)と通常のScope Exitに従う。Panicはunwindせず、発散や強制終了に新たな後始末保証を与えない。初期化途中のstructを完成済みとして破棄しない。

上のBoxでは、通常ソースの識別子がA.kimi、B.kimiなら、A.kimiのcountが先になる。B.kimiに`var enabled: bool = true`を追加しても有効で、enabledの初期化はcountの後になる。生成ソースが追加するStorageは通常ソースの後に並ぶ。

#### 2.3.5. Source Generatorの出力を確定する時点

Generatorの出力は、その宣言が影響するスコープの通常の名前解決を開始する前に収集し、条件選択と統合を行う。未完成の型を使って解析を始め、後からStorageを追加してはならない。レイアウトは、選択された全断片とPropertyのStorage分類が確定してから決める。

生成ソースも独立したSourceDocument・CodeContext・論理識別子を持ち、名前解決はその環境で行う。GeneratorのAPI・実行段階の詳細は別途定義する。必要な名前探索環境を確定できない生成依存の循環はエラーとし、確定済みの参照を書き換えて解消しない。

<a id="name-resolution"></a>

## 3. 名前の参照先を決める

名前の種類、使える範囲、アクセス権を確認し、決められた順序で参照先を探す。

### 3.1. 名前の種類と有効範囲

#### 3.1.1. 型名と値名を分ける

| Namespace | 含める名前 |
| --- | --- |
| Type | group、struct、enum、contract、Kotonoha参照名、コア型パラメーター、所有・借用などを表す型パラメーター、関連型、`Self` |
| Value | 関数、Property、引数、ローカル、ローカル関数 |
| Origin | Origin宣言 |
| Label | Labeled BlockなどのLabel |

名前空間は宣言を管理する区分であり、Lookup Roleは構文上の用途に応じて探索対象を絞る条件である。例えばgroupはType namespaceに属するが、Core Typeとしての探索対象には含めず、Qualifierとしての探索対象には含める。Lookup Contextには名前空間とLookup Roleの両方を保持し、探索を止める前に役割への適合を判定する。

| Lookup Role | Namespace | 名前を使う位置と主な探索対象 |
| --- | --- | --- |
| Core Type | Type | 型注釈などで基礎となる型を書く位置。struct、enum、Core Typeパラメーター、関連型、Selfなど |
| Type Semantics | Type | `s/T`のsなど、所有・借用などの性質を書く位置。Semanticsパラメーターなど |
| Qualifier | Type | 型・Container側の修飾名の途中。group、Kotonoha参照名、修飾の起点になれる型など |
| Value | Value | 値の参照位置。関数、Property、引数、ローカル、ローカル関数 |
| Requirement | Type | Type Contractなどの要件名の位置。contractで宣言した能力や、要件構文で許された型・Semantics・カテゴリなど |
| Declaration Container | Type | aliasの対象位置など、Containerを要求する位置。対象構文で許されたContainer宣言 |
| Origin | Origin | Origin名の位置。Origin宣言 |
| Label | Label | Label名の位置。Labeled BlockなどのLabel |

1つの宣言が複数の役割を持ってよい。structはCore TypeにもQualifierにもなれる。組み込み型やSemanticsなどの言語定義の表記は、それぞれの構文規則に従う。

Lookup Roleは名前を使う構文位置から決める。型引数の個数、呼び出し引数の型やラベル、期待戻り値型、Type Contractの成立、実際に後続メンバーが存在するかどうかを、役割による候補の選別へ混ぜない。`f()`のfもValueとして探し、呼び出せる宣言だけを対象とする役割は設けない。

型名と値名は別名前空間なので共存できる。同一名前空間・同一スコープでは、Containerの適法な統合、型Signatureによる区別、関数オーバーロードを除いて同名宣言を禁止する。

Lookup Roleの違いはこの宣言衝突規則を変更しない。同一スコープへ`group X`と`struct X`を直接宣言することは許可しない。

#### 3.1.2. ローカル変数と前方参照

- ローカル変数は宣言位置以降で有効とし、初期化式には新しいbindingを導入しない。
- `let x = x`の右辺は外側の`x`を参照する。外側に存在しなければ未定義名エラーとする。
- 内側のスコープでは、外側と同名のローカル変数を宣言して、外側の名前を隠せる（shadowing）。同じブロックでの同名ローカル再宣言は許可しない。
- Container内のメンバーは宣言順にかかわらず参照できる。ただし、名前が見えることと、初期化前に値を読めることは別である。
- ローカル関数は、宣言を含むブロックに入った時点から名前を使える。そのため、関数を書く前にも呼び出せる。同じブロックの同名ローカル関数はSignatureが異なる場合にオーバーロード集合を作る。
- ローカル関数と同じブロックのローカル変数・引数の同名衝突は許可しない。引数と関数本体直下のローカルは、この重複検査では同じ宣言空間とする。
- 型パラメーターは宣言元の関数・型のスコープに属する。
- ローカル関数本体から外側の型パラメーターを参照できる。一方、外側の実行時ローカルの捕捉は、捕捉仕様が導入されるまでエラーとする。
- 関数・無名関数の境界を越える名前の可視性は、捕捉を暗黙に許可しない。

**例：ローカル変数とローカル関数では、有効になる時点が違う。**

```kimi
func example() -> i32
    let x = 10
    if true
        let x = x + 1 // 右辺のxは外側の10。内側のxは11になる。

    let result = later() // ローカル関数は宣言前に呼べる。
    func later() -> i32 => 20
    return result
```

```kimi
func invalid() -> i32
    let result = laterValue // エラー：ローカル変数は宣言前に使えない。
    let laterValue = 20
    return result
```

#### 3.1.3. Self、self、storage、value

- `Self`は予約名とし、通常宣言による再定義を禁止する。有効な型文脈の外では使用エラーとする。
- `self`、`storage`、`value`は特定の文脈だけで特別な意味を持つ名前とする。
- 特別な名前が有効な場所では、その名前をローカル変数や引数として再宣言してはならない。
- 有効でない文脈では通常名として宣言・使用できる。
- 特別な名前の導入範囲は受け手・accessorの仕様で定める。ネストされた関数へ実行時bindingを暗黙に捕捉しない。
- OriginとLabelは独立名前空間で解決し、同名のTypeやValueを参照しない。

**例：valueが特別な意味を持つ場所だけ、同名宣言を禁止する。**

```kimi
struct Counter
    var count: i32 = 0
        set
            let value = 10 // エラー：setterのvalueを隠すことはできない。
            storage = value

func identity(value: i32) -> i32 => value // 通常の関数では引数名に使える。
```

#### 3.1.4. ファイル直下の実行コード

本原案の補完規則として、トップレベルのローカルとローカル関数はSourceDocumentごとの実行スコープに属する。他ファイルから参照できず、Compilation rootにも公開しない。ファイル間で共有する関数・Propertyは、名前付きContainerに宣言する。

生成関数へ複数ソースの構文を配置する実装であっても、このソース単位のスコープとCodeContextを維持する。ソース間の実行順は本書では定義しない。

### 3.2. アクセスできる範囲

#### 3.2.1. private、internal、public

| Accessibility | アクセス範囲 |
| --- | --- |
| private | 宣言元Containerと、その内側にある本体 |
| internal | 同一Kotonoha |
| public | 宣言自体はKotonohaの外部からもアクセス可能 |

アクセス修飾子を持てる宣言の既定はprivateとする。ローカル、引数、特別な名前には字句スコープ規則を使用する。

Accessibilityはアクセス権を、Name Reachabilityは使用位置から名前を探せる経路を表す。Name Reachabilityの経路には、字句スコープやContainerからの直接参照、修飾名、alias、明示的なre-exportがある。通常の解決候補になるには、有効な経路、要求されたLookup Roleへの適合、Accessibilityのすべてが必要である。

publicでも、有効な参照経路がなければ名前を解決できない。例えば公開型でもaliasなどで導入されていなければ非修飾名では参照できず、直接依存Kotonohaからの修飾経路などが必要になる。逆にaliasやre-exportで名前を導入してもアクセス権は拡大しない。包含するContainerと経路上のアクセス制限も満たす必要がある。ここでのName Reachabilityは、SPEC.mdの制御フロー上のReachabilityとは別の概念である。

- privateのContainerは統合後のSymbolで判定する。同じContainerの別ソース断片も範囲内である。
- privateは「同じソースファイル」を意味しない。
- 親Containerから子Containerのprivateメンバーへアクセスする権限は、親であることだけでは与えない。
- extensionは外部型の宣言元Containerの本体ではない。extensionであることだけで対象型のprivateメンバーへのアクセス権を与えない。
- 実効的なアクセス範囲は、包含するContainerの制限も受ける。publicメンバーだけでprivateな公開経路を迂回できない。
- 外部公開Signatureは、利用者から参照可能な型・要件で表現できなければならない。
- accessorはPropertyのAccessibilityを継承し、より厳しい制限だけを指定できる。

**例：privateは、ファイルではなく宣言元のContainerを基準にする。**

```kimi
// A.kimi
group Vault
    private var secret: i32 = 7
```

```kimi
// B.kimi
group Vault
    func read() -> i32 => secret // 許可：統合後は同じVaultの内部。

group Other
    func read() -> i32 => Vault.secret // エラー：OtherはVaultの内部ではない。
```

OtherをA.kimiへ移しても結果は変わらない。

#### 3.2.2. アクセスできない宣言を見つけた場合

アクセスできない同名宣言は診断情報として認識するが、通常の解決候補には含めない。それだけでは外側探索を止めない。要求されたLookup Roleに合わない宣言も探索を止めず、種類不適合の診断情報として保持する。

一方、アクセスできるPropertyを選んだ後にsetterがprivateであることや、選んだインスタンスメンバーに受け手がないことは、外側を探し直す理由にならない。

### 3.3. 名前だけで参照する場合

#### 3.3.1. 名前を探す順序

要求された名前空間とLookup Roleについて、次の順に探索する。

| 優先順位 | 対象 |
| --- | --- |
| 1 | 現在のローカルスコープから、外側の字句スコープ・引数スコープへ |
| 2 | 現在のContainer |
| 3 | 親Containerを順にたどり、プロジェクトrootまで |
| 4 | Compilation rootにある直接依存Kotonohaの参照名。型の名前空間のみ |
| 5 | 現在のSourceDocumentの明示alias |
| 6 | Compilationのデフォルトalias |

直接依存Kotonohaの参照名の段階は、外部ライブラリー内部の非修飾探索ではなく、修飾の起点となる参照名の探索である。型パラメーターのスコープは、その宣言元の関数・型に対応する字句位置で探索する。特別な名前は有効な文脈の字句スコープに置く。

#### 3.3.2. 探索を止める条件

1. 各段階で、同名・同名前空間の宣言を収集する。
2. 同じSymbolへの経路を重複排除する。
3. Lookup Roleへの適合とAccessibilityで、通常候補と診断専用情報を分ける。
4. 要求された役割に合い、アクセスできる宣言がなければ次の段階へ進む。
5. 要求された役割に合い、アクセスできる宣言があれば、その段階で候補集合を確定する。

候補集合を確定した後は、型引数の個数、引数型、引数ラベル、Type Contractが合わない場合や、見つかった値が呼び出せない場合も、外側へ戻らない。高速化のために型引数の個数で候補を先に絞る実装でも、この探索停止の規則を守る。

**例：近いgroupは、Core Typeとしての探索を止めない。** SomeLibraryは公開されたstruct Xを持つものとする。

```kimi
alias SomeLibrary

group Current
    group X
        public var count: i32 = 1

    func use(value: X) -> i32
        return X.count
```

引数の型注釈の`X`はCore Typeとして探すため、Current.Xを候補に含めず、alias側のSomeLibrary.Xへ解決する。`X.count`の型側の先頭名はQualifierとして探すため、Current.Xへ解決する。このように、同じ綴りでも構文上の役割によって別の宣言を参照してよい。

Current.Xにcountがなければ、`X.count`は名前解決エラーとする。後続メンバーがあるかどうかでSomeLibrary.Xへ切り替えない。

**例：名前を見つけた後の引数不一致では、親へ戻らない。**

```kimi
group Outer
    func f(value: i32) -> i32 => value

    group Inner
        func f(value: string) -> string => value

        func test() -> ()
            f(1)              // エラー：Inner.fはstringを要求する。
            ::Outer.f(1)      // 許可：親側の関数を明示している。
```

`f(1)`を見たとき、Innerのfが見つかった時点で名前の探索を止める。Outer.fなら呼べるという理由では切り替えない。

ローカル`f`が整数でもValueの役割には合うため、その段階で探索を止める。`f()`は呼び出せない値としてエラーとし、外側の同名関数へ切り替えない。

すべての段階を調べても候補がなければ、要求された役割に合うがアクセスできない宣言がある場合はアクセス拒否を説明する。それがなく、アクセスできる同名宣言が役割に合わない場合は「XはCore Typeとして使用できない」などの種類不適合を説明し、それ以外は要求された役割の名前が未定義であると診断する。

#### 3.3.3. selfを自動で補わない

インスタンスメンバーへの暗黙の`self`補完を行わない。インスタンスメンバーを使用する場合は`self.member`など受け手を明示する。

アクセスできる同名インスタンスメンバーしか見つからない非修飾参照は、「受け手が必要」と診断する。親の同名静的メンバーやaliasへ切り替えない。

### 3.4. 修飾名と絶対修飾を使う場合

#### 3.4.1. A.B.Cの解決

`A.B.C`の先頭`A`は、その位置のLookup Roleを指定して通常の名前探索で解決する。その後は解決した対象のメンバーの探索だけを行い、対象の親スコープへ戻らない。型位置の`A.B.C`なら、AとBはQualifier、最後のCはCore Typeとして探す。aliasの対象なら最後はDeclaration Containerなど、終端の役割は構文に従う。

式の中など、型名と値名の両方を使える場所では、値名を優先せず、Type namespaceのQualifierとValue namespaceのValueから修飾名をたどる。値側の先頭名は、後続メンバーを持つことを探索条件にしない。

1. 各名前空間で、先頭名の役割に合い、アクセスできる候補が最初にある段階を確定する。
2. 各経路について修飾名全体をたどる。各要素を構文上許された役割で探索し、メンバーの存在、Accessibility、静的メンバーとインスタンスメンバーの区別を検査する。途中で型側・値側の両方の経路が可能なら、両方を検討する。
3. 一方の経路だけが成立すれば、それを採用する。
4. 独立した複数経路が成立すれば曖昧性エラーとする。同じSymbolへの同一の参照は重複排除するが、異なる受け手を持つ値アクセスは同一視しない。
5. どちらも成立しなければ名前解決エラーとする。

先頭名を確定した後に後続メンバーが見つからない場合や、後続の名前が要求された役割に合わない場合も、同じ名前空間の外側の先頭名へ戻らない。途中の型・値を確定するためにオーバーロード呼び出しの戻り値が必要なら、その呼び出しを独立に確定する必要がある。

「経路が成立する」は名前解決の条件を意味する。`A.B(args)`の引数適合性や期待戻り値型で型/値の経路を選び直してはならない。関数群への経路が1つに決まってからオーバーロード解決を行う。

**例：同名の型側と値側の両方でメンバーが見つかる。** 次は、Bを持つ値の型InstanceAが別途定義されている場合の例である。

```kimi
group A
    public var B: i32 = 1

// InstanceAには、公開されたinstance Property Bがあるものとする。
func read(A: ref/InstanceA) -> i32
    return A.B // エラー：group AのBと、引数AのBの両方が成立する。
```

この場合、引数Aを優先しない。group側を選ぶなら`::A.B`と書く。値側を選ぶなら、引数を`instance`などに改名し、`instance.B`と書く。

#### 3.4.2. ::から始まる絶対修飾

`::A.B.C`はCompilation rootを起点とする。ローカル、ソースalias、デフォルトaliasを先頭名の解決に使用しない。

Compilation rootには次を置く。

- プロジェクトrootの宣言。
- 直接依存Kotonohaの参照名、すなわち依存ライブラリーの参照名。

プロジェクトrootの宣言と直接依存Kotonohaの参照名の同名衝突は禁止する。これは型/値の名前空間の違いにかかわらず適用する。プロジェクトrootの宣言同士の共存は通常の名前空間とSignature規則に従う。

絶対修飾にも各要素のLookup Roleを適用し、Accessibilityを迂回しない。役割に合う候補がなくても、ローカルやaliasへ探索先を切り替えない。

**例：通常の修飾と、rootから始める修飾。**

```kimi
group Config
    public var count: i32 = 3

func read(Config: i32) -> i32
    return ::Config.count // ローカル引数Configを調べず、rootのgroupを使う。
```

`Config.count`と書いた場合は両名前空間を検討する。この例では整数の引数にcountがないので、group側だけが成立する。

### 3.5. 型名の候補を選ぶ（Type Name Selection）

型名の探索と、型引数による型宣言の選択を分ける。明示型引数を持つ名前では、次の順に処理する。

1. Name Resolutionで、Lookup Roleに合い、アクセス可能な宣言が最初にある探索段階の候補集合を確定する。
2. 明示された型引数の個数・種類が宣言に合う候補を残す。型引数自身の名前は、使用位置のLookup Contextで解決する。
3. 残った候補が1つなら、その型宣言を選択する。
4. 0なら型引数不一致とする。
5. 複数なら曖昧性エラーとする。
6. いずれの失敗でも外側の探索段階へ戻らない。

型引数の個数・種類は探索停止後に検査する。Type Contractは選択後に検査し、制約不成立を理由に別の型宣言を選び直さない。型引数に未定義名や不正な型構文がある場合は、そのエラーを報告する。正当な依存で種類が未確定なら、候補段階を固定して選択を保留する。

修飾された型名では、3.4節で確定した対象内の候補集合にこの選択を適用する。型引数を明示しない名前では、各構文で規定した省略・推論規則に従う。推論範囲をこの選択のために広げたり、近い候補が不適合だから外側を調べたりしない。

例えば、同じ探索段階にBox<T>とBox<T, U>があれば、`Box<i32>`は前者を選ぶ。近い段階にBox<T, U>しかなく、alias側にBox<T>があっても、`Box<i32>`は近い段階で型引数不一致となる。同じ段階の別aliasから異なるBox<T>が導入されれば、`Box<i32>`は曖昧である。

## 4. 呼び出す関数を決める

名前解決で候補が決まった後、引数や型の条件を調べて関数を選ぶ。選択後に、Moveや借用、unsafeの使用可否を検査する。

### 4.1. 同名の宣言を区別する条件

#### 4.1.1. Signatureに含める情報

| 宣言 | Signature |
| --- | --- |
| 型 | Type Semantics、Name、型パラメーターの個数という既存の型Signatureを基礎とする |
| 関数 | Name、型パラメーターの個数（Generic Arity）、順序付きの正規化引数型 |
| Property | Name |

型SignatureはSPEC.mdの用語を維持するが、Container宣言断片の統合には2.3.1節の識別情報を使う。型に適用されたSemanticsを統合キーに使わない。

**正規化引数型**は、受け手を含む引数のTypeを、4.1.2節のSignature比較規則に従って正規化したものである。[SPEC.mdのParameter Signature](../SPEC.md#51-signatures)に対応し、Type SemanticsはTypeの構成要素として含める。SemanticsをTypeと別の情報として二重に加えない。

Signature比較ではOrigin名・Originリスト・寿命関係を識別情報から除外する。これらを含む完全なTypeとOrigin契約は意味解析用に保持する。「正規化引数型」は、完全なType同一性の検査によってOriginだけのオーバーロードを許す意味ではない。受け手の`ref/Self`と`uniq/Self`は、Type Semanticsが異なるため区別する。

関数の戻り値型、外部引数名・内部引数名、既定値の式、省略可能かどうかの指定、Accessibility、unsafe修飾、Type Contractの違いだけではオーバーロードを作れない。

`ref/T`や`uniq/T`は型Tを借用して使うための型であり、それぞれが別のContainer宣言になるわけではない。Tの宣言を表すSymbolと、Tに所有・借用などの性質を付けた型を区別する。

#### 4.1.2. 書き方の違いをそろえて比較する

- 名前の表記やalias経路ではなく、解決済みSymbolに基づいてCore Typeを比較し、適用されたType Semanticsも比較する。
- `T`と`owner/T`など同義の表記を正規化する。
- 型パラメーターは宣言位置の番号と種類で表現し、`f<T>(T)`と`f<U>(U)`を同じSignatureとする。
- 宣言断片のヘッダー名一致と、異なる関数宣言のSignatureでの型パラメーター名の正規化は、別の検査である。
- 正規化引数型のSignature比較からOrigin名、Originリスト、寿命関係を除外し、それらだけが異なる関数オーバーロードを禁止する。Origin契約は型検査と呼び出し検査のために保持する。
- 受け手を含む引数のType Semanticsが異なれば、別のオーバーロードを作れる。`ref`と`uniq`などの意味の違いを正規化で消してはならない。
- 別Kotonoha・別バージョンの宣言Symbolを同一視しない。

同じSignatureの宣言は宣言側でエラーとする。別Containerからaliasによって同じ形の関数が導入された場合は、それぞれ別Symbolであり、使用時に1つに選べなければ曖昧性エラーとなる。

**例：受け手のType Semanticsが異なる関数は共存できる。**

```kimi
struct Reader
    func read(self: ref/Self) -> i32 => 0
    func read(self: uniq/Self) -> i32 => 0 // 許可：受け手のSignatureが異なる。
```

両方の`Self`は同じReaderを指すが、共有借用と排他的な借用の違いで宣言を区別する。通常の引数でも`ref/T`と`uniq/T`は区別する。一方、`T`と`owner/T`だけが異なる宣言は、正規化後に同じSignatureとなるため共存できない。

宣言の共存と、呼び出し時に候補が1つに決まることは別である。この`read`も4.2節の型適合と4.3節の優劣規則で選び、決まらなければ呼び出しを曖昧性エラーとする。

**例：型パラメーターの名前だけを変えても、別の関数にはならない。**

```kimi
func identity<T>(value: T) -> T => value
func identity<U>(value: U) -> U => value // エラー：同じSignature。
```

**例：戻り値型だけを変えた宣言も禁止する。**

```kimi
func convert(value: i32) -> i32 => value
func convert(value: i32) -> string => "text" // エラー：同じSignature。
```

これは宣言自体の重複であり、呼び出し側に期待型を書いても合法にはならない。

### 4.2. 各候補を呼び出せるか調べる

#### 4.2.1. 候補を検査する順序

名前解決で確定した候補集合について、各候補を独立に検査する。

1. 明示された型引数の個数・種類を調べる。
2. 位置引数・名前付き引数を宣言側の引数へ対応付ける。
3. 受け手と呼び出し側の引数から、型パラメーターに当てはめる型を推論する。
4. 必要なら、既知の期待戻り値型で未確定部分を補う。
5. 許可された型適合、関数型との適合、Type Contractを検査する。
6. 適用可能な候補を収集する。
7. 4.3節の優劣規則で候補を1つ選ぶ。
8. 選択結果を確定し、使用可否を検査する。

候補が0なら「適用可能なオーバーロードがない」、他の候補よりよいものが1つに決まらなければ曖昧性エラーとする。いずれの場合も名前解決の外側探索へ戻らない。

候補検査中は、実行時のCopy/Move・借用・既定値の評価を実行せず、最終的なBinding木にも確定しない。

候補の宣言自体にある未定義の型名、不正なType Contract、同じSignatureの重複などは宣言エラーである。別候補が成功したことを理由に、その宣言エラーを隠してはならない。候補ごとの失敗として扱うのは、合法な宣言が今回の呼び出しへ適用できない場合である。

#### 4.2.2. 呼び出し側の引数を宣言へ対応付ける

1. 位置引数を宣言側の引数の先頭から順に対応付ける。
2. 名前付き引数を外部引数名で対応付ける。
3. 未知の外部引数名、位置引数の渡しすぎ、同じ引数への二重指定をエラーにする。
4. 未指定の省略できない引数があれば拒否する。
5. 未指定の省略可能な引数を既定値の使用として記録する。

位置引数は名前付き引数より先に記述する。名前付き引数同士の順序は任意とする。評価は明示引数の記述順、次に省略された既定値を引数が宣言されている順序とする。

既定値の式は宣言位置で名前解決し、宣言上、前にある引数を参照できる。呼び出し元のローカルや宣言上、後ろにある引数は参照できない。省略された既定値の式から型パラメーターを推論しない。

通常の関数型は、外部引数名と既定値を保持しない。関数値の呼び出しは、全引数を位置で渡す。

**例：外部引数名と内部引数名を分ける。**

```kimi
func scale(value: i32, by? => factor: i32 = 2) -> i32
    return value * factor

scale(3)                  // value=3、factorは既定値2。
scale(3, by: 4)           // 呼び出し側は外部名byを使う。
scale(by: 4, value: 3)    // 名前付き引数同士の順序は自由。
scale(3, value: 4)        // エラー：valueへの二重指定。
scale(3, factor: 4)       // エラー：factorは関数内部の名前。
```

上の呼び出しでは、書かれている引数を記述順に評価してから、必要な既定値を評価する。

#### 4.2.3. 暗黙に認める型の合わせ方

許可する適合を次の分類に限定する。

| 変換の種類 | 意味 |
| --- | --- |
| 完全一致（Exact） | 正規化後の型が一致し、型を変更する暗黙の適合を必要としない |
| リテラルの適合（Literal fitting） | 未確定リテラルを、候補の期待型へ直接適合させる |
| 安全な借用・再借用（Safe borrow/reborrow） | 型、受け手の権限、式の形に応じて、許可された借用や再借用を行う |

Exactは型適合の分類であり、Copy/Moveの有無を表さない。Copy/Moveは候補選択後に[SPEC.mdのValue Lifetime規則](../SPEC.md#71-copy-and-move)に従って決め、実行可能かを使用可否の段階で検査する。例えば保存されたi32の値渡しはExactでもCopyし、保存された非Copy所有値の値渡しはExactでもMoveする。Copy/Moveの違いを変換品質の順位に加えない。

同じ引数に対する比較では、完全一致、リテラルの適合、安全な借用・再借用の順に良いものとする。同一分類内の未定義の優先順位を推測して追加しない。

初期の借用による型の適合表は次を基礎とし、実装前にOrigin・一時値の条件を含む完全な表へ展開する。

| 入力 | 期待される型 | 適合 |
| --- | --- | --- |
| 読み取り可能な`T`の場所 | `ref/T` | 共有借用 |
| 排他的な書き込み権限を持つ`T`の場所 | `uniq/T` | 排他的な借用 |
| `uniq/T` | `uniq/T` | 呼び出し用の排他的な再借用 |
| `uniq/T` | `ref/T` | 共有の再借用 |
| `obj/T`のアクセス可能な場所 | `objref/T` | オブジェクトの共有借用 |
| 排他的な書き込み権限を持つ`obj/T`の場所 | `objuniq/T` | オブジェクトの排他的な借用 |
| `objuniq/T` | `objuniq/T`または`objref/T` | 対応する再借用 |

同じ表記の排他的な参照を渡す場合も、再借用が必要なら完全一致として扱わない。共有参照の適法な短縮など、既存のOriginの下位型規則で許される適合を漏らさず表に含める。`rc`/`arc`など未整理の組み合わせを、上表から類推して追加しない。

候補を検査するときは、型の種類、型や宣言から分かる権限、式が変数などの場所を指すか一時的な値かを調べる。現在のLoanとの衝突やMove済みなどの実行の流れに沿って変わる状態は4.5節で検査する。借用による型の適合は寿命を延長せず、暗黙に所有権を複製しない。

数値幅、符号、整数/浮動小数点間の暗黙変換、ユーザー定義暗黙変換、無制限の参照解除・変換連鎖を導入しない。生ポインターの参照解除は明示する。SPEC.mdで別途定義されたNeverなどの型規則は、型検査上の規則として維持し、オーバーロード専用の優先順位を追加しない。

**例：完全一致と、暗黙の借用を区別する。**

```kimi
func inspect(value: i32) -> () => ()
func inspect(value: ref/i32) -> () => ()

let number: i32 = 10
inspect(number) // i32なら完全一致。ref/i32への借用より優先する。
```

どちらの候補に対しても、検査中に値を移動したり借用を確定したりはしない。候補を選んだ後で、必要な操作を確定する。

#### 4.2.4. リテラルを候補の型に合わせる

- 未型付けの整数リテラルは、値が表現可能な候補の整数型に直接適合する。
- 浮動小数点リテラルは、SPEC.mdの数値規則に従って候補の浮動小数点型に適合する。
- 最初にi32/f64へ確定してから変換する方式にしない。
- 同じ整数値がi32とi64へ適合しても、i32や小さい幅を優先しない。
- `null`、空コレクション、無名関数など期待型を必要とする式に、万能な既定型を与えない。
- 候補比較の曖昧性を、数値の既定型で解消しない。
- 独立した式で期待型がなければ、既存のi32/f64などの既定規則を適用する。ジェネリックの型推論でも、既定型を選ぶ前に受け手・他の引数・既知の期待型からの制約を処理する。

**例：数値を直接渡す場合と、型が決まった変数を渡す場合。**

```kimi
func f(value: i32) -> () => ()
func f(value: i64) -> () => ()

f(1) // エラー：1はi32にもi64にも収まり、どちらとも決まらない。

let x = 1 // 期待型がないので、ここでxの型がi32に決まる。
f(x)      // i32の候補が完全一致。
f(1@i64)  // 型を明示したので、i64の候補が完全一致。
```

#### 4.2.5. 期待戻り値型を使う

本原案では、期待戻り値型を推論補助と適用可能性の条件に使用する。戻り値変換の良さを、候補順位の追加段階にはしない。

1. 受け手と呼び出し側の引数から確定した型引数を維持する。
2. まだ未確定の型引数を、既に存在する期待戻り値型から補える場合は補う。
3. 具体化した戻り値型が、下記の規則で期待型へ適合しない候補を除外する。
4. 残った候補に4.3節を適用する。

この節での「適合」は、正規化後の型同一性、またはSPEC.mdで定義済みの下位型関係によって判定する。Origin引数を具体化して制約を検査し、共変位置でのOriginの短縮など、値操作を追加しない型の適合を許す。未知の型関係を暗黙に補わず、Neverは既存の結果検査規則に従う。

期待戻り値型へ合わせるために、新たなBorrow/Reborrow、参照解除、数値変換、ユーザー定義変換などの値操作を挿入して候補を適合させてはならない。`T`を返す候補を`ref/T`へ借用して残したり、`uniq/T`を返す候補を`ref/T`へ再借用して残したりしない。確定済みの戻り値型を、関数本体にあるリテラルの値から別の型へ付け直すこともしない。

これは期待戻り値型による候補検査の規則である。引数側の適合は4.2.3節に従う。選択した関数の宣言済み戻り値型に伴う[Origin・Loanの伝播](../SPEC.md#764-calls-and-origin-propagation)や、結果のCopy/Moveは通常どおり行う。借用結果に必要なLoanまで禁止するものではない。

「戻り値だけではオーバーロードを区別しない」は、関数のSignatureが同じで戻り値だけ異なる宣言を禁止するという意味に具体化する。合法な異なるSignatureの候補間では、期待戻り値型による除外で1つに決まってよい。この解釈は6.1節にも記録する。

**例：異なる引数型を持つ合法な候補から、期待型に合うものを残す。**

```kimi
func f(value: i32) -> string => "text"
func f(value: i64) -> i64 => value

let unknown = f(1)       // エラー：期待型がなく、両候補が残る。
let text: string = f(1)  // stringを返さない候補を除外し、f(i32)を選ぶ。
f(1)                    // 戻り値を捨てても曖昧なまま。Unitを期待型にしない。
```

この例の2つの関数は引数型が違うので、宣言を共存させられる。戻り値型だけが違う重複宣言を許す規則ではない。

**例：戻り値を借用して期待型に合わせる候補は残さない。** 次は型とOriginの関係を示す疑似コードであり、sourceは有効な共有借用元とする。

```text
候補A: fetch(i32) -> i32
候補B: fetch(i64) -> ref/i32 from source
呼び出し: fetch(1)、期待型: ref/i32 from source
    → Aは除外。戻り値のi32への共有借用を挿入しない。
    → Bを選択。宣言済みのOrigin・Loan要件は維持する。
```

期待型は型注釈、確定した引数の宣言型、宣言された戻り値型などから得る。選ぼうとしている候補自身の戻り値を、外部から与えられた期待型として循環利用しない。

結果を使わない場所（Discard Context）でも、期待型Unitを与えない。戻り値を捨てるだけでUnitを返す関数へ切り替えない。

### 4.3. 呼び出せる候補同士を比較する

候補を次の順に比較する。各段階の結果は「Aがよい」「Bがよい」「同等」「比較不能」のいずれかとする。

**次の段階へ進むのは「同等」の場合だけである。** 一方がある引数でよく、もう一方が別の引数でよい場合などは「比較不能」とし、後の規則で無理に勝者を作らない。

1. 引数に必要な変換の比較。
2. 引数の宣言型の具体性。
3. ジェネリックでない関数を優先。
4. 既定値を使う引数が少ない関数を優先。
5. それでも決まらなければ曖昧性エラー。

#### 4.3.1. 引数に必要な変換を比べる

受け手と各明示引数について、候補Aへの適合と候補Bへの適合を比較する。

受け手のType Semanticsだけが異なる候補も、この比較に含め、各候補に必要な借用・再借用を4.2.3節の分類で評価する。

**ref/uniqの比較:** `ref/T`と`uniq/T`の両候補が適用可能で、通常の変換品質によって一方を選べない場合、Type Semanticsの強弱だけでは優先順位を付けない。残る違いがref/uniqだけなら、4.3.2節でも比較不能となり、呼び出しは曖昧性エラーとする。呼び出し側は、引数の借用形態または期待関数型を明示して、候補が1つになるようにする。

AをBよりよいとするには、すべての引数でAが同等以上であり、少なくとも1つの引数でAの方がよい必要がある。名前付き引数でも、ソース上の同じ引数を基準に比較する。候補ごとの引数宣言順に並べ替えて、別々の式の変換を比較してはならない。

- 全位置で同等なら次段階へ進む。
- 第1引数ではA、第2引数ではBが良い場合は比較不能とする。ジェネリックでない関数や既定値を使う引数の数でこの食い違いを解消しない。
- 既定値の式は明示引数の変換品質比較には含めない。
- 変換品質を数値化して合計しない。

**例：引数ごとに優劣が逆転する場合。**

```kimi
func choose(left: i32, right: ref/i32) -> () => ()
func choose(left: ref/i32, right: i32) -> () => ()

let a: i32 = 1
let b: i32 = 2
choose(a, b) // エラー：どちらがよいとも決まらない。
```

| 候補 | aに必要な操作 | bに必要な操作 |
| --- | --- | --- |
| 1つ目 | 完全一致 | 借用 |
| 2つ目 | 借用 | 完全一致 |

これは同等ではなく、比較不能である。例えば一方に省略可能な引数が追加されても、既定値を使う個数でこの食い違いを解消しない。

**例：共有借用と排他的な借用の両方に適合する場合。**

```kimi
func inspect(value: ref/i32) -> () => ()
func inspect(value: uniq/i32) -> () => ()

var x: i32 = 0
inspect(x)     // エラー：両候補へ借用できるが、優劣が決まらない。
inspect(x@ref) // ref/i32の候補を選ぶ。
inspect(x@uniq) // エラー：両候補への再借用が可能で、なお曖昧。

let inspectUnique: (uniq/i32) -> () = inspect // 期待関数型でuniq側を選ぶ。
inspectUnique(x@uniq)
```

最初の呼び出しは、どちらもSafe borrow/reborrowで変換品質が同等となる。`uniq/T`から`ref/T`への再借用は値操作であり、それだけで`uniq/T <: ref/T`という下位型関係を定義しない。現在の具体性規則でも優劣が付かないため曖昧性エラーとなる。`var`であることを理由にuniq側を優先しない。この結論は、両方の借用が可能な初期化済みのTの場所にも当てはまる。

`x@uniq`では、uniq側への排他的な再借用とref側への共有再借用が同じ分類になるため、型の明示だけではこの2候補を一意に選べない。最後の2行は4.4.3節の期待関数型による選択を使い、uniq側を確定してから呼び出す。明示した借用形態と一致するという理由だけで候補へ優先順位を追加せず、借用の使用可否は選択後に検査する。

#### 4.3.2. 引数の宣言型の具体性を比べる

明示引数に対応する引数の宣言型と受け手を比較する。初期仕様では、各候補の推論・代入後の型について、定義済みの下位型の関係を使う。

対応するすべての引数で、Aの宣言型がBと同じかBの下位型であり、少なくとも1カ所で同じではない下位型ならAを優先する。双方向に異なる位置で優劣がある場合、または比較できない型関係が残る場合は比較不能とする。すべて同等なら次段階へ進む。

- 数値幅が小さいことだけで、より具体的としない。
- `ref/T`と`uniq/T`に対して、共有・排他というSemanticsの強弱や再借用可能性だけから下位型関係を作らない。ここで比較不能なら、後段のジェネリック有無や既定値の個数で解消しない。
- Type Contractの条件数や論理的な強さで順位付けしない。
- ジェネリック宣言の形同士を仮の型引数で推論し合う、一般的な部分順序付けは初期仕様に導入しない。
- そのため、代入後の型が同じになる2つのジェネリック関数の候補は、宣言パターンの見かけが異なっても、この段階では同等になり得る。

**例：ジェネリック宣言の見た目からは順位を追加しない。** 次は、Box<T>が宣言済みの場合の例である。

```kimi
func inspect<T>(value: T) -> () => ()
func inspect<U>(value: Box<U>) -> () => ()

func test(value: Box<i32>) -> ()
    inspect(value) // エラー：この原案では曖昧。
```

1つ目ではTがBox<i32>、2つ目ではUがi32になる。型を当てはめた後の引数型は、どちらもBox<i32>である。両方がジェネリックで既定値の使用数も同じなので、後の規則でも決まらない。「2つ目の方が宣言の形が詳しい」という理由では選ばない。

#### 4.3.3. まだ同等なら追加規則を使う

前段まで同等なら、ジェネリック関数でない方を優先する。ここでジェネリックかどうかは、関数自身が型パラメーターを宣言しているかで判定する。関数を含む型がジェネリックであることだけでは、その関数をジェネリック関数とは扱わない。

なお同等なら、その呼び出しで既定値を使う宣言側の引数の数が少ない方を優先する。さらに同等なら曖昧性エラーとする。

候補が3つ以上の場合も、他のすべての候補よりよいものがちょうど1つ存在する場合だけ選ぶ。最後まで決まらなくても、宣言順、ファイル順、alias順、名前の辞書順で決着させない。

**例：型の比較まで同等なら、ジェネリックでない方を選ぶ。**

```kimi
func identity(value: i32) -> i32 => value
func identity<T>(value: T) -> T => value

let number: i32 = 1
identity(number) // 両方i32に完全一致するので、ジェネリックでない方。
```

**例：さらに同等なら、既定値を使う引数が少ない方を選ぶ。**

```kimi
func offset(value: i32) -> i32 => value
func offset(value: i32, by?: i32 = 1) -> i32 => value + by

offset(3) // どちらも呼べるが、既定値を使わない1つ目を選ぶ。
```

### 4.4. 型推論をどこまで行うか

#### 4.4.1. 型を確定する時点

- ローカル変数の型は宣言時に確定する。後の使用から過去の宣言へ型を伝播させない。
- private関数を含め、宣言または推論による関数の戻り値型は、その関数が別の式のオーバーロード解決に参加する前に確定し、呼び出し候補ごとに推論し直してはならない。
- 外部へ公開する関数は戻り値型を明示する。
- 非公開関数の戻り値推論が循環する場合は、循環に関係する関数へ戻り値型の明示を要求する。
- 既定値の式は呼び出し時ジェネリックの型推論の情報源にしない。
- 明示型引数の部分指定や未指定部分を表す仮記号からの推論は、初期仕様では導入しない。明示する場合は関数が要求する型引数をすべて指定する。

ジェネリックの戻り値型は、型パラメーターを含む型式として確定してよい。候補検査でその型式へ型引数を代入することは、本体を使った戻り値型の再推論ではない。

**例：戻り値の推論が循環する場合は、型を明示する。**

```kimi
func first() => second()
func second() => first()
// エラー：互いの戻り値型を必要とするため、型注釈を要求する。
```

これは実行時の再帰を禁止する規則ではない。型を明示すれば、型推論の循環はなくなる。関数が実行時に終了するかどうかは別の問題である。

#### 4.4.2. 入れ子の呼び出しで推論を広げすぎない

双方向の検査は、リテラル、無名関数、オーバーロードされた関数参照、および候補型に対して直接検査できる式に使用する。

`f(g(x))`で、外側の複数候補それぞれに対して内側のオーバーロード解決を再試行する組み合わせ探索は行わない。

1. 周囲の候補に頼らず型を決められる引数と、明示された型情報を先に処理する。
2. 候補を絞った結果、内側へ渡す期待型が全残存候補で同じなら、その型で内側を検査できる。
3. 外側候補が型を必要とする引数の検査前に1つに決まっているなら、その候補の期待型で検査できる。失敗後に除外済み候補へ戻らない。
4. 異なる期待型で内側のオーバーロード探索をやり直さなければ決まらない場合は、型注釈・明示型引数・一時変数による分割を要求する。

これは候補数に応じて意味を変える最適化ではなく、言語の推論能力の境界である。並列処理やキャッシュによってこの境界を拡張してはならない。

**例：内側の呼び出しに期待型を明示する。**

```kimi
func inner(value: i32) -> i32 => value
func inner(value: i64) -> i64 => value
func outer(value: i32) -> () => ()
func outer(value: i64) -> () => ()

outer(inner(1)) // エラー：外側候補ごとに内側を解き直す必要がある。

let intermediate: i64 = inner(1) // 期待戻り値型i64から、内側が決まる。
outer(intermediate)             // i64に完全一致する外側を選ぶ。
```

単に変数へ分けるだけでなく、必要な型情報を与える。例えば`let intermediate = inner(1)`だけでは、内側の曖昧さは残る。

#### 4.4.3. 関数値と無名関数の型を決める

- 単独の関数参照が複数オーバーロードを指す場合、期待関数型から引数の宣言型と戻り値型を検査する。
- 期待関数型がなく、関数参照が1つにも決まらなければ型注釈を要求する。
- 無名関数の明示型、引数数などで候補を絞る。なお異なる期待関数型が残り、本体を各型で解析し直さなければ決まらない場合は注釈を要求する。
- 期待される関数型が確定した後は、その型を無名関数の引数や結果へ伝えるとともに、本体から分かった型も使って検査できる。これが双方向の型検査である。
- 関数値の作成に、呼び出し時の既定値や名前付き引数を持ち込まない。
- 外側の実行時ローカルを暗黙に捕捉しない。
- 現行SPECのunsafe functionを関数値にできない規則を維持する。unsafeを理由に別オーバーロードへ切り替えない。

**例：無名関数に期待される型を明示する。**

```kimi
func apply(action: (i32) -> i32) -> i32 => action(1)
func apply(action: (i64) -> i64) -> i64 => action(1)

let unknown = apply(func (x) => x + 1)
// エラー：異なる引数型で無名関数の本体を調べ直さない。

let action: (i32) -> i32 = func (x) => x + 1
let result = apply(action) // actionの型が決まっているので、1つ目を選べる。
```

**例：関数名を値として受け取るときも、期待型を使える。**

```kimi
func identity(value: i32) -> i32 => value
func identity(value: i64) -> i64 => value

let action: (i64) -> i64 = identity // 期待される関数型に合う方を選ぶ。
```

#### 4.4.4. Type Contractとジェネリックの具体化

ジェネリックの型推論後にType Contractを検査し、不成立候補を除外する。成立、不成立、正当な依存による未確定、式のエラーを区別する。

- 未知の名前は型パラメーターへの依存として保留せずエラーとする。
- ジェネリックの定義では、宣言された制約と選択済み条件から証明できる能力を使う。
- `T is C`を証明できないことだけで`T is not C`を成立扱いにしない。肯定・否定のどちらにも証拠がなければ未確定とする。
- 型パラメーターに依存しない名前は定義位置で確定する。
- 依存するメンバーや条件の解決を特殊化まで保留する場合も、定義元のCodeContextと、既に確定した外側の探索環境を保持する。条件に依存するスコープ自身の環境は、4.4.5節に従って選択後に確定する。
- 呼び出し元のaliasやextensionを、特殊化時の候補へ追加しない。
- 完全に具体化された呼び出し・特殊化の確定時に、必要な制約を未確定のまま残さない。
- 制約の強さの比較をオーバーロード順位に使わない。任意の定理証明や、利用可能な型を列挙して証明を探す処理を導入しない。

**例：呼び出し側のaliasで、定義済みの名前を変更しない。** HelpersAとHelpersBは、それぞれ公開されたtag()を持つものとする。

```kimi
// Definition.kimi
alias HelpersA

group Work
    public func process<T>(value: T) -> i32 => tag()
```

```kimi
// Caller.kimi
alias HelpersB

let result = Work.process<i32>(1)
// process内のtagはHelpersA.tagのまま。HelpersB.tagには変わらない。
```

#### 4.4.5. 条件付きの宣言を扱う

`#if`/`#case`は[SPEC.mdの段階的評価とスコープごとの確定規則](../SPEC.md#222-staged-condition-evaluation)に従う。除外された構文は通常Bindingしない。

**あるスコープの名前探索環境を変更する条件は、その環境を使う通常の名前解決を開始する前に選択を確定しなければならない。未確定の間は、その名前解決を開始しない。** 名前探索環境には、宣言・オーバーロード候補・有効なaliasとextensionを含む。個々の名前やLookup Roleが条件の影響を受けないことを理由に、未確定の環境で通常の名前解決を先行させない。

条件自体の名前を解決するDirective Bindingは、対象スコープの条件付き宣言に依存しない、既に確定した環境で行う。条件が自身の導入する宣言に直接、または循環を通じて依存する場合はエラーとする。

| 条件が制御するもの | 選択を確定する時点 |
| --- | --- |
| 外側の名前探索環境へ導入する宣言・aliasなど | その環境を使う通常の名前解決の開始前 |
| 名前探索環境を変えない式・文・制御フロー | 特殊化まで保留可能。最終確定の期限は守る |
| 特殊化後に初めて解析する分岐内のローカル宣言 | 分岐選択後、その分岐の環境を使う通常の名前解決の開始前 |

例えば`#if windows`で宣言する`Test`は、ターゲット情報から有無を決めてから名前表へ反映する。`#case T is i32`で戻り値を選ぶ関数は特殊化まで保留できる。選択後に初めて解析する分岐内の`let result = 32`も、その分岐の名前探索環境を先に確定すれば許可する。コード例は上記SPEC.mdの節を参照する。

- 有効な宣言だけで統合・重複検査・候補集合を作る。条件選択を理由に、使用開始済みの名前探索環境へ候補を追加・削除・置換しない。
- どのスコープに宣言を導入するかは通常のスコープ規則に従う。外側へ導入する宣言を分岐内部だけの宣言と扱って期限を遅らせたり、directiveのために特別なスコープを作ったりしない。
- 宣言位置によるローカルの可視範囲は維持する。名前探索環境の確定は、すべてのローカルを宣言前から可視にすることではない。
- 環境が確定した別スコープの解析は進めてよい。未確定のスコープは、後のBindingや特殊化で確定可能なら解析開始を待つ。解析・最終確定が必要な時点までに確定できなければエラーとする。
- 条件依存のaliasや候補のキャッシュは、対象Compilation・特殊化・条件選択の状態を区別する。保留を解消するときも、別の特殊化で使用中の環境や解決済み参照を書き換えない。

### 4.5. 選んだ操作を実行してよいか調べる

候補を選んだ後、次を検査する。

- unsafe操作に必要な文脈。
- Move済み・未初期化の値の使用。
- 既存Loanとの衝突、参照の有効期間、選択した適合によって発生する実際の借用。
- getter/setter権限と、操作に必要な書き込み能力。
- その他、選択済み操作に対する制御フロー・所有権上の条件。

型を合わせるために必要な受け手の権限やOriginの型関係は、候補を検査するときに調べる。一方、値をすでにMoveしたか、現在の借用と衝突するかなど、実行の流れに沿って変わる状態が原因のエラーでは、別候補を選び直さない。

**例：unsafeの権限がなくても、別候補へ切り替えない。**

```kimi
unsafe func inspect(value: i32) -> () => ()
func inspect(value: ref/i32) -> () => ()

let number: i32 = 1
inspect(number) // i32の完全一致を選んだ後、unsafe権限がないためエラー。
```

safeな借用側へ切り替えることはしない。Move済みの場合も同様で、選んだ引数渡しが実行できなければ使用エラーとする。

**互換性の注意:** より優先されるオーバーロードの追加は、追加された候補が後のUsage Legalityで失敗する場合も、既存ソースをコンパイル不能にし得る。上の例でsafeな借用候補だけだったところへunsafeな完全一致候補を追加すると、以前は有効だった呼び出しがエラーになる。

### 4.6. extensionと演算子を扱う

#### 4.6.1. 通常メンバーを優先する

- 通常メンバーとextensionを、初めから同じオーバーロード集合に混ぜない。
- 要求されたLookup Roleに合い、アクセスできる同名通常メンバーがあれば、通常メンバーの候補集合で確定する。引数・型引数・制約が不適合でもextensionへ進まない。
- アクセスできない、またはLookup Roleに合わない通常メンバーだけなら、通常の探索停止規則と同様にextension探索を妨げない。
- extensionは、使用位置のスコープ、使用元SourceDocumentの明示alias、Compilationのデフォルトaliasによって有効になったものだけを探索する。
- extension同士は探索段階を守り、同じ段階で得た候補へ通常のオーバーロード規則を適用する。
- 演算対象や引数の型に関連する別のContainerを、自動的に追加探索する仕組みは導入しない。

使用位置とは、そのメンバーアクセス式がソース上に書かれた位置である。ジェネリック本体内の式では定義元SourceDocumentとその字句スコープを使い、特殊化を要求した呼び出し元のaliasやextensionを追加しない。依存する探索を保留する場合も、この使用位置のCodeContextを保持する。

**例：通常メンバーで名前が見つかった後は、extensionで救済しない。** extension宣言の細部は未確定なので、以下は候補を示す疑似コードである。

```text
型Documentの通常メンバー:
    save(path: string) -> ()

有効なextension:
    save(revision: i32) -> ()

document.save(1)
    → エラー。通常メンバーsaveの引数型が合わない。
    → extensionのsave(i32)へは進まない。
```

通常メンバーに、使用位置からアクセスでき、要求されたLookup Roleに合うsaveがない場合に、extensionを探索する。

#### 4.6.2. 演算子の候補を扱う

演算子の構文、優先順位、結合規則、評価順はSPEC.mdに従う。演算対象の式について型を合わせる処理と、候補同士の比較には、通常のオーバーロード規則を使う。

組み込み演算子、Type Contractが提供する演算子、extension演算子の候補収集方法と明示的な選択構文は、演算子宣言の仕様とともに別途確定する。未定義の演算子拡張を、通常の名前探索から暗黙に生成しない。

## 5. コンパイラーの処理と検証

前の章までが言語の規則であり、この章はそれを実装・検証するための方針である。高速化しても、候補や解決結果を変えない。

### 5.1. Bindingの手順とデータの持ち方

#### 5.1.1. 処理の段階を分ける

```text
ソースごとの解析と宣言断片の収集
  → 対象スコープへ寄与するSource Generator出力の収集を完了
  → 確定済みの環境で条件のDirective Bindingと選択を実施
  → 条件が確定した宣言を集め、同じContainerかを確認
  → Compilation rootと各スコープに名前表を作成
  → ソースごとにaliasの参照先を解決
  → ヘッダー・型・Signature・Type ContractのBinding
  → 統合不一致・重複宣言検査
  → 本体のName Resolution
  → Candidate Applicability
  → Best Candidate Selection
  → 選んだ操作の使用可否を検査
  → 確定した変換・借用の計画とSymbol参照を後段で使用
```

スコープごとに、通常の名前解決に入る前に宣言・alias・extensionの環境を確定する。環境を変える条件が未確定なら、その環境を使う解析を開始せず保留する。特殊化後に選ぶ分岐は、選択後にそのローカル環境を作ってから解析する。互いの結果を待ち続ける循環を検出し、全段階を無制限に繰り返さない。この図は処理の役割を示すものであり、すべてを必ず1回の走査で処理できるという意味ではない。

#### 5.1.2. 解決結果と候補ごとの状態を保持する

- スコープごとに型/値の名前表を持つ。Origin/Labelの表は独立させる。
- Lookup Contextに構文位置から決めたLookup Roleを保持し、役割に合う候補を収集してから探索停止を判定する。役割ごとの名前空間を追加する必要はない。
- 名前解決の結果は、「1つのSymbolに決定」「同名関数の候補集合に決定」「必要な情報を待って保留」「エラー」などに分けて保持する。
- 正規化された型を共有し、型の構造比較やalias経路の解決を繰り返さない。
- 解決済みの名前はSymbol参照として保持する。後段で実行用の表現へ変換する処理（Lowering）などでも、名前文字列から探し直さない。
- 候補ごとに型変数、制約、引数対応、変換計画、診断理由を分離する。
- 失敗候補での推論や無名関数の仮Bindingを他候補へ持ち越さない。
- 選択した候補だけを最終Binding結果へ反映する。続く使用可否が失敗しても、候補選択はやり直さない。
- 名前、引数個数、外部引数名、明示型引数個数などの安価な検査を、詳細な型推論より先に行う。ただし名前の探索停止段階を維持する。
- 引数型を候補に依存せず確定できる部分は共有して解析する。
- 候補同士には比較不能の場合もあるため、単純な順位表には並べられない。初期実装では、残った候補を2つずつ比較する。候補数nに対して最大O(n²)回の比較になり得るが、各比較の型判定費用は別に評価する。

**例：解決結果は、名前文字列ではなく参照先として保持する。** 次は内部処理を説明する疑似コードである。

```text
入力: f(number)

候補Aの検査結果:
    Symbol = f(i32)
    型引数 = なし
    引数の適合 = 完全一致

候補Bの検査結果:
    Symbol = f<T>(T)
    型引数 = Tをi32に置換
    引数の適合 = 完全一致

選択後に保存するもの:
    呼び出し先 = 候補AのSymbol
    引数 = numberの解決済み参照
    引数渡し = 選択された操作の計画
```

後段では「fという名前をもう一度探す」という処理を行わない。また、候補Bの型推論結果を候補Aへ混ぜない。

#### 5.1.3. キャッシュを安全に再利用する

キャッシュは、前に調べた結果を再利用するための記録である。再利用するときは、結果に影響する条件が同じかを確認する。そのため、保存するときの検索キーに必要な条件を含めるか、条件に依存しない部分だけを保存する。

| 対象 | 必要な文脈の例 |
| --- | --- |
| 名前だけでの探索 | スコープ、名前、名前空間、Lookup Role、ローカル可視範囲、SourceDocumentのalias環境 |
| アクセス権も含めた探索 | 使用側Kotonoha、宣言元Containerとの関係などのアクセス文脈 |
| 対象のメンバーの探索 | 対象Symbol/型、名前、名前空間、Lookup Role、型引数、静的メンバーかインスタンスメンバーか、有効なextension環境 |
| オーバーロード 適用可能性 | 候補Signature、引数型・リテラル値・ラベル・式の形、期待型、型引数、制約環境 |
| 条件依存処理 | Compilation target、コンパイル時条件の状態、特殊化情報 |

例えば、同じ整数リテラル種別でも値によって候補の型に収まるかどうかが変わる。CodeContextだけでアクセス権の判定結果をキャッシュすると、同じファイルの異なるContainer間で誤った権限を再利用し得る。

同じスコープ・名前・名前空間でも、Core TypeとしてのXとQualifierとしてのXは別の宣言へ解決され得る。役割で絞った候補集合や探索停止段階を、異なるLookup Roleへそのまま再利用してはならない。

借用実行の流れに沿って変わる状態を通常の候補選択キャッシュへ混ぜず、使用可否側で検査する。ソース、依存ライブラリー、alias、条件選択、Symbol表の更新では、関連キャッシュを無効化する。

**例：同じファイルでも、アクセス権の検査結果は共有できるとは限らない。**

```kimi
group Vault
    private var secret: i32 = 1
    func inside() -> i32 => Vault.secret // アクセスできる。

group Other
    func outside() -> i32 => Vault.secret // アクセスできない。
```

名前とCodeContextだけをキーにすると、insideで得た「アクセス可」をoutsideでも使ってしまう。少なくとも、アクセス元のContainerなど、判定結果に影響する条件を区別する必要がある。

#### 5.1.4. 処理量の上限とエラー

意味上の推論境界を先に定義し、実装の時間切れで「最初に見つかった候補」を採用しない。実装上の処理量制限に達した場合は、曖昧性や型不一致と区別して診断し、注釈や式の分割を案内する。

候補を無理に順位順へ並べたり、ファイル順で選んだりしない。エラーの説明のために外側の同名宣言を調べることはできるが、それを正規の呼び出し先として採用してはならない。

### 5.2. エラーの説明と検証例

#### 5.2.1. エラーの種類を分ける

- 未定義名。
- 同名宣言はあるが、要求されたLookup Roleには使用できない。
- 宣言は存在するがアクセス不能。
- 型/値修飾経路の曖昧性エラー。
- 同じ探索段階の異種値の宣言の衝突。
- 受け手が必要、または静的メンバーとインスタンスメンバーの使い分けの誤り。
- 型引数の不一致、引数対応付けの失敗。
- 適用可能なオーバーロードがない。
- 適用可能な候補間の曖昧性エラー。
- 明示型が必要な推論境界。
- 宣言・戻り値推論・条件依存の循環。
- 選択済み操作の使用可否の検査でのエラー。

曖昧性エラーでは候補のSignatureと宣言位置を示す。適用不能では候補を除外した理由を保持し、ラベル不一致・型不適合・制約不成立などを説明する。候補内部の仮解析のエラーを、そのまま全候補分出力して利用者を混乱させない。

## 6. 原案の位置付けと残る決定事項

この原案で補った規則と、まだ細部を決める必要がある事項を区別する。

### 6.1. 原案で具体化した規則と既存仕様との違い

本節はレビュー時に重点的に確認する箇所である。いずれも実装済みであることは意味しない。

1. **期待戻り値型:** 合法な候補間では、型同一性と値操作を追加しない定義済み下位型関係による除外を許す。期待型に合わせる新たなBorrow/Reborrowなどは挿入しない。戻り値だけの同じSignature宣言は禁止し、戻り値の適合品質で順位付けしない。
2. **推論の範囲:** 外側オーバーロードの各候補に対する内側オーバーロード・無名関数本体の再探索を制限する。必要な箇所では注釈を要求する。
3. **宣言型:** 外部公開関数の戻り値型を必須とする。非公開関数を含め、他の式の候補選択へ参加する前に戻り値型を確定し、推論循環には明示型を要求する。
4. **ジェネリックの具体性:** 初期版は代入後の型関係を比較し、ジェネリック宣言の形の一般的な部分順序付けは導入しない。
5. **Container統合:** 宣言元・親・宣言名・種別・型パラメーター数で断片を整理し、使用側のSemanticsは統合キーから除く。Type Contractを除きヘッダーを一致させる。structのStorageは生成ソースを含む複数断片に置け、論理宣言順序・配置・初期化を区別する。これらのStorage規則はSPEC.mdにも反映済みである。
6. **トップレベル実行スコープ:** 生成関数への集約とは独立に、ソース単位のローカルスコープを維持する。
7. **正規化引数型:** SPEC.mdのParameter Signatureを、Type Semanticsを含みOriginだけの違いを除外した比較用の型として表す。ref/uniqの宣言は共存できるが、両方へ同等に借用・再借用できる呼び出しは、現行規則では曖昧になり得る。
8. **CodeContext:** ソース由来のcontextをSourceDocumentに固定する。現行の複数SourceDocumentを同じCodeContextで解析できる経路は変更が必要になる。
9. **既存実装との境界:** 現行のContainer名だけの表やTypeKotoベースのSignatureは、そのまま意味上の型同一性・統合検査を完成させるものではない。Symbolと解決済み型の層を設ける。
10. **Lookup Roleと探索停止:** 名前空間と役割で候補段階を確定する。Type Name Selectionはその後に明示型引数の個数・種類で選択し、失敗しても外側へ戻らない。後続メンバー不在による再探索も認めず、宣言衝突規則を維持する。
11. **条件付きの名前探索環境:** SPEC.mdと共通の規則として、環境を変える条件は、その環境を使う通常の名前解決の開始前に選択を確定する。本体の処理や、特殊化後に初めて解析する分岐内のローカル宣言は、各環境の解析開始前に確定できれば保留を許す。
12. **その他の補完:** 同一ブロックのローカル再宣言禁止、ローカル関数のオーバーロード、外側型パラメーターの参照許可、全型引数を指定する初期構文は、本原案で具体化した規則である。

### 6.2. 今後決める必要がある事項

次の項目は本書で基礎方針を示すが、詳細仕様の完成・実装着手には追加決定が必要である。未定義の動作を実装依存の探索で補わない。

| 項目 | 残る決定 |
| --- | --- |
| 外部参照・re-export | バージョン別参照名の設定形式、re-export構文、参照グラフと循環の診断 |
| Containerの各種別 | enum/contractの分割宣言で許す内容、extensionの独立した同一性・公開名 |
| 統合順序 | groupの複数断片にまたがる静的Property初期化順、トップレベル実行順。structのStorage順は2.3.4節で規定 |
| Source Generator | 安定した識別子を受け渡すAPI、生成入力の取得と実行段階、生成依存の検査。出力確定の期限は2.3.5節で規定 |
| 構築・固定配置 | 明示的な構築処理や生成初期化処理の構文・アクセス規則・初期化完了検証、FFI向け固定配置の明示方式 |
| 型パラメーターの宣言 | Core Type/Semanticsの複合表記と型パラメーターの個数・明示型引数の厳密な対応 |
| 借用で型を合わせる規則 | 全Type Semantics、Originの下位型規則、一時値、受け手に対する権限を含む有限の適合表 |
| 特別な名前 | 各accessor/function形式でのself/storage/valueの導入・終了位置 |
| Type Contract | associated typeの解決・一致検査、and/or/notの証明規則、保留可能な依存の範囲 |
| operator/構築 | 組み込み・contract・extension候補の収集、型構築・indexerとの接続、曖昧時の明示構文 |
