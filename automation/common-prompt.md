# 共通契約

これは非対話の実行です。通常の実装判断は自律的に行い、会話の記憶ではなく現在のリポジトリから作業を再開してください。段階固有の指示はこの後に続きます。

## 根拠と境界

- 適用されるAGENTS.md、SPEC.md本文、IMPLEMENTATION_PLAN.md、STATUS.md、AUDIT_FINDINGS.md、git status/diffを確認する。存在しない文書を読んだと報告しない。計画と指摘の初回作成はPlanが担当する。
- SPEC本文を主な根拠とする。doc/ 以下は原則として広域検索・読込から除外するが、SPECが採用済み・優先と明記する文書は該当契約の確認に限って参照する。参照先と優先理由を記録し、その文書から別の草案へ無制限に辿らない。Design/の旧例や未採用案を規範にしない。採用済み設計の本文統合はImplementationが行い、既決事項の再承認を要求しない。未設計API・言語仕様を創作せず、未実装を隠すために規範・完了条件・必須範囲を弱めない。
- 既存の未コミット変更を保護する。将来事項と条件付き項目を勝手に必須化しない。NativeAOTのpublish・テストはユーザーの明示指定時だけ実施し、通常のLLVM/native検証と区別する。
- 別途指示がない限り、commit/push/外部公開、Automationの再帰起動、automation/・doc/・AGENTS.md（子階層も含む）・.codex/・.agents/や実行状態の変更を行わない。段階ごとの編集範囲を守る。検証の生成物・ログは既存のignore出力先かCurrent evidence prefix配下へ保存し、監査のために追跡対象のfixture・lock・設定を再生成しない。
- 外部情報・権限・ユーザーによる仕様決定が必要なら、論点・影響・必要な質問・解除条件を保存する。回答を待ち続けず、依存しない作業があれば進める。独立した有益な作業もなければblockedを返す。

## 証拠と引継ぎ

- ドキュメントの完了主張は実ソースとテストで確認する。構文・宣言だけ、未接続処理、Unsupported/Pending/Missing、入力gate、無効化テストを調べる。intrinsic、abstract/requirement、生成・登録経路をstubや未使用と即断しない。
- 差分と前回の残作業を優先し、変化のない全領域を毎回読み直さない。既存の証拠はソース・設定・入力が一致する場合に利用し、過去の検証と今回の実行を区別する。
- STATUSの先頭に「現在の自動実装引継ぎ」を一つ維持し、過去の調査時だけの編集制限を現段階へ持ち越さない。必須文書もまず現行要約・章索引・関連節を読み、長いSPECや履歴を一括出力してコンテキストを消費しない。初回の全体照合も領域単位で行う。
- 検証はコマンド、構成、終了コード、件数/失敗/skip/警告、対象ソース（HEADと未コミット差分・入力hash等）、ログの場所を記録する。0件、古いバイナリー、skip、未実行、途中停止を成功扱いにしない。
- 製品失敗、起動失敗、環境による未実行を区別する。同じ条件で同じ失敗を繰り返さず、新しい仮説・修正・環境変化がある場合に再試行する。
- STATUSの現在の引継ぎに、対象/完了ID、今回の差分、検証、残作業、次のIDと操作、阻害要因を簡潔に記録する。同じ日記を積み増さない。終了前にdiffと保存状態を確認する。
- 実行時間上限とUTC deadlineを確認する。残り5分（短い段階では上限の10%）は検証結果の整理・引継ぎ・最終JSONに充てる。収まらない検証は未実行として次回に渡し、タイムアウト直前に大規模検証や新機能を開始しない。段階を跨ぐバックグラウンド処理を残さない。

## 計画の機械可読形式

計画IDは既存の表形式 `| [ ] TASK-01 | 実装内容 | 完了条件 | 依存 | 検証方法 |` を維持する。完了は `[x]`、IDは大文字英数字とハイフンで一意にする。条件付き・任意項目だけ `OPTIONAL-` 接頭辞を使い、必須項目をこの接頭辞へ移して完成条件から除外しない。task_idsは実在IDだけを返す。runnerは必須の未完了行があるcomplete / verified_completeを拒否する。チェックが古い場合も監査で直接書き換えず、not_completeでImplementationへ同期を渡す。

## 指摘台帳: AUDIT_FINDINGS.md

指摘はAF-0001形式の一意なIDで保持する。同じ問題を重複登録せず、既存IDを再利用する。各指摘に次を記載する。

Planが初回に見出しと下記の表を作成する。指摘なしなら表のデータ行は空にする。各IDを正確に1行で登録し、列の先頭3つ（ID / Priority / State）はこの順・英語値を保持する。詳細は行の後ろの列または対応するIDの本文へ記載する。旧形式があればPlanが内容を保ったまま移行する。

~~~markdown
| ID | Priority | State | Plan / SPEC | Finding / evidence / resolution |
| --- | --- | --- | --- | --- |
~~~

データ行の形式は `| AF-0001 | required | open | TASK-01 | 根拠・対応・解消条件 |`。実在しない例示IDを台帳へコピーしない。finding_idsはopen / planned / blockedのblocking / required行を**全件**列挙する。runnerは省略・重複・解消済み指摘の混入を拒否する。

- 発見段階、対象計画IDまたはSPEC節、優先度（blocking / required / advisory）。
- 根拠となるファイル・再現条件・期待と実際の差、必要な対応、解消条件。
- 状態: open / planned / resolved / dismissed / blocked。
- 対応計画ID、採否の理由、検証証拠。根拠付きの不採用はdismissedとする。

plannedは計画へ反映済みで、実装修正の完了ではない。resolvedには解消条件を満たす証拠が必要。blockingは該当する実装範囲に着手する前に解消し、無関係な範囲を止めない。advisoryは必須の完成を妨げず、理由付きで延期できる。必須条件の指摘をadvisoryへ格下げして完成扱いにしない。

## 最終出力

指定されたJSON Schemaに従い、最終応答はJSONオブジェクトだけを返す。コード囲みや前後の文章を付けない。途中の進捗報告は通常どおり行ってよい。

- status: 各段階で定義する値。
- summary: 今回の差分・判断・未確認事項を簡潔な日本語で記載。
- next_task: 次の具体的操作、または停止の解除条件。complete / verified_completeの場合だけnull。
- task_ids: 今回扱った計画IDの配列。該当なしは空配列。
- finding_ids: 未解消のblocking/required指摘IDの配列。台帳に実在するIDを使う。解消済み・不採用・advisoryは含めない。
- evidence: 実装箇所、検証コマンドと結果、保存したログ等の具体的根拠の配列。未検証はその旨をsummaryへ記載し、成功の証拠に含めない。
- Implementationだけprogressを追加する。今回得た新しい実装・検証・原因究明の進展があればtrue。文書の整形、チェックの付替え、既知の結果の反復だけならfalse。trueには具体的evidenceが必要。
