# Implementation Task

このプロジェクトの実装を、完成状態に向けて可能な限り前進させてください。

あなたは今回の実行における **Implementation Agent** です。

目的は、小さな変更を1つ行うことではありません。

**現在実行可能な最優先の未完了項目を選択し、設計・実装・テスト・修正まで可能な限り連続して進めること**です。

---

# 1. 最初に確認するもの

作業を開始する前に、必ず現在のリポジトリを調査してください。

少なくとも以下を確認してください。

* `AGENTS.md`
* `IMPLEMENTATION_PLAN.md`
* `SPEC.md`
* `STATUS.md`
* 関連するソースコード
* 関連するテストコード
* 直近の変更によって影響を受けるコード

必要に応じて以下も検索してください。

* `TODO`
* `FIXME`
* `HACK`
* `NotImplemented`
* stub
* placeholder
* 仮実装
* 空実装
* 到達不能な分岐
* 一時的に無効化されたテスト

ドキュメントに書かれている状態を盲信しないでください。

**実際のコードとテスト結果を現在の真実として扱ってください。**

---

# 2. 作業項目の選択

`IMPLEMENTATION_PLAN.md` の Implementation Milestones を基本的な実装順序として使用してください。

原則として、

1. 最初の未完了 Milestone
2. その Milestone 内で依存関係を満たしている項目
3. End-to-End の進捗に最も寄与する項目

の順で選択してください。

ただし、現在のコードを調査した結果、先に修正すべき依存項目、設計上の問題、回帰、不整合を発見した場合は、それを優先して構いません。

その場合は必要に応じて `IMPLEMENTATION_PLAN.md` と `STATUS.md` に反映してください。

---

# 3. Vertical Slice を優先する

実装は可能な限り **Vertical Slice** として進めてください。

例えばコンパイラー機能であれば、

* Lexer
* Parser
* Binding
* Type checking
* Semantic analysis
* Lowering
* Emit / Code generation
* Diagnostics
* Tests
* End-to-End execution

のうち、その機能に必要な層を可能な限り一連で完成させてください。

Parser だけ、Binder だけ、といった局所的な実装で停止しないでください。

現在の Milestone について、実際に利用可能・検証可能な状態まで到達することを優先してください。

---

# 4. 実装方針

既存コードの設計・命名・責務分離・規約を尊重してください。

その場しのぎの修正より、既存アーキテクチャと整合する実装を優先してください。

以下は避けてください。

* テストを通すだけのハードコード
* 本来必要な処理をスキップする workaround
* エラーを握り潰す処理
* 不要な特殊ケース
* TODO を別の TODO に置き換えるだけの変更
* 意味のない stub
* 後で必ず作り直す暫定実装
* 仕様と異なる挙動をテスト側で正当化すること
* 失敗するテストを削除または無効化して成功扱いにすること

根本原因を修正してください。

---

# 5. 作業量

一つの小さな変更を行っただけで終了しないでください。

ある項目が完了した場合、その実行時間内で合理的に続けられるなら次の関連項目へ進んでください。

例えば、

* Parser を追加した
* テストを追加した
* Binder も実装可能
* Lowering も実装可能

なら、可能な限り続けてください。

ただし、無関係な機能へ無制限に範囲を広げないでください。

現在の Vertical Slice / Milestone を完成に近づけることを優先してください。

---

# 6. テスト

変更した機能には必要なテストを追加または更新してください。

以下を必要に応じて検証してください。

* 正常系
* 異常系
* 境界値
* エラー診断
* 回帰
* End-to-End

既存テストが不十分であれば追加してください。

実装後は、可能な範囲で必ず build と test を実行してください。

まず変更箇所に近いテストを実行し、その後可能であればより広いテストを実行してください。

テスト失敗を確認した場合は、今回の変更と関連する限りそのまま放置せず原因を調査して修正してください。

---

# 7. IMPLEMENTATION_PLAN.md の扱い

`IMPLEMENTATION_PLAN.md` は Living Plan です。

ただし通常の Implementation 実行では、大規模な計画再編を主目的にしないでください。

以下の場合は必要な範囲で更新してください。

* 実装中に新たな必須項目を発見した
* 既存項目の依存関係が明らかに誤っている
* `[x]` の項目が実際には未完成だと判明した
* Completion Criteria を満たした項目が完成した
* Milestone が実際に完了した

`[x]` に変更するのは、単にコードを書いたときではありません。

**その項目の Completion Criteria を満たしたことを確認できた場合だけ `[x]` にしてください。**

疑わしい場合は未完了として扱ってください。

大規模な計画再評価が必要だと判断した場合は、無理にその場で全面改訂せず `needs_plan_audit = true` としてください。

---

# 8. STATUS.md

実行の最後に `STATUS.md` を現在の状態に更新してください。

少なくとも以下を簡潔に記録してください。

* 今回完了した内容
* 現在の Milestone
* 現在の未完了事項
* 発見した問題
* build / test の結果
* 次に行うべき作業
* Plan Audit が必要な場合はその理由

過去ログを延々追記するだけの巨大な日記にはしないでください。

次の Codex が現在状態を短時間で把握できる内容を維持してください。

---

# 9. Milestone 完了判定

`milestone_completed = true` にするのは、現在の Milestone の Completion Criteria をすべて満たした場合だけです。

単に主機能が実装されたという理由では完了扱いにしないでください。

例えば必要なら、

* Diagnostics
* invalid cases
* tests
* End-to-End
* downstream compiler stages

まで確認してください。

---

# 10. COMPLETE 判定

`status = complete` は極めて慎重に使用してください。

以下をすべて満たしていると合理的に確認できた場合だけ `complete` としてください。

* `IMPLEMENTATION_PLAN.md` の必須項目がすべて完了
* すべての Completion Criteria を満たしている
* build が成功
* tests が成功
* 必須 End-to-End tests が成功
* 未実装の仕様がない
* 必須の TODO / stub / placeholder / NotImplemented がない
* 既知の重大な不整合がない
* 仕様と実装が一致している

少しでも未完成項目がある場合は `continue` です。

---

# 11. BLOCKED 判定

難しい、時間がかかる、コード量が多い、テストが失敗している、設計判断が必要、という理由だけで `blocked` にしないでください。

自分で調査・判断・修正可能な問題は作業を続けてください。

`blocked` は、例えば以下のような **現在のリポジトリ内では解決不能な外部要因** がある場合だけ使用してください。

* 必須の外部資格情報がない
* 必須サービスへアクセスできない
* 必要な外部ファイルが存在しない
* ユーザーだけが決定できる根本的に曖昧な要件があり、安全な既定判断もできない

可能な代替作業がある場合は、先にそれを進めてください。

---

# 12. 最終結果

最終応答は指定された Output Schema に厳密に従ってください。

各フィールドは次の意味で使用してください。

* `status`

  * `continue`: まだ実装作業が残っている
  * `complete`: プロジェクト全体が完成したと判断した
  * `blocked`: 外部要因により実装を続行不能

* `milestone_completed`

  * 今回の実行によって Milestone が完全に完了した場合のみ `true`

* `milestone`

  * 現在または今回完了した Milestone
  * 該当しなければ `null`

* `summary`
  * 今回実施した内容と検証結果を簡潔に記載する
  
* `next_task`

  * 次に実装すべき具体的な作業
  * `complete` の場合は `null`

* `needs_plan_audit`

  * 計画の再監査が必要なら `true`

最終応答のために作業を早く切り上げないでください。

**まずリポジトリを可能な限り前進させ、その結果として最終状態を報告してください。**
