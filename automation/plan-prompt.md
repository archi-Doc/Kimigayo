# Plan

共通契約に従い、実装完了までの計画を作成・更新してください。編集対象はIMPLEMENTATION_PLAN.md、STATUS.md、AUDIT_FINDINGS.mdだけです。

1. 初回はSPEC本文、全ソース領域、テスト、build設定を調査し、計画が存在すれば差分・未完了・監査指摘を優先して更新する。毎回作り直さない。
2. SPECの必須規則を計画ID・実装箇所・正常系/不正使用の検証へ対応付ける。CLI、LSP、拡張、backend、CI・配布も既存製品の必須範囲として確認する。実装不足・検証不足・仕様決定待ちを区別する。
3. 前回のCompletion Audit指摘を計画へ反映し、台帳をplannedにする。修正・検証前にresolvedへ変更しない。
4. 項目は一意なID、実装内容、完了条件、依存ID、検証方法を持たせ、依存順に並べる。独立して実装・検証できる単位へ分け、関数単位の細分化は避ける。
5. 既存IDを維持し、分割・統合の対応、重複・循環・未定義参照、最終完了項目からの必須依存漏れを確認する。全条件を証拠で満たす項目だけ[x]、部分実装・検証待ちは[ ]。
6. 次の2回のImplementationの優先対象を選ぶ。回帰修正、着手済みの残実装・検証、依存を満たす次のIDの順とし、対象・完了条件・最初の操作をSTATUSへ残す。実装を伴わない調査だけが延々続く計画にしない。
7. 同じ阻害要因が続く場合は、依存の修正、項目の分割、新しい切り分け、独立作業への切替を計画する。ユーザーだけが決められる仕様は質問と影響を記録する。

最終status:
- ready: 次のPlan Auditへ提出できる計画と根拠を保存した。指摘が残っていても対応・待ち条件が明確ならよい。全必須項目が完了済みなら、その主張を監査する次作業を示す。
- blocked: 必須情報不足で有用な計画を作れない、または全必須作業が外部待ちで独立作業もない。

計画の承認やプロジェクトの完成認定は行わないでください。
