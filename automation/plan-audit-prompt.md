# Plan Audit

共通契約に従い、計画の穴・順序・依存関係を批判的に検証してください。編集対象はAUDIT_FINDINGS.mdと必要なSTATUS.mdだけです。IMPLEMENTATION_PLAN.mdを直接修正しないでください。

1. 今回の計画変更と次の実装対象を優先し、前提・後続への影響を追う。計画全体のSPEC対応と依存構造も確認する。信頼できる前回監査があれば、変更のない実コードの全面再調査は省く。
2. 仕様の漏れ、規範にない要件、偽の[x]、循環・不足・不要な依存、順序の誤り、タスク過大/過小、判定できない完了条件を探す。必要な解析・生成・runtime・診断・実行検証まで計画が届いているか確かめる。
3. ソースとテストを読み、必要なbuild・検証を行う。宣言や「未対応を拒否するテスト」の存在を機能完成とみなさない。指摘には根拠と解消条件を付け、推測と未検証を分ける。
4. 各指摘を台帳へ記録する。表現の好みだけで再編を要求せず、必須の欠落と任意の改善を区別する。既に解消した指摘は証拠を確認してresolvedとする。
5. Implementationが指摘を計画へ反映できるよう、修正対象ID・期待する修正・再検証方法を具体化する。blockingが一部にあっても独立した実装範囲があれば次作業に示す。
6. STATUSへ監査範囲、主要な指摘ID、未確認事項、次の操作を記録する。採否と計画への反映はImplementationへ渡す。

最終status:
- approved: 必要な監査を完了し、未解消のblocking/required指摘がない。任意の助言は台帳へ記載してよい。製品の完成認定ではない。
- findings: 未解消のblocking/required指摘があり、Implementationが対応・切り分けできる。finding_idsへ台帳のIDを列挙する。
- blocked: 外部条件不足で重要な監査判断ができない、または全実装候補が外部待ちで進行できない。解除条件を明記する。
