## Scope and working method

The main source of excess work was grouping different invariants under two broad issue IDs, then combining implementation, exhaustive diagnostic review and repeated full verification. The shared technical risks are lost failure dependencies, implicit parser context and unclear retained-state lifetimes. Address these at their owning phase; do not add a general suppression layer or redesign the entire compiler.

1. **Reproduce before scheduling a fix.** For the next family only, check the current revision against [BINDING_REVIEW.md](BINDING_REVIEW.md) or [PARSING_REVIEW.md](PARSING_REVIEW.md). These are historical findings, not a current defect count. Record the minimal input, owning rule, expected/actual behavior, revision and existing coverage. Classify it as reproduced, already covered, not reproduced, or dependent on a separately owned foundation. A passing example alone does not establish coverage of the whole family.
2. **One root-cause family per implementation session.** Before editing, list the failing examples, valid control, independent-error control where relevant, touched phase, required checks and stop condition. Several examples sharing one cause may form one unit. Split a unit when it requires a different invariant or a second independent mechanism; do not wait for every family below before committing.
3. **Reuse a narrow mechanism.** Prefer existing prerequisite facts, canonical identities, list baselines and scratch storage. A failed semantic prerequisite must retain both invalid state and its exact cause. Share that operation only where its semantics match; avoid a new generic framework, duplicate failure tables or repeated whole-tree scans.
4. **Use incremental feedback, then formal completion.** Implement with focused tests, run the related verification once the unit is stable, review and commit that unit, associate formal evidence and push. End the session after its agreed family and final verification. Reverify after relevant changes or failures, not merely to collect another mode label.
5. **Keep new discoveries bounded.** Fix regressions introduced by the unit before completion. Record independent discoveries for a later unit instead of extending the session. Record already-fixed findings with their regression/evidence reference; do not reimplement them.

On a future authorized implementation run, update affected specification/support/navigation documents only when their contracts, support boundary or entry points change, as AGENTS requires. Keep detailed evidence in `artifacts/verify/` and a short session record in PLAN_HISTORY. Those updates are outside this document-only revision.

The labels below identify remaining work, not completed implementation units. All historical symptoms require current-revision confirmation. ### U1. Failed attributes and base declarations — next family

- **Targets:** `Binding.Diagnostics`, `Binding.Attributes`, `Binding.MemberLookup`; `LayoutAttributeBindingTest`, `BaseTypeFormationBindingTest` and the affected conformance tests.
- **Change:** reproduce one failed Layout attribute and one derived-base chain. Reuse or introduce a narrow dependent-failure operation that keeps the declaration invalid and retains the first applicable failed premise. Separate unavailable prerequisites from independent wrong-kind, openness/access and cycle checks. Start with attributes; include bases in the same unit only if they use the same failure semantics.
- **Reason:** the previous investigation found repeated formation failures without the dependency needed by later checks. `CompleteDependent` alone leaves a node unresolved; conformance/certificate gates need an invalid declaration. Presentation-time suppression cannot establish that distinction. Inspect existing `constraintDiagnosticCauses` and `partPrerequisites` before adding storage.
- **Verify:** the two minimal failures and their valid counterparts; one independent failure beside each; a primary base-cycle cause if that path changes; affected declaration/conformance state, edits and repeated Binding. Run related functional and allocation/reuse checks, with native fixtures only for affected valid execution paths.
- **Stop:** the selected chains retain the right cause, do not gain valid plans/certificates and keep independent errors. Leave constraint environments and match arms to U2/U3; no exhaustive attribute/base interaction audit.

### U2. Invalid constraint environments

- **Targets:** `Binding.Constraints`, constraint environments and diagnostic prerequisites; `ConstraintRecoveryTest` and the affected Contract-binding tests.
- **Change:** retain the cause of a failed environment through members and uses, using U1's operation where appropriate. Check every independently available clause before completing the environment; distinguish unavailable premises from refuted clauses.
- **Reason:** a failed constraint must neither turn every dependent use into a new primary error nor prevent an unrelated clause from being checked.
- **Verify:** select representatives for a missing constraint Name, a cycle and contradictory premises according to distinct code paths; include a valid environment, an independent clause failure, edit recovery and affected conformance gates. Reuse existing controls instead of constructing a full cross-product.
- **Stop:** each selected failure path has a retained cause and independent-clause coverage. Do not expand into candidate equivalence or general Contract inference.

### U3. Pending match plans and pattern recovery

- **Targets:** match/pattern Binding, match plans, scope indexing and prerequisites; `PatternBindingTest`, `PatternTypeFormationBindingTest` and affected match tests.
- **Change:** retain why a match plan is pending. Make dependent pattern bindings unavailable when the subject or prerequisite fails, while checking independent guards/bodies in their legal contexts. Reserve Unsupported for an actual unsupported form.
- **Reason:** marking an entire arm tree Unsupported can multiply one failure and withhold independent errors; suppressing the whole tree has the same loss of information.
- **Verify:** a failed subject/premise, an invalid pattern, an independent guard/body error, multiple arms, a valid match and edit recovery. Check plan validity separately from diagnostic count; include related reuse checks and native fixtures if valid match behavior changes.
- **Stop:** blocked plans preserve their cause and independent arm checks survive. Do not broaden into every ownership or exhaustiveness interaction unless the changed path reaches it.

### U4. Names lost by omitted declarations and list items

- **Targets:** `Parser.OmitDeclaration`, declaration/list readers, `CodeContext`, `Kotonoha` omission facts, Binding indexing and lookup.

## Invariants, risks and conditions for changing the plan

- **Language consistency:** never weaken a required form to match an implementation limit. Preserve separately owned Unsupported boundaries, including P36 and G78. A deliberate specification revision needs a soundness, consistency or simplicity rationale under the Kimigayo Principles and coordinated examples/tests/docs; it is not a shortcut around a failing case. New milestone implementation, NativeAOT tests and draft edits are not authorized by this plan.
- **Failure propagation:** diagnostic ordering, suppression or client capabilities cannot determine semantic acceptance. A failed prerequisite cannot establish a capability, partial Origin relation or valid certificate. Fewer messages alone is not a correctness result; independent failures must remain observable.
- **Identity and locality:** preserve exact bound Contracts and live canonical Types/Origins. Omission facts belong to their source snapshot and lexical owner. Do not restore the removed function-wide missing-Origin heuristic, which hid an independent lifetime error.
- **Allocation and retained state:** retain guaranteed zero-allocation valid warm paths; first-use failure facts may allocate but should reuse storage thereafter. Pruning and pooling must not retain obsolete source snapshots or discard live canonical entries. Never relax allocation bounds or add warm-up to obtain a pass.
- **Cross-feature regression risk:** shared layout changes previously broke defaults and anonymous bodies. Run representative adjacent tests early instead of discovering that dependency only in the closing Session. Broaden native coverage when execution/dispatch/lowering dependencies require it or a failure exposes a wider impact; record the reason.
- **Unconfirmed items:** current reproduction of each historical finding, the exact failed-versus-unresolved state needed by each consumer, ownership of retained cache entries, §8.4.6 required proof/acceptance boundaries, remaining G10 overlap and interpolation's net optimization benefit. Investigate each at its own unit entry, not as a new compiler-wide audit.
- **Deviation triggers:** already-covered behavior needs no new implementation; different root causes need separate units; unbounded equivalence proof, broken live identity or additional persistent memory without benefit requires redesign. A newly discovered independent defect is queued, while a regression introduced by the current unit is fixed before completion. An external foundation gets a named owner and explicit support boundary, not silent acceptance or deletion from the backlog.
