# Compiler Code Map

Navigation for compiler changes, not a specification or support matrix. Required behavior is in [SPEC.md](../SPEC.md) and [IMPL.md](../IMPL.md); verified coverage is in [STATUS.md](../STATUS.md). Entries are starting points, not exhaustive change or test selections. Follow callers and shared data before editing.

## Implementation map

The main path is source input → Koto syntax → Binding → control-flow/ownership analysis → physical emission model → LLVM IR → native tools. Checking stops after the front end; generation and native execution have separate entry points.

Paths below are relative to [src/Kimi](../../src/Kimi/).

| Area | Entry point / source | Responsibility and handoff |
| --- | --- | --- |
| Commands and project input | [Unit/Command](../../src/Kimi/Unit/Command/), [Project.cs](../../src/Kimi/SolutionAndProject/Project.cs): `Check`, `Generate`, `Build`, `Run` | Load configuration and sources, orchestrate phases. `Generate` publishes IR/manifest inputs; `Build` invokes native tools; `Run` executes an existing build. State boundaries to preserve: rebinding invalidates downstream semantic facts; ownership analysis requires final Binding. Emission preparation rechecks current analyses and reuses scratch storage. LlvmModuleWriter consumes the closed emission model without reading Binding, syntax or ownership state. See the linked implementations for the full contracts.

## Language feature map

Other stems can be located by filename. Tests are class/file stems under [tests/xUnitTest/Tests](../../tests/xUnitTest/Tests/).

Syntax changes also start in `Parser*` and the corresponding `Parsing/Koto` node, even when omitted below. A dash means no separate feature-specific entry is listed, not absent support or an irrelevant phase.

For library-backed features, also inspect the corresponding `.kimi` declarations/bodies in [Library](../../src/Kimi/Library/) (for example `Iterator.kimi`, `Dictionary.kimi`, `Array.kimi`, `Slice.kimi`, `Formatting.kimi`) and the matching KimiLibrary validation files. Disjoint array pairs (§4.6.10) enter through `Array.kimi` / `Storage.FixedArray`, share `Storage.tryGetPairUniq` in `Storage.kimi`, and are covered by `DisjointArrayPairTest` and `DynamicArrayCostTest`.

Dictionary optional lookup and removal enter through `Dictionary.kimi` (`tryGet`/`remove`), `Storage.findDictionaryLink` and `DictionaryStorage.removeEntry`; `DictionaryLibraryTest`, `DictionaryOperationsTest` and `DictionaryCostTest` cover source bodies, result Loans and costs. Catalog `SourceFunction` entries retain public signature validation without a compiler operation. Dictionary index/indexUniq implement UniqIndexable through source; `Binding.Elements` routes subscripts through `Binding.Indexers`, and `OwnershipAnalysis.Pointers`/`Borrows` handle published Places; `DictionaryIndexableTest` covers subscripts, direct and generic dispatch. Dictionary projections have no builtin lowering; `GenericStoragePlan.PrepareDictionaryConstructions` prepares literal equality only. Catalog caller-location metadata flows through `FunctionAbiPool`, `GenericStoragePlan` and `BodyLowering.Calls` to the private missing-key primitive. `tryInsert`/`insertOrReplace` are source bodies over `Storage.placeEntry`/`placeValue` (`BodyLowering.LowerDictionaryPlacement`, `DictionaryHelperKind.Place`/`PlaceValue`, validated in `KimiLibraryDictionaryLayout`); `DictionaryLibraryTest.InsertionCompilesFromOrdinarySource` covers them; `reserve`/`shrinkToFit` call `Storage.reserveEntries`/`shrinkEntries` (`BodyLowering.LowerDictionaryCapacity`, `CapacityOperationsCompileFromOrdinarySource`).
`OwnershipBody.Borrows.ResultArgument` follows explicitly named inputs inside compound result contracts; `DictionaryStoredReferenceTest` covers optional Tuple projections, generic forwarding, slot conflicts and warm allocation reuse.
`ElementAccess.AccessType`, `Binding.ReceiverElement` and `OwnershipAnalysis.Receiver` carry a selected projection's receiver acquisition into `BodyLowering.StructBorrows`; `PublishedPlaceProjectionTest` covers Tuple/stored fields below Indexable and direct/generic Place results.
`Dictionary.clear` enters `DictionaryStorage.clearEntries` and shares `Storage.destroyDictionaryEntries` with owning remainder cleanup. The private layout projection is validated in `KimiLibraryDictionaryLayout` and lowered in `BodyLowering.DictionaryStorage`; `BodyLowering.GetDictionaryEntryLayout` shares allocation-free physical offsets/stride across storage primitives and mutation helpers; `DictionaryLibraryTest` checks that borrowed lookup registers no destruction helper. `DictionaryStorageValidationTest` and `Utf8ReserveEffectTest` cover its contract and destruction effects.

For cross-cutting changes: project/dependency input starts with `DependencyResolutionTest` and `DependencyLockTest`; check/diagnostic publication with `CheckServiceTest`, `DiagnosticOwnerTest`, `DiagnosticContractTest` and `DiagnosticRelationTest`; LSP with `LspProtocolTest` and `LspProjectDiagnosticTest`; edit invalidation with `SyntaxEditInvalidationTest`.

Ownership table dimensions enter through `OwnershipStorage`; `PackedAnalysisTable` stores Loan modes and liveness for `OwnershipBody.Borrows`. `BorrowDependencyStorageTest`, `OwnershipStorageLimitTest` and `Benchmark --borrow-storage` cover reuse, retained space, Resource diagnostics and fixed-workload measurements.

## Use and maintenance

1. Read the owning specification and the relevant row, then trace callers and shared plans. Locate filenames with `rg --files src/Kimi/Compiler -g '*Comparison*.cs'`; find consumers with `rg -n 'BoundComparison' src/Kimi tests/xUnitTest`.
2. Select related tests from their source, including allocation/reuse tests for hot paths. Follow [VERIFICATION.md](VERIFICATION.md) and [milestone programs](../../tests/milestones/README.md) for completion evidence; the table is not a complete verification command.
3. Update affected entries in the same commit as changes to feature placement, phase responsibilities, entry points or listed source/test names. Add a row only for a distinct navigation need; retain representative entry points rather than cataloging every helper.
4. Verify changed links, file stems/globs and method names against the checkout. Keep requirements in SPEC/IMPL, support boundaries in STATUS and detailed diagnostic rules in DIAGNOSTICS; link to them instead of copying their content.
