# Kimigayo Diagnostics

Developer notes for the compiler's diagnostics. SPEC [§23.2.2](../spec/23-compiler-services.md#2322-results-and-acceptance), [§23.1](../spec/23-compiler-services.md#231-diagnostics) and [§23.4](../spec/23-compiler-services.md#234-language-server) define the observable behavior; this document records the internal model that realizes it, the rules that keep it consistent, current recovery and recorder rules, and a link to the explicitly requested [Diagnostic Development Workflow](DIAGNOSTIC_WORKFLOW.md). It never overrides the specification.

## 1. Principles

| ID | Principle |
| --- | --- |
| I1 Definition | The meaning and definition of a diagnostic are decided in one place. |
| I2 Determinism | Published content and order never depend on arrival, threads or wording. |
| I3 Explanation | Suppressing a cascade never removes the record that explains the problem. |
| I4 Acceptance | Acceptance never depends on display, suppression or supplements. |
| I5 Locality | Adding an unrelated problem never reduces the explanation of another. |
| I6 Boundary | Published content is finalized once and never changed afterwards. |

## 2. Common rules

Arithmetic selection and declaration failures follow [SPEC arithmetic Contracts §6](../spec/13-operators-and-assignment.md). Retain selected facts and candidate evidence; a missing user conformance is not a blanket nonnumeric-operand error. Origin, Loan, effects and setter failures keep their existing cause-specific paths.

Operator checks retain the actual operand Type, written operator and failure location, with a requirement/proof only when Binding queried it. Applicability licenses the directional expectation before fitting; a failed fit supplies no operand fact. Unknown is a Proof diagnostic, Refuted the relevant Language diagnostic; a tuple comparison names its decisive queried leaf, never a fabricated whole-tuple query. A known independent prohibition survives a missing counterpart, including string joins in either association and `p * missing`; a missing Type needed by provider selection defers that judgment. `Binding.Diagnostics.Operators` formats the retained facts without re-proving them; its Note displays the same real condition as unproven or unsatisfied in CLI/LSP text, bounding each displayed Type before composing the Note (DECISIONS G51-2).

Each rule replaces a family of special cases. A change that needs an exception to one of them first revisits the rule.

1. **One requirement, one phase.** A requirement is judged by the phase of its owning partition. A later phase that depends on it names it as a prerequisite and never reports it again.
2. **No free text.** A code's message, label and Reason come from its typed facts. A difference within one requirement is a Reason value; a different requirement or category is a different code; wording alone never adds a code.
3. **Unsupported is one location.** A form the SPEC permits but the implementation does not support is one `Unsupported_Kd` record with its location only (SPEC §23.1.1): the first phase that cannot handle it reports it, and no table explains the missing feature. An effect-bound check that meets an effect its summary cannot classify yet (`EffectViolation.Limit`) is this record at the conformance, Callable use or virtual declaration, never a bound violation.
4. **One node state, many facts.** A syntax node keeps one analysis state, which its first failure sets. Diagnostic facts are kept per problem key and recorded at the final decision; a second failure adds a fact without changing the state.
5. **Context only when it matters.** A context (instantiation, expansion) is part of a key only when the requirement's outcome or Args depend on it; a check without a context has no instantiation-specific Args.
6. **Total order by structure.** Every key component has a total order: source table order and span for positions, a fixed order for enumerations, and a structural order for Types (declaration source and span, then Type arguments recursively; built-in Types in a fixed order). Display names are never compared.
7. **Records are independent of display.** A record is finalized without knowing its output. Limits are the only settings: constants in one place, which tests exceed with long inputs rather than replace.
8. **One fallback rule.** A phase that ends incomplete, with no Error in its partition or an earlier one, reports one fallback at its first incomplete subject (SPEC §23.2.2). The contract check for unexplained rejections is the last safety net. Tests treat any fallback as a defect.
9. **One fault record.** A Faulted result is explained by exactly one `CheckFaulted_Kd` whose Reason carries the fault kind. `InternalInvariant_Kd` is reserved for internal failures in a Completed result.
10. **Decisions look backwards.** A decision queries only the partitions that precede it: emission and acceptance read every front-end partition.
11. **No Advice.** Records carry no Advice: a fix is offered only as a repair candidate whose effect follows from the check's facts (SPEC §23.1.3); a fix that needs a choice is not offered.

Constructor inference follows SPEC §10.8 and §23.1. Keep Type lookup, missing slot evidence, structural/Semantics conflicts, declaration-shape failures, call-correlation failures and fixed-binding selection changes as distinct facts. Save original input evidence and candidate identities before inference/fitting; formatting never reruns selection. An explicit-argument fix is offered only as a repair candidate whose snapshot, complete bindings and selection conditions the common repair model establishes; otherwise it is not offered. Do not promise that spelling the provisional binding resolves ambiguity or that an anonymous concrete Type can be written.

## 3. Definitions

| Source | Holds |
| --- | --- |
| `src/Kimi/Diagnostics/DiagnosticCode.tinyhand` and `DiagnosticEntry` | Severity, category, and default Message, Label and Note |
| Phase-specific reporting conversions (C#), checked against the catalog schemas | Argument and evidence values, roles of related locations, conditional explanations |
| `DiagnosticRequirement` (a C# value of the owning partition and that partition's kind enumeration) | The requirement's stable name (public vocabulary, like code names), its owning partition and its semantic order |
| `DiagnosticRequirement.tinyhand` | A short description per stable name; for a syntax form also the `Phrase` its diagnostics display |
| `SyntaxForm` (`src/Kimi/Compiler/Parsing/SyntaxForm.cs`) | The forms the parser expects or finds misplaced: the requirement Kind of the Syntax partition, named `Syntax.<Form>` (§4.4) |
| `OwnershipRequirement` (`src/Kimi/Diagnostics/DiagnosticRequirement.cs`) | The requirement Kind of the Ownership partition, named `Ownership.<Kind>`, which the ownership analysis records as its failure kind |

- Enumerations are written by hand; a consistency test keeps enumeration, catalog and description table equal. No enumeration is generated.
- The catalog is validated when it loads: unknown, duplicate and missing entries, invalid severities/categories, malformed or duplicate fact names and a template whose placeholders differ from its schema's arity are catalog anomalies. Message templates are parsed once, at load. Record-time checks reject nonnumeric Number values, undefined Enumeration values, non-Boolean Boolean values and a Requirement value without a phrase. The reporting APIs currently accept objects; this validation is not a claim that every recorder has a separate statically typed generator.
- A fact of kind `Requirement` is a requirement by its stable name (exact in the Reason); the message and label display its phrase. `PrerequisiteUnavailable_Kd` names the undecided requirement this way, and the syntax codes of §4.4 name their form.
- `PrerequisiteUnavailable_Kd` (Error, `Proof`): "This requirement cannot be decided because its prerequisite could not be established." Its Reason is `requirement` (a stable name) and `condition` (the condition and the fact it needs).
- Callers obey the definition: a serialized source in an incompatible format is an `Input` problem with its own code, never a syntax form with prose.

## 4. Model

### 4.1. Facts and keys

Generation retains a refused generic instance's pooled ownership issues and concrete call until publication or the next preparation. `ReportInstanceDiagnostics` uses the ordinary ownership fact reporter in the Emission partition, preserving codes, categories, primary and related locations, and adding instantiation context. A refusal without an issue is Internal; classification never comes from its message. Preparation replaces previous Emission diagnostics, and instance refusal does not invalidate the universally checked definition. `GenericGenerationDiagnosticTest` exercises publication and recovery. Under MIR code generation (R5's sel) the instance collector reports an instance's limits, capability gaps and layouts over 2^63 - 1 bytes (`OversizedLayout_Kd`, Language, at each by-value use; DECISIONS R5-M52) at check instead, in the ControlFlow partition at the subject its location rule gives (DECISIONS R5-M40, R5-M41); G2 makes that every pipeline's.

A logical model; it requires no allocation per field.

```text
DiagnosticFact
  Code        : DiagnosticCode
  Subject     : a syntax node, token, input or compiler process of this analysis
  Check       : requirement and condition number (independent of the code)
  Context     : instantiation or expansion context, or none (rule 5)
  Primary     : primary location
  Args        : the code's typed facts
  Evidence    : supplementary evidence with roles
  DerivedFrom : check keys of the unmet prerequisites (an unresolved mark when unknown)
```

- The **check key** is `(Subject, Check, Context)`; the **problem key** is `(check key, Code)`. Identity never uses display ranges or strings.
- A requirement is distinct across phases: establishing a declaration's Type and a call's argument count are different requirements. The condition number distinguishes arguments, Contract conditions or Places within one requirement.
- A Subject distinguishes source snapshots and analysis generations. A syntax error names a token or boundary; an input failure names the input. A synthesized node is identified by its original subject, its transformation role and its order within the transformation.
- A problem with several subjects is normalized before it is recorded (SPEC §23.1.2).
- A problem that a later phase reports with a code without facts, such as MIR code generation's `InternalInvariant_Kd` (a broken contract at its site; the instance collector's only after a complete Binding, DECISIONS R5-M151) and gate step 2's refusals (an A1 or A2 code of no argument, or until H3 the location-only `Unsupported_Kd` of an arena skip, rule 3; DECISIONS R5-M96, R5-M146), has its location as its subject (`DiagnosticCollection.ReportLocation`): the reports of two nodes at one location, such as the siblings a transformation synthesizes with its span, are one problem (DECISIONS R5-M65).
- Values that can change after recording (a rebound call, reused scratch storage) are captured as values; immutable analysis data may be referenced. Prerequisite, evidence and related-location arrays are copied at the recording boundary, including the first report of a problem.
- Analysis-specific failure enumerations remain; each converts to diagnostics in one place (Binding's `Check` switch, `OwnershipIssue.Code`, the control-flow conversion).

### 4.2. Owner, partitions and error state

- One **diagnostic owner** per check request is created before input preparation and passed to the compilation and later phases. It replaces named collections, `IsGlobal`, the mutable current `SourceDocument` and positional removal.
- Facts are recorded in **partitions** that follow the existing invalidation boundaries:

| Partition | Invalidated when |
| --- | --- |
| Input and configuration | Kept for the whole check request |
| Syntax (one per module) | That module's syntax tree is rebuilt; it also holds the recovery map |
| Semantics (Binding, startup, control flow and ownership) | Any syntax changes (all of it), or one phase is analyzed again (that phase and later ones) |
| Later phases | One per result unit |

- Invalidation replaces a partition's fact list as a whole and never scans facts; `BeginSourceParsing` must stay cheap. Production analyzes each compilation once; repeated analysis happens in tests and benchmarks.
- Recording an Error sets the error flag of its partition and module before aggregation or suppression; a valid partition never clears it.
- Acceptance and emission query the owner under rule 10. A decision inside one call (token caching, `Documentation.Finish`) uses that call's local result. `errorCount`, `ErrorVersion` differences and `HasSourceErrors` are removed.
- A tentative retry inside an analysis stays inside it; only the adopted decision becomes a fact.

### 4.3. Recording, aggregation and prerequisites

- Facts aggregate by problem key when recorded. For one key, Primary and Args must be equal (a contract violation otherwise); causes and captured evidence are unions, and evidence keeps the first N by the order of SPEC §23.1.
- Invariant: `Code == PrerequisiteUnavailable_Kd` exactly when `DerivedFrom` is not empty. An unknown cause records the unresolved mark.
- Only Errors are derived. A warning check whose prerequisite failed records nothing.
- The recorder of a derived failure names the unmet prerequisites by check key; the prerequisite's code may be unknown and recording order does not matter. A prerequisite key names the referenced check and accounts for every Error it reported; another requirement gets another key. An empty prerequisite array is equivalent to no prerequisites and preserves a direct diagnostic's facts.
- Nested parts skipped because a check failed are explained by the failure and get no facts. When an explicitly referenced prerequisite was itself skipped, the derived fact inherits the skip's cause.
- **Consultation (Binding).** Each checked node is bound in a frame: expressions (`BindNode`), Type expressions (`BindType`), variables (`BindVariable`) and a call's member callee. A frame records the operands the node read that did not resolve, and every node failed while it is open. A use of a parameter or property whose Type failed consults the written Type. An expression bound against an expected Type whose written syntax failed (an initializer, an assigned value, a returned value) names that syntax where it needs the expectation, and a call with no applicable candidate rests on a candidate whose signature failed. An operand that resolves later is not a prerequisite, and a node whose lookup succeeded but was never completed contributes nothing. A failure that reports missing information (`MissingName`, `MissingType`, `Unsupported`) with an unresolved prerequisite is derived, and so is a constraint proof (`InvalidConstraint`) that a declaration-level check found failing because a part it recorded with `AddPrerequisite` failed, such as a Property whose declaration context is invalid; every other failure is direct. A call whose candidate or selected target lies in a failed declaration (`InvalidDeclarationContextCause`) rests on that declaration instead of failing itself. A failure of any kind is derived when the check consulted a recovery node, directly or through unresolved operands (`RestsOnRecovery`): the parser's guess explains what the check combined. A declaration-level check that reads a part outside a frame records it with `AddPrerequisite` (a function's recovery Constraint, a nominal header's `length` slot, an associated Type's Origin parameter, a Property whose declaration context is invalid); these part prerequisites survive consultation-frame replacement and are cleared with the other pass facts on rebind.
- **Several problems of one node.** A check that fails independently at several of its parts reports one fact per part with the node as subject and the condition number as the part's ordinal. A parameter acquisition shape violation (SPEC §7.4, `ParameterShapeMismatch_Kd`) reports each conflicting parameter of the later declaration in source order at the parameter Type, with conditions `0..n-1` and the overlapping earlier parameters as related locations; a group gathered at a use reports one record at the called Name, whose condition 0 is the check that dependents of the failed call name as their prerequisite (`PrerequisiteKeys` uses condition 0).
- **Declaration parts (Binding; G52-2).** A rejected selected Attribute records its own failure and invalidates its target through the existing part prerequisite, preserving any independent target Failure. Presence and cause traversal read consultation frames and declaration parts with the same live definition: not Resolved, or syntax recovery. The first non-recovery part is retained; recovery may replace it. A rejected attribute, and any earlier struct part retained before Layout validation, cannot resolve in that pass; this guarantee is not extended to arbitrary pending base/field inputs. Rebind clears and reconstructs both stores. Only Invalid with a live declaration part resists a pending transition. Within the existing declaration-context walk, that part precedes the independent Failure's signature-preservation rule. A stored InvalidConstraint or Unsupported can remain a derived requirement key whose record closes to the actual cause; a definite independent failure remains direct. Base availability includes prior rejection, but prior rejection is not evidence that a base rule failed.

- **Recovery.** When parsing fails, recovery links what it keeps to the key of the lexical or syntax check that caused it: every `ErrorKoto` carries the key of the Error reported just before it (`TokenReader.NewErrorKoto` and each direct construction), and synthesized syntax kept in place of a rejected form, such as the combined node of a chained comparison, a body supplied for a missing one (§4.4) or the armless match of a missing arm list, is recorded in its `CodeContext` (a map that exists only after a recovery). The lexer and the parser of one document record through one target, so a token the lexer rejected is not reported again: the parser recalls the lexical Error at that token's span (`DiagnosticCollection.RecallError`) and rests its recovery on it. A function body missing because of a syntax Error is marked (`FunctionKoto.MissingBody`) and gets no ownership body. Binding checks the operands of a recovered form on their own, not its guessed combination, and names the key as the prerequisite of every check that depends on the recovered node. A compile-time condition that is an `ErrorKoto` is outside the grammar without a report of its own. The parser records a skipped declaration in `Kotonoha.OmittedDeclarations`, so a check over the member set can rest on it. A syntax transplant imports only its referenced recovery causes and their prerequisite closure into the destination diagnostic owner/module, reindexing all locations; both recovery representations survive root provenance replacement (DECISIONS AST2).
- **Later phases.** A startup or control-flow check, or a HIR lint, that reads Binding's result at a node that Binding failed, or left resting on a failure, is derived from those Binding causes (`Binding.FailureCauses`). This covers a later phase repeating Binding's own check of one requirement. The HIR lints (`Binding.Lints`: the discards of SPEC §17.5, `while true`, an interpolated string passed to `Utf8Writer.write`, an operation that needs an Unsafe Block outside one, an unused Unsafe Block, a transfer without a valid target, a label overlapping an enclosing one and a Block body whose structural end its declared result cannot take, `FunctionFallthrough_Kd`, judged by result validation) are non-failing Binding records, judged by one walk at the end of each final pass: requirement `Binding` with `BindingFailure.None` and the lint's row as condition, so they never fail a node and share no check key with Binding's own warnings (condition 0). The old ownership analysis counts a lint Error as a rejection of its own (`Binding.LintErrors`) until R6-check. Checks judged from syntax alone (jump targets, labels, fallthrough, Unsafe Blocks, `while true`) stay direct, so independent problems at one node survive. A warning whose check rests on a Binding failure records nothing; an Unsafe Block containing an operation whose need for the permission is unknown is therefore not reported as unused. The startup check that finds no body rests on the omitted declarations when the parser skipped one. A control-flow check or a HIR lint rests on a recovery's syntax Error only where the recovery guessed what the check reads (the lint table's guess column, `ControlFlowAnalysis.GuessedBy`, `Binding.GuessedCompletion`): the target syntax of a jump whose label was guessed or of a label, and the normal completion that a fallthrough (`FunctionFallthrough_Kd`, `RequireFallthrough_Kd`) or a discarded tail (`DiscardedTail_Kd`) reads. A jump target written in source is judged independently of a recovered operand (`ContextualLabelTest`). A completion check rests on the bodies the parser supplied for missing ones (§4.4) when the checked syntax, or for a tail any syntax its descent passed, completes normally only through them, since a written body might have returned or exited: the Error is derived from their keys and the warning records nothing. Binding's guess rule (`Binding.GuessedCompletion`, which the control-flow require fallthrough check calls) also counts an expression Binding left unresolved as such a guess, resting on its Binding causes. A completion that written syntax also reaches stays direct, such as a written branch that falls through, an if without else (`syntax.json`: `guessed-*`, `written-*`), or a require failure body written in source, after a missing `else` or as a recovered form such as a chained comparison (`RequireRecoveryDiagnosticTest`). The check assumes the guesses do not complete in a second structural completion, created only after a recovery or in an incomplete pass, so valid input never builds it. Ownership analysis skips the body of a function that is a recovery. The result that a function's Block body leaves undelivered at its normal end is the fallthrough seen from the result Place (rule 1): ownership's `UninitializedPlace_Kd` at that delivery rests on Binding's check of the body when Binding recorded `FunctionFallthrough_Kd` there (`Binding.FallthroughKey`), and stays direct otherwise, so an unresolved prerequisite never replaces it. Other ownership problems of the function stay direct (`DiagnosticPrecisionTest`, `syntax.json`: `written-fallthrough`, mutation `missing-return`), except a Loan conflict SPEC §15.6.5 makes caused only by Refuted Origin relations, which A5 records with `Cause` facts naming those relation problems and publication derives from them (`PrerequisiteUnavailable_Kd` with their check keys; DECISIONS R4-M132).
- **Defaults.** The declaration prepass checks each default before caller bodies, so omitted and supplied calls share its failures. `DefaultArgumentAccess_Kd` identifies forbidden exclusive access or mutation; `DefaultArgumentBorrow_Kd` identifies a new Borrow/Reborrow retained by the result, following acquired values through locals, aggregates and call contracts. Both relate the preceding prepared parameter, without speculative repair candidates; a failure limited to some Semantics cases names them in its Reason, Note and related binder declarations. An escaping Reborrow is explained once by the result diagnostic, while a separate mutation keeps its own access diagnostic (`DefaultAccessTest`, CLI/LSP). Reading a stored shared reference copies its existing external dependency rather than borrowing its slot. On the MIR (DECISIONS R4-M98) A5 reports both in each default template view: `DefaultArgumentBorrow_Kd` at a new Borrow of a preceding slot that the result or storage the body does not own keeps, `DefaultArgumentAccess_Kd` at a write to the slot or an exclusive Borrow of it that neither keeps; a Borrow past a shared Deref (`x@follow@ref`) or a Place past a raw pointer read from a slot is neither, and the related parameter is an `Anchor` fact at its Type node; a failure in a default's copy that an event outside that evaluation takes part in (the caller's Loan or reservation, another default's, an earlier evaluation's) is the call's, at the outermost omitting call (DECISIONS R4-M97). A default's own ownership problem is recorded once, by its declaration check (SPEC §7.2.3): a definite Move of a prepared argument (`DefaultArgumentMove_Kd`, at the operand or the capture entry) and a non-Copy preceding parameter that a default closure's omitted capture list reads (`TransferRequired_Kd` at the closure). Its evaluation at each call adds no record, reports no unsupported execution and moves no prepared argument, so the call reports no moved Place (`DefaultOwnershipTest`, `FunctionDefaultTest`). A default whose execution is outside the subset is one `Unsupported_Kd` at the default, and the calls that omit it add no other record. Control flow completes a default without the bodies of the closures it creates, so a call in such a body that omits the same default, as a recursive call does, is not an unresolved cycle (`PrerequisiteUnavailable_Kd`). A default closure that needs a non-Copy preceding argument, through its omitted list or a bare entry, offers no transfer or borrow, since neither is valid in a default; its Note says why, and giving the Function Type a parameter instead is not offered. The same Note explains an exclusive entry (`[k@uniq]`), an Owned failure of the erased environment (`[text@ref]`, a Reborrow of an exclusive parameter, or a Copy of a non-static borrow) and contextual `self` in a default, so no record in a default proposes `@move`, `@ref`, a Reborrow or keeping the concrete closure.
- **Declaration shape errors.** An accessor whose written receiver is not the shape of its operation (`AccessorReceiverShape_Kd`, SPEC §11.3) is one problem of the accessor declaration, located at the receiver Type with the Property header related. Its body is checked with the written receiver and adds no facts of its own. A Property use whose receiver is rejected under the written receiver but accepted under the operation's fixed shape rests on the declaration (`ReceiverRestsOnAccessorShape`); every other rejection of the use stays direct.
- **Suppression.** At finalization, valid facts are indexed by check key and each prerequisite is bound to every Error its check reported. A prerequisite without an Error, with warnings only, outside the result or in an invalid partition is unresolved. A derived fact is suppressed only when every cause reaches a published direct Error without an unresolved link or a cycle; otherwise it is published and suppresses nothing. Causes are resolved in one non-recursive pass that shares the verdict per prerequisite key; suppressed facts are released without being published.

### 4.4. Syntax forms

The parser reports what it expected, not what it saw. A **syntax form** (`SyntaxForm`) is a grammar position the parser can expect, such as an expression, a Type, a body, the end of the line or a closing delimiter, or a construct it can find where it is not permitted, such as an indented body that no header introduces. Each form is a requirement of the Syntax partition, `Syntax.<Form>`; the requirement table gives it only a phrase (no article, lower case unless it is a quoted token or a capitalized term). Three codes explain every form:

| Code | Facts | Location |
| --- | --- | --- |
| `ExpectedSyntax_Kd` | `expected:Requirement`, `found:Text` (the token's source text) | The token found where the form was expected |
| `MissingSyntax_Kd` | `expected:Requirement` | An insertion point, length zero, right after the last written token before the line, block or source ended |
| `MisplacedSyntax_Kd` | `form:Requirement` | The misplaced syntax |

Rules, realized once in `TokenReader.Diagnostics.cs` (`Expect`, `ExpectLineEnd`, `Missing`, `Unexpected`, and `Expect(TokenKind)` with `FormOf`, the one map from a required token to its form) and `DiagnosticCollection.ReportSyntax`:

- A reporting site names a form and nothing else; the code and the location follow from the form and the current token. A site never passes text, and a difference in wording is never a new form. The reader's skip and consume helpers (`TryConsume`, `TryRead`, `SkipUntil`, `SkipListItem`, `SkipCurrentBlock`) report nothing of their own: `TryConsume` with a diagnostic expects the token's form through `FormOf`, `ExpectCloser` and `TryReadName` expect the closer or the Name, and the others leave the report to the caller that knows what it expected.
- A line boundary (`Separator`, `StartBlock`, `EndBlock`), a synthesized token or the end of the source means the form is missing, inserted after the last written token; a token spans its text as written, so the insertion point after a string literal follows its closing quote. Any other token is where the form was expected.
- A node ends at its last written token as well (`TokenReader.PreviousSyntaxEnd`), never at the line boundary that closes it. The tokenizer places an `EndBlock` at the first character of the next dedented line, so a block, a match arm list, a property accessor block and a `#switch` Case Group read their end before consuming it; the nodes that end with them (a function, a closure, an if, a require, a declaration) follow. The blank and comment lines after a body and the next line's indentation belong to no node, so no record, key or excerpt spans them, and adding them changes positions only (§9.3).
- The first form missing at an insertion point is the problem; a later non-closer form the parser expects there is its consequence and recalls that Error (`TokenReader.Missing`, `lastMissing`), while closers stay distinct problems. A closer the tokenizer synthesized counts as the first missing form at its insertion point once the reader passes it (`NoteMissingCloser`), and a closer the parser expects at a token mid-line recalls the tokenizer's report at the end of that line instead of reporting the token (`LineEndInsertionPoint`).
- A token left on a statement header's line before the indented body that follows is where the header's line should end, as after a function header (`ExpectLineEnd`): the header expects the line end there and the body, or a match's arm list, is still its own (`TokenReader.IndentedBodyFollows`, `SkipHeaderLine`). Without such a body the token is where the body was expected, the empty body stands for it, and the rest of the line goes with it, so an aligned `else` on the next line still continues the header. Inside a grouping, which ends on its line with its closer, nothing past that closer is skipped. A match's arm list is not an executable body (SPEC §14.2), so it has its own form (`MatchArms`). A body-bearing expression in a header (`HeaderBodyExpression`, including a compile-time Condition) is reported at its keyword; when an indented body follows the line, that body is the statement's, so the expression is not read and the rest of the line rests on the Error (`Parser.ParsePrefixExpression`); otherwise the expression is read with its bodies on the line.
- `&&` and `||` are recognized but are no operators (SPEC §2.4, §13.8). An expectation at either token reports the token itself as misplaced (`AmpersandAmpersand`, `BarBar`), whose repair candidate replaces it with `and` or `or` (§4.5, with a space on each side that touches a non-space character); the form the parser expected there rests on that Error.
- An `else` that no if body precedes is `ElseWithoutIf`; its own body is read as part of the recovery.
- Recovery inside a grouping stays inside it. The tokenizer closes every grouping before what follows it, with a supplied closer where none is written, so every opener has its closer. A written outer closer supplies the intermediate missing closers before ending its grouping. With no matching opener, a wrong-kind closer reports the required innermost closer and relates its opening; without any open grouping it reports `UnmatchedCloser`. Either unmatched token retains its kind and `Token.ClosesNothing`: it ends an expression as any closer does but list recovery skips it. A grouping kept open after a wrong-kind closer derives its later synthesized-closer failure from that token. A `;` inside a grouping, where no statement ends (SPEC 2.4), is an invalid token. A list item followed by text that is no comma or closer is where the comma or closer was expected; the rest of the item is skipped to its next comma or the grouping's closer (`TokenReader.SkipListItem`, `ExpectCloser`), nested groupings and bodies whole, and the item before the skipped text, such as a call's last argument, an array element, a grouped operand or an index, is kept as a recovery (`Parser.RecoverItem`): every check that reads it, such as the call's overload selection or a fixed array's length, rests on the Error, while the other items keep the list's context. A Pattern keeps its items, so an arm's bindings survive. A Name expected in a list is read by `TokenReader.TryReadName`, which leaves any other token for the list to end at, and a list loop that reads nothing ends, so recovery always makes progress.
- An attribute where the grammar takes none (SPEC §6.7) is `Attribute` misplaced, reported once over the whole attribute wherever the parser meets it (`TokenReader.ReportMisplacedAttributes`: `TryConsume`, `ExpectLineEnd`, the Name and Type positions of a binding or Property, a function's Name and result Type, the expression parser), and the token the grammar expected may follow it, so `var x #Attr : i32 = 1` keeps its Type and initializer. SPEC §6.7 sets no adjacency rule for an attribute's argument list, so where the grammar expects `(` (a function or function expression header before its parameter list, `TryConsume` of `(`), an attribute takes a list only when another `(` follows that list: the last list is the header's (`Parser.ParseAttributeKoto`, `beforeList`). `func f #Test () => ()`, `func f #Test (x: i32)` and `init #Test (v: i32)` therefore report only the attribute, `#Attr(1) (x: i32)` keeps `(1)`, and `func f #Attr(1) => ()` gives `(1)` to the header, whose parameter problem is a second, independent one. A kept attribute that lands on a function expression's parameter is not that parameter's attribute (`HasWrittenAttribute`). The attribute stays on the next node so the source round-trips through the tree, and it is that Error's recovery: Binding lets it mark nothing (`Binding.IndexVisitor`, `TestSyntaxVisitor`), so the node it landed on is checked on its own. Attributes, modifiers or a compile-time prefix at the end of a body or of the source introduce no declaration and report `Declaration` missing after them (`Parser.ConsumeAttributeAndModifier`), in a Container body as in a function body. Modifiers share the line of the word that introduces their declaration and follow its attributes (Appendix F.6): modifiers that end their line, or that precede a directive, introduce nothing and report `Declaration` missing or expected there, and an indented body after such a line is skipped with it as after a failed header; an attribute after a modifier is misplaced. Each `static` and an `open` before anything but `struct`, or not directly before it, is reported where it is read and kept for recovery; a declaration's own checks judge the other modifiers only (`Parser.Judged`), a `static` alone needs no declaration after it, and a repeated modifier is named as written. Pending attributes before an item that takes none (a Constraint, an Origin relation, an effect, an `associate` declaration, an enum Case) are reported as misplaced and kept as recoveries (`Parser.ReportPendingAttributes`), as are attributes in an accessor list; attributes before a parameter list's closer precede no parameter and are where its Name was expected; an alias takes its pending header before its target is read; and the attributes an `init` header report rejects are its recoveries. A keyword, number or other token at the Name position of a declaration is where the Name was expected (`TokenReader.TryReadName`, `Parser.ParseDeclarationName`); a header that fails there or at its parameter list introduces no declaration: the declaration's line and the body it would introduce are skipped to the line boundary and the omission is recorded (`Parser.OmitDeclaration`), so the next statement keeps its own problems, a nameless Container merges with no other, and a check over the member set rests on the Error.
- An indented block that no header introduces is `IndentedBody` misplaced: in an executable body its items are parsed as a block; in a Container body, and after a statement that takes no body (`TokenReader.ExpectLineEnd`), it is skipped whole, the Container recording the omission; it never ends the enclosing body. A Container declared where none nests, in an enum, a Contract or an executable block (SPEC 6.1.1), is `ContainerDeclaration` misplaced and skipped with its body. A Container keyword starts a declaration unless an expression continues after it or its line ends without an indented body; there it is a Name (SPEC F.3, `Parser.IsContainerDeclarationStart`).
- A token that starts no Type where a Type belongs is where the Type was expected (`Parser.ParseType`): a literal, `_` or a token the lexer rejected stands where the Type was written and is consumed with the report; any other token, such as `=>`, `is`, `and`, a closer or an operator, is left to end the enclosing construct. After a `.`, a Type member is a Name or a parenthesized Contract (SPEC 8.5), and a failed member makes the qualified Type the Error's recovery. A root-qualified Type is the path after `::`; its Origin and `?` belong to the enclosing Type. A Constraint whose subject or requirement failed is a recovery: Binding keeps an Error constraint for it and binds none of its parts, in a function and in a Container alike.
- A body missing after a header is supplied as a recovery: an empty block at the insertion point (`ParseRequiredBlock`) or, after `=>`, the Error expression (`ParseSingleBodyItem`). Binding completes the empty block without a Type, so a result check that reads it rests on the Error, and an Unsafe Block whose body it supplies is not reported as unnecessary, since what the body uses is unknown. Binding is then incomplete, so ownership records wait for the repair, as with any recovered expression (§9.5). Control-flow checks that read its normal completion rest on it as §4.3 states.
- A token is blamed once: an expectation at a token the lexer rejected, or that an earlier expectation already named, rests on that Error and records nothing (`DiagnosticCollection.RecallError` over the Syntax partition). Distinct forms missing at one insertion point, such as the closers of nested groupings, are distinct problems; a repeated report of one form merges by its key.
- The key of a form report is `(span, Syntax.<Form>)`; the report becomes `LastError`, so `NewErrorKoto` and `RecordRecovery` name it as their cause. A nested part the parser skips because a form failed, such as the closer of a Type argument list whose last argument failed, records nothing (§4.3).
- The tokenizer reports a closer missing at a line end or the end of the source as `MissingSyntax_Kd` with the opening delimiter as related evidence and the closer at the insertion point as a repair candidate (`Repair.InsertToken`, §4.5), as does the parser's `Missing` for a closer it expects; a closer with no open grouping is `MisplacedSyntax_Kd` (`UnmatchedCloser`); the parser's statement end then blames neither again.
- Excluded compile-time syntax is parsed by the same item loops as selected syntax (SPEC §19.4), so it reports the forms the selected path would, at the same insertion points: the condition missing after `#if` or `#case`, the line end after `#switch`, the body missing after a header that requires one, and the declaration missing after a trailing `#if` prefix.
- A `#switch` Case Group is scanned once before its arms are parsed (`Parser.ScanCompileTimeSwitch`): it reports every header, structure and Condition problem, including an arm without a body, which leaves the group invalid like a malformed header; the arm walk that follows reports nothing again. A group that selects no arm is kept as a marker (`CompileTimeSwitchKoto`) recorded as the recovery of the Error that kept it from selecting one, so Binding and control flow add nothing at it. Attributes before a `#switch` or an orphan `#case` are reported before its Conditions are read (`RejectDirectiveBlockAttributes`); an orphan `#case` without a body is the whole item, so an enclosing `#if`'s exclusion ends with it. A Condition is a header expression, and the evaluator treats a recovered node as Binding does: an attribute reported as misplaced marks nothing, and a recovered form such as a chained comparison has its parts checked on their own while its value rests on the syntax Error (`CompileTimeConditionEvaluator`). Excluded members are parsed under their container's header (`DeclarationContainerKoto.ExcludedOwner` shares the generic parameters), so a member's Constraint on the declaring Type's parameters is judged as when selected. A directive where no item is selected, in a parameter list, before an operand or in a match arm list, is `CompileTimeDirective` misplaced over `#` and its keyword: in an attribute position its Condition is read and set aside and what follows is parsed in place (`Parser.ParseAttributeKoto`); in an arm list its line, with an indented arm block or Case Group, is skipped. Any other reserved word after `#` is where the attribute Name was expected, and the construct it would start is not read; an indented body after a word that ends its line would be that construct's and is skipped with it.
- Adding a form is one enumeration value, one table row and at least one case of `tests/diagnostics/syntax.json`: `SyntaxDiagnosticTest` checks that every case publishes exactly its expected records through the check entry, that every form has a phrase and a case, and that both output adapters show the form's label.

Unterminated strings, char literals and block comments keep an invalid token at their opening delimiter, whose lexical Error is recalled by the parser. Argument lists distinguish such tokens from the end of input, including when a malformed comment consumed the rest of an argument list. Delimiters already open when the scan fails record that lexical check as a prerequisite of their missing-closer checks; later delimiters and other sources remain independent. `Tokenizer.RecoverLexicalToken` shares this path for all three forms. Recovery unwinds every grouping and body required by the next line's indentation, so the next statement keeps its original scope. The delimiter-to-cause map is allocated only on malformed input. `StringDiagnosticTest` and `LexicalRecoveryTest` cover opening ranges, matching quote count (including raw strings), rejection and repaired acceptance, independent problems, rebinding, line endings, source isolation and CLI/LSP output. This implements §23.1.2 without changing token syntax or guessing a delimiter insertion point.

Malformed character escapes in strings, interpolation segments and char literals span the escape itself, including its backslash; an invalid escape's fact also includes the backslash. The shared decoder derives this range from the consumed source length, before physical line endings or supplementary scalars are decoded. Separate escapes therefore retain separate records even when their code and facts are identical (`StringDiagnosticTest`).

### 4.5. Repair candidates

A record offers repair candidates (SPEC §23.1.3) as part of its facts; a candidate is never inferred from Note prose, and no tool applies one unasked.

- **Recording.** A recorder passes `DiagnosticRepairFact` values to `Koto.Report` (`repairs:`) or `DiagnosticCollection.Report`: the kind (`RepairKind`), the kind's facts captured as values, the edits, and the relevant conditions it judged **verified** or **required** (`RepairConditionSet`). A refuted condition is never recorded: the recorder withholds the candidate, and the repair is not offered. An edit is located through `Koto.Edit` or `DiagnosticCollection.Edit` (a span of the node's or the target's document and the replacement text); a source without text or a `compiler://` source is an invalid location. Candidates exist only on failing paths, so a check without diagnostics allocates nothing for them.
- **Catalog.** `RepairKind.tinyhand` defines each kind once, like the requirement table: its stable name (`Repair.<Kind>`), the title template over its facts, the facts as `name:Kind` and mandatory `Conditions` plus occurrence-dependent `ConditionalConditions`. A recorder supplies a conditional condition only when its check establishes relevance. `RepairKinds` validates it when it loads; an anomaly faults every report that offers a candidate (`DiagnosticCatalogTest`). The implemented conditions (`Take`, `ExclusiveAccess`, `UsageLegality`, `Structure`, `Selection`) and the phrase templates of required conditions are fixed in `RepairConditions`; the vocabulary is closed by the SPEC. `Repair.Qualify` always judges `Selection`; `UsageLegality` is relevant only for a value operation.
- **Recording boundary.** `DiagnosticCollection.Report` validates each candidate against the catalog (kind, fact count and kinds, each relevant condition in exactly one of verified and required, at least one edit, no candidate on a derived record), orders the edits by position with two insertions at one point joined and overlapping edits rejected, and orders the candidates by kind then first edit. A repeated report of one problem merges candidates like evidence: absent ones are taken, different ones conflict.
- **Finalization.** `DiagnosticOwner.Finalize` keeps the first candidates up to `DiagnosticLimits.Repairs`, omits whole a candidate with more than `RepairEdits` edits or more than `RepairText` characters of replacement text, and counts the omissions as `repair candidates`. `Describe` types and bounds the facts by the kind's schema, forms the title and the phrases of required conditions from the bounded values, and gives each edit its display range and the bounded text it replaces (`RepairEdit.Replaced`). The sources of kept edits enter the source table; omitted candidates add no entry.
- **Outputs.** The public form is `RepairCandidate` on `CheckDiagnostic.Repairs`; equality compares candidates. Commands render each candidate after the Note (`Repair: <title>`, one ` = path:line:column: insert|replace|delete` line per edit, then ` = verified: …; requires: …`), the JSON form keeps every field, and the snapshot harness compares candidates as a difference of kind `repair` (§9.1).
- **Recorders.** Syntax: `TokenReader.ReplaceToken` and `InsertToken` (a misplaced `&&` or `||`, the former Origin keyword `from` in `Parser.ParseBorrowOriginSuffix`, a closer the parser expects at an insertion point) and `Tokenizer.ReportMissingDelimiter` (a closer missing at a line end). HIR lints: `Binding.RemoveUnsafeRepairs` offers `Repair.RemoveUnsafe` with `Structure` verified for an Unsafe Block that is a statement of an indented body whose Body declares no Name and registers no `defer`, when the `unsafe` line holds nothing else, every Body line has a full level of space indentation and no string literal spans lines (`RemoveUnsafeEdits`); a declaring or deferring Body and an expression position refute `Structure`, and the other forms are offered no candidate. Acquisition: a bare Place that Binding or the ownership analysis rejects for a missing `@move` offers `Repair.Transfer` at the Place (`Binding.TransferRepair`, `(*p)@move` around a dereference) with `Take` judged from the Place's path alone (`Binding.TakeJudgment`: verified for an owned path from a local, parameter or capture root and for a raw referent; refuted for a borrowed, published or shared path, a Property's storage, a Pattern candidate and an element outside a static Move Path; required otherwise) and `UsageLegality` required; the borrow alternative where a reference may be meant and the remaining alternatives when `Take` is refuted are not offered. Binding remembers the Place that set `transferRequired` or `lendingRequired` (`acquisitionPlace`, recorded with the failure by `FailAcquisition` into `acquisitionPlaces`) so the record is located at the Place and names it. Open (PLAN G262, DECISIONS BU-45): a bare argument or payload of a pair layer without a plan in some Semantics cases is Binding's record without those cases (no `case` fact, case Note or binder relation, which the old path's record carried), since the recorded failure states the Place and its spelling but not its failing cases nor whether the bare plan or an explicit operation's Copy requirement failed, so `FailingCaseNote`, which a bare capture entry's Note uses, cannot be applied by one rule. Open, pre-existing: where such an input's outer Origin also mismatches, AdaptInput's argument rule names the failed acquisition alone, one of two independent failures. A missing `@uniq` or `@objuniq` offers `Repair.BorrowExclusively` with `ExclusiveAccess` verified, because the Place was already judged exclusively borrowable. A bare capture entry of a Non-Copy binding offers `Repair.Transfer` (`x@move`) and `Repair.Borrow` (`x@ref`). Discards: the HIR lint (`Binding.DiscardRepairs`) offers `Repair.ExplicitDiscard` (`_ = `) for a discarded Result or try success value that is a direct item of an indented body and, for a Result whose error Type the enclosing function's Result takes (`FailureTargetFits`, SPEC §17.3), `Repair.PropagateFailure` (`_ = try `) first; no condition is relevant, and the alternatives the candidates cannot express are not offered.
- **Tests.** `DiagnosticContractTest` covers finalization, order, limits, every contract violation and the command rendering; `DiagnosticOwnerTest` the JSON round trip; `SyntaxDiagnosticTest` the `Repairs` expectations of `syntax.json`; `UnnecessaryUnsafeBlockTest`, `OriginSyntaxDiagnosticTest`, `AcquisitionRepairTest`, `RawPlaceAccessTest`, `BorrowAcquisitionTest` and `DiscardRepairTest` the recorders above, including the forms that offer nothing; the verified cases apply the edits and check that the edited program is accepted. A recorder that adds candidates fixes, per reporting site, the refuted and required counterexamples of each condition.

## 6. Diagnostic contract and faults

- Violations (SPEC §23.1) go through one fault path. It discards the partial records and reports `CheckFaulted_Kd` with fixed text and the fault kind as its Reason. The fault path depends on neither the catalog nor ordinary formatting; its fixed values live in one place, and a test checks them against the catalog.
- A malformed repair candidate (§4.5) is a violation at the recording boundary: no edits or overlapping edits, an edit outside its source or in a source that is not a recorded input (`InvalidLocation`), a candidate on a derived record, an unknown kind, facts that do not match the kind, or a relevant condition judged neither or twice (`InvalidArgument`); two reports of one problem with different candidates conflict (`ConflictingProblem`).
- When an analysis throws while the diagnostic path is intact, the valid facts are kept, `CheckFaulted_Kd` (kind `Exception`) is added, and the result is Faulted. `CheckService` no longer formats its own records.
- An exception after the front end ran is the `Exception` fault on both paths, including an `InvalidDataException` of test discovery; only an invalid test configuration thrown before the front end blocks the check (`ProjectPreparationFailed_Kd`). The check entry decides Blocked from whether the front end ran (`CheckContext.Compilation`), never from the categories of the records.
- Cancellation and waiting for an unestablished input keep their current handling: both propagate as exceptions, and a cancelled check has no output.

## 7. Outputs

- **Commands** print a result once it is finalized; `Project.BuildTarget` has one finalization point for every return path, including an analysis exception, which it renders as the check entry's Faulted result (valid records plus `CheckFaulted_Kd`, or only the fault after a contract violation) before the command fails. Input preparation that ends without an Error reports its fallback in the shared front end, so the command and the check entry publish the same records; the check entry adds no fallback of its own, and a rejection that reaches finalization unexplained is the `UnexplainedRejection` fault on both paths. The project file is registered when its compilation is created, on both paths, so records naming it keep its consumption order. `kimi test` keeps diagnostics on standard error.
- **Language server.** `LspDiagnostic` equality is structural, including related information, because deduplication and repeat suppression compare values. The client's `relatedInformation` capability is read at `initialize`.
- **JSON implementation boundary (PLAN S1015).** `CheckJsonOutput` still checks one unit through the shared check entry and writes a single-unit `kimi.check/2` `CheckDocument`. `DiagnosticJsonContext` uses camelCase names and string enumerations; source hashes come from `HashingInputSource`, and the snapshot harness (§9.1) keeps the result as evidence. The required [SPEC §23.3](../spec/23-compiler-services.md#233-json-check-output) and [schema](../spec/schemas/check-output.schema.json) now define `kimi.check/3`: one command result containing all selected unit results. Aggregation, continued checking after unit failures, ordering and cancellation remain to be implemented under §23.2.3.
- **Code actions** (SPEC §23.4). `WorkspaceCheck.Place` also places each record's candidates whose edits all lie in the record's own document as `LspRepair` values (the sent diagnostic, the title with any required phrases, the edits as text edits), kept per report URI in `UnitResult.Repairs`. The state owner keeps, per URI, the candidates every valid contributor agrees on (`Reconsider`, updated at every adoption, also when the payload is not resent) and answers `textDocument/codeAction` from them without a check: the request's range is matched against each sent diagnostic's range (half-open intersection, a point within a range with the end included, equal points), `context.only` without `quickfix` returns nothing, and so does a URI whose contributors are not all valid, so an edit, a reopen or a desynchronization clears the quick fixes until the next adoption. Each action is a `quickfix` with the sent diagnostic and one `TextDocumentEdit` at the document's current version. The capability is advertised only when the client declares code action literals and versioned document changes; without it the request returns nothing. `LspCodeActionTest` covers the capability, matching, `only`, validity and the restored version.

- **Recovery of a failed declaration.** A misplaced or malformed part that a later phase would otherwise judge again is removed from what that phase sees, or the node is recorded as a recovery: a modifier or attribute without a declaration skips its line and the indented body it would have introduced (`Parser.SkipDeclarationLine`); a malformed attribute attaches to nothing; a struct with several bases keeps the first; a setter with a result Type other than `()` keeps the Unit result; a `$require` with a malformed list keeps its condition and a recovery message; a binding, Property or parameter without its Type annotation gets a recovery Type, so its uses rest on the Error; an enum without a body, a computed Property without `get`, a renamed or defaulted receiver, a specialization without Type arguments, a Property whose accessor line names neither `get` nor `set`, a requirement accessor with an access modifier and a constructor whose initializer does not name `base` record the declaration as a recovery (`CodeContext.RecordRecovery`), so Binding's own check of it is derived and ownership analysis skips its body. A decoration that leaves the declaration checkable, such as `public` on a specialization, records nothing, so independent problems stay visible. `Koto.Unexpected` reports a node as misplaced, `Koto.Expected` reports a form expected where a node stands (its first source line is what was found), and both return the key; the caller decides whether the node is a recovery. Additional recovery forms: an `origin` clause after an accessor or executable item is dropped; a Constraint prefix whose subject the declaration does not permit stays a Constraint of the function (SPEC 7.5) recorded as a recovery, and a `length` slot outside a function's Type parameter list stays in the list, so Binding's own checks of the function and of the declaration's formation still follow (S3); a `during` line in a body, a nested if expression and a `$` prefix on a call that is neither abort nor tryWrite are recorded as recoveries; a `?` on a Semantics shorthand, `move`/`copy` as a Semantics prefix, an annotated adaptation borrow layer, a literal, bare-Name or empty-payload case Pattern and an `init` reference without `(` become recovery nodes with the Error as their cause.

- **Recovered expressions.** Binding checks an expression node that the recovery map names on its operands alone and completes it without a Type, so every check of it, including the overload selection of a call whose argument it is, rests on the syntax Error (one rule in `BindNode`; it replaced the per-kind cases for chained comparisons, jumps and labels). A literal kept as a recovery, such as a positional argument after a named one, is bound this way instead of being fitted after selection. Review every removed record as a duplicate or cascade, never as an improvement by count alone.

## 9. Evaluation

### 9.1. Snapshot harness

One harness checks a fixed corpus through the check entry: milestone programs, rejection fixtures, examples and mutation cases. It writes normalized records, outcomes and acceptance as JSON under `artifacts/verify/`, and classifies differences against a baseline by kind: case, acceptance, code, severity, attribution, location, text, repair (a changed repair candidate) and order. Timing belongs to the separate measurements (§9.4). A stage lists the kinds it intends; any other difference needs review.

### 9.2. Mutation tests

- Mutate a milestone program that passes, or a part verified independently. Change a copy in memory or under `temp/`, never the original, and confirm that the edited text is unique. An unfinished program with existing errors is never a single-error base.
- A case records its base source, effective configuration, change, intended problem and expected public records. Expectations are written independently of the generators.
- Cases cover definitions and recorders, prerequisites and cascades (including recovery), error state and invalidation, outcomes and faults, locations and snapshots, outputs and limits.
- Compare codes, requirements, Reasons and locations. Full-text comparison is limited to a few display tests, and people review underlines against explanations. A lower diagnostic count is not a goal.

### 9.3. Input relations

- Adding a blank line outside strings and documentation comments changes positions only, including blank and comment lines after a body (`DiagnosticRelationTest`).
- For the same check, input and prerequisites, adding an unrelated problem leaves existing primary records and explanations unchanged.
- Changing wording alone leaves identity, suppression and order unchanged, and the change of the published values is detected.
- Reordering inputs whose order the SPEC leaves free leaves records and order unchanged. The compiler has no hook for reordering its own work.
- Changing limits never changes a problem's survival, category or acceptance.

### 9.4. Performance

- Paths without diagnostics gain no per-node allocation or string formatting; only published records are formatted.
- Targets: resolving causes in O(F + E) for F facts and E prerequisite references, ordering in O(D log D) for D published records, explanations in O(D × K) for a per-record limit K.
- Compare time, allocations and retained size before and after on the same machine, configuration and input: the existing warm zero-allocation probes, front-end timings of milestone programs, and the LSP measurements. A reproducible regression is fixed; an unmeasured improvement is not claimed.
- Analysis is single-threaded and each compilation owns its diagnostics, so recording needs no lock.
