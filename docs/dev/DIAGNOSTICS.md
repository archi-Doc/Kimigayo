# Kimigayo Diagnostics

Developer notes for the compiler's diagnostics. SPEC [§23.3.3](../spec/23-compiler-services.md#2333-outcomes-and-acceptance), [§23.3.6](../spec/23-compiler-services.md#2336-diagnostics) and [§23.4.7](../spec/23-compiler-services.md#2347-publication) define the observable behavior; this document records the internal model that realizes it, the rules that keep it consistent, the migration rules of the Diagnostics track (PLAN.md) and the detail of the [Diagnostic development workflow](../../AGENTS.md#diagnostic-development-workflow). It never overrides the specification.

## 1. Principles

| ID | Principle |
| --- | --- |
| I1 Definition | The meaning and definition of a diagnostic are decided in one place. |
| I2 Determinism | Published content and order never depend on arrival, threads or wording. |
| I3 Explanation | Suppressing a cascade never removes the record that explains the problem. |
| I4 Acceptance | Acceptance never depends on display, suppression or supplements. |
| I5 Locality | Adding an unrelated problem never reduces the explanation of another. |
| I6 Boundary | Published content is finalized once and never changed afterwards. |

## 2. Common rules

Each rule replaces a family of special cases. A change that needs an exception to one of them first revisits the rule.

1. **One requirement, one phase.** A requirement is judged by the phase of its owning partition. A later phase that depends on it names it as a prerequisite and never reports it again.
2. **No free text.** A code's message, label and Reason come from its typed facts. A difference within one requirement is a Reason value; a different requirement or category is a different code; wording alone never adds a code.
3. **Unsupported is its own category.** A form the SPEC permits but the implementation does not support uses an `Unsupported` code, with the missing feature in the Reason.
4. **One node state, many facts.** A syntax node keeps one analysis state, which its first failure sets. Diagnostic facts are kept per problem key and recorded at the final decision; a second failure adds a fact without changing the state.
5. **Context only when it matters.** A context (instantiation, expansion) is part of a key only when the requirement's outcome or Args depend on it; a check without a context has no instantiation-specific Args.
6. **Total order by structure.** Every key component has a total order: source table order and span for positions, a fixed order for enumerations, and a structural order for Types (declaration source and span, then Type arguments recursively; built-in Types in a fixed order). Display names are never compared.
7. **Records are independent of display.** A record is finalized without knowing its output. Limits are the only settings: constants in one place, which tests exceed with long inputs rather than replace.
8. **One fallback rule.** A phase that ends incomplete, with no Error in its partition or an earlier one, reports one fallback at its first incomplete subject (SPEC §23.3.3). The contract check for unexplained rejections is the last safety net. Tests treat any fallback as a defect.
9. **One fault record.** A Faulted result is explained by exactly one `CheckFaulted_Kd` whose Reason carries the fault kind. `InternalInvariant_Kd` is reserved for internal failures in a Completed result.
10. **Decisions look backwards.** A decision queries only the partitions that precede it: library validation reads the library's syntax partition, emission and acceptance read every front-end partition.
11. **Introduce at first use; rewrite each call site once.** A concept arrives in the stage that first uses it, and a reporting call site is rewritten once, with its generator, key, prerequisite and location together.

## 3. Definitions

| Source | Holds |
| --- | --- |
| `src/Kimi/Diagnostics/DiagnosticCode.tinyhand` and `DiagnosticEntry` | Severity, category, and default Message, Label, Note and Advice |
| Phase-specific reporting conversions (C#), checked against the catalog schemas | Argument and evidence values, roles of related locations, conditional explanations |
| `DiagnosticRequirement` (a C# value of the owning partition and that phase's failure enumeration) | The requirement's stable name (public vocabulary, like code names), its owning partition and its semantic order |
| `DiagnosticRequirement.tinyhand` | A short description per stable name; for a syntax form also the `Phrase` its diagnostics display and its conditional `Advice` |
| `SyntaxForm` (`src/Kimi/Compiler/Parsing/SyntaxForm.cs`) | The forms the parser expects or finds misplaced: the requirement Kind of the Syntax partition, named `Syntax.<Form>` (§4.4) |

- Enumerations are written by hand; a consistency test keeps enumeration, catalog and description table equal. No enumeration is generated.
- The catalog is validated when it loads: unknown, duplicate and missing entries, invalid severities/categories, malformed or duplicate fact names and a template whose placeholders differ from its schema's arity are catalog anomalies. Message templates are parsed once, at load. Record-time checks reject nonnumeric Number values, undefined Enumeration values, non-Boolean Boolean values and a Requirement value without a phrase. The reporting APIs currently accept objects; this validation is not a claim that every recorder has a separate statically typed generator.
- A fact of kind `Requirement` is a requirement by its stable name (exact in the Reason); the message and label display its phrase. `PrerequisiteUnavailable_Kd` names the undecided requirement this way, and the syntax codes of §4.4 name their form.
- `PrerequisiteUnavailable_Kd` (Error, `Proof`): "This requirement cannot be decided because its prerequisite could not be established." Its Reason is `requirement` (a stable name) and `condition` (the condition and the fact it needs).
- The former `Fix` field is Advice, with no alias. The former `hint` argument is gone; its content is a Note or Advice built by a typed generator.
- Callers obey the definition: a serialized source in an incompatible format is an `Input` problem with its own code, never a syntax form with prose.

## 4. Model

### 4.1. Facts and keys

Generation retains a refused generic instance's pooled ownership issues and concrete call until publication or the next preparation. `ReportInstanceDiagnostics` uses the ordinary ownership fact reporter in the Emission partition, preserving codes, categories, primary and related locations, and adding instantiation context. A refusal without an issue is Internal; classification never comes from its message. Preparation replaces previous Emission diagnostics, and instance refusal does not invalidate the universally checked definition. `GenericGenerationDiagnosticTest` exercises publication and recovery.

A logical model; it requires no allocation per field.

```text
DiagnosticFact
  Code        : DiagnosticCode
  Subject     : a syntax node, token, input or compiler process of this analysis
  Check       : requirement and condition number (independent of the code)
  Context     : instantiation or expansion context, or none (rule 5)
  Primary     : primary location
  Args        : the code's typed facts
  Evidence    : supplementary evidence with roles
  DerivedFrom : check keys of the unmet prerequisites (an unresolved mark when unknown)
```

- The **check key** is `(Subject, Check, Context)`; the **problem key** is `(check key, Code)`. Identity never uses display ranges or strings.
- A requirement is distinct across phases: establishing a declaration's Type and a call's argument count are different requirements. The condition number distinguishes arguments, Contract conditions or Places within one requirement.
- A Subject distinguishes source snapshots and analysis generations. A syntax error names a token or boundary; an input failure names the input. A synthesized node is identified by its original subject, its transformation role and its order within the transformation.
- A problem with several subjects is normalized before it is recorded (SPEC §23.3.6.4).
- Values that can change after recording (a rebound call, reused scratch storage) are captured as values; immutable analysis data may be referenced. Prerequisite, evidence and related-location arrays are copied at the recording boundary, including the first report of a problem.
- Analysis-specific failure enumerations remain; each converts to diagnostics in one place (Binding's `Check` switch, `OwnershipIssue.Code`, the control-flow conversion).

### 4.2. Owner, partitions and error state

- One **diagnostic owner** per check request is created before input preparation and passed to the compilation and later phases. It replaces named collections, `IsGlobal`, the mutable current `SourceDocument` and positional removal.
- Facts are recorded in **partitions** that follow the existing invalidation boundaries:

| Partition | Invalidated when |
| --- | --- |
| Input and configuration | Kept for the whole check request |
| Syntax (one per module) | That module's syntax tree is rebuilt; it also holds the recovery map |
| Semantics (Binding, startup, control flow and ownership) | Any syntax changes (all of it), or one phase is analyzed again (that phase and later ones) |
| Later phases | One per result unit |

- Invalidation replaces a partition's fact list as a whole and never scans facts; `BeginSourceParsing` must stay cheap. Production analyzes each compilation once; repeated analysis happens in tests and benchmarks.
- Recording an Error sets the error flag of its partition and module before aggregation or suppression; a valid partition never clears it.
- Acceptance, emission and library validation query the owner under rule 10. A decision inside one call (token caching, `Documentation.Finish`) uses that call's local result. `errorCount`, `ErrorVersion` differences and `HasSourceErrors` are removed.
- A tentative retry inside an analysis stays inside it; only the adopted decision becomes a fact.

### 4.3. Recording, aggregation and prerequisites

- Facts aggregate by problem key when recorded. For one key, Primary and Args must be equal (a contract violation otherwise); causes and captured evidence are unions, and evidence keeps the first N by the order of SPEC §23.3.6.5.
- Invariant: `Code == PrerequisiteUnavailable_Kd` exactly when `DerivedFrom` is not empty. An unknown cause records the unresolved mark.
- Only Errors are derived. A warning check whose prerequisite failed records nothing.
- The recorder of a derived failure names the unmet prerequisites by check key; the prerequisite's code may be unknown and recording order does not matter. A prerequisite key names the referenced check and accounts for every Error it reported; another requirement gets another key. An empty prerequisite array is equivalent to no prerequisites and preserves a direct diagnostic's facts.
- Nested parts skipped because a check failed are explained by the failure and get no facts. When an explicitly referenced prerequisite was itself skipped, the derived fact inherits the skip's cause.
- **Consultation (Binding).** Each checked node is bound in a frame: expressions (`BindNode`), Type expressions (`BindType`), variables (`BindVariable`) and a call's member callee. A frame records the operands the node read that did not resolve, and every node failed while it is open. A use of a parameter or property whose Type failed consults the written Type. An expression bound against an expected Type whose written syntax failed (an initializer, an assigned value, a returned value) names that syntax where it needs the expectation, and a call with no applicable candidate rests on a candidate whose signature failed. An operand that resolves later is not a prerequisite, and a node whose lookup succeeded but was never completed contributes nothing. A failure that reports missing information (`MissingName`, `MissingType`, `Unsupported`) with an unresolved prerequisite is derived, and so is a constraint proof (`InvalidConstraint`) that a declaration-level check found failing because a part it recorded with `AddPrerequisite` failed, such as a Property whose declaration context is invalid; every other failure is direct. A call whose candidate or selected target lies in a failed declaration (`InvalidDeclarationContextCause`) rests on that declaration instead of failing itself. A failure of any kind is derived when the check consulted a recovery node, directly or through unresolved operands (`RestsOnRecovery`): the parser's guess explains what the check combined. A declaration-level check that reads a part outside a frame records it with `AddPrerequisite` (a function's recovery Constraint, a nominal header's `length` slot, an associated Type's Origin parameter, a Property whose declaration context is invalid); these part prerequisites outlive the per-pass prerequisite storage because the checks run once per Bind.
- **Several problems of one node.** A check that fails independently at several of its parts reports one fact per part with the node as subject and the condition number as the part's ordinal. A parameter acquisition shape violation (SPEC §7.3.1, `ParameterShapeMismatch_Kd`) reports each conflicting parameter of the later declaration in source order at the parameter Type, with conditions `0..n-1` and the overlapping earlier parameters as related locations; a group gathered at a use reports one record at the called Name, whose condition 0 is the check that dependents of the failed call name as their prerequisite (`PrerequisiteKeys` uses condition 0).
- **Recovery.** When parsing fails, recovery links what it keeps to the key of the lexical or syntax check that caused it: every `ErrorKoto` carries the key of the Error reported just before it (`TokenReader.NewErrorKoto` and each direct construction), and synthesized syntax kept in place of a rejected form, such as the combined node of a chained comparison, a body supplied for a missing one (§4.4) or the armless match of a missing arm list, is recorded in its `CodeContext` (a map that exists only after a recovery). The lexer and the parser of one document record through one target, so a token the lexer rejected is not reported again: the parser recalls the lexical Error at that token's span (`DiagnosticCollection.RecallError`) and rests its recovery on it. A function body missing because of a syntax Error is marked (`FunctionKoto.MissingBody`) and gets no ownership body. Binding checks the operands of a recovered form on their own, not its guessed combination, and names the key as the prerequisite of every check that depends on the recovered node. A compile-time condition that is an `ErrorKoto` is outside the grammar without a report of its own. The parser records a skipped declaration in `Kotonoha.OmittedDeclarations`, so a check over the member set can rest on it.
- **Later phases.** A startup or control-flow check that reads Binding's result at a node that Binding failed, or left resting on a failure, is derived from those Binding causes (`Binding.FailureCauses`); an incompatible result also rests on its consumer, the node that reads it. This covers a later phase repeating Binding's own check of one requirement. Checks judged from syntax alone (jump targets, labels, fallthrough, Unsafe Blocks, `while true`) stay direct, so independent problems at one node survive. A warning whose check rests on a Binding failure records nothing; an Unsafe Block containing an operation whose need for the permission is unknown is therefore not reported as unused. The startup check that finds no body rests on the omitted declarations when the parser skipped one. A control-flow check rests on a recovery's syntax Error only where the recovery guessed what the check reads (`ControlFlowAnalysis.GuessedBy`): the target syntax of an unlabeled jump or a label, and the normal completion that a fallthrough (`FunctionFallthrough_Kd`, `RequireFallthrough_Kd`) or a discarded tail (`DiscardedTail_Kd`) reads. A jump target written in source is judged independently of a recovered operand (`ContextualLabelTest`). A completion check rests on the bodies the parser supplied for missing ones (§4.4) when the checked syntax, or for a tail any syntax its descent passed, completes normally only through them, since a written body might have returned or exited: the Error is derived from their keys and the warning records nothing. A completion that written syntax also reaches stays direct, such as a written branch that falls through, an if without else (`syntax.json`: `guessed-*`, `written-*`), or a require failure body written in source, after a missing `else` or as a recovered form such as a chained comparison (`RequireRecoveryDiagnosticTest`). The check assumes the supplied bodies do not complete in a second structural completion, created only after a recovery, so valid input pays one null check per visited node. Ownership analysis skips the body of a function that is a recovery. The result that a function's Block body leaves undelivered at its normal end is the fallthrough seen from the result Place (rule 1): ownership's `UninitializedPlace_Kd` at that delivery rests on the control-flow check of the body when control flow reported `FunctionFallthrough_Kd` there (`ControlFlowAnalysis.Reported`), and stays direct otherwise, so an unresolved prerequisite never replaces it. Other ownership problems of the function stay direct (`DiagnosticPrecisionTest`, `syntax.json`: `written-fallthrough`, mutation `missing-return`).
- **Declaration shape errors.** An accessor whose written receiver is not the shape of its operation (`AccessorReceiverShape_Kd`, SPEC §11.2) is one problem of the accessor declaration, located at the receiver Type with the Property header related. Its body is checked with the written receiver and adds no facts of its own. A Property use whose receiver is rejected under the written receiver but accepted under the operation's fixed shape rests on the declaration (`ReceiverRestsOnAccessorShape`); every other rejection of the use stays direct.
- **Suppression.** At finalization, valid facts are indexed by check key and each prerequisite is bound to every Error its check reported. A prerequisite without an Error, with warnings only, outside the result or in an invalid partition is unresolved. A derived fact is suppressed only when every cause reaches a published direct Error without an unresolved link or a cycle; otherwise it is published and suppresses nothing. Causes are resolved in one non-recursive pass that shares the verdict per prerequisite key; suppressed facts are released without being published.

### 4.4. Syntax forms

The parser reports what it expected, not what it saw. A **syntax form** (`SyntaxForm`) is a grammar position the parser can expect, such as an expression, a Type, a body, the end of the line or a closing delimiter, or a construct it can find where it is not permitted, such as an indented body that no header introduces. Each form is a requirement of the Syntax partition, `Syntax.<Form>`; the requirement table gives it a phrase (no article, lower case unless it is a quoted token or a capitalized term) and optional advice. Three codes explain every form:

| Code | Facts | Location |
| --- | --- | --- |
| `ExpectedSyntax_Kd` | `expected:Requirement`, `found:Text` (the token's source text) | The token found where the form was expected |
| `MissingSyntax_Kd` | `expected:Requirement` | An insertion point, length zero, right after the last written token before the line, block or source ended |
| `MisplacedSyntax_Kd` | `form:Requirement` | The misplaced syntax |

Rules, realized once in `TokenReader.Diagnostics.cs` (`Expect`, `ExpectLineEnd`, `Missing`, `Unexpected`, and `Expect(TokenKind)` with `FormOf`, the one map from a required token to its form) and `DiagnosticCollection.ReportSyntax`:

- A reporting site names a form and nothing else; the code, the location and the advice follow from the form and the current token. A site never passes text, and a difference in wording is never a new form. The reader's skip and consume helpers (`TryConsume`, `TryRead`, `SkipUntil`, `SkipListItem`, `SkipCurrentBlock`) report nothing of their own: `TryConsume` with a diagnostic expects the token's form through `FormOf`, `ExpectCloser` and `TryReadName` expect the closer or the Name, and the others leave the report to the caller that knows what it expected.
- A line boundary (`Separator`, `StartBlock`, `EndBlock`), a synthesized token or the end of the source means the form is missing, inserted after the last written token; a token spans its text as written, so the insertion point after a string literal follows its closing quote. Any other token is where the form was expected.
- A node ends at its last written token as well (`TokenReader.PreviousSyntaxEnd`), never at the line boundary that closes it. The tokenizer places an `EndBlock` at the first character of the next dedented line, so a block, a match arm list, a property accessor block and a `#switch` Case Group read their end before consuming it; the nodes that end with them (a function, a closure, an if, a require, a declaration) follow. The blank and comment lines after a body and the next line's indentation belong to no node, so no record, key or excerpt spans them, and adding them changes positions only (§9.3).
- The first form missing at an insertion point is the problem; a later non-closer form the parser expects there is its consequence and recalls that Error (`TokenReader.Missing`, `lastMissing`), while closers stay distinct problems. A closer the tokenizer synthesized counts as the first missing form at its insertion point once the reader passes it (`NoteMissingCloser`), and a closer the parser expects at a token mid-line recalls the tokenizer's report at the end of that line instead of reporting the token (`LineEndInsertionPoint`).
- A token left on a statement header's line before the indented body that follows is where the header's line should end, as after a function header (`ExpectLineEnd`): the header expects the line end there and the body, or a match's arm list, is still its own (`TokenReader.IndentedBodyFollows`, `SkipHeaderLine`). Without such a body the token is where the body was expected, the empty body stands for it, and the rest of the line goes with it, so an aligned `else` on the next line still continues the header. Inside a grouping, which ends on its line with its closer, nothing past that closer is skipped. A match's arm list is not an executable body (SPEC §14.2), so it has its own form (`MatchArms`). A body-bearing expression in a header (`HeaderBodyExpression`, including a compile-time Condition) is reported at its keyword; when an indented body follows the line, that body is the statement's, so the expression is not read and the rest of the line rests on the Error (`Parser.ParsePrefixExpression`); otherwise the expression is read with its bodies on the line.
- `&&` and `||` are recognized but are no operators (SPEC §2.4, §13.8). An expectation at either token reports the token itself as misplaced (`AmpersandAmpersand`, `BarBar`), whose repair candidate replaces it with `and` or `or` (§4.5, with a space on each side that touches a non-space character) and whose Advice states that Kimigayo defines no such operator; the form the parser expected there rests on that Error.
- An `else` that no if body precedes is `ElseWithoutIf`; its own body is read as part of the recovery.
- Recovery inside a grouping stays inside it. The tokenizer closes every grouping before what follows it, with a supplied closer where none is written, so every opener has its closer; a closer that closes no grouping is the lexer's `UnmatchedCloser` Error and stays a closer marked `Token.ClosesNothing`, which ends an expression as any closer does but which list recovery skips, and a `;` inside a grouping, where no statement ends (SPEC 2.4), is an invalid token. A list item followed by text that is no comma or closer is where the comma or closer was expected; the rest of the item is skipped to its next comma or the grouping's closer (`TokenReader.SkipListItem`, `ExpectCloser`), nested groupings and bodies whole, and the item before the skipped text, such as a call's last argument, an array element, a grouped operand or an index, is kept as a recovery (`Parser.RecoverItem`): every check that reads it, such as the call's overload selection or a fixed array's length, rests on the Error, while the other items keep the list's context. A Pattern keeps its items, so an arm's bindings survive. A Name expected in a list is read by `TokenReader.TryReadName`, which leaves any other token for the list to end at, and a list loop that reads nothing ends, so recovery always makes progress.
- An attribute where the grammar takes none (SPEC §6.5) is `Attribute` misplaced, reported once over the whole attribute wherever the parser meets it (`TokenReader.ReportMisplacedAttributes`: `TryConsume`, `ExpectLineEnd`, the Name and Type positions of a binding or Property, a function's Name and result Type, the expression parser), and the token the grammar expected may follow it, so `var x #Attr : i32 = 1` keeps its Type and initializer. SPEC §6.5 sets no adjacency rule for an attribute's argument list, so where the grammar expects `(` (a function or function expression header before its parameter list, `TryConsume` of `(`), an attribute takes a list only when another `(` follows that list: the last list is the header's (`Parser.ParseAttributeKoto`, `beforeList`). `func f #Test () => ()`, `func f #Test (x: i32)` and `init #Test (v: i32)` therefore report only the attribute, `#Attr(1) (x: i32)` keeps `(1)`, and `func f #Attr(1) => ()` gives `(1)` to the header, whose parameter problem is a second, independent one. A kept attribute that lands on a function expression's parameter is not that parameter's attribute (`HasWrittenAttribute`). The attribute stays on the next node so the source round-trips through the tree, and it is that Error's recovery: Binding lets it mark nothing (`Binding.IndexVisitor`, `TestSyntaxVisitor`), so the node it landed on is checked on its own. Attributes, modifiers or a compile-time prefix at the end of a body or of the source introduce no declaration and report `Declaration` missing after them (`Parser.ConsumeAttributeAndModifier`), in a Container body as in a function body. Modifiers share the line of the word that introduces their declaration and follow its attributes (Appendix F.3): modifiers that end their line, or that precede a directive, introduce nothing and report `Declaration` missing or expected there, and an indented body after such a line is skipped with it as after a failed header; an attribute after a modifier is misplaced. Each `static` and an `open` before anything but `struct`, or not directly before it, is reported where it is read and kept for recovery; a declaration's own checks judge the other modifiers only (`Parser.Judged`), a `static` alone needs no declaration after it, and a repeated modifier is named as written. Pending attributes before an item that takes none (a Constraint, an Origin relation, an effect, an `associate` declaration, an enum Case) are reported as misplaced and kept as recoveries (`Parser.ReportPendingAttributes`), as are attributes in an accessor list; attributes before a parameter list's closer precede no parameter and are where its Name was expected; an alias takes its pending header before its target is read; and the attributes an `init` header report rejects are its recoveries. A keyword, number or other token at the Name position of a declaration is where the Name was expected (`TokenReader.TryReadName`, `Parser.ParseDeclarationName`); a header that fails there or at its parameter list introduces no declaration: the declaration's line and the body it would introduce are skipped to the line boundary and the omission is recorded (`Parser.OmitDeclaration`), so the next statement keeps its own problems, a nameless Container merges with no other, and a check over the member set rests on the Error.
- An indented block that no header introduces is `IndentedBody` misplaced: in an executable body its items are parsed as a block; in a Container body, and after a statement that takes no body (`TokenReader.ExpectLineEnd`), it is skipped whole, the Container recording the omission; it never ends the enclosing body. A Container declared where none nests, in an enum, a Contract or an executable block (SPEC 6.1.1), is `ContainerDeclaration` misplaced and skipped with its body. A Container keyword starts a declaration unless an expression continues after it or its line ends without an indented body; there it is a Name (SPEC 2.5.1, `Parser.IsContainerDeclarationStart`).
- A token that starts no Type where a Type belongs is where the Type was expected (`Parser.ParseType`): a literal, `_` or a token the lexer rejected stands where the Type was written and is consumed with the report; any other token, such as `=>`, `is`, `and`, a closer or an operator, is left to end the enclosing construct. After a `.`, a Type member is a Name or a parenthesized Contract (SPEC 8.4.3), and a failed member makes the qualified Type the Error's recovery. A root-qualified Type is the path after `::`; its Origin and `?` belong to the enclosing Type. A Place result takes no `?` (`PlaceResultSuffix`, SPEC 7.1.1) and rests on the Error. A Constraint whose subject or requirement failed is a recovery: Binding keeps an Error constraint for it and binds none of its parts, in a function and in a Container alike.
- A body missing after a header is supplied as a recovery: an empty block at the insertion point (`ParseRequiredBlock`) or, after `=>`, the Error expression (`ParseSingleBodyItem`). Binding completes the empty block without a Type, so a result check that reads it rests on the Error, and an Unsafe Block whose body it supplies is not reported as unnecessary, since what the body uses is unknown. Binding is then incomplete, so ownership records wait for the repair, as with any recovered expression (§9.5). Control-flow checks that read its normal completion rest on it as §4.3 states.
- A token is blamed once: an expectation at a token the lexer rejected, or that an earlier expectation already named, rests on that Error and records nothing (`DiagnosticCollection.RecallError` over the Syntax partition). Distinct forms missing at one insertion point, such as the closers of nested groupings, are distinct problems; a repeated report of one form merges by its key.
- The key of a form report is `(span, Syntax.<Form>)`; the report becomes `LastError`, so `NewErrorKoto` and `RecordRecovery` name it as their cause. A nested part the parser skips because a form failed, such as the closer of a Type argument list whose last argument failed, records nothing (§4.3).
- The tokenizer reports a closer missing at a line end or the end of the source as `MissingSyntax_Kd` with the opening delimiter as related evidence and the closer at the insertion point as a repair candidate (`Repair.InsertToken`, §4.5), as does the parser's `Missing` for a closer it expects; a closer with no open grouping is `MisplacedSyntax_Kd` (`UnmatchedCloser`); the parser's statement end then blames neither again.
- Excluded compile-time syntax is parsed by the same item loops as selected syntax (SPEC §19.5), so it reports the forms the selected path would, at the same insertion points: the condition missing after `#if` or `#case`, the line end after `#switch`, the body missing after a header that requires one, and the declaration missing after a trailing `#if` prefix.
- A `#switch` Case Group is scanned once before its arms are parsed (`Parser.ScanCompileTimeSwitch`): it reports every header, structure and Condition problem, including an arm without a body, which leaves the group invalid like a malformed header; the arm walk that follows reports nothing again. A group that selects no arm is kept as a marker (`CompileTimeSwitchKoto`) recorded as the recovery of the Error that kept it from selecting one, so Binding and control flow add nothing at it. Attributes before a `#switch` or an orphan `#case` are reported before its Conditions are read (`RejectDirectiveBlockAttributes`); an orphan `#case` without a body is the whole item, so an enclosing `#if`'s exclusion ends with it. A Condition is a header expression, and the evaluator treats a recovered node as Binding does: an attribute reported as misplaced marks nothing, and a recovered form such as a chained comparison has its parts checked on their own while its value rests on the syntax Error (`CompileTimeConditionEvaluator`). Excluded members are parsed under their container's header (`DeclarationContainerKoto.ExcludedOwner` shares the generic parameters), so a member's Constraint on the declaring Type's parameters is judged as when selected. A directive where no item is selected, in a parameter list, before an operand or in a match arm list, is `CompileTimeDirective` misplaced over `#` and its keyword: in an attribute position its Condition is read and set aside and what follows is parsed in place (`Parser.ParseAttributeKoto`); in an arm list its line, with an indented arm block or Case Group, is skipped. Any other reserved word after `#` is where the attribute Name was expected, and the construct it would start is not read; an indented body after a word that ends its line would be that construct's and is skipped with it.
- Adding a form is one enumeration value, one table row and at least one case of `tests/diagnostics/syntax.json`: `SyntaxDiagnosticTest` checks that every case publishes exactly its expected records through the check entry, that every form has a phrase and a case, and that both output adapters show the form's label and advice.

Unterminated strings keep an invalid operand token at their opening delimiter, whose lexical Error is recalled by the parser. Argument lists distinguish such tokens from the end of input. Delimiters already open when the literal fails record that lexical check as a prerequisite of their missing-closer checks; later delimiters and other sources remain independent. Recovery unwinds every grouping and body required by the next line's indentation, so the next statement keeps its original scope. The delimiter-to-cause map is allocated only on malformed input. `StringDiagnosticTest` covers the opening range, matching quote count (including raw strings), rejection and repaired acceptance, independent problems, rebinding, line endings, source isolation and CLI/LSP output. This implements §23.3.6.4 without changing literal syntax or guessing a quote insertion point.

- Explanations are formed once at finalization for published records (SPEC §23.3.6.5). Limits are constants in one place (`DiagnosticLimits`: excerpt lines and width, displayed value length, Note length, related locations); tests exceed them rather than replace them. Bounded text never splits a surrogate pair.
- **Facts.** The catalog names every message argument (`Arguments="name:Kind"`, with Kind `Number`, `Enumeration`, `Boolean`, `Text` or `Type`) and the evidence a recorder may add (`Evidence`, all of it or none). SPEC §23.3.6.5 adds the Kind `Origin` for the Origin relation records and `Owned` failures: an Origin display of kind `expression`, `borrow` or `omitted` with a bounded string, published in JSON as a value of kind `Origin` with that kind in `origin`; the catalog gains it with the Origin-relation unit (PLAN G56). The Reason is the arguments, then the evidence. A `Label` may reference them in that order and is omitted when a report lacks a referenced fact. A recorder may also name a primary location other than its subject (`at`) and related locations with roles.
- One bounded formatter (`DiagnosticText`) serves Types, Constraints and long names; the two Types of a mismatch keep their differing parts and elide the common head and tail. When one Type lies wholly inside the common parts, as `T` in `ref/T`, each Type is bounded on its own instead. Environment text is a bounded Note. The message and label display the bounded values.
- **Excluded syntax** (SPEC §19.5). The parser records each excluded range of a document with its innermost excluding directive (`CodeContext.RecordExcludedRange`); a re-parse of the module clears them. At finalization, a record whose primary span lies in a recorded range gets one `excludedBy` related location at that directive, from the smallest containing range, so lexical diagnostics receive it too. It is never evidence: code, primary span and Reason stay identical in every Compilation of the module.
- Related evidence is unioned by its full captured value, then ordered by ordinal role name, consumed source order, span and full value, before display bounding or limiting. Locations without a source come last within a role. The final source table contains only published primary/related sources, in consumption order; related-location arrival cannot change source order. What a limit drops is counted in the record's Omissions (related locations, excerpt lines).
- Order and equality follow SPEC §23.3.6.6 and rule 6. The semantic order compares subject, code name, requirement, condition and context. Subjects at one location compare by structure: depth, node kind, and for the synthesized calls of one transformation (such as the writes of an interpolation) the source order of their operands. A problem of a synthesized call is located at the syntax it concerns, such as the value an interpolation writes.
- A problem of a part that has no node of its own, such as one capture entry of a Closure (SPEC §7.6.2), keeps its node as the subject and key and is located at the part's span (`Koto.Report` with `span`).
- **Origin slots** (SPEC §15.3.2). A storage name (an instance Field Type, an enum payload or a base) that matches no declaration of any role is `MissingOriginBinding_Kd` at the name, with the Reason "name is not a declared Origin slot", a Note that own slots are declared only in the header, Advice with both repairs (an existing Origin, named, or a new header slot written out, which changes the public API) and the header (`header`) or, without one, the Type name (`type`) as the related location; nothing is reported at the Type. `during self` in storage keeps the storage rule of SPEC §11.3, and a name of another role keeps its role error. A projection of a slot its Type does not declare is `InvalidOriginBinding_Kd` once per projection at the slot name, with the declared slots in the Note and the header related; in its function, the unbound result slot and the Origin relations that need that slot, such as those of a returned value whose Type differs only in its bindings (SPEC §15.6.1), rest on that projection and are not reported. The header span is kept on `OriginNameList.HeaderSpan`; related spans without a node of their own pass through `Koto.Report(relatedSpans:)`.
- **Effect items** (SPEC §8.4.10.6). `InvalidEffectBound_Kd` is located at the effect item. Binding records only the facts of a rejection (`EffectBoundRejection`); its short Reason (`cause`), its Note (the path, such as the receiver Origin or the omitted Origin a dependent result names) and its Advice are formed at publication. The related locations are the target requirement (`requirement`) and, for a bound declared twice in one Contract, the bound declared earlier (`bound`); restating an ancestor's bound is valid and reports nothing. The selector and Name of an effect item are declaration syntax, completed with the item and never reported on their own.
- **Bound violations** (SPEC §8.4.10.6). A conformance that a bound rejects keeps `IncompatibleContractImplementation_Kd` with the conformance's Self clause as subject, located at the first violating effect in the implementation's own body (the effect summary queues every node with the own-body syntax that reaches it). The Reason (`reason`) names the kind of effect and the bound: an environment effect is named by the operation that obtained the authority (a mutable static access, an external operation, a foreign function call, a raw pointer read from an immutable static, a pointer made from an integer). The Note names the requirement and the declaring Contract and tells a definite violation (an environment effect, a conflicting result Loan) from an unknown effect counted as a conflict, adding why the Loans of earlier results were not excluded for a requirement call (SPEC §8.4.10.5): the call is not on a Field path of self in the own body, the body replaces a value on the path, an earlier result may keep an argument's Loans, or come from another requirement, another value or an untraced Field. Related locations: the effect itself when it lies in a callee or differs from the reaching own-body syntax (`effect`), the source or replacement that prevented the exclusion (`source`), the Self clause (`conformance`) and the effect item (`bound`). Advice keeps the guarantee; weakening the Contract is mentioned only when the bound is user source. The destruction pass after ownership analysis reports through the same record.
- **Requirement-call effects** (SPEC §8.4.10.4, §8.4.10.6). `CallEffectConflict_Kd` is located at the later call, once per call, with the Place keeping the Loan (`loan`) and the earlier call that created it (`call`) as related locations. Its Reason names the requirement and the Place; its Note states that no available bound excludes the access under the premises, never that a conflict occurs. A call that already has a record (such as `CallActivationConflict_Kd` for a result keeping the receiver borrow itself) gets none, so one conflict is reported once.
- **Origin relations** (SPEC §15.6.1, §15.6.5, §23.3.6.5; PLAN G56). One requirement, the required Origin relation (`Binding.OriginRelation`), covers every fit, declared relation and Type occurrence. A relation that is not proven fails only when Refuted, a finite Origin outliving a fixed one (`UnsatisfiedOriginRelation_Kd`, `Language`; an annotated local's omitted Origin is an inferred region, never fixed, so a chain into it is the located limit), or Unknown between fixed Origins (`UnprovenOriginRelation_Kd`, `Proof`); `static` over a body Origin is Proven, and any other chain with a body Origin at one end is Unrepresentable: the spec proves it and leaves it to region inference, but ownership keeps Loans only through a holder's written Origins, so ownership reports it as a located `UnsupportedOwnership_Kd` until region-inference edges exist (`Binding.JudgeOriginRelation`). A fit that holds structurally (`ReferenceTypes.StorageMatches`) but not in an Origin part is recorded as an `OriginRelationFact` at the value that supplies the longer end, never as `TypeMismatch_Kd` (`Binding.RecordMismatch`); a fit whose only unproven Origin part is a chain the judge accepts needs local-region inference and is a located `UnsupportedBinding_Kd`; its position is the first failed one in the order outer layer, Semantics target, slots, Type arguments, with `==` at an invariant position. Obligations left to ownership analysis, a local annotation's fit at its initializer and well-formedness (`wellFormed`) at its Type occurrence, are each a record (`OwnershipAnalysis.ReportUnprovenOriginObligations`), and the Loan, destruction and result checks proceed without them (rule 1); any other unchecked obligation, such as an unsolved inference, still stops the analysis. `Binding.OriginRelationFacts` forms the Reason (`relation`, `longer`, `shorter`, `source`, `destination`), the Advice and the related locations for every phase; a `borrow` or `omitted` end is related with the role `origin`, and the message names it as such (`DiagnosticOwner`, "the borrow `local@ref`"); a Function Type's per-call input, which has no name, is `omitted` at its input Type occurrence, and its Advice is to write the fixed Origin in that input (`Binding.OmittedInput`); an inferred local Origin is displayed by its Type occurrence; Advice for an anonymous function's input writes the Origin on that input, since anonymous functions have no origin clauses. The `closure` display `call result` is the shorter end of an inferred closure result over call-local storage (`Binding.CallLocalOrigin`, `CallResultOrigin`), and `call receiver` displays an environment atom, the longer end when an erased closure's result borrows its environment (`OriginDisplay`, `ReportOriginContract`); it is related at the header, from `func` through the parameter list (`FunctionKoto.HeaderEnd`), and the Borrow inside the returned value is found by `BorrowSource`. Control flow's `IncompatibleResult_Kd` judges only the structural part. The omitted-input Note of SPEC §15.4.3 is attached to the relation record. Pending (G56 U3/U4): a Binding-level relation is a node failure and still stops ownership analysis, so an independent Loan conflict in that body waits for it; call arguments still judge Origin parts during applicability; substituted clauses at calls (`declared`, role `relation`), the `Owned` condition of a common Function conversion (`UnsatisfiedConstraint_Kd`/`UnprovenConstraint_Kd` with `origin` and `member`) and `UnprovenOriginContract_Kd` for conformance and specialization are not reported yet. A common Function conversion with matching signatures is one `UnprovenOriginContract_Kd` (`Binding.ConversionContractFailure`, `FailedInstancePart`, published by `ReportOriginContract`): `CheckTypeUse` never decomposes a Function Type, the first failing member under the `CallableInstance` is reported with both ends instantiated, and an omitted end is related at its Type occurrence.
- **Inference boundaries and function references** (SPEC §10.5, §10.6; PLAN G10). A required slot that stays unsolved and appears in the fixed expected call signature of a waiting argument gets inference-boundary Advice: write that argument's Types (an anonymous function's parameter or result Types, a function reference's explicit Type arguments) or annotate the call's result. An ambiguous function reference shows the fitting candidates with their substituted signatures, relates their declarations and advises explicit Type arguments or an annotation. A slot that a per-call Origin leaves unsolved shows the slot and the corresponding parameter of the fixed expected call signature and advises wrapping the reference in an anonymous function. None offers a candidate, since the needed Types are unknown until the body is checked or a choice is made. A reference without a fixed expected call signature (SPEC §10.5) is `AmbiguousBinding_Kd` when two or more candidates remain, relating each with its callable signature, and `UnboundTypeArgument_Kd` (`Language`, Reason `parameter`, related `declaration`) when its one generic candidate has unbound slots; both advise an annotation or explicit Type arguments. Explicit arguments that no candidate takes are `NoApplicableOverload_Kd`, and a refuted Constraint for them `UnsatisfiedConstraint_Kd`. A generic reference that S cannot bind keeps `TypeMismatch_Kd` with a Note on slot binding; one whose Item is not proven Owned keeps it with a Note on the erasure condition. A method named through a value without a call (SPEC §7.3) is `BoundMethodValue_Kd` (`Language`, Reason `method`, related `declaration`), advising the Type-qualified reference or an anonymous function.
- **ObjectCallCompatible status** (SPEC §12.4.4.2, IMPL A.8; OCC-S and OCC-X, PLAN). A use whose status is not yet computed is neither Proven nor NotProven: it is a located `UnsupportedBinding_Kd` naming the selected implementation, the projection path and the unfinished verification.
- **Qualification** (SPEC §9.4, §23.3.6.9; PLAN P25). `QualificationRequired_Kd` (Error, `Language`) is located at the Name. The Reason holds the name, the namespace, `cause` (`Receiver` or `Inherited`), the searched Container `C`, whether the found declarations include an instance member and, for `Inherited`, the base declaration of the layer where the examination stopped. Related locations are the first found declaration (`declaration`) and, for `Inherited`, the base clause of `C` (`base`), which may lie in another fragment. Candidates are `Repair.Qualify` with `Selection` (§4.5); qualifiers not offered are described in Advice.

### 4.5. Repair candidates

A record offers repair candidates (SPEC §23.3.6.9) as part of its facts; a candidate is never inferred from Note or Advice prose, and no tool applies one unasked.

- **Recording.** A recorder passes `DiagnosticRepairFact` values to `Koto.Report` (`repairs:`) or `DiagnosticCollection.Report`: the kind (`RepairKind`), the kind's facts captured as values, the edits, and the relevant conditions it judged **verified** or **required** (`RepairConditionSet`). A refuted condition is never recorded: the recorder withholds the candidate and leaves the repair to the Advice. An edit is located through `Koto.Edit` or `DiagnosticCollection.Edit` (a span of the node's or the target's document and the replacement text); a source without text or a `compiler://` source is an invalid location. Candidates exist only on failing paths, so a check without diagnostics allocates nothing for them.
- **Catalog.** `RepairKind.tinyhand` defines each kind once, like the requirement table: its stable name (`Repair.<Kind>`), the title template over its facts, the facts as `name:Kind` and the relevant conditions. `RepairKinds` validates it when it loads; an anomaly faults every report that offers a candidate (`DiagnosticCatalogTest`). The implemented conditions (`Take`, `ExclusiveAccess`, `UsageLegality`, `Structure`) and the phrase templates of required conditions are fixed in `RepairConditions`; the vocabulary is closed by the SPEC, which also defines `Selection` for `Repair.Qualify` (`QualificationRequired_Kd`, not yet implemented, PLAN P25).
- **Recording boundary.** `DiagnosticCollection.Report` validates each candidate against the catalog (kind, fact count and kinds, each relevant condition in exactly one of verified and required, at least one edit, no candidate on a derived record), orders the edits by position with two insertions at one point joined and overlapping edits rejected, and orders the candidates by kind then first edit. A repeated report of one problem merges candidates like evidence: absent ones are taken, different ones conflict.
- **Finalization.** `DiagnosticOwner.Finalize` keeps the first candidates up to `DiagnosticLimits.Repairs`, omits whole a candidate with more than `RepairEdits` edits or more than `RepairText` characters of replacement text, and counts the omissions as `repair candidates`. `Describe` types and bounds the facts by the kind's schema, forms the title and the phrases of required conditions from the bounded values, and gives each edit its display range and the bounded text it replaces (`RepairEdit.Replaced`). The sources of kept edits enter the source table; omitted candidates add no entry.
- **Outputs.** The public form is `RepairCandidate` on `CheckDiagnostic.Repairs`; equality compares candidates. Commands render each candidate after Note and Advice (`Repair: <title>`, one ` = path:line:column: insert|replace|delete` line per edit, then ` = verified: …; requires: …`), the JSON form keeps every field, and the snapshot harness compares candidates as a difference of kind `repair` (§9.1).
- **Recorders.** Syntax: `TokenReader.ReplaceToken` and `InsertToken` (a misplaced `&&` or `||`, the former Origin keyword `from` in `Parser.ParseBorrowOriginSuffix`, a closer the parser expects at an insertion point) and `Tokenizer.ReportMissingDelimiter` (a closer missing at a line end); their records carry no Advice that repeats the edit. Control flow: `WarnUnnecessaryUnsafe` offers `Repair.RemoveUnsafe` with `Structure` verified for an Unsafe Block that is a statement of an indented body whose Body declares no Name and registers no `defer`, when the `unsafe` line holds nothing else, every Body line has a full level of space indentation and no string literal spans lines (`RemoveUnsafeEdits`); a declaring or deferring Body and an expression position refute `Structure`, and the other forms keep the Advice alone. Acquisition: a bare Place that Binding or the ownership analysis rejects for a missing `@move` offers `Repair.Transfer` at the Place (`Binding.TransferRepair`, `(*p)@move` around a dereference) with `Take` judged from the Place's path alone (`Binding.TakeJudgment`: verified for an owned path from a local, parameter or capture root and for a raw referent; refuted for a borrowed, published or shared path, a Property's storage, a Pattern candidate and an element outside a static Move Path; required otherwise) and `UsageLegality` required; the Advice states the borrow alternative where a reference may be meant and the remaining alternatives when `Take` is refuted, and nothing for a call argument, whose position acquires by value for every candidate (SPEC §7.3.1). Binding remembers the Place that set `transferRequired` or `lendingRequired` (`acquisitionPlace`, `NoteAcquisition`) so the record is located at the Place and names it. A missing `@uniq` or `@objuniq` offers `Repair.BorrowExclusively` with `ExclusiveAccess` verified, because the Place was already judged exclusively borrowable. A bare capture entry of a Non-Copy binding offers `Repair.Transfer` (`x@move`) and `Repair.Borrow` (`x@ref`). Discards: `WarnDiscard` offers `Repair.ExplicitDiscard` (`_ = `) for a discarded Result or try success value that is a direct item of an indented body and, for a Result whose error Type the enclosing function's Result takes (`FailureTargetFits`, SPEC §17.2.4), `Repair.PropagateFailure` (`_ = try `) first; no condition is relevant, the warning's Advice then names the alternatives the candidates cannot express, and the catalog's Advice describes every repair where no candidate is offered.
- **Tests.** `DiagnosticContractTest` covers finalization, order, limits, every contract violation and the command rendering; `DiagnosticOwnerTest` the JSON round trip; `SyntaxDiagnosticTest` the `Repairs` expectations of `syntax.json`; `UnnecessaryUnsafeBlockTest`, `OriginSyntaxDiagnosticTest`, `AcquisitionRepairTest`, `RawPlaceAccessTest`, `BorrowAcquisitionTest` and `DiscardRepairTest` the recorders above, including the forms that offer nothing; the verified cases apply the edits and check that the edited program is accepted. A recorder that adds candidates fixes, per reporting site, the refuted and required counterexamples of each condition.

## 6. Diagnostic contract and faults

- Violations (SPEC §23.3.6.7) go through one fault path. It discards the partial records and reports `CheckFaulted_Kd` with fixed text and the fault kind as its Reason. The fault path depends on neither the catalog nor ordinary formatting; its fixed values live in one place, and a test checks them against the catalog.
- A malformed repair candidate (§4.5) is a violation at the recording boundary: no edits or overlapping edits, an edit outside its source or in a source that is not a recorded input (`InvalidLocation`), a candidate on a derived record, an unknown kind, facts that do not match the kind, or a relevant condition judged neither or twice (`InvalidArgument`); two reports of one problem with different candidates conflict (`ConflictingProblem`).
- When an analysis throws while the diagnostic path is intact, the valid facts are kept, `CheckFaulted_Kd` (kind `Exception`) is added, and the result is Faulted. `CheckService` no longer formats its own records.
- An exception after the front end ran is the `Exception` fault on both paths, including an `InvalidDataException` of test discovery; only an invalid test configuration thrown before the front end blocks the check (`ProjectPreparationFailed_Kd`). The check entry decides Blocked from whether the front end ran (`CheckContext.Compilation`), never from the categories of the records.
- Cancellation and waiting for an unestablished input keep their current handling: both propagate as exceptions, and a cancelled check has no output.

## 7. Outputs

- **Commands** print a result once it is finalized; `Project.BuildTarget` has one finalization point for every return path, including an analysis exception, which it renders as the check entry's Faulted result (valid records plus `CheckFaulted_Kd`, or only the fault after a contract violation) before the command fails. Input preparation that ends without an Error reports its fallback in the shared front end, so the command and the check entry publish the same records; the check entry adds no fallback of its own, and a rejection that reaches finalization unexplained is the `UnexplainedRejection` fault on both paths. The project file is registered when its compilation is created, on both paths, so records naming it keep its consumption order. `kimi test` keeps diagnostics on standard error.
- **Language server.** `LspDiagnostic` equality is structural, including related information, because deduplication and repeat suppression compare values. The client's `relatedInformation` capability is read at `initialize`.
- **JSON.** `kimi check --Format json` (`CheckJsonOutput`) checks one unit through the shared check entry, as the language server does for the same inputs, and writes the `kimi.check/1` document (`CheckDocument`: schema, compiler identity, unit, outcome, acceptance, test presence, the source table with the SHA-256 of every input read through `HashingInputSource`, and the records with their candidates) to standard output alone; the rest of the command's output goes to standard error, a project that cannot be found, loaded or given one target is a Blocked document, and the exit code follows acceptance. The source-generated serializer (`DiagnosticJsonContext`) writes it with camelCase names and string enumerations; `docs/spec/schemas/check-output.schema.json` is its public schema. The snapshot harness (§9.1) keeps the result form as evidence.
- **Code actions** (SPEC §23.4.8). `WorkspaceCheck.Place` also places each record's candidates whose edits all lie in the record's own document as `LspRepair` values (the sent diagnostic, the title with any required phrases, the edits as text edits), kept per report URI in `UnitResult.Repairs`. The state owner keeps, per URI, the candidates every valid contributor agrees on (`Reconsider`, updated at every adoption, also when the payload is not resent) and answers `textDocument/codeAction` from them without a check: the request's range is matched against each sent diagnostic's range (half-open intersection, a point within a range with the end included, equal points), `context.only` without `quickfix` returns nothing, and so does a URI whose contributors are not all valid, so an edit, a reopen or a desynchronization clears the quick fixes until the next adoption. Each action is a `quickfix` with the sent diagnostic and one `TextDocumentEdit` at the document's current version. The capability is advertised only when the client declares code action literals and versioned document changes; without it the request returns nothing. `LspCodeActionTest` covers the capability, matching, `only`, validity and the restored version.

## 8. Migration rules (Diagnostics track)

The stages and their completion conditions are in [PLAN.md](PLAN.md). These rules hold while the track runs.

- **D1** changes no published diagnostic. Tests read diagnostics through one helper, so later stages change only that helper.
- **D2a** keeps the old start-offset suppression as a transitional filter: per old collection unit (the `CodeContext` collection name), by start offset, with a rangeless location counted as 0, keeping the first fact in recording order (partitions in phase order, then arrival). It is not improved. Contract checks that depend on problem keys (conflicting facts, unexplained rejection, undefined order) stay off; the others are on.
- **D2b** migrates recorders upstream first: lexing and parsing (with the recovery map), Binding, startup, control flow, ownership. The transitional filter drops only facts of recorders not yet migrated; facts of migrated recorders still occupy their offsets. Each recorder is rewritten once (rule 11). When the last recorder is migrated, the filter, `DiagnosticDependencyVisitor` and the `BorrowOriginHint` suppression are removed and every contract check is on. Done: every recorder reports problem identities, the filter and the former-collection units are removed, and a rejected result without a published Error is the `UnexplainedRejection` fault in both the check entry and command rendering. `BorrowOriginHint` now only supplies a Note and classifies a failure it explains as direct.
- A path never runs the old and new methods together, and no intermediate identity such as `(range, code)` is introduced.
- Explanations are bounded from the start.
- **D5** (syntax forms, §4.4) migrates the parser's reporting sites region by region: expressions, Types, bodies, line ends, closers and Names first (S1); declarations, members, parameters, patterns, compile-time directives and Origins next (S2); then cause propagation for every partial node (S3) and the evaluation (S4). The thirteen legacy syntax codes are gone: S1 removed the seven whose last site it migrated (`MissingExpectedToken_Kd`, `MissingComma_Kd`, `UnmatchedToken_Kd` and the four `Unmatched*_Kd`); the six that still had sites (`UnexpectedToken_Kd`, `IncompleteSyntax_Kd`, `TokenMismatch_Kd`, `UnexpectedTrailingToken_Kd`, `IdentifierExpected_Kd`, `EmptyExecutableBlock_Kd`) were `[Obsolete]`, with CS0618 disabled only in files that still reported them, until S2 unit 3 migrated the last sites and unit 4 removed the codes, their catalog entries and the pragmas. A site is rewritten once into a form; a form that no corpus case reaches is not added, and a site that no source reaches (the tokenizer closes every block and interpolation, and ends a numeric member Name at its digits) is removed rather than migrated. An implementation limit is a `Resource` code (`ForBindingLimit_Kd`), not a form. A specific code with its own explanation (`OriginSchemaRelation_Kd`, `OriginBindingSetName_Kd`, `OriginBindingSetTarget_Kd`, `LegacyBorrowOrigin_Kd`, `CallableOriginList_Kd`, the compile-time switch codes) is kept when it states a rule rather than a bare expectation. A code leaves the catalog, and a pragma its file, with the last site.
- **Recovery of a failed declaration.** A misplaced or malformed part that a later phase would otherwise judge again is removed from what that phase sees, or the node is recorded as a recovery: a modifier or attribute without a declaration skips its line and the indented body it would have introduced (`Parser.SkipDeclarationLine`); a malformed attribute attaches to nothing; a struct with several bases keeps the first; a setter with a result Type other than `()` keeps the Unit result; a `$require` with a malformed list keeps its condition and a recovery message; a binding, Property or parameter without its Type annotation gets a recovery Type, so its uses rest on the Error; an enum without a body, a computed Property without `get`, a renamed or defaulted receiver, a specialization without Type arguments, a Property whose accessor line names neither `get` nor `set`, a requirement accessor with an access modifier and a constructor whose initializer does not name `base` record the declaration as a recovery (`CodeContext.RecordRecovery`), so Binding's own check of it is derived and ownership analysis skips its body. A decoration that leaves the declaration checkable, such as `public` on a specialization, records nothing, so independent problems stay visible. `Koto.Unexpected` reports a node as misplaced, `Koto.Expected` reports a form expected where a node stands (its first source line is what was found), and both return the key; the caller decides whether the node is a recovery. Unit 3 adds: an `origin` clause after an accessor or executable item is dropped; a Constraint prefix whose subject the declaration does not permit stays a Constraint of the function (SPEC 7.4) recorded as a recovery, and a `length` slot outside a function's Type parameter list stays in the list, so Binding's own checks of the function and of the declaration's formation still follow (S3); a `during` line in a body, a nested if expression and a `$` prefix on a call that is neither abort nor tryWrite are recorded as recoveries; a `?` on a Semantics shorthand, `move`/`copy` as a Semantics prefix, an annotated adaptation borrow layer, a literal, bare-Name or empty-payload case Pattern and an `init` reference without `(` become recovery nodes with the Error as their cause.
- **Recovered expressions.** Binding checks an expression node that the recovery map names on its operands alone and completes it without a Type, so every check of it, including the overload selection of a call whose argument it is, rests on the syntax Error (one rule in `BindNode`; it replaced the per-kind cases for chained comparisons, jumps and labels). A literal kept as a recovery, such as a positional argument after a named one, is bound this way instead of being fitted after selection. Each unit's snapshot differences are of the kinds code, location and text; a record that disappears is reviewed as a duplicate or a cascade, never counted as an improvement by itself.
- **S3 (cause propagation).** Binding derives every failure that rests on a recovery node, whatever its kind, and links the declaration-level checks that read a recovery part (§4.3). A recovery Constraint keeps an Error constraint and binds none of its parts; a `length` slot in a nominal header is a recovery kept in the list; an associated Type application keeps a recovery parameter; the condition evaluator and the startup check consult recoveries and omitted declarations. Unit 2 adds the parser-side rules of §4.4: one problem per insertion point, closers the tokenizer reported, an orphan `else` and a missing argument comma. Unit 3 closed S3: generalizing the control-flow rule to every recovery node hid the independent target check of a jump with a recovered operand, so later phases keep deriving per check; the nested-struct Origin and Constraint failures under a header with a `length` slot proved independent of the slot (they appear without it), so no further `InvalidDeclarationContext` link was needed. No corpus case publishes a non-syntax Error that is not independent.

## 9. Evaluation

### 9.1. Snapshot harness

One harness checks a fixed corpus through the check entry: milestone programs, rejection fixtures, examples and mutation cases. It writes normalized records, outcomes and acceptance as JSON under `artifacts/verify/`, and classifies differences against a baseline by kind: case, acceptance, code, severity, attribution, location, text, repair (a changed repair candidate) and order. Timing belongs to the separate measurements (§9.4). A stage lists the kinds it intends; any other difference needs review.

### 9.2. Mutation tests

- Mutate a milestone program that passes, or a part verified independently. Change a copy in memory or under `temp/`, never the original, and confirm that the edited text is unique. An unfinished program with existing errors is never a single-error base.
- A case records its base source, effective configuration, change, intended problem and expected public records. Expectations are written independently of the generators.
- Cases cover definitions and recorders, prerequisites and cascades (including recovery), error state and invalidation, outcomes and faults, locations and snapshots, outputs and limits.
- Compare codes, requirements, Reasons and locations. Full-text comparison is limited to a few display tests, and people review underlines against explanations. A lower diagnostic count is not a goal.

### 9.3. Input relations

- Adding a blank line outside strings and documentation comments changes positions only, including blank and comment lines after a body (`DiagnosticRelationTest`).
- For the same check, input and prerequisites, adding an unrelated problem leaves existing primary records and explanations unchanged.
- Changing wording alone leaves identity, suppression and order unchanged, and the change of the published values is detected.
- Reordering inputs whose order the SPEC leaves free leaves records and order unchanged. The compiler has no hook for reordering its own work.
- Changing limits never changes a problem's survival, category or acceptance.

### 9.4. Performance

- Paths without diagnostics gain no per-node allocation or string formatting; only published records are formatted.
- Targets: resolving causes in O(F + E) for F facts and E prerequisite references, ordering in O(D log D) for D published records, explanations in O(D × K) for a per-record limit K.
- Compare time, allocations and retained size before and after on the same machine, configuration and input: the existing warm zero-allocation probes, front-end timings of milestone programs, and the LSP measurements. A reproducible regression is fixed; an unmeasured improvement is not claimed.
- Analysis is single-threaded and each compilation owns its diagnostics, so recording needs no lock.

## 10. Diagnostic development workflow (detail)

AGENTS.md lists the required steps. This section gives their detail.

- **Triggers.** A change that adds or modifies a diagnostic, a check that reports diagnostics, recovery or suppression, or diagnostic publication and presentation. Reusing an existing code does not exempt a new reporting path. A reported confusing, missing or misleading diagnostic also starts the cycle.
- **Capture.** A minimal reproducer or a mutation of a known-valid program (§9.2), with the intended failure and independently written expectations. Confirm that the case reaches the intended check; an unrelated earlier error is no evidence. Add a valid counterpart to catch false positives.
- **Review.** Code, severity, category, primary range and label, the factual Reason, related locations, Note and Advice. The message explains the problem on its own; essential facts survive limits; established facts are separated from suggested intent, and advice states its conditions. Inspect representative CLI and language-server output for changed user-visible behavior, including how underlines match explanations.
- **Interactions.** Focused cases for the relevant prerequisites and recovery, independent errors and the input relations (§9.3). The cause stays explained, independent problems stay visible and acceptance does not depend on suppression or presentation. Cover the affected output adapters; a future CSP adapter keeps the same records. Choose cases by the change's impact instead of repeating every test for each diagnostic.
- **Repair and repeat.** Fix missing evidence, misleading explanations, wrong ranges or unwanted cascades at their source, rerun the affected checks and inspect the revised output. Never weaken expectations to match current output, and never count fewer diagnostics as an improvement. Keep the reproducer and its expectations as regression tests.
- **Evidence.** Follow the repository verification workflow; measure (§9.4) when a changed path is hot or a milestone completes. Record the reviewed behavior, intended public-output changes, verification results and remaining uncertainty in commits and `artifacts/verify/`.
- **Completion.** A unit is complete only when its problem is explained accurately and understandably at the right locations, the applicable interaction and output checks pass, and every quality defect observed in the unit is repaired and verified again. Passing tests alone does not establish clarity. Otherwise record the unresolved condition and the next action, without marking the unit complete or claiming support.
