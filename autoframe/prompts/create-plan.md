# PLAN.md作成・更新用プロンプト

自動実行前に、ユーザーがCodexへ依頼するためのプロンプト。runnerのWorker段階では使用しない。

## 入力

ユーザーから、対象プロジェクト、目的、対象範囲、望む完成状態、対象外・制約を受け取る。既存PLAN.mdの更新なら、変更したい内容も使う。

## 作成手順

1. autoframe.md、適用されるAGENTS.md、対象プロジェクトの構成・参照資料・既存の検証手順を必要範囲だけ確認する。
2. 目的を、対象が有限で結果を確認できる完成条件にする。調査の完了と不具合修正の完了を区別する。
3. work_scope、必要な検証入力、生成物の書込範囲、環境識別を具体化する。存在や使い方を確認できないコマンド・資料を確定事項として記載しない。
4. 要求から判断できる分割・順序・検証方法は具体化する。目的、必須条件、変更可能範囲を左右する不足だけ質問する。通常の詳細化に繰り返し確認を求めない。
5. 仕様のマーカーに囲まれた単一のJSONブロックを持つPLAN.mdを作成する。tasksとmilestonesは有用な場合だけ記載し、詳細すぎる実行手順は自動実行時のPlanに任せる。
6. JSON構文、必須フィールド、一意ID、参照先、依存の循環、完成条件との対応を検査する。未確認の検証を実施済みと報告しない。

## 編集範囲と簡潔さ

- ユーザーが指定したプロジェクトのPLAN.mdだけを作成・更新する。製品の修正、テスト実行、runnerの起動、認証・設定変更は始めない。
- 既存PLAN.mdがある場合は内容を確認し、依頼された変更と整合に必要な修正だけを行う。project_id、既存ID、依頼外の要件を不用意に変えない。
- 適用される上位の指示・制約を維持し、ユーザーの要件を達成しやすい条件へ緩めない。
- PLAN.mdにはユーザー定義だけを書く。status、evidence、findings、runner用revision、実行履歴は含めない。
- 定義の重複、資料・コードの転載、長い背景説明を避ける。条件の具体性や未解決の判断事項を削って短くしない。
- 必須の判断が残る場合は、実行可能な完成版と称して保存しない。具体的な不足を質問する。

## 完了報告

保存先、目的・完成条件の要点、行った形式検査を短く報告する。PLAN.mdの全文や作成過程を繰り返さず、自動実行は開始していないことを明示する。
