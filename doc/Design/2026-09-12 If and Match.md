# ifとmatchの共通仕様

ifとmatchを「選択式」と呼ぶ。本体の構文には違いがあるが、結果の供給・型検査・yieldの規則は共通とする。値が必要かどうかは使用位置で決め、本体の改行や要素数では決めない。

本書は設計仕様をまとめたものであり、SPEC.mdへの反映は別途行う。

## 1. 本体の構文

本体は、同じ行で式を開始する形式と、次行からインデントする形式を持つ。

| 構文 | 同じ行の式本体 | 次行のインデント本体 |
| --- | --- | --- |
| if／else if／else | ヘッダーに続けて `=> expression` | ヘッダーの後に記号を付けず改行 |
| matchアーム | `Pattern [if guard] => expression` | `Pattern [if guard] =>` の後で改行 |

表の角括弧は省略可能を表す。式本体は1つの式、インデント本体は1つ以上の式・文・宣言からなる。if・matchとも `: InlineStatement` は認めない。

同じ行の本体に任意のInlineStatementは認めない。let・var・defer・requireなどの文を書く場合はインデント形式を使う。yield・returnなど、既存の式文法に含まれる転送式は同じ行にも書ける。

```kimi
if ready
    start()
else if waiting
    showWaiting()
else
    stop()

let price = if member => 80 else => 100
```

matchの `=>` は、同じ行か次行かによらずアーム本体の開始記号である。ifの `=>` は同じ行で式本体を開始するときだけ使い、直後の改行は構文エラーとする。開始済みの式は、括弧内などで通常どおり継続できる。

`=>` の有無は値の破棄や供給を意味しない。1つの選択式の中で両形式を混在できる。本体はソース上で非空とし、空行・コメントだけでは本体にならない。セミコロンで複数文を連結しない。

## 2. ifの動作

ifは条件を順に評価し、最初にtrueになった本体を実行する。どれもtrueでなければelseを実行する。条件の正常な結果はboolでなければならない。

- Statement contextではelseを省略できる。条件不成立なら何もせずUnitで完了する。
- Value Contextでは最終elseが必須である。
- else ifの連鎖は、全体で1つの選択式として扱う。

## 3. matchの動作と網羅性

matchは1つ以上のアームを持つ。対象を一度評価・取得し、アームを上から順に調べる。Patternと、指定されていればガードの両方を満たす最初の本体を実行する。実行後に次のアームへ進むことはない。

```kimi
match event
    .Close if ready =>
        close()
    _ =>
        ()
```

`.Close if ready` の `if ready` がガードである。Patternが一致した場合だけ評価し、正常な結果はboolでなければならない。falseなら次のアームを試す。

**matchは常に網羅的（exhaustive）でなければならない。** ガード付きアームは、`if true` も含めて網羅性の証明に数えない。本体の結果型や非終了性による例外も設けない。証明には既存のPattern網羅性規則を使う。

`_` は残りの値に一致する通常のWildcard Patternであり、本体も必須である。何もしない既定処理は `_ => ()` と書ける。上の例のインデント形式と同じ意味を持つ。

## 4. 結果を使う場合・捨てる場合

| 使用位置 | 本体の結果 | 選択式全体 |
| --- | --- | --- |
| Statement context（Discard Context） | 結果を捨てる。結果供給も本体間の結果型一致も不要 | 正常終了時はUnit |
| Value Context | 正常完了する全到達経路で、共通の結果型Tに適合する値を供給する | Tの値を返す |

独立した式文はDiscard Context、初期化子・引数・条件・演算子や転送のオペランドなどはValue Contextである。コンテキストは構文上の位置で決め、最適化や後から値が使われるかどうかでは変えない。

式本体やyieldがあるだけでは、結果要求を発生させない。Statement contextなら、選ばれた呼出しが異なる型の値を返してもよい。

```kimi
// check() はbool、log() はUnitを返すとしても有効
if ready => check()
else => log()
```

Unitが必要なValue Contextは、Discard Contextとは異なる。その場合もUnitの結果供給が必要であり、結果を供給しない正常終了はエラーとなる。

## 5. 末尾式と暗黙yield

Value Contextでは、本体の最後の直下要素が式なら、その結果を暗黙にyieldする。1行形式では、その1つの式が末尾式になる。末尾以外の直接の式はDiscard Contextで評価する。

```kimi
// calculate()、calculateOther() はi32を返す
let result: i32 = match value
    .A => calculate()
    .B =>
        prepare()
        if ready
            calculateOther()
        else
            0
    _ => 0
```

`.B` の末尾式はif全体なので、そのifもValue Contextになる。内側の各本体の末尾式がifの結果を供給し、その結果がmatchへ渡る。

ifでも、本体の形式を変えて結果の意味は変わらない。次の2つは同じ値を返す。

```kimi
let price1 = if member => 80 else => 100

let price2 = if member
    80
else
    100
```

末尾式は条件付きコンパイル後の構文で決める。宣言・文や到達不能な要素を飛び越えて「最後に使えそうな式」を探してはならない。末尾が宣言などで結果を供給せず正常終了する経路はエラーとなる。Unitなら末尾に `()` を置ける。

利用可能な期待型Tは末尾式へ伝える。Statement contextでは末尾式もDiscard Contextとし、期待型Unitを押し付けない。内部の引数・初期化子などは、それぞれのValue Contextを保つ。

暗黙yieldはif・matchの本体に適用する。関数・ループなどの本体は、それぞれの既存の結果規則に従う。

## 6. ラベル付き選択式と明示yield

### 6.1. 構文とラベルの範囲

if・matchの直前に `Label:` を付け、明示yieldの転送先として名前で指定できる。

```text
Label: if ...
Label: match ...
yield expression
yield expression to Label
```

`Label:` とif／matchは同じ物理行に置く。ラベルは選択式そのものに名前を付け、追加のブロック・スコープ・評価コンテキストを作らない。else ifの連鎖では全体に1つのラベルが付き、個々のelse if／elseやmatchアームには付けない。

ラベル名は既存のName規則とラベル名前空間に従う。同じ関数内で有効範囲が重なる同名ラベルはエラーとする。選択式のラベルは各本体の内部だけで参照でき、自身の条件・match対象・ガードでは参照できない。外側のラベルは、その有効範囲と転送境界の条件を満たす限り、内側の選択式のヘッダーからも参照できる。

`to` はyieldの値の式に続く位置でだけ認識する文脈キーワードとし、直後のNameはラベルとして解決する。`to Label` は値の式の終了と同じ物理行に置く。名前付きyieldのオペランド内に別の選択式・転送式を書く場合は、それを括弧で囲み、`to` の所属を明示する。

```kimi
yield (if ready => 1 else => 2) to resultLabel
```

### 6.2. 転送先の決定と結果の検査

明示yieldは、対象の選択式を途中で終了して値を渡す。値の省略は認めず、Unitは `yield ()` または `yield () to Label` と書く。

| 形式 | 転送先 |
| --- | --- |
| `yield expression` | 最も内側のif／match |
| `yield expression to Label` | 指定名を持つ、自分を囲むif／match |

転送先を先に確定し、その選択式の評価コンテキストに従って検査する。Value Contextなら値は結果型Tに適合し、利用可能な期待型Tをオペランドへ伝える。Statement contextなら値を捨て、結果要求や本体間の型一致を発生させない。どちらの場合もオペランド自体はValue Contextで評価する。

型不一致・else不足・網羅性不足などを理由に転送先を付け替えてはならない。暗黙yieldは、末尾式が属する本体の選択式へ結果を渡し、ラベルを探索しない。

requireは選択式の境界を作らないため、次のyieldはmatchを終了する。

```kimi
let result: i32 = match value
    .A =>
        require ready else yield 0
        calculate()
    _ => 0
```

### 6.3. 入れ子から外側へ結果を渡す

```kimi
var result: i32 = labelA: match a
    .B =>
        if x => yield 1 to labelA
        else => yield 2 to labelA
    _ => 0
```

どちらのyieldも内側のifを抜け、外側のmatchを終了する。内側のifには正常完了経路がないため型はNeverであり、そのif自身の結果供給は不要である。matchは1・2・0のいずれかを結果とする。ラベルを付けても網羅性は必須である。

ifにも同じ規則でラベルを付けられる。

```kimi
let result: i32 = selection: if ready
    if cached
        yield 10 to selection
    calculate()
else
    0
```

readyがtrueのとき、cachedもtrueなら外側のifを10で終了し、calculate()は実行しない。cachedがfalseならcalculate()の末尾結果を返す。`to selection` を省くとyieldは内側のifだけを終了し、その後calculate()を実行する。readyがfalseならelseの0を返す。

末尾で内側の結果をそのまま渡すだけなら、ラベルは不要である。

```kimi
var result: i32 = match a
    .B =>
        if x => 1
        else => 2
    _ => 0
```

Statement contextの指定先にも転送できる。次の例は、stopEarlyがtrueならmatchを終了してtrueを捨て、falseならhandle()を実行する。trueとhandle()の結果の型をそろえる必要はない。

```kimi
handling: match a
    .B =>
        if stopEarly
            yield true to handling
        handle()
    _ => ()
```

### 6.4. 転送境界と禁止事項

名前付きyieldは、途中のif／match、通常のブロック、ラベル付きブロック、unsafeブロックを越えられる。ただし、ラベルの有無によらず、転送先に達する前に関数・ループ・deferの境界に当たればエラーとする。境界は各構文の本体の内部でのみ働く。選択式自身の条件・対象・ガードには、その選択式のyield転送先境界を設けない。

指定できるのは、自分を囲む有効な選択式のラベルだけである。次はエラーとする。

- 未定義・範囲外・兄弟・内側のラベルを指定する。
- yieldの転送先として、通常のラベル付きブロックやループを指定する。
- 選択式のラベルをexit／continueの転送先にする。
- ラベルを値として参照したり、本体の途中へ飛び込んだりする。同名の変数がある場合の値参照は、別の名前空間で通常どおり解決する。

```kimi
let result: i32 = selection: if ready
    for item in items
        yield 1 to selection // エラー：ループの境界を越える
    0
else
    0
```

ループ内で作った選択式へ、そのループの境界を越えずにyieldすることはできる。名前付きexit／continueの既存規則は変更しない。

## 7. 改行・括弧・スコープ

- ifの条件は、条件内部の括弧の外にある `=>` または改行で終了する。条件を複数行にする場合は括弧内で継続し、括弧の外で始まるドット継続などで条件を延長しない。外側の呼出し括弧などの中でも、このヘッダー終端規則を適用する。
- ifの式本体では `=>` と式の開始をヘッダー終端と同じ物理行に置く。インデント本体では `=>` を書かず、次の有効行から本体を開始する。
- matchアームの `=>` はPattern・ガードの終端と同じ物理行に置く。本体は同じ行、または次の有効行から開始する。
- インデント本体は、構文開始時の構造上の基準より1段深くする。別行のelse／else ifは最初のifの基準にそろえる。
- 括弧内では、その位置に必要な継続インデントを基準とする。ifの文字位置や、条件内部の改行で基準を変えない。
- ヘッダー行から始めた式の後のelseは、その式の終了行または次の有効行に置く。インデント本体の後では、本体終了後の次の有効行に置く。間に別の項目を挟まない。
- 条件・matchの対象・ガード・同じ行の本体に別のif／matchを埋め込む場合は、その選択式全体を括弧で囲む。ラベル付きならラベルも括弧に含める。オペランドや引数の内部にも適用し、入れ子の本体内部は個別に検査する。ヘッダー内のラベル付きブロックなど、本体を持つ他の構文にも括弧を要求する。

```kimi
let result = if a => (if b => 1 else => 2) else => 3

if (
    ready && permitted
)
    start()
```

elseは括弧の境界を越えず、対応するifに結合する。結合先がなければ構文エラーである。グループ化の括弧は評価コンテキストと期待型を保ち、スコープや転送先を追加しない。

ガードは外側の `=>` で終了する。区切り内の記号とは区別し、改行・インデントだけで本体へ読み替えない。式の継続は既存のレイアウト規則に従う。

1行形式と、同じ式だけのインデント形式では、本体スコープ・束縛・一時値の寿命・結果規則を同じにする。フォーマッタは構文とelseの所属を保存し、ifの両形式を変換するときは `=>` も挿入・削除する。matchでは `=>` を維持する。複数行のifは、必要ならラベルを先頭に置き、独立した行で開始する書式を推奨する。

## 8. Never・型検査・Scope Exit

外側へのreturn・exit・continue・名前付きyieldや非終了処理など、対象の選択式を正常完了させない経路には、その選択式の結果を要求しない。自分を対象とするyieldは、自分の結果を供給する経路として数える。正常完了経路が一切なければ選択式の型はNeverとなる。結果不足をNeverとして扱ってはならない。

yield自体がNeverでも、対象へ届ける値は検査する。到達不能コードも局所的な構文・名前・型・転送の検査を受け、結果型Tが利用可能なら既存規則に従って結果の適合性も検査する。

明示・暗黙yieldは、結果を通常のCopy／Move規則で確保してからScope Exit処理を行い、結果を届ける。名前付きyieldでも、転送により離れる各スコープのdefer・破棄を既存の順序で実行する。deferの実行を伴うことと、その本体から外へ転送することは異なり、後者は禁止する。

オペランドの評価が別の転送や非終了処理で終われば、元のyieldは実行されない。cleanupが正常完了しなければ結果は届かない。借用・破棄・Resultの破棄警告などの既存規則は維持し、ラベルを付けても局所値への借用を不正に外へ持ち出せない。

```kimi
let result: i32 = selection: if ready
    defer: cleanup()
    if cached
        yield 10 to selection
    calculate()
else
    0
```

cachedがtrueなら10を確保し、cleanup()と必要な破棄を実行してから外側のifを10で完了する。calculate()の末尾結果を返す経路でも、同じスコープ終了処理を行う。

## 9. 他の本体構文との関係

for・while・loopのブロック本体はコロンなしのインデント形式を維持する。unsafe・deferは既存の `:` による1行・複数行形式、requireは既存のelseによる失敗本体を使う。これらのInlineStatement内では、内部の式も含めて同じ物理行で完結させる制約を維持する。

ifのインデント本体はfor・while・loopと同じく記号なしとし、式本体だけ `=>` を使う。matchアームは常に `=>` を使う。`Name:` は構文にラベルを付け、unsafe・deferの `:` はそれぞれの専用構文として扱う。関数やアクセサーの既存の `=>` は、それぞれの仕様に従う。

## 10. 診断とSPEC.mdへの反映

| 誤り | 診断・修正案 |
| --- | --- |
| if／else if／elseの `=>` 直後からインデント本体を開始 | `=>` を削除する。式本体を意図したなら同じ行で式を開始する |
| matchアームの `=>` がない | Patternまたはガードの後に `=>` を追加する |
| Value Contextの結果不足 | 末尾式かyieldで結果を供給し、ifの最終elseも確認する |
| 内側のyieldで外側へ結果を渡すつもりだった | 実際の転送先を示し、末尾式による受け渡しかラベル付き選択式と `to Label` を提示する |
| ラベルが見つからない、種類が異なる、境界を越える | 指定名・必要な対象種別・越えられない境界を示す。別の対象へ自動で付け替えない |
| 名前付きyieldの結果型が不一致 | 指定先の選択式と期待型を示す |

SPEC.mdへの反映時は、§2のレイアウト・文脈キーワード、§14.4のラベル、§14.5の転送構文・探索、§14.7〜§14.9のif・match・結果検査、および付録Fの文法を一括して更新する。旧来の「式本体やyieldの存在で結果要求が発生する」規則を残さず、使用位置に基づく共通規則へ置き換える。
