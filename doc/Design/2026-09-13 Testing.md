## 1. 基本方針

### 1.1 四つの共通規則

1. **製品とテストの依存は一方向。** テストは製品を参照できるが、テストの追加で製品の意味を変えない。
2. **検証処理を共通化する。** `$expect` と `$require` は条件の評価・失敗記録を共有し、失敗後の継続先だけを変える。
3. **ケースを初期化から回収までの単位とする。** 1 ケースにつき新しい子プロセスを使い、上限付きで並列実行する。
4. **診断の評価と保存を分離する。** 評価順序・所有権・cleanup を維持し、保存量・通信待ち・回収時間に上限を設ける。

Swift Testing の宣言・検証・診断を参考にするが、新しい例外機構、汎用マクロ、言語のスレッド機構は導入しない。

### 1.2 用語と最小例

| 用語 | 意味 |
| --- | --- |
| テスト定義 | `#Test` を付けた関数 |
| ケース | 個別に実行し、結果を持つ単位。初期版は 1 定義につき 1 ケース |
| ランナー | 子プロセスの起動・監視・回収と結果集計を行う親側の処理 |
| テスト実行ファイル | 指定されたケースを実行する生成済みの native 実行ファイル |
| cleanup | スコープ退出に伴う `defer` と値の自動破棄 |

```kimi
group Arithmetic
    func add(left: i32, right: i32) -> i32
        return left + right

    #Test
    func addition()
        let actual = add(1, 2)
        $expect(actual == 3)
```

`kimi test` で `addition` を発見・実行する。`#Test` 関数は通常ビルドから除外する。

## 2. 宣言とビルド

### 2.1 宣言の所属と依存方向

宣言には **製品用／テスト用** の所属を持たせる。通常ソースの `#Test` 関数と、テスト専用ソースの宣言はテスト用。それ以外の通常ソースの宣言は製品用とする。関数の内部宣言は外側の所属を引き継ぐ。

```text
通常ソース
  ├─ 製品用の関数・型 ──→ 製品用の宣言・依存だけを参照
  └─ #Test 関数 ───────→ 製品用とテスト用を参照
テスト専用ソース ──────→ 製品用とテスト用を参照
```

テスト専用ソースと依存はプロジェクト設定で明示する。`tests` などのファイル・ディレクトリ名自体に特別な意味を与えない。通常ソースの無印ヘルパーは自動除外しない。

製品用の名前解決、オーバーロード選択、型、配置、適合、特殊化、初期化・破棄規則を、製品入力だけで確定する。テスト用宣言はこの確定結果を変更できない。製品の generic 本体をテストから具体化する場合も、製品側の定義時の名前解決と通常の具体化規則を維持する。

テスト用関数を製品と同じ Container に置くことはできるが、製品側の候補集合には加えない。既存の重複宣言・可視性規則は維持する。製品型への Field・基底型・適合などの追加によって確定済みの意味を変えることはエラーとする。テスト専用型には通常の型定義規則を適用する。

生成ソースにも所属を適用する。製品の生成処理を先に確定し、テスト用の生成処理はその結果を変更しない。製品用の生成処理へテスト専用入力を混ぜず、生成された `#Test` もテスト用として分離する。

```kimi
// 通常ソース。
group Product
    func calculate() -> i32
        return onlyInTests() // エラー: テスト用宣言では解決できない。
```

```kimi
// テスト専用ソース。
group Product
    func onlyInTests() -> i32
        return 42
```

### 2.2 `#Test` の対象

初期構文は引数なしの `#Test`。対象は次のすべてを満たす関数とする。

| 項目 | 条件 |
| --- | --- |
| 種類 | 本体を持つ safe な通常の名前付き関数 |
| 引数・receiver | なし。デフォルト値で省略できる引数も対象外 |
| generic・Origin | 関数と祖先 Container に未確定のパラメーターがない |
| 戻り値 | Unit。注釈省略または `-> ()` |
| 宣言位置 | ソース直下、または非ジェネリックな `group`・`rootgroup`・`struct`・`enum` 内 |
| 対象外 | foreign import、明示的特殊化、別関数内のローカル関数、capture が必要な関数 |

`struct` 内は receiver のない型関数に限り、インスタンスを自動生成しない。ソース直下の関数は SourceDocument 内の名前解決を維持する。重複した属性、不正な対象・シグネチャはエラーとし、黙って登録を省かない。

通常ビルドでも属性・宣言構文と構文だけで確認できる対象条件は検査するが、テスト関数の名前解決・本体の型検証・コード生成は行わず、テスト専用依存を要求しない。完全な対象検証はテスト用ビルドで行う。既存の `#if` による除外規則は維持する。

ユーザーコードから `#Test` 関数を直接呼び出したり、関数値として取得したりすることは禁止する。共通処理は通常のヘルパーに分離する。非公開テストを呼び出す権限は生成されたランナー起動処理だけが持ち、テスト本体のアクセス権を広げない。

### 2.3 discovery と成果物

```text
製品入力の選択・生成・意味の確定
  → テスト入力の選択・生成・追加
  → #Test の発見と全テスト宣言の検証
  → 検証済み一覧
      ├─ --list: 一覧を出力
      └─ 実行: 全ケースを含む実行ファイルを生成・再利用
                 → 選択したケースだけを起動
```

対象プログラムの初期化やテスト関数を実行せず、コンパイル時に発見する。条件付きコンパイルで除外された定義は登録しない。依存ライブラリのテストは自動収集せず、明示的に対象にしたプロジェクトを調べる。

フィルターは実行対象の選択に限る。対象外のテストも通常の型・所有権・制御フロー検証を受け、コンパイルエラーを隠さない。`--list` は検証済みの宣言情報から取得でき、codegen・リンク・子プロセス起動を要求しない。

通常とテスト用の成果物・manifest・キャッシュは区別する。製品解析は、ソース・生成結果・依存・対象・設定・compiler が適合する場合に共有できる。意味の確定は二度のフルコンパイルを要求しない。テスト用設定で製品の条件を変える場合は、その条件を結果に明示し、異なる条件の解析を流用しない。

実行ファイルと静的診断テーブルは、実行中に置き換えない不変の成果物として扱う。全ケースを含む同じ成果物を使い、フィルター変更やケースごとの再コンパイル・再リンクを避ける。

### 2.4 Application

テスト用ビルドは専用エントリポイントを使う。製品の明示的な `main` は通常の関数として検証するが、自動実行しない。

テストに取り込むソースにトップレベル実行文や `let`・`var` が残る場合はエラーとする。対象処理を関数へ移すか、起動用ファイルを入力から明示的に除外する。実行文を黙って捨てたり、テスト前に実行したりしない。

```kimi
group App
    public func calculate() -> i32
        return 20 + 22

    #Test
    func calculation()
        $expect(calculate() == 42)

public func main()
    if App.calculate() == 42
        ::Core.writeLine("Application started")
```

`kimi test` は `App.calculation` を実行し、`main` の出力は行わない。

## 3. 検証操作

### 3.1 構文と使用位置

```kimi
$expect(condition)
$expect(condition, message: "追加の説明")
$require(condition)
$require(condition, message: "前提条件の説明")
```

両操作は Composition Root の組み込み操作であり、差し替え可能な関数やマクロではない。最初の位置引数は bool、任意の `message:` は string 式。初期版では他の引数、generic 引数、末尾カンマを受け付けない。

正常継続時の型は Unit。独立した実行項目として使い、検証操作自体を別の式の引数・初期化式に埋め込まない。

| 操作 | 使用可能な場所 |
| --- | --- |
| `$expect` | テスト用の関数本体と、その中のローカル関数・Closure・`defer` |
| `$require` | `#Test` 本体と、その通常の分岐・ループ・`do` 内。別関数・Closure・`defer` の本体は除く |

所属は §2.1、失敗の帰属先は §4.1 に従う。製品用の関数へ検証操作を書き、テスト時だけ呼ぶ使い方は許可しない。

`$require` は置かれたテスト関数からの return であり、ヘルパーの奥から呼び出しスタックをまたいで脱出しない。通常の `require condition else ...` 文は変更せず、Option・Result の自動取り出しや型の絞り込みも追加しない。

### 3.2 共通の評価手順

```text
条件を一度評価し、bool と必要な診断用の値を確保
  ├─ 真 → 条件の cleanup → 継続
  └─ 偽 → 失敗を確定し、基本診断を報告
           → 条件の cleanup
           → 任意メッセージを評価・報告し、その一時値を cleanup
             ├─ expect  → 継続
             └─ require → 通常の関数 return と退出スコープの cleanup
```

基本診断の報告・省略は §5 に従う。条件が真の検証について、診断文字列・失敗レコード・成功イベントを生成しない。条件内部で別の検証が失敗した場合は、その失敗を別途記録する。

評価順序、短絡評価、オーバーロード選択、Copy・Move、Loan、破棄順序を維持する。条件の一時値は既存の bool 条件と同じ寿命境界で片付ける。失敗時だけのメッセージ評価を実際の分岐として解析し、そこでの Move や未初期化状態を後続の所有権解析へ反映する。

条件評価が転送・Abort・非終了になれば既存の動作に従い、未確定の真偽を検証失敗にしない。偽が確定した後は失敗を取り消さず、cleanup やメッセージ中の Abort・非終了は終了状態にも残す。

```kimi
group Checks
    #Test
    func continueAfterFailure()
        let actual = 4
        $expect(actual == 3)
        $expect(actual < 10) // 前が失敗しても実行する。

    #Test
    func stopAfterFailure()
        defer => ::Core.writeLine("cleanup")
        $require(false, message: "入力の準備が必要")
        ::Core.writeLine("この行には到達しない")
```

後者は失敗を記録して `cleanup` を出力する。cleanup 中の `$expect` 失敗は追加で記録する。Abort は既存どおり残りの cleanup を打ち切り、子プロセスを終了する。

### 3.3 メッセージの制御境界

メッセージは条件が偽の場合だけ一度評価する。通常の可視性・所有権に従い、条件内部の一時値へ特別にアクセスできない。

**メッセージ式から、その外側にある制御先へ転送してはならない。** 明示的な `return`・`exit`・`continue`・`yield` と、入れ子の `$require` が生成する return の両方を検査する。メッセージ内で完結するループや `do` の転送、内部で宣言・呼び出した関数自身の return は通常どおり許可する。転送先を確認する規則であり、暗黙の Closure 化や capture は行わない。

```kimi
group InvalidMessage
    #Test
    func cannotBypassRequirement()
        region: do
            $require(false, message: do
                exit to region // エラー: メッセージの外へ転送している。
            )
```

同じ境界を `$expect` と `$require` に適用する。Abort・非終了は転送先を持たず、既存の規則に従う。

### 3.4 値の観測と表示

値表示は、**元の式が評価された時点で得られた値**を使う。関数・Property・比較を再実行せず、右辺の副作用や cleanup の後に元の変数を読み直さない。短絡した部分は評価せず「未評価」として扱える。

初期の保存対象は bool と実装済み数値型を中心とし、外側の比較の左右などに絞る。表示目的の言語上の Copy・Move、Loan の延長、寿命変更は禁止するが、得られた scalar のビット列を compiler 内部の一時領域へ保存することは許可する。

安全に保存できない型は式・位置だけを表示し、値を省略したことを示す。任意のオブジェクト走査やユーザーの表示関数の暗黙呼び出しは行わない。比較の左右を自動で「実際値」「期待値」と決めつけず、式の名前または left・right で示す。

```kimi
// ready() と inspect() は bool を返す通常の関数とする。
#Test
func shortCircuit()
    $expect(ready() and inspect())
```

`ready()` が偽なら `inspect()` は診断のためにも呼ばない。

## 4. ケースの実行と回収

### 4.1 実行期間と帰属先

```text
ケースを割り当て、報告用の最小 runtime を準備
  → 有効なケースを設定
  → ユーザー初期化 / テスト本体 / cleanup / shutdown
  → 完了報告、ケースを無効化、子プロセス終了
  → 親がプロセス群・通信路・一時領域を回収
  → 結果確定
```

ユーザー初期化から shutdown 完了まで、許可された `$expect` はすべて同じケースに帰属する。static の初回アクセスによる初期化が本体や cleanup に入れ子で起きても、ケースを切り替えない。診断には初期化・本体・cleanup・shutdown の段階を付け、入れ子の段階は戻ったときに復元する。

初期化・破棄の必要性と順序は通常の規則に従う。テストのための先行初期化はしない。runtime 準備の失敗は親が起動・実行エラーとして扱う。有効ケースのない検証呼び出しは、条件の真偽にかかわらず誤用として扱い、成功・無視・別ケースへの記録にしない。

### 4.2 プロセス隔離と環境

同じ実行ファイルへケース ID を渡し、**1 ケースにつき新しい子プロセスで 1 回**実行する。ケース間で static 状態を共有せず、自動リトライはしない。対象が実行環境に対応していなければ実行エラーにする。

- 作業ディレクトリは対象プロジェクトのルートに固定する。
- ケースごとに固有の一時ディレクトリを提供し、終了後に親が回収する。
- 環境変数は実行開始時の親環境を基礎に設定を適用し、各ケースへ同じ設定を渡す。
- stdout・stderr はケースごとに継続的に読み取り、他ケースと混ぜない。保存上限は §5.3 に従う。

ファイル・DB・ポートなどの外部資源はプロセスを分けても共有される。ケースごとに資源を分け、難しければ `--no-parallel` を使う。一時領域の回収は、ユーザーの `defer` や外部 DB の復元を代行しない。

### 4.3 並列実行と順序

`--jobs N` は同時に動かす子プロセス数の上限で、N は正の整数。省略時は CPU 並列度とメモリ・I/O などの制約を基に有限の値を選ぶ。`--no-parallel` は上限 1 とし、ケースごとの新規プロセスは維持する。両オプションの同時指定は引数エラー。

開始順・完了順は保証せず、直列でも順序依存を認めない。一覧と最終集計の表示順は同じ入力・設定で安定させる。ケースの失敗は他のケースを止めないが、継続不能なランナー障害とユーザー中断では新しい起動を止める。

### 4.4 有限の停止・回収

ケースの実行期限と回収猶予は、親の単調時計で管理する。実行期限は子の起動開始から終了までとし、runtime 準備・初期化・本体・cleanup・shutdown・完了報告を含む。待ち行列とビルド時間は含めない。

正常終了、異常終了、期限超過、中断のいずれも共通の回収処理へ入る。期限超過・中断時は対象を停止し、正常終了時も残る管理対象の子孫プロセスを回収する。

```text
子の終了 / 期限超過 / 中断
  → 有限の回収猶予
      ├─ プロセス群の停止・終了確認
      ├─ 通信の残りを読み取り、接続を閉じる
      └─ 使用終了を確認した一時領域を回収
  → 完了、または残存プロセス・未回収資源を伴う回収エラー
```

起動時点から OS の管理単位などでプロセス群を管理し、後からの PID 列挙だけに依存しない。EOF 待ち・停止待ち・一時領域の回収を無期限に行わない。猶予超過時は回収エラーを報告し、元の終了理由も保持する。未終了プロセスが使う領域を回収済みとしない。

強制終了時にユーザーの cleanup は保証しない。OS で管理できる範囲を超える外部プロセスの隔離・回収までは保証しない。資源不足で継続不能なら全体を実行エラーにする。期限・猶予の具体値は §9 で確定する。

## 5. 診断と結果

### 5.1 識別子

| ID | 識別するもの |
| --- | --- |
| ArtifactId | compiler・対象・設定・入力に対応する実行ファイルと静的診断テーブル |
| TestId | プロジェクト内のテスト宣言 |
| CaseId | 定義内の実行ケース。初期版にも既定ケースを 1 つ割り当てる |
| SiteId | 成果物内の検証位置。式・ソース位置・表示型を持つ静的テーブルの項目 |
| IssueId | ケース内で記録する失敗の各発生。同じ SiteId の再実行も区別する |

TestId・CaseId は表示名・行番号・絶対パス・実行順だけに依存させず、同じソース・設定で安定させる。宣言の改名・移動をまたぐ同一性は保証しない。TestId はプロジェクト、Container、Signature、必要なら文書の相対パスで区別する。CaseId は TestId と定義内のケース識別情報を組み合わせ、実行対象の範囲で一意にする。

IssueId は一意な整数とし、基本失敗・評価値・追加メッセージを結び付ける。「最後の失敗へ詳細を追加する」方式は使わない。詳細が届かなくても基本失敗を保持する。保存を省略した失敗には個別 ID を要求しない。ID は再利用・wrap させず、枯渇後は §5.3 の詳細省略に移る。

```kimi
// テスト専用ソース。
group DiagnosticTests
    func detail() -> string
        $expect(false, message: "内側の失敗")
        return "外側の説明"

    #Test
    func nestedDiagnostics()
        $expect(false, message: detail())
```

```text
CaseId
  ├─ IssueId 1 → 外側の基本失敗 → 外側の説明
  └─ IssueId 2 → 内側の基本失敗 → 内側の説明
```

### 5.2 報告と成功の条件

結果通信は stdout・stderr と分離する。開始時に ArtifactId と CaseId を照合し、選択した成果物以外の結果を受け付けない。ケース内のイベント順序を保持し、報告件数・失敗有無・省略情報・完了が整合することを検査する。

保存対象の基本失敗は、条件の cleanup やメッセージなど後続のユーザー処理より前に独立した報告として送る。子の終了まで全件を溜めない。親が受信した保存対象の情報は、その後の子の Abort でも保持する。報告自体の障害は実行エラーとし、成功へ読み替えない。

正常な経路では shutdown 後に完了を報告し、子は終了コード 0 で終了する。検証失敗の有無は完了情報で表し、CLI 全体の終了コードとは分ける。

**成功は、完了報告・子の正常終了・通信の整合・回収完了がすべて揃い、検証失敗がない場合に限る。** 検証を一度も呼ばない正常なケースも成功。終了コード 0 だけ、または完了報告だけでは成功にしない。

### 5.3 保存と通信の上限

ケースごと・実行全体に診断の件数と保存 byte 数の予算を設ける。失敗一覧、評価値、追加メッセージ、stdout・stderr、ディスクへの退避を対象とし、先頭の保存可能な範囲と省略情報を保持する。メッセージ長、通信 frame、未処理待ち行列、読み取り buffer にも上限を設ける。

- 上限後も条件・失敗時のメッセージ・cleanup は通常どおり評価し、保存だけを省略する。
- 失敗有無は一度確定したら戻さない。最初の失敗通知、完了、異常終了などの制御情報には、詳細保存と別の有限な領域を確保する。
- 件数・省略件数は飽和と下限表示で扱い、overflow で小さい値へ戻さない。
- 詳細を省略する場合は子側でも出力量を抑える。未送信の全件を親または子の無制限な列へ移さない。
- 最終件数は正常完了時に集計し、異常終了で確定できない件数は観測済みの下限として示す。
- 保存容量に達しても通信は読み取り続け、必要な情報を処理して残りを捨てる。通信待ちは §4.4 の期限・猶予内に収める。

意図した詳細省略は追加の実行エラーにしない。必要な制御情報の欠落・破損、保存対象の書き込み失敗などは実行エラーとする。ユーザーのメッセージ式自身のメモリ利用までは、保存予算で制限できない。

### 5.4 結果の分類と出力

ケースには検証失敗の記録、終了理由、通信・回収エラーを別々に保持する。異常終了後の回収エラーが元の Abort やタイムアウトを上書きしない。

| 状態 | 集計 |
| --- | --- |
| 正常完了・検証失敗なし・管理上のエラーなし | 成功 |
| 正常完了・検証失敗あり | 検証失敗 |
| Abort・クラッシュ | 異常終了 |
| 実行期限超過 | タイムアウト |
| ユーザー中断 | 中断。未起動のケースも成功・スキップにしない |
| 起動・通信・回収の障害 | 実行エラー。取得済みの終了理由・検証失敗を併記 |

Abort の理由は確実に取得した情報だけを使い、終了コード 1 から推測しない。診断の出力を保証できない場合は理由不明の異常終了として扱い、Abort 後にユーザーコードや cleanup を再開しない。

人間向け表示と機械可読結果を提供する。後者には形式バージョン、プロジェクト・対象・設定、各 ID、位置・式・値・メッセージ、実行段階、所要時間、終了状態、エラー、ログの保存先・省略情報を含める。端末の整形結果を外部連携の解析形式にしない。

```text
FAIL Arithmetic.addition
  tests/arithmetic.kimi:12:9
  $expect(actual == expected)
    actual:   4
    expected: 3
```

## 6. CLI

| コマンド・指定 | 動作 |
| --- | --- |
| `kimi test` | 対象プロジェクトの全ケースを実行 |
| `kimi test --list` | ID と名前を含む検証済み一覧を出力。対象プログラムは実行しない |
| `kimi test --filter Arithmetic` | 完全修飾テスト名に対する、大文字・小文字を区別するリテラル部分一致 |
| `kimi test --case <CaseId>` | 一覧の ID と完全一致する 1 ケースを実行。未知の ID はエラー |
| `kimi test --jobs 4` | 最大 4 子プロセスを同時実行 |
| `kimi test --no-parallel` | 新規プロセスによる隔離を保ち、1 ケースずつ実行 |

プロジェクト指定は既存 CLI に合わせる。`--case` と `--filter` の同時指定はエラー。`--list` に選択指定がある場合は、その選択結果を列挙する。部分一致に正規表現・ワイルドカードを暗黙導入しない。

機械可読の一覧・結果出力と、制限時間・回収猶予・保存予算の指定を提供する。形式・指定名・既定値は §9 で確定する。

発見または選択の結果が 0 件なら既定でエラー。明示的な空集合許可指定だけで成功を認めるが、不正な `--case` は空集合許可でもエラーとする。全ケース成功時の CLI 終了コードは 0、それ以外は非 0。

## 7. 性能と実装方針

| 部分 | 方針 |
| --- | --- |
| 検証の lowering | 共通の処理から生成し、失敗後の継続先だけを変える |
| 成功する検証 | 条件評価と必要な分岐を中心にし、診断通信・文字列生成・失敗用 allocation を行わない |
| 値の保存 | 元の評価で得た scalar を必要な範囲だけ保存し、register 圧迫と一時領域を抑える |
| 診断 | 式・位置・型の静的テーブルと小さな ID・値イベントを使い、表示整形は親で行う |
| ビルド | 適合する製品解析と全ケース入り実行ファイルを再利用する |
| 親ランナー | 実行枠と読み取り buffer を再利用し、ケース終了時に状態をリセットする |
| 並列数 | CPU 数だけで決めず、メモリ・I/O・起動コストを考慮する |

Debug・Release とも検証を有効にする。通常の最適化で副作用のない恒真検証は除去できるが、必要な評価・cleanup・診断上の意味は維持する。恒偽な実行時条件という理由だけでコンパイルエラーに置き換えない。

成果物の適合確認は実行開始時に行い、不変の snapshot を使ってケースごとのコピーや重複した全量検査を避ける。各子の ID 照合は維持する。反射的なテスト登録、検証ごとの UUID やヒープオブジェクトを要求しない。

短いケースはプロセス起動・回収が支配的になり得る。性能の効果は未測定であり、空の多数ケース・短い演算・I/O・大量失敗を使い、時間、親子のメモリ、通信量、生成コード量を測定する。

## 8. 将来の拡張

### 8.1 パラメータ化と Suite

テスト定義とケースは最初から分離する。将来は入力と期待値をまとめたケース列を使い、各ケースを個別に識別・報告・選択・並列化する。複数の引数列から直積を暗黙生成せず、Non-Copy 値を暗黙複製しない。値の生成・Move・プロセスへの渡し方と、静的 discovery の境界は導入時に定める。

分類には既存の `group`・`rootgroup` を使う。将来の `#Suite` は表示名・タグ・実行設定を中心とし、共有の可変 fixture を既定にしない。設定の継承、Suite 内の直列化、別 Suite にまたがる資源の排他を区別する。

```text
MathTests
  └─ Addition
       ├─ positiveNumbers → 既定ケース
       └─ withArguments   → 将来のケース A / B / C
```

### 8.2 その他の境界

条件付きスキップ、資源別排他、Option・Result の検証支援、文字列・コレクションの差分、添付、期待した Abort、コンパイル失敗テスト、coverage は将来の機能とする。初期版では Abort は成功にせず、フィルターで未選択のケースを実行済みスキップとして数えない。

子プロセス再利用は static・FFI 状態・初期化回数を変えるため、透明な高速化として導入しない。将来提供する場合は別の隔離モードとして明示する。同一プロセス内並列化には、別途言語の並行処理・メモリモデルが必要になる。

## 9. 具体化する詳細と確認項目

### 9.1 実装前に定める形式・既定値

| 項目 | 残る具体化 |
| --- | --- |
| プロジェクト | テスト専用ソース・依存のキー名、パス・設定の結合規則 |
| テスト環境 | 一時ディレクトリのパスを得る公開 API |
| 実行制御 | 有限な実行期限・回収猶予の既定値と指定形式 |
| 保存 | ケース別・全体の予算、frame・待ち行列上限、ログ保存先・期間 |
| 通信・結果 | transport、schema、機械可読出力・空集合許可の指定名、終了コード割り当て |
| ID | encoding、衝突検査、形式バージョン、整数の上限 |

主要な動作は前節までの規則に従い、上表を理由に無制限な待機・保存や曖昧な成功判定を許さない。

### 9.2 整合性と性能の確認

- テスト追加で製品の Binding・配置・適合を変えず、生成物にも所属を適用する。
- 全テストの検証、通常成果物からの除外、禁止された呼び出し・使用位置を確認する。
- 単一評価、短絡、メッセージからの外向き転送禁止、失敗分岐の Move、scalar の観測時点を確認する。
- `$require` の通常 return、cleanup 内の追加失敗・Abort、初回 static 初期化と shutdown の帰属を確認する。
- 入れ子・同位置の再実行を IssueId で区別し、基本診断だけが到着するケースも保持する。
- 保存上限後も評価を維持し、制御情報・省略件数・ID 枯渇・件数飽和を扱う。
- 大量ログ、通信破損、完了報告なしの終了コード 0、古い ArtifactId、残存パイプ・子孫プロセスを確認する。
- 正常・異常・中断で有限の回収を行い、元の終了理由と回収エラーをともに残す。
- フィルター変更時の成果物再利用、並列上限、Debug・Release の同じ意味、成功時 allocation を確認する。

実装は、所属と discovery → 直列の検証・結果報告 → cleanup・異常終了・回収 → 並列化と外部出力の順で進められる。未対応の機能を黙って受理しない。既存の C# compiler テストを直ちに置き換えず、NativeAOT テストは AGENTS.md に従い明示指定時だけ行う。

### 9.3 文書の対応

SPEC の属性、Composition Root、制御フロー・cleanup、失敗処理、ビルド・CLI、起動・runtime、文法の各節へ統合する。本書への参照と STATUS の更新は設計の記録であり、詳細統合や実行対応の完了を示さない。
