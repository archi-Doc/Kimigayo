# 分岐本体の構文と match の網羅性

## Current Specification

- `if` は `=> Expression` の式本体と、`=>` なしのインデントブロックを使う。式は `=>` と同じ物理行で開始する。
- `match` は全アームに `=>` を必要とし、直後の同じ物理行で式を開始すると式本体、次行で本体を開始するとブロック本体になる。
- Discard Contextで、全アームがブロック本体で、自身を対象とする `yield` がない `match` は非網羅的でもよい。
- 式本体が1つでもあると分岐全体がResult-requiringになる。結果を使わなくても結果型の整合性が必要であり、正常終了するブロック本体には `yield` が必要になる。
- ガードは外側の `=>` で終了する。本体開始の判定はドットによる式継続より優先される。
- `unsafe:`／`defer:` にはInlineStatementによる1行形式がある。分岐の全アームには本体が必要であり、実行可能ブロックは空にできない。

根拠：SPEC.md §2.2.1／§2.2.2、§14.2.1、§14.3.1、§14.7.1、§14.8／§14.8.3／§14.8.4、§15.1.6、付録F.5。本書の旧案の裸の `_` は、現行SPECの機能ではない。

## Proposed Specification

### 共通の本体構文

| 形式 | 意味 |
| --- | --- |
| `=> Expression` | 式本体。Value Contextで評価し、正常な結果を分岐全体に供給する。 |
| `: InlineStatement` | 1行ブロック本体。直接の式はDiscard Contextで評価し、値を捨てる。 |
| インデントされたExecutableBlock | 複数行ブロック本体。`=>` も `:` も付けない。 |

```kimi
match msg
    .Quit: stop()
    .Write(let t): write(t)       // boolを返しても捨てる
    .Move(let x, let y) if x > 0: moveTo(x, y)
    _: ()

if ready: start()
else if waiting: log("wait")
else: stop()
```

`P: s` は `P` の下に `s` だけをインデントしたブロックと同じ意味を持つ。同じ本体スコープ、束縛の可視性、転送先、Scope Exitを用い、意味上の余分なスコープは追加しない。`defer` の登録先と実行時期も維持する。

どちらのブロック形式も、それ自体ではResult-requiringを発生させない。結果が必要なら正常終了する経路は `yield` を使う。外側への転送や非終了経路は従来どおり結果不要である。

```kimi
// Unitを返す関数の本体内。score(t) は i32 を返す。
let code: i32 = match msg
    .Quit => 0
    .Write(let t): yield score(t)
    _: return                    // 関数へ戻るためmatchの結果は不要
```

### 1行本体と改行

- `:` はPattern、ガード、条件、`else` のヘッダー終端と同じ物理行に置く。継続行の先頭には置けない。
- 本体は `:` と同じ物理行で始まり、その行で完結する。括弧内を含む改行継続、後続のインデントブロック、セミコロンによる複数文は認めない。
- 使用できる文は§14.3.1の式文、`let`／`var`、`return`／`exit`／`continue`／`yield`、1行の `unsafe:`／`defer:`／`require`。既存の型・転送先・境界規則を適用する。
- **新しい1行本体を持つ `if` と `match` アームはInlineStatementに含めない。** 式文・初期化子・転送のオペランドや、再帰的な `unsafe:`／`defer:`／`require` を経由した入れ子も認めない。従来の、式本体だけからなる単一行の `if` 式は維持する。
- 1行本体後の `else`／`else if` は元の `if` とそろえた次の有効行に置き、同じ物理行には続けない。空行・コメントだけの行は無視する。式本体の既存のBranchJoinは維持する。
- `P:`／`if c:` の行内に本体がなければ「1行本体がない」構文エラーとし、ラベル付きブロックやインデントブロックとして読み直さない。`if`／`else if` の条件内のラベル付きブロックは括弧で囲む。
- `=>` は現在の `if` と同じく、式を同じ物理行で開始する。式開始後の通常の継続と、元のヘッダーより1段深い行での `=>` 自体の継続は維持する。`=>` の次行で式を開始する形式はエラーであり、ブロックに再解釈しない。

```kimi
if a: if b: work()               // エラー：新しい1行ifはInlineStatementではない
if a: work() else: rest()        // エラー：外側のelseは次の有効行
```

今回の追加対象は `if` と `match` とする。文法名は共通のInlineBlockBodyにするが、`for`／`while`／`loop` への `:` 形式の追加は含めない。

### ガードの終端と本体開始

ガードは正常な結果が `bool` である1つの式とし、次の規則で境界を決定する。

1. 括弧や入れ子の構文内の `=>`／`:` は外側の区切りではない。外側のヘッダーに属する最上位の `=>` は式本体、`:` は1行本体を開始する。
2. それらがなければヘッダーの論理的な終端でガードを終了し、元のアームヘッダーより1段深くブロック本体を開始する。**本体開始をドットによる式継続より先に判定する。** 許可された `=>` のヘッダー継続は本体と区別し、`:` の継続は許可しない。
3. 複数の物理行にわたるガードは、ガード全体を `(...)` で囲む。閉じるまでは括弧内の継続・インデント規則を適用する。括弧外の1段深い `.name` をガードのメソッドチェーンに吸収しない。
4. ガード内の `if`・`match`・`loop`・ラベル付きブロック、およびブロック本体の匿名関数は、その式を括弧で囲むことを必須とする。ガード全体の括弧がその式を囲む場合は兼用できる。
5. 空行・コメントだけの行は境界を変えない。本体は必須であり、欠落時に後続の同じ深さ・浅い深さの項目を取り込まない。

```kimi
match value
    .Some(let x) if (
        x.isReady()
            .check()): process(x)
    _: ()
```

括弧なしの `if x.isReady()` の次行に1段深く `.check()` と書いた場合、それはブロック本体の先頭であり、ガードの続きではない。Case構築としての合法性は別途検査する。

### 網羅性・結果要求・既定アーム

すべての実行時 `match` に網羅性を要求する。本体形式、評価コンテキスト、結果型、`yield` の有無による例外は設けない。既存の限定的な証明規則と、ガード付きアームは網羅性に寄与しない規則を維持する。

Result-requiringの条件は、Value Context、式本体の存在、自身を対象とする `yield` の存在を維持する。網羅性必須化によって全 `match` をResult-requiringにすることはない。

**本体を省略した裸の `_` は廃止し、通常のWildcard Patternと本体だけを認める。** 最終アームにも例外を設けない。

| 記法 | 意味 |
| --- | --- |
| `_` だけ | 本体欠落の構文エラー。 |
| `_: ()` | 何もしないブロック本体。結果要求を単独では発生させない。 |
| `_: yield ()` | ブロックからUnitを結果として供給する。 |
| `_ => ()` | Unitを結果とする式本体。Result-requiringを発生させる。 |

`_: ()` は結果要求がある場合に暗黙の結果を供給しない。`_: yield ()` のUnitも通常の型検査を受ける。対象の取得・Move・借用・破棄は、何もしない既定アームでも通常どおり行う。

結果要求のある分岐で、正常終了する1行本体に `yield` なしの非Unitの式文を書いた場合、結果供給不足をエラーとし、「式本体の `=>` にするか、`yield` を付ける」という修正案を診断に含める。式が正常終了しない場合はこの診断を要求しない。

### Case追加に関する推奨lint

enumの既存の全Caseを、先行するガードなしのCaseアームが既存の網羅性証明規則で個別にカバーしている場合、後続のガードなしの `_` に「新しいCaseも既定処理に吸収される」と知らせるlintを推奨する。ペイロードの部分的な分割の合成やガードの真偽の推測は行わない。

これは「先行する1つのPatternによる包含」の必須警告とは別の任意lintとする。受理条件・網羅性証明・到達可能性・結果検査は変更しない。

## Changes

- `match` の `=>` 付きブロックを、インデントブロックまたは `: InlineStatement` に移行する。
- 裸の `_` と暗黙のUnit供給の特例を削除する。非網羅的な処理には `_: ()` などの明示的な既定アームを追加する。
- ガードの区切り、括弧要件、本体開始の優先順位、1行本体後のBranchJoinを定義する。
- Parser、AST／Binder、結果分類、網羅性・制御フロー・所有権解析、診断、フォーマッタとテストを追随させる。
- フォーマッタはInlineStatementの制約を満たす単一文ブロックと1行本体を、構文上の所属を保って相互変換できる。必要な `else` の改行も行う。`=>` との相互変換は整形として行わない。

## Rationale

既存の `unsafe:`／`defer:` と同じ「コロンの後に1文」を分岐へ広げる。`=>` は結果を供給する式本体、`:` は直接の式の値を捨てるブロック本体を表す。副作用だけの1行処理を全アームで書けるため、`_` 専用の省略・推論規則が不要になる。

非空要件を維持し、最後の `_` のインデント誤りを省略アームと後続処理として受理する危険を除く。ガードの括弧要件と本体優先は、ドット継続や入れ子の区切りの読み違いを防ぐ。

網羅性要求を本体形式から独立させる対象は `match` である。`if` は副作用だけの条件付き処理を `if c: work()` と書けるよう、ブロック形式では従来どおり `else` を省略できる。式本体などで結果要求が生じれば `else` が必要になる。この差は意図的であり、統一するのは本体構文とその意味である。

網羅性必須化だけでは、`_` があるコードのCase追加漏れは検出できない。既定処理は新Caseも受け入れる意図を表す。Case追加時に再検討したいコードでは個別列挙を使い、不要な `_` への推奨lintで判断を助ける。

| 検討案・指摘 | 扱いと理由 |
| --- | --- |
| ガードの本体優先・複数行の括弧必須化、複雑なガードの括弧必須化 | 採用。§2.2.2と整合させ、外側の境界を明示する。 |
| 裸の `_` を結果不要の場面だけ許可する | 不採用。省略形自体を廃止するため不要であり、インデント誤りの危険も残る。 |
| enum全Case列挙後の `_` への警告 | 推奨lintとして採用。既存の必須警告と受理条件を維持する。 |
| Unit型の式本体を結果要求から除外する | 不採用。型検査前の構文に基づく分類を型依存にしてしまう。 |
| `=> do`／`-> stmt`／`{ stmt }` | 不採用。新キーワード、結果型記号の転用、予約された波括弧の用途追加を避け、既存の `:` を使う。 |
| ループにも1行本体を追加する | 今回は見送る。共通名InlineBlockBodyを用意し、ループの文法変更は別途検討する。 |
| Binding Patternの型注釈 | 今回は導入しない。アーム位置の `let n: log(n)` はBinding Patternと本体である。将来導入する場合も裸の `let n: Type` と衝突させず、括弧で区切る案を別途検討する。 |

## Decision

1. `=>` は分岐の式本体専用とし、式を同じ物理行で開始する。
2. `if`／`match` に `: InlineStatement` の1行ブロック本体を追加し、インデントブロックと同じ意味にする。
3. すべての実行時 `match` に網羅性を要求し、結果要求とは分離する。
4. 裸の `_` と暗黙のUnit供給の特例を廃止し、`_: ()` などの明示的な本体を必須にする。
5. ガードの終端・必須括弧・本体優先、同一行の `:` と本体、次の有効行の `else` を規定する。
6. 既存の型・所有権・結果検査と `if` の `else` 要求を維持し、enumの既定アームへの推奨lintを追加する。
