# 分岐本体の構文と match の網羅性

## Current Specification

- `if` は `=> Expression` の式本体と、`=>` なしのインデントブロックを使う。式は `=>` と同じ物理行で開始する。
- `match` は全アームに `=>` を必要とし、直後の同じ物理行で式を開始すると式本体、次行で本体を開始するとブロック本体になる。
- Discard Contextで、全アームがブロック本体で、自身を対象とする `yield` がない `match` は非網羅的でもよい。
- 式本体が1つでもあると分岐全体がResult-requiringになる。結果を使わなくても結果型の整合性が必要であり、正常終了するブロック本体には `yield` が必要になる。
- ガードは外側の `=>` で終了する。本体開始の判定はドットによる式継続より優先される。
- `unsafe:`／`defer:` にはInlineStatementによる1行形式がある。分岐の全アームには本体が必要であり、実行可能ブロックは空にできない。

根拠：SPEC.md §2.2.1／§2.2.2、§14.2.1、§14.3.1、§14.7.1、§14.8／§14.8.3／§14.8.4、§15.1.6、付録F.5。本書の旧案の裸の `_` は、現行SPECの機能ではない。

## Proposed Specification

### 共通の本体構文

意味上の本体は**式本体とブロック本体の2種類**とする。ブロック本体には1行形式とインデント形式があり、`if` の各分岐と `match` の各アームで混在できる。

| 形式 | 意味 |
| --- | --- |
| `=> Expression` | 式本体。Value Contextで評価し、正常な結果を分岐全体に供給する。 |
| `: InlineStatement` | 1行ブロック本体。直接の式はDiscard Contextで評価し、値を捨てる。 |
| インデントされたExecutableBlock | インデント形式のブロック本体。1文でもよく、`=>` も `:` も付けない。 |

```kimi
match msg
    .Quit: stop()
    .Write(let t): write(t)       // boolを返しても捨てる
    .Move(let x, let y) if x > 0: moveTo(x, y)
    _: ()

if ready: start()
else if waiting: log("wait")
else: stop()
```

ヘッダー `H` に対する `H: s` は、`H` の下に `s` だけをインデントしたブロックと同じ意味を持つ。同じ本体スコープ、束縛の可視性、転送先、評価順序、Scope Exitを用い、追加のスコープや制御境界は作らない。直接の式を捨てても、内部の引数・初期化子などは元のValue Contextを保ち、型・所有権検査や `Result` の破棄警告も省略しない。

Patternの本体束縛と直下の文は同じ宣言空間に属する。たとえば `let n: let n = 0` は再宣言エラーである。`if ready: defer: close()` の `defer` は分岐スコープに登録され、通常どおりその分岐を出るときに実行される。

どちらのブロック形式も、それ自体ではResult-requiringを発生させない。結果が必要なら正常終了する経路は `yield` を使う。外側への転送や非終了経路は従来どおり結果不要である。

```kimi
// Unitを返す関数の本体内。score(t) は i32 を返す。
let code: i32 = match msg
    .Quit => 0
    .Write(let t): yield score(t)
    _: return                    // 関数へ戻るためmatchの結果は不要
```

### 1行本体と改行

- `:` はPattern、ガード、条件、`else` のヘッダー終端と同じ物理行に置く。継続行の先頭には置けない。
- 本体は `:` と同じ物理行で始まり、その行内で完結する。括弧内を含む改行継続、複数行リテラル、後続のインデントブロック、セミコロンによる複数文は認めない。制約は本体の構文に適用し、それを囲む式の閉じ括弧や引数区切りまで禁止するものではない。
- 使用できる文は§14.3.1の式文、`let`／`var`、`return`／`exit`／`continue`／`yield`、1行の `unsafe:`／`defer:`／`require`。既存の型・転送先・境界規則を適用する。
- **InlineStatementの構文内に、新しいInlineBlockBodyを持つ `if` を含めない。** 括弧・初期化子・転送のオペランド・再帰的な `unsafe:`／`defer:`／`require` の内部にも同じ制限を適用する。`match` はアーム列にインデントを必要とするため、本体形式によらずInlineStatementには入らない。関数・宣言コンテナの宣言、ラベル付きブロックなど、既存の除外規則も維持する。
- 式本体だけからなる単一行の `if` 式と、単一行の `require` は従来どおり使える。ただし、その内部の `else` を含む全構文を同じ物理行で完結させ、次行の `else` を内部へ取り込まない。単一行の `require` の条件に選択式を使う場合の括弧要件も維持する。
- **外側の分岐に属する** `else`／`else if` は、1行本体の後では元の `if` とそろえた次の有効行に置く。同じ物理行には続けない。空行・コメントだけの行は無視する。これは本体内の `require ... else ...` や単一行の `if` 式の `else` を禁止する規則ではない。式本体の既存のBranchJoinは維持する。
- `P:`／`if c:` の行内に本体がなければ「1行本体がない」構文エラーとし、ラベル付きブロックやインデントブロックとして読み直さない。`if`／`else if` の条件内のラベル付きブロックは括弧で囲む。
- `=>` は現在の `if` と同じく、式を同じ物理行で開始する。式開始後の通常の継続と、元のヘッダーより1段深い行での `=>` 自体の継続は維持する。`=>` の次行で式を開始する形式はエラーであり、ブロックに再解釈しない。

```kimi
if a: if b: work()               // エラー：新しい1行ifはInlineStatementではない
if a: work() else: rest()        // エラー：外側のelseは次の有効行
```

```kimi
// 関数本体内。最初のelseはrequire、次行のelseは外側のifに属する。
if ready: require valid else return
else: stop()
```

今回追加する1行形式は `if` の分岐と `match` のアームだけとする。`match subject: ...` という1行のアーム列や、関数・`for`／`while`／`loop` の `:` 本体は追加しない。`require` 自体の区切りも従来の `else` のままとする。

### ガードの終端と本体開始

ガードは正常な結果が `bool` である1つの式とし、次の規則で境界を決定する。

1. 括弧や入れ子の構文内の `=>`／`:` は外側の区切りではない。外側のヘッダーに属する最上位の `=>` は式本体、`:` は1行本体を開始する。
2. 同じ行に外側の区切りがなく、ガードが構文上完了した場合、次の有効行が元のアームヘッダーより1段深い `=>` で始まればヘッダー継続とする。それ以外ではヘッダーの論理的な終端でガードを終了し、1段深い行からインデント本体を開始する。**本体開始をドットによる式継続より先に判定する。** `:` のヘッダー継続は許可しない。継続行・本体の深さは元のアームヘッダーを基準とし、閉じ括弧や継続した区切りの行から加算しない。
3. 複数の物理行にわたるガードは、ガード全体を `(...)` で囲む。閉じるまでは括弧内の継続・インデント規則を適用する。括弧外の1段深い `.name` をガードのメソッドチェーンに吸収しない。
4. ガード内の `if`・`match`・`loop`・ラベル付きブロック、およびブロック本体の匿名関数は、対象の式そのものをグループ化する `(...)` を必須とする。ガード全体がその式そのものである場合は、複数行ガード用の括弧と兼用できる。内部の構文・転送先・型規則は変更しない。
5. 空行・コメントだけの行は境界を変えない。本体は必須であり、欠落時に後続の同じ深さ・浅い深さの項目を取り込まない。

```kimi
match value
    .Some(let x) if (
        x > 0 and
        x < limit): process(x)
    _: ()
```

括弧なしの `if x.isReady()` の次行に1段深く `.check()` と書いた場合、それはブロック本体の先頭であり、ガードの続きではない。Case構築としての合法性は別途検査する。ガードは選択中の `match` へ `yield` できず、ガードが正常終了しなければ本体の束縛取得も後続アームの実行も行わないという既存規則を維持する。

### 網羅性・結果要求・既定アーム

すべての実行時 `match` に網羅性を要求する。本体形式、評価コンテキスト、結果型、`yield` の有無による例外は設けない。既存の限定的な証明規則と、ガード付きアームは網羅性に寄与しない規則を維持する。

Result-requiringの条件は、Value Context、自身の分岐に式本体があること、自身を対象とする `yield` があることのいずれかとする。型や到達可能性によらず、転送先を解決してから分類する。入れ子の分岐形式や、入れ子だけを対象とする `yield` は外側の分類に数えない。網羅性必須化によって全 `match` をResult-requiringにすることはない。

**本体を省略した裸の `_` は廃止し、通常のWildcard Patternと本体だけを認める。** 最終アームにも例外を設けない。

| 記法 | 意味 |
| --- | --- |
| `_` だけ | 本体欠落の構文エラー。 |
| `_: ()` | 何もしないブロック本体。結果要求を単独では発生させない。 |
| `_: yield ()` | ブロックからUnitを結果として供給する。 |
| `_ => ()` | Unitを結果とする式本体。Result-requiringを発生させる。 |

`_: ()` は結果要求がある場合に暗黙の結果を供給しない。`_: yield ()` のUnitも通常の型検査を受ける。対象の取得・Move・借用・破棄は、何もしない既定アームでも通常どおり行う。

結果要求のある分岐では、**Unitを期待する場合も、到達可能な正常終了経路の結果不足をエラーにする。** 単一の式文だけのブロックが値を捨てている場合は、結果を供給する意図なら `=>` または `yield` を使うという修正案を示す。宣言などには機械的な `=>` 置換を勧めず、必要な結果を `yield` する案を示す。供給する値の型整合性は別途必要である。転送や非終了するScope Exitなどにより正常完了しない経路には結果を要求しない。

### Case追加に関する推奨lint

enumの既存の全Caseを、先行するガードなしのCaseアームが既存の網羅性証明規則で個別にカバーしている場合、後続のガードなしの `_` に「新しいCaseも既定処理に吸収される」と知らせるlintを推奨する。ペイロードの部分的な分割の合成やガードの真偽の推測は行わない。

これは「先行する1つのPatternによる包含」の必須警告とは別の任意lintとする。受理条件・網羅性証明・到達可能性・結果検査は変更せず、lint対象のアームも通常どおり検査する。既定アームが実際に既存の未処理Caseをカバーする場合は、このlintの対象にしない。

## Changes

- `match` の `=>` 付きブロックを、インデントブロックまたは `: InlineStatement` に移行する。
- 裸の `_` と暗黙のUnit供給の特例を削除する。非網羅的な処理には `_: ()` などの明示的な既定アームを追加する。
- ガードの区切り、括弧要件、本体開始の優先順位、1行本体後のBranchJoinを定義する。
- Parser、AST／Binder、結果分類、網羅性・制御フロー・所有権解析、診断、フォーマッタとテストを追随させる。
- フォーマッタはInlineStatementの制約を満たす単一文ブロックと1行本体を、構文上の所属、コメント、スコープを保って相互変換できる。必要な `else` の改行も行う。複数文や継続を必要とする文は1行化せず、`=>` との相互変換は整形として行わない。

## Rationale

既存の `unsafe:`／`defer:` と同じ「コロンの後に1文」を分岐へ広げる。`=>` は結果を供給する式本体、`:` は直接の式の値を捨てるブロック本体を表す。副作用だけの1行処理を全アームで書けるため、`_` 専用の省略・推論規則が不要になる。

非空要件を維持し、最後の `_` のインデント誤りを省略アームと後続処理として受理する危険を除く。ガードの括弧要件と本体優先は、ドット継続や入れ子の区切りの読み違いを防ぐ。

網羅性要求を本体形式から独立させる対象は `match` である。`if` は副作用だけの条件付き処理を `if c: work()` と書けるよう、ブロック形式では従来どおり `else` を省略できる。式本体などで結果要求が生じれば `else` が必要になる。この差は意図的であり、統一するのは本体構文とその意味である。

網羅性必須化だけでは、`_` があるコードのCase追加漏れは検出できない。既定処理は新Caseも受け入れる意図を表す。Case追加時に再検討したいコードでは個別列挙を使い、不要な `_` への推奨lintで判断を助ける。

| 検討案・指摘 | 扱いと理由 |
| --- | --- |
| ガードの本体優先・複数行の括弧必須化、複雑なガードの括弧必須化 | 採用。§2.2.2と整合させ、外側の境界を明示する。 |
| 裸の `_` を結果不要の場面だけ許可する | 不採用。省略形自体を廃止するため不要であり、インデント誤りの危険も残る。 |
| enum全Case列挙後の `_` への警告 | 推奨lintとして採用。既存の必須警告と受理条件を維持する。 |
| Unit型の式本体を結果要求から除外する | 不採用。型検査前の構文に基づく分類を型依存にしてしまう。 |
| `=> do`／`-> stmt`／`{ stmt }` | 不採用。新キーワード、結果型記号の転用、予約された波括弧の用途追加を避け、既存の `:` を使う。 |
| ループにも1行本体を追加する | 今回は見送る。共通名InlineBlockBodyを用意し、ループの文法変更は別途検討する。 |
| Binding Patternの型注釈 | 今回は導入しない。アーム位置の `let n: log(n)` はBinding Patternと本体である。将来導入する場合も裸の `let n: Type` と衝突させず、括弧で区切る案を別途検討する。 |

```ebnf
BranchBody      := "=>" Expression | InlineBlockBody | ExecutableBlock
InlineBlockBody := ":" InlineStatement
MatchArm        := Pattern ("if" GuardExpression)? BranchBody
GuardExpression := ? 上記の括弧・境界規則に従う1つの式 ?
```

この文法は§2のレイアウト規則、InlineStatementの行内完結条件、BranchJoinと併せて適用する。1行本体は自身のINDENT／DEDENTを必要とせず、意味上は通常のブロックとして扱う。実行時 `match` のアーム列は従来どおり非空のインデント列であり、コンパイル時の `#match` は変更しない。

主な検証境界は次のとおり。表中の呼出し・転送先・Patternがそれぞれ型と配置の規則を満たすことを前提とする。

| 入力・状況 | 必要な判定 |
| --- | --- |
| 結果を使わない `match` の `P: f()` と `_: ()` | `f()` の結果型による結果要求は発生しない。全体の網羅性は必須。 |
| Unitが必要な `match` の `_: ()`／`_: yield ()` | 正常終了経路では前者は結果不足、後者はUnitを供給する。 |
| 結果要求のあるブロック内で外側へ `return`／`exit`／`continue` | 通常の転送規則に適合すれば、その経路の `yield` は不要。 |
| `P: require cond else yield 1` | 自身へのyieldが結果要求を発生させる。require成功後に正常終了する経路が到達可能なら、結果不足となる。 |
| 最後の裸の `_`、行末の `P:`／`if c:` | 本体欠落の構文エラー。次行を本体へ読み直さない。 |
| `=>` の次行で式を開始／継続行の先頭の `:` | 構文エラー。ヘッダー継続行の `=> expr` は有効。 |
| `if a: require b else return` の次行の `else` | 行内の `else` はrequire、次行は外側のifに所属する。 |
| `if a: if b => 1` の次行の `else` | 次行は外側のifに所属し、内側のifは最終else不足となる。 |
| 括弧外のガードの次行に、1段深い `.Case(...)` | ガードの継続ではなく、本体のCase式として検査する。 |

既存のDesign Decisionが未確定としていた `=>` 直後の改行は現在の `if` に合わせて確定し、本書の旧版の省略既定アーム案を置き換える。STATUS.mdは実装の進捗に合わせて更新する。

## Decision

1. `=>` は分岐の式本体専用とし、式を同じ物理行で開始する。
2. `if`／`match` に `: InlineStatement` の1行ブロック本体を追加し、インデントブロックと同じ意味にする。
3. すべての実行時 `match` に網羅性を要求し、結果要求とは分離する。
4. 裸の `_` と暗黙のUnit供給の特例を廃止し、`_: ()` などの明示的な本体を必須にする。
5. ガードの終端・必須括弧・本体優先、同一行の `:` と本体、次の有効行の `else` を規定する。
6. 既存の型・所有権・結果検査と `if` の `else` 要求を維持し、enumの既定アームへの推奨lintを追加する。
