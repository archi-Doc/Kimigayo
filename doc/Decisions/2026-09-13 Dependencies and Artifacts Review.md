## 1. 評価

ソース配布先行、独立した定義環境、複数版の明示的な identity、内容による依存検証、不在への依存、使用時 Loan 検証を残す方針は維持できる。問題は主として、ソース・配布・検証・生成という各段階の境界にある。

| ID | 優先度 | 問題 | 改善の共通規則 |
| --- | --- | --- | --- |
| R1 | 高 | Project の検証結果を、そのまま配布用の固定グラフへ移す手順がない | 最終的に配布する論理入力を確定し、その入力を検証する |
| R2 | 高 | テスト追加が製品の generic 生成・予算選択を変え得る | 製品を確定し、テストは不変の製品へ追加する |
| R3 | 中 | lock の解決結果と作業中のソース snapshot が混在する | 解決の保存と、各 build が使用した入力の記録を分ける |
| R4 | 中 | 全依存を含む入力 ID が宣言 ID まで変え、細粒度再利用を妨げる | 宣言の対応付け、内容、有効な検証結果を分ける |
| R5 | 中 | native 要求の target・取得元・実ファイル固定の契約が不足する | 要求を定義側で宣言し、供給を target ごとに解決して記録する |
| R6 | 中 | 合法な版名が既定の保存パスで衝突する | 論理名をそのまま物理ストレージのキーにしない |

R1・R2 は実装前に解決したい。R3–R6 も、lock・cache・pack の形式を固定する前に整理することを勧める。バイナリ配布を初期へ繰り上げる必要はない。

## 2. 問題と改善策

### R1. 検証した入力と配布する入力を一致させる手順が不足する

**対象:** 設計 §3.1、§3.3、§4.2、§5.3。

§3.1 はローカル Project 参照を認める一方、§3.3 は配布依存をパッケージの SourceId へ固定する。§5.3 のローカル snapshot は配布形式ではないとも明記されている。次の通常の開発構成について、変換が未定義である。

```text
Geometry.kimiproj
  Math -> Project ../Math/Math.kimiproj

pack Math     -> Math.kimipkg、パッケージの SourceId
pack Geometry -> Project 参照をどの SourceId へ結び直すか？
```

Math を先に pack しても、Geometry の Project 参照がその成果物と等価かを確認する規則はない。キャッシュ用の Project SourceId を配布依存へ書くと取得できない。ID／Version だけで既存 package を選ぶと、その後に編集された Math のソースと違う内容を配布できてしまう。

同じ問題は、実効 LangVersion、ソース所属・順序、default alias、native 設定の配布への変換にもある。「同じ snapshot を pack」だけでは、snapshot をどの段階で確定するかが足りない。

**改善案:** pack は取得元を直接書き換える操作ではなく、通常の resolver が扱える**配布用の論理入力を作る操作**とする。

1. 必要なローカル入力と設定を snapshot にする。
2. Project 依存を末端から配布用入力へ変換し、それぞれの最終 SourceId を確定する。既存の Package 依存は固定内容を検査して再利用する。
3. 親の manifest に、その確定済み ID を入れる。元 Project の取得パスと生成物のパスは identity から分離する。
4. 通常の package loader／意味検証器で、この最終グラフを検証する。
5. 完成した依存パッケージを先に公開し、親を最後に公開する。

初期実装では同じ pack 操作で必要な Project 依存も処理すると、手作業の設定変更や「pack 済み候補を見つける」特別なルールを減らせる。通常 build が発行済み依存を Project で置換することは、引き続き許可しない。

検証のために ZIP を一度書いて解凍する必要はない。通常の loader と同じ論理 manifest／file view を使い、検証済みの byte 列を archive writer へ渡せばよい。検証環境・compiler build・診断は build record へ保存し、target 非依存の配布入力へ生成結果や host パスを混ぜない。

**確認例:** Math を pack 後に編集して Geometry を pack、Project にだけ存在する alias、テスト専用ソースの除外、未指定 LangVersion の確定、依存の公開途中で停止。最後の例では不要な完成済み子が残ることは許せるが、不足する子を指す完成済み親は残さない。

### R2. テスト追加が製品の生成計画を変え得る

**対象:** 設計 §3.4、§7、generic 共有設計 §8.3。

§3.4 はテストの変更で製品の生成計画を変えないとする。一方、§7 は最終生成単位の body をすべて予算へ計上し、generic 設計は生成単位の基準量 B に比例した全体予算を持つ。同じ最終単位へテストを加えると、製品側の特殊化選択が変わり得る。

次は仕組みを示す仮の係数であり、推奨既定値ではない。

```text
製品 B = 100、全体増加率 = 0.2       -> 全体予算 20
製品関数の個別予算 = 40、候補費用 = 30 -> 不採用

テストの基準量 100 を同じ B に加算   -> 全体予算 40
同じ製品候補の費用 = 30              -> 採用
```

逆に、テストの候補が予算を使って製品候補を押し出す場合もある。予算だけを分けても、テストから新しい generic 代入を追加して製品の共有クラス、context schema、frame の構成を作り直すなら、同じ問題が残る。

**改善案:** 所属の境界を、名前解決だけでなく**生成要求・共有計画・任意最適化予算まで**適用する。

- 製品入力から製品の意味、必要代入、共有クラス、入口、予算選択を確定する。
- テストはその不変の結果を参照する。既存の製品 entry を、その契約に適合する場合に再利用する。
- テストだけから要求された製品 generic の追加代入は、定義時の契約を維持したテスト側の生成要求とする。製品の既存共有クラスや frame を変更しない。
- 追加生成と任意最適化はテスト側の予算で処理する。同じ追加クラス内では通常の重複排除・共有を行う。
- 同じ ID／Version の依存の一意性も、製品を含むテスト拡張グラフ全体で検査する。異なる内容をテスト専用の同版ノードとして二重ロードしない。

二度の全面コンパイルや二つの native 実行ファイルを必須にする案ではない。意味計画と生成の所有区分を固定し、同じ最終ファイルへ格納することは可能である。テスト用の entry、診断、到達可能性が異なるため、最終ファイル全体の byte 一致までは要求しない。

**確認例:** 無関係なテスト100件の追加、製品 generic の新しい型でのテスト、テスト依存だけが同版の別内容を要求する場合。製品の論理生成計画・予算選択が変わらないことを確認する。

### R3. lock が依存解決と編集中 snapshot の両方を担っている

**対象:** 設計 §3.2–3.4。

通常 build は Project のソース編集を受け入れて lock を更新し、依存宣言・固定 package の変更では restore を要求する。lock 不在時は build 自身が作成する。このため、保存を伴う分岐が build、check、restore、test にまたがる。

通常の編集ごとに共有・コミット対象の lock が変わるほか、並行する build と test が別の旧版から lock 全体を書き戻し、製品区分やテスト区分を失う余地がある。staging による一括置換は途中のファイルを防ぐが、この更新の取りこぼしは防げない。古いテスト区分がどの製品 snapshot に対して有効だったかも、明示的に結び付ける必要がある。

**改善案:** **restore は解決結果を保存し、build は実際に使用した入力を記録する**という所有規則へ揃える。

| 保存物 | 更新主体 | 内容 |
| --- | --- | --- |
| dependency lock | restore | 参照グラフ、固定 package 内容、Project の ID／取得元、明示固定時点の Project snapshot |
| build input record | 各 build／check／test | 今回読んだルート・Project・native・target・設定の不変 snapshot |

通常 build は Project の現在の内容を使い、結果を build record に記録するが lock を書き換えない。依存宣言や package の不一致は restore を要求する。初回も restore に揃えると、lock がない場合だけ build が解決を書き戻す例外を除ける。

既存案の `--locked` による Project 内容の完全固定は維持できる。通常 build は Project を live 入力として読み、`--locked` は restore 時点の固定 snapshot と照合する。完全固定の基準を更新したい場合も restore を使う。ルートのソースまで固定する保証は、依存 lock ではなく build input record の責任と明示する。

テスト区分は、その解決時に使った製品区分の digest に結び付ける。製品区分が違えば未解決として扱う。restore 同士の並行更新は、読み始めた lock の世代を照合して競合を診断し、古い全体を後勝ちで保存しない。record は入力 identity ごとの不変データにすれば共有 lock の取り合いを減らせる。

**確認例:** Project ソースだけの編集、Project 依存宣言の編集、固定 package の差し替え、build と test の同時実行、二つの restore の競合、製品区分だけを更新した後の test。

### R4. 宣言の identity と検証の有効性が強く結合しすぎている

**対象:** 設計 §2.1、§5.2–5.3。

ModuleInputId は直接依存の ModuleInputId を再帰的に含み、DeclarationId は自分の ModuleInputId に結び付く。末端の private な関数を一つ編集しても、利用側の ModuleInputId と全 DeclarationId が連鎖して変わる。

これは保守的には正しく、現在の規則だけで古い証明が誤って受理されるわけではない。しかし、§5.2 の宣言単位の再利用を行うときに、比較対象まで全部別 identity になる。旧新宣言の再対応付けを認める記述はあるが、どの情報を対応付けに使い、どの一致で結果を再利用できるかが未定義である。

**改善案:** 三つの役割を区別する。

| 役割 | 使用例 |
| --- | --- |
| 宣言を対応付けるキー | 元モジュールの ID／Version、Container、宣言種別、正規化した宣言識別情報 |
| 内容の fingerprint | 署名、body、効果、適合、探索した宣言集合など、検証が実際に読んだ内容 |
| 検証結果のキー | 前提環境、検証規則、必要な内容 fingerprint の集合 |

対応付けキーの一致だけで同じ証明や ABI を採用しない。Origin、Constraint、access などを識別から省ける場合でも、それらに依存する検査の fingerprint には必ず残す。対応付け不能・曖昧な宣言は再検証し、全編集をまたぐ安定 ID の保証は要求しない。

ModuleInputId は全体一致の高速経路として残せる。不一致なら影響する内容を比較し、変更された宣言の検証結果と、その結果に依存する判断を更新する。初期版でこの比較器を実装しない場合は、全体失効を明記すればよく、宣言単位の再利用が既に成立すると扱わない。

SourceId は配布内容の完全性のキーとして維持する。manifest の空白だけで SourceId が変わる規則を緩めて、異なる配布内容を同じものと扱う必要はない。字句入力や正規化した意味情報の再利用を、その下の別層で行う。

**確認例:** 未使用 private body 編集、公開署名変更、access 拡大、同名宣言の追加、同版の別 SourceId。必要な失効を維持しつつ、影響のない解析の再利用件数を測る。

### R5. native 接続の要求と解決結果が十分に分かれていない

**対象:** 設計 §3.2、§4.1、§7。

既存 NativeLibraries は target 別だが、新しい NativeBindings は PackageId／Version／Name／Kind／Input だけで、target 別の対応がない。nativeRequirements の内部 schema、契約 identity の照合方法、root 側 Input の基準ディレクトリも十分には確定していない。現在の Windows 単一 target では表面化しにくいが、宣言済みの複数 target を扱う時に同じ論理名へ異なる供給を割り当てられない。

また Sha256 が任意であり、ソースの lock が一致していても `.lib` の内容は変わり得る。最終ビルド記録に実入力を残す原則はあるものの、任意の供給側 hash と、compiler が必ず計算する実入力 hash の区別が必要である。依存 lock の一致をビルド全入力の一致として扱うと、生成物の再利用条件を誤る。

**改善案:** 型の依存と同様に、native も**要求 → target ごとの解決 → 実入力記録**へ揃える。

- nativeRequirements は target ごとの論理名 map とし、kind、明示された契約 ID、任意の要求 hash を持つ。kind と target は必須。契約 ID は供給契約の名前であり、機械語の正しさの証明にはしない。
- NativeBindings も既存 NativeLibraries と同じ target 分類を持ち、PackageId／Version／Name で要求へ対応させる。相対 Input は記述したルートプロジェクトを基準にする。
- 実ファイルを解決したら、target、kind、要求契約、実際の内容 hash を build record に必ず保存する。利用者による hash 指定は追加の受入条件であり、自動記録の代わりではない。
- 同じ byte 内容のファイルの移動は供給の変更とせず、パスが同じでも内容が違えば変更とする。実 symbol の共有には、呼出契約と provider の一致も必要である。
- ABI に影響する kind／契約は関連計画の入力へ、実 archive の内容は少なくとも link／最終成果物の入力へ結び付ける。ソース lock の成功だけで native 成果物を再利用しない。

import library の hash は実行時 DLL や OS 全体の固定を保証しない。その境界は既存の外部接続契約として明示し、初期版に DLL 配布基盤を追加して解決しようとしない。

**確認例:** 同名 native 要求の target 別供給、同パスで `.lib` を差し替える場合、同内容を別パスへ移す場合、static／import の取り違え、論理名は別でも実 symbol が衝突する場合。

### R6. 合法な版名が物理出力パスで衝突する

**対象:** 設計 §2.1、§4.1–4.2。

PackageVersion は大小文字を区別する完全一致文字列であり、`1.0.0+ABC` と `1.0.0+abc` は別の版になる。一方、既定の出力は `bin/packages/<PackageId>/<PackageVersion>.kimipkg` で、大小文字を区別しないディレクトリでは同じファイルへ解決する。正しい二つのパッケージを順番に pack するだけで、一方を上書きし得る。

archive 内の大小文字重複を拒否する規則は、この archive 自身の出力名の衝突を防がない。論理名を直接 host 名へ写す方式には、host の命名制約との整合も必要になる。

**改善案:** 既定の保存場所を `bin/packages/<SourceId>.kimipkg` とする。SourceId は package の ID／Version を含む manifest も覆っているため、一つの内容キーで区別できる。ID／Version は manifest、一覧表示、診断にそのまま使う。

利用者が出力名を明示した場合も、既存ファイルが異なる package identity／内容なら、黙って置換せず衝突として報告する。default の内容保存は完成後に不変とし、同じ SourceId の成果物は検査して再利用する。この方式はキャッシュの保存にも適用でき、Windows 向けだけの例外的な版名制限を避けられる。

**確認例:** 大小文字だけが異なる版、同版の別内容、同内容の再 pack、異なる出力名から同じ既存ファイルへ解決する場合。

## 3. 性能改善案

### P1. 配布入力、意味計画、生成計画を分けて再利用する

SourceId は完全性、検証キーは意味計画、生成設定は生成計画を管理する。生成だけに影響する倍率・予算変更で、意味解析をやり直さない。§5.3 は ABI 確定後の情報もキャッシュできる余地を持つが、初期版は generic 設計どおり意味計画に限定し、ABI／context／frame／予算選択は現在の生成方式で作る方が単純である。

ソース byte 列や、言語版を含む条件が一致する不変の字句情報は共有できる。定義環境や条件選択に依存する Koto／Binding を別モジュールへそのまま使い回さない。同じ綴りの型や同じ layout を理由に、異なる版の nominal identity を統合しない。

**測定:** ソース不変で生成倍率だけを変更、同じソースを異なる target で検査、無関係な private 編集。字句解析・意味検証・生成を分けて所要時間と allocation を測る。

### P2. 一つの内容を一度読み、モジュールの情報表を共有する

取得した内容を immutable snapshot とし、hash、parse、pack が同じ byte 列を使う。ZIP header の自己申告ではなく実際の展開 byte 列を hash し、完了済みの snapshot の ID を使い回す。全体を連結した巨大な hash 用 buffer を作らず stream で処理する。

同じ依存が100経路に現れても、解決済みノード、宣言表、文字列・Type・Origin 表、検証結果は一組とする。各経路は整数 ID で参照し、診断時に必要な経路だけを復元する。完全な依存経路一覧を各ノードへ複製しない。

検証済み自前キャッシュの body は必要時に展開できる。ただし、未使用定義も含む必須検証の完了と必要な依存情報が確認済みであることが前提であり、body をまだ読んでいないことを検証済みの代わりにはしない。

**測定:** 同一依存を多数経路から参照する diamond／fan-in、巨大なライブラリの一部使用。読込 bytes、hash 回数、展開済み body 数、最大メモリを測る。

### P3. 再検証は「変わった内容」と「変わった結論」で段階的に伝播する

R4 の内容 fingerprint と逆依存表を使う。private body が変わったら、その body と関連する効果・保証を再検証する。公開する結果が変わらなければ、その結果だけに依存する caller へ再検証を広げない。本体を直接使う generic 生成や inline 計画は、本体変更の影響を別に受ける。

モジュール DAG と、内部の再帰関数・効果の循環を混同しない。内部の循環成分をまとめて固定点を再計算し、完了した内容を fingerprint にする。互いの hash を再帰的に定義して計算不能にしたり、循環する未完了の証明を成功と扱ったりしない。

不在への依存も同じ仕組みで管理する。探索した宣言集合を一つの依存事実として扱い、Name／access／specialization の追加を見落とさない。正しさが確認できるまでモジュール全体の失効を使う段階導入も可能である。

**測定:** 効果が変わらない private body 編集、効果が変わる編集、再帰群の一箇所変更、宣言の追加。再検証した定義数と caller 数を別々に記録する。

### P4. 初期の実行性能は共通生成で確保し、独立した機械語キャッシュは急がない

検証済みのソース依存を一つの最終 LLVM module に渡す方針を維持する。module identity と公開境界を保ちつつ、静的に確定した呼び出しは直接呼び出しにできる。cross-module の generic 計画は同じキー規則で重複排除する。

到達不能な機械語・不要 metadata の生成を減らし、既存の軽い定数伝播と共有／固定の選択を使う。ただし到達不能な宣言の必須意味検証は省略せず、恒常的な強制 inline や全型への特殊化でコード量を増やさない。R2 の製品／テスト境界も維持する。

機械語キャッシュを導入するかは、意味計画を再利用した後の LLVM 処理・link がどの程度支配的かを測ってから決める。初期に別 object の安定接続契約を増やす必要はない。

**測定:** 小さな外部関数の多数呼び出し、同一 generic の複数モジュール使用。コンパイル時間、実行時間、呼出回数、IR／native のコード量を比較する。

## 4. 改訂の記録

R1・R2 の入力確定点と所属、R3–R6 の保存・識別・native の具体規則を設計書へ反映した。P1–P3 は段階的な実装方針、P4 は共通生成と測定方針として採用した。実装・性能検証の完了を意味しない。

共通の処理順は次で足りる。

```text
依存要求を解決
  -> 不変の論理入力を確定
  -> 宣言・契約・依存事実を検証
  -> 製品の意味と生成要求を確定
  -> 必要ならテスト専用入力・生成要求を追加
  -> 現在の生成方式で出力
  -> 使用入力と完成成果物を結び付けて公開
```

pack も同じ検証器へ配布用の論理入力を渡し、restore は解決結果だけを所有する。ソース配布先行という大方針を維持し、設定・コマンド・言語コード・処理例を設計書へ追加した。generic 共有設計と Testing の接続も更新し、SPEC 本体への反映は行っていない。
