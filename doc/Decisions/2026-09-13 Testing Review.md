## 1. 評価と優先順位

`#Test`、静的 discovery、単一評価、通常の cleanup に接続した `$require`、ケースごとのプロセス隔離という骨格は維持できる。先に直したいのは、特別な規則を追加することより、境界と状態の定義を揃えることである。

| ID | 優先度 | 問題 | 改善の共通規則 |
| --- | --- | --- | --- |
| R1 | 高 | メッセージからの転送で `$require` の終了を回避できる | 診断用の式から外側への制御転送を禁止する |
| R2 | 高 | テスト専用宣言が製品コードの意味を変え得る | 製品からテストへの依存を禁止し、製品の意味を確定してからテストを追加する |
| R3 | 高 | 検証失敗の件数・診断量に上限がない | 診断全体に保存予算を設け、評価と保存を分離する |
| R4 | 中 | テスト実行期間と static 初期化・shutdown の扱いが揃わない | 1 ケースを初期化から終了までの 1 実行として扱う |
| R5 | 中 | プロセス停止後の回収や通信終了待ちに期限がない | 正常・異常を問わず、終了と回収を共通の状態遷移にする |
| R6 | 中 | 入れ子の診断で基本失敗と追加情報の対応が曖昧 | 失敗の発生ごとに一意な ID を割り当てる |

## 2. 問題点と改善策

### R1. メッセージが `$require` からの退出を上書きできる

**対象:** 初期仕様 §4.4、§5.2。

§4.4 は、条件が偽ならテスト関数から return すると定める。一方、§5.2 はメッセージ内の制御転送を優先するため、次の反例が成立する。

```kimi
group RequirementTests
    #Test
    func requirementCanBeBypassed()
        region: do
            $require(false, message: do
                exit to region
            )

        ::Core.writeLine("前提条件が偽なのに、後続処理が実行される")
```

メッセージの `do` は外側へ転送するため、正常な string 結果を持たなくても Never として適合できる。外側の `do` が転送を受け取り、その後のテスト本体へ進む。検証失敗は残るが、「残りを実行しない」という利用者向け契約は守れない。メッセージにある `continue` も同種の問題を起こす。

**改善案:** `$expect`・`$require` のメッセージに共通して、「診断用の式から、その式の外側にある制御先へ転送できない」と定める。メッセージ内のループや `do` の内部で完結する転送、呼び出した通常関数自身の return は許可する。メッセージを生成する Closure を自動生成して capture・Move を変える必要はなく、転送先の検証境界として実装する。

条件式自体は元の規則を維持する。条件の評価が完了する前の転送には、まだ真偽による検証結果がない。Abort と非終了も既存の動作を維持する。

失敗処理の順序は両操作で共通化する。

```text
条件を評価し、bool と必要な診断用の値を確保する
  ├─ 真 → 条件の cleanup → 継続
  └─ 偽 → 基本失敗を記録 → 条件の cleanup
           → 任意メッセージを評価・記録 → メッセージの cleanup
             ├─ expect  → 継続
             └─ require → 通常の関数 return
```

途中の Abort・非終了は既存どおり優先する。メッセージは診断を補うものであり、テストの分岐先を選ぶ手段にはしない。

### R2. テスト専用ソースを加えることで製品コードの Binding が変わる

**対象:** 初期仕様 §1.4、§2.2、§3.1。

現在は通常ソースとテスト専用ソースをまとめて処理する。製品側からテスト専用の関数・型を参照できないという規則はない。group の分割宣言を使うと、例えば次が可能になる。

```kimi
// 通常ソース。
group Product
    func calculate() -> i32
        return onlyInTests()
```

```kimi
// テスト専用ソース。
group Product
    func onlyInTests() -> i32
        return 42

    #Test
    func calculation()
        $expect(calculate() == 42)
```

通常ビルドでは `onlyInTests` が存在しない。テスト用ビルドでは存在するため、`kimi test` だけを使うと、製品コードの不正な依存を見逃す可能性がある。

製品が単独でもビルドできる場合も、テスト側のオーバーロード、型への追加 Field、適合宣言、特殊化、生成ソースなどが、製品の呼び出し先や配置・破棄を変える問題が残る。「通常ビルドも一度成功させる」だけではこの差を排除できない。

**改善案:** 宣言に製品用／テスト用の所属を持たせ、依存を一方向にする。

```text
製品の意味を確定する
  └─ テスト宣言を追加する
       ├─ 製品の確定済み宣言を参照できる
       └─ 製品側の Binding・型・配置・適合・初期化規則を変更できない
```

製品側の名前解決にテスト専用宣言を参加させない。テスト側から参照できる製品 API の範囲は、従来どおり可視性で決める。製品と同じ group にテストを置いても、製品側の候補集合は変えない。テスト専用ソースから製品型のレイアウトや適合を変更することは拒否する。

生成ソースも同じ所属を引き継ぐ。製品の生成処理を確定し、テスト用の生成処理がその結果を変更できないようにする。単なるファイル名判定ではなく、生成物を含む宣言の所属を共通規則にする。

これは意味上の境界であり、製品を二度フルコンパイルする要求ではない。通常／テスト間で一致が証明できる製品解析を再利用できる。テスト用設定が製品のコンパイル条件を変える場合は、条件を明示してその条件の製品解析を使い、異なる条件の成果物を流用しない。

### R3. 大量の検証失敗で親ランナーまで資源不足になる

**対象:** 初期仕様 §6.1、§7.2、§8.4。

stdout・stderr の上限はあるが、検証失敗一覧、条件値、追加メッセージ、結果イベントには同等の上限がない。

```kimi
group ReportingTests
    #Test
    func manyFailures()
        loop
            $expect(false)
```

タイムアウトまでの短時間でも、失敗を無制限に蓄積すると親ランナーのメモリや保存先を圧迫する。子プロセス隔離だけでは親側の問題を防げない。巨大なメッセージの生成や、メッセージからの入れ子の検証も同様である。

**改善案:** ケースごとと実行全体に、診断の件数・保存 byte 数の予算を持たせる。先頭の診断など所定の範囲を保存し、残りは省略件数を報告する。IPC の frame 長と未処理待ち行列にも上限を設け、単に子から親へ上限なしの列を移さない。

重要なのは、保存の省略とプログラムの評価を分けることである。

- 上限後も条件、失敗時のメッセージ、その cleanup は仕様どおり評価する。
- メッセージの副作用や Move を、保存しないという理由で飛ばさない。
- 検証失敗を成功へ戻さない。少なくとも失敗有無と省略の事実を保持する。
- 件数 counter は overflow で wrap させず、飽和と下限表示などで扱う。
- 完了・異常終了の制御情報を、詳細診断の保存予算とは別に確保する。
- 受信済み診断を保存する保証は、明示した保存範囲に対する保証として記述し直す。

ユーザーのメッセージ式そのものが大きなメモリを使うことまでは、この保存予算では制限できない。それは子プロセス側の資源利用として扱う。

### R4. ケースの有効期間と static の扱いに余分な境界がある

**対象:** 初期仕様 §3.3、§4.2。

一方では static 初期化・shutdown を検証操作の有効期間から除外し、他方ではテスト関数開始から cleanup 完了までを有効とする。static が初回アクセス時に初期化される場合、テスト本体の途中で初期化が走るため、この二つの期間が重なる。

その initializer がテスト専用ヘルパーを呼ぶと、テスト実行中なのに `$expect` を誤用とするのか、テストの失敗にするのか、明示的な優先規則が必要になる。除外を実装するには、初期化への出入りで有効ケースを退避・復元する特別な処理も必要になる。shutdown の failure はケースへ帰属するのに、同じ期間のテスト専用ヘルパーによる検証だけを誤用とするのも分かりにくい。

**改善案:** 子プロセスが選択する 1 ケースを、ユーザーコードの初期化から shutdown までの共通した帰属先にする。

```text
親がケースを割り当てる
  → 報告用の最小 runtime を準備する
  → ユーザー初期化 / テスト本体 / cleanup / shutdown
  → 完了を報告する
  → 終了を親が確認する
```

有効期間中に許可されたテスト用 `$expect` は、すべて同じケースへ記録する。phase を診断に付ければ、初期化・本体・終了処理のどこで失敗したかを区別できる。必要になる前に static を先行初期化する変更はしない。

製品コードで `$expect` を使用できないという静的規則と、`$require` はテスト関数自身からの return に限る規則は維持する。報告用 runtime 自身の初期化失敗は親が起動・実行エラーとして扱う。

### R5. タイムアウト後の回収と通信終了待ちが無期限になり得る

**対象:** 初期仕様 §7.2、§7.4、§8.3。

現在は期限超過時にプロセスを終了し、その終了を確認してから資源を解放するが、終了確認や通信の読み取り完了を待つ時間の上限がない。テストが作った別プロセスにパイプの書き込み口が残ると、テスト本体のプロセスが終了しても EOF を待ち続ける設計になり得る。

異常終了時だけでなく、正常完了したケースが子孫プロセスを残す場合も共通の問題である。後始末の期限に関する規則がなければ、ケースの制限時間が親の終了を保証しない。

**改善案:** ケース単位でプロセス群・通信路・一時領域を管理し、終了理由によらず同じ回収処理へ入る。

```text
起動・実行
  → 正常終了 / 異常終了 / 期限超過 / 中断
  → 有限の猶予でプロセス群を回収し、報告を読み取る
  → 成功条件が揃えば結果確定
  → 揃わなければ回収・通信エラーとして結果確定
```

実行の期限と、停止・回収の猶予を分ける。起動時点から OS が提供する管理単位へ収容し、後から PID を列挙するだけの競合しやすい方法に依存しない。具体的な OS API は実装時に選ぶ。

猶予内に回収できなかった場合は、残存プロセス・未回収資源を報告し、成功扱いをしない。未終了プロセスが使っている一時領域を正常に回収できたと報告してはならない。管理可能な範囲の限界は保持し、任意の外部プロセスまで隔離できるとは約束しない。

### R6. 基本失敗と追加情報を結ぶ ID が不足している

**対象:** 初期仕様 §4.3、§5.2、§8.3–8.4。

基本の失敗を先に記録し、cleanup とメッセージ評価を後から行うため、その間に別の `$expect` が発火できる。

```kimi
// テスト専用ソース。
group DiagnosticTests
    func detail() -> string
        $expect(false, message: "メッセージ生成中の失敗")
        return "外側の失敗の説明"

    #Test
    func nestedDiagnostics()
        $expect(false, message: detail())
```

報告順は「外側の基本失敗 → 内側の基本失敗 → 内側の詳細 → 外側の詳細」となり得る。「最後に起きた失敗へ詳細を追加する」方式では取り違える。ケース ID だけでは足りず、同じソース位置が再帰・ループで繰り返された場合は位置 ID だけでも足りない。

**改善案:** 失敗の発生ごとにケース内で一意な `IssueId` を採番する。基本失敗・値・追加メッセージは同じ `IssueId` を持つ。ソース位置など静的情報を表す `SiteId` とは分ける。

```text
CaseId
  ├─ IssueId 1 → SiteId A → 外側の基本失敗 / 外側の詳細
  └─ IssueId 2 → SiteId B → 内側の基本失敗 / 内側の詳細
```

一時的な ID は整数で十分であり、検証のたびに UUID やヒープオブジェクトを作る必要はない。詳細が Abort 等で到着しなくても、基本失敗は未完の診断として保持する。R3 の省略規則とも組み合わせる。

## 3. 性能改善案

### 3.1 成功時の処理を最小化する

`$expect` と `$require` を同じ検証処理から lowering し、失敗後の継続先だけを変える。成功時は条件評価と必要な分岐を中心とし、イベント送信、文字列生成、失敗レコード生成を行わない。副作用のない恒真条件は、通常の最適化で検証の処理自体を除去できる。

値表示は、元の式の評価時点で既に得られた scalar の値を使う。cleanup や右辺の副作用の後で元の変数を読み直さない。元の言語上の Copy・Move を追加しない規則と、compiler 内部で scalar のビット列を一時保存することは区別する。すべての中間値を無条件に保存すると register 圧迫が増えるため、最初は外側の比較の左右など、範囲を限定する。

### 3.2 静的情報は一度だけ保存し、失敗時は小さなイベントを送る

式の文字列・ファイル位置・型の表示名は静的テーブルへまとめる。子は `SiteId`、`IssueId`、必要な scalar 値と状態を送り、人間向け整形は親で行う。大きな文字列を毎回構築・再送しない。

基本失敗は、メッセージや cleanup が Abort しても残せるよう、後続ユーザー処理の前に独立した報告として送る。単に終了時まで全件をバッファする最適化は避ける。失敗時の診断用通信が必要であることと、成功時には通信しないことを両立させる。

R3 の保存予算と R6 の ID により、bounded buffer で処理できる。親が読み取れない・通信路が壊れた場合の待機も、R5 の有限な終了処理と接続する。

### 3.3 製品の解析結果と全テストの実行ファイルを再利用する

R2 の製品／テスト境界を使い、ソース・生成結果・コンパイル条件が同じ製品の解析を再利用する。キャッシュの一致確認を省いて共有するという意味ではない。

フィルターは、検証済み一覧から実行ケースを選ぶ操作にする。フィルター変更だけで再リンクしなくて済むよう、初期版では全ケースを含む同じ実行ファイルを再利用する。フィルター対象外のコンパイルエラーを隠す変更はしない。実行時のケース ID 選択は静的な分岐やテーブルで行える。

`--list` は検証済みの宣言・discovery 情報を利用し、codegen・リンク・子プロセス起動を必要としない経路を持たせる。構造化された一覧とケース ID による厳密な選択を初期から追加すると、IDE が名前の部分一致で余計なケースを実行することも避けられる。

### 3.4 プロセス隔離を維持したまま固定費を減らす

短いテストでは、本体よりプロセス起動・初期化・通信準備・回収の時間が支配的になり得る。目安は次の関係になる。

```text
1 ケースの時間 ≈ 起動 + 初期化 + 本体 + cleanup / shutdown + 回収
全体時間       ≈ ビルド + スケジューリングされた各ケースの所要時間
```

並列数を増やすとメモリ・I/O の競合も増えるため、単純に CPU 数まで増やせば速くなるとは限らない。

親側の実行枠、読み取り buffer、静的テーブル、解析結果を再利用する。実行ファイルはビルド後の不変な snapshot として扱い、ケースごとのコピーや再検証を必要以上に繰り返さない。ケース ID とともに成果物の識別情報も照合し、同じ ID を持つ古い実行ファイルの結果を混ぜない。

worker プロセスの再利用は static 状態・FFI の状態・初期化回数を変えるため、透明な最適化にはしない。将来導入する場合は、別の隔離モードとして明示する。まず「何もしない多数のケース」「短い演算」「I/O を含むケース」「大量失敗」の各負荷で、実行時間・親子のメモリ・通信量・生成コード量を測定する。

## 4. 推奨する整理

改善後の基礎は次の四つに集約できる。

1. **製品とテストの依存は一方向。** テストの追加で製品の意味を変えない。
2. **検証は共通の条件評価・失敗記録で扱う。** expect と require は失敗後の継続先だけが異なる。
3. **ケースは初期化から回収までの 1 実行。** 診断の所属と終了判定を同じ単位に揃える。
4. **診断の評価と保存は分離する。** 評価の意味を維持し、保存・通信・回収は有限にする。

まず R1–R3 を直し、R4–R6 と通信の具体化を揃えてから実装することを勧める。例外機構、共有 fixture、同一プロセス内並列実行を追加しなくても、これらの問題は解決できる。
