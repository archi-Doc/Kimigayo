# 分岐本体の構文と match の網羅性

## Decision

`if` と `match` の分岐本体について、次の2点を採用する。

- `=>` は式本体専用とし、ブロック本体には付けない。式本体は式の値を結果にし、インデントされたブロック本体は結果を渡す場合に `yield` を使う。
- `match` は常に網羅性を必須とする。本体形式、評価コンテキスト、結果の型、`yield` の有無による例外を設けない。

```kimi
// 式本体
let result = match flag
    true => 1
    false => 2

// ブロック本体：結果を使わない処理
match message@ref
    .Write(let text)
        inspect(text)
    _
        ()
```

`=>` の用途の制限は分岐本体の構文に関するものであり、名前付き Origin 引数など、他の構文での使用は変更しない。

## Context

従来は `if` のブロック本体に `=>` を付けず、`match` のアームには本体形式によらず `=>` を必要としていた。

`match` では `=>` の後の式を次の行へ移すとブロック本体になり、式の値が捨てられる。さらに、結果を使わず、全アームがブロック本体で、自身を対象とする `yield` がない場合には、網羅性が不要になった。整形に見える変更が、結果の扱いと処理漏れの検査を変えていた。

SPEC.md §14.7.1／§14.8 は、この意味変化を通常の整形として行わないようフォーマッタに要求していた。

## Alternatives

1. **現状維持**：従来の構文と条件付きの網羅性要求を維持する。
2. **構文のみ統一**：`=>` を式本体専用にするが、網羅性要求の条件は維持する。
3. **網羅性のみ必須化**：すべての `match` に網羅性を要求するが、本体構文は維持する。
4. **両方を変更（採用）**：本体構文を統一し、すべての `match` に網羅性を要求する。

## Pros / Cons

| 候補 | Pros | Cons |
| --- | --- | --- |
| 現状維持 | 既存コードの移行が不要。部分的な処理を短く書ける。 | 改行で値の扱いと網羅性要求が変わり、構文の非対称性も残る。 |
| 構文のみ統一 | `=>` の有無で本体形式を識別でき、`if` と書き方がそろう。 | 本体形式などによって網羅性要求が変わる規則は残る。 |
| 網羅性のみ必須化 | 処理漏れの検査が本体形式に依存しない。 | 改行による値の破棄と、`if`／`match` の構文の非対称性は残る。 |
| 両方を変更 | 本体形式を明示し、網羅性要求を本体形式から独立させられる。 | 既存のブロックアームの移行と、部分的な処理への既定アーム追加が必要。 |

## Rationale

分岐本体の表記は値の扱いを明示し、網羅性検査は処理漏れを検出する役割に集中させる。両者を分離することで、構文の一貫性と検査の予測可能性を確保できる。

対象外のケースを無視する意図は `_` アームで明示する。記述量の少なさよりも、意図が読み取れ、整形で検査条件が変わらないことを優先する。

## Consequences

- §14.7.1／§14.8と付録F.5の文法・例を更新し、`match` のブロック本体から `=>` を除く。
- ガードの終端を `=>` だけに依存させず、ブロック本体の開始との境界を定義する。改行・インデント規則も整合させる。
- 網羅性と結果要求を分離する。全 `match` を Result-requiring にするわけではなく、結果を使わない全ブロック形式の処理には、従来どおり `yield ()` を要求しない。
- 非網羅的な `match` はエラーとする。何もしない既定処理は、ブロック形式の `_` アームに `()` を書く。`_ => ()` を追加すると既存の式本体の規則により結果要求が生じるため、機械的に置換しない。
- §14.9の制御フロー、§15.1.6の破棄規則、付録A.10の検証項目から、許可された非網羅的 `match` の不一致終了経路を除く。対象の取得・Move・借用・破棄の基本規則は維持する。
- ガード付きアームが網羅性に寄与しない規則と、既存の限定的な網羅性の証明規則は維持する。`if` の最終 `else` の要求条件も変更しない。
- Parser、網羅性検査、制御フロー解析、テスト、関連する実装状況の文書を追随させる。

`=>` の直後で式の開始を次の行へ折り返せるかは、本決定では確定しない。許可する場合も式本体として扱い、ブロック本体への再解釈は認めない。
