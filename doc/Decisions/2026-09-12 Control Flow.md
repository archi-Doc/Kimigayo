# Control Flow — 制御フローの統一

## Decision

Kimigayoの制御フローは、[Control flow.md](../Design/Control%20flow.md)を本案として採用する。詳細な規則と例は同文書に定め、本記録は決定の要点と理由を示す。

| 論点 | 決定 |
| --- | --- |
| 式と文 | if・match・for・while・loop・block・制御転送を式、unsafe・defer・requireを文とする。文は値の位置に置かない |
| 共通Body | `=>` の右に式または文を1個置く単一本体と、改行＋インデント本体の2形式に統一する。関数・アクセサー・init・deinitなどにも適用する |
| 本体の結果 | 単一本体の値は所属構文と使用位置で使うか捨てるかを決める。インデント本体の末尾式は捨て、末尾到達はUnitとする。反復本体の完了は次の反復へ進む |
| 結果型 | 構造上のすべての結果源を型制約に使い、到達不能な明示転送も検査する。その場で捨てる値同士は型をそろえない。結果を捨てるif・match・block・loopの対象結果型はUnitとし、明示転送の値も適合させる |
| 静的解析 | 構造的完了と実行到達性は、条件値やPattern包含で経路を除外しない共通規則を使う。前者は暗黙Unit・Never、後者は初期化・Move・Loan・絞り込み・後始末・requireの非継続を扱う。到達不能コードは型検査用の継続で検査する |
| 選択 | matchは常に網羅的とし、証明には既存の限定的な規則を使う。ifのelse省略は `else => ()` と等価とする |
| 転送 | 対象を先に決め、不適切でも外側へ探し直さない。ラベルなしyieldは最も近いif・matchを指し、それがDiscard Contextならエラー。名前付きの値は `exit to label: value`・`yield to label: value` と書く。blockは予約語とし、ラベルは任意とする |
| 関数と推論 | 名前付き関数の戻り型省略はUnit。単一本体の扱いは検査前に確定し、総称引数の具体化後に再解釈しない。入れ子の期待型伝播をリテラルの既定型確定より先に処理し、既に確定した型やオーバーロード選択はやり直さない |
| 文と後始末 | unsafeはその場の許可、deferは直近のスコープへの終了処理の登録、requireは失敗時の正常な後続を禁止する。転送の値は先に確保してから後始末する。条件のbool結果も先に確保し、条件の一時値を破棄してから分岐する |

```kimi
func direct() -> i32 => compute()

func indented() -> i32
    return compute()

let value = choice: if ready
    if cached() => yield to choice: cachedValue()
    yield compute()
else => 0

defer => cleanup()
require valid else => return
```

例は独立した断片とする。単一本体とインデント本体は意味が異なるため、フォーマッタは形式を維持し、相互変換は意味を検査するリファクタリング操作とする。

## Context

構文ごとに本体形式や結果の扱いが異なり、改行・本体形式・使用位置によって、値の破棄やmatchの網羅性要求が変わっていた。到達する結果だけを推論に使う案では、条件や制御経路の解析が型制約の選択にも影響していた。

また、捨てる分岐の型をそろえる規則は、値を返す副作用目的のAPIを使いにくくした。暗黙の転送先、ラベルと値の区切り、条件の一時値の寿命にも、読み手が判断しにくい点があった。

必要なのは、例外の追加ではなく、本体・値の使用・型・制御経路・後始末の役割を分け、共通規則で説明できる設計である。

## Alternatives

以下は、論点ごとに検討した代替案であり、全体案として互いに排他的なものではない。

- **A：従来の本体構文を維持する。** 構文ごとの記法と結果規則を残す。
- **B：インデント本体の末尾式を暗黙の結果にする。** return・yield・exitの記述を減らす。
- **C：到達する結果だけで型を推論する。** 到達不能な結果は推論から除き、別途検査する。
- **D：boolリテラルで静的な経路を除外する。** `while true` などを無条件反復として扱う。
- **E：捨てる分岐も共通型へそろえる。** 使用位置によらず結果型を統一する。
- **F：matchの網羅性を条件付きにする。** 本体形式や結果の使用に応じて省略を認める。
- **G：転送先やラベルの解釈を文脈で補う。** yieldの対象を外側へ探し直す案、値とラベルを区切らない記法、blockを文脈キーワードにする案を含む。
- **H：匿名関数の値の破棄に特別な適合規則を設ける。** 本体を調べて候補に順位を付ける案、宣言に直接書いたUnitだけを破棄の対象にする案を含む。

## Pros / Cons

| 候補 | Pros — 長所 | Cons — 短所 |
| --- | --- | --- |
| 本案 | 本体・結果・転送・後始末を共通規則で説明できる。型制約の収集を到達可能性による選別から分離できる | 明示転送や型注釈が増える場合がある。到達不能コードも検査し、保守的な経路を残すため、実行上は問題ないコードも拒否する |
| A：従来構文 | 移行が少ない | 構文ごとの非対称性と、本体形式に伴う意味の違いを個別に覚える必要がある |
| B：末尾式を結果にする | 値を返す処理を短く書ける | 末尾への処理追加で結果が変わり、副作用のための式と結果の式が区別しにくい |
| C：到達する結果だけを推論 | 実際に返りうる値を中心に型を決められる | 型制約の収集と経路解析が結び付き、到達不能な結果の扱いも別に必要になる |
| D：リテラルで経路を除外 | `while true` や一時的な `if false` を扱いやすい | 条件値を参照する規則が必要。解析間で扱いをそろえるか、差を説明する負担が生じる |
| E：捨てる分岐も型を統一 | 使用位置による違いが減る | 値を返す副作用目的の呼出しが、別分岐のUnitなどと不一致になる |
| F：条件付きの網羅性 | 部分的な処理を短く書ける | 本体形式や使用位置の変更で処理漏れの検査が変わる |
| G：文脈による補完 | ラベルや括弧などを省略できる | 構文の移動や入れ子で転送先が変わりやすい。区切りのない値が呼出し・添字・減算に見える |
| H：匿名関数への特別規則 | 注釈を減らしたり、直接書いたUnitの扱いを明確にしたりできる | 本体による候補選択は既存の推論境界と整合せず、Unitの由来による区別は同じ型に別の扱いを持ち込む |

## Rationale

短さより、構文を読んだときに結果と転送先を予測できることを優先した。単一本体は短い処理を表し、インデント本体は処理列を表す。値を使う位置と捨てる位置を分けることで、副作用目的の呼出しを許しつつ、明示した結果は型検査できる。

結果源の収集、構造的完了、実行到達性、型検査用の継続は、それぞれ別の役割を担う。型の絞り込みなどのフロー情報は必要な箇所で使いながら、実行到達性を理由に結果源や型制約を取り除かない。推論順や最適化設定で受理結果を変えず、既存のオーバーロード解決の境界も維持する。

matchの網羅性、転送対象を探し直さない規則、条件評価と後始末の共通順序により、処理漏れ・誤転送・寿命の判断を個別の構文例外へ依存させない。

## Consequences

- [本案§6.2](../Design/Control%20flow.md#62-specmdとの対応)に従い、SPEC.md、Parser、型推論、制御フロー・所有権解析、診断、フォーマッタ、関連テストを追随させる。本記録は実装完了を意味しない。
- [先行決定](2026-09-11%20Branch%20Body%20Syntax%20and%20Match%20Exhaustiveness.md)のうち、本体形式・結果規則・ifのelse要求・折り返しの扱いは本決定で更新する。matchを常に網羅的とする方針は維持する。
- 本体用コロンや旧転送記法を移行し、予約語blockを識別子として使う箇所を改名する。末尾式を結果にしていたコードには、必要な明示転送を追加する。
- 無条件反復にはloop、静的検査からの除外には `#if` を使う。到達不能な明示転送も型不一致を起こしうる。未確定の呼出し・匿名関数には注釈が必要になる場合がある。
- 非網羅的なmatchには明示的な補完が必要になる。Case追加の検出を保つ場合はCaseごとの補完を使い、Tupleなどの限定的な網羅性証明では入れ子のmatchを検討する。
- 条件の一時値は分岐前に破棄するため、本体まで保持したい値は外に保存する。deferの登録先スコープ、転送値の確保、逆順の後始末も移行時に確認する。
- 意図しないUnit推論や作用のない値の破棄は警告で案内する。警告で型・実行結果・オーバーロード選択を変えない。区切り範囲・本体スコープ・転送対象・探索境界は別の概念として実装・説明する。
